# 窗口只用了不到 6%，工具结果却被砍掉三分之一：按长度截 JSON 会整段删掉后面的证据，代价先是多干活，再是答错

你有没有过这种体验：agent 某一类任务就是做不好，你翻日志，看到上下文才用了几万 token，离窗口上限远着呢，于是认定「不是上下文的问题，是模型推理不行」，或者「这类任务本来就难」。然后你开始调 prompt、换模型、加 skill。

**但你看的日志，记录的是 harness 交给模型的东西，不是工具真正产出的东西。** 两者之间如果丢了数据，日志里永远看不出来。

加拿大 Brock 大学和渥太华大学的这篇 **Context Is a Pipeline, Not a Window: Information Attrition in LLM Agent Harnesses**（arXiv:2610.36114）就是在自家一个真实 agent 里抓到了这件事：一个读 Linux 内核 trace 找故障根因的 agent，720 次运行里最大的一次 prompt 只用了窗口的 5.75%，可三分之一的工具结果在送到模型之前就被截断了，而且每一个被截断的结果都变成了坏掉的 JSON。看完我的感受：**这篇最有价值的不是那个 bug，而是它把「上下文」从一个容量问题改写成了一条管道上的损耗问题，并且老老实实地把「损耗是不是导致答错」这件事做成了预注册的对照实验，结果还推翻了作者自己的预测。**

## 核心摘要

作者把 agent 的上下文建模为五段管道：工具产出到送达模型（S1）、送达到行动（S2）、行动到保留（S3）、保留到移交（S4）、移交到持久化（S5），每段都可能丢信息。在一个读内核 trace 做故障诊断的 agent 上，S1 的实测问题是：harness 用固定长度对序列化后的 JSON 做前缀截断，720 次运行、11,189 个工具结果中有 3,827 个被截，全部变成无效 JSON；由于 JSON 键顺序固定，前缀截断不是均匀缩短，而是整段删掉靠后的字段：同一个结果里，一个字段只在 742 次调用中的 4.7% 送达模型，另一个字段送达了 99.3%。哪个字段装着故障证据，取决于故障进程是在 trace 期间新起的（证据在前面那个列表）还是早就在运行（证据在后面那个列表），而诊断准确率正好沿这条线分裂：新起进程的故障 60 次里对 40 到 55 次，常驻容器的故障对 0 到 24 次。作者回放了 864 个真实工具结果，在一条生产规模的 trace 上，出厂截断把故障证据所在列表的 128 条记录全部删光。随后的预注册对照实验（145 次运行）发现：当 agent 有第二条路径能找到答案时，截断并不让它答错，而是让它多干活：工具调用从 53 次涨到 68 再到 76 次，计算次数从 18 涨到 32 再到 36，产出率（记录的发现数除以执行的计算数）从 0.61 掉到 0.34 和 0.31。对七个 agent 框架的源码调研发现，langchain-core 和 smolagents 也按位置截断工具输出。作者坦白：截断是否真的导致了现场的准确率分裂，仍未定论。

## 🎯 为什么这件事值得写

关于 agent 上下文，主流研究在问三类问题：窗口有多大、模型在窗口里怎么分配注意力、怎么用记忆把窗口扩出去。关于 harness，很多工作把包裹模型的代码当成次要细节。最近两篇源码研究读了 11 个和 13 个生产级 harness，但都没测数据在里面发生了什么。失败分类学给成千上万次运行贴标签，但标签不是损耗测量。

作者点出的共同盲区只有一句话：**运行日志记录的是工具交付了什么，不是工具产出了什么。在进日志之前就丢掉的东西，日志里找不到。**

这件事和我们 repo 里最近几篇高度相关。SkipTheCompressor 发现压缩器删掉的恰好是要改的那一行；CacheEngineering 讨论压缩上下文其实在烧重算；CarryOn 主张别压缩对话历史，让文件和状态本身当进度载体。Byron 前几天标了想看更多的 pi-protokoll，主张用代码组装的分层协议块做压缩，而不是让 LLM 自由摘要。这篇论文给了这条路线一个很硬的反面证据：**最原始的「截断」都会按位置而不是按价值丢数据，而且丢得悄无声息。**

## 🏗️ 机制：五段管道，各自怎么坏

一次诊断运行的路径是：agent 调工具（比如列出容器），工具返回结果（产出）；harness 把结果转成文本、塞进预算（送达）；agent 把调查拆给多个 worker，每个 worker 有自己的工具调用轮数上限，逐轮行动（行动）；每个 worker 只保留一定长度的历史，旧轮次被丢弃（保留）；worker 算出的东西必须交给写最终结论的环节，否则等于没算（移交）；下一次运行不继承任何东西（持久化）。

| 边界 | 现场测得的问题 |
| --- | --- |
| S1 产出 → 送达 | 720 次评测：前缀截断，34% 的结果被截且全部损坏；一个字段送达 4.7%，另一个 99.3% |
| S2 送达 → 行动 | 554 个 worker 的一次批量运行：步数预算是一堵墙，51% 的 worker 恰好停在上限 |
| S3 行动 → 保留 | 一次前后对比：保留长度从 80k 字符提到 150k，总 token 从 303k 涨到 545k |
| S4 保留 → 移交 | 同一批 554 个 worker：移交是自愿的，98 个 worker 什么都没交，沉默被读成「什么也没找到」 |
| S5 移交 → 持久化 | 设计如此，未测：为保持运行独立，什么都不留 |

五段坏法不同：S1 和 S4 是**直接销毁证据**；S2 不销毁，而是让一部分工作根本没发生；S3 也不销毁，只是重复发送不必要的历史，让运行更贵；S5 是刻意关掉的。作者仍把它们放在一条管道里，因为它们的共同点是：**每一段都是 harness 在决定什么能活到下一步。**

**为什么前缀截断特别坏。** 如果结果的键顺序固定、截断是前缀切片，那么一个字段能不能存活只取决于它在文本里的位置。没有任何理由认为靠后的字段不重要，而模型本来就对窗口内的位置注意不均匀；harness 让情况更糟：被截掉的字段不是「注意得少」，而是在注意力有机会看到它之前就没了。

**测量方法。** 作者提议在各边界上插桩，和准确率一起报告每一段存活了多少证据。S1 的单位是工具结果的顶层字段，内容出现在模型收到的文本里就算送达（JSON 是否还能解析单独报告）；S4 的单位是一条记录的发现或一次捕获的计算，到达做决定的环节才算移交。汇总指标是**产出率**：

$$\text{yield} = \frac{\text{记录的发现数}}{\text{执行的计算数}}$$

这是「到达决策的工作」的一个窄而可测的代理，不衡量相关性。

## 🧪 关键证据

**1. 现场数据。** 720 次运行里最大的单个 prompt 是 23k token，窗口 400k，占 5.75%。11,189 个工具结果里 3,827 个被截，全部损坏。被截结果中，一个字段在 742 次调用里只送达 4.7%，同一批结果里的另一个字段送达 99.3%。在两个测试应用上，起新进程的故障 60 次里对 40 到 55 次，常驻容器里的故障只对 0 到 24 次。作者坦白：他们以前以为这个差距是内核 trace 本身能看到的东西有限，送达数字说明自己的 harness 至少要负一部分责任。

这里的准确率来自严格评分器：只有在答案字段里点名正确容器才算对。作者之前用过一个宽松评分器，只要顺带提到就算对，后来发现问题换掉了。

**2. 回放。** 每次工具调用，transcript 里同时存了完整结果和实际发给模型的文本，所以可以离线回放。31 次运行里的 864 个结果，过一遍出厂的前缀截断和修好的「按行截断」：超预算的结果在前缀截断下每一个都坏，在按行截断下一个都不坏。超预算的都是「列东西」的工具：50% 的进程列表调用坏了，agent 自己的分析输出坏了 43%，小摘要只坏了 1%。**全部调用里只有 2.5% 受影响**，这正是它能躲过检查的原因：大多数调用风平浪静，偏偏在关键的那几次致命。

**3. 生产规模回放。** 一个真实的 21 容器部署，其中一个服务被 CPU 限流。故障源是「安静」的那种：trace 开始前就在跑，agent 没有第二条独立路径发现它；它是五个 Java 容器之一，每个都占约 1.4% 的内核事件，体量上也不突出。这条 trace 的列表结果有 33,370 个字符，是出厂预算 6,000 字符的 5.6 倍，作者没调任何参数。出厂截断送达了前一个列表 118 条里的 30 条，后一个列表 128 条里的 **0 条**，并且整个 payload 已经坏了。**在真实部署数据、真实预算下，故障源的整类证据在模型看到之前就消失了。**

**4. 框架调研。** 作者检查了七个框架当前版本的工具输出截断代码（langchain-core 1.6.12、langchain 1.4.6、smolagents 1.26.0、openai-agents 0.24.0、autogen-agentchat 0.7.5、pyautogen 0.10.0、crewai 0.11.2）：

- 两个通用截断器，都按位置切：**langchain-core 把序列化后的工具输出切到 500 字符，只留开头；smolagents 对超过 20k 字符的观察删掉中间。** 都不看被切内容的结构。
- 三个框架根本不截工具输出，这只是把同样的损耗推到了后面的窗口里。
- 一个框架只截自己的追踪数据。
- 唯一一个结构感知的截断器，是一个 shell 中间件，按整行切并且会明说。**安全模式是存在的，只是不是默认。**

**5. 预注册对照实验。** 现场数据只能说明送达和准确率一起动，而且有混杂：修送达那次还顺手上线了两个新分析工具。所以作者把每个缺陷单独放回去，固定 agent、工具、任务和模型（温度 0），每一波运行前先写下预测，计划的每次改动都带日期和理由记在随附文件里。两类故障：spawned（故障进程在 trace 中途启动）和 resident（早就在跑），健康 trace 作阴性对照。每类故障 5 条录制、重复 3 次，配置间配对，共 145 次运行，没有失败的运行。

| 配置 | 正确 | 调用次数 | 每次运行被截 | 计算次数 | 产出率 | 输入 token |
| --- | --- | --- | --- | --- | --- | --- |
| 修复版 | 14/15 | 53 | 0 | 18 | 0.61 | （567k） |
| S1 缺陷 | 15/15 | 68 | 27 | 32 | 0.34 | +5% |
| S1 缺陷加键序反转 | 15/15 | 76 | 30 | 36 | 0.31 | +14% |
| 仅键序反转（不截） | 10/10 | 48 | 0 | 16 | 0.61 | −12% |

（以上是 spawned 类故障各配置 15 次运行的中位数，仅键序反转那一组是 10 次。）

窗口从来不是瓶颈：一次运行的中位输入是 567k token、53 次调用，约每次 10k，只占 400k 窗口的 2.5%。在缺陷下，agent 每次运行中位丢了 27 个结果，占调用的 40%，每个都坏了，但它依然在 15/15 次里点对了故障进程，修复版是 14/15，这个差异在这个样本量下是噪声。**变的是工作量**：调用从 53 到 68 再到 76，分别涨 28% 和 43%；计算从 18 到 32 到 36，约翻倍；输入 token 涨 5% 和 14%。产出率掉到 0.34 和 0.31，是因为 agent 做了更多计算却没找到更多东西，发现数始终是 11 个。仅反转键序的对照组产出率回到 0.61，说明产出率测的是真实效应，不是重排本身。

**6. 生产规模的重复回放。** 修好送达（结果永不在记录中间被截）和步数预算（给 worker 更多轮）之后，同一 trace、同一 prompt 两种条件重跑：修复版 6 次里 3 次点对被限流的服务，0 个坏 payload；S1 缺陷版 5 次里 0 次点对，每次运行都有 10 到 14 个坏 payload。数据销毁这一半结果在生产规模下毫无例外地复现；准确率这一半方向一致但噪声更大，修复版 6 次里还有 3 次错，原因和数据损耗无关。作者的定性是：**这是对机制的直接重复复现，不是「截断单独驱动了现场准确率分裂」的证明。**

诚实泼冷水：

- **一个 harness、一个领域、一个模型。** 论文没有说诊断 agent 用的是哪个模型，只说温度 0。作者论证缺陷类别具有一般性，理由是管道本身不可避免，以及七个框架里有两个用同样方式截断。
- **缺陷是作者自己写的**，对照实验是在预注册预测下重新引入它，不是修复叙事。
- **每类故障 5 条录制、配对重复**，不是 5 个独立的故障实例；实验预算按较小的 trace 缩放过，只有生产规模回放保留了出厂预算。
- 现场准确率分裂的因果性仍是**相关而非因果**。

## 🔬 最有意思的部分

**第一，作者自己的预测被推翻了，替代它的规则更尖锐。** 他们预测：把键顺序反转，故障源所在列表就会从全送达变成全删除，准确率应该下降。操纵是成功的，transcript 显示每个列表 payload 里都没有故障源，可 agent 仍然 15/15 点对了。它换了一条路：这个故障源是 trace 里最吵的进程，占 14.0% 的内核事件，在 agent 自己构建的每张排序表里都排在前几行，而前几行恰好是截断后存活的部分。于是规则变成：

> **截断只在 agent 没有第二条路径通往答案时才伤害准确率，而且它的代价先表现为额外工作，再表现为错误。**

吵闹的故障源能扛住任何单一路径的丢失；一个只活在某一个字段里的安静故障源，比如现场数据里那个只送达 4.7% 的常驻故障，就没有第二条路。

**第二，为什么没人注意到：三个遮蔽因素。** 一是**几乎不费时间**：在两个生产 coding agent 的 10 次不设上限运行里，等模型占了中位 84% 的墙钟时间（范围 80% 到 91%），团队盯着的延迟指标几乎感觉不到这个缺陷对正确性和 token 的影响。二是**容量看起来很好**：窗口几乎没用，没有任何迹象表明上游在丢证据。三是**常见补救会掩盖症状**：给 agent 一份书面流程，得出的结论和自由探索一样，只用 35% 的 token。团队感到上下文压力，加了结构，看到改善，就不再往这里看了。作者的评价很精辟：**这是用错误理由做对了的修复，它减少了需要送达的证据，而不是把证据送达得更好。**

**第三，评分器自己也差点骗了作者。** 第一版评分器只要提到就算对，把其中一组的得分从 2/15 抬到 14/15，作者在审计到第 46 次运行时发现并换掉了。这一段放在论文里很诚实，也很有警示意义：**测量管道本身也是一条会丢信息、也会造信息的管道。**

## 🤔 我的判断

**定位：harness 上下文工程的测量基础设施论文，外加一个干净的单点因果实验。** 不提出新方法，修复手段（按行截断、分页取回）都很朴素，贡献在于把「上下文」从窗口容量改写为管道损耗，并给出逐段可数的单位和一个产出率指标。

亮点：

1. **把盲区说清楚了：日志记的是交付，不是产出。** 只要 harness 在写日志之前截断，任何事后分析都看不见丢失。解决方法也简单：transcript 里同时存完整结果和实际发给模型的文本。
2. **预注册加对照，且敢于报告被推翻的预测。** 「代价先是多干活再是答错」这个结论，比「截断导致答错」更有用，因为它告诉你应该去看哪个指标。
3. **跨框架调研给了可行动的结论。** langchain-core 默认切 500 字符只留开头、smolagents 删中间，这对所有在用这两个框架的人都是一个立刻可以检查的点。

问题与局限：

- 单一 harness、单一领域、未指明的单一模型，样本小，准确率因果仍未确立。
- 产出率只衡量「计算有没有变成发现」，不衡量发现是否相关；作者自己也承认相关性需要真值，留作未来工作。
- 分页取回机制在实验里一次都没触发，所以「按需翻页」这种更主动的修法有没有效，还没有数据。

对工程的直接启发：

- **在 harness 里同时存「工具产出」和「送达文本」两份。** 没有这个，任何截断、压缩、摘要造成的损耗都无从测量。
- **永远不要对序列化后的 JSON 做前缀切片。** 改成按记录或按行截断，并在结果里明说截掉了多少；必要时提供分页取回。能做到结构感知就别用字符长度。
- **把逐段损耗当成和准确率并列的指标报告。** 两个准确率相同的 harness，产出率和 token 可能差一倍；作者也建议检验同准确率 harness 的产出率差异能否预测更难任务上的表现。
- **把这些检查放进不调用模型的 CI。** 作者指出表里每一种失败都是机械的：结果被截坏、步数预算撞墙、算出来的结果没移交，都可以写成测试。这和「harness-as-repo 加 eval 门禁」的思路完全一致，而且比 LLM 裁判便宜得多。
- **压缩和裁剪的设计，按结构和协议来，不按长度来。** 这也是 pi-protokoll 那类代码组装分层协议块的理由：可控的压缩至少知道自己删了什么。
- **当你发现「给个书面流程就好了」时，回头查一下上游有没有在丢证据。** 流程减少了对证据的需求，不代表证据送达没问题。

一句话收束：**agent 读到的从来不是工具的输出，而是 harness 愿意给它看的那部分；窗口空着，不代表证据都到了。**
