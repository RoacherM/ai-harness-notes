# 别按任务分 harness，按能力分：一棵能力树管 46 个基准，没见过的 18 个也涨了 22 点

你有没有过这种体验：给 agent 调好了一套做 ARC 的脚手架，换去做迷宫就不灵了；于是你又给迷宫单独调一套，再给棋类调一套，最后手里攒了十几套 harness，每套都只在自己那块地上好用，新来一个任务还得先猜它像哪一套。

这几周我们归档的 harness 自进化论文（RRSI、SelfEvolvingHarness、RiseHarness、CoEvo-RSI、RSIHub）大多默认一个前提：**进化单位是任务或任务族**。这在 coding、数学这种需求相近的场景里没问题，一旦任务跨了模态、跨了形式，要么一套全局 harness 顾此失彼，要么每个任务一套导致过拟合。

Inf Rec、新加坡国立大学、港中文、港科大等机构的 **The Trinity: Capability-Driven Recursive Self-Improvement for Multimodal Agents**（arXiv:2610.36077）把进化单位换了：**不按任务表面分类，而是按任务底下共享的能力需求分**，ARC-AGI-3 和 Micromouse 长得完全不一样，但都要「准确感知并追踪状态」，那就让它们在同一个能力节点上一起学。看完我的感受：这篇工程很重，但「能力树 + 固定拓扑的 harness 树 + 路由」这个三件套，正好补上了我们最近关心的「多 profile 子代理路由」和「OO 式 harness 继承」之间缺的那块：**路由该按什么维度路**。

## 核心摘要

Trinity 用冻结的 Claude Opus 5 当主干，设三个角色：Explorer 跑任务收轨迹，Evolver 从轨迹里归纳能力需求、把原始任务树重组成层级能力树，Creator 按能力节点造简化但可验证的模拟世界（Capability-Driven Real2Sim2Real，模拟里学能力、回原任务测迁移）。沿着能力树，Explorer 的 harness 按六类协议模块（感知、记忆、推断、规划、编排、循环）做选择性继承和局部改进，形成一棵与能力树同构的 harness 树；最后用一个能力感知路由器，根据公开任务信息和已验证的执行经验选分支。28 个训练基准均分从 39.1 涨到 73.2（第 4 轮），18 个未见基准从 42.1 涨到 64.1，超过论文给的 Codex（47.5）和 DeepSeek（46.2）参考线。一轮迭代下，用模拟世界训的能力树比用真实任务训的高 3.51 / 4.95 点，推理 token 还最省；完整路由器在训练集和未见集上分别拿到 71.27 和 60.96，离事后最优 Oracle（73.16 / 63.61）只差 2 到 3 点。

## 🎯 为什么要从「按任务进化」换成「按能力进化」

论文把多模态智能看成「世界出题、人类引导、agent 交互产出可验证结果」的循环，这个循环有两个瓶颈：

1. **大规模、异构、可验证的环境手工造不起**，所以需要自动造世界；
2. **agent 能力越来越受 harness 约束**，而 harness 的人工迭代跟不上任务的复杂度和多样性。

现有 harness RSI 的做法是 task-specific evolution。作者的判断很直接：任务需求相近时这样没问题，但跨异构任务会让 harness 过拟合、泛化差；反过来一个全局 harness 又容纳不了互相冲突的需求，比如具身任务里性能和效率的权衡。

他们的立场写得很明白：**RSI 应该从任务驱动转向能力驱动**，由跨任务共享的能力需求来指导多个专精 harness 的学习和优化，而这自然引出一个按能力需求给任务配 harness 的路由器。

## 🏗️ 机制：三棵树和一个路由器

### harness 的形式化：六协议、冻结模型

一个 harness 配置协调冻结模型，由六个控制流协议组成：感知（Perception，从观察里抽事实）、记忆（Memory，构建依赖历史的视图）、推断（Inference，维护相容候选）、规划（Planning，排序或剪枝候选成指令）、编排（Orchestration，判断哪些资源可用）、循环（Loop，决定执行和承诺，包括不出手）。

几条约束值得记下来：模块是只读公开记录的纯函数，不碰隐藏状态、不直接执行环境动作；只有记忆模块可以显式携带状态；推翻一个假设需要观察到矛盾；**进化只改模块配置，模型参数不动**。另外，评测时用的 skills 是单独准备的，不存进树里，不进化、不继承、也不参与路由。

### 第一棵树：任务树

Evolver 把公开多模态基准规范化成统一描述（目标、观察、动作、反馈、完成标准、预算），分进五个需求域：规则发现、约束求解、感知与控制、多智能体交互、长程环境。训练集和未见集的划分在归纳能力之前就固定。Explorer 用初始 harness 在训练实例上收轨迹，执行记录用哈希链校验。

### 第二棵树：能力树

Evolver 从任务目标、允许的观察、动作规则和完成标准里推出能力需求，用规则检查把它们和满足或违反这些标准的轨迹步骤对上。多个独立 agent 先提能力类别，一个裁判合并，再由评审独立检查定义、证据、分配和覆盖率。每个训练任务拿到一个固定的需求集合。

建树的方式很朴素：**按一个事先固定的能力顺序把每个任务的需求集合排序成路径，再把所有路径插进一棵 Trie**，公共前缀自动合并。未见任务的能力需求只在树固定之后才标注，而且只用于事后评估路由，不改树。

能力树建好后，Creator 按节点造世界：同一节点下的异构任务虽然表面不同，但比如都需要「先核实证据再做决定」，那就由 Evolver 根据节点需求和代表任务的公开规范设计简化训练关卡（**刻意排除目标任务的布局、私有证明和解题轨迹**，只保留核心决策过程），Creator 实现它们，验证器池检查节点绑定、执行、状态转移、渲染和完成判定。最后 Explorer 用一个冻结的筛选 harness 试玩，**只收那些表现落在预设中间区间的世界**，太难太易都打回去按预设维度调难度。

### 第三棵树：harness 树

Explorer 在每个节点用继承来的模块加本地模块跑已准入的世界；Evolver 对比成功和失败的轨迹，找出节点特有的改进，以注册过的绑定形式改进六协议库里的模块。每次更新都要记录节点、前驱版本、episode 和可执行样例引用；宿主在接受前校验证据、归属、接口、谱系和带类型的输入输出断言。

两个关键规则：

- **选择性继承**：子节点的配置是「父节点导出的注册表」和「本地模块」的右偏并集，本地同名覆盖父节点。父节点更新后，子节点**只有在相同验证任务、相同试次和预算下，用宿主核验的完成数严格更高时**才接受新的父注册表，否则保留旧的。
- **本地准入不要求涨分**：本地更新通过证据和契约检查就接受，评估归评估。

Creator 那边走另一条线：只有验证器发现失败时才进化，每轮结束把各节点的有效提案和现有 Base Harness 合并，互补的合并、近重复的保留先学到的那个，产出下一轮的 Base Harness。

### 路由器：上下文、动作、反馈

对 Explorer 的 harness 树，路由是一个「上下文、动作、反馈」循环：输入公开目标、初始观察、元数据和图片，候选是固定的、有版本号的 harness 池；检索余弦相似度不低于 0.5 的最多十条历史记录，记忆是 2 万条的 FIFO；摘要里只包含实际执行过的配置的表现和成本，没试过的就是未知。agent 在执行前带着依据提交选择，终局回执和提交的决策、注册表哈希核对之后，结果和成本才追加进记忆供后面的任务用。技术故障记零分，选错不兜底。

## 🧪 关键证据

所有变体共用 Base Harness（Prime Agent）和冻结的 Claude Opus 5。28 个训练基准，18 个未见基准（含两个真实机器人任务）。

**模块和 skills 是互补的（第 1 轮）：**

| 方法 | 训练 | 未见 |
| --- | --- | --- |
| Base | 39.06 | 37.45 |
| 只进化模块 | 56.95 | 47.26 |
| 只加 skills | 58.86 | 48.67 |
| 两者都有 | 63.80 | 53.53 |

**组织方式的对比（第 1 轮，只用模块、不加 skills）：**

| 组织方式 | harness 数（能力树另有 11 个训练环境） | 训练 | 未见 | 训练开销（M token） | 推理（训练集，M） |
| --- | --- | --- | --- | --- | --- |
| 全局一套 | 1 | 53.04 | 42.92 | 582.54 | 531.81 |
| 按任务域 | 15 | 51.17 | 40.82 | 278.25 | 540.36 |
| 按能力域（扁平） | 6 | 49.25 | 39.43 | 136.94 | 562.32 |
| 能力树（真实任务训） | 10 | 53.44 | 42.31 | 211.56 | 526.53 |
| 能力树（模拟世界训） | 10 | 56.95 | 47.26 | 405.70 | 514.42 |

几个读法：扁平按能力分组最省训练 token，但分数反而不如全局一套；加上树结构和选择性继承后涨 4.19 / 2.88 点；再把训练环境从真实任务换成 Creator 造的模拟世界，又涨 3.51 / 4.95 点，推理 token 也是最低的。代价是训练开销比真实任务版能力树高出近一倍（405.70M 对 211.56M），不过仍低于全局一套的 582.54M。

**多轮 RSI**：训练均分 39.1 → 73.2，未见均分 42.1 → 64.1。第一轮涨得最多，第 2 到 4 轮又加了 9.4（训练）和 6.4（未见）。具体基准上 ARC-AGI-3 从 41.0 到 53.6，SciGym 从 45.2 到 57.1，BuildArena 从 93.3 到 97.8；但 Mastermind 停在 88.9，Eleusis 从 82.2 微降到 81.1，Crafter 和 DiG-bench 最终仍低于 Codex 和 DeepSeek 两条参考线。

**路由（第 4 轮 harness 树）：**

| 方法 | 训练 | 训练 token（M） | 未见 | 未见 token（M） |
| --- | --- | --- | --- | --- |
| 随机选 | 52.74 | 567.08 | 46.23 | 594.25 |
| 自路由（只看任务和接口描述） | 65.79 | 535.53 | 52.36 | 582.29 |
| 加能力定义和表现成本摘要 | 70.34 | 510.55 | 58.27 | 556.21 |
| 再加检索执行经验（完整路由器） | 71.27 | 497.89 | 60.96 | 541.28 |
| Oracle | 73.16 | 486.53 | 63.61 | 528.34 |

随机路由和完整路由在未见集上差了近 15 点，说明 harness 树里的分支确实专精化了，选错代价很大；而「能力定义」这一层贡献了最大一段提升（未见 +5.91）。

**模块干预**：往 Base 里随机加一个和任务需求相关的模块，从 39.06 涨到 58.45（+19.39）；加一个无关模块只到 40.08（+1.02）。从第 4 轮的完整 harness 里拿掉一个相关模块，从 73.16 掉到 70.42，token 还从 496.70M 涨到 517.26M。相关性分析里最强的配对是「假设与反例推断」对推断模块（0.744）、「目标承诺与价值权衡」对循环模块（0.444）。

**具身迁移**：把两个机器人任务映射到能力树的同一节点、直接用那里进化出的 harness，再在重建的模拟器里试 5 次总结成 skills。SOON（Unitree G1 走到风扇旁的桌子并伸手）模拟从 0 到 80%、真机从 0 到 60%；CaP-X（AlohaMini2 翻杯找方块）模拟从 10 到 60%、真机从 0 到 60%。作者自己说明，各轮部署在消息处理、接口、指引和验收规则上并不完全相同，这组对比**没法拆开模块进化和 skill 准备各自的功劳**。

## 🤔 我的判断

**定位：一个把「harness 该按什么维度组织」讲清楚的大工程，证据面很广，但不少关键对比是单轮、单主干、无方差的。**

亮点：

1. **按能力而不是按任务组织 harness。** 这是这篇最值得拿走的想法。它解释了为什么按任务域拆 15 套 harness 反而不如一套全局的：拆得太细，每套看到的信号太少；扁平按能力分 6 组也不行，要用前缀共享加选择性继承，才既专精又有足够数据。
2. **继承有闸门。** 父节点更新后，子节点要在同等条件下严格涨完成数才接受，否则保留旧版。这和我们之前看的 OO-Harness 基类回退、SelfEvolvingHarness 的回归预算是同一类保护，但 Trinity 把它做成了树上每条边的默认规则。
3. **路由器的输入设计很克制。** 只用公开任务信息、能力定义、已执行配置的表现成本摘要和检索到的经验，没试过的配置就标未知，选错不兜底。这对做多 profile 子代理路由的人是一个可以直接照抄的协议：**路由信号 = 能力描述 + 实测表现成本，而不是让模型凭名字猜**。

问题与局限：

- 所有结果都基于一个冻结的 Claude Opus 5，没有换主干的实验，也没有报告多次运行的方差。「模拟比真实高 3.51 点」这类差距，在 28 个基准均分上有多稳，论文没给。
- 能力类别是由多个 agent 提出、裁判合并、评审检查出来的，这一步本身的稳定性（换一批 agent 会不会长出不同的树）没有测。
- 能力顺序是事先固定的，它决定了 Trie 的形状和继承关系；作者说顺序不代表因果依赖，但不同顺序对结果的影响没有消融。
- 局限里作者只提了网页搜索发现基准的覆盖问题和只在 harness 层做 RSI，没有讨论 Creator 造世界的成本随任务规模怎么增长，而模拟版能力树的训练开销已经是真实任务版的近两倍。

对工程的直接启发：

- **先给任务打能力标签，再决定 harness 拆分粒度。** 如果你手里有多套子代理 profile，可以先回头看看它们是按任务类型分的还是按能力分的；按能力分，新任务进来时路由才有可解释的依据。
- **训练环境可以比真实任务更简单。** 只保留核心决策过程、去掉表面复杂度的模拟关卡，反而给了更干净的进化信号。对 harness 自进化来说，「造一个小而准的练习场」可能比「在真实任务上硬跑」更划算。
- **路由器的记忆只记执行过的结果。** 这个「未试即未知」的规则很重要，它防止路由器根据描述就高估一个从没跑过的配置。

一句话收束：**harness 拆分的单位不该是任务名，而是任务背后要用到的那组能力，拆对了，继承和路由才都有了依据。**
