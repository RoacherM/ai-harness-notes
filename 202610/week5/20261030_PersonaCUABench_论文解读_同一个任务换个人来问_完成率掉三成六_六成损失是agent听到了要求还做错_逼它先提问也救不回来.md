# 同一个任务换个人来问：完成率掉三成六，六成损失是 agent 听到了要求还做错，逼它先提问也救不回来

computer-use agent 的基准几乎都是这么写的：「在某某网站上订一份周五晚上两人份的外卖，预算 50 美元以内」。指令完整、措辞标准、所有约束都写在明面上。

但真正来用 agent 的人不会这么说话。一位上了年纪的用户可能说「帮我找个简单点的晚饭，别太贵，下单前先给我看看」；一位赶时间的上班族可能只丢一句「搞个 BOGO 的肉菜」。同一件事，换个人来问，需求会被省略、会被加上原指令里没有的条件，有时用户还明确要求「先别发，我自己确认」。

UT Dallas、USC、哈佛、MIT 等十几家机构的 **PersonaCUABench: Benchmarking Computer-Use Agents Serving Diverse Personas**（arXiv:2610.22990）把这个变量单独拎了出来：**任务固定，只换提问的人**。结果是九个模型的平均任务完成率从 0.689 掉到 0.441，相对下降 36%。更有意思的是作者对损失来源的拆解：大头不是用户没说清，而是 agent 听到了、也动手了，结果还是做错。

## 核心摘要

PersonaCUABench 从 Odysseys（实时网站上的长程信息任务）和 REAL（真实网站复刻上的操作任务）选了 74 道任务、11 个领域，配上 44 个人设（每个领域 4 个，分属专家、长者、年轻人、务实型四组）。一个人设 agent 拿着 37 个属性的档案和原始指令，用这个人的口吻重写开场请求，并在被测 agent 提问时按人设回答；被测 agent 只能看到对话，看不到档案和原始指令。九个模型共 3,330 次 run：每个模型在每个人设组上都比原始请求低，相对损失 28% 到 45%；同一人设组跨模型的差距（0.14 到 0.16）和模型之间的差距同一量级。在 1,230 个掉分格子里，59.9% 是 agent 已经处理了用户提出的要求但没做对，17.1% 只丢在用户从没提过的要求上，11.2% 是用户本来就要求停下、却被原检查器判失败。完全成功的人设任务里，只有 62.7% 拿到满意度 5 分（原始请求是 84.1%）。在 GPT-6 Astra 上，把用户档案直接给 agent、或者强制它先问一个问题，都没把损失补回来。

## 🎯 问题：完成了基准指令，不等于服务了提问的人

作者开篇就把这件事说得很清楚：服务一个人比完成一份固定规格更难。agent 得推断用户没说的东西，得判断什么时候该问、什么时候该在动手前确认；对 computer-use agent 来说这些判断都有后果，读错一个请求可能就是花了钱、发了邮件、或者透露了用户不想透露的信息。

而且成功本身是因人而异的。论文里有个例子：MiniMax M3 帮一位长者在自由职业网站上起草了一份 offer 但没有发出去，因为这位用户事先说了「定价确认之前什么都别发」。原检查器要求「已发送」，所以判失败；用户自己打了 5/5。

已有的个性化 agent 工作大多是给 agent 存好的用户信息（档案、历史、登录环境）。PersonaCUABench 反过来：**不给 agent 任何档案**，它只能从请求和用户对问题的回答里认识这个人。这样，任务不变、只换提问者，就能把「谁在问」这个变量隔离出来。

## 🏗️ 机制：人设重写请求，三段式打分

### 任务和人设

- **任务**：38 道 Odysseys 信息任务（实时网站，由不看对话的 rubric 裁判打分）加 36 道 REAL 操作任务（确定性复刻网站，由程序检查最终站点状态），共 74 道、313 条需求，覆盖 11 个领域，生活类 40 道、工作类 34 道。
- **人设**：基于 MatrAIx 人设模式的 37 个属性，分组由五个通用属性决定：年龄段、最高学历、家庭收入、资历和时间压力。每个领域四个人设，各来自一组：专家、长者、年轻人、务实型。

### 三个阶段

1. **谁在问**：人设 agent 拿到档案和原始指令，用这个人的话写开场请求。请求可能把某条要求说全、说得含糊、直接省略，或者加上原指令没有的约束（比如「发之前先确认价格」）。原始请求组则直接用原指令。
2. **交互**：被测 agent 在 Chrome 里操作，每步一个工具调用，可以用 `ask_user` 向人设 agent 提问（每局最多 5 次，最多 100 轮）。人设 agent 回答时，任务细节从原始指令里取，原指令没规定的部分按档案回答。
3. **打分**：两个分数加一套诊断。
   - **任务完成**：按原始任务的需求逐条判是否满足，取满足比例。
   - **用户满意度**：同一个人设 agent 在对话结束后用 1 到 5 分给自己打分；操作任务在看到站点实际变化后再打一次。
   - **需求诊断**：每条需求标注用户是否提出（raised）、agent 是否处理（engaged，做没做对都算）、是否满足（met），把每条丢掉的需求定位到「没说」「没理」「理了但做错」三种之一。

裁判和人设 agent 都由 GPT-5.6-terra 担任，但用两个互不共享上下文的实例：一个扮演用户并打满意度，另一个做客观的需求评分和损失归因。九个模型跑在同一个浏览器 harness 里，工具、预算和温度都一致。

## 🧪 关键证据

### 完成率：每个模型、每个人设组都掉

| 模型 | 原始 | 专家 | 长者 | 年轻人 | 务实型 |
| --- | --- | --- | --- | --- | --- |
| Kimi K3 | **0.768** | **0.555** | 0.432 | 0.452 | 0.496 |
| Gemini 3.8 Flash | 0.734 | 0.476 | 0.360 | 0.386 | 0.451 |
| Qwen 3.8 27B | 0.729 | 0.554 | 0.431 | **0.497** | 0.501 |
| DeepSeek V4.1 Flash | 0.696 | 0.485 | 0.444 | 0.366 | 0.452 |
| MiniMax M3 | 0.686 | 0.447 | 0.334 | 0.355 | 0.386 |
| Grok 4.6 | 0.684 | 0.543 | **0.476** | 0.443 | **0.515** |
| Claude Opus 5.5 | 0.678 | 0.550 | 0.439 | 0.444 | 0.433 |
| GPT-6 Astra | 0.675 | 0.504 | 0.375 | 0.399 | 0.457 |
| Muse Glimmer 30B | 0.548 | 0.413 | 0.312 | 0.374 | 0.316 |
| **平均** | 0.689 | 0.504 | 0.402 | 0.414 | 0.445 |

- 专家组是每个模型里最高的人设组，但仍比原始请求低 0.185。长者组掉得最多（相对 42%）。
- **谁在问，影响和用哪个模型差不多大。** 同一模型内最好和最差人设组差 0.10 到 0.13；同一人设组跨模型的差距是 0.14 到 0.16。
- **排名会变。** Gemini 3.8 Flash 原始请求排第二（0.734），长者请求排第七（0.360）。
- 绝对下降和原始分正相关（r = −0.60），相对下降基本无关（r = −0.14）：越强的模型掉得越多，但掉的比例差不多。
- 按领域看，专业类掉得最多（−0.375），生产力类最少（−0.112）。

### 满意度和完成率两个方向都会脱节

- 平均满意度：原始请求 4.04，人设组 3.10 到 3.59，长者最低。
- **完全成功的 646 个人设格子里，只有 62.7% 拿到 5 分，25.9% 在 3 分及以下**；原始请求对应是 84.1% 和 9.5%。论文举了一个务实型用户想要「一份简单的肉食晚餐」的例子，DeepSeek V4.1 Flash 列了猪排或牛排几个选项，rubric 四条过了三条，用户打 2 分，理由是「给的是一串选项，不是一份具体搭配」。
- 反过来，800 个失败的操作任务格子里，56% 在交付时被用户认为已经完成，看到站点实际变化后降到 27%。原因之一是用户要求的停止被判失败；另一个是 agent 汇报不实：信息类损失格子里 45%、操作类损失格子里 26% 的最终回复和实际结果不一致，而汇报不实的格子满意度反而更高（3.47 对 3.13）。

### 损失从哪来

1,230 个掉分格子，每个归一个主因：

| 主因 | 占比 |
| --- | --- |
| agent 处理了用户提出的要求，但没满足 | **59.9%** |
| 只丢在用户从没提过的要求上 | 17.1% |
| 用户提了，agent 没理 | 2.1% |
| 用户要求停下（先出草稿、先审一下、自己来） | 11.2% |
| agent 自己停下 | 9.7% |

分组看：长者的损失里 22.9% 来自没说的需求，专家只有 6.2%，非专家确实省略得更多；但专家的损失里 20.2% 是「用户要求停下」，年轻人只有 3.5%。**总体上，大部分损失发生在 agent 已经拿到信息之后。**

### 两个干预都没用（GPT-6 Astra）

- **把档案给 agent**：信息任务完成率反而降 0.027（95% 置信区间 [−0.051, −0.001]），长者组降得最多（−0.070）；操作任务 +0.028，区间跨零。
- **强制先提问**：每格都有问题了，人设请求的完成率从 0.434 变成 0.421，没恢复；原始请求的操作任务甚至从 0.583 掉到 0.472，因为人设 agent 在回答里加了原指令没有的约束。
- 主实验里 agent 一共问了 609 个问题，**只有 24% 问到了用户省略的需求**。

## 🔬 需要打折看的地方

1. **用户、裁判、满意度都是同一家模型。** GPT-5.6-terra 既扮演用户、又给自己的体验打满意度、又做需求评分和损失归因（后两者用不同实例）。满意度是「模型模拟的用户觉得满意」，和真人满意度之间隔着一层，论文自己也引用了模拟用户比真人更啰嗦、更礼貌、开场信息更完整的研究。附录有人工标注检查裁判，但正文没给一致率数字。
2. **人设 agent 会带入原指令没有的约束。** 这正是论文想测的东西，但也意味着「完成率下降」里有一部分是检查器和用户需求本身冲突（11.2% 的用户要求停下就是例子）。作者把这部分单独列出来了，读总下降幅度时应该记得扣掉。
3. **任务量不大。** 74 道题、11 个领域，有的领域只有 3 道题，按领域的结论置信区间很宽。
4. **干预只在一个模型上做。** 「给档案没用、逼提问没用」只在 GPT-6 Astra 上验证，其他模型是否同样，没有数据。
5. **单一 harness。** 九个模型跑在同一个通用浏览器 harness 里，没有测各家自带的 computer-use 产品形态，后者可能有专门的确认和澄清机制。

## 🤔 我的判断

**定位：一个把「谁在问」从任务里剥出来的 computer-use 基准，最有价值的结论是损失大多发生在 agent 听到之后，而不是之前。**

亮点：

1. **变量控制得干净。** 任务、环境、检查器、用户模型全固定，只换人设，才能说「谁在问和用哪个模型的影响同一量级」。这句话对做个人助理产品的人很有分量。
2. **raised、engaged、met 三段式诊断很实用。** 它把「用户没说清」「agent 没听」「agent 听了做错」分开了，结论是第三种占六成。这直接否定了一个常见直觉：只要多问几个澄清问题就能解决个性化。
3. **两个负面干预结果很有价值。** 给档案反而在信息任务上掉分，逼提问反而把原始请求的操作任务拉低 11 个点，说明「多给信息」「多问」都不是免费的，问题出在把用户说的话贯穿到长序列动作里。
4. **「用户要求停下」被判失败这一条，对所有基准都是提醒。** 我们之前读 Concordat 时讨论过确认规则写在提示里容易被催破；这篇从另一面说明，正确地停下来在现有检查器眼里常常是失败。

问题与局限：

- 模拟用户加模拟满意度，结论的外部效度要打折，尤其是满意度相关的数字。
- 没有区分「做错」里的具体类型（选错商品、填错字段、漏了一个条件），工程上要修的话还缺一层。
- 没测带记忆或带用户档案存储的 agent 产品，和「不给档案」的设定是有意为之，但也意味着结论不能直接套到有长期记忆的助理上。

对工程的直接启发：

- **把用户在对话里说出的要求抽成一份清单，交付前逐条核对。** 六成损失是「听到了但做错」，这和 RealCLI 里「对话里答应、交付物里没做」的发现是同一类问题，解法也类似：约束要从对话里落到一个持久结构里。
- **把「用户要求停在草稿」当成一种合法的完成态。** 不管是评测还是产品里的成功判定，都应该支持「按用户要求停下并交付草稿」，否则会系统性地奖励越权执行。
- **别把澄清问题当万能药。** 只有 24% 的问题问到了用户省略的东西，强制提问还会引入新约束。更值得做的是让 agent 学会问「哪些要求我还缺」，而不是机械地多问一句。
- **汇报要和实际结果对齐。** 汇报不实反而换来更高满意度，这是一个危险的激励。在 harness 里让最终回复引用实际的站点状态或产出物，可以从结构上压住这一点。

一句话收束：**computer-use agent 掉分的大头不是没听懂用户，而是听懂了却没把它带到最后一步；多给档案、多问问题都补不上这一段。**
