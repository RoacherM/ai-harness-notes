# 裁判别只读轨迹，要自己跑代码；rubric 边审边加：80B 开源模型在 Kaggle 难题上百分位涨了近 15 点

你有没有过这种体验：agent 跑完一个数据科学任务，日志里每一步都很像样，交叉验证分数也报出来了，提交文件也写好了；结果一看排行榜分数离谱，回头才发现一个路径写错，所有测试样本都被当成了空数据，模型对每条都预测了同一个类别，而它自己全程没察觉。

这正是卡内基梅隆大学和微软的 **AdaPRA**（arXiv:2610.33245）开头那个例子：一次尝试里，错误的路径让全部 158,538 条测试音频都按静音加载，每条预测都是 "unknown"。负责审查的 agent 发现预测概率全都一模一样，顺藤摸瓜修好了它。

我们最近归档的 judge 类论文（DeCert、VerifierBench、TraceTrial、farol 那一组）大多在问「裁判的判断可不可信」。AdaPRA 问的是另一个问题：**在长程任务的进行过程中，裁判能不能主动去查证，而不是只读 agent 给它看的东西？** 看完我的感受：这篇把「过程审查」从打分器升级成了一个有自己终端的审查 agent，再配一套能边审边长的 rubric，收益在难题上尤其明显。它和 AgentProofBench 讨论的「验收程序要看部署态」是同一个方向：**审查者要能亲自看现场。**

## 核心摘要

AdaPRA 由三部分组成。第一是一个持久化 harness：每个 Kaggle 任务固定一个工作区，五次尝试共享，只重置上下文，每次尝试会拿到前面尝试的摘要和最终审查的反馈。第二是过程奖励 agent（Process Reward Agent，PRA，用 Claude Sonnet 4.6）：每隔 c 轮和在 agent 宣布完成时介入，它有自己的终端和草稿区，能读 agent 的工作区（只读）、跑代码核实，然后按 rubric 逐条打分，只把重要且没满足的那几条反馈回去。第三是自适应 rubric：先从强弱轨迹的对比里挖出 19 条种子 rubric，运行中 PRA 可以在亲自检查之后为当前任务新增、更新或退役 rubric。基础 agent 是 Qwen3-Coder-Next（80B）。相比 DSGym 原生 harness，五次尝试取最好时的平均排行榜百分位在 DSPredict-Easy（38 题）上从 44.5 涨到 69.0（+24.5），在 DSPredict-Hard（54 题）上从 21.3 涨到 36.1（+14.8）；相比作者自己的持久化 harness 单独使用，也分别多出 8.2 和 10.6 点，Hard 上超过中位数的比例从 18.5% 涨到 33.3%。代价是 PRA 占了监督运行成本的七成以上。

## 🎯 问题：长程任务里，错误往往静悄悄

Kaggle 式的数据科学任务是典型的长程任务：读数据、做特征、训模型、调交叉验证、写提交文件，一次尝试动辄上百轮。错误很少表现为报错，更多是静悄悄的：交叉验证写错导致分数虚高、预测分布被压缩、提交前没核对格式。只看最终分数的结果奖励来得太晚，只读轨迹文本的过程奖励模型又看不到真实的文件和数据。

作者的判断是，监督要满足三个条件：**在过程中介入**（不是只在结束时打分）、**能主动核实**（读文件、跑代码，而不是只读 agent 的自述）、**标准能随任务变化**（固定 rubric 覆盖不了每道题的特殊坑）。

## 🏗️ 机制：持久工作区、会动手的审查者、会生长的 rubric

### 持久化 harness

建在 OpenHands 之上。每个任务一个工作区，跨五次尝试保留文件；每次尝试开始时上下文重置，但会注入前面尝试的摘要和最终审查的反馈。这样后面的尝试能复用前面写好的数据处理代码和结论，又不会被前面的长对话拖垮。

这个 harness 本身就值不少分（见后面的表）。

### PRA：有自己终端的审查 agent

PRA 的设计细节，几乎每一条都是消融出来的：

- **介入时机**：每 c 轮一次，外加 agent 宣布完成时一次。审查期间 agent 暂停。完成时的审查如果不通过，agent 有一轮修改机会。
- **能动手**：PRA 有自己的终端和草稿区，可以只读访问 agent 的工作区，自己写脚本检查数据、预测分布、交叉验证设置。agent 的轨迹被写成文件，PRA 按需去读，而不是整段塞进上下文。
- **打分方式**：对每条 rubric 给出满足程度 p、重要性 i、理由和建议动作。
- **只报重要的失败**：只把 i≥0.5 且 p<0.6 的 rubric 反馈给 agent。作者试过把所有 rubric 都给 agent 看，agent 的行为没什么变化。
- **注入位置**：审查报告直接插进 agent 的消息流，效果比写成一个 markdown 文件让 agent 自己去读更好。

### 种子 rubric：从强弱对比里挖

先在一批任务上跑 agent，按分数取前四分之一和后四分之一的尝试做对比，用 Sonnet 4.6 挖出行为差异：共 906 条（564 条问题行为、342 条良好行为）。问题行为里 344 条是基于轨迹判断的，良好行为里 235 条是基于产出物判断的。再按 MECE（互斥且完全穷尽）原则聚类，用了其中 519 条，得到 17 条 rubric（其中 4 条改写成要看此前所有尝试），再加 2 条人工整理、专门针对跨尝试失败（比如后面几次尝试收敛到同一个方案）的 rubric，共 19 条种子。每个任务的 rubric 库彼此隔离，结果不依赖任务的运行顺序。

### 自适应 rubric：先查证，再加规则

运行中，PRA 可以为当前任务维护一个 rubric 库，操作有三种：新增、更新、退役。关键约束是**新增之前必须先跑一次检查**，有证据才能加。

新增的 rubric 往往是任务特定的。比如在 House Prices 任务上，PRA 加了一条叫 prediction underdispersion 的 rubric，检查交叉验证预测是否比真实目标分布窄得多，这通常说明模型把极端房价往均值拉了。

但作者也给了反例：新增的 rubric 可能编码一个达不到的目标。在混凝土强度回归任务上，PRA 在第 1 次尝试的第 20 轮加了 prediction_dispersion_health，写脚本查出交叉验证预测的标准差只有 10.90，目标的标准差是 16.40，比值 0.664，低于它设的 0.80 阈值，于是建议加样本权重或用分位数回归，agent 随后就去处理这个分布问题。这类阈值是 PRA 自己定的，未必是这道题能达到的。

## 🧪 关键证据

### 主结果（最好尝试，五次尝试中取最好）

**DSPredict-Easy（38 题）：**

| 方法 | 平均百分位 | 有效提交率 | 超过中位数 | 奖牌率 |
| --- | --- | --- | --- | --- |
| DSGym 基线 | 44.5 | 76.3 | 50.0 | 2.6 |
| 持久化 harness 单独 | 60.8 | 100 | 71.1 | 7.9 |
| harness 加 DataPRM | 54.6 | 100 | 65.8 | 5.3 |
| **AdaPRA** | **69.0** | 100 | **86.8** | 7.9 |
| 去掉自适应 rubric | 67.3 | 100 | 86.8 | 7.9 |
| 去掉 PRA 执行代码 | 63.0 | 100 | 86.8 | 2.6 |

**DSPredict-Hard（54 题）：**

| 方法 | 平均百分位 | 有效提交率 | 超过中位数 | 奖牌率 |
| --- | --- | --- | --- | --- |
| DSGym 基线 | 21.3 | 68.5 | 11.1 | 3.7 |
| 持久化 harness 单独 | 25.5 | 81.5 | 18.5 | 5.6 |
| harness 加 DataPRM | 23.1 | 88.9 | 14.8 | 3.7 |
| **AdaPRA** | **36.1** | 90.7 | **33.3** | 5.6 |
| 去掉自适应 rubric | 31.8 | 88.9 | 22.2 | 5.6 |
| 去掉 PRA 执行代码 | 31.8 | 90.7 | 25.9 | 9.3 |

（「去掉 PRA 执行代码」指 PRA 只靠阅读打分，不跑检查。）

几个读法：

- **另一个过程奖励模型 DataPRM 反而拉低了分数**（Easy 从 60.8 降到 54.6，Hard 从 25.5 降到 23.1）。只读文本的打分器加进来不一定有帮助。
- **harness 和监督的贡献在难易题上反过来了。** Easy 上 harness 贡献 16.3 点、监督贡献 8.2 点；Hard 上 harness 只贡献 4.2 点、监督贡献 10.6 点。题越难，过程中的纠错越值钱。
- **自适应 rubric 在 Hard 上的贡献是显著的**：去掉后百分位从 36.1 降到 31.8，逐题对比 AdaPRA 赢 32 题、输 13 题，p=0.024。去掉 PRA 执行代码同样掉到 31.8（29 赢 18 输，p=0.077，不显著），在 Easy 上则从 69.0 掉到 63.0（p=0.012，显著），奖牌率也从 7.9% 掉到 2.6%。奇怪的是 Hard 上只读版的奖牌率反而更高（9.3% 对 5.6%，五块对三块）。
- 按单次尝试平均看，Easy 上 AdaPRA 是 61.0，harness 单独是 51.3，论文给的 GPT-5.1（high）参考是 60.4。也就是说，**一个 80B 开源模型加上 PRA 监督，单次尝试的平均水平和 GPT-5.1 相当**。

### 种子 rubric 能跨难度迁移

只用固定的 19 条种子 rubric（不自适应），在 Hard 上也带来 6.3 点提升（p=0.007），和 Easy 上的 6.5 点（p=0.017）接近。rubric 的重要性排序在两个基准之间的 Spearman 相关是 0.91，失败率排序是 0.66。

最常失败的是几条「偏好简单方案」类的 rubric，在 68% 到 84% 的尝试里都没满足。到了 Hard 上，无效交叉验证的比例从 32% 涨到 57%，未经核实就提交的比例从 33% 涨到 52%。这组数字本身就是一个很好的诊断：**题变难之后，agent 最先丢掉的是验证习惯。**

### 审查频率

单次尝试、Easy 上：c=10 时 56.4，c=5 时 52.7，c=20 时 49.9，harness 单独 48.4。审查不是越频繁越好，太频繁会打断 agent。Hard 上为了控制成本用的是 c=20，在 Easy 上这是效果最弱的设置，所以 Hard 的结果可能低估了监督的收益。

### 换基础模型

用 DeepSeek-V3.2 当基础 agent（单次尝试，Easy）：百分位从 36.9 涨到 44.7，超过中位数从 23.7% 涨到 47.4%，逐题 25 赢 11 输（p=0.005）。

### 成本

| 设置 | Agent（美元） | PRA（美元） | 总计（美元） | 每次尝试（美元） |
| --- | --- | --- | --- | --- |
| Easy，harness 单独 | 193 | 0 | 193 | 1.0 |
| Easy，AdaPRA | 193 | 1,225 | 1,418 | 7.5 |
| Hard，harness 单独 | 465 | 0 | 465 | 1.8 |
| Hard，AdaPRA | 547 | 1,640 | 2,187 | 8.2 |

PRA 占监督运行成本的 72% 到 86%，每次尝试的成本涨到原来的 4.5 到 7.5 倍。去掉 PRA 执行代码、只靠阅读打分，能省 11%（Easy）到 22%（Hard）。

## 🔬 rubric 只增不减的问题

自适应部分有一个作者自己点出来的硬伤：四轮运行里一共 177 次新增、1 次更新、0 次退役。rubric 库只会越来越大。原因是 PRA 没有办法把本地验证分数的提升归因到某一条 rubric 上，所以也就没有依据去修改或淘汰那些没用的 rubric。

这和 TTME 那篇的对比很有意思：TTME 的记忆有 20 步过期、24 条上限，强制淘汰；AdaPRA 的 rubric 库没有任何淘汰压力。对一个跑五次尝试的任务来说问题不大，但如果想把 rubric 库跨任务积累下来，没有信用分配就会很快膨胀。

## 🤔 我的判断

**定位：一个把「过程监督」从文本打分器升级成能动手核实的审查 agent 的扎实工作，证据在难题上很硬，成本是主要障碍。**

亮点：

1. **审查者要能亲自看现场。** PRA 有自己的终端、能只读访问工作区、能跑代码，这是它和 DataPRM 这类只读文本的过程奖励模型的根本区别。DataPRM 拉低分数、AdaPRA 拉高分数，这个对比本身就是很强的论据。
2. **只报重要的失败。** i≥0.5 且 p<0.6 的过滤、注入消息流而不是写文件，都是很实用的接口设计。审查报告给太多，agent 会忽略；放在文件里，agent 会不读。
3. **新增 rubric 必须先查证。** 这条约束防止审查者凭空添规则，和 farol 那类「LLM 审完再加一道确定性闸门」的思路是一致的。
4. **难题上监督比 harness 更值钱。** 这个发现对资源分配很有参考价值：如果你的任务越来越难，与其继续堆 harness，不如投资一个会核实的审查者。

问题与局限：

- PRA 用的是闭源的 Claude Sonnet 4.6，成本占大头，复现也依赖这个模型持续可用。用一个更强的闭源模型监督一个开源模型，收益里有多少来自「强模型的知识泄露给弱模型」，论文没有拆开。
- rubric 只增不减，没有信用分配。
- 只在 Kaggle 式的预测任务上测，开放式分析或没有明确预测目标的数据科学任务没有覆盖。
- 主结果只有一个基础模型，DeepSeek-V3.2 只做了单次尝试的验证。
- 只测了五次尝试，更多次尝试下不加监督的「多试几次选最好」可能会追回一部分差距。

对工程的直接启发：

- **给你的 judge 一个只读的沙箱。** 很多 harness 里的审查步骤只把 agent 的输出文本给裁判看。哪怕只是让裁判能读文件、跑一段 Python 检查预测分布，都可能把它从「看起来对」升级成「核实过是对的」。
- **审查报告只给失败项，并且直接插进对话。** 别给 agent 一份完整的打分表，也别写到它可能不读的文件里。
- **用强弱对比挖种子 rubric。** 取前后四分之一的轨迹做对比、聚类成互斥穷尽的类别，是一个可以直接照搬的流程，而且挖出来的 rubric 能跨难度迁移。
- **盯住验证习惯类的指标。** 无效交叉验证、未经核实就提交，这两项在题变难时涨得最快，值得做成确定性检查。
- **审查频率要调。** 每 10 轮一次比每 5 轮和每 20 轮都好，太频繁的审查会打断 agent。

一句话收束：**过程监督真正起作用的条件，是审查者能自己动手核实现场，并且只把最要紧的几条失败直接告诉 agent。**
