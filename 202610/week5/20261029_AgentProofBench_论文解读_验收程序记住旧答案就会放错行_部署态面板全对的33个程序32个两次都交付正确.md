# 验收程序记住了旧答案就会放错行：部署态面板全对的 33 个程序，32 个两次都交付正确

你有没有过这种体验：让模型给一个 agent 任务写了个验收脚本，第一次跑得漂亮，Pass 和 Fail 分得清清楚楚，于是你把它冻结下来当 CI 门禁、当 RL 奖励、当「agent 说完成了就先过一下这个」的 gate。过了两周，同一条用户指令，数据库里换了一个同名用户、某个状态字段初值从 Active 变成 Dormant，脚本还在照着当初那份快照里的 ID 和字面值比对，把正确的结果拒掉，把错误的结果放行。

更糟的是，它拒掉之后 agent 会继续干活。你本来想要一个「不放过错误」的门卫，结果它把一个已经做对的状态推回去重做，做错了，然后它再点头放行。

CMU 的 **AgentProofBench: Benchmarking Reusable Verifiers for Web Agents**（arXiv:2610.34634）就是专门量这两件事的：**一个冻结的验收程序，在初始数据变了之后还能不能跟着需求走；它的判决接进执行循环之后，会把 agent 带到哪里。** 看完我的感受：这是 VerifierBench 之后在「生成式 verifier」这条线上最工程化的一篇，它把「验收程序可复用」从一句口号变成了可以配对检验的契约，而且给出了一个很反直觉的基线：在它测的这组设置里，什么都不判、只说一句「继续检查，保留已完成的工作」，交付正确率反而最高。

## 核心摘要

AgentProofBench 在 Agent-Diff 的企业服务副本上构建了 97 个任务、79 个任务族、4 个 Web 服务（Linear、Slack、Box、Calendar），验收接口统一为 verify(task, before, after)，返回 Pass、Fail 或 Unknown，异常、格式错误、超出执行上限记为 Error，程序在只读沙箱里用任务 actor 的 API 权限跑，单次限 1 CPU、1 GB、60 秒、80 次业务操作。核心是两个配对研究。P1 复用研究取 48 个任务族，每条公开指令配三种初始条件：Source（构建时的状态）、Background（只改无关数据）、Related（改动一个必需的实体绑定、初值、集合或保留条件），并加入一个「源决策见证」：在源状态下合法的旧决策，在 Related 状态下变成非法。DeepSeek Flash 和 Pro（都关闭 thinking）各生成源程序和重建程序，共 576 个冻结程序，跑在 558 个终态上。源程序在 Related 状态下的平衡准确率 Flash 93.23%、Pro 90.36%，复用减重建的差是 −1.56 [−5.47, 1.57] 和 −4.95 [−10.16, 0.00]；但完整主面板全对的程序从 89/96 降到 83/96（Flash）、83/96 降到 81/96（Pro），主面板加见证都对的联合正确数是 82/96 和 79/96，重建程序是 82/96 和 86/96。P2 执行研究取 22 个任务族、44 条轨迹、88 个保存的起点，比较四种策略共 352 个结果：部署态面板零错误的 33 个程序分配里有 32 个在两个起点上都正确交付，有面板错误的 11 个里只有 1 个；全部 17 次程序门禁扣留和全部 3 次回退都落在有错误的那组。四种策略里，中性续写（不判、只提示继续并保留已完成的工作）在检查点上修好了 Flash 16 个失败里的 14 个、Pro 16 个里的 16 个，交付正确 20/22 和 22/22，程序门禁只有 17/22 和 16/22。

## 🎯 为什么这件事值得写

这个月我们反复碰到同一个结构：LLM 生成一个可执行的判定器，然后把它冻结起来反复用。VerifierBench 量的是生成的 verifier 在六个 agent benchmark 上分不分得清对错，HarnessVerification 拆了验证在 harness 里该放哪一层、完成闸门和独立 critic 谁更划算，write-judge、farol 这类工程项目则把一个决策模型或静态规则当成 agent 写入前后的 gate。大家默认的好处是：程序一次生成，之后每次检查都是毫秒级、零 token、可审计。

但「一次生成、反复使用」隐含了一个契约：**程序要从运行时的 before 状态里推导出当前的需求，而不是记住构建时看到的那份快照。** 用户说「把 Plot B3 分给 Rashida，保持它原来的状态」，「原来的状态」是运行时的初值，不是构建那天的 Active。用户说「分给 Elena」，Elena 对应哪个 ID 要每次现查。以前的 verifier 评测多是固定实例上的准确率，测不出这类绑定错误，因为构建状态和评测状态是同一个。

第二个被忽略的问题是：verifier 的判决会被执行。门禁拒绝之后 agent 会继续操作，而继续操作是有写副作用的。一个误拒不只是「少给了一分」，它可能把一个已经正确的业务状态改坏。AgentProofBench 的价值在于把这两件事都做成了配对的、可复现的测量。

## 🏗️ 机制：一个验收契约、三种初始条件、四种执行策略

**1. 验收接口和参考语义。** 每个任务有公开指令、API 文档和普通鉴权接口，宿主端的参考谓词 G 判定任务是否完成，覆盖身份、值、集合、关系四类要求，用版本化的选择器从每个 before 状态里重新定位必需对象。参考谓词在原生状态和普通 API 上共享，评分衡量的是对这份显式契约的符合度。

为了检查参考本身，作者让 GPT-6 Astra 当 LLM 评审，在不看参考判决的情况下审了 62 个任务的 195 个状态：已判定的 192 个标签里同意 191 个（99.5%），3 个无法判定。

**2. 四类结果面板。**

| 面板 | 测什么 |
| --- | --- |
| 自然结果 | 普通 agent 运行的真实终态，556 个，452 成功、104 失败 |
| 原生前缀 | 把完整执行连到更早的半成品状态 |
| 类型化故障 | 用服务 API 在成功锚点上注入一个已知违反的要求 |
| 合法替代 | 改动公开指令允许的行为，检验会不会误拒 |

**3. P1 配对复用。** 48 个任务族（18 Linear、10 Slack、19 Box、1 Calendar），每条指令三个初始条件：

- **Source**：构建状态；
- **Background**：只改请求范围外的数据，作为对照；
- **Related**：改一个必需的实体绑定、初值、集合或保留条件。

每个条件包含一个完整结果、可能时一个合法替代、两个变异失败，共 144 个初始状态、558 个主面板终态（270 有效、288 失败）。另加一对**源决策见证**：在 Source 下合法的一次业务决策，原样重放到 Related 下应当非法。如果程序只是记住了源答案，就会在这里放行。

构建时程序可以读构建状态、可以调试，构建 prompt 明确写了复用契约。Flash 和 Pro 各在源条件生成 2 个源程序，在每个目标条件生成 2 个重建程序，共 576 个冻结程序；在线 API 评审（API12，12 轮）每个终态每个模型独立判两次，共 2,232 次在线观测。

**4. P2 执行中的验收。** 22 个任务族，每个任务一条 Flash、一条 Pro 的 actor 轨迹，从 Related 初始状态出发，共 44 条。每条轨迹保存两个起点：自然结束点，和第一次包含写操作的完整工具轮之后的检查点，共 88 个起点。每个起点分出四种策略：

| 策略 | 做法 |
| --- | --- |
| Actor stop | actor 自己说完就交付 |
| Fixed continue | 固定两轮中性续写，第二轮后交付 |
| Program gate | 用一个源构建的 Pro 程序判，Pass 才交付，否则最多再续两轮 |
| Online gate | 用新鲜的 Pro API12 在线评审判，规则同上 |

程序门禁的程序是按任务和 actor 的固定奇偶规则分配的，和程序质量无关。中性消息原文是「Continue checking and completing the original user request. Preserve valid work already completed.」，门禁不通过时只在前面加一句「The acceptance check has not accepted this outcome.」，**不带任何检查项和实体 ID**。每轮 actor 限 20 次模型调用、100 次业务操作、1 美元、900 秒，扣留交付时已执行的写操作会保留。

## 🧪 关键证据

**P1：平均准确率看不出问题，完整面板能看出。**

| 指标 | Flash | Pro |
| --- | --- | --- |
| 源程序 Related BA | 93.23% | 90.36% |
| 复用减重建 BA（95% 区间） | −1.56 [−5.47, 1.57] | −4.95 [−10.16, 0.00] |
| 完整主面板全对：Source → Related | 89/96 → 83/96 | 83/96 → 81/96 |
| 重建程序 Related 主面板全对 | 85/96 | 87/96 |
| 源程序接受源见证 | 92/96 | 89/96 |
| Related 下误接受旧决策重放（源程序 / 重建） | 6/96 / 5/96 | 5/96 / 2/96 |
| 联合正确（主面板加见证，源程序 / 重建） | 82/96 / 82/96 | 79/96 / 86/96 |

两个预注册区间都包含零，Holm 校正后 p 分别是 0.4350 和 0.1254，所以按平均 BA 看，复用和重建没有显著差别。但 Pro 那边联合正确数 79 对 86，源程序少了 7 个。Background 对照下判决完全一致，说明程序不是对任何数据变动都敏感，而是专门在「需求真的变了」的地方出错。Pro 源程序在 Related 见证上还给出了 2 个 Unknown 和 2 个 Error。

三个案例把错误类型说得很清楚：

- **linear_44**：两个 Flash 源程序都保留了旧的 Elena 标识符。Source 下四个结果全对，到了 Related，公开名字 Elena 指向另一个在线用户，两个程序都拒掉了两个有效结果。重建程序都对，其中一个通过 users API 现查了名字。
- **linear_52**：保留条件任务。Pro 副本 1 记住了源常量 Active，于是拒绝了正确保留 Dormant 的结果，又接受了把状态改回 Active 的错误结果。副本 2 读运行时 before 状态，两个条件下全对。区别就在验收关系本身：终态是和「当前初值」比，还是和「记住的字面值」比。
- **box_141**：指令说合格的 JSON 可以是顶层数组，也可以是 results 数组。Pro 源副本 1 十二个主面板结果全对，却接受了一个漏掉新增必需 JSON 文件的见证。它的 API 读到了那个文件，但谓词只检查包装层根字段，漏掉了 results[0] 里的记录。主面板的局部故障没覆盖到这个集合分支，见证把它暴露出来。

**P2：部署态面板对不对，几乎决定了交付对不对。**

| 分组 | 两个起点都正确交付 | 起点级 |
| --- | --- | --- |
| Related 面板零错误 | 32/33 个分配 | 64/66 |
| Related 面板有错误 | 1/11 个分配 | 2/22 |

起点级正确交付差 87.9 个百分点，任务族聚类区间 [68.8, 100.0]。全部 17 次程序门禁扣留和全部 3 次参考定义的回退都在有错误的那组；被扣留的终态里有 13 个其实满足参考，也就是门禁扣下了已经做对的东西。零错误组里两次错误交付是同一个 Flash Linear27 分配，从头到尾都是失败；反过来，有错误组里 Flash Box130 两次都交付正确。只看源面板不够：通过全部源面板测试的 36 个分配里，3 个 Related 面板有错误的全部交付错误或被扣留。

**四种策略的交付正确数（22 个起点）：**

| 策略 | Flash | Pro |
| --- | --- | --- |
| 中性续写（检查点） | 20/22，修好 14/16 失败 | 22/22，修好 16/16 失败 |
| 程序门禁 | 17/22 | 16/22 |
| 在线门禁 | 20/22 | 21/22 |

自然结束点上 actor 本身就有 20/22（Flash）和 22/22（Pro）成功，中性续写不发起写请求就保住了它们。中性续写相对程序门禁的配对增益：Flash 13.64 [0.00, 27.27]，Pro 27.27 [9.09, 45.45]。

**Linear45 一个完整的失败链路**：程序拒绝了一个分给当前 Backend 团队的正确结果；收到泛化拒绝后，actor 把两个 issue 挪到了旧团队；程序接受，放行了这个失败。中性续写则保住了正确状态。

**固定实例的验收画像（Flash）：** 在同一批 before/after 状态上（36 个任务、29 个族，99 个失败状态加 36 个成功锚点），十二次调用构建的程序 B12 误接受率 3.5%，在线评审 API12 是 31.7%，差 −28.2 [−40.7, −16.7]；但有效锚点接受率 B12 只有 77.8%，API12 是 98.6%。自然面板 BA：B12 92.1%，API12 99.0%；难例集 87.1% 对 96.2%。单次评估中位延迟 0.58 秒对 20.69 秒。程序更严、更快，在线评审更宽、整体更准。这和 VerifierBench 的结论一致：生成的程序拒错很准，认对很差。

**成本：** 中位构建成本 Flash 0.0173 美元、Pro 0.0765 美元；一次在线评审 9 或 12 个状态的面板分别要 0.0188 和 0.0980 美元；按 API 费用算，回本点中位数 Flash 12 次、Pro 10 次评估（范围 2 到 29、2 到 36）。用到十次时，Flash 程序门禁平均 0.0195 美元（自然结束点）和 0.0189 美元（检查点），冷启动是 0.1396 和 0.1390；Pro 十次是 0.0509 和 0.0478。

**构建方法的消融（附录 D）：** 构建时允许读初始状态 API（InitialRead）比只看指令和文档（SelfReview）自然面板 BA 高 12.0 [4.2, 20.4]（Flash）和 12.3 [4.2, 20.8]（Pro）。对 22 个程序的 149 次误拒做归因：109 次是表示或标识符问题，8 次漏了合法替代，7 次是过严的精确匹配，9 次是加了用户没要求的保留条件，16 次是其他任务绑定错误。

诚实泼冷水：

- **所有生成器、评审和 actor 都是 DeepSeek Flash/Pro，且关闭 thinking。** 换模型、开 thinking，误拒率和绑定错误比例可能完全不同。
- **P2 的规模很小**：22 个任务族、44 个分配，区间很宽，Flash 的中性续写增益下界就是 0。32/33 对 1/11 的对比方向很强，但样本量决定了它更像一个强关联，而不是可以外推的效应量。
- **门禁反馈是刻意泛化的**，不带检查项和实体 ID。这样隔离了「判决」本身的作用，但真实 harness 里的 gate 往往会把失败原因回传。中性续写赢，部分是因为门禁的反馈几乎没有信息量，而误拒又会诱导 actor 改动已经正确的状态。
- 程序门禁只用一个按奇偶分配的 Pro 源程序，不挑质量，这是公平的设计，但也意味着它不代表「精选过的 verifier」上限。
- 评分衡量对作者显式参考契约的符合度，GPT-6 Astra 审计支持了参考标签，但「保留条件」「合法替代」的边界本身有解释空间，9 次「用户没要求的保留条件」误拒就是例子。

## 🔬 最有意思的部分

**第一，平均 BA 掩盖了复用失败，完整面板和见证才能抓到。** 93% 的 Related BA 看起来很好，复用减重建的区间也包含零，如果只报这个，结论就是「冻结程序可以放心复用」。但按程序计数，Pro 源程序的联合正确数比重建少 7 个，而且错误类型高度集中：记住旧 ID、记住旧字面值、只检查包装层。这些都是「构建状态里恰好成立、换个状态就不成立」的捷径。149 次误拒里 109 次是表示或标识符问题，和这个画像完全一致。

**第二，门禁的误拒有写副作用。** Linear45 是一个教科书式的反例：门禁拒绝正确结果，agent 为了让门禁满意去改数据，改坏了，门禁反而放行。被扣留的 17 次里 13 次其实是对的。这也呼应了 HarnessVerification 里「完成闸门直接驳回」那一类设计的风险。在可写环境里，gate 的错误代价是不对称的：误放行是少抓一个 bug，误拒绝可能主动制造一个 bug。所以「先加个 gate 总没坏处」这个直觉，在这组设置里不成立。

**第三，中性续写是一个很强的基线。** 一句不带任何判断的「继续检查并完成原始请求，保留已完成的有效工作」，在检查点上把 Pro 的 16 个失败全修好了。它说明这些 actor 的很多失败是「停早了」，而不是「做错了」。任何声称 gate 有用的工作，都应该先赢过这个基线。

## 🤔 我的判断

**定位：生成式 verifier 的复用契约基准，外加一个把判决接入执行的因果测量。** 它不提出新的 verifier 生成方法，贡献是测量设计和资源：97 个任务、可重建的状态、版本化参考谓词、程序源码、API 证据和完整动作历史。

亮点：

1. **把「可复用」写成了可配对检验的契约。** Source、Background、Related 三条件加源决策见证，把「程序从运行时推导需求」和「程序记住了快照」区分开，这是固定实例准确率测不出来的。
2. **把 verifier 质量和下游交付连起来了。** 部署态面板全对的程序 32/33 两次都交付正确，有错的 1/11。这给了一个很实用的上线标准：在目标部署状态上跑一遍带标签的完整面板，全对再上。
3. **给出了不舒服但必要的基线。** 中性续写胜过程序门禁、和在线门禁持平或略好，这让「加 gate」从默认选项变成了需要证据的选项。

问题与局限：

- 单一模型家族、关闭 thinking、四个服务、22 个执行族，外推要谨慎。
- 门禁反馈刻意不含信息，和真实 harness 里会回传失败原因的 gate 不完全可比；带结构化失败原因的 gate 能否赢过中性续写，论文没有回答。
- 程序和在线评审各有偏向：程序误接受 3.5% 但有效接受 77.8%，在线评审有效接受 98.6% 但误接受 31.7%。论文给出了画像，但没有给出一个组合方案（比如程序先筛、在线复核）的实测。

对工程的直接启发：

- **生成验收程序时，强制它从 before 状态现查 ID 和初值，禁止在代码里出现构建时的字面 ID 和状态值。** 这可以做成静态检查：扫描程序源码里有没有出现构建快照中的实体 ID。附录 D 里 InitialRead 带来 12 个点的 BA 提升，说明构建时给它读状态很重要，但读完要「现查」而不是「抄下来」。
- **复用前用「换绑定」的状态跑一遍完整面板，再加一个旧决策重放的见证。** 只在构建状态上测通过，不足以说明能复用。这和我们关心的 farol 式静态 gate、write-judge 式决策模型 gate 是同一个问题：gate 本身也需要在部署分布上验收。
- **在可写环境里，gate 拒绝之后不要让 agent 自由改写。** 至少要回传具体失败项，或者只允许追加不允许回退已完成的写操作；否则先和「中性续写」这个基线比一比，再决定要不要上 gate。
- **算清楚回本点。** Flash 十几次评估就回本，程序门禁适合高频、需求稳定的检查；需求经常变、合法解很多样的任务，在线评审更宽容的接受率可能更值钱。

一句话收束：**冻结的验收程序要现查当前状态而不是背诵当初的答案；而在 agent 还能动手的地方，一个会误拒的门卫，可能比没有门卫更危险。**
