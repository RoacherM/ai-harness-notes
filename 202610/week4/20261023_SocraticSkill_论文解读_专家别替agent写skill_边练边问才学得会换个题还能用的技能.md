# 专家别替 agent 写 skill：边练边问，才学得会换个题还能用的技能

给 agent 攒 Agent Skills，常见做法有两种。一种是让它跑完任务，再从轨迹里蒸馏出一份 `SKILL.md`；另一种是干脆让更强的模型直接写。两种都能在原题上跑得漂亮，可换一个同类但参数不同的题，比如同样是解析 WAL 日志，换了编码方式、换了损坏深度，skill 就开始失灵。原因不难猜：**一次成功的尝试，往往没检验过这个流程在什么条件下成立。** 蒸馏只能抄走它做过的，强模型直接写则只能写它以为对的。

南京大学和阿里巴巴的这篇 **Socratic Skill Learning: Interleaving Teaching and Practice for Transferable Agent Skills**（arXiv:2610.17860）提出 **SSL**：让一个 Educator 在 Student 练习过程中插话，解释、质疑、诊断或保持沉默，而 Student 始终是唯一操作环境、唯一写 skill 的人，可以反问、试验、改写甚至拒绝建议。配套的 **SkillTransferBench** 专门测 skill 能不能迁移到同族的新题上。看完我的感受：这篇最有价值的不是「师生对话」这个包装，而是两个可操作的结论，**指导要在练习中给，不是练完再给；专家的注意力该跟着未解决的问题走，而不是按固定间隔巡检。**

## 核心摘要

SkillTransferBench 从 Terminal-Bench、AgentIF-OneDay、SpreadsheetBench、CodeContests、FullStackBench、OfficeBench 六个来源构造了 35 个任务族、408 个可执行用例，覆盖系统、服务、数据处理、科学计算、金融、办公六个领域。每个族有一道锚点题用于练习，一份公开的族规格（哪些目标不变、哪些地方允许变化），其余成员留作测试。skill 包冻结后，在每个测试用例上开一个全新的求解会话评估。SSL 有两种实现：**Fixed-Window SSL** 每隔 g 次 Student 工具调用让 Educator 审一次；**Issue-Guided SSL** 把 Educator 的每条建议变成带验收标准的「学习问题」，组成一棵问题树，只有问题新开、变化或重开时才触发审阅。主实验用 Qwen3.7 Plus 当 Student 和求解器、Qwen3.7 Max 当 Educator，在 22 个族、155 个测试用例的主集合上：**不给 skill 是 0.723，改编版 Trace2Skill 是 0.761，改编版 SKILL-KD 是 0.751，Fixed-Window SSL 是 0.801，Issue-Guided SSL 是 0.805**，后者比前者少用 61.7% 的 Educator token、少 16.9% 的总获取 token。价值定位：给「skill 怎么学才能迁移」提供了一个比蒸馏和代写都好的流程，以及一个专门测迁移的基准。

## 🎯 为什么这件事值得写

现有的 skill 获取方法大致是三类：从轨迹蒸馏（Trace2Skill），从强弱模型轨迹对比里提补丁（SKILL-KD），以及失败后由老师给反馈再修（SkillLearnBench 的 Teacher Feedback）。它们都有一个共同点：**反馈是在学习者已经做完选择之后才到的。** 学习者测哪个假设、追哪个失败，这些决定已经塑造了 skill，一个没测过的假设很可能已经被写成了可复用规则。

这篇问的问题是：外部专家应该在学习者还在收集证据的时候怎么介入？对做 harness 的人来说，这直接对应一个产品决策，就是「强模型帮弱模型写 skill」这件事，应该让强模型执笔，还是让它当教练。

## 🏗️ 机制：一个只看不动手的老师，一个自己写 skill 的学生

**角色分工。** Student 用的就是将来的求解器模型，它是唯一能操作环境、唯一能写 skill 包的角色；skill 包 \( K=(M,R) \)，M 是 `SKILL.md`，R 是可选的脚本、参考和资产。Educator 只读 Student 最近的推理、工具结果和当前 skill，可以解释、质疑、诊断、建议一个检查，或者什么都不说。

**迁移效用。** 对任务族 f，冻结的 skill 在全新会话里由求解器使用：

$$
U_f(K;\pi_S)=\mathbb{E}_{x\sim D_f}\left[r_f\left(\pi_S(x,K)\right)\right]
$$

**轮次。** 每轮结束时，一个全新求解器拿当前 skill 去做重置后的锚点题，结果和验证反馈进入下一轮；Student 和 Educator 的会话跨轮保留，只有最终的 skill 包被拿去测新题。主实验用 3 轮。

**Fixed-Window SSL。** 每 g 次工具调用（主实验 g=10）审一次，Student 可以澄清或反驳，然后继续。

**Issue-Guided SSL。** 每条建议带一个学习焦点和一个验收标准（什么可观察的证据能解决它），存成学习问题；在一个问题里冒出的新疑问成为它的子节点，子节点关闭后注意力回到最近的未解决祖先。Student 把文件修改打包成一次有摘要、有证据、注明解决哪个问题的修订；问题可以因三种情况关闭：验证过的修订、写明适用条件的证据、或者有证据地拒绝建议。「验证关闭」要求建议之后有一次成功的检查。之后只有问题新开、变化或重开才会再请 Educator；如果锚点上的全新求解器给出矛盾的反馈，对应问题会在下一轮重开，已解决的兄弟节点保留。

## 🧪 关键证据

**主表（Qwen 主集合，22 族 155 用例，0 到 100，括号里是相对不给 skill 的增益）：**

| 方法 | 全部 | 系统 | 服务 | 数据 | 科学 | 金融 | 办公 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 不给 skill | 72.3 | 78.6 | 58.2 | 68.1 | 66.8 | 78.0 | 90.4 |
| 专家直接写 | 72.8 (+0.5) | 77.9 | 58.7 | 71.6 | 72.4 | 72.5 | 91.4 |
| 练完再教 | 74.8 (+2.4) | 73.6 | 64.4 | 73.7 | 76.4 | 78.1 | 91.3 |
| Trace2Skill（改编） | 76.1 (+3.8) | 85.0 | 63.4 | 71.0 | 73.3 | 77.9 | 90.0 |
| SKILL-KD（改编） | 75.1 (+2.8) | 85.5 | 60.9 | 73.2 | 68.2 | 75.7 | 90.3 |
| **Fixed-Window SSL** | 80.1 (+7.8) | **88.7** | 67.3 | 75.1 | 77.0 | 82.4 | 94.1 |
| **Issue-Guided SSL** | **80.5 (+8.2)** | 85.7 | **71.0** | **75.9** | **77.1** | **83.6** | **94.6** |

两个 SSL 在总分和每个领域都排第一、第二。Fixed-Window SSL 比 Trace2Skill 高 3.99 个点，按族配对 bootstrap 的 95% 区间是 [1.45, 6.49]。要求所有私有检查全过的全通过率，从不给 skill 的 32.5% 提到 49.5% 和 50.8%。

**专家怎么介入（共享 10 族 77 用例，相对不给 skill 的增益，pp）：**

| 协议 | Qwen | DeepSeek | Kimi |
| --- | --- | --- | --- |
| Fixed-Window SSL | +4.1 | +3.1 | +8.2 |
| Issue-Guided SSL | +4.5 | +2.5 | +7.4 |
| 专家直接写 | +1.1 | +1.2 | +5.8 |
| 练完再教 | −0.7 | +0.5 | +4.1 |

三组模型里排序一致：两种边练边教都超过专家直接写，练完再教在每组都落后于专家直接写。在主集合上，Fixed-Window SSL 比练完再教高 5.31 个点，获取 token 还少 21%。

**省专家的钱。** 主集合上把固定间隔改成 g=5 或 g=20 都不如 g=10（都是约 77.6），而 Issue-Guided 在 0.805 的效用下，审阅次数少 47.8%，每次审阅的 token 少 26.7%，每百万 Educator token 带来的增益是 Fixed-Window 的 2.75 倍。DeepSeek 和 Kimi 上分别少用 63.8% 和 77.4% 的 Educator token，效用差距都在 1 个点以内；不过 DeepSeek 因为 Student 多干了活，总 token 反而上升。

## 🔬 最有意思的部分

**一是教学需求会下降，但 skill 还在长。** 作者追踪了 66 次 Fixed-Window 运行里的 630 次审阅：给出建议的比例从第一轮 73.0% 降到第三轮 16.1%，建议内容也从讲道理转向诊断。可是在锚点已经满分之后的 99 轮里，有 98 轮 skill 包仍在修改。按轮次调整后，比起沉默，一条建议之后下一次调用写文件的概率高 23.9 个点，十次调用内 skill 被修改的概率高 38.6 个点。建议确实被落进了 skill 里。

**二是 Student 会改进老师的建议，而不是照抄。** HTML 财报这个族里，Educator 建议「用其他条目推导出报告值来发现不一致」。Student 先用通用算术实现，结果标出了 4 个指标，其实只有 1 个错；看了输出后，它换成财务恒等关系和反向推导，准确定位到第 210 行的那条错误。最终的 skill 保留了这些关系，并区分「没检验过的值」和「被证伪的值」，一个全新求解器在没见过的现金流量表上 4 项检查全过。**建议只负责指方向，证据决定它最后变成什么样的知识。**

**三是固定间隔审阅越到后面越浪费。** 随着上下文累积，每次审阅的 token 从第一轮到最后一轮涨了 5.3 倍，而最后一轮审阅 token 里有 85.8% 花在了最终说「没意见」的审阅上。Issue-Guided 的问题树正是为这个设计的：没有未解决的问题就不叫老师。

## 🤔 我的判断

**定位：skill 获取方向很扎实的一篇，流程可直接搬，基准规模和模型覆盖还偏小。**

亮点三条：

1. 「Student 执笔、Educator 只读」这个约束很关键。专家直接写在三组模型里都只有很小的增益，说明强模型写的 skill 对弱模型并不天然适用，skill 要由使用它的模型自己在环境里验证过才可靠。
2. 「练完再教」落后于「专家直接写」这个结果很有说服力：反馈到得太晚，早先的选择已经固化进 skill，事后修补救不回来。
3. Issue-Guided 的学习问题树，把每条建议绑定一个验收标准，这其实就是给 skill 修订加了一个轻量的测试闸，和最近几篇「skill 入库要过测量闸」的思路是一致的。

问题与局限：主结果只有 Qwen 一组模型跑了 3 次，DeepSeek 和 Kimi 只跑 1 次；主集合 22 族 155 用例，族内用例 5 到 17 个，迁移只测同族内，没测跨族；Trace2Skill 和 SKILL-KD 是作者改编的版本，和原始实现不完全一样；不给 skill 时办公类已经 90.4 分，天花板很低，部分领域的差距空间有限。

对工程的直接启发，尤其是给 Pi 这类 harness 自动积累 skills 的场景：

- **强模型当教练，不当作者。** 自动生成 skill 时，让执行模型自己写、自己验证，强模型只读它的过程和当前 skill，按需提问或指出缺失的检查。
- **skill 要配一份「族规格」。** 写清楚哪些目标不变、哪些可以变化，学习时按这份规格去试变化，测试时用同族新题而不是原题，否则测不出迁移。
- **把建议变成带验收标准的问题。** 每条反馈写成「要查什么、什么证据算解决」，没解决的问题才值得再叫专家，这比固定频率的审阅便宜得多。
- **让学生有权拒绝建议。** 允许 Student 用证据拒掉一条建议并记录原因，这本身就是 skill 里很有价值的「适用条件」信息。

一句话收束：**能迁移的 skill 不是被写出来的，是被试出来的；专家的价值在于问对问题，而不是替人作答。**
