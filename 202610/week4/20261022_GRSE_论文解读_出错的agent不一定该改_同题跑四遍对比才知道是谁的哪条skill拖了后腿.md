# 出错的 agent 不一定该改：同题跑四遍对比，才知道是谁的哪条 skill 拖了后腿

你有没有过这种体验：一个两段式的 agent 团队，检索 agent 负责找证据，回答 agent 负责作答。最后答案错了，复盘时大家自然盯着回答 agent，给它加一条「答不出来要再想想」的规则。下一轮分数没涨，反而有几道原本答对的题被改错了。后来才发现，问题出在检索 agent 那条搜索语句上，**回答 agent 只是在拿不到证据时诚实地说了「没提到」。**

Mayo Clinic、曼彻斯特大学、阿里和上财的这篇 **Which Agent's Skill Should Change? Group-Relative Credit Assignment for Evolving Multi-Agent Teams**（arXiv:2610.27227）研究的正是这个问题：在不更新参数、只靠改 skill 来进化的多 agent 团队里，**团队的一个总分到底该记到哪个 agent 的哪条 skill 头上**。现有方法看哪条 skill 出现在轨迹里就给它记功，作者一句话点破：**出现不等于负责**，一条有害 skill 只要在成功轨迹里出现过，照样被加分。他们的方法 GRSE 借鉴 GRPO：同一道题、同一套 skill 库跑四遍，拿四次执行对比来归因。看完我的感受：这是把「组内相对优势」从训练权重搬到了训练 skill 上，而且配了一套能被检查的失败诊断格式，对做 skills 自进化的人很有参考价值。

## 核心摘要

GRSE（Group-Relative Skill Evolution）每轮做三件事。第一，对每道题在固定 skill 库下从全新上下文采 \(G=4\) 条完整团队轨迹，按 GRPO 方式算组内相对优势。第二，一个群体相对 critic 同时读这四条轨迹，按 agent 逐个比较高优势和低优势执行的差异，给每个「agent 加 skill」对打分（帮助、冗余、有害、中性，外加效用分 \(u\in[-1,1]\)），并输出结构化失败诊断：哪个 agent、哪条 skill、八类失败类型之一、引用的失败步骤和成功步骤、解释、修正建议、动作（细化、新建或不改）。接口会检查引用的步骤是否存在、是否属于该 agent、失败步骤是否来自没拿满分的执行、成功步骤是否来自满分执行；工具故障和归因不明只允许「不改」。第三，跨题聚合：按「被多少道不同的题支持」计权，同一道题跑四遍不算四份证据；然后沿用 MASkills 的编辑算子去细化、剪枝、合并、新建 skill，每个 agent 的候选库只有在验证集上不低于原分才保留。在 HotpotQA 和 LoCoMo 上，用 Qwen3.8-27B 和 Gemma-4-31B-it 两个执行模型、Qwen3.8-27B 当 critic，GRSE 在 HotpotQA 上 83.7 对 MASkills 80.6，LoCoMo 多跳题 F1 分别加 6.7 和 3.2。最有说服力的是一个「投毒」实验：**初始 skill 库里埋了有害和无关 skill，GRSE 对五条有用和有害 skill 的归因符号全对，恢复到只用有用 skill 的水平（66.9 对 66.7），MASkills 错了两条，最终比起点还低。** 价值定位：给多 agent skill 进化补上了最缺的一环，可验证的行为级信用分配。

## 🎯 为什么这件事值得写

skills 让 agent 行为变成可编辑的自然语言，于是「不训练权重、只改 skill」成了很热的自进化路线：Reflexion、ExpeL、EvoSkill、SkillRL 都在单 agent 上做；MASkills 把它推到了多 agent 团队，但它对每条轨迹单独记功。

多 agent 的信用分配在 MARL 里是老问题，有差分奖励、反事实基线等解法；到了语言模型团队，问题变成了「自动失败归因」。难点有两个：

| 难点 | 例子 | GRSE 的回应 |
| --- | --- | --- |
| 出错的地方不等于该改的地方 | 回答 agent 说「没提到」，其实是检索语句没搜到 | 同题多次执行对比，看哪个 agent 的行为在成败之间有差异 |
| 归因要具体、可检查 | 「推理不够严谨」这种解释无法验证 | 结构化诊断，必须引用具体失败步骤和成功步骤，并通过一致性检查 |

还有一个容易踩的坑：同一道题跑多次，不能当成多份独立证据，否则一道难题就能主导整个库的修改。

## 🏗️ 机制：组内对比、结构化诊断、按题计权

**组内相对优势。** 对题目 \(q\) 的 \(G\) 次执行：

$$
A_{qg}=\frac{r_{qg}-\bar r_q}{\sigma_q+\epsilon},\qquad \bar r_q=\frac{1}{G}\sum_g r_{qg}
$$

critic 同时拿到绝对奖励和相对优势。四次执行共享题目和 skill 库，高低优势之间的行为差异就起到了类似反事实基线的作用。奖励全相同的组没有对比，但仍能看出哪些行为一直成功或一直失败，默认保留。

**八类失败类型。** skill 没被遵守、skill 本身有缺陷、缺少能力、交接错误、证据缺失、答案格式、工具故障、归因不确定。这个划分把「该改 skill 的」「该新建 skill 的」和「不该因此改 skill 的」分开了。

**一致性检查。** 引用的步骤要存在、属于被点名的 agent；失败步骤必须来自没拿满分的执行，成功步骤必须来自满分执行；细化动作要求该 skill 确实出现在被引用的失败轨迹里；没有成功对照的修正只标为假设。

**按题计权的新建 skill。** 把诊断按 (agent, 失败类型, skill, 动作) 分组，支持度是出现这种模式的**不同题目数**：

$$
w(p)=\left|\{\,q:\exists d\in\mathcal D_q,\ \mathrm{key}_q(d)=p\,\}\right|
$$

**验证门。** 每个 agent 的候选库单独替换进团队，验证分 \(\hat s_i\ge b_t-\delta\) 才接受。归因错了的修改会在这里被拦下。

## 🧪 关键证据

- **HotpotQA**：Qwen3.8 执行时 GRSE 83.7，MASkills 80.6（加 3.1），离最强单模型基线 Self-Refine 的 84.1 只差 0.4；Gemma4 执行时 82.8 对 82.3，各方法都挤在 81.1 到 83.3 之间。
- **LoCoMo**：除开放域（最小的类别，52 道题）外每类都超过 MASkills。多跳题 F1 加 6.7、BLEU 加 5.3（Qwen3.8），F1 加 3.2、BLEU 加 2.8（Gemma4）；时间类题两种执行模型下都是最高（73.4、67.4）。Gemma4 下 GRSE 相对空库在每个类别都涨（1.8 到 11.2 F1），MASkills 在时间类反而比空库低 4.3；Qwen3.8 下 MASkills 在多跳题比空库低 3.0，GRSE 涨 3.7。多跳题上 GRSE 的跨运行波动也更小。
- **涨分来源**：MASkills 改错的原本答对的题，在 HotpotQA（Qwen3.8）上是 GRSE 的三倍，在 LoCoMo（Gemma4）上是两倍，后者的损失把修复全部抵消（总变化 −0.3 对 +7.4）。GRSE 在 LoCoMo 上的 7.4 里有 6.0 来自「原本拒答变成答对」，并且把「检索证据里没引用任何对话轮次」的比例从 22% 降到 14%；MASkills 这个比例一直是 22%，34 道拒答转答对里有 9 道是没证据硬答的，GRSE 61 道里只有 5 道。
- **成本**：每题跑 4 遍，执行 token 是 MASkills 的 1.6 到 2.9 倍，墙钟时间 1.3 到 1.8 倍，只发生在训练阶段，推理不变。

小瑕疵：结论段写的是「除多跳题外」，和正文、摘要的「除开放域外」对不上，按正文和表格理解应是开放域。

## 🔬 最有意思的部分

**一是投毒实验。** 在 LoCoMo 单跳题（453 道测试题）上，两个 agent 各保留一条有用 skill，再各塞两条措辞合理但有害或无关的 skill，不告诉 critic 和优化器哪些是坏的。GRSE 最终 66.9 F1，几乎等于只用有用 skill 的 66.7，拒答率从 9.7% 降到 4.6%，比 MASkills 高 8.5 F1。看第一轮聚合后的效用：GRSE 对五条有用和有害 skill 的符号全对，有用和有害的均值差 0.31；MASkills 错两条，均值差只有 0.03。最典型的是回答 agent 那条有害的 `verbatim-evidence-guard`：MASkills 给它正分，接下来两轮还继续加分，GRSE 判为有害并在第 3 轮剪掉。无关 skill 两边都给了 0 分，但 GRSE 原样留着，MASkills 却把它合并进了检索 agent 的新协议。

**二是全同奖励的组也有用。** 按 DAPO 的做法只把奖励有差异的组送给 critic，每轮 32 组里会丢掉 7 到 13 组，类别平均 F1 掉 0.5，开放域掉 4.1，单跳反而涨 2.4。没有对比的组仍在告诉 critic 哪些行为稳定地成功或失败。

**三是用标签反而偏科。** 让 critic 看数据集类别标签来组织证据，总分最高，但全是靠占测试集 54% 的单跳题撑起来的，其余每类都更差，开放域掉 6.7，类别平均最低。共享库会被最大的类别拉走。

**四是迁移。** HotpotQA 和 LoCoMo 多跳题互换最终库：GRSE 的迁移库比空库好（加 1.3 和 1.8），在目标任务上自己学的库又比迁移库好（加 1.9 和 1.2）；MASkills 在目标任务上自己学的库反而不如迁移来的，也不超过空库。

## 🤔 我的判断

**定位：方法创新，把多 agent skill 进化里的信用分配做成了可对比、可检查、可聚合的流程。**

亮点三条：

1. 「出现不等于负责」这个诊断非常准，投毒实验把单轨迹记功的失败模式展示得很清楚，任何按 skill 使用频率给分的系统都该警惕。
2. 结构化失败诊断把 LLM critic 的输出约束成可校验的数据：引用必须存在，失败和成功步骤必须来自对应的执行，工具故障不许改 skill。这是 LLM 当裁判时最该补的一层。
3. 按不同题目数计权、按 agent 单独过验证门，这两个细节都直接降低了「一道怪题带偏整个库」的风险。

问题与局限：只测了两 agent 顺序团队和两个问答基准，离长程、工具密集的 coding 或工作区任务还远；critic 和优化器固定用一个模型，没测 critic 换模型的稳定性；训练成本翻倍以上；收益在某些设置下很小（Gemma4 的 HotpotQA 只加 0.5）。

对工程的直接启发：

- **skill 自进化要做组内对比，不要单条复盘。** 同一任务在同一套 skills 下多跑几次，拿成功和失败的执行对比去定位，比让模型看一条失败轨迹写反思靠谱得多。
- **失败归因先分类，再决定改不改。** 工具故障、交接错误、skill 缺陷、缺能力，处理方式完全不同；把「不改」作为合法输出，能挡住大量无效修改。
- **skill 的归因证据要带引用。** 每次修改都附上被引用的失败步骤和成功步骤，修改记录就成了可审计的 golden 线索，也方便以后回滚。
- **给 skills 库做投毒回归。** 定期往库里埋几条看起来合理的坏规则，看进化流程能不能识别并剪掉，这是检验信用分配是否靠谱的低成本办法。

一句话收束：**团队输了，先别急着骂最后开口的人；把同一局多打几遍，看是谁的哪一步不一样，才知道该改谁。**
