# 让 agent 自己造考卷：最好的也只排对四分之三，跑起来最便宜的那份反而排得最准

你有没有过这种体验：每改一次 prompt、换一个 skill、调一次 harness，都想跑一遍完整评测确认没退步，可完整跑一遍 SWE-bench 加 GDPval 加 HLE 要几个小时、几百美元，于是你开始偷偷只跑一个子集，再凭感觉挑题。人类专家会这么干，tinyBenchmarks 这类工作也在系统地这么干。问题是，**如果要让 agent 做递归自我改进（RSI），这一步「造一套又准又便宜的反馈」也得交给 agent 自己。**

俄勒冈州立大学、UCSD、宾州州立和 AG2 AI 的这篇 **EvalResearchBench: Can AI Agents Build Their Own Feedback for Recursive Self-Improvement?**（arXiv:2610.04184）第一次把「评测设计」本身当成一个研究任务来考：给 agent 三小时、两笔各 100 美元的预算，让它选题或造题、写评分器、在试跑里修，最后冻结一个可执行的评测器，再拿它去和 14 个真实基准的分数比对。看完我的感受：这是对「自造反馈」这条路最务实的一次摸底，结论不浪漫：**最好的评测器排对约 75% 的模型对，离 91% 的天花板还很远；在可见基准上拟合得最好的，在隐藏基准上并不最好；人类设计的随机抽题基线依然很能打。**

## 核心摘要

ERB 的设定里有三种角色：研究员（一个跑在 Codex 或 Claude Code harness 里的模型，负责设计评测）、候选（被测的模型）、目标基准（评测器应当复现其分数的成熟基准）。研究员能看到目标说明、可用的原始题目和评分资源、历史执行轨迹、开发候选的参考分数，并通过计量网关调用 4 个开发候选；另有 9 个封存候选和 8 个封存目标在研究期间完全不可见。提交物至少 100 道题，配可执行评分器和固定聚合规则，按编码、协作办公（co-work）、推理三个领域各出一个分。评估时在独立预算（总计 120 美元、每个候选 30 美元）下把冻结评测器跑在全部 13 个候选上，用两把尺子比：**Score** 是 100 倍的 Lin 一致性相关系数（CCC，既要排序对，也要分数水平和离散度对），**PA** 是候选对之间排序一致的比例。9 个研究员配置的结果：GPT-6 Astra 总 Score 最高（22.79），Grok 4.7 总 PA 最高（74.87%），没有谁在所有领域、所有指标上领先；编码是多数评测器最弱的领域。Fable 5.1 在开发目标上 Score 最高，在封存目标上却不是。人类设定配额的随机抽题基线 Random120 在 12 个共同候选上，八个 agent 评测器里有七个 Score 超过它，但只有四个 PA 超过它。最反直觉的一条：**执行成本最低的评测器（Grok 4.7，整套 8.63 美元）拿到了最高 PA**，而题量相近的 Fable 5.1 要 109.41 美元。价值定位：把 RSI 里最常被假设为「已经有了」的那一环，评测反馈本身，变成了一个可以被测量、被比较的 agent 能力。

## 🎯 为什么这件事值得写

现有的自动改进工作，几乎都把评测当成给定的：PostTrainBench 让 agent 选数据和后训练算法，但目标基准和评测 harness 是固定的；RSIBench-Data 让 agent 根据固定评测服务返回的分数改数据策略；AlphaEvolve 靠用户提供的评估函数进化程序。换句话说，**「测什么、怎么打分、怎么让重复测量负担得起」一直是人在决定**，所以把自主改进推广到一个新领域，仍然需要人先设计一套评测。

另一边，自动化评测设计的工作（PACE 选便宜题去校准昂贵的 agent 目标、AutoBencher 和 BenchAgents 自动造基准、BenchBench 比较模型造的题库质量）都只解决了一部分，没有一个把完整问题摆出来：在有限实验预算下选测量策略、花钱试跑、根据试跑失败决定是加难题、换覆盖、修 rubric 还是加执行预算，最后交一个能追踪复杂目标基准的可执行评测器。作者把这叫作 **autonomous evaluation research（自主评测研究）**。

对做 harness 闭环的人来说，这件事的意义很直接：judge 和 eval 是自进化回路的「传感器」，传感器自己是怎么造出来的、造得准不准，过去基本没人量过。

## 🏗️ 机制 / 任务定义

**三笔预算分开记。** 研究员推理（agent 自己思考和用工具）、开发测试（调候选和辅助模型）、独立评估（跑冻结评测器）三笔钱互不挪用，前两笔各 100 美元，研究时限 3 小时。分开记是为了防止 agent 的思考吃掉试跑预算。

**可见性分开分配。** 候选和目标的可见性独立设定：

| 组成 | 开发可见 | 封存 |
|---|---|---|
| 候选 | GPT-5.5、GLM-5.2、DeepSeek V4 Flash-0731、Qwen3.8 Max（4 个） | GPT-6 Astra、GPT-5.6 Sol、Kimi K3、MiMo V2.5 Pro 等 9 个 |
| 编码目标 | DeepSWE、SciCode、SWE-bench Multilingual | Terminal-Bench 2.1、ProgramBench、SWE-bench（Vals） |
| 协作办公目标 | GDPval、AdvancedIF | BrowseComp、Harvey LAB-AA、AA-Briefcase |
| 推理目标 | HLE | AA-LCR、CritPt |

**打分。** 领域分是完成题目的加权平均 \( x_{a,m,d}=\sum_i w_{a,i}s_{a,m,i}/\sum_i w_{a,i} \)，权重由研究员在冻结前定。与每个目标的对齐用两把尺子：

$$
\mathrm{Score}_{a,t}=100\cdot\frac{2\,\mathrm{Cov}(x,y)}{\mathrm{Var}(x)+\mathrm{Var}(y)+(\bar x-\bar y)^2}
$$

PA 则是参考分不并列的候选对里，测量分排序方向一致的比例（测量并列记半分）。CCC 惩罚均值和尺度的偏差，所以「排序对但分数挤在一起」在 Score 上会吃亏。

**基线。** Random120 从 16 个公开题源按人设定的配额各抽 40 道编码、协作、推理题，等权重，不用任何目标参考分。

## 🧪 关键证据或主结果

- **天花板与现实。** 目标基准之间本身就互相矛盾，排序冲突把总体 PA 的上限压在 91.20%；最好的评测器 PA 约 75%。
- **没有全能选手。** Grok 4.7 编码 Score 最高（23.28），Astra 协作办公最高（42.06），Opus 5 推理最高（38.46）。Astra 和 Opus 5 的编码总 Score 甚至是负的（-0.20 和 -0.31）。
- **开发拟合不等于迁移。** Fable 5.1 开发目标平均 Score 23.40 居首，封存目标只有 20.87；Grok 4.7 封存目标 26.14 最高。
- **随机抽题很强，尤其在编码。** Random120 的编码 PA 是 75.25%，比所有 agent 评测器都高；agent 的优势主要集中在协作办公和推理。相对 Random120，Astra 的编码 Score 低 25.6，协作高 36.3，推理高 29.2。
- **贵不等于准。** 整套评估花费：Grok 4.7 107 题 8.63 美元，Fable 5.1 110 题 109.41 美元（其中 rubric 裁判 33.97），Opus 5 108 题 105.24 美元。同一批候选上 Fable 5 的生成成本是 Grok 的 7 到 17 倍，完成题数差距不到 10%。每题输出上限的总和，Grok 是 0.115M token，Fable 5.1 是 1.374M。
- **失败方式很具体。** Fable 5 跑到评估预算上限也没跑完候选面板，只能用插补场景单列；DeepSeek V4 Pro 的短确定性检查让分数挤在天花板附近。

冷水：每个研究员只跑了一个 episode，没有种子方差；候选只有 13 个，CCC 和 PA 在这么小的面板上本身就抖；参考分是公开快照，部分目标的分数尺度换算（比如 Elo）需要人为约定。

## 🔬 最有意思的部分

**权重是双刃剑。** Grok 的做法是按「哪些开发候选能过」给试跑题分组，再搜一组权重去复现可见的排序和分差。结果协作办公 20 道题里有 6 道几乎拿走了全部权重。把它的评分重算成等权重，编码和协作的 Score 都明显上升，PA 几乎不变。**冻结的题库里其实有信号，是它自己选的权重没用好。** 这是一个非常典型的「对开发集过拟合」：权重拟合了 4 个可见候选的排序，牺牲了分数尺度的忠实度。

**难度和真实感不等于测量价值。** K3 在试跑接近满分后加了 5 道硬编码题，Astra 读了上游软件任务后加了仓库追踪题。作者做了「删掉这组题，和同领域同数量随机删题比」的反事实：这些看起来很用心的题组影响都很有限；反倒是 Astra 的 8 道电子表格题对协作办公两个指标贡献最大。题目的价值取决于它能不能按目标的方式把候选拉开，而不是它看起来有多难、多像真活。

**试跑反馈决定了成本形状。** Grok 在难的 HLE 试跑里撞上输出截断、看不到答案，于是转向短代码、输出预测、数值检查和本地评分器，提示中位长度只有 233 个字符，评估时不调任何辅助模型。Fable 5.1 遇到同样的截断，选择保留长的专业交付物并加大输出上限，再配一个 rubric 裁判。两条路都「合理」，成本差了一个数量级，而 PA 是便宜的那条更高。作者把执行成本拆成两个设计选择：候选必须产出什么，以及答案怎么被判。

**题量越多越稳，但问题是怎么少花。** 在 Astra、GLM-5.3、K3 的冻结题库上做嵌套子集，题越多，平均 Score 越高，Score 和 PA 的波动越小。小子集会漏掉有用的题族，或让少数回答过度代表。设计问题于是变成：用更少的调用保住这些信号和稳定性。

## 🤔 我的判断

**定位**：测量基础设施。它不提出新方法，而是给「agent 自造评测」这件事定了一个可复现的考场：预算分账、可见性隔离、冻结后独立评估、CCC 加 PA 双指标，外加一个诚实的人类基线。

**亮点三条**：
1. 开发目标和封存目标分开，直接暴露了「对可见参考拟合」这个自造反馈里最大的风险，而且给出了量化证据。
2. 把构建成本和执行成本拆开。评测器只造一次，却要为每个新候选反复跑，RSI 回路真正在乎的是后者。
3. Random120 这个基线很有分寸：它提醒我们，人类积累的题源、配额和评分器本身就是很强的先验，agent 的价值在于找到「保留目标相关差异」的题，而不是更努力地迭代。

**问题与局限**：单 episode、小候选面板、领域只有三个；研究员的 harness 只有 Codex 和 Claude Code 两种，harness 本身对结果的影响没有拆开；评分里的 LLM 裁判（rubric judge）本身的校准没有单独审计。

**对工程的直接启发**：
- 给自己的 harness 做回归评测时，留一组「造评测时完全不看」的封存基准，专门检查评测器的迁移，而不是只看它能否复现你调过的那几个参考分。
- 警惕权重搜索。如果你按开发集排序去调题目权重，先和等权重版本对比一次；很可能等权重更忠实。
- 优先短答案、本地可判、确定性的检查，把 LLM rubric 裁判留给真正需要它的少数题，这和「先 rubric 二值检查、代码检查优先于 LLM 裁判」的建设顺序完全一致。
- 同时报 CCC 类的「分数忠实度」和 PA 类的「排序一致性」，两者会给出不同的赢家。

一句话收束：**RSI 回路里最先该被自动化、也最先该被怀疑的，是那个告诉你「变好了」的传感器**；这篇告诉我们，今天的 agent 能造出一个四分之三靠谱的传感器，但还不能替你决定它在没见过的地方也靠谱。
