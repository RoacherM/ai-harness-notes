# 结构化输出掉分别怪解码器：同一提示同一格式下加约束只涨不跌，答案空间约束最多多 17.4 点

你有没有过这种体验：为了让工具调用和下游解析稳定，把模型输出切到 JSON schema 加 constrained decoding，结果准确率掉了一截。然后你在网上搜到一堆说法：「让模型在 JSON 里推理会伤害推理能力」「structured output 会让模型变笨」，于是有人给 schema 加 `reason` 字段，有人先自由推理再让第二个模型抽取，有人干脆关掉约束靠正则兜底。

这类技术统称 **constrained decoding**（Outlines、guidance 这类，在每一步把不合法 token 的 logit 屏蔽掉）。问题是：**掉分到底是解码器屏蔽 token 造成的，还是因为我们在比较时悄悄换了提示词和输出格式？**

Télécom Paris 和 Nokia Bell Labs 的 **Constrained Decoding: Harmful or Beneficial? Revisiting Its Impact on LLM Performance**（arXiv:2610.35328，ICLR 2027）专门把这两个因素拆开。看完我的感受：这篇对做 harness 和 serving 的人很实用，它给 schema 约束正了名，**真正伤分的是「换了一种让模型说话的方式」，屏蔽本身在答案合法的前提下只会把概率往对的地方推**；更有意思的是，它把约束分成了三种，其中「答案空间约束」几乎是白捡的分。

## 核心摘要

论文把约束分成三类：**格式约束 FC** 只保证输出结构（比如 JSON，答案字段允许任意字符串）；**有效性约束 VC** 在 schema 里编码答案空间的先验（比如答案是非负整数、0 到 999 的整数、恰好四个或八个字母）；**推理约束 RC** 限制推理轨迹（比如强制以「Let's think step by step」开头）。理论部分证明：在提示词、期望输出格式和推理轨迹都相同的条件下，只要正确答案本身满足约束，逐 token 屏蔽加局部归一化只会让正确答案的概率不降；如果约束在正确答案的路径上真的屏蔽掉了模型赋予正概率的非法 token，概率就严格上升。实验覆盖 Qwen3、Qwen3.5、Llama3、Gemma2、SmolLM3 四个家族共 11 个 1.7B 到 32B 开源模型，任务包括 GSM8K、Last Letter、作者扩展的 LastLetter-Extended（八个名字）和 AIME 2026，比较三种「推理加可抽取输出」策略：JSON 里带 `reason` 字段、两步 NL-to-Format、单次生成里靠触发 token 切换的 InWriting，约束实现用 Litelines（基于 outlines-core）。结论：**JSON 和自由推理之间的差距确实存在，但在同一提示同一格式的对照下，FC+VC 始终不低于无约束；VC 比 FC 带来的增益更稳定，最多 +17.4 点；RC 只有在强制的轨迹本身有益时才涨，Qwen3.5-4B 在 AIME 2026 上反而掉了 6.6 点。** 价值定位：给「结构化输出伤推理」这个流行说法做了一次干净的因果消融，并且把约束从格式工具扩展成了一种答案一致性的执行机制。

## 🎯 为什么这件事值得写

在 agent harness 里，结构化输出不是可选项：工具调用要符合参数 schema，子 agent 要回结构化结果，裁判和决策模型要输出可解析的判决。前几天还有人报告用 vLLM 的服务端约束解码把某开源模型工具调用的 schema 准确率拉满。可另一边，「约束解码会伤推理」的说法一直流传，相关论文给出的解释也分成两派：

- 一派认为是约束解码本身的问题，比如有限输出文法降低表达力、约束生成造成分布偏移，于是提出加 `reason` 字段、两步生成、触发 token 切换等补丁；
- 另一派认为主要是提示层面的差异，或者约束和非约束的比较本身就不公平。

这篇论文站在第二派，但它做得更彻底：先给出理论条件，再在固定提示、固定期望格式、固定推理轨迹的前提下做因果消融。

## 🏗️ 机制：一个不等式和三种约束

设输入为 $x$，推理轨迹 $R$ 固定，答案序列 $Y=(s_1,\dots,s_T)$。约束解码每一步屏蔽不允许的 token 并局部归一化：

$$
P_C(s_t\mid x,R,s_{<t})=\frac{P_\theta(s_t\mid x,R,s_{<t})\,\mathbb{1}[s_t\in V_C(s_{<t})]}{Z_t(x,R,s_{<t})},\quad 0<Z_t\le 1
$$

于是整条答案的概率是

$$
P_C(Y\mid x,R)=\frac{P_\theta(Y\mid x,R)\,\mathbb{1}[Y\in\mathcal{Y}_C]}{\prod_t Z_t}
$$

**假设 1（约束是可靠的）**：正确答案 $Y^*$ 满足约束 $C$。此时约束下的期望准确率 $P_\theta(Y^*\mid x,R)/\prod_t Z_t^*$ 不小于无约束的 $P_\theta(Y^*\mid x,R)$，也就是**不会伤分**。

**假设 2（正确路径上有非平凡屏蔽）**：在 $Y^*$ 的某个前缀上，约束屏蔽了一个模型赋予正概率的非法 token。此时 $Z^*<1$，准确率**严格上升**。如果模型本来就完全遵守格式，$Z^*=1$，约束就没有效果。

这个推导直接给出了三类约束的直觉：

| 约束 | 做什么 | 理论上的效果 |
| --- | --- | --- |
| FC 格式约束 | 只保证结构，答案字段设为 `str` | 模型已经守格式时无效；会漏括号引号时把那部分概率挪回来 |
| VC 有效性约束 | 在 schema 里编码答案空间先验 | 屏蔽的非法 token 更多，$Z^*$ 更小，增益更大 |
| RC 推理约束 | 限制推理轨迹 | 完全排除好轨迹时一定伤分；只保留好轨迹时一定涨；实际是部分保留，结果不确定 |

实验里 VC 的具体配置很朴素：GSM8K 答案限定为非负整数，AIME 2026 限定为 0 到 999 的整数，LastLetter 限定为恰好四个字母，LastLetter-Extended 限定为恰好八个字母。schema 用 Pydantic 定义，比如 JSON 策略是 `reason: str` 加 `answer: int = Field(ge=0, le=9_999_999_999)`；FC 对照则把 `answer` 设为 `str`。

三种「既推理又可抽取」的策略：

- **JSON**：在 JSON 里带 `reason` 字段，约束从第一个 token 一直持续到结束；
- **NL-to-Format**：第一步自由推理，第二步用另一个模型（Qwen3-32B）抽取成目标格式；
- **InWriting**：单次生成，先自由推理，遇到触发 token 再切换到约束模式输出 `{"answer": ...}`。

## 🧪 关键证据

**先承认差距存在。** 无约束的 JSON 在一些模型上几乎崩溃，比如 GSM8K 上 Gemma2-9B 的无约束 JSON 是 0，LastLetter 上 Llama3-8B、Gemma2-9B、Qwen3-1.7B 的无约束 JSON 都是 0。这和前人观察到的「JSON 推理不如自由推理」一致。

**再看同格式对照。** 只要把提示和期望格式固定，加上 FC+VC 基本都涨。GSM8K 上的例子（无约束 → FC+VC）：

| 模型 | JSON | InWriting | NL-to-Format |
| --- | --- | --- | --- |
| Llama3-8B | 42.1 → 71.8 | 74.7 → 77.8 | 76.4 → 77.1 |
| Gemma2-9B | 0 → 86.7 | 82.9 → 86.7 | 83.6 → 84.4 |
| Qwen3-8B | 56.7 → 90.9 | 89.4 → 91.4 | 88.8 → 90.1 |
| Qwen3.5-2B | 61.0 → 69.9 | 47.1 → 74.9 | 69.0 → 72.1 |
| Qwen3.5-9B | 91.2 → 91.9 | 90.4 → 93.9 | 91.1 → 92.6 |

**FC 和 VC 拆开看（LastLetter，InWriting 策略，无约束 → +FC → +FC+VC）：**

| 模型 | 无约束 | +FC | +FC+VC |
| --- | --- | --- | --- |
| Llama3-8B | 53.6 | 53.6 | 71.0 |
| Gemma2-9B | 42.5 | 42.6 | 56.6 |
| Qwen3-1.7B | 54.2 | 55.0 | 65.2 |
| Qwen3.5-2B | 50.1 | 63.0 | 75.5 |
| Qwen3.5-9B | 87.6 | 87.6 | 92.8 |
| Qwen3.5-27B | 93.9 | 94.7 | 95.7 |

模型已经守格式的时候 FC 几乎没作用（Llama3-8B 53.6 → 53.6），真正拉开差距的是 VC，Llama3-8B 在这一格上的 17.4 点就是论文说的「最多 17.4」。JSON 策略下 FC 的作用会大一些，比如 Qwen3.5-9B 从 23.1 到 86.7，因为它无约束时 JSON 经常解析不出来。

**解析率。** 加 FC 之后，InWriting 和 NL-to-Format 的解析率都在 99.6% 以上，JSON 大多在 93% 以上，最低是 Qwen3.5-2B 在 GSM8K 上的 88.4%；最难看的是无约束 JSON，GSM8K 上 Gemma2-9B 只有 0.2%，Qwen3-1.7B 28.5%；LastLetter-Extended 上 Llama3-8B 和 Gemma2-9B 都是 0。即便是 Qwen3.5-27B，无约束 JSON 在 LastLetter-Extended 上的解析率也只有 82.4%，加 FC 到 93.8%。

**推理约束是混合结果。** 强制以「Let's think step by step」开头，GSM8K 上 Qwen3-1.7B 75.8 → 77.7、Qwen3.5-2B 74.9 → 77.4；AIME 2026 上 Qwen3.5-27B 81.9 → 84.3，但 Qwen3.5-4B 62.2 → 55.6，掉 6.6 点。

**token 开销。** InWriting 在实验里只多出不到 15 个 token；NL-to-Format 要第二次调用，token 用量接近翻倍；JSON 的屏蔽开销从第一个 token 开始持续整段生成，随约束复杂度增长。

诚实泼冷水：

- VC 的实验范围很窄，主要在 LastLetter 两个变体上做，加一个 IMDb 内容过滤的初步实验；作者自己在局限里也这么写。
- 用的 JSON 都很简单（两个字段），复杂嵌套 schema 加长推理的情况没测，而这恰恰是工具调用最常见的形态。
- RC 的「有益轨迹」是从前人工作里拿来的固定模式，论文没有给出如何找到有益轨迹的方法。
- 模型最大到 32B，全部开源，没有闭源服务端的结构化输出接口。

## 🔬 最有意思的部分

**一是 VC 不只是后处理，而是一种「答案和推理一致性」的执行。** 附录里的例子很说明问题：推理里写的最后字母是 o、y、a、a，无约束输出的答案却是「oya」，限定四个字母之后变成「oyaa」；推理写的是 a、a、d、y，无约束多出一个 a 成了「aaday」，约束后是「aady」；推理正确识别出 H、E、N、E 却在答案里插了空格，约束后是「hene」。作者指出，空格和多余字符往往不是独立 token，而是像 ` e`、` n`、`da` 这样的复合 token，所以 VC 迫使模型在满足约束的前提下选择**和自己推理轨迹一致**的那条续写，而不是简单删字符。

**二是 schema 本身也会违反假设 1。** 无约束 JSON 解析失败里有两类很常见：一类是先自由写一大段推理，最后才给一个 JSON；另一类是把 JSON 包在 Markdown 的 json 代码块里。后者很多系统都默认接受，但论文提醒：如果你认为这种输出是对的，schema 就必须显式允许它，否则约束会把所有以代码块开头的路径全部剪掉，这就违反了「正确答案满足约束」的前提，约束开始伤分。**你在 schema 里没写进去的「其实也算对」，约束会替你当成错。**

**三是一个内容过滤的小实验。** IMDb 情感分类里，提示要求输出 Positive 或 Negative，但约束只允许输出一组同义词（Good、Favorable、Disappointing 等）。Qwen3-4B 从标签约束的 92.6 降到 83.4，Qwen3.5-4B 从 94.8 降到 85.8，掉了将近 9 个点但没崩。作者把这当作「禁止某些词时模型仍能保住意图」的证据，我觉得它同时也是一个警告：**提示里说的格式和约束允许的格式不一致，本身就是一种代价。**

## 🤔 我的判断

**定位：因果消融加理论澄清，属于「给工程实践纠偏」的论文，不是新解码算法。**

亮点：

1. 理论条件写得很清楚：约束不伤分的前提是正确答案满足约束，约束涨分的前提是模型在正确路径上真的会犯格式或有效性错误。两个假设都可以在工程里逐条检查。
2. 把「JSON 推理掉分」和「约束解码掉分」这两件常被混为一谈的事拆开，结论对 serving 层很友好：可以放心开约束，但别顺手改提示和输出形态。
3. VC 这个分类很有用，它把 schema 从「语法」升级为「语义先验」，而 harness 里大量字段本来就有明确的取值空间。

问题与局限：

- 任务偏玩具，复杂 schema、长链工具调用、多字段相互依赖都没覆盖，结论外推到 agent 工具调用需要谨慎。
- 只报告 token 数，没有报告约束带来的实际延迟和吞吐变化，而这在服务端是真成本。
- RC 的结果说明它很难当成通用手段，但论文没有讨论 RC 和「先自由推理再约束输出」之间的边界。

对工程的直接启发：

- **工具调用 schema 能收窄就收窄。** 枚举、整数范围、固定长度、正则模式，都是 VC。把参数空间写进 schema，比在提示里写「请输出合法值」更可靠。
- **约束打开前后，提示和期望格式必须完全一致再比。** 很多「开了约束掉分」的内部对比，其实同时换了 prompt 或让模型在 JSON 里写推理，先排除这个混淆。
- **推理留在自由文本，约束只管最后的输出块。** InWriting 这种触发 token 切换的方式只多不到 15 个 token，又避免了 JSON 内推理的长程屏蔽开销，适合 harness 里的裁判和决策模型输出判决。
- **schema 要把你认为「也算对」的形态写进去。** 否则约束会替你把它们全部剪掉。

一句话收束：**约束解码不是推理的敌人，没对齐的提示和没写全的 schema 才是。**
