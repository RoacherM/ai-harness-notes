# 压缩上下文其实是在烧重算：别改文本，直接丢 KV，还能便宜近三成

你有没有过这种体验：长任务跑到一半，harness 触发了 compaction，把前面几十轮对话压成一段摘要。账单上看 token 少了，可压缩之后那一轮明显变慢，而且 agent 开始忘事，前面查到的某个关键数字突然「不记得了」，又去重新搜一遍。你省下的是上下文长度，**付出的是整段保留内容的重新 prefill，以及中间轮次信息的丢失。**

清华 NICS 和港中文的这篇 **Cache Engineering for Agents**（arXiv:2610.28577）把这个两难讲得很透：context engineering（裁剪或摘要历史）一旦改动了轨迹前缀，后面所有缓存都作废，越早改动要重算的越多，所以主流 harness 只能等到阈值才一次性大砍。作者提出另一条路，叫 **cache engineering**：文本轨迹一字不动，**让 agent 直接决定哪些 KV 不再参与后续注意力，保留的 KV 原样复用**，并配套做了一个服务引擎 AKV。看完我的感受：这是把「上下文管理」从文本层下沉到缓存层的第一个完整方案，而且它不是让推理框架偷偷做 KV 淘汰，而是把控制权交给 agent 和 harness。

## 核心摘要

cache engineering 在标准的 append（追加新 token 的 KV）之外，加了两个操作：**drop** 把选中的 KV 从后续注意力里排除，保留项和位置编码都不变；**repos** 用 RoPE 旋转把保留下来的 key 重新排到 \(0,\dots,r-1\)，并重置下一个 token 的位置，不需要重算。主力策略非常朴素：**tool-response rolling drop**，保留所有推理消息和最近 12 条工具返回的 KV，更早的工具返回逐步丢掉。难点在服务端：同样的 token 序列，因为 drop 和 append 的先后不同，缓存状态会不同，普通前缀匹配会复用错。AKV 用「无状态接口、有状态服务」解决：请求里照常带完整 messages，再加一个可选 cache 字段描述 drop 和 repos；服务端用带 drop 节点和 reposition 节点的扩展 radix 树做正确复用，用感知 drop 的淘汰策略尽早回收，用 segment-batch attention 在一次 prefill 里恢复被淘汰的状态。在 MiniMax-M2.7、GPT-OSS-120B、MiroThinker-1.7-Mini 三个模型和 BrowseComp-Plus、xbench-DeepSearch、GAIA-Text、SWE-bench Verified 四个基准上，相比 96K（或 192K）阈值摘要，**平均成本降 27.7%，平均分数涨 1.7 个点**；服务端峰值下输出吞吐 1.18 倍，P95 请求延迟快 1.51 倍。让 agent 自己用 RSI 迭代缓存策略，在留出任务上还能比人工策略再省 7.1%。价值定位：给长程 agent 的成本问题加了一层新的、可编程的控制面。

## 🎯 为什么这件事值得写

长程 agent 的成本大头早就不是生成，而是 KV 的读写和存储。现在的两类做法各有硬伤：

| 做法 | 改什么 | 代价 |
| --- | --- | --- |
| 摘要（Claude Code、Codex、Pi 的 compaction） | 把大段历史换成摘要 | 保留部分要重 prefill；砍得狠就丢中间信息 |
| 裁剪（只留最近 N 轮工具返回） | 删掉旧消息 | 每轮都改前缀，每轮都要重算后缀 |
| KV 压缩和淘汰（H2O、SnapKV 等） | 推理框架按注意力分数淘汰 | 不懂消息角色和任务，agent 控制不了 |

作者在 GPT-OSS-120B、BrowseComp-Plus 前 100 题上做了一个很直观的对照：**只留最近 12 轮工具返回的裁剪法，成本是全上下文基线的 1.85 倍**（因为每轮都要重算）；48K 阈值摘要省了大约 7% 成本，却掉了 5 个点准确率。直接 drop 旧工具返回的 KV，则同时做到更准、更便宜。

还有一个容易被忽略的点：被保留的 KV 是在当初能看到旧内容的时候算出来的，**旧内容的信息有一部分已经「融」进了保留的缓存里**。文本层删掉就真没了，缓存层丢掉还能留一点余温。

## 🏗️ 机制：三个操作加一个会记历史的服务端

**三个缓存操作。**

| 操作 | 效果 | 位置编码 |
| --- | --- | --- |
| append | 基于当前活跃缓存算新 token 的 KV 并追加 | 下一个位置加一 |
| drop(P) | 把逻辑下标在 P 里的 KV 移出后续注意力 | 不变，也不重置 |
| repos | 保留项按逻辑顺序重排到 \(0,\dots,r-1\) | key 用 RoPE 旋转，value 不动 |

repos 的旋转很直接：

$$
K' = R(q)\,R(p)^{-1}K
$$

需要 repos 的原因是只 drop 不重排的话，位置下标仍随逻辑轨迹增长，缓存很小也会撞到模型的位置上限。

**为什么要记操作历史。** 同样保留 B 和 C：①先追加 C 再丢 A，②先丢 A 再追加 C，③从 B 开始再追加 C。三种情况下 C 的 KV 都不一样，因为它算的时候能看到的东西不同。所以缓存状态由 token 序列加操作序列 \(o_{1:m}\) 共同决定，前缀匹配必须同时匹配两者。

**AKV 的三件套。**

- **扩展 radix 树**：在 drop 的触发点插入 drop 节点，在 repos 之后插入 reposition 节点；前缀相同、drop 时机不同的请求共享前半段，在分叉处各走各的。
- **感知 drop 的淘汰**：一段 KV 被所有相关请求都 drop 了就能回收，节点留作空占位，后代仍可匹配；回收时优先淘汰已 drop 的缓存，而不是已完成请求的缓存（后者下一轮更可能复用）。
- **segment-batch attention**：恢复缺失缓存时按 drop 和 repos 的触发点切分 query，每段只看自己该看到的 KV，FFN 仍按整段一次跑，一次 prefill 复原，避免按操作历史逐段重放。

对客户端来说，接口仍是无状态的：每次请求带全量 messages，再加一个 cache 字段，用「在第几条消息之后丢掉哪几条」的语法描述 drop，用消息下标描述 repos。

## 🧪 关键证据

- **主结果**：三模型四基准平均，相比 Standard（高阈值摘要）成本降 27.7%，相比 Text Engineering（48K 阈值摘要）降 21.9%；平均成功率分别高 1.3 到 2.1 个点和 0.9 到 8.7 个点。成本按各家官方或 Groq 价格算，repos 的旋转也按缓存命中价计费，故意偏保守。
- **准确率从哪来**：GPT-OSS-120B 在 BCP 上，48K 以下三种方法差不多；48K 到 96K 区间 Text Engineering 最差，96K 以上 Standard 最差，正好对应各自的摘要阈值。突然的大砍才是掉分来源，滚动丢弃是渐进的。
- **服务效率**：8 张 A800、4 卡 prefill 加 4 卡 decode，Top-80 SWE-Verified 负载下，AKV（并发 14）对比 Standard（并发 12）各自峰值，平均和 P95 请求延迟分别快 1.36 倍和 1.51 倍，输入吞吐 1.53 倍、输出吞吐 1.18 倍。并发越高优势越大，因为 Standard 的重 prefill 吃掉了 decode 并发。decode 加速主要来自全注意力时间变短。
- **SWE-bench Verified 在线评测**：同样跑前 100 题，AKV 以最少 GPU 时间达到最高最终通过率。

## 🔬 最有意思的部分

**一是 repos 不是锦上添花。** 消融里，BCP 上只 drop 不 repos 是 55%，加上 repos 是 62%：没有重排，agent 会撞到位置上限被迫停下，探索不下去。

**二是别丢推理。** 开着 repos 时，丢推理消息的缓存，或者推理和工具返回一起丢，两个基准上都不如只丢工具返回。作者的注意力分析也支持这一点：越旧的 token 得到的注意力越少，而同样相对位置上，工具返回得到的注意力比助手消息少。这和 harness 里常见的直觉一致：**工具输出是最可丢的，模型自己的推理链是骨架。**

**三是策略本身可以让 agent 自己改。** 用 MiniMax-M2.7 在 20 道 BCP 题上做 RSI 迭代缓存策略，在 100 道留出题上评估，第 3 轮和第 6 轮的策略分别比 Standard 省 15.6% 和 17.8%，同时保持准确率。把缓存管理做成工具让 agent 自己调用（Cache-As-Tool），BCP 子集上 GPT-OSS-120B 拿到 61.0%、MiniMax-M2.7 拿到 64.0%，都是最高；但成本一个降（13.4 到 12.1 美分），一个升（5.4 到 5.9 美分，因为跑了更多轮）。

## 🤔 我的判断

**定位：系统加接口的组合创新，给 harness 设计打开了一个新的控制层。**

亮点三条：

1. 把「为什么 compaction 总在阈值才触发」讲透了：根源是改文本就要重算后缀，这个成本结构决定了 harness 只能大砍，大砍又掉分。
2. 无状态接口加有状态服务的设计很务实，客户端几乎不用改，只多一个 cache 字段；这让它有机会进入现有 API 生态。
3. tool-response rolling drop 简单到可以当默认策略，同时又留出了 RSI 和 agent 自主管理的空间。

问题与局限：依赖自部署推理（SGLang 改造），用闭源 API 的 harness 今天用不上；只支持 RoPE 系全注意力模型，线性注意力和 MLA 等结构还没覆盖；没有在训练阶段让模型适应这种「被抽掉 KV」的上下文；各基准的分模型明细我这里只引用了论文给出的平均数。

对工程的直接启发：

- **自托管模型的 harness，先把 compaction 改成工具返回滚动丢弃。** 保留推理和最近若干条工具返回，旧的工具输出退出注意力，比阈值摘要更省、更稳。
- **用闭源 API 时也能借鉴思路。** 尽量只追加不改写前缀，把需要淘汰的内容集中在工具返回上，并把淘汰节奏做成渐进的，减少一次性大砍造成的信息断崖。
- **把上下文策略当成 RSI 的对象。** 缓存或压缩策略是一段小而可评测的代码，非常适合让 agent 在小训练集上迭代、在留出集上验收，和 harness 自进化的流程直接对接。
- **成本评测要计入重 prefill。** 只看活跃上下文长度会误判；按真实计费（输入、缓存命中、输出）算，裁剪类方法可能比不压缩还贵。

一句话收束：**上下文太长，不一定要改写历史；让模型不再看它，比重新讲一遍便宜得多。**
