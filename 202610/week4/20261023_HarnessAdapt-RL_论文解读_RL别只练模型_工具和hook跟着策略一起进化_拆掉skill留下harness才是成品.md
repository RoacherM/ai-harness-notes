# RL 别只练模型：工具和 hook 跟着策略一起进化，拆掉 skill、留下 harness 才是成品

如果你自己跑过 coding agent 的 RL，大概见过这种轨迹：模型在 shell 里用 `sed` 改代码，引号转义一错，命令失败，再试三次，上下文被一屏 `cat` 输出塞满，最后匆匆提交了一个没跑过测试的补丁。你很清楚这些问题加一个编辑工具、一个截断输出的读文件工具、一个「提交前先跑测试」的 hook 就能缓解，可训练框架里的 harness 通常是写死的，**模型在变，脚手架一动不动。** 更麻烦的是，训练到后期模型自己的坏习惯也会变，比如前期还会跑测试，后期反而跳过了。

浙江大学和 LIGHTSPEED 的这篇 **Training the Whole Agent, Not Just the Model**（arXiv:2610.28069）把这件事做成了一个完整的训练配方 **HarnessAdapt-RL**：GRPO 训练策略的同时，一个老师按任务写「机制层 skill」，另一个老师跨任务进化工具和 hook，只有在「通过率」和「可训练率」都不降、且至少一个上升时才接受改动。看完我的感受：它把「模型和 harness 是一对」这句口号，第一次落成了 RL 训练里可以照抄的接受规则和部署清单。

## 核心摘要

作者把 agent 写成策略加 harness 的二元组，harness 又拆成三块：skill（只在训练时给策略看的文字指导）、工具（把常用修复操作打包成动作）、hook（运行时在特定状态下注入的反馈）。训练时，一个冻结的 GLM-5.3-Flash 老师对每个需要辅助的任务比较当前策略的两条轨迹，写出**只讲「什么时候、为什么用这种修复策略」、不出现仓库路径、符号名和代码**的机制层 skill；另一个老师（GPT-5.6 Sol，经 Codex 调用）读全部准备轨迹，找跨任务反复出现的交互问题，直接写代码实现新的工具和 hook。候选 harness 和当前 harness 在同一策略、同一批任务、同一 rollout 预算下各跑一遍，**只有通过率和可训练率都不降、且至少一个上升才接受**。每个 epoch 开头最多五轮这样的进化，之后 harness 冻结、继续 GRPO。部署时 skill 和老师全部拿掉，只留训练好的权重和最终的工具与 hook。用 Qwen3.5-9B、mini-swe-agent 作底座 harness、R2E-Gym-Lite 训练，**SWE-bench Verified、Multilingual、Pro 三项平均 pass@1 从 GRPO 的 35.3% 提到 44.9%**，也超过用人工设计的 OpenHands harness 训练的版本（39.0%）。价值定位：把 harness 优化从「冻住模型调脚手架」推进到「脚手架跟着策略一起长」，并且给出了哪些东西该留到部署、哪些该拆掉的实证答案。

## 🎯 为什么这件事值得写

过去一年 harness 优化大致分成两派：

| 路线 | 代表 | 模型权重 | harness |
| --- | --- | --- | --- |
| 冻模型、改脚手架 | Meta-Harness、RHO、HarnessEvolve | 不动 | 按轨迹搜索或改写 |
| 改模型、冻脚手架 | 常规 agentic RL（GRPO on SWE） | 训练 | 固定 |
| 交替进化 | Co-Harness（配 SFT） | 训练 | 交替更新 |

问题是前两派各自只解一半。冻模型时搜到的 harness 是给初始模型配的，模型训完后它的毛病变了，这套 harness 不一定还对口；冻脚手架时，策略学到的是「在这套难用的工具里怎么凑合」，而不是「怎么修 bug」。HarnessAdapt-RL 回答三个具体问题：训练时的 skill 应该写成什么样，工具和 hook 怎么随策略变化来选，部署时到底该留下哪些部件。

## 🏗️ 机制：两个老师、一条接受规则、一份部署清单

**一、机制层 skill：讲原理，不给答案。** 作者比较了三种 skill：

| 变体 | 怎么生成 | 去掉 skill 后三项平均 |
| --- | --- | --- |
| Skill-Bank | 老师跨任务维护一个固定容量的通用修复技能库 | 34.1% |
| Skill-Hint | 给近乎答案的提示，含具体变量名、函数名和代码改动 | 32.7% |
| **Skill-Mechanism** | 对比两条轨迹，解释何时、为何用某种修复策略，不出现路径、符号和字面代码 | **38.3%** |
| （对照）GRPO | 无 skill | 35.3% |

**二、工具和 hook 进化：四步提案。** 老师（1）跨任务找反复出现的工具使用和反馈问题；（2）逐条读工具调用、输出和 hook 消息；（3）设计一个或几个服务于同一修复流程的工具、hook 组合；（4）直接写成代码。生成的代码不经人工修改，但要先过格式、工具 schema、模块加载和一个冒烟测试，提案之外的工具和 hook 必须字节级不变。

**三、训练感知的接受规则。** GRPO 依赖同组内成败的对比，全对或全错的组对梯度没有贡献。所以除了通过率，作者还定义了**可训练率**：

$$
\text{trainable rate}=\frac{\#\{\text{未截断、且所在组同时有成有败的 rollout}\}}{\#\{\text{全部采样 rollout}\}}
$$

全成功组里的成功 rollout 计入通过率，但不计入可训练率；截断和奖励未知的都留在分母里。接受条件是：

$$
\Delta\text{pass}\ge 0,\quad \Delta\text{trainable}\ge 0,\quad \Delta\text{pass}+\Delta\text{trainable}>0
$$

每侧 184 条 rollout，作者明说这只是观测比例的比较，不是显著性检验。被拒的提案里的部件以后还可以重新提。

**四、跨 epoch 再进化。** 第一个 epoch 结束得到 H1（7 个工具、4 个 hook），第二个 epoch 从 H1 出发，用更新后策略的轨迹继续进化出 H2（8 个工具、5 个 hook）。

**五、部署。** 拿掉 skill 和所有老师，交付的是 \( (\theta_T, H_T) \)：训好的权重加最终的工具和 hook。

## 🧪 关键证据

**主表（pass@1，%，均不带 skill，各自用最终 harness 评测，三次评测取均值）：**

| 配置 | Skill | Harness | Verified | Multilingual | Pro | 平均 |
| --- | --- | --- | --- | --- | --- | --- |
| 基座 | 无 | H0 | 42.2 | 19.3 | 31.8 | 31.1 |
| GRPO | 无 | H0 | 47.8 | 24.7 | 33.3 | 35.3 |
| OpenHands-GRPO | 无 | OpenHands | 51.4 | 33.3 | 32.3 | 39.0 |
| Skill-Mechanism | 机制层 | H0 | 52.2 | 28.0 | 34.6 | 38.3 |
| Pre-Evolved | 机制层 | Hpre（先冻模型搜） | 55.2 | 33.0 | 37.0 | 41.7 |
| H1+Mechanism | 机制层 | H1 固定 | 55.4 | 32.7 | 37.7 | 41.9 |
| **HarnessAdapt-RL** | 机制层 | H1→H2 | **57.6** | **37.3** | **39.7** | **44.9** |

几个对照分得很清楚：Pre-Evolved 用同样的搜索步数和任务，只是搜索时策略停在基座，最终低 2.4 到 4.3 个点；H1+Mechanism 和完整方法共享第一个 epoch，只是第二个 epoch 不再进化，低 2.0 到 4.6 个点。**用当前策略的轨迹去改 harness，比用初始策略的轨迹改一次更好。**

**部署时拆 harness 的代价（权重不变，不带 skill）：**

| 模型 | H0 Verified / Multi / Pro | H2 Verified / Multi / Pro |
| --- | --- | --- |
| Skill-Mechanism（用 H0 训） | 52.2 / 28.0 / 34.6 | 54.2 / 33.3 / 36.9 |
| HarnessAdapt-RL（用进化 harness 训） | 52.8 / 29.6 / 35.0 | 57.6 / 37.3 / 39.7 |

H2 给没见过它的模型也能涨 2.0 到 5.3 个点，但给一起训出来的模型涨 4.7 到 7.7 个点，三个基准合并后差异显著。反过来，**把 H2 换回 H0，HarnessAdapt-RL 会掉最多 7.7 个点**，所以工具和 hook 必须跟权重一起交付。

**进化出的 harness 可以复用。** 把 H2 冻住、从基座重新训一个策略（Frozen-H2+Mechanism），三项都在完整方法 1 个点以内，并比 Pre-Evolved 高 1.6 到 5.3 个点。也就是说，进化只需做一次，前提是它得在训练过程中做。

**成本。** 完整方法总共采了 18,056 条 rollout，其中用于策略更新的是 8,464 条；GRPO 基线为了公平给了双倍训练 rollout，共 16,928 条。另有 1,570 次 skill 生成请求和 10 次 harness 老师调用。rollout 数不等于算力，因为各配置轨迹长度不同。

## 🔬 最有意思的部分

**一是「训练时更容易成功」反而有害。** 近答案提示让训练成功率大幅上升、每条 rollout 的 token 少了 40.8%，但去掉提示后比纯 GRPO 还差。原因有两层：它让策略跳过了定位代码、决定怎么改这些独立修复必需的步骤；同时它制造了更多全成功组，同时有成有败的组只占 39.0%，机制层 skill 是 46.5%。**skill 的目标不是让这一题过，而是让这一组 rollout 产生可学习的对比。**

**二是模型的坏习惯会随训练漂移，harness 得追着改。** 第一个 epoch 的进化集中在上下文管理和提交：读文件和搜索工具限制返回长度，编辑工具代替容易因引号出错的 shell 命令，第一条这类提案就把通过率相对提了 13.7%、可训练率提了 7.4%。到第二个 epoch，策略开始少跑验证测试，尽管已经有测试工具和提醒。老师的应对是把「准备补丁」工具改成自动挑相关测试来跑，再由 hook 报告失败、提醒提交前检查，这条又带来 6.3% 和 7.4% 的相对提升。另一个改动是 Git 撤销命令被禁时，hook 推荐新的 `restore_file`，只恢复一个文件，不丢其他文件的修改。

**三是可训练率真的在拦东西。** 有一条提案加了个 hook，让策略对照需求逐项自查补丁，通过率相对涨了 2.7%，但可训练率降了 7.0%，被拒。后来老师把自查和 `view_diff`（展示所选文件实际增删改的行）结合起来重提，两个指标都涨，才被接受。只看通过率的选择器会收下第一个版本。

## 🤔 我的判断

**定位：目前最完整、最可照抄的「训练期 harness 共进化」配方，单模型、单次训练的证据强度要打折扣。**

亮点三条：

1. 可训练率这个指标很关键。它把 harness 选择的目标从「这一批过得多」改成「这一批对 GRPO 有用」，解释了为什么近答案提示和某些自查 hook 看起来涨分却该拒。
2. 「skill 训练时用、部署时拆；工具和 hook 训练时进化、部署时保留」这个分工，有清楚的消融支撑，可以直接当部署清单。
3. Pre-Evolved、H1 固定、Frozen-H2 三个对照把「必须在训练中进化」和「进化一次就能复用」分开证明了。

问题与局限：只有一个 9B 模型、只有 SWE 修复任务，每个配置只训了一次，三次重复只是同一 checkpoint 的三次评测，不反映训练种子方差；接受规则不是显著性检验，184 条 rollout 的噪声和反复搜索都可能让偶然的改动留下来；更大的模型本来就会的操作，打包成工具还有没有这么大的收益，作者自己也说不知道。

对工程的直接启发，尤其是 Pi 这类工具、hook、skill 都显式可配的 harness：

- **把可训练率放进 harness 评测面板。** 不只看通过率，还看组内成败分布；全对组太多说明 harness 或提示把题变简单了，对 RL 没价值。
- **训练期 skill 写机制，不写答案。** 讲触发条件和原因，去掉路径、符号和代码，这和「自动沉淀的 skill 不要直接进常驻上下文」的思路一致：skill 是教练，不是成品的一部分。
- **工具和 hook 要版本化，并和权重绑定发布。** 模型 checkpoint 和它训练时的 harness 版本一起记录，换 harness 等于换了一半 agent。
- **harness 提案要带「不变式」检查。** 提案之外的工具字节级不变、先过 schema 和冒烟测试再比较，这套护栏在自动改 harness 的系统里值得直接搬。

一句话收束：**策略在变，脚手架也得跟着变；训练的产物不是一个模型，而是一对模型和 harness。**
