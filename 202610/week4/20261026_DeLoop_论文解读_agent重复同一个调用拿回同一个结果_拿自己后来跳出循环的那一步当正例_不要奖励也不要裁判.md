# agent 重复同一个调用、拿回同一个结果：拿它自己后来跳出循环的那一步当正例，不要奖励也不要裁判

你有没有过这种体验：盯着一个长程 agent 的轨迹，看它第三次调用 `FindUnvisited(3,0)`，第三次拿回 `(3,0)`，然后第四次又调。上下文压缩过一轮之后这种事更频繁，你加了「已执行动作清单」进摘要，它照样重复；你在 harness 里拦掉重复调用、直接返回上次结果，它下一步还是想再调一次。问题不在于历史里有没有这条记录，而在于策略本身不会用这条记录。

Google 与波士顿大学等的这篇 **DeLoop: Repeated Actions as Self-Supervision for Long-Horizon Agents**（arXiv:2610.19376）把这个现象定义成 loop：同一个工具调用、同样的参数、拿回同样的观察。然后它发现一个很省事的训练信号：同一条 rollout 里，循环那一步是天然的负例，agent 后来第一个跳出循环的不同动作就是正例，直接拿去做 DPO。看完我的感受：这是「失败轨迹本身就是监督」的一个非常干净的例子，检测器就是一条精确重复规则，连 LLM 裁判都不用。

## 核心摘要

作者先量化问题：CodeGym 上 Qwen3-8B 在完整历史下有 29.0% 的任务出现 loop，4,096 token 阈值触发摘要后升到 57.3%，2,048 阈值升到 64.7%；三个 Gemini 模型压缩后也都明显上升，Gemini 3.1 Pro 涨了 2.9 倍。六个 Qwen3 与 Gemini 模型里，带 loop 的 run 失败率全部高于无 loop 的 run，平均 59.5% 对 33.4%。更换上下文管理（动作 trace、尝试过动作的 ledger、ACON、LLMLingua-2、检索记忆）都压不回完整历史的水平。DeLoop 的做法是：在压缩设置下跑训练任务，用结构检测器找出 looping action 当 \(y^-\)，同一 rollout 中第一个非循环且不同的后续动作当 \(y^+\)，上下文是循环前的历史，LoRA DPO 训一轮（Qwen3-8B 用 8,000 对，\(\beta=0.05\)）。**Qwen3-8B 的 loop 率从 57.3% 降到 6.1%，每任务步数从 15.00 降到 4.67，token 降 47%，成功率 25.1% 到 25.9% 基本持平；Qwen3-14B 和 32B 上成功率分别涨 7.2 和 7.1 个点（32B 从 37.7% 到 44.8%）。** 加入跨域配对的 DeLoop-Mix 让 8B 成功率到 30.3%，并迁移到 ALFWorld、AppWorld、Terminal-Bench 和 BrowseComp-Plus。

## 🎯 loop 的定义很窄，所以很好用

记第 \(t\) 步的工具调用为 \(a_t\)、观察为 \(o_t\)，\(\kappa\) 把调用规范化以忽略格式差异，步签名 \(x_t=(\kappa(a_t),o_t)\)。

$$
s_t=\begin{cases}1 & \exists\, i<t,\ x_t=x_i\\ 0 & \text{otherwise}\end{cases}
$$

只要轨迹里有一个 \(s_t=1\) 就算 looping run。注意重复调用但拿回新观察的不算 loop，所以轮询一个变化中的状态不会被误杀。

几个让我印象深刻的诊断数字：

- 带 loop 的 Qwen3-8B run 平均有 6.5 个循环动作，比无 loop run 多执行 10.5 个动作、多 11k token。
- 作者重建了 300 个压缩后的历史，在 Qwen3-8B 选下一步之前，保留最近一次完成调用的记录时重复率 3.3%，删掉这条记录时 48.8%。记录确实有用，但即使保留，完整历史下仍有 29.0% 的 run 出现 loop，压缩后有 25.2% 的 run 重复了一个**仍逐字留在上下文里**的调用。
- 在 harness 里放一个「拦截重复调用并返回上次结果」的 blocker，Qwen3-8B 仍在 71.3% 的任务里提出已执行过的调用，和没 blocker 时的 69.8% 一样；DeLoop 降到 13.6%。

这三条合起来的结论是：loop 主要是策略问题，不是记忆问题，所以作者选择训策略、固定压缩器。

## 🏗️ 机制：一条 rollout 自带正负例

$$
x=h_{<t},\quad y^-=a_t,\quad y^+=a_{t'},\quad t'=\min\{u>t: s_u=0,\ \kappa(a_u)\neq\kappa(a_t)\}
$$

如果 agent 到 rollout 结束都没跳出来，就不构造这一对；一条 rollout 可以贡献多对。关键点是**即使整条 rollout 最终失败，只要中途跳出过循环，这一对也成立**，所以不需要任务奖励、标准答案或裁判。

训练用标准 DPO，参考模型是冻结的基座：

$$
\mathcal{L}=-\log\sigma\Big(\beta\log\frac{\pi_\theta(y^+|x)}{\pi_{\text{ref}}(y^+|x)}-\beta\log\frac{\pi_\theta(y^-|x)}{\pi_{\text{ref}}(y^-|x)}\Big)
$$

推理时 harness 照常在历史超过 4,096 token 时让同一个模型写摘要，摘要生成共享更新后的权重但没有单独的训练目标。

| --- | --- | --- | --- | --- | --- |
| 完整历史（参照） | 无 | 29.0 | 31.7 | 12.23 | 24.3 |
| 压缩基线 | 无 | 57.3 | 25.1 | 15.00 | 23.9 |
| 检索记忆 | 无 | 42.7 | 27.7 | 13.34 | 26.1 |
| ACON 压缩器 | 无 | 46.3 | 29.3 | 14.84 | 20.5 |
| 精确重复拦截 | 无 | 46.7 | 25.3 | 14.71 | 24.9 |
| 卡住时 Reflexion | 无 | 55.3 | 24.3 | 14.62 | 24.1 |
| Outcome DPO | 任务成败 | 34.7 | 25.7 | 10.99 | 15.9 |
| Gold-label DPO | 任务成败 | 22.3 | 25.7 | 8.10 | 11.3 |

| **DeLoop** | 无 | **6.1** | 25.9 | **4.67** | 12.7 |
| **DeLoop-Mix** | 无 | 10.1 | **30.3** | 5.94 | **9.6** |

**目标函数消融（同一批 8,000 对）：** DPO 6.1% / 25.9%，KTO 12.6% / 23.8%，IPO 11.7% / 24.0%，在线 GRPO 把 loop 当每步惩罚 15.0% / 24.7%，只 SFT 正例 37.7% / 21.3%。**负例这一半才是关键**：只模仿跳出动作，loop 率还剩 37.7%。

**规模：** 14B 和 32B 上 loop 分别降 3.5 倍和 3.0 倍，token 降 35% 和 29%，成功率各涨 7 个点出头。

**泛化：** DeLoop-Mix 在七种记忆策略下 loop 率都下降，带 action ledger 时从 62.7% 降到 11.3%、成功率涨 5.7 点；四个额外环境里 loop 都下降，AppWorld 降 32.8 点。Terminal-Bench 上无效重复调用从每任务 16.6 次降到 6.9 次；BrowseComp-Plus 全部 830 题上 loop 率从 22.4% 降到 1.2%，准确率与未训练模型持平。只用 CodeGym 对训练的 32B 零样本迁到 ALFWorld，成功率从 33.6% 到 42.5%。训练后剩下的重复动作里，能拿回新信息的比例从 29.9% 升到 69.8%，说明它没有简单学成「永远不重复」。

## 🔬 最有意思的部分

**一是「更好的压缩」和「更好的策略」被拆成了两个正交维度。** 过去一年上下文工程的大部分工作都在决定留什么，这篇的数据说明留住了也不一定用得上，而且两者可以叠加：DeLoop-Mix 在每种记忆策略下都进一步降 loop。

**二是 8B 上 loop 大降但成功率几乎不动。** 作者没有回避这一点：去掉无效动作省了三分之二步数和近一半 token，但小模型的能力上限没变；到 14B、32B，省下来的预算才真正转化成成功率。这对评估「效率型」改进很有参考价值，不能只看 pass rate。

**三是 Gold-action GRPO 几乎没用。** 作者解释即使每步都给标准动作匹配奖励，也只有 2.7% 的 GRPO 组有信息量。这又一次说明稀疏奖励下，离线成对对比是更划算的信号来源。

## 🤔 我的判断

**定位：一篇方法极简、诊断扎实、对 harness 工程师很实用的论文。**

亮点：

1. 检测器是确定性规则，正负例从同一条轨迹自动挖，整条流水线没有任何 judge，成本和偏差都很低。
2. 把 loop 与压缩、与失败率、与 inference-time 拦截的关系逐一量化，结论可以直接拿去说服团队别再只调摘要提示词。
3. 跨环境、跨 harness（Terminal-Bench、BrowseComp-Plus 的原生 harness）都做了迁移评估。

需要注意：

- loop 的定义只覆盖「完全相同调用加完全相同观察」，语义等价但参数不同的兜圈子、或者在两三个动作之间来回切换的循环不在检测范围里。
- 主实验在 CodeGym 这类合成工具环境，8B 上成功率没有提升；在 ScienceWorld 上 DeLoop-Mix 成功率还从 3.5% 降到 1.5%，AppWorld 从 7.0% 降到 5.8%，基数都很小，但说明并非处处正收益。
- 代码和数据尚未公开。

对搭 agent harness 的直接启发：

- **先在日志里加 loop 检测。** 规范化调用签名加观察哈希，一行逻辑就能算出 loop 率，它和失败率强相关，可以当廉价的在线健康指标。
- **别指望拦截器解决问题。** 拦截能省一次执行，但模型下一步还会想重复，记录要喂给策略，而不只是 harness。
- **有训练能力时，把自己生产环境的轨迹挖成 DPO 对。** 负例是循环动作，正例是后来跳出的动作；这和前几天归档的 AntiPersistence、MCCL 一样，都在说经验的价值要看下一次行为有没有变好。
- **效率指标单独上面板。** 步数、token 和 loop 率要和成功率并列，否则 8B 这种「省了一半钱但成功率持平」的改进会被埋没。

一句话收束：**agent 自己跳出循环的那一步，就是它最好的老师；先让它别再问一遍已经知道答案的问题。**
