# 同一道题时过时不过，才是改 harness 的线索：对照成败轨迹加内部 trace，稳定通过率涨 14 个点

跑过长程终端 agent 的人大概都有这种挫败感：同一个模型、同一套 harness、同一道题，跑四次过两次。你翻失败那次的轨迹，看到 agent 最后很自信地说「已验证」，可往前翻二十轮，有一条探测命令其实早就报了错，只是那段输出被一个空闲的终端提示符淹没了。问题出在模型身上，还是 harness 根本没把那条失败带到确认完成的时刻？光看 agent 轨迹，你分不出来。

腾讯混元 LLM Frontier 联合印第安纳大学、马里兰大学等的这篇 **Harness Self-Evolution for Long-Horizon Terminal Agents**（arXiv:2610.27435）提出 **RiseHarness**：冻住模型权重，只盯「翻转任务」（同配置下既有成功又有失败的题），把成功轨迹当失败轨迹的参照，再叠一层运行时监控记下的 harness 内部 trace，用 Harness Handbook 把函数调用映射回行为职责和源码，最后去其他 harness 框架里找现成实现当设计参考。看完我的感受：这篇最有价值的不是涨了几个点，而是它把「agent 说要做什么」和「harness 实际做了什么」拆成两条证据链，这正是多数 harness 自动优化工作缺的那一半。

## 核心摘要

RiseHarness 是一个固定模型、只改 harness 的迭代进化框架。每一轮：（1）在开发集上重复跑每道题，同时录 agent 轨迹和 harness trace（函数边界上的调用关系、参数、返回值、异常和源码位置），按 run id 和 episode 编号对齐；（2）挑出翻转任务，成败配对，经过 Compare、Wish、Revise、Group 四步，得到「harness 在什么可观察条件下应该做什么」的共性需求，并核查当时 harness 是否拿得到所需信息、是否已经做过这件事；（3）把需求翻译成搜索问题，去别的框架、源码和技术文档里找先例，结合当前执行流、可用信号和模型行为改写成本地方案；（4）实现后先过行为契约检查，再做针对性筛选和完整重复评测，只有记录有效、跑满、总通过率高于声明基线才采纳。用 GPT-6-sol 和 DeepSeek-V4-Flash，从未改动的 Terminus-2 出发，在 100 题的 Terminal-Bench Hard（TBH）上进化，在 89 题的 Terminal-Bench 2.1（TB2.1）上只做迁移评测。**DeepSeek-V4-Flash 在 TBH 上 Pass@1 从 56.75% 到 64.00%，四次全过的题占比 Pass⁴ 从 37% 到 51%（+14）；GPT-6-sol 的 Pass@1 从 50.25% 到 55.50%**，两个模型都超过 ModularRSI 和 AHE Harness。Pass@4 只涨 1 到 2 个点，说明收益主要是「稳定做对」，不是「能做对的题变多」。价值定位：把 harness 自进化的诊断粒度从 agent 轨迹推进到 harness 内部执行，并且给出了模型专属 harness 的交换实验证据。

## 🎯 为什么这件事值得写

长程终端任务里，一条错命令或一次漏看的输出就会改变环境和后续上下文，所以同一模型同一题会跑出不同结局。作者用四个指标把「平均能做对」和「每次都做对」分开，设第 \(i\) 题 \(r\) 次重复里成功 \(k_i\) 次：

$$
\text{Pass@1}=\frac{1}{Nr}\sum_i k_i,\quad \text{Pass}^r=\frac{1}{N}\sum_i \mathbb{I}[k_i=r],\quad \text{Pass@}r=\frac{1}{N}\sum_i \mathbb{I}[k_i>0],\quad \text{Flip}=\text{Pass@}r-\text{Pass}^r
$$

作者特别提醒：Flip 降低本身不代表更可靠，翻转题也可能变成全错题，所以 Flip 要和 Pass^r 一起看。

翻转任务集定义为 \(F_t=\{i: 0<\sum_j y_{i,j}(H_t)<r_t\}\)。它的好处是：成功轨迹证明当前「模型加 harness」本来就能解这道题，失败就有了一个同配置的现成参照，不需要像 HarnessEvolve 那样借助标准答案生成参照。

## 🏗️ 机制：双 trace、Handbook、外部先例、行为契约

**一、双 trace。** agent 轨迹只记录模型收到了什么、回了什么，看不到 harness 内部：模型请求的命令可能没被派发，终端输出可能没完整返回。运行时监控在选定的 harness 函数边界记录调用关系、参数、返回、异常和源码位置，与 agent 轨迹按 run 和 step 对齐。

**二、Harness Handbook。** 一个行为可能横跨多个函数，Handbook 把函数级记录映射到行为职责、触发条件、实现函数和退出条件，比如命令执行、观察构造、上下文管理、完成确认。trace 说明「发生了什么」，Handbook 说明「这是哪个行为、代码在哪」。

**三、四步分析。**

| 操作 | 作用 |
| --- | --- |
| Compare | 对比成败轨迹的相关交互，借 Handbook 解释 harness 的角色 |
| Wish | 写出 harness 应在什么可观察条件下做什么 |
| Revise | 查 harness trace，判断所需信息当时是否可得、现有机制是否已经做过，据此修正 |
| Group | 跨配对汇总，能用同一改动解决的归一组，形成共同需求 |

分组后有独立复审，再按覆盖的不同任务数、不同失败 run 数和发现数排序选组。

**四、外部研究与本地适配。** 附录里 GPT-6-sol 的案例很典型：一个 HTTP 调度服务任务，第 3 轮 `date` 对 `24:00` 报了 invalid date，第 8 轮 agent 却声称「已验证」，harness 确认完成时只给它看了一个空闲提示符。Revise 一步查明：`get_incremental_output` 只做屏幕差分，`_limit_output_length` 只查长度，没有任何调用能判断某个探测失败过、后来是否被同一输入的重跑解决。系统据此去搜 Harbor Terminus-2 源码和 pytest 文档，找到 pytest `--lf`（缓存失败用例、只重跑失败项）作先例，标注为「需要扩展」：pytest 有测试节点 id，tmux 通道只有合并的增量输出、拿不到每条命令的退出码，所以本地方案得改为独立 `environment.exec` 执行专门的检查并记录自己的返回码。

**五、验证与采纳。** 每个机制写一份契约，包含正例、反例和恢复用例，在三种配置下检查：

$$
O(H_t,x)=o^-(x),\quad O(C_t,\text{新机制关闭},x)=o^-(x),\quad O(C_t,\text{新机制开启},x)=o^+(x)
$$

关闭时必须保持原行为，开启时必须出现预期行为，进程崩溃不算正确处理反例。过检后先在相关任务上筛选，再在开发集完整重复评测，总通过率高于基线才发布，新版本的源码、Handbook 和评测 trace 一起成为下一轮的参照语料。

## 🧪 关键证据

**主表（r=4，%）：**

| 模型 | Harness | TBH Pass@1 | TBH Pass⁴ | TBH Pass@4 | TBH Flip↓ | TB2.1 Pass@1 | TB2.1 Pass⁴ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| GPT-6-sol | Terminus-2 | 50.25 | 39.00 | 59.00 | 20.00 | 78.65 | 68.54 |
| GPT-6-sol | ModularRSI | 50.75 | 43.00 | 58.00 | 15.00 | 78.65 | 66.29 |
| GPT-6-sol | AHE Harness | 54.75 | 44.00 | 59.00 | 15.00 | 78.09 | 60.67 |
| GPT-6-sol | **RiseHarness** | **55.50** | **46.00** | 60.00 | 14.00 | **81.74** | **69.66** |
| DeepSeek-V4-Flash | Terminus-2 | 56.75 | 37.00 | 71.00 | 34.00 | 72.19 | 58.43 |
| DeepSeek-V4-Flash | ModularRSI | 58.00 | 43.00 | 70.00 | 27.00 | 73.03 | 53.93 |
| DeepSeek-V4-Flash | AHE Harness | 59.75 | 46.00 | 70.00 | 24.00 | 76.12 | 62.92 |
| DeepSeek-V4-Flash | **RiseHarness** | **64.00** | **51.00** | 73.00 | 22.00 | **79.49** | **67.42** |

**DeepSeek 的四个机制全都落在「完成确认握手」上（累加版本，TBH / TB2.1 Pass@1）：**

| 版本 | 机制 | TBH | TB2.1 |
| --- | --- | --- | --- |
| Base | 两次连续声明完成即结束 | 56.75 | 72.19 |
| +SE | 模型在完成声明里给出验证命令和期望退出码，harness 真去执行比对 | 57.75 | 77.81 |
| +DI | 任务指定了调用方式、但只观察到替代调用时，要求先跑指定调用 | 56.75 | 77.81 |
| +OO | 第二次声明时通过环境接口执行验证命令，30 秒探测上限，沙箱异常时放行 | 57.50 | 79.49 |
| +IR | 支撑完成的读数只来自一种读取方式时，要求换一种独立方式再读 | **64.00** | 75.28 |

每个检查每次 run 最多拦一次完成，给一次修正机会，不会无限要求验证。

**GPT-6-sol 留下的是另一类改动**：完成确认时附上本次 run 前面做过的工作证据，而不是只给空闲提示符；把真正写入文件的改动以 workspace diff 呈现，而不是依赖终端回显；终端会话丢失时恢复会话并告诉 agent 状态丢了。更早的 GPT-5.6-Terra 实验里，改动则是让 tmux 把命令里的字面 tab 当数据而不是按键，TBH Pass⁴ 从 22% 到 29%。

**消融（DeepSeek-V4-Flash，%）：**

| 方法 | TBH Pass@1 | TBH Pass⁴ | TB2.1 Pass@1 | TB2.1 Pass⁴ |
| --- | --- | --- | --- | --- |
| RiseHarness | 64.00 | 51.00 | 79.49 | 67.42 |
| 去掉 harness trace 和 Handbook | 57.00 | 43.00 | 76.40 | 62.92 |
| 去掉外部研究 | 58.50 | 45.00 | 76.69 | 64.04 |

**交换 harness 会掉分。** 把 DeepSeek 进化出的 harness 给 GPT-6-sol，TBH Pass@1 是 52.75%（自己的是 55.50%）；把 GPT-6-sol 的给 DeepSeek，是 58.25%（自己的是 64.00%）。两个模型在两个基准上都是用自己的 harness 更好。

## 🔬 最有意思的部分

**一是「agent 想要什么」和「harness 能不能给」被严格分开。** Revise 这一步会直接得出「不能，harness 根本拿不到这个信息」这种结论，然后把需求改写成先补信号再改行为。很多自动改 harness 的系统只看 agent 轨迹，提出的「应该提醒 agent 某某」其实 harness 早就做了，或者根本没有数据源可做。

**二是收尾检查是 DeepSeek 的主要瓶颈。** 四个被采纳的机制都在完成确认环节，核心思路是把模型的「我验证过了」变成 harness 可以执行或交叉核对的证据。对 GPT-6-sol 则是会话连续性和反馈真实性。同一个起点 harness，不同模型缺的东西完全不同。

**三是中间版本并不单调。** TBH 上 +SE、+DI、+OO 都在 57% 上下徘徊，直到 +IR 才跳到 64%；而 TB2.1 上 +OO 最好，+IR 反而回落到 75.28%。作者没有回避这一点，明说累加曲线衡量的是组合版本，不是单个机制的因果效应。

## 🤔 我的判断

**定位：harness 自进化里诊断最扎实的一篇，但统计强度和选择口径要打折扣看。**

亮点：

1. 双 trace 加 Handbook 的诊断链条清楚，消融里去掉它 TBH Pass⁴ 掉 8 个点，是目前对「harness 内部可观测性」价值最直接的量化。
2. 外部研究被做成了可审计的流程：搜索计划、先例、信号映射、需要扩展什么，全都落成结构化记录。
3. 行为契约的三配置检查（旧 harness、新机制关、新机制开）很适合直接搬进任何自动改 harness 的系统。

需要注意：

- 表 1 里 DeepSeek 的 TB2.1 用的是按 TB2.1 分数挑出的 +OO 版本，作者在附录里写明了；直接迁移 TBH 选出的最终 +IR 版本，Pass@1 涨 3.09、Pass⁴ 涨 6.74，仍然有效但比表里小。
- 采纳规则只看总通过率高于基线，作者承认这可能留下损害原本稳定任务的改动；GPT-6-sol 的消融没有报告。
- 每题只跑 4 次，100 题的开发集上反复选择会利用噪声，历史基线也会受服务和环境漂移影响。
- 只从可追踪的翻转任务里发现问题，一直失败的题不在视野里。

对搭 agent harness 的直接启发：

- **给 harness 加函数级 trace，并和 agent 轨迹对齐。** 先回答「模型请求的东西是否真的被执行、输出是否完整回到模型」，再谈改提示词。
- **维护一份行为到代码的 Handbook。** 这和 OO-Harness 把 harness 写成代码类的思路互补：自动修改要有行为级的地图才能定位。
- **把「完成」做成可执行证据。** 让模型在声明完成时附验证命令和期望退出码，由 harness 去跑；同一读数要求两种独立方式确认；每类检查只拦一次。
- **评测面板同时放 Pass@1、Pass^k 和 Flip。** 稳定性提升和覆盖提升是两件事。
- **harness 版本绑定模型。** 交换实验说明 harness 是给特定模型调的，换模型要重新评测。

一句话收束：**模型能做对一次，harness 的活是让它每次都做对；先看清 harness 实际做了什么，再决定改什么。**
