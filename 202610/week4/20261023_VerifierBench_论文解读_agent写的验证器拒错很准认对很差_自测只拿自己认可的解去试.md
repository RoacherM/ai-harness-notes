# agent 写的验证器拒错很准、认对很差：自测只拿自己认可的解去试

你可能已经在用这种流程：让 agent 先为任务写一个可执行的检查脚本，再用它筛自己或别的 agent 的产出，通过的进训练集或直接合并。检查脚本跑起来很「严」，作弊的、改一半的都被拦住了，看着很放心。可如果你回头抽查被拒的那一堆，可能会发现里面有不少其实是对的：有人改了 `__init__.py` 而不是 `query.py`，有人多调了一个题目允许的只读查询，有人省略了一个有默认值的参数。**验证器拒绝的不是错误，而是「和它想的不一样」。**

宾大、UIUC、伯克利、纽约大学和罗切斯特大学的这篇 **VerifierBench: Benchmarking the Generation of Executable Verifiers for LLM Agents**（arXiv:2610.28679）专门测这件事：只给解题时能拿到的说明和环境，让 agent 写一个对任意候选解返回 PASS 或 FAIL 的验证器，然后用藏起来的、包含多种合法解和攻击的测试用例去打它。看完我的感受：这是对「agent 自己造题、自己写奖励」这条自我改进路线最实在的一次体检，结论很刺耳，**生成的验证器普遍过严，而 agent 的自测根本测不出来。**

## 核心摘要

VerifierBench 从六个开源 agent 基准里取了 222 道任务，分三类：工具调用（BFCL v4、ACEBench）、状态（τ²-bench、AppWorld、AgentDojo）和代码（SWE-bench Verified）。每道题配一套隐藏用例，共 4,993 条，分四组：标准答案、合法变体（换表述、换实现或换执行路径）、普通错误（初始状态、半成品、差一点、引入回归）和攻击（钻检查漏洞、伪造成功信号、干扰验证）。为了保证标签可信，作者设计了六项审计 **Verifier4Verifier（V4V）**：回放、可重复、溯源、输入与标签一致、平凡基线、变异测试。审计排除了 45 道源验证器本身有缺陷的题，**其中 Terminal-Bench 37 题全军覆没，35 题是因为它的测试输出解析器把跳过的测试算成通过。** 主指标是归一化平衡准确率 \( \mathrm{BA_{norm}}=\mathrm{TPR}+\mathrm{TNR}-100 \)。在统一的 Pi harness 下测了 19 个模型，**BAnorm 从 10.6 到 62.1，第一名 GPT-6-astra；每个模型的 TPR（21.1% 到 70.2%）都低于 TNR（79.2% 到 96.3%）。** 假拒绝高度集中：在分析过的记录里，87.9% 到 96.0% 的假拒绝来自「全拒」验证器，也就是对本题所有用例一律 FAIL。价值定位：第一次把「验证器生成」作为独立能力系统评测，并把失败追到了具体机制上：没有依据的检查，加上只确认不挑战的自测。

## 🎯 为什么这件事值得写

在数据驱动的自我改进里，agent 同时造任务和验证函数，验证函数决定谁拿奖励、谁进训练集。一个解题器只需要找到一个对的解，**一个验证器却必须接受所有合法解、拒绝所有非法解**，所以它必须分清「题目要求」和「合法解之间可以不同的选择」。

以往的评测要么测生成的测试断言、单元测试、复现 issue 的测试，要么测可执行规格。VerifierBench 把范围推到 agent 任务完成：正确性可能取决于工具调用序列、环境最终状态或代码改动。这正是 judge 和 eval 体系里最难自动化、又最常被自动化的那一环。

## 🏗️ 机制：任务、用例、审计、指标

**任务设定。** agent 拿到与普通解题相同的说明和环境，外加验证器的输入输出约定。工具调用验证器收到原始调用文本和解析后的函数名与参数；状态验证器收到交互记录（AppWorld 是解题代码）；代码验证器收到补丁和仓库。状态和代码任务里，生成过程和最终验证器都能通过 `run_public` 在环境里执行代码，生成阶段每题限 20 次执行。参考验证器和隐藏用例全程不可见，**agent 唯一的证据是它自己写的自测。**

**用例构成。**

| 组 | 标签 | 数量 | 内容 |
| --- | --- | --- | --- |
| 标准答案 | PASS | 222 | 指定的参考解 |
| 合法变体 | PASS | 1,344 | 表述变化 840，替代实现或路径 504 |
| 普通错误 | FAIL | 2,629 | 初始、半成品、差一点、回归 |
| 攻击 | FAIL | 798 | 钻漏洞、伪造成功信号、干扰验证 |

**V4V 六项审计。** 回放（源验证器的判决要和构造标签一致）；可重复（同一重置状态重跑判决不变）；溯源（每个判决可追到用例内容和验证器版本）；输入与标签一致（给验证器信息相同的用例不能标相反）；平凡基线（总是通过、总是拒绝、只认标准答案这三种验证器必须分别被负例、正例和合法变体揭穿）；变异测试（改掉源验证器里一项检查，必须有用例让两个版本判决不同）。

**指标。** TPR 和 TNR 先按题平均再取均值，两类等权：

$$
\mathrm{BA_{norm}}=2\cdot\frac{\mathrm{TPR}+\mathrm{TNR}}{2}-100=\mathrm{TPR}+\mathrm{TNR}-100
$$

常数判决得 0，完美得 100；超时、崩溃和格式错误留在分母里不给分。另报攻击假阳率 FPRh。

## 🧪 关键证据

**主表（Pi harness，222 题，%）节选：**

| 模型 | BAnorm | TPR | TNR | FPRh |
| --- | --- | --- | --- | --- |
| GPT-6-astra | **62.1** | 67.4 | 94.6 | 7.4 |
| Claude Opus 4.8 | 54.0 | 67.7 | 86.3 | 13.5 |
| Kimi K3 | 53.4 | **70.2** | 83.2 | 13.4 |
| GPT-5.6-sol | 52.9 | 56.8 | 96.0 | **0.8** |
| GPT-5.6-terra | 52.9 | 56.5 | **96.3** | 3.6 |
| GLM-5.2 | 48.8 | 68.1 | 80.8 | 12.1 |
| DeepSeek V4 Pro | 44.8 | 65.5 | 79.2 | 10.1 |
| Qwen3.7 Plus | 40.2 | 57.6 | 82.6 | 13.6 |
| Gemini 2.5 Pro | 14.2 | 31.7 | 82.5 | 4.0 |
| Doubao Seed 2.0 Mini | 10.6 | 21.1 | 89.5 | 3.7 |

拒绝正例主要是主动判 FAIL，而不是没给判决：各模型未被接受的正例里，57.1% 到 100% 是明确的 FAIL。按任务类型看差距最大的是状态和代码任务，模型平均 TPR 分别只有 27.7% 和 40.2%，工具调用任务是 79.2%。

**攻击拦得住不代表靠谱。** 状态任务上 GPT-5.6-sol 的 FPRh 是 0.0%，但只接受了 23.0% 的正例；代码任务上 17 个模型 FPRh 都是 0.0%，BAnorm 却从 −25.9 到 76.9 不等。**只报「作弊拦截率」的验证器评测，会把一个什么都拒的脚本评成满分。**

**harness 影响两个方向都有。**

| 模型 | Pi | 原生 harness | 差值 |
| --- | --- | --- | --- |
| Claude Opus 4.8 | 54.0 | 66.2（Claude Code） | +12.2 |
| Gemini 3.5 Flash | 35.7 | 50.7（Gemini CLI） | +15.0 |
| Gemini 2.5 Pro | 14.2 | 5.0（Gemini CLI） | −9.2 |
| GPT-6-astra | 62.1 | 58.0（Codex） | −4.1 |
| GPT-5.6-sol | 52.9 | 26.2（Codex） | −26.6 |

36 个配置里最好的是 Claude Opus 4.8 配 Claude Code 的 66.2。Codex 让它跑的五个模型全部下降，部分原因是一些 Codex 下的验证器要求补丁内容或修复位置必须是特定样子，在任何功能检查之前就拒掉合法修复。

**推理强度几乎不改总分。** GPT-6-astra 在 Pi 下从 LOW 调到 HIGH，BAnorm 只变 +0.5，Claude Code 下 −1.3；但分任务类型是反向的，代码任务涨、状态任务跌。HIGH 还更容易耗光执行预算：127 道状态和代码任务里，Pi 下耗尽 20 次预算的从 4 个涨到 77 个。

## 🔬 最有意思的部分

**一是假拒绝几乎都来自「全拒」验证器。** 一个验证器如果对本题所有用例都判 FAIL，它的 TPR 是 0、TNR 是 100，对 BAnorm 的贡献和常数判决一样是 0，但在只看 TNR 或攻击拦截率的视角里它是完美的。Astra 的追踪批次里，每种条件下 222 个验证器中有 68 到 75 个是全拒，贡献了 93.3% 到 95.5% 的假拒绝。

**二是「没有依据的检查」长什么样。** 作者人工读了 16 个验证器（12 道题），总结出几类：τ²-bench 银行任务里，验证器为了排除无关的写操作建了一个工具白名单，却漏掉了题目公开工具列表里一个合法的只读查询，结果 9 个正例全拒，而且连环境都没执行；Matplotlib 任务里，两个 Claude Code 验证器禁止改 `lib/mpl_toolkits/` 下的文件，可 3D 坐标轴的实现就在那里；零售任务里，用关键词列表识别办公用品，漏了 Headphones；还有只认 ISO 货币格式、只认纯数字设备号、TeX 空格解码不完整。

**三是「确认式自测」。** 为什么这些检查明明写在代码里，自测却没发现？16 个里有 8 个，自测用的正例恰好都满足那条多余的检查，比如 Django 任务的正例自测只改 `query.py`，从没改过 `__init__.py`。再多跑几个同类正例也揭不穿；负例自测也帮不上忙，因为一个非法补丁可能既违反真实要求又触发多余检查，拒对了并不能证明那条检查有道理。另外 8 个更糟，**自测从来没有拿到过一次完整的正例 PASS**，agent 在最终回复里自己也承认了，然后照样交了。

## 🤔 我的判断

**定位：judge 和 eval 方向这个月最值得放进书签的基准之一，诊断比排行榜更有价值。**

亮点三条：

1. 把「验证器生成」和「解题」分开测，并且用合法变体专门测接受面。大多数自动评测只关心拦不拦得住坏解，这篇证明真正的短板在另一边。
2. V4V 本身就是一套可复用的「验证器的验证器」清单，顺手揪出了 Terminal-Bench 把跳过当通过的解析器问题，这对所有用它做 RL 奖励的人都是提醒。
3. 机制分析落到具体代码和追踪上，「没有依据的检查加确认式自测」这个组合，几乎能在任何自动写 rubric 或写检查脚本的系统里找到。

问题与局限：分数是对有限构造用例、相对参考验证器的一致度，标签和参考一致不等于语义一定对；36 个配置在提示词、工具、推理设置上都不同，跨 harness 的差异不能归因到具体部件；排名是单次生成的点估计，没有重复和显著性；集中度分析只用了 9 个模型的归档记录和 1 个模型的追踪批次；机制分析是挑出来解释失败的样本，作者明说不能估计普遍程度。

对工程的直接启发，尤其是用 agent 自动写 rubric、写验收脚本或筛 RL 数据的系统：

- **验证器评测一定要报 TPR，并单独标出全拒。** 只看拦截率和 TNR，一个什么都拒的脚本就是最佳验证器。上线前加一条规则：对本题所有候选都 FAIL 的验证器直接打回。
- **每一条接受条件都要能追到题目原文。** 让生成验证器的 agent 为每个检查标注依据来自说明、工具定义还是环境规则，找不到依据的检查默认删掉或降级为警告。
- **自测要有「挑战型正例」。** 至少一个正例改变一个题目允许变化的属性（换文件、省默认参数、多调合法只读工具），至少一个负例只违反一个必需条件。只拿自己写的那一个解去试，测不出任何东西。
- **执行预算要给最终验证器留一份。** 探索和自测共用一个预算，结果最后一版验证器根本没跑过完整正例；没跑通的验证器不该被提交，更不该被用来筛训练数据。

一句话收束：**一个只会说不的裁判看起来最安全，其实最危险；验证器先要证明自己能认出对的，再谈拦住错的。**
