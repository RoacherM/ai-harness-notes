# 同一份 skill，强模型涨 31 点，弱模型反掉 8.8 点：要求明明写着却做不到，先改写法再谈自进化

你有没有过这种体验：从公开仓库里挑了一份写得很漂亮的 SKILL.md，挂到 Opus 上效果立竿见影；换成本地跑的小模型，同一份 skill 挂上去几乎没变化，有时还更差。你翻日志一看，skill 里白纸黑字写着「直接用 `pcap_utils.py` 里的 helper」「只填 value 列，保留 metric 名」，小模型偏偏跳过 import、自己手敲了一份 CSV，37 个测试一个没过。

业内把这类做法叫 **harness self-evolution**：不动模型参数，从执行经验里提炼 skill、改写 harness，让 agent 越用越好。前面大家关心的多是「经验有没有抽对、有没有忠实写进 skill」。问题是：**经验写对了，执行它的模型接得住吗？同一份 skill 对不同能力的模型，是否需要不同的写法？**

中科院大学、清华、UCSC、NUS、中科院软件所中文信息处理实验室等团队的 **Evolving to Match Capabilities: Improving Harness Self-Evolution via Skill Adaptation**（arXiv:2610.33024）研究的就是这个错配。看完我的感受：它把「skill 写给谁看」这件事第一次做成了可测的变量，而它给出的那份 meta-skill 本身就是一份很实用的 skill 写作规范。

## 核心摘要

作者从 SkillsBench、DocOps、Tessl 三个构造方式互不相关的基准里取了 607 个能在自家环境稳定运行的 task-skill 对，按无 skill 时的表现把七个模型分成三档：弱档 Gemma-4-E4B、Qwen3.5-9B、Qwen3.6-flash，中档 GPT-5.4-mini、Claude-Sonnet-4.6，前沿档 GPT-5.6-luna、Claude-Opus-5。全量平均时 skill 对每个模型都只是小幅增益，看不出档位规律；但用一条「前沿档明显受益且明显高于弱档」的规则筛出 **103 个 skill 敏感对** 后，**skill 让 GPT-5.6-luna 涨 31.1 点，却让 Gemma-4-E4B 掉 8.8 点；在弱模型仍失败的 run 里，86% 违反的要求本来就写在 skill 里。** 作者读弱模型轨迹，把首个可观察失败归为四类：工具执行、上下文管理、指令遵循、验证，再把这四类诊断蒸馏成一份固定的、与任务无关的 meta-skill，用来指导改写 skill。两种用法都有效：一是让强模型在不看任何执行证据的情况下一次性改写，Kimi-K3 带 meta-skill 改写后三个弱执行者比原 skill 涨 5.1 到 14.1 点，比只给一句「改成对所有模型都好用」多 5.1 到 6.0 点；二是放进五轮自进化循环，每个模型根据自己上一轮的轨迹和 verifier 输出改自己的 skill，七个执行者从 Gemma-4-E4B 到 Kimi-K2.5 第五轮都比不带 meta-skill 的同一循环高 2.0 到 5.1 点。价值定位：harness 的收益不是 harness 自身的属性，评估要按能力档分开看，自进化循环要给「弱执行者怎么失败」的诊断指导。

## 🎯 为什么这件事值得写

我们之前归档过不少 skill 方向的论文：Skill-Use 发现挂上 skill 不等于会用，RASO 讲公开 skill 要跨 harness 适配，MetaSkill 让 Builder 学元技能，GRSE 用同题多跑对比找出拖后腿的那条 skill，SocraticSkill 让 agent 边练边问。它们的共同前提是「一份 skill 写好了就能到处用」。

这篇的切入点更具体：**skill 是写一次、原样发给所有模型的**，而 skill 的作者往往是强模型或人类专家，默认读者也像他们一样能从参考材料里推断步骤。论文的图 1 就是一个缩影：同一份 skill，Opus-5 照着 import 了 helper、拿到正确的 TCP 包数，37 个测试全过；Gemma-4-E4B 跳过了 import，手敲数据，0 个通过。

这件事对两类人特别重要：

1. 用小模型或本地模型跑 agent 的人，他们拿到的公开 skill 几乎都是为强模型写的；
2. 做 harness 自进化的人，如果评估只用一个代表性模型，可能会把「对强模型有效」误当成「对所有模型有效」。

## 🏗️ 机制：筛出敏感对，诊断四类失败，写成 meta-skill

**筛选规则。** 记 $s_m(T_i,S_i)$ 为模型 $m$ 带 skill 的得分，$s_m(T_i,\varnothing)$ 为不带 skill 的得分，skill 增益 $\Delta_m(T_i)=s_m(T_i,S_i)-s_m(T_i,\varnothing)$，档位增益 $\Delta_G$ 是档内平均。档位 $G$ 被认为受益，当且仅当

$$
\Delta_G(T_i)\ge\tau\quad\text{且}\quad\Delta_G(T_i)-\Delta_W(T_i)\ge\tau,\qquad \tau=0.10
$$

前沿档受益，或前沿档无 skill 已饱和（均分不低于 0.95）而中档受益，就算 skill 敏感；弱档带 skill 已经不低于 0.80 的对被剔除。最终 103 对：SkillsBench 32、DocOps 32、Tessl 39，其中文档处理占 37%，软件工程 20%。

**四类失败。** 作者读这 103 对里三个弱模型的带 skill 轨迹，给每条轨迹的**首个可观察失败**打标签，一共 131 个标签：

| 失败类 | 判定 | 标注对数 |
| --- | --- | --- |
| 工具执行 EXE | 没有交付物：一两次工具调用就停，把 xlsx 这种文件格式当工具调，或者工具报错后没恢复 | 51 |
| 指令遵循 IF | 有多次工具调用也有输出，但 skill 里写明的要求只完成了一部分 | 35 |
| 上下文管理 CTX | 把 skill 的示例或参考文件当成当前任务，或者交付到错误路径 | 28 |
| 验证 REF | 产物完整但答案和 verifier 算的不一样，轨迹里没有有效检查 | 17 |

**meta-skill 的四条处方。** 它是一份放在改写者 system prompt 里的固定文档，核心思路是「先定位最早的那个断点，再修它；浅层的断点还在时，深层的修补没有效果」：

- **EXE**：在开头写清哪些名字是可调用的、哪些只是文档，加环境预检，给第一个可能失败的兜底，命令要能原样执行；
- **CTX**：开头先写用户任务、允许修改的范围和交付路径，用一句话说明其余内容是参考材料而不是新请求，需要的辅助文件内容直接内联；
- **IF**：把每条相关要求改写成一行「动作、目标、完成条件」，包括反向分支（比如「如果 X 已存在，就停止且不做任何改动」），并且明确指出**写得更多没用，原文本来就有**；
- **REF**：结尾加一个独立检查，从磁盘重读产物、用第二种方法重算、和明确阈值比较、不过就循环；「我写了文件」「运行没报错」不算证据。

外加几条硬规则：只改证据指向的地方，不强制文档结构；只引用任务、skill、轨迹、verifier 输出或执行接口里出现过的函数、参数和路径，不许编名字；不许贴期望输出或答案；证据不支持改进时返回 NO_CHANGE。

**改写协议和闸门。** 改写者拿到任务说明、执行者的完整工具列表（SkillsBench 用 OpenHands 的工具 schema，DocOps 和 Tessl 用 Claude Code 暴露的工具名）、当前 skill 原文和辅助文件列表；自进化时再加上上一轮的结果、轨迹摘要和 verifier 输出。返回值要么是改动文件的完整新内容，要么是 NO_CHANGE。harness 对每个返回文件做两道检查：

- **可加载**：非空、路径对应已有 skill 文件、YAML frontmatter 的 name 不变、不超过 64,000 字符；
- **答案泄漏**：收集只出现在隐藏测试或参考解里、却不在公开材料和改写者可见证据里的特定 token（至少八个字符且含数字或下划线的标识符，以及至少两位小数的数），引入一个这样的期望值或两个这样的标识符就拒绝。

被拒绝时执行者跑原 skill 并照常计分，所以无效改写会拉低本组均值而不是被悄悄丢掉。自进化是一条五轮直链，不挑最好的一轮，不回滚，并且每轮都对比同一时间窗口内重跑原 skill 的基线，以排除服务端漂移。

## 🧪 关键证据

**一次性改写（不看执行证据，103 对均分）：**

| 改写者 | Qwen3.6-flash | Gemma-4-E4B | Qwen3.5-9B | 平均 |
| --- | --- | --- | --- | --- |
| 原 skill | 0.529 | 0.029 | 0.323 | 0.294 |
| 弱模型自己改 | 0.476 | 0.056 | 0.280 | 0.271 |
| GPT-5.6-sol | 0.563 | 0.139 | 0.303 | 0.335 |
| GPT-5.6-luna | 0.602 | 0.119 | 0.307 | 0.343 |
| GLM-5.3 | 0.626 | 0.138 | 0.374 | 0.379 |
| Kimi-K3 | 0.616 | 0.170 | 0.374 | 0.387 |

四个强改写者都把平均拉高了，Kimi-K3 和 GLM-5.3 三个执行者全涨；弱模型在没有证据的情况下自己改，平均反而从 0.294 掉到 0.271。最弱的 Gemma-4-E4B 涨得最多，在 Kimi-K3 下从 0.029 到 0.170。

**把 meta-skill 换成一句话。** 同样用 Kimi-K3，只给「把这个 skill 改成对所有模型都好用」：Qwen3.6-flash 0.565、Gemma-4-E4B 0.115、Qwen3.5-9B 0.314，最后一个甚至略低于原 skill 的 0.323；带 meta-skill 分别是 0.616、0.170、0.374。meta-skill 带来的额外增益 5.1 到 6.0 点，占平均增益的一半以上。

**五轮自进化（第五轮，带 meta-skill 与不带的差）：** Qwen3.6-flash +0.030，Gemma-4-E4B +0.051，Qwen3.5-9B +0.049，Qwen3.5-27B +0.046，Gemma-4-26B +0.020，Qwen3.5-plus +0.025，Kimi-K2.5 +0.035。七个执行者符号全部为正。不带 meta-skill 时自我改写帮助不大而且不稳定：Qwen3.5-9B 第三轮见顶后回落到接近基线，Gemma-4-E4B 每一轮都低于基线（基线 0.104，五轮分别是 0.097、0.060、0.089、0.071、0.096）；带 meta-skill 时 Gemma-4-E4B 从第三轮起一直高于基线（0.116、0.161、0.147）。

**按失败类看 meta-skill 的增益（三个弱执行者平均）：**

| 失败类 | 一次性改写 | 五轮自进化 |
| --- | --- | --- |
| EXE（51 对） | +0.056 | +0.065 |
| IF（35 对） | +0.055 | +0.046 |
| CTX（28 对） | +0.103 | +0.007 |
| REF（17 对） | +0.003 | +0.104 |

诚实泼冷水：

- 每个格子只跑一次。作者自己也说不对 0.02 到 0.05 的差值大小做解读，只依赖七个执行者符号一致。
- 同一个执行者在两个实验里的「原 skill」得分并不一样，Gemma-4-E4B 一次性改写实验里是 0.029，自进化实验同时间窗口重跑的基线是 0.104，这个波动本身就和很多增益同量级。
- 按基准拆开看有反向格子，比如 Qwen3.5-plus 在 DocOps 上第五轮带 meta-skill 反而低 0.188，Qwen3.6-flash 和 Gemma-4-26B 在 DocOps 上也是负的。
- meta-skill 是用 Claude-Opus-5 辅助写的，诊断用的正是三个弱执行者在这 103 对上的轨迹，测试集和构造集重叠；额外四个执行者算是部分的外推检验。
- skill 是整份注入上下文的，没测检索和渐进披露；多 skill 当成一个整体评估。

## 🔬 最有意思的部分

**一是「写得更多没用，原文本来就有」。** 这句话直接写进了 IF 类的处方里。86% 的弱模型失败违反的是 skill 里已有的要求，说明问题不在信息量，而在信息的**可执行形态**：一条要求要拆成动作、目标、完成条件，还要写反向分支。这和我们平时写 AGENTS.md、规则文件的习惯正好相反，大家通常是出错一次就往里加一段说明。

**二是证据和指导缺一不可，而且分工很清楚。** 一次性改写只能看 skill 文本，所以它擅长修「从文本就能看出来的问题」：有没有说清可调用工具、每条要求有没有完成条件、开头有没有写任务和交付路径，CTX 类涨 +0.103。验证类问题光看文本看不出来，skill 可以写一个检查，但只有轨迹能告诉你执行者到底做没做；所以自进化里 REF 类涨 +0.104，比一次性改写多 0.101。反过来，**只有证据没有指导时，弱改写者会漂**；只有指导没有证据时，弱模型自己改反而变差（一次性改写里弱执行者带着 meta-skill 改自己的 skill，三个里有两个掉分，平均从 0.294 掉到 0.271）。

**三是 skill 能告诉弱执行者做什么，做不做得到看模型。** 图 7 那个地理任务很典型：不带 meta-skill 的 skill 一直是六节参考笔记，没有交付目标也没有结果检查，同一个错误距离活过了五轮改写；带 meta-skill 后第一轮就写清了输入、输出路径和键、只用 EPSG:4087 不许自造投影、时间转 ISO 8601 并检查格式、重读 answer.json 重算距离直到匹配，Qwen3.6-flash 五轮过了四轮。唯一失败的那一轮，它改了脚本却没重跑。作者总结的残余失败也都是这一类：改了脚本不重跑、重复失败的调用、没写产物就停、多约束时只保住 skill 强调的那一条。

## 🤔 我的判断

**定位：问题刻画加一个轻量方法，测量部分比方法部分更有分量。**

亮点：

1. 把「skill 收益随执行者能力变化」做成了可复现的筛选规则和 103 对测试床，并跨三个构造方式无关的基准复现。
2. 四类失败按「走到哪一步断的」排序，处方要求先修最早的断点，这是一条可以直接用在任何 harness 改写循环里的原则。
3. 改写协议很工程化：完整文件输出或 NO_CHANGE，加载检查加答案泄漏检查，拒绝后照常计分，五轮直链不挑最好不回滚，同窗口基线排除端点漂移。这套闸门比 meta-skill 本身更值得抄。

问题与局限：

- 单次运行，噪声和增益同量级，结论主要靠符号一致性撑着。
- meta-skill 的构造集和测试集重叠，泛化到新任务、新 harness 的证据还不够。
- 方法只改 skill 文本，执行者自身的「改了不重跑」这类问题它承认无能为力，这部分可能需要 harness 层的机制（比如改后提醒或强制重跑）来补。

对工程的直接启发：

- **skill 的评估要按能力档分开报。** 如果你的系统里有强弱模型混用或者子 agent 路由到小模型，同一份 skill 最好在每个档位上各测一次，而不是只拿主模型测。
- **给不同档位的执行者维护不同写法的 skill。** 强模型那份可以是参考材料风格；弱模型那份要把任务、范围、交付路径放最前面，要求写成动作、目标、完成条件，结尾强制重读和重算。这和按 profile 路由子 agent 的思路正好能接上：路由到哪个模型，就挂哪一版 skill。
- **自进化循环里，改写者的 system prompt 放一份失败诊断规范，user prompt 放证据。** 两者分开，前者固定可以吃前缀缓存，后者每轮变化。再加上可加载和答案泄漏两道代码闸门，改写结果才能进 harness。
- **只改 adapter 层就能拿到收益。** 整个方法不动模型参数，也不动 harness 代码，只改 skill 文本，属于成本最低的一层演化面。

一句话收束：**skill 不是写给「模型」看的，是写给「这个模型」看的，自进化要先学会换位写作。**
