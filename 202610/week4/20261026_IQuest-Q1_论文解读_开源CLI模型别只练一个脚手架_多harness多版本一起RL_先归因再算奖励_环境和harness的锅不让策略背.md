# 开源 CLI 模型别只练一个脚手架：多 harness 多版本一起 RL，先归因再算奖励，环境和 harness 的锅不让策略背

你有没有过这种体验：一个开源模型在榜单上配着某个 harness 跑得很漂亮，你把它接进自己的 Claude Code 或 OpenCode 配置里，第一个长任务就因为工具名对不上、参数格式不认识，连着报几十次 tool-call 错误。模型不是不会干活，是它只见过一种调用格式、一种 harness 的交互节奏。

IQuest Research 的这篇技术报告 **IQuest-Q1: Advancing Foundation Capabilities for Agentic CLI Systems**（arXiv:2610.30949）发布了一个 320B 总参、15B 激活的开源 MoE 模型，整条训练流水线都围绕 CLI 交互来设计。架构和预训练部分写得很细，但对我们做 harness 的人来说，最值得读的是后训练：**在 Claude Code、Codex、OpenCode 及其不同版本的轨迹上训同一个策略**，奖励前先把失败归因给策略、环境或评测器，再加上一套三层防 reward hacking 的环境管线，以及一段「模型参与开发自己下一代」的人在环上的案例。看完我的感受：这篇把「harness 泛化」从论文概念变成了一个开源模型的工程默认项，而且给出了不少可以直接抄的环境卫生做法。

## 核心摘要

IQuest-Q1 分三段训练：（1）预训练用 Stable SplitNorm、Muon 优化器和 μP 参数化，四阶段课程把代码数据占比从 40% 提到 70%，预训练加中训练共 29T token；（2）中训练扩展数据领域和格式、渐进拉长上下文；（3）后训练是两阶段 SFT（240B+ 和 50B+ token）、按领域的 RL、四个冻结专家的多教师在线蒸馏（MOPD），中间穿插跨阶段残差模型合并。RL 的每个 episode 明确指定任务领域、harness 及其版本、环境和评测器，GRPO 只在同一 harness 与评测器版本内比较重复 rollout，采样平衡「领域乘 harness」组合并保留回归样例。主要结果：SWE-Bench Pro 57.5、DeepSWE v1.1 64.6、NL2Repo-Bench 63.0、CyberGym 84.5、SkillsBench 74.1、Terminal-Bench 2.1 83.2、MCP-Atlas 78.4、Toolathlon-Verified 75.0，与 GLM-5.3-Flash、DeepSeek-V4-Flash-0731 等开源模型互有胜负，整体仍明显落后于 Claude Opus 5。报告也坦白 Terminal-Bench 3.0 和 4.0 只有 17.9 和 22.7，低于 GLM-5.3-Flash 的 30.0 和 32.8。

## 🎯 为什么一个模型技术报告值得放进 harness 笔记

我们之前归档过 HarnessScaling（只在一个脚手架里练 RL 会偏科）和 HarnessAdapt-RL（工具和 hook 跟着策略一起进化）。这些都是研究性结论，IQuest-Q1 则是一个开源基座把它们做成了生产流程：训练运行时可以在一次 run 里混合多个 harness 和多个版本的轨迹，每个训练实例指定自己的 scaffold、环境和验证器，运行时在隔离沙箱里执行，并且保留原 harness 的工具编排、上下文管理和交互流程，再把不同 API 协议映射到统一的策略接口。

这意味着它学到的不只是「怎么写代码」，还有「Claude Code 的 hook 会在什么时候拦我」「Codex 的工具 schema 长什么样」。报告第 6.2 节的案例正好反过来证明了这件事的必要性。

## 🏗️ 后训练的几块关键设计

**一、任务合成分三类。** 通用 agent 任务从 RapidAPI 和 Smithery 的 API 与 MCP server、网上公开的 skills、工作区文件出发，按标准职业分类覆盖各行业，走「先解再改」循环；推理任务走文档锚定管线控制概念覆盖和难度；编码任务从 GitHub 仓库和工业数据构建可执行环境，用多个版本的 Claude Code、Codex 驱动环境构建，skills 辅助搭建。

**二、编码实例的质量闸门。** 这一段我认为最实用：

| 环节 | 做法 |
| --- | --- |
| 验证器来源 | agent 写的测试、改造的仓库测试、从文档行为派生的检查 |
| 离线化 | 外部依赖换成本地 fixture 或 mock |
| agent-judge 循环 | 检查可执行性、泄漏，以及指令、参考解、环境、验证器之间的一致性，修复坏实例、拒绝弱断言 |
| 基本门槛 | 参考解必须通过，no-op 解必须失败 |
| 轨迹审查 | rubric 审查过滤作弊和低质量执行，不只看二元成败 |
| 难度 | 重复跑估难度，太简单的加 skill 或约束后重新验证，保留能暴露模型失败的有效实例 |

实例来源分两种：从原始素材新建环境，以及对已验证环境做 re-task、重写、故障注入、演化、加固修复和选择性重跑。

**三、三层防 reward hacking。**

- **环境准备**：按任务清理 Git 历史、删掉可能泄露答案的文件、或者干脆建只含必要材料的新环境，并隔离任务之间的资源。
- **执行时检查**：限制网络和敏感文件访问，在工具调用执行前拦截；拦截规则来自观察到的作弊行为；被拦截的操作返回明确反馈，agent 可以继续干活而不是直接崩掉。
- **轨迹审计**：规则检查加 rubric 引导的 LLM 判断，看执行的命令、工具输出和提交的解，识别取泄露补丁、读隐藏测试、改评测脚本等；确认作弊的轨迹剔除，可疑的标记复审，检出案例再反哺拦截规则。

针对具体任务的做法也写得很具体：SWE 类任务只保留到 base commit 的 Git 历史，并**用 Claude Code、Codex、OpenCode 的 hook 拦截取现成答案的尝试**；Terminal-Bench 不需要 Git 历史就删，必须保留时在执行前查命令；ProgramBench 则建只含编译后 oracle 和文档的新容器。

**四、奖励之前先归因。** 独立验证器决定终局正确性；长轨迹的分段辅助奖励只给可度量的进展，惩罚多余计算、违反约束和 reward hacking；模型生成的诊断必须有执行记录作为证据才能进入信号。更重要的是：**策略造成的错误提供学习信号，与策略无关的环境或 harness 故障被 mask 掉，评测器故障直接阻止样本被消费。** 这一点和我们在 HarnessRL 那篇里看到的「先分清没信号还是虚高」是同一种纪律。

**五、MOPD 与合并。** 学生从 SFT 第二阶段初始化，按任务领域选择四个冻结教师之一：交互体验专家、多 harness 专家（Claude Code、Codex、OpenCode）、长程专家（长编码和安全任务）、通用专家。优势是裁剪后的 token 级对数比：

$$
\tilde a_{i,t}=\text{clip}\Big(\log\frac{q_{d_i}(y_{i,t}|h_{i,t})}{p_k(y_{i,t}|h_{i,t})},-c,c\Big)
$$

损失按长度归一，只在模型生成的 token（含 tool-call token）上计算，重复性 rollout 的权重 \(m_i\) 置零。工程上，教师权重放分布式存储按需加载，只把当前教师需要的分片放进显存，下一个教师在当前前向时预取。rollout 与训练的一致性靠 token-in token-out 链路加会话级前缀树保证。

## 🔬 最有意思的部分：模型参与开发自己的下一代

第 6.2 节是一个完整的「人在环上的递归自我改进」案例。目标是适配不同 scaffold 和 tool-call schema：模型在熟悉 schema 上表现好，换一个陌生的就会在一个长任务里产生 35 次 tool-call 错误。基于 IQuest-Q1 的 agent 追踪了 6,054 次工具调用，发现训练数据严重偏向单一 schema，还有一部分记录因为预处理问题导致工具定义和调用参数不匹配；它提出清洗这些记录并用多样 schema 做数据增强，人类专家审查诊断和方案后批准训练；agent 实现清洗与增强管线、准备实验配置，训练用了 2.35B token、938.7 GPU 小时，在留出 schema 和熟悉 schema 上评测并检查回归。

另一个小细节在基础设施部分：为了减少 RSI 过程中模型和训练改动带来的静默错误，agent 会从训练配置里挖掘语义不变量，转成分布式训练时运行的检查，用来发现与单机语义不一致或违反预设约束的情况。

报告没有给出这次迭代前后的具体数字，只说明了流程。但它很清楚地展示了一个分工：agent 负责失败分析、干预设计、实现和评测，人类负责审关键决策、控制昂贵实验和决定哪些改动带到下一轮。

## 🤔 我的判断

**定位：一份对 harness 工程师比对模型研究者更有用的技术报告，重点读第 4 节和第 6.2 节。**

亮点：

1. 多 harness 多版本 RL 被做成了训练运行时的一等公民，每个实例声明 scaffold、环境、验证器，GRPO 只在同版本内比较，这是 harness 泛化的落地范式。
2. 奖励前的失败归因和环境三层防作弊写得足够具体，hook 拦截、no-op 必败、参考解必过、rubric 轨迹审查，都可以直接搬进自己的 RL 或评测环境。
3. 第 6.2 节把 tool-call schema 偏置这个很多人踩过的坑，以一个可复现的诊断流程呈现出来。

需要注意：

- 它是技术报告，几乎所有设计都没有消融，多 harness RL、MOPD、合并各自贡献多少无从判断。
- 在最难的 Terminal-Bench 3.0 和 4.0 上明显落后 GLM-5.3-Flash，长程终端能力仍是短板；报告自己也承认会忽略约束、重复失败尝试。
- IQuest-CLIBench 是闭源自建基准，交互体验结论要等社区复现。
- 6.2 节的 RSI 案例没有前后对比数字。
- 只支持文本输入；tool call 使用 IQuest 专用格式，需要兼容的服务端解析器和 harness。

对搭 agent harness 的直接启发：

- **训练和评测都要跨 harness。** 至少在两三个主流 harness 及其不同版本上跑同一套任务，否则 schema 偏置会在上线第一天暴露。
- **奖励先归因再计算。** 把 harness 故障、环境故障、评测器故障和策略错误分开，前两类 mask，第三类阻止消费，这能省掉大量被污染的训练信号。
- **环境闸门固定成清单。** 参考解必过、no-op 必败、泄漏检查、弱断言拒绝、rubric 轨迹审查，这五条是可验证环境的最低配置。
- **用 harness 的 hook 当防作弊层。** 被拦截的操作返回明确反馈而不是直接终止，让 agent 能继续正常完成任务。
- **让 agent 参与改进时，人管决策和预算。** 6.2 节的分工方式比「全自动 RSI」更适合现阶段落地。

一句话收束：**想让模型在任何 harness 里都好用，就得让它在训练时见过各种 harness，并且别把 harness 的错算到模型头上。**
