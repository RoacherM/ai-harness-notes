# 压缩器删掉的，正是要改的那一行：挑对几个整文件原样给，比压缩和检索都强

你有没有过这种体验：为了给 coding agent 省 token，在上下文里接了一个提示压缩器或者代码检索，账单确实降了，可它交出来的 patch 时不时就「打不上」：diff 里要改的那一行，在真实文件里根本不存在。行业里管这一层叫 **context compression / repo retrieval**（上下文压缩与仓库检索）。**在同样的 token 预算下，到底是删 token、检索片段，还是挑几个整文件原样塞进去，能修好更多 issue？**

UIUC 翟成祥组这篇 **Skip the Compressor**（arXiv:2610.21073）做了一次预算严格对齐、用测试判分的对照。它的答案很朴素：**把预算花在「选哪几个文件」上，然后整文件一字不改地给**。他们的简单选择器 CQ2-CARE 在 300 个 SWE-rebench issue 上，比三种压缩器、三种检索器都强，还略胜两个专门为修 issue 训练的方法。看完我的感受：这篇的价值不在方法多巧，而在 **把失败拆成了两个可测的量**，一个是「要改的文件在不在上下文里」，一个是「给的代码是不是原文」，两者分别都会让你丢分。

## 核心摘要

作者把仓库看成 agent 的长期记忆，把提示看成它的压缩视图，问：固定预算下哪种压缩视图能修好最多 issue。实验设定是单次出 patch：固定模型拿到 issue 和一份上下文，写一个 unified diff，用 SWE-rebench 官方 harness 跑 FAIL_TO_PASS 和 PASS_TO_PASS 测试判分。每个 issue 的预算 $B_i$ 等于 CQ2-CARE 在该 issue 上实际用掉的 token 数，压缩器调自己的压缩率落到 $B_i$ 的 ±2% 内，检索器按排序装到 $B_i$。CQ2-CARE 的做法是：只给模型一份路径清单，独立问两次「哪些文件必须改」，取两次都点名的文件（排除测试和文档目录），再让模型提最多 4 个 grep 检索（定义、调用方、字符串），把命中的片段补进来，文件整份原样给。结果：GPT-5.6 修好 **43.7%**，Claude Opus 5 修好 **46.7%**，比最好的压缩器都高 **6.3 个点**，比最好的检索器高 9.3 和 12.7 个点；比 SWE-Pruner 高 2.0 和 7.3，比 SweRank 高 0.7 和 1.7（后者不显著）。拆解下来，检索器的问题是 **漏掉要改的文件**，chunk 检索在四分之一以上的 issue 上一个要改的文件都没给；压缩器的问题是 **改了原文**，LLMLingua-2 只有 17.5% 的行是原文，patch 能打上的比例从 98.0% 掉到 70.7%。最关键的对照：在 CQ2-CARE 自己的上下文里每行删掉 20% 的 token，文件一个没变，修复率就掉 9.7 个点。作者给的结论是一条规则而不是排名：**先把候选文件选好，真要裁就整行裁**。

## 🎯 为什么这件事值得写

上下文管理已经是 coding agent 降本的主战场：之前的工作报告过能把成本砍半或者砍掉五分之一到三分之一。SWE-bench 仓库平均 3,010 个非测试文件、43.8 万行，不压缩根本塞不下。但三条相关研究线各自只看了一部分：提示压缩（LLMLingua 系列）主要在自然语言上验证，仓库检索主要看相似度，issue 修复系统里的裁剪（SWE-Pruner、SWEzze）要么只在已知故障位置附近比。**没有人在同一预算、让每种方法自己决定放哪些文件的条件下，把三者放在一起比。**

这和我们本周读过的几篇是一条线：

| 工作 | 压缩的对象 | 立场 |
| --- | --- | --- |
| CarryOn | 对话历史 | 别压缩历史，让文件和状态当进度载体 |
| TokenEconomizer | 每轮塞给 agent 的内容 | 从历史轨迹学该塞什么该砍什么 |
| **Skip the Compressor** | 仓库代码 | 别删 token，挑文件、原样给 |

作者点出的根本原因很简单：压缩器面向「输出是答案或摘要」的场景设计，删几个词无伤大雅；**而改代码必须逐字引用要改的那几行**，Anthropic 的引用替换式编辑工具、Aider 的 SEARCH/REPLACE、SWE-agent 和 OpenHands 的行号编辑都依赖这一点。

## 🏗️ 机制：三种填预算的方式和两个度量

**三种上下文构造。** 记仓库为 $R$，issue 为 $q$，上下文 $m$ 是一串源码片段，每段带 `--- SOURCE k: path lines a-b ---` 头。

- 检索：把仓库切成单元（顶层定义、60 行窗口或整文件），按与 $q$ 的相似度排序，原样装满预算；
- 裁剪：从一个更大的候选上下文里删掉打分模型认为最没用的单元（token、行或代码块），直到落进预算；
- 精确选文件：预测要改的文件集合 $F$，整份原样给，再接上少量证据片段 $E$：

$$
m_{\text{sel}} = \big(f[1{:}|f|]\big)_{f\in F} \oplus E
$$

**两个事后度量（用金标 patch 计算，从不给模型看）。**

$$
\rho(m)=\frac{|F^\star\cap\{f_1,\dots,f_K\}|}{|F^\star|},\qquad
\varepsilon(m)=\frac{|\{\ell\in m:\ell\in f(\ell)\}|}{|\{\ell\in m\}|}
$$

$\rho$ 是金标要改的文件有多少出现在上下文里，$\varepsilon$ 是上下文里有多少行是原文。检索保住 $\varepsilon=1$ 但会丢 $\rho$；裁剪保住 $\rho$ 但压低 $\varepsilon$；精确选文件保住 $\varepsilon$，把预算全花在 $\rho$ 上。

**CQ2-CARE 的四步。**

1. 盘点：模型看不到整个仓库，只看到一份路径清单，按与 issue 共享的词数挑出、按字母序列出（排除 node_modules、vendor、dist 等目录）；
2. 定位：独立采样两次「哪些文件必须改」，取交集，去掉 test(s)/doc(s) 目录，按倒数排名和排序；交集为空就退回第三次采样；
3. 证据：模型读 issue 和选中文件后，提最多 4 个类型化检索，每个检索用 `git grep` 在至多 2 个新文件里取包围定义或附近窗口，最多累计 8 个文件；
4. 组装：选中文件每份最多 60K token，证据片段每段最多 12K，总量超过 80K 的块跳过。

GPT-5.6 下平均选中 1.7 个文件（中位数 1），另带 6.0 个文件的证据片段，平均 13.8K token；Claude 选得更多，平均 27.1K。

## 🧪 关键证据

**主结果（修复率 %，预算逐题对齐）。**

| 上下文 | GPT-5.6 | Claude Opus 5 | GPT 下 $\varepsilon$ | GPT 下 $\rho$ | GPT 下 patch 可应用 |
| --- | --- | --- | --- | --- | --- |
| **CQ2-CARE** | **43.7** | **46.7** | 100.0 | 79.0 | 98.0 |
| LLMLingua-2 | 30.0 | 40.3 | 17.5 | 78.3 | 70.7 |
| LongLLMLingua | 35.0 | 29.0 | 67.1 | 63.7 | 84.0 |
| LongCodeZip | 37.3 | 36.0 | 96.8 | 72.2 | 89.7 |
| SWE-Pruner（训练过） | 41.7 | 39.3 | 91.7 | 77.4 | 93.0 |
| BM25（chunk） | 29.0 | 34.0 | 100.0 | 58.3 | 86.7 |
| Dense（chunk） | 22.7 | 33.7 | 100.0 | 57.9 | 78.3 |
| BM25（整文件，SWE-bench 原版） | 34.3 | 34.0 | 100.0 | 49.8 | 95.7 |
| SweRank（训练过） | 43.0 | 45.0 | 100.0 | 71.7 | 97.3 |
| 金标文件（上界） | 49.3 | 46.3 | 100.0 | 97.0 | 97.7 |
| 不给源码（下界） | 8.7 | 13.0 | n/a | 0.0 | 42.0 |

GPT-5.6 下金标文件只比 CQ2-CARE 多 5.7 个点，Claude 下没多：**在压缩器会用的预算里，让模型自己挑几个整文件，已经拿回了「知道该改哪个文件」的大部分收益**。

**成本。** GPT-5.6 下整条流水线每题 API 花费 0.151 美元，未压缩的单次定位上下文 0.199 美元，压缩器上下文 0.168 到 0.177 美元（它们要先构造未压缩上下文）。LongLLMLingua 和 LongCodeZip 每题还要额外花中位 34 到 37 秒 GPU 时间。

**泼冷水。** 第一，这是单次出 patch，不是能自己再读文件、跑测试的多轮 agent，作者明确把多轮下的取舍留给未来；真实 agent 看到压缩视图后可以回头读全文，部分损失可能被弥补，只是要多花一轮和 token。第二，只有 Python、只有一个基准，预算取在 CQ2-CARE 自己的工作点上。第三，大多数格子只有一次 patch 采样，第二次采样会翻转 8.7% 到 18.9% 的结果，像 Claude 对 LLMLingua-2 这种 p=0.027 的小差距很脆。第四，实验计划是书面的但没有时间戳，作者自己说不算预注册；整文件 BM25、两个训练方法和第 4 节分析都是事后加的。

## 🔬 最有意思的部分

**一是两种失败被干净地拆开了。** 检索器失败在「没给」：chunk BM25 和 dense 只有五分之一或更少的行来自要改的文件（CQ2-CARE 是一半），并且在 26.2% 和 27.5% 的 issue 上一个要改的文件都没出现，CQ2-CARE 这个比例是 3.4%。图 1 的例子是 twine 的一个 issue：报告某些错误消息漏了 f-string 的 `f`，chunk BM25 用仓库里的 issue 模板填满了预算，因为它们和报告措辞最像；LLMLingua-2 保住了要改的文件，却把 `f` 前缀和引号删了，模型据此写的 patch 改的是一行不存在的代码。压缩器失败在「改了」：CQ2-CARE 能修而 LLMLingua-2 修不了的 48 个 issue 里，28 个是 patch 打不上。

**二是控制实验证明两种损失各自都要命。** 在 CQ2-CARE 自己的上下文里每行删 20% token，文件完全不变，patch 可应用率从 98.0% 掉到 78.7%，修复率掉 9.7 个点，和主实验里压缩器的损失量级相当。反过来，让压缩器从 CQ2-CARE 选好的候选文件出发去裁，LongCodeZip 修好 44.7%，反而比 CQ2-CARE 的 43.7% 略高；LLMLingua-2 按整行裁只差 3.0 个点，按 token 裁差 7.3。也就是说 **LongCodeZip 在主实验里输，是因为它从一个更差的文件集合起步**。

**三是「采样一致性」不是功臣，「少而准」才是。** 两次采样取交集把定位 F1 从 0.430 提到 0.613，看起来很亮眼；但把单次采样截到同样的文件数，F1 就到 0.600，修复率 42.7%，和 43.7% 几乎一样。取两次采样的并集多花 2.3K token，修复率到 47.7%（+4.0）。证据检索那一步贡献 3.0 个点，未达显著（p=0.068）。

**四是作者把自己踩过的坑写进了附录。** 研究开始前，他们的执行器只要测试命令退出码为 0 就算修好，不应用 issue 的测试补丁、也不核对 FAIL_TO_PASS 列表；抽查 6 个 issue，空 patch 在 4 个上被判为「修好」。改用官方判分后全部重做，并且事先确认每个 issue 金标 patch 能修、空 patch 修不了（340 个候选里 328 个合格）。另外，压缩后的文本还会诱导模型「照抄压缩痕迹」：Claude 在 LongLLMLingua 上下文上有 36 个回答无法解析，其中 31 个是 `...`、`<unified diff>` 这类占位符。

## 🤔 我的判断

**定位：工程对照研究，方法极简，价值在实验设计和失败拆解。**

亮点三条：

1. 预算逐题对齐、测试判分、配对 McNemar 加 Holm 校正，这套对照方法本身就是「怎么公平比上下文策略」的模板。
2. $\rho$ 和 $\varepsilon$ 两个量很好算，任何 harness 都能拿来给自己的上下文管道做体检：要改的文件在不在，给的是不是原文。
3. 「先选文件、真要裁就整行裁」是一条可以直接落地的规则，且不需要任何额外压缩模型。

问题与局限：单次出 patch 和真实多轮 agent 差距不小；只测 Python；小差距对采样噪声敏感；SweRank 只差不到两个点，不能说明两者相当或明显更差。

对工程的直接启发：在 Pi 或 Claude Code 这类 harness 里，**别把 LLMLingua 一类 token 级压缩器接在要编辑的代码上**；如果必须压，压对话历史、压检索结果的摘要，被编辑的文件保持整行原文。做上下文预取时，与其按相似度召回一堆片段，不如先让模型从路径清单里点名一两个「必须改的文件」整份给，再用 grep 补定义和调用方。评测侧，务必用官方测试判分，不要用退出码；顺便统计「patch 打不上」的比例，它往往是上下文被改坏的第一信号。

一句话收束：**coding agent 的上下文预算不该花在把更多代码挤进来，而该花在选对那几份、一个字都不改。**
