# coding agent 的账单里，一大块是重复劳动：从历史轨迹学会该塞什么、该砍什么

你有没有过这种体验：在同一个仓库里连着让 Claude Code 修了十个 issue，每一次它都要先跑一遍 `pytest`，发现环境里根本没装 pytest，再去翻怎么用项目自带的测试入口；每一轮请求都带着二十几个工具的 schema，其中十几个从来没被调用过；偶尔撞上一个修不动的 bug，它就在「改一行、跑测试、同样的报错」里转上四十轮。行业里讨论 token 成本，常见的办法是 **降推理强度、压缩输出、加仓库地图**。**可如果成本是在同一个环境里反复出现的，为什么不让 harness 从已经干完的活里学会省钱？**

UC Berkeley 和微软研究院这篇 **TokenEconomizer**（arXiv:2610.22732）把成本优化的单位从「单个任务」换成「同一环境里按时间顺序到来的一串任务」。它是一个套在 agent 外面的控制器，不改模型、不改 agent 循环，只通过三个已经暴露的旋钮干活：往指令前缀里塞几条一句话的「微技能」、把一直没用的工具从 schema 里拿掉、在 agent 陷入失败循环时先提醒一次再决定要不要掐掉。看完我的感受：这篇的方法论比数字更值钱，**每条经验都配了可执行的检测器和退役规则**，这正是大多数「自动沉淀 skill」系统缺的那一环。

## 核心摘要

作者先在 60 个 SWE-Bench 任务（6 个仓库各 10 个）上做成本剖析，发现三件事：一是固定策略没有一个能稳定省钱，RTK（压缩 shell 输出）、Serena（语义代码导航）、Aider RepoMap（仓库符号地图）都在某些仓库省、在另一些仓库更贵；二是轨迹里有三类可以去掉的成本，同仓库里至少一半任务都会出现的操作占工具调用字节的 12% 到 28%，23 个工具 schema 每轮都加载但没有一个仓库用超过 7 个，失败任务占 17% 却花掉 32% 的钱；三是「重复报错」本身不能当失败信号，50 个成功轨迹里也有 36 个出现过重复报错。于是 TokenEconomizer 设计了三个与环境无关的元策略，在每个环境里各自学出具体策略：**微技能注入**（LLM 从最近轨迹摘要里提候选，每条配正则或内置谓词写成的作用域、确认、矛盾、需要四类检测器，只有在 3 个编辑文件互不重叠的任务上被确认、且需要率不低于 0.4 时才注入，支持度带时间衰减、一次矛盾按 5 倍计，跌破零永久退役）；**工具裁剪**（核心的 shell、读、写、编辑永远保留，其余工具连续 3 个任务没被调用就屏蔽，或由 LLM 判定和当前任务无关就屏蔽，定期恢复全量做复审）；**失败循环干预**（按该仓库成功轨迹轮数的高分位数乘一个系数算轮数预算，规则先检测重复报错和预算超限，再由 LLM 判断是卡死还是在推进，卡死先重定向一次，再犯才终止，另有一个在 2.5 倍预算且同时满足编辑反复、报错密集、签名重复时 judge 也否决不了的强制停止）。在 Claude Code（Sonnet 5、Opus 4.8）、Codex（GPT-5.6 Terra、Sol）、Copilot CLI（Sonnet 5）五种组合、277 个 SWE-Bench 任务上，含控制器自身开销的平均单任务成本降 **18.4% 到 30.9%**，五个组合里四个 Pass@1 还略有上升；30 个「仓库乘设置」格子里**全部省钱**，而 RTK 单用有 12 格更贵、RepoMap 有 15 格更贵。价值定位：一套把「跨任务经验」变成「可验证、可退役的成本控制策略」的工程框架。

## 🎯 为什么这件事值得写

coding agent 的账单结构很简单：每一轮都要重新计费「系统提示加工具 schema」这段固定前缀，再加上一路累积的交互历史。缓存能打折，但打不掉。于是成本优化通常分三层：

| 层级 | 典型做法 | 问题 |
| --- | --- | --- |
| 模型层 | 降推理强度 | 省得多，但 Pass@1 掉 1.8 到 10.3 个点 |
| harness 层 | 手动配工具、加辅助说明 | 要人工配置，换仓库就失效 |
| 轨迹层 | 压缩、过滤观测、专用检索 | 常要改 agent 循环或训练额外组件 |
| **跨任务经验层（本文）** | 从已完成轨迹学环境专属策略 | 需要一串同环境的任务才能起效 |

真实的开发不是孤立任务，而是在一个不断演进的代码库里连续干活。作者的剖析数据很直观：当前任务之前已有至少 5 个同仓库任务时，30% 的工具调用都和之前某个任务里的动作匹配；换成另一个仓库的完整历史当对照，只有 7% 匹配，基本是通用的安装和测试命令。**重复是环境专属的**，所以经验也必须按环境学、按环境用。

## 🏗️ 机制：三个元策略，各自带回退路径

控制器在每个任务开始前做一次决策：

$$
(\Delta P_i,\ U_i,\ B_i) = C(\tau_i,\ S_{i-1})
$$

$\Delta P_i$ 是本次激活的微技能，渲染成一段短手册插在 harness 指令和任务描述之间；$U_i$ 是本次加载的工具集；$B_i$ 是失败循环守卫的轮数预算；$S_{i-1}$ 是之前所有任务累积下来的仓库状态。控制器也可以什么都不做，保持默认配置。

**元策略一：带检测器的微技能。** 第 4 个任务后开始，每 5 个任务调用一次提议器，读最近 8 个任务的操作摘要（不含解答和标准补丁），最多提 4 条候选，每条至少要引用窗口里 2 个能命中确认检测器的任务。每条候选是一句操作性说明加四个检测器：

| 检测器 | 回答的问题 | 例子 |
| --- | --- | --- |
| 作用域 scope | 这次轨迹有没有碰到这个情境 | 是否跑了测试 |
| 确认 confirm | 说明是否被验证为对 | 命令里出现 `sympy.test(` |
| 矛盾 contradict | 说明是否被证明是错的 | 出现 `ModuleNotFoundError` |
| 需要 need | 这次是否真用得上 | agent 是否做了说明里警告的多余重装 |

支持度按时间衰减累加：

$$
q_i(f) = \sum_{j<i} \gamma^{\,i-j}\Big(\mathbb{1}[\xi_j \text{ confirms } f] - \lambda\,\mathbb{1}[\xi_j \text{ contradicts } f]\Big),\quad \gamma<1,\ \lambda>1
$$

生命周期是「候选、确认、退役」：在 3 个编辑文件互不重叠的任务上被确认才升为确认态（防止一个 issue 里的局部规律被当成仓库规律）；确认态里需要率在至少 4 次触发中不低于 0.4 才真正注入；支持度跌破零就永久退役，被标为高风险的技能（比如测试命令、构建步骤）第一次被反驳就退役。不对称是故意的：**该退没退的技能每一轮都要重复计费，退早了的技能大不了换个编号重新提**。

**元策略二：工具裁剪。** shell、读、写、编辑永远保留。其他工具每被调用一次就重置「未使用计数」，计数到 3 就屏蔽；还没到 3 的从未调用过的工具交给 LLM judge 结合任务描述判断相关性（任务描述里的 PR、issue、commit、文件链接会被遮掉）。judge 调用失败就保留。定期恢复全量工具做复审，复审中被调用的工具从此不再屏蔽。

**元策略三：失败循环干预。** 预算按该仓库已成功任务的轮数高分位数乘系数 $\beta>1$ 计算，用分位数而不是最大值，防止一个特别长的成功把预算撑大。每次工具调用后先跑不调模型的规则检查：重复失败签名（报错首行去掉数字、地址、路径后归一化）、报错密集、超预算。规则触发后，LLM judge 读最近动作摘要判断是卡死还是在推进，最多每 5 轮问一次，每次判为「在推进」间隔再加 5 轮，上限 20。卡死先由 LLM 写一段「你最近做了什么」的总结，要求换一个实质不同的假设；再犯且仍判卡死才终止。

## 🧪 关键证据

**SWE-Bench 主结果（三个种子，成本为相对高推理强度默认执行的变化，含控制器开销）。**

| 设置 | 默认 Pass@1 | TE 成本变化 | TE Pass@1 | 降到中等强度的 Pass@1 |
| --- | --- | --- | --- | --- |
| Claude Code，Sonnet 5 | 74.7 | **-23.6%** | 76.0 | 70.0 |
| Claude Code，Opus 4.8 | 74.0 | **-30.9%** | 73.0 | 72.2 |
| Codex，GPT-5.6 Terra | 73.8 | **-24.7%** | 74.7 | 69.6 |
| Codex，GPT-5.6 Sol | 80.1 | **-26.1%** | 81.7 | 76.7 |
| Copilot CLI，Sonnet 5 | 75.0 | **-18.4%** | 77.6 | 72.6 |

降到中等推理强度能省 17% 到 29%，但 Pass@1 掉 1.8 到 4.7 个点；TokenEconomizer 在相近的省钱幅度下基本不掉分。叠加 RTK 后 Claude Code 加 Opus 4.8 能省到 33.2%。

**消融（Claude Code）。** 工具裁剪单项贡献最大（Sonnet 5 上 -13.2%、Opus 4.8 上 -17.7%），因为它作用在每个任务的每一轮；微技能紧随其后（-11.8%、-14.3%）；失败守卫是个位数（-7.1%、-5.4%）。没有任何单项能达到组合效果，也没有任何单项让 Pass@1 偏离默认超过 3 个点。

**冷启动。** 每个仓库开头没有历史轨迹，除 xarray 外其余仓库前几个任务都比默认更贵，到第 6 个任务全部转为更便宜，累计省 16.9% 到 32.0%。

**泛化。** Web-Bench（102 个连续 web 开发任务）省 16.0% 到 21.2%；两个安全审计基准每个任务换一个仓库，所以关掉了微技能，只剩两个元策略，CredData 省 16.5% 到 19.6%，ReposVul 只省 6.4% 到 9.3%，因为轨迹本身短。

**泼冷水。** SWE-Bench 的「任务流」是同一仓库里按时间排序的独立修复，相邻任务中位相隔几天，不是真实用户的连续会话；成功信号直接用了基准的官方评分，真实场景里拿不到这么干净的标签，失败守卫的预算估计会变粗；没有测 Pi 这类极简 harness，作者说只需要写适配器，但没有数字。

## 🔬 最有意思的部分

**一是检测器能救回错误的经验，前提是检测器写得对。** 附录里有个很诚实的反例：SymPy 流里提议器提了一条「用 `python -m pytest` 跑测试」的高风险技能，可这个环境根本没装 pytest，所有 57 条调用 pytest 的轨迹都失败了。它居然被激活了，原因是确认检测器匹配的是「命令里出现了 pytest」而不是「测试跑通了」，于是 agent 之前的失败尝试全被算成了确认。好在第一个收到这条技能的任务里，agent 试完命令又去探测模块，`ModuleNotFoundError` 命中了矛盾检测器，按 5 倍权重一次就把支持度打到负数，只注入一次就退役了。另一条流里学到的则是正确的原生测试入口 `sympy.test(...)`，激活后在 10 次触发里 10 次确认、零矛盾。**教训：经验的确认条件必须挂在结果上，而不是挂在动作上。**

**二是「对但没用」的技能也不该注入。** 同一条 SymPy 流里有一条技能说「包从源码树导入，改完不用重装」，10 次确认、零矛盾，完全正确，但 agent 从来没尝试过重装，需要率一直是 0，于是永远不注入。正确的知识如果不能阻止任何浪费，塞进前缀只会每轮多收一次钱。这条「需要率门控」是我觉得最该抄的设计。

**三是重复报错不等于失败。** 剖析数据显示 51% 的花费发生在轨迹第一次出现重复失败签名之后，但这部分花费里一半以上落在最终成功的轨迹里。所以守卫用了三层：便宜的规则先开门，LLM judge 区分卡死和难题，强制停止要同时满足预算、编辑反复、报错密集、签名重复四个条件。**先重定向、后终止**，比简单的轮数上限温和得多，也和我们之前看 LEASH 里「先识别失败苗头再决定是否接管」的思路相通。

## 🤔 我的判断

**定位：harness 层的工程框架，测量和设计都扎实，方法本身不难但组合得很克制。**

亮点三条：

1. 经验条目「一句说明加四类可执行检测器」的格式，把 skill 从自然语言笔记变成了可以被轨迹自动确认、反驳、退役的对象，这是给自演化 skill 系统补上的一块闭环。
2. 成本核算严格：控制器自己的每一次 LLM 调用都记到触发它的任务头上，而且报了 30 个格子里每一格的方向，不只报平均数，这让「全部省钱」的结论可信。
3. 三条元策略都配了回退路径：错技能会被反驳退役，误砍的工具在复审时回来，误判的难题先被提醒而不是直接掐掉。

问题与局限：确认检测器的质量完全取决于提议器写的正则，上面的 pytest 反例说明这一步很容易写错；微技能需要至少几个同环境任务才能起效，单次使用或经常换仓库的人拿不到这部分收益；成功信号依赖评分器，现实中需要用测试结果或人工反馈替代；γ、β 这类超参是全局固定的，跨团队迁移时可能要重新调。

对工程的直接启发：在 Pi 或 MMP 这种显式清单式 harness 里，可以把 TokenEconomizer 的三件事直接做成扩展。第一，Skills 清单里的每条仓库级 skill 加上 `scope`、`confirm`、`contradict`、`need` 四个正则字段，每次会话结束后离线跑一遍，把需要率低于阈值的条目从注入列表里拿掉，被反驳的标记退役。第二，MCP 和扩展工具按「连续 N 个会话没被调用」自动移出 Manifest，定期全量复审一次。第三，失败守卫用归一化后的报错首行做签名，配合本仓库成功会话的轮数分位数做预算，触发时先注入一段「换个假设」的总结，而不是直接停。

一句话收束：**省钱的关键不是让 agent 少想，而是别让它在同一个仓库里第十次重新发现同一件事。**
