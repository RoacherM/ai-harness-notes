# 钱最后到账了也算违规：支付 agent 的考卷要查过程，不只查结果

你有没有过这种体验：让 agent 跑一个长流程，最后结果对上了，日志一翻却发现中间它先斩后奏执行了一笔没批准的操作，或者某一步把账户余额打穿了，后面又补了回来。按现在大多数 agent 基准的打分方式，这一单算成功。行业里把这种评测叫 **outcome-only evaluation**（只看终态）。**在支付这种高风险业务里，中间违规本身就是事故，那考卷到底该怎么出、怎么判？**

蚂蚁国际和北大这篇 **BizBench**（arXiv:2610.20424，v2 改名 BizAgentBench）就是冲着这个缺口来的。它从一家头部支付公司的真实业务流程里抽出 SOP，重建成一个可执行环境：789 份知识文档、601 个要靠自己发现的业务工具、一个 LLM 扮演的客户，再用确定性检查同时判「目标达没达成」「过程合不合规」「受保护对象有没有被碰」。看完我的感受：这是我近期看到 **把「过程合规」做成可执行检查最彻底** 的一个业务 agent 基准，而且它顺手给出了一组很扎心的数：工具调用多不等于在推进，前沿模型重复跑三次全对的任务也只有四成。

## 核心摘要

BizBench 把每个任务的成功定义为三个确定性检查的合取：目标检查 $G$（请求的结果和允许的终态）、过程检查 $P$（授权必须覆盖实际执行条款且先于执行，余额下限这类约束在每次状态变化时都要满足）、保护检查 $F$（受保护对象和禁止的副作用）。检查跑在业务状态、账本、回执和事件历史上，能区分「真执行了」和「只是提议、被批准、被拒绝」，不和 Golden 轨迹逐步比对，也 **不用 LLM 裁判**。50 个任务都有一条能回放通过的 Golden 轨迹，平均 111.8 次 agent 工具调用；评测器还用「另一种合法走法」「定向违规轨迹」「改掉关键事实」三类反例验过，确认它接受合法解、拒绝违规解。主结果：Claude Opus 5 严格成功率 **64.0%**，GPT-6 Sol **61.3%**；Qwen3.8-27B 目标达成 42.0%，严格成功只有 **32.7%**，差值就是只看终态会漏掉的违规。GPT-6 Sol 三次全成功的任务只有 **40.0%**。DeepSeek-V4.1-Flash 平均每次 191.3 次工具调用，是 Golden 的 1.71 倍，多出来的几乎全是查库和读文档；把工具调用卡在 Golden 的 2 倍，它的严格成功率从 43.3% 掉到 26.7%。信息消融里，直接给对文档只把成功率从 43.3% 提到 50.0%，而把客户信息一次性全给到能提到 70.0%：**问清客户约束并在后面一直记住，比找文档更难**。价值定位：一套业务 agent 的过程合规测量基础设施，加一份「长轨迹到底在干什么」的诊断。

## 🎯 为什么这件事值得写

现有长程 agent 基准大致两类：SWE-bench、Terminal-Bench 这类看终态，τ-bench 家族、CRMArena、TheAgentCompany 这类引入了业务规则和组织语境，AutomationBench 也只看最终应用状态、不规定调用顺序。BizBench 保留了「允许不同走法」的灵活性，但在关键步骤上加了过程检查，比如转账之前有没有拿到针对这笔转账的批准。

作者从自家业务里总结了三条「真实业务才有」的难点，正好是终态评测测不到的：

| 难点 | 例子 | 终态评测为什么漏掉 |
| --- | --- | --- |
| 过期和冲突的指引 | 旧版规则还能被检索到；两条看似冲突的规则其实管不同产品、地区或生效期 | 只要结果碰巧对，就看不出它用错了规则 |
| 授权和执行有效性 | 账户有 60 美元，必须一直留 20 美元；付掉 60 美元的定金后归零，后面退款补回也修复不了那一刻的违规 | 收尾余额达标，中间违规被掩盖 |
| 延迟信息和时间敏感决策 | 等仓库确认再订优先配送，窗口已经关了，第一个交付期限就赶不上 | 需要建模「什么时候能看到什么」 |

论文里一句话很到位：**一笔未授权支付，即使钱后来退回来了，仍然是一次合规违规。**

## 🏗️ 机制：任务怎么造、怎么判

**环境。** agent 有 9 个常驻工具，通过它们去发现和调用 601 个业务能力；用户模拟器有 10 个工具，能上传材料、批准请求。知识库 789 份文档，正文约 59.9 万 token；数据库 398 个可查集合，2,994 条记录。每次运行用一份独立的数据库副本。为了保密，敏感业务细节都改写过，但保留了决策逻辑和依赖关系。

**五步构造。**

1. 把业务文档整理成结构化 SOP：步骤、决策、跳转、返回路径，每条规则记录适用范围、前置条件、动作、例外，冲突解决不了的内容直接剔除；
2. 选共享资源、或者一个流程的输出是另一个流程前置条件的工作流，用共享资金、授权额度和时间约束连起来，**一个允许的动作可能吃掉另一项义务需要的资源**；
3. 配一个 LLM 用户模拟器：客户的私有事实只在被问到时才透露，批准绑定在具体请求和当前条款上，条款一变就要重新批准；
4. 写 Golden 轨迹并从初始状态完整回放，确认目标和约束可以同时满足；
5. 用合法替代路线、定向违规和改事实三类反例验证评测器，再由五名研究员和业务专家团队复核，只保留两关都过的任务。

**判定。** 设执行历史为 $\tau=(s_0,e_1,s_1,\dots,e_T,s_T)$，任务 $i$ 成功当且仅当

$$
\text{Success}_i(\tau)=G_i(\tau)\wedge P_i(\tau)\wedge F_i(\tau)
$$

另报一个中间失败率 $\text{IF}=\neg(P\wedge F)$。一个细节值得抄：评测器要求「工具合同允许的幂等重试不产生额外业务效果」，也就是说，重复提交不会被误判成多执行了一次。

**运行设置。** 不限总 token、总工具调用和调度步数，只保留墙钟超时和工具错误阈值；上下文溢出时把最早四分之一的检索和读文档返回替换掉，完整执行记录另存。默认用户模拟器是 DeepSeek-V4.1-Flash。

## 🧪 关键证据

**主结果（%）。** Claude Opus 5 和 Muse Spark 1.3 每题一次，其余每题三次取平均。

| 模型 | 目标 G | 过程 P | 保护 F | 中间失败 IF | 严格成功 |
| --- | --- | --- | --- | --- | --- |
| Claude Opus 5 | 64.0 | 96.0 | 98.0 | 4.0 | **64.0** |
| GPT-6 Sol | 64.7 | 94.7 | 100.0 | 5.3 | **61.3** |
| GLM-5.3-Flash | 48.0 | 79.3 | 87.3 | 29.3 | 43.3 |
| DeepSeek-V4.1-Flash | 46.7 | 92.0 | 96.7 | 9.3 | 43.3 |
| DeepSeek-V4-Pro | 41.3 | 85.3 | 88.7 | 24.7 | 39.3 |
| Qwen3.8-27B | 42.0 | 74.0 | 93.3 | 28.0 | 32.7 |
| Qwen3.5-9B | 0.0 | 18.7 | 89.3 | 83.3 | 0.0 |

每个模型的过程通过率都低于保护通过率（18.7% 到 96.0%，对比 87.3% 到 100.0%），说明 **最容易出事的不是乱碰东西，而是顺序和授权**。

**可靠性。** 三次全成功（pass^3）：GPT-6 Sol 40.0%，DeepSeek-V4.1-Flash 26.0%，GLM-5.3-Flash 22.0%，Qwen3.8-27B 10.0%，DeepSeek-V4-Flash 和两个 Qwen3.5 都是 0。

**信息消融（DeepSeek-V4.1-Flash 严格成功）。** 默认 43.3%，直接给对文档 50.0%，开场就把客户知道的全部信息交出来 70.0%（批准仍然要走）。即使信息全给，仍有 30% 的任务做不出来，剩下的是规划和合规执行本身的难度。

**泼冷水。** 第一，只有 50 个任务，两个最强模型之一 Claude Opus 5 只跑了一次，排名差距不大的地方别太当真。第二，环境是基于真实流程重建的，记录是合成的，敏感细节改写过，「真实业务」的含金量取决于改写的保真度，外部没法核验。第三，评测器是确定性的，但客户是 LLM 扮演的；作者测了原始提示下 50 题有 4 题模拟器违反轮转协议，改版提示后为 0（配对 McNemar p=0.125），换模拟器模型后 Qwen3.8-27B 的成功率在 30.7% 到 36.0% 之间浮动。第四，所有模型跑在同一个 runner 下，论文比较的是模型，不是 harness 设计，工具调用上限那张表也是事后截断统计，不是真的带预算重跑。

## 🔬 最有意思的部分

**一是「终态对了但过程错了」被逐条抓出来。** DeepSeek-V4.1-Flash 有 5 次达成目标却没过完整标准：4 次中途跌破现金储备下限后又补回，1 次在批准之前就尝试执行被拒。Qwen3.8-27B 有 14 次，其中 8 次是批准前执行。Qwen3.5-9B 150 次里 122 次过程不合格，其中 88 次是批准前执行，而且一个目标都没达成。附录 Q13 的例子很典型：agent 在客户批准前调用 `execute_request`，工具返回 `CUSTOMER_APPROVAL_REQUIRED`，钱一分没动，客户随后批准、目标全部完成，判定仍是 $G=1, P=0, F=1$。**「银行拦住了」不等于「agent 守规矩」**，这个判法对任何会动真实系统的 agent 都应该照搬。

**二是长轨迹里多出来的全是「找」而不是「做」。** DeepSeek-V4.1-Flash 平均 191.3 次调用，Golden 是 111.8 次；查库 111.1 次对 59.2 次，检索和读文档 43.3 次对 11.5 次，而真正的业务调用和执行请求几乎一样（26.9 对 28.7）。每次运行还有 16.4 次「工具名、参数、返回都一模一样」的重复查库。GLM-5.3-Flash 用 118.3 次调用、读 9.4 份文档，就拿到了和 DeepSeek-V4.1-Flash（191.3 次、20.1 份）一样的 43.3%；Qwen3.5-397B-A17B 用了 216.4 次，150 次里只成功 1 次。**工具调用数不能当进度指标。**

**三是预算一收紧，成功率断崖。** 按 Golden 调用数的倍数事后截断：1.2 倍只剩 0.7%（150 次里 1 次），1.5 倍 6.7%，2 倍 26.7%，不限 43.3%。连两倍参考预算都会砍掉很多本来能成功的运行，这正好量化了「信息搜寻和反复确认」的代价。

**四是相似术语会把检索带偏。** Golden 平均每题只读 5.4 份不同文档，模型读 20.1 份。附录 Q01 里，搜「税款支付匹配期间对账」，排第一的是另一个产品的多缴抵扣文档，第五是那个产品的税务代理文档，agent 两份都打开了，但哪份都不管这个任务。

## 🤔 我的判断

**定位：测量基础设施，业务 agent 的「过程合规」评测样本，方法不新但落地很完整。**

亮点三条：

1. $G\wedge P\wedge F$ 三段式加「连续约束在每次状态变化时检查」，把「中途违规」从口头要求变成了可执行断言，而且全程不用 LLM 裁判，这正是「代码检查优先于 LLM judge」的范例。
2. 评测器本身也被测：合法替代路线必须通过、定向违规必须失败、改关键事实后判定要跟着变、幂等重试不能多算一次。很多团队做 golden set 只验「对的能过」，没验「错的会挂」。
3. 把「多少调用花在找信息上」「多少是完全重复的读」「预算收紧到几倍还能活」拆成独立指标，比单报成功率更能指导 harness 优化。

问题与局限：任务量小、部分模型单次运行；环境是重建版，真实性靠作者背书；用户模拟器是 LLM，虽然做了稳健性检查，仍是一处不确定源；只比模型不比脚手架，没回答「什么样的 harness 能把过程违规压下来」。

对工程的直接启发：给自己的 agent 评测加一列「过程检查」，至少覆盖两类断言：**批准必须先于执行且条款一致**（被工具拦下的尝试也算违规），**不变量在每次状态变化后都要成立**（不是只查收尾）。在 harness 侧，可以把「识别到写操作就先确认批准记录」做成一个 hook，并把完全重复的工具调用（同名同参同返回）单独计数当作效率告警；上线前用「Golden 调用数的 1.5 到 2 倍」做一次事后截断，看看你的 agent 在真实预算下还剩多少成功率。

一句话收束：**终态评测问的是「事办成了吗」，业务部署要问的是「每一步都有资格这么办吗」，BizBench 把后一个问题写成了代码。**
