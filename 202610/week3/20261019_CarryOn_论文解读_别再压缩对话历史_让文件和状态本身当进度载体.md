# 别再压缩对话历史：让文件和状态本身当进度载体

你有没有过这种体验：agent 跑到第两百步，上下文已经二十万 token，里面一大半是「我打开了 PPT，点了插入，选了图片，调了透明度」这种过程记录；可那份 PPT 就躺在桌面上，打开就能看到做到了哪一步。于是你加了压缩，摘要一写，下一步 agent 又开始重做已经做完的事，或者忘了「透明度要保持 40%」这条约束。行业里管这叫 **context compaction**（上下文压缩），主流做法是摘要、检索、裁剪历史。**可进度已经写在任务对象里了，为什么还要反复去读「它是怎么来的」？**

UCSD 这篇 **Pack Light, CarryOn**（arXiv:2610.18784）换了个组织单位：上下文不再围着历史转，而是围着**可复用的任务对象**转。文件、查到的结论、某个应用里的状态，各自变成带身份、带复用条件、带版本的「延续载体」；没被对象承载的目标、约束、悬而未决的问题放进「执行上下文」；最近几步原样保留成「活尾巴」。看完我的感受：它和 [LongHarness](../week2/20261014_LongHarness_论文解读_证据和结论别埋在对话历史里_共进化状态才把一亿token语料问对.md)、[MutableTranscripts](../../202609/week4/20260928_MutableTranscripts_论文解读_对话别只追加纠错_把历史改成可编辑状态剪掉上下文污染.md) 都在说「历史不该是唯一真相」，但 CarryOn 更进一步：**真相在环境里，上下文只需要记下去哪找、在什么条件下还能用**，而且每次折叠都要先过一遍只读的环境检查。

## 核心摘要

CarryOn 是一个和 agent 并行运行的上下文运行时，上下文视图写成 $V_t = (A_k, E_k, L_t)$：$A_k$ 是延续载体集合，分三种（外部对象如代码、文档、表格；信息产物如综合出的结论，直接存成带来源的断言；情境状态如某个应用会话里的进度，记录环境锚点和适用范围）；$E_k$ 是执行上下文，记当前焦点、开放义务、有效约束和下一步指令；$L_t$ 是上次折叠之后的原始交互。每次折叠分四步：Tracker 读最近交互维护候选登记表并决定哪些候选可以编译；运行时为每个请求绑定证据，Grounder 对文件做只读检查（是否存在、是否相对初始快照变化、是否为空、docx/pptx/xlsx 容器是否有效、文本单元差异、是否出现任务指令原文）；Compiler 同时产出载体增改和新的执行上下文；运行时校验身份、引用、版本是否仍为当前、证据是否被授权，且**至少要有一个载体变化**，通过后原子提交并把整条活尾巴折掉，交互日志本身只追加不删。全程用 Claude Opus 4.7 当 agent、Tracker、Compiler，不做训练。结果：OSWorld 2.0 部分分 **43.9% 到 49.7%**、二元分 15.7% 到 19.4%，总 token 降 **51.9%**、单任务成本 36.83 美元降到 23.62 美元（降 35.9%，含运行时开销）；BrowseComp-Plus 100 题子集准确率 **49% 到 56%**，token 降 22.9%。价值定位：把长程 agent 的上下文管理从「怎么压缩历史」改成「怎么维护一组可验证的进度对象」，而且给出了可直接借鉴的数据结构。

## 🎯 为什么这件事值得写

长程 agent 的进度存在两个地方：**任务状态**（做出来的东西）和**交互历史**（怎么做出来的）。图片插进了幻灯片、测量值填进了报告，任务状态已经完整记下了进度，后面的步骤可以直接检查和修改。可大多数 harness 仍把历史当续跑的主要依据，压缩只是让这份「二手记录」变短；摘要一旦和真实文件对不上，agent 就会基于一份漂移的叙述继续干活。

| 路线 | 续跑依据 | 典型问题 |
| --- | --- | --- |
| 滑动窗口 | 最近 N 条消息 | 早期约束直接丢 |
| 通用摘要 | 一段续跑笔记 | 摘要会漂，与实际文件不一致 |
| 外部化状态或进度记录 | 另写一份结构化状态 | 又多一份需要同步的副本 |
| **对象化上下文（CarryOn）** | 环境中的对象加复用条件，外加执行上下文 | 依赖 Tracker 判断和环境检查覆盖面 |

## 🏗️ 机制：载体、执行上下文、活尾巴

**载体记录长什么样。** 每个已提交载体有：身份、类型、可复用内容或对象引用、继续使用的条件、适用范围、来源、版本。外部对象的身份来自规范化路径；信息产物的身份是表示类型加结构化主题，内容存成带编号的断言，修订时可以增、改、撤回单条断言，其余原样保留；情境状态的身份是状态域加环境锚点。更新会生成指向旧版的后继版本，旧版保留用于追溯。

**一次折叠的四步。**

1. **跟踪候选**：Tracker 读最近交互和候选登记表，候选可以跨多次调用慢慢成熟，登记或修改候选本身不触发折叠。
2. **准备证据**：为每个可编译请求绑定候选快照、相关旧载体、被授权的来源；对象类请求由 Grounder 做只读检查，每项检查在执行前就绑定好候选身份、对象引用、谓词和期望值。判定规则很严：所有条件都支持才算支持，任何一条矛盾就算矛盾，其余为未知；矛盾或未知的候选不编译。
3. **联合编译**：Compiler 只对被选中的候选改载体，但执行上下文要对照整条活尾巴重写，确保没被载体覆盖的目标和约束不丢；已被载体表达的内容从执行上下文删掉，避免重复。
4. **校验提交**：检查版本是否仍为当前、证据是否授权、输出约束是否满足、是否至少有一个载体变化；通过就原子提交，否则一切不变。作者强调这些检查**保证运行时一致性，不保证任务正确**。

**触发时机。** OSWorld 2.0 上自上次扫描或折叠以来新增交互文本超过约 6,000 token 就调 Tracker；BrowseComp-Plus 上首次触发要求 prompt 增长 120,000 token，连续扫描都没折叠就把阈值翻倍，最多翻六次，成功折叠后重置。

## 🧪 关键证据

**主结果（OSWorld 2.0 全量，500 步预算）。**

| 配置 | 二元分 | 部分分 | 单任务成本（美元） |
| --- | --- | --- | --- |
| Claude Opus 4.7（max），复现 | 15.7 | 43.9 | 36.8 |
| Claude Opus 4.7（max）加 CarryOn | 19.4 | 49.7 | 23.6 |
| Claude Opus 4.8（max），官方报告 | 18.5 | 49.3 | 76.1 |
| GPT-5.5（xhigh），官方报告 | 13.0 | 49.5 | 25.5 |

**成本曲线。** 基线上下文随轨迹一路涨过 200K token，CarryOn 稳定在约 65K；前期因为多了管理调用更贵，累计成本在两百轮之前交叉（文中图注写约 150 轮），到第 500 轮累计成本低 34.1%。运行时自身 token 只有 0.69M（基线总量 40.10M），但运行时成本 3.11 美元不算小。

**和其他压缩策略比（OSWorld 2.0 共享 40 题子集）。**

| 方法 | 折叠后文本（千字符） | 二元分 | 部分分 |
| --- | --- | --- | --- |
| 不压缩基线 | 无 | 22.50 | 50.32 |
| 滑动窗口 | 12.08 | 15.00 | 37.41 |
| 通用摘要 | 17.60 | 15.00 | 44.94 |
| 按 CarryOn 原则写摘要 | 23.94 | 20.00 | 50.93 |
| CarryOn | 21.54 | 22.50 | 55.93 |

泼冷水：BrowseComp-Plus 只是随机 100 题，7 个点的提升对应 7 道题；40 题子集上二元分 CarryOn 只是**追平**基线；OSWorld 的对照模型数字一部分来自官方报告，不是同一套复现。

## 🔬 最有意思的部分

**一是「压缩本身不会让你变强」被数字坐实了。** 滑动窗口和通用摘要上下文最短，分数却都低于不压缩的基线，部分分分别掉了 13 和 5 个点。只把组织原则写进摘要（CGS）就能把损失大部分补回来，说明**关键不在压多少，而在保留的是什么**。

**二是两个组件各管一半。** 把执行上下文对 agent 隐藏，部分分从 55.93% 掉到 44.00%，调用次数几乎不变，意思是 agent 知道做了什么，却不知道还差什么。把载体隐藏，部分分掉到 44.62%，调用次数多 23.8%、成本多 22.3%，意思是 agent 只能重新摸索已完成的进度。

**三是载体是「维护」出来的，不是每次重建。** 每次折叠前后对比，80% 的载体记录被保留或更新，只有 20% 是新加的。CGS 每次重写一整份摘要，保留的文字更多，部分分却低 5 个点。作者给的解释是显式维护的记录让 agent 更容易接着已有进度干，这和 coding agent 里「让 git 状态说话，而不是让聊天记录说话」的经验是一回事。

## 🤔 我的判断

**定位：harness 层的上下文运行时设计，工程样本价值很高。**

亮点三条：

1. 把三类载体（外部对象、信息产物、情境状态）分开，正好对应 coding agent 的工作区文件、调研结论、终端或浏览器会话，抽象可以直接迁移。
2. Grounder 的「支持、矛盾、未知」三值判定加上「检查执行前就绑定谓词和期望值」，是把环境检查当证据而不是当装饰，思路和代码检查优先于 LLM judge 一致。
3. 折叠必须带至少一个载体变化，单改执行上下文不准折历史，这条小规则防住了「摘要越写越空」的退化。

问题与局限：OSWorld 上的环境检查只有文件存在、哈希变化、大小、容器有效、文本差异、指令原文匹配几种，很浅，没法验证「透明度确实是 40%」这类语义条件，所以载体的「可复用」很大程度仍靠 Tracker 的判断；Tracker 和 Compiler 都用 Opus 4.7，换成便宜模型是否还成立没测；BrowseComp-Plus 样本量小；每次成功折叠都折掉整条活尾巴，部分折叠没探索。

对工程的直接启发：在 Claude Code 或 Pi 一类 harness 里做压缩时，可以先不急着写更好的摘要提示词，而是维护一张「工作区对象表」：每个改过的文件记路径、当前完成了什么、继续使用的前提，压缩时用 `git diff` 和文件哈希做只读校验；另外单独维护一份「还没做完、必须遵守」的清单，压缩后两者一起注入，原始对话照样落盘留查。

一句话收束：**长程 agent 要轻装上路，该带的不是更短的回忆录，而是一张指向真实进度的清单。**
