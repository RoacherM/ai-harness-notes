# 别等问题来了再检索：先让 agent 把语料整理成下一个 agent 好找的文件夹

你有没有过这种体验：同一批文档，今天问一个问题，agent 从头搜一遍、读十几个文件、拼出答案；明天换个问法，它又从头搜一遍，昨天辛辛苦苦摸清的「这三份文档讲的是同一个发布」「这个人名在另一份里换了写法」，一点都没留下。行业里的标准答案是 **RAG**（检索增强生成），进阶一点是 **GraphRAG** 这种先建知识图谱。**可 Claude Code 这类 agent 最擅长的明明是在文件系统里 `ls`、`cat`、顺着目录往下找，为什么没人训练它们先把文件系统整理好，留给下一个 agent 用？**

Stanford 和 CMU 这篇 **Librarian Agents**（arXiv:2610.22273，Chelsea Finn 和 Aviral Kumar 组）抓住的正是这个不对称：agent 很会**用**现成的文件系统，却几乎没被训练过**造**一个可复用的工作区。它让一个「图书管理员」agent 在问题到来之前，把原始文档改造成带层级、带来源链接的合成文件夹，再让一个冻结的回答 agent 只靠列目录和读文件去答题，用 RL 直接按回答准确率优化建库策略。看完我的感受：这是「**记忆就是文件系统**」这条路上第一个把建库当成可训练策略的工作，一个 4B 的小模型被训出了明显不同的整理习惯；但评测还停留在静态语料问答，离 coding agent 的真实工作区还差「语料会变」这一步。

## 核心摘要

Librarian Agents 把工作区构建写成有限步 MDP：状态是当前文件系统（原始文档加已创建的合成文件、目录和引用链接），动作只有四种，CreateFile（从若干原始文档或合成文件整合出一个新文件，附来源链接）、MergeFiles（把相关合成文件聚成更高层的摘要或目录，引入层级）、Delete（删掉冗余合成文件，**永远不删原始文档**）、Stop。回答 agent 只能列目录、读文件。奖励是建完之后回答 agent 在一批建库时看不到的训练问题上的准确率；为了缓解长序列的信用分配，每 8 轮建库做一次「可回答性探针」，用相邻两次探针的准确率差当中间奖励，再加终局奖励，按势函数奖励塑形的道理，这和只给终局分在目标上等价。主实验里建库 agent 是 Qwen3.5-4B，用 GRPO 加 LoRA（秩 32）在 BrowseComp-Plus 的 680 个任务上训练，最多 32 轮建库，具体写文件由固定的 Qwen3.5-35B-A3B 执行。结果：在 50 个留出任务上，冻结的 Qwen3.5-4B 回答 agent 准确率 **0.75**（嵌入检索 0.42、重排 0.44），换 Gemini 3.1 Flash Lite 回答是 **0.77**（GraphRAG 0.36，不训练的同款建库 agent 0.28）；零样本迁移到 BRIGHT 三个子集，平均 pass@1 **52.0%**，最好的基线约 20.8%。建库一次约 17.9 万 token，按准确率归一化后每个正确答案少用 **33.8%** 的 token（每份语料 10 个问题时）。价值定位：把「上下文工程」里最费人工的那一步，整理工作区，变成了一个可以按下游效果训练的策略。

## 🎯 为什么这件事值得写

长语料问答的两条主流路线，各自卡在一个地方：

| 路线 | 什么时候花算力 | 卡点 |
| --- | --- | --- |
| 被动检索（RAG、Agentic RAG） | 每次提问 | 跨文档关系每次都要重新发现 |
| 预计算结构（知识图谱、GraphRAG） | 一次性前置 | 抽象是写死的（实体、关系），问题不对口就没用 |
| 自动压缩（周期性总结） | 运行中 | 细节被摘要吃掉，很难回溯 |
| **预判式工作区（本文）** | 一次性前置，可复用 | 需要训练，且目前只在静态语料上验证 |

作者给了三条好工作区的标准，我觉得可以直接当设计清单用：**覆盖加好走**（合成文件要覆盖大部分可能的问题，并且放在浅层、目录名能看懂）、**可靠回退**（任何合成文件都保留指向原文的链接，摘要漏掉的细节能顺藤摸瓜找回来）、**摊销复用**（建库成本要能被很多次查询分摊，一次性的答案草稿不值得写）。

这和我们之前读过的 CarryOn、LongHarness 是同一个大方向：**真相留在可寻址的对象里，上下文只负责指路**。区别是那两篇在运行时维护，这篇在问题到来之前就把路修好。

## 🏗️ 机制：一个建库 agent、一个回答 agent、一套探针奖励

**下游效用。** 先定义一个文件系统的期望回答成功率：

$$
S(\mathcal{F}) = \mathbb{E}_{q\sim\mathcal{Q}}\ \mathbb{E}_{\tilde y\sim\pi_{\text{ans}}(\cdot\mid q,\mathcal{F})}\big[\text{Acc}(\tilde y, y^*(q))\big]
$$

再扣掉合成文件的 token 成本和读文件次数（只对答对的回合扣，答错直接零分）：

$$
U(\mathcal{F}) = S(\mathcal{F}) - \lambda_{\text{tok}} C_{\text{tok}}(\mathcal{F}) - \lambda_{\text{read}} C_{\text{read}}(\mathcal{F})
$$

**稀疏与稠密奖励。** 终局奖励是 $U(\mathcal{F}_H) - \alpha\sum_t \text{Cost}_{\text{build}}(\mathcal{A}_t)$；理想的稠密奖励把每一步的边际贡献记给这一步：

$$
r_t^{\text{dense}} = U(\mathcal{F}_t) - U(\mathcal{F}_{t-1}) - \alpha\,\text{Cost}_{\text{build}}(\mathcal{A}_t)
$$

无折扣时稠密奖励求和正好等于稀疏奖励减去一个常数，所以优化目标不变，只是信用分配更细。实际训练里每步都评一遍太贵，于是每 8 轮做一次探针，一条建库轨迹最多 4 次探针。主实验把 $\lambda_{\text{tok}}$、$\lambda_{\text{read}}$、$\alpha$ 都设成 0，只按准确率优化，也没有任何「目录结构好看」的奖励。

**防泄漏。** 用来算奖励的问题对建库 agent 不可见；评测问题从不参与建库，也不参与挑选检查点。

**分工。** 建库 agent（4B）只决定「做什么操作、作用在哪些文件上」，每次生成限 1,024 token、整条轨迹限 6 万 token；真正写合成文件内容的是固定的 35B MoE 执行器；过长的建库历史由 Gemini 3.1 Flash Lite 压缩。这个「小模型做决策、大模型做苦力」的拆法很实用。

## 🧪 关键证据

**BrowseComp-Plus（50 个留出任务）。**

| 方法 | Qwen3.5-4B 回答 | Gemini 3.1 Flash Lite 回答 |
| --- | --- | --- |
| 嵌入检索 | 0.42 | 0.30 |
| 嵌入加重排 | 0.44 | 0.42 |
| **Librarian Agents** | **0.75** | **0.77** |

**建库成本（Gemini 回答）。**

| 方法 | 准确率 | 建库 token |
| --- | --- | --- |
| GraphRAG | 0.36 | 11,923 |
| 自动压缩 | 0.04 | 501,637 |
| 不训练的建库 agent | 0.28 | 127,683 |
| **Librarian Agents** | **0.77** | 178,926 |

**复用场景。** 作者把数据集扩展成每份语料对应多个问题：50 份语料、443 个合成问题，每份 7 到 10 个。训练后的建库 agent 让准确率从 0.24 提到 0.64，但回答 agent 每题读的文件从 2.7 个涨到 26.9 个、token 从 1,238 涨到 9,346，原因是工作区更丰富了。按「每个正确答案的 token」算才更省，每份语料 10 个问题时省 33.8%（95% 置信区间对应比值 0.504 到 0.836）。

**BRIGHT 零样本迁移（每子集 50 题，一个子集一套文件系统）。** AOPS 36.0%、Biology 34.5%、Stack Overflow 85.5%，平均 pass@1 52.0%、pass@3 66.8%。附录里另外九个 BRIGHT 子域每个 20 题，训练后都明显好于未训练版本。

**泼冷水。** 第一，主评测只有 50 个留出任务，而且 BrowseComp-Plus 的每个任务自带一份独立语料、对应一个问题，「预判未来问题」在主实验里其实就是「为一个已知分布的问题类型整理语料」；真正多问题复用的数据是作者用 Gemini 合成的。第二，复用场景下每题读的文件和 token 都多了好几倍，「更省」只在按准确率归一化之后成立。第三，Stack Overflow 子集 85.5% 对比基线 9% 左右，差距大得反常，论文没有单独解释，我会先当成可能有数据或语料组织上的特殊性来看。第四，GraphRAG 和自动压缩的数字低得很夸张（自动压缩 0.04），基线实现是否充分值得打个问号。

## 🔬 最有意思的部分

**一是 RL 真的改变了「整理习惯」，而且没有专门奖励结构。** 在 BRIGHT 上，训练后的建库 agent 平均产出 53.4 个活跃合成文件、45.4 个聚类、8.0 个合并产物；未训练版只有 4.8 个文件、4.2 个聚类、0.6 次合并。奖励里没有任何「多建层级」的项，层级是被「下游答对」逼出来的。定性对比也一样：基座模型建出来的文件系统是碎片化的，回答 agent 很难导航；训练后会把相关信息集中到专门的文件里。

**二是回退路径不是摆设。** 论文给了一个案例：某个 BrowseComp-Plus 问题需要的细节在合成层被漏掉了，回答 agent 顺着来源链接找到对应的原始文件，答对了，而且没有遍历整个语料。这正是「Delete 永远不删原文」和「CreateFile 必须带来源链接」这两条约束的价值。作者自己也承认，什么时候该绕过合成层直接读原文，目前还没有好办法。

**三是「建一次」和「每次都搜」的成本账终于被摆上桌。** 表里 GraphRAG 建库最便宜（1.2 万 token）但只有 0.36；自动压缩花了 50 万 token 反而几乎全错；Librarian 花 17.9 万拿到 0.77。**建库花多少不是重点，花在下游真会用到的结构上才是重点。**

## 🤔 我的判断

**定位：方法探索加训练配方，问题定义很有价值，实证规模偏小。**

亮点三条：

1. 把「为下一个 agent 整理工作区」定义成可训练的策略，并用回答 agent 的准确率直接做奖励，绕开了「什么是好的记忆结构」这个说不清的问题。
2. 四个受限动作加「原文不可删、合成文件必带来源」的约束，是一套很容易迁移的工作区规范，不训练也能先当规则用。
3. 探针式的中间奖励（每 8 步测一次可回答性差值）给长程建库轨迹提供了比终局奖励细得多的信号，思路可以迁移到任何「先准备、后使用」的 agent 任务。

问题与局限：只在静态语料上做问答，文档变化后工作区怎么增量维护没碰；建库 agent 要看很大的文件上下文，规模上限没测；主实验的「预判」更像是针对一类问题分布的离线整理；奖励依赖有标准答案的训练问题，换到没有标签的企业知识库，得先解决「拿什么当奖励」。

对工程的直接启发：在 coding agent 的仓库里，`AGENTS.md`、`docs/`、skills 目录其实就是一个「给下一个 agent 用的工作区」，现在大多是人手写或者 agent 顺手写。可以借这篇的三条标准给它们立规矩：合成文档放在浅层、按抽象层级命名目录；每条结论都带指向源文件或 commit 的链接；只写会被多次查询复用的内容。再进一步，可以用「新会话里 agent 回答一组固定的仓库问题的准确率」当回归指标，衡量每次文档整理是否真的有用，这比凭感觉判断 `AGENTS.md` 写得好不好可靠。作者最后提的方向也很对口：让工作区从自己的访问流量里学习，**每一次被回答的问题都是下一次该整理什么的证据**。

一句话收束：**会用文件夹的 agent 已经很多了，会替下一个 agent 收拾文件夹的，才刚开始被训练出来。**
