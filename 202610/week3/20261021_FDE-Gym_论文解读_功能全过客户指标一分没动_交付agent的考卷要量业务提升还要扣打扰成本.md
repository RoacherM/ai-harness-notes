# 功能全过，客户指标一分没动：交付 agent 的考卷要量业务提升，还要扣打扰成本

你有没有过这种体验：客户副总要一个「每日摘要邮件」加一个「问问你的油井」聊天框，顺口说一句「停工编码系统已经有了，不在范围内」。你按需求做完、按时交付、功能检查全绿，结果客户每个月的承包商停工索赔照样被驳回，因为真正的毛病恰恰在那套被排除在范围外的关键词脚本里：它总把一些停工错算到承包商头上，每个月都有争议条目，当月索赔直接冻结。**东西交了，问题没解决。** 做过驻场交付的人对这一幕都不陌生。

DeepLethe 联合二十多家高校和企业做的 **FDE-Gym**（arXiv:2610.22350）就是拿这类真实交付项目出题的基准。FDE 是 forward-deployed engineer，被厂商派到客户那里驻场、把 AI 系统真正落地的工程师。看完我的感受：这是我读过的第一个把**「需求可能是错的、约束没人说、问人要花钱、交付按客户自己的 KPI 计分」**四件事装进同一个可复现考场的 agent 基准，而它最反直觉的发现是：领先模型并没有卡在「识别需求是错的」，而是卡在**拿到了事实之后，还是造不出够好的系统**。

## 核心摘要

FDE-Gym 有 95 个端到端交付任务，来自 20 个客户场景、18 个行业，由行业专家从 2024 年以来在中国、新加坡、美国做过的真实项目改编，专家投入超过 1 万小时。每个场景有一个原始任务加 2 到 7 个变体，变体改动关键事实（哪条规则过时了、谁掌握关键信息、发起人的需求到底对不对）。agent 拿到工作区：任务说明、客户生产系统副本、文档和历史数据、员工通讯录；可以用命令联系 130 多个脚本化的干系人，他们有耐心上限、需要证据、会临时不在、有些人不该被打扰。交付物原样部署到生产，在留出的生产数据上算客户自己的业务指标。核心分数是**归一化业务提升 U 减去干系人联系成本 C**：什么都不做得 0，专家参考方案得 1，照字面做需求最多 0.2，出事故则正向提升清零。13 个模型配置在同一个只有五个文件和命令工具的极简框架里跑，每个组合跑三次。结果：L3（发起人原始需求）设置下最好的 Claude Opus 5.5 平均 **0.56**，95 题只解决 **14** 道（分数至少 0.8 且无事故）；五个配置一道都没解决；最弱的几个模型在 60% 到 83% 的任务上低于「什么都不做」。价值定位：一份把交付判断力变成单一可复现数字的评测方法，外加一组对 agent 落地很有用的诊断维度。

## 🎯 为什么这件事值得写

现有 agent 基准几乎都默认「问题已经定义好了」：SWE 类给 issue 和隐藏测试，部署类给规格，企业类给预设任务，澄清类只是从一个正确的任务里藏掉一点信息。问题本身从来不会错。

FDE-Gym 把交付拆成五个阶段，每个阶段都有现成基准，但从没有人把它们串成一条因果链：

| 阶段 | 已有基准在测什么 | FDE-Gym 补了什么 |
| --- | --- | --- |
| 问题定义 | 缺信息时会不会问、会不会被误导 | 发起人需求可能整个指错方向，错了就拿不到分 |
| 信息发现 | 在文件、系统、模拟同事里找约束 | 资料互相矛盾、过时、带立场；问人要收费 |
| 方案设计与实现 | 代码过不过隐藏测试 | 这段代码该不该写 |
| 部署运维 | 产物过不过检查、能否处理事故 | 交付物原样上生产，接回原来的入口才生效 |
| 交付结果 | 模拟经营的利润、专家打分 | 客户自己的业务指标，没有人类评委 |

对做 harness 和 judge 的人，这篇的意义在于它的**计分设计**：一套能防住「照字面做」「拟合历史数据」「凑整阈值」「全部甩给人工」这些捷径的锚点体系。

## 🏗️ 机制：四级任务说明、业务提升分、准入锚点

**四级任务说明，环境和评分完全不变。**

1. L0：告诉你真正的问题、适用规则和约束、怎么计分，只剩设计和实现；
2. L1：问题说清楚，但规则和约束要自己找；
3. L2：只给一个模糊但方向对的需求；
4. L3：发起人的原话，可能指向错误的问题。L3 是主设置。

因为只有说明文字在变，各级之间的分差就能归因到被隐藏的那部分信息上。

**分数定义。** 归一化业务提升：

$$
U=\frac{\mathrm{KPI}_{\text{delivered}}-\mathrm{KPI}_{\text{baseline}}}{\mathrm{KPI}_{\text{reference}}-\mathrm{KPI}_{\text{baseline}}}
$$

出现预定义事故（比如越权操作）时，正向提升清零、负向保留：\( U_{\text{adj}} = \min(U, 0) \)。联系成本 \( C=\sum_k c_k \)，每个干系人有隐藏的单条消息费率，超出耐心或违反联系限制时更贵，试运行和等待一天也计费。单次分数 \( S = U_{\text{adj}} - C \)，至少 0.8 且无事故算解决。汇总时把 \( U_{\text{adj}} \) 截在 -1，防止个别巨亏主导平均。

agent **不会被告知**问人要钱、有些人不该联系、需求可能是错的。线索散在通讯录、文档和数据里，和真实项目一样：文档可能过时，遗留代码可能基于错误假设。

**四个准入锚点。** 每个任务必须同时满足：参考方案至少 0.95；什么都不做恰好 0；照字面实现需求最多 0.2；捷径策略最多 0.8。唯一例外是需求本身既对又完整的任务，此时字面方案就是参考方案、必须至少 0.95，这样「永远不信发起人」也不会成为通吃策略。绕过客户控制或操纵评分器的分数被压到接近 0，评分器经过 270 多种捷径和绕过策略的测试。

**干系人是脚本化的，不是 LLM 扮演。** 一个小模型把问题映射到话题，每个人的知识、误解和透露信息的条件都预先写死。理由很实在：换一个用户模拟模型，agent 成功率就能差好几个点。

## 🧪 关键证据

**主结果（L3，全部 95 题，节选）。**

| 配置 | 分数 S | 95% 区间 | 业务提升 U | 联系成本 C | 解决数 | 低于 0 的题数 |
| --- | --- | --- | --- | --- | --- | --- |
| Claude Opus 5.5 | **0.56** | 0.50 到 0.62 | 0.70 | 0.14 | 14 | 5 |
| Claude Sonnet 5.5 | 0.49 | 0.43 到 0.55 | 0.67 | 0.18 | **15** | 7 |
| GPT-6 Astra | 0.38 | 0.30 到 0.46 | 0.60 | 0.22 | 9 | 18 |
| GPT-6.1 Sol | 0.37 | 0.28 到 0.44 | 0.57 | 0.20 | 7 | 17 |
| Mistral Small 4 | -0.32 | -0.41 到 -0.23 | -0.31 | 0.01 | 0 | 57 |
| Claude Haiku 4.5 | -0.33 | -0.42 到 -0.24 | -0.23 | 0.09 | 0 | 79 |

每道题取 13 个配置里的最好成绩，也只有 0.70、解决 30 道；16 道题没有任何配置达到 0.5。

**各级说明的分差（20 个原始任务，三家领先模型平均）。** L0 到 L1 掉 **0.28**（区间 0.17 到 0.39），L1 到 L3 只再掉 0.04（区间 -0.03 到 0.14）。Opus 5.5 在 L1、L2、L3 分别是 0.62、0.54、0.55。作者原本以为瓶颈在问题定义，数据不支持：一旦模型开始主动找约束，它们顺便也发现了发起人真正需要什么。弱模型则每一级都在掉：GPT-5.5 从 0.51 到 0.15、0.04、0.06。

**拿到事实不等于做好系统。** L3 下领先模型每题问 10.0 到 12.3 个问题，拿到 72% 到 85% 的关键事实，业务提升却只有 0.60 到 0.70。三家模型拿全所有关键事实的 73 个「任务乘模型」案例里，提升达到 0.8 的只有 27 个（37%）。Opus 5.5 自己拿全事实的 23 题里只有 10 题达到 0.8。

**花得多、干得久不等于分高。** GPT-6.1 Sol 每次 0.24 美元、25 轮，得 0.37；Gemini 3.8 Flash 每次 1.54 美元、121 轮，得 0.19。Qwen 3.8 Flash 平均 169 轮、110 分钟，152 个组合里只有 11 个在限额内提交。领先模型全部按时提交，26 到 60 轮。

**泼冷水。** 第一，L0 到 L2 只在 20 个原始任务上测，其中 3 个场景的 L2 直接复用 L3 结果，分级结论样本量偏小，作者自己也只声称「没看到更大的进一步下降」。第二，所有模型用同一个极简框架，换成带规划、记忆、子代理的产品级 harness，分数和排名都可能变。第三，联系成本由出题专家定价，是对干系人时间的建模，不是测量。第四，暂无人类基线，「人类专家只拿发起人原话能做到多少」还在收集。第五，DeepLethe 自己运营平台和榜单，存在利益相关。

## 🔬 最有意思的部分

**一是「照字面做最多 0.2」这条锚点。** 它让「需求写什么就做什么」在绝大多数任务上直接失效，即使需求方向正确也一样，因为说明里漏掉的约束仍然决定结果。这比在 rubric 里加一句「是否理解用户真实意图」硬得多：**不是让裁判去判断你懂没懂，而是让客户的 KPI 告诉你**。这和我们之前读过的 Trains but Doesn't Learn（检查全过、交付的模型并不比底座好）是同一类失败，FDE-Gym 用锚点把它系统性地挡在门外。

**二是联系成本把「会问」变成了「问得值」。** agent 不知道提问要钱，于是像不要钱一样问。GPT-6 Astra 交付的系统有 36 道题本身达到 0.8，扣掉联系成本后只剩 9 道还算解决；Opus 5.5 是 40 道变 14 道。联系成本吃掉了 Opus 0.70 提升里的 0.14，Astra 0.60 里的 0.22。另一个极端是 Mistral Small 4，每题只问 0.7 个问题，拿到 6% 的关键事实。澄清类基准通常只测「该问时问没问」，这里多了一维：**问谁、问几次、在什么时候问**。

**三是零分不是地板。** 一个该拒却赔付的售后 agent、一个算错责任方的计费任务、一个半夜叫醒错人的值班系统，都比原来的系统更糟。扣联系成本之前，Mistral Small 4 交付的系统就有 51 道低于「什么都不做」，其中 23 道造成的损害超过参考方案带来的收益。Claude Haiku 4.5 开不开扩展思考都一样（-0.33 和 -0.35）。作者的原话很直接：弱 agent 不是强 agent 的便宜版，它在这些任务上的期望贡献是负的。

**四是组件基准是交付能力的弱信号。** 同一批在 Terminal-Bench 2.1、Vibe Code Bench、Finance Agent 上分别能解到 88%、90%、61% 的模型，在 FDE-Gym 上只有 0.19 到 0.56，最好的也只解决 15% 的任务。量纲不同不能直接比，但方向很清楚：**会写代码、会用终端，离「让客户的业务变好」还差一整段判断力**。

## 🤔 我的判断

**定位：评测设计的标杆样本，计分和防捷径机制比排行榜本身更值得抄。**

亮点三条：

1. 「什么都不做 = 0，参考方案 = 1，字面实现 ≤ 0.2，捷径 ≤ 0.8」的四锚点准入，是一套可以迁移到任何 agent 评测的出题质检规则，等于把「先拿 do-nothing 和 shortcut 审基准」这条最佳实践做成了硬门槛。
2. 只改说明文字、环境和评分不动的四级设计，让失败可以归因到具体缺了哪类信息，这比报一个总分有用得多。
3. 把联系成本和事故清零写进分数，第一次让「agent 打扰人类」和「agent 闯祸」进入同一个可优化目标。

问题与局限：分级样本量小；单一极简框架；联系定价是专家设定；无人类基线；变体和参考方案不公开，外部复现只能靠平台。

对工程的直接启发：

- **给自己的 agent 评测加 do-nothing 和 literal 两条基线。** 如果字面执行就能拿高分，说明考卷测不出判断力；如果 agent 低于 do-nothing，说明它在帮倒忙，这比任何 judge 分数都更早暴露问题。
- **把「问人」当成有成本的工具调用来记账。** 在 harness 里给 ask_user 或联系干系人加预算和计费，评测时把联系成本单独报告，训练时也许能逼出「先查文档再问人」的习惯。
- **把「拿到事实」和「做出系统」分开测。** FDE-Gym 的评分器记录了 agent 拿到了哪些关键事实，这让信息发现和系统构建两段的损失可以分开。做 judge 时也该这么拆：一条轨迹先判「找没找全证据」，再判「证据有没有变成正确的行动」。
- **脚本化模拟用户值得重视。** 想让评测可复现，用 LLM 扮演用户是最大的噪声源之一；能写死就写死。

一句话收束：**交付的最后一公里，量的不是代码写没写对，而是客户的那个数字有没有动。**
