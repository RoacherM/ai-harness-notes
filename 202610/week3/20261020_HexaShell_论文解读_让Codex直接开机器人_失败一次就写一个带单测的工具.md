# 让 Codex 直接开机器人：失败一次，就修一个带单测的工具

你有没有过这种体验：coding agent 在仓库里跑测试，红了，它读报错、改代码、再跑，绿了，这次修复就永远留在代码库里，下次不用再踩。可一换到机器人上，大家的做法就变了：要么训练一个视觉动作模型，要么让大模型每一步直接选抓取点，失败了下一回合从零再来，什么都没留下。行业里把后一条路叫 **VLM agent as policy**（把视觉语言模型直接当策略）。**那如果把机器人当成另一个「仓库」，让一个没改过的 coding agent 用写工具、修工具的方式去学，能走多远，又会卡在哪？**

HexaFuture 这篇 **HexaShell**（arXiv:2610.23479）就是做这个实验。harness 薄到只剩一条命令行 `robo`：把命令翻译成关节运动，别的一概不管。agent 看三路 RGB 相机加标定，失败后由同一个模型扮演的优化 agent 读日志、诊断、改一个工具并补单测，再在同一个场景重试。看完我的感受：这是我近期看到最干净的「**学到的东西以代码形式沉淀**」样本，比在提示词里塞经验可信得多；而它给出的能力边界也很诚实，**卡住它的是接触，不是推理**。

## 核心摘要

HexaShell 把一个原封不动的 Codex（GPT-6-Astra，中等推理强度）放进一个没有模拟器、没有 API key、没有宿主目录的容器，只给它 `robo` 一条命令、约六十行的手册和一个刷新观测的 `obs/` 目录（三张 640×480 RGB 图、相机内参和位姿、两只手的 TCP 位姿、关节角，没有深度图）。服务端只做命令校验、2 厘米间隔的直线插值、cuRobo 逆运动学和梯形速度规划，没有运动规划器。所有策略都写在工具里：一个工具就是 `tool.py` 加 `interface.md`，只能用机器人观测到的东西，不能读物体真实位姿。核心感知手段是几何三角测量：桌面高度用平面扫描一次测出（三对相机互相差不到 1 毫米），已知平面上的点用射线和平面求交，两个视角都看见的点用两条射线求交，一个视角不够就把腕部相机挪过去再看一眼，代价是消耗任务的动作步数。演化循环在每个任务种子 0 的前 10 个布局上逐个跑，失败后优化 agent 改工具并跑单测，过交付检查才保留，同一布局最多改 5 次；10 个布局跑完冻结工具，在 10 个新布局上复测。结果：RoboDojo 全部 42 个任务按榜单口径成功率 **39.7%**、进度分 **48.0**，高于最好的学习型策略 VPP2（32.3%、39.3），同一模型不带工具只有 22.5%。同一 harness 下三角测量比 Depth Anything V2 高 **8.7 个点**，按布局配对 57 胜 23 负。能力边界非常清楚：推动类 **92.5%**，记忆类 65.0%，紧配合插入只有 **8.3%**。价值定位：一份「把 agent 的经验沉淀成可测试代码」的工程方法，加一张 VLM agent 在物理世界的能力地图。

## 🎯 为什么这件事值得写

过去让大模型写机器人代码的工作很多：Code as Policies、VoxPoser、ReKep、SayCan。它们有个共同点：**程序按指令临时生成、用完就扔，底层原语是人写的**。HexaShell 把分工倒过来：原语由 agent 自己写，跨回合保留，被优化的对象正是这些原语，每回合的「临时程序」反而很短。

这和 harness 圈子最近关心的问题是同一个：agent 的经验该存在哪里？

| 路线 | 经验存放处 | 能否被检查 |
| --- | --- | --- |
| 提示词或记忆笔记 | 自然语言 | 很难，靠模型自觉 |
| 改脚手架本身（自改进 coding agent） | harness 代码 | 能，但影响全局 |
| 训练权重 | 参数 | 不透明 |
| **HexaShell** | 任务级工具加单测 | 能，单测和交付检查兜底 |

作者刻意把 agent 的脚手架、提示词、基础接口全部固定，只允许改 `tasks/<task>/` 下的工具，共享的 `pick` 和 `table_plane` 两个工具也不准动。这种「改动面很窄」的设计，和我们之前读过的 Harness² 那类「可编辑面加禁区」思路一脉相承，只不过这次落在物理任务上。

## 🏗️ 机制：薄 harness、三角测量工具、修复循环

**四条设计原则。** harness 只翻译不决策；真值靠架构隔离，跑 agent 的容器里没有模拟器、任务和打分代码；成功只由基准自带的 checker 判定，不改它；手册只写接口，策略全在工具里。

**命令与预算。** 基础命令有 `move`（沿世界坐标轴平移，每轴最多 0.20 米）、`rotate`、`point`、`gripper`、`home`、`wait`、`obs`、`status`、`done`。每条命令返回 JSON：规划结论、到达位姿、剩余预算。观测、测量、模型思考都不计步，只有真正执行的动作步计数，每个任务上限 200 到 1900 步。

**用几何代替深度网络。** 一个像素加标定只能给出一条射线，要定位还需要一个额外约束：

$$
\mathbf{X} = \mathbf{C} + \lambda \mathbf{d},\quad \text{约束：} \mathbf{X}\in\Pi_{\text{plane}} \ \text{或} \ \mathbf{X}\approx \mathbf{C}' + \mu \mathbf{d}'
$$

其中 $\mathbf{C}$ 是相机中心，$\mathbf{d}$ 是像素射线方向。约束可以是桌面、积木顶面、碗沿这类已测平面，也可以是第二个视角的射线。分工是：**模型挑像素，代码量世界**。

**演化循环。**

1. 执行 agent 用当前工具尝试一个布局；
2. 成功则优化 agent 在 `playbook.md` 里记一条「哪个工具为什么有效」；
3. 失败则优化 agent 读命令日志、每条命令的相机帧、执行 agent 的对话记录和工具代码，把诊断写进 `skill.md`，新增或修复一个工具；
4. 交付检查确认文件完整、工具能加载、接口文本里**不出现任务名和物体名**，不通过就回滚；
5. 重启模拟器，同一布局再试，最多 5 次修改；10 个布局后整理笔记、冻结、复测。

另一个细节值得抄：同一个服务端有两种执行器，直接执行器能重置、回放、记录真实位姿（但容器永远拿不到），桥接执行器包成官方评测客户端的策略，没有重置也没有真值。**每个交付的工具都必须能在桥接执行器下跑**，保证开发时的便利不会漏进评测。

## 🧪 关键证据

**主结果（冻结工具，10 个新布局）。**

| 系统 | 成功率（榜单口径） | 进度分 | 54 个变体简单平均 |
| --- | --- | --- | --- |
| GPT-6-Astra，不带工具 | 22.5 | 29.0 | 24.3 |
| PhysicalRSI（VLA 加语言模型调度） | 31.4 | 36.3 | 26.1 |
| VPP2（世界动作模型） | 32.3 | 39.3 | 30.6 |
| **HexaShell** | **39.7** | **48.0** | **35.4** |

**三角测量和深度网络对比（同 harness、同循环、同模型，开发布局）。** 三角测量榜单口径 38.3%，Depth Anything V2 29.6%，模拟器渲染深度 48.8%（仅作参考，标准观测里没有）。深度网络在物体像素上的中位误差是头部相机 41 毫米、腕部约 100 毫米，而抓取和放置需要大约 1 厘米。

**多看一眼的代价。** 三角测量把 3.6% 的执行步数花在挪相机上（深度网络 0.7%），43% 的回合至少挪过一次。但在挪过相机的 180 个布局上，它成功 39 次，深度网络只有 22 次。预算并没有因此更紧：用掉四分之三以上预算的失败更少，被步数上限截停的回合也更少。

**泼冷水。** 第一，榜单上的条目报的是每个种子 50 个回合、三个种子，HexaShell 是种子 0 上 10 个新布局各跑一次，样本量差一个数量级，而且新布局和开发布局来自同一个种子。第二，复测时 agent 的提示词里有任务描述、评分表和开发阶段的工具表现笔记，25 个任务的优化 agent 还读过一份「checker 要什么」的说明（只给优化 agent，执行 agent 看不到）。第三，RGB 工具是从之前带深度的运行结果出发再演化的，每个任务给了 12 小时开发预算。第四，单个复测回合中位耗时 739 秒，对应 26 秒机器人时间，几乎全是模型延迟，RoboDojo 不计时间，真机上不可能这么慢。

## 🔬 最有意思的部分

**一是「接触，而不是推理」这条边界画得很准。** 作者给每个任务打两个标签，一个是成功需要的物理接触，一个是几何之外要做的决策。物理标签决定一切：推动 92.5%，刚体抓放 50.0%，运动物体 40.0%，可形变 33.3%，铰接物体 7.5%，紧配合插入 8.3%；决策标签影响很小，只有记忆类显著（65.0%）。学习型策略 VPP2 正好相反，推动只有 24.7%，插入 28.1%、可形变 49.4%。两条路线的长短板几乎互补。

**二是失败的「死法」本身就是诊断信号。** 268 个失败回合里，57% 用完了预算，30% 是 agent 宣布完成但 checker 不认，13% 是还剩四分之一以上预算就放弃。可形变、铰接、刚体类有 60% 到 77% 的失败是用完预算：**agent 知道自己没做成，就是做不出那个动作**，这是执行缺口。记忆类有一半失败是「自以为成功」：这是感知或判断缺口，和 VLM 看不清细节、判不准成败的老问题一致。把「宣布成功被否」和「预算耗尽」分开统计，对任何 agent 评测都是值得照搬的维度。

**三是优化 agent 像程序员读 bug report，而不是看图。** 769 轮优化里，530 轮在失败后，中位 6.3 分钟一轮，中位跑 16 条 shell 命令，92% 的轮次跑了单测，中位改动加 118 行删 6 行。作者精挑的 7 个案例里，**5 个优化 agent 一张图都没看**，靠命令日志、工具返回的拒绝原因和代码就定位了问题。比如推 T 任务里面积检查按每个像素在平面上的足迹算，不同相机像素尺寸不同导致结论打架；插管任务里工具把单目射线上 28,935 个没测过深度的体素当成硬障碍，把原本可行的路径全否了，修法是降级成偏好并加一次原路径复查。最后一共沉淀出 327 条任务命令、约 7.8 万行 Python。

**四是工具会「锁死一种解释」。** 叠衣服任务里，带工具反而只有 50%，不带工具的同一模型有 72%。工具把一种理解和一段预先规划的动作固定下来，而逐步行动的 agent 还能边看边纠正。这提醒我们：**把经验写成代码不是总赢**，开放式、需要持续反馈的任务，固化反而丢掉了闭环。

## 🤔 我的判断

**定位：harness 设计加能力测量的工程样本，方法不新但组合得很干净，测量部分尤其有价值。**

亮点三条：

1. 改动面极窄、验收是「同一布局重新执行一遍」而不是模型自评，这比 Reflexion 一类自我反思更硬，也和「代码检查优先于 LLM judge」的思路一致。
2. 交付检查里「接口文本不准出现任务名和物体名」是一条很便宜但很有效的防过拟合规则，任何让 agent 自己写 skill 的系统都可以加。
3. 失败分型（宣布成功被否、预算耗尽、提前放弃）把评测从一个成功率拆成可以行动的诊断，比单纯报平均分有用得多。

问题与局限：复测样本量和榜单不可比，同种子新布局的泛化力度有限；提示词和优化 agent 的额外笔记让「完全靠自己学」的叙事打了折扣；模型延迟让它离真机很远；工具库 7.8 万行，长期维护和跨任务复用没讨论，除了两个共享工具，几乎全是任务专属。

对工程的直接启发：在 Pi 或 Claude Code 这类 harness 里做「技能自演化」时，可以直接套这个循环：失败后让同模型的优化 agent 只改 skill 目录下的一个文件，必须同时补测试，交付检查卡住命名泄漏，然后在同一个失败用例上重放验收，通过才合入；成功也记一条 playbook，不只记失败。评测侧把「agent 声称完成但 checker 不认」单独作为一类指标追踪，它往往比总成功率更早暴露 judge 能力的短板。

一句话收束：**把机器人当仓库、把经验当代码，推理那一半已经够用了，剩下那一半是手。**
