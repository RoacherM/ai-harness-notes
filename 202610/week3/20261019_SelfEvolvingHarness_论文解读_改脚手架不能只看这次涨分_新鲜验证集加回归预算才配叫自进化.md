# 改脚手架不能只看这次涨分：新鲜验证集加回归预算，才配叫「自进化」

你有没有过这种体验：让 agent 自己改 prompt、改 skill、甚至改 harness 代码，跑一轮评测涨了几个点，于是把新版本合进主干；过两周换了一批任务，老问题又冒出来，回头一查，那次「涨分」是在同一批调参任务上挑出来的。行业里管这件事叫 **Harness RSI**（脚手架递归自我改进），这一年论文多到一周好几篇。可大家很少停下来问：**一次被接受的脚手架修改，凭什么说它会泛化、不会把以前会的东西忘掉？**

中关村学院和中科大这篇 **Self-Evolving Agent Harness**（arXiv:2610.18813）不是又一个新方法，而是给这个方向立「宪法」：先把什么算自进化定义清楚，再按「改的是什么」分类，然后用演化算法和持续 PAC 学习的语言写出三个条件——期望泛化界、带回归预算的保留界、以及**只用新鲜独立验证集**的高概率准入规则。看完我的感受：它把 [Cortex](./20261016_Cortex_论文解读_加一条skill别靠一次成功_测量门控才留下rules.md)、[RRSI](../../202609/week4/20260923_RRSI_论文解读_Harness_RSI会过拟合正则提案与筛选才保住OOD.md)、[EvoHarnessBench](../../202609/week3/20260921_EvoHarnessBench_论文解读_脚手架越加越忘_非平稳性放进harness本身.md) 这些工程直觉收进了一套统一的话语里，而且直接点名：HarnessBank 和 Self-Harness 的搜索期检查**不满足独立性假设**。

## 核心摘要

论文把 harness 定义为「治理模型 M 在环境 E 中执行的软件与配置」，含七类运行时功能（agent loop、工具与 skill 编排、上下文构造、记忆与状态、上下文压缩、调度协作、执行基础设施），最终评估 J 必须在可编辑面之外。自进化是一个持久的反馈循环：第 k 轮由在任 harness 跑一批 rollout，Update 算子做诊断、提案、评估、准入，没被接受就保留原版；它要求两件事成立，一是用自己执行的反馈生成修改且保留继续更新的能力，二是被接受的修改跨 run 持久加载。按「改的是什么」，作者把更新目标分成解释态（指令、经验、在固定算子上的任务级编排）和可执行修订（组件实现、仓库级控制逻辑、插件组合 Everything Is a Plugin），并把 SICA、MCE、SkillOpt、DGM、HarnessBank、Meta-Harness 等映射到 (1+1)-ES、(1+λ)、档案式搜索、重组、MAP-Elites、协同进化、Pareto 选择、bandit 预算分配八种演化结构。理论部分给出三条结论：替换一个任务后整条更新过程的敏感度 β 控制期望泛化差距；如果每次后续修改对历史分布的退化不超过预算 ε，累计遗忘最多是这些预算之和；每轮固定最多 K 个候选、再抽 m 个新鲜独立任务做配对比较，用 Hoeffding 加 union bound 得到「只接受上界为负的候选」的准入规则，评估器与真实目标的偏差 η 还要再加 2η。这篇的价值不在新数字（引用的 SpreadsheetBench 和 EIP 数字都来自别人），而在于**把「接受一次修改」从工程拍板变成一个有统计含义的动作**，同时把物理安全、机构问责这些后果写进了设计约束。

## 🎯 为什么这件事值得写

过去一个月仓库里归档的 harness 自进化论文已经不下十篇：有改 skill 的、改记忆的、改整个仓库代码的、改插件绑定的。它们共享一个默认流程：跑任务，看失败，提修改，在某个验证集上比一比，赢了就留。问题是每篇用的「赢了」定义不一样，验证集常常和搜索集重叠，几乎没人报告「接受这次修改后，老分布掉了多少」。

这篇的切口是**定义和准入**，而不是更强的搜索器：

| 常见做法 | 隐含假设 | 论文指出的问题 |
| --- | --- | --- |
| 在训练任务上筛选再在测试集报告 | 筛选集分数近似真实收益 | 搜索期检查缺独立性，自适应复用会高估 |
| 只要总分涨就合并 | 混合分布涨等于每组都不掉 | 混合增益不保证分组保留 |
| 把 judge 当最终裁判 | judge 等于目标 | 需要单独校准偏差 η，judge 换了要重校 |
| 把日志追加、固定规则压缩也叫进化 | 状态变了就是学习 | 没有可继续的更新机制、没跨 run 持久化，不算 |

一句话：**自进化的风险不是改不动，而是改得太顺手**。

## 🏗️ 机制：定义、分类、三条理论条件

**定义。** 运行写成

$$\tau \sim \mathrm{Run}(M, H, E),\quad y = J(\tau)$$

第 k 轮 $B_k = \{\tau_{k,i}\}_{i=1}^{b}$ 由 $H_{k-1}$ 产生，$H_k = \mathrm{Update}(H_{k-1}, B_k)$。候选可以改 harness 内部的 critic 或临时检查，但**不能改 J**。

**分类看的是「改动边界」不是编程语言。** 只在固定算子上调顺序、调路由，即使写成代码，也算解释态；一旦改了算子实现或执行协作的运行时机制，就是可执行修订。可执行修订再分三层：

| 层级 | 可编辑面 | 代表 | 主要风险 |
| --- | --- | --- | --- |
| 工具与代码补丁 | 指定组件，入口与 I/O 合同不变 | Self-Harness、HarnessCompass、AHE | 输出变化经共享状态外溢 |
| 仓库与运行时逻辑 | 上下文构造、编排循环、hook、恢复、终止 | DGM、SICA、Meta-Harness、HarnessOpt | 改一处，其它未改组件的输入假设也变了 |
| 插件组合 EIP | 哪个实现提供记忆、工具分发、agent loop 等服务 | DSH Everything、HarnessX、Autogenesis | 接口合同不等于行为隔离 |

**三条理论条件。** 记 $\ell(H,z)\in[0,1]$ 为对执行随机性平均后的损失：

1. **期望泛化**：把第 s 轮的一个任务换成独立新样本、重跑所有下游更新得到 $H_k^{(s,i)}$，平均敏感度 $\beta_{s,k}$ 给出 $\mathbb{E}[R_s(H_k) - \hat R_s(H_k)] \le \beta_{s,k}$。作者特意提醒：代码改动小不代表整个更新过程稳定。
2. **保留**：若每次后续转移对第 s 轮分布的退化不超过 $\varepsilon_{s,u}$，则

$$\mathbb{E}R_s(H_k) \le \mathbb{E}\hat R_s(H_s) + \beta_{s,s} + \sum_{u=s+1}^{k}\varepsilon_{s,u}$$

   预算是额外假设，不是稳定性推出来的，而且会累加。
3. **准入**：每轮固定最多 K 个候选，再抽 m 个与候选构造独立的新任务，配对差 $\hat\Delta_k(H')$ 落在 $[-1,1]$，T 轮共 KT 次比较，以至少 $1-\delta$ 的概率同时成立

$$\Delta_k(H') \le \hat\Delta_k(H') + \sqrt{\frac{2\ln(KT/\delta)}{m}}$$

   只接受上界为负的候选；若评估器与目标风险差最多 η，还需 $\hat\Delta_k + \sqrt{2\ln(KT/\delta)/m} + 2\eta < 0$。

## 🧪 关键证据：这是一篇框架论文，数字都是借来的

论文本身不跑新实验，所引数字作者也很克制地加了限定：

- **HarnessOpt（SpreadsheetBench）**：GPT-5.4-nano 加 HarnessOpt 和 skill 到 **77.58%**，高于 GPT-5.5 加 SkillOpt 的 **76.20%**；四个模型上 HarnessOpt 加 skill 比 SkillOpt-Lite 高 **5.69 到 11.39** 个点。作者原话的意思是：这展示了模型与 harness 的配对交叉，**不说明同成本下更优**。
- **EIP 办公表格负载**：首个任务工具调用从 13 次降到 3 次，但墙钟时间多 **54.9%**、token 多 **15.7%**；另一份累计报告五个任务后省 **110,351** token 和 **22.97** 秒。两份报告第一个任务的数字对不上（一个推出 +6,453 token，一个写 +4,895），作者直接说**不能当成同一条成本曲线**。
- **LiveBrowseComp**：XYZ 加 dsh-everything 51.39，作者注明来源未给单位，需要重复实验、匹配预算和任务质量才能谈因果。

我自己算了一下准入规则有多保守（以下是我的估算，不是论文数字）：取 K=5、T=10、δ=0.05，则 $\ln(KT/\delta)=\ln 1000\approx 6.91$。m=200 个新鲜任务时，置信边距约 **0.26**，意味着候选要把平均损失降 26 个点以上才敢收；m=1000 时约 **0.12**；m=5000 时约 **0.05**。日常 harness 改动的真实增益往往只有几个点，按这条规则几乎永远不会被接受。

## 🔬 最有意思的部分

**一是点名「搜索期检查不独立」。** HarnessBank 先在训练任务上筛选再做单独终测，Self-Harness 复用一个留出的回归切分，作者说这些都不满足构造候选与验证样本独立的假设；而且**保密、做多重比较校正都消除不了自适应依赖**，要么用新样本，要么用 reusable holdout 一类的自适应有效推断。这其实把很多论文里「我们留了 held-out」的说法打了折扣：留出集被反复看，就不再是留出集。

**二是「重复跑」和「多加任务」不是一回事。** 样本量由独立任务数决定，多跑几次 rollout 只降执行噪声，不增加有效样本。同一会话里相关的多个片段要分组，非可加指标（比如 pass@k 一类）要另做集中不等式。这对把「每题跑 5 次」当成 5 倍样本的实践是个直接提醒。

**三是安全约束写进定义。** 机器人场景里，软件回滚能改未来指令，但**回不了已经发生的形变、磨损或伤害**；临床和公共服务里，回滚补不回错过的治疗窗口。所以作者主张急停、力与速度上限、授权检查永远放在可编辑面之外，「创造能力不等于授予权限」。

## 🤔 我的判断

**定位：测量与治理基础设施的理论底座**，不是方法突破。

亮点三条：

1. 「改的是什么」按改动边界而不是文件数或语言来分，解释了为什么改编排代码有时比改一个工具实现更危险。
2. 准入规则把「新鲜、独立、固定候选数」三个条件写死，和 Cortex 的曝光感知门控、RRSI 的正则筛选可以对齐成一张工程清单。
3. 把 judge 偏差 η 放进准入不等式，等于说**换了裁判就要重新校准，旧的接受记录不能直接沿用**。

问题与局限：Hoeffding 加 union bound 用的是区间宽度 2 的最坏情况，配对差方差通常远小于这个，按原式几乎收不进任何真实修改；更实用的应该是方差自适应的 Bernstein 型界或序贯检验，论文没给。理论都在任务独立同分布、模型与评估器固定的假设下，而真实部署恰恰是分布和裁判都在漂。引用的案例数字作者自己都说不能当因果证据。

对工程的直接启发：在 MMP 这类确定性 harness 里，可以把「每轮最多 K 个候选、准入只用这轮新抽的任务、按任务族分组报告退化、J 与权限边界放在 Manifest 之外不可编辑」直接写成准入流程；另外把每次接受的版本、证据和准入历史记下来，和论文对公共服务场景的建议一样，出事时才查得到是哪一版规则惹的祸。

一句话收束：**自进化真正稀缺的不是会改的 agent，而是一套舍得说「这次不收」的准入纪律。**
