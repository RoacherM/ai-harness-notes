# 没有标准答案也能改脚手架？对比探针定改动，改进库让下一次改得更好

你有没有过这种体验：给 coding / office agent 换了一套脚手架，在离线验证集上调得漂漂亮亮，一上线碰到没见过的新活就水土不服；想在线边跑边改，又发现**线上任务根本没有标准答案**，改一条 guardrail 到底是变好还是变坏，只能靠感觉。更糟的是，这次为一个任务改出来的高度定制 harness，原样带到下一个任务往往是噪声。业内把这件事叫 harness 的递归自改进（RSI），**可开放世界里真正的问题是：没有 verifier 时凭什么改？改完的经验又怎么让「下一次怎么改」也变强？**

Google Cloud AI Research 与 Northwestern 的 **Harness²**（arXiv:2610.14224）给的答案是两层递归：任务内用「提案 → 同条件探针对比 → 选择性合成」的对比步替代 ground-truth；任务后把被采纳的 harness 和有执行证据支撑的教训写进一个**改进 harness 的库**，下一个任务从公共初始 harness 出发，但由更新过的改进器来改。看完我的感受：这是把今天早上那篇 [SelfEvolvingHarness](./20261019_SelfEvolvingHarness_论文解读_改脚手架不能只看这次涨分_新鲜验证集加回归预算才配叫自进化.md)「改脚手架要有新鲜验证集」的问题，换成了另一种更贴近部署的回答：**没有验证集时，拿同任务的行为对比当证据，并且不继承执行 harness，只继承改进经验。**

## 核心摘要

Harness² 把 harness 拆成 8 个以文件形式挂进运行时的可编辑组件（system prompt、guardrails、memory、skills、tool guidance、scripts、subagents、middleware plugin，在 AHE 的文件级分解上多加一个 plugin）。每个任务先跑一次参考执行，编辑器（默认 Claude Opus 4.8 跑在 OpenCode 里）提出两份候选：**invariant**（跨领域会复发的 agent 缺陷，如规划、工具使用、上下文管理、委派）和 **domain**（当前领域的知识、流程、约束）；两份候选在同模型同环境下各跑一次，与参考执行做行为对比；Composer 读 diff 与全部执行证据，选择性合并、改写、只采一份或保持原样，每个决定都要绑定具体观察而不是假想分数。\(k>1\) 时有并行（\(k\) 个候选池、\(k\) 个独立合成会话）与串行（链式 \(k\) 步）两种递归，最后由不看来源 harness 的 agentic selector 选交付物。任务结束后 Reflector 只把**有行为对比支撑**的教训写入库（每条 = 完整可执行 harness 树 + `EXPERIENCE.md`），证据不足就不写。主结果：在 WorkBuddy-Bench、JobBench、Harvey LAB 三个专业基准、两种执行模型（GLM-5、Gemini 3.5 Flash）× 两种初始 harness（OpenCode、Codex）上，**单步 \(k=1\) 全部涨分**：GLM-5 + OpenCode 在 WorkBuddy 平均 **64.2 → 75.7（+11.5）**，反超同 harness 下 Gemini 的基线 72.4；LAB Partial 最高 **+11.8 pp**（GLM-5 + OpenCode，59.6 → 71.4）；JobBench 最高 **+4.5**。并行递归 \(k=5\) 再加 2.9–3.9（WB）、3.0–4.2（JobBench）、2.6–6.7 pp（LAB），且执行步数大多更少。真正的价值定位：**开放世界、无标签任务流上的 harness 在线进化协议**，核心是「证据怎么来」和「经验存什么」。

## 🎯 为什么这件事值得写

harness RSI 这条线我们已经归档过不少：[Meta-Harness](../../202609/week3/20260918_Meta-Harness_论文解读_脚手架也能端到端搜_完整轨迹文件系统比压缩反馈狠.md) 离线搜 harness 代码，[RRSI](../../202609/week4/20260923_RRSI_论文解读_Harness_RSI会过拟合正则提案与筛选才保住OOD.md) 提醒 RSI 会过拟合，[Harness-Design](../../202609/week3/20260918_Harness-Design_论文解读_脚手架不是一整块_组件要按模型和预算配.md) 说组件要按模型和预算配，[Cortex](./20261016_Cortex_论文解读_加一条skill别靠一次成功_测量门控才留下rules.md) 要求加 skill 先过测量门。它们大多默认手里有训练任务、单测或验证反馈。

Harness² 瞄准的是两个更难的缺口：

1. **线上没有 verifier。** 新任务在设计期没见过，没有标准答案，代理信号、自评或两两比较都不可靠。
2. **任务级改动不迁移。** 直接继承上一个任务的定制 harness，在分布漂移时会把噪声一路带下去。

| 路线 | 改什么 | 监督来源 | 跨任务带走什么 |
| --- | --- | --- | --- |
| 离线搜索（Meta-Harness 等） | 执行 harness | 训练集分数 | 一个固定最优 harness |
| 检索记忆（ReasoningBank） | 不改 harness | 过去轨迹蒸馏 | 策略文本 |
| 逐实例改（Harness Scaling） | 当前任务 harness | 额外推理预算 | 不带状态 |
| **Harness²** | 当前任务 harness + 改进器 | 同任务行为对比 | 可执行 harness 树 + 带证据的经验 |

## 🏗️ 机制：两层递归

**任务级对比步。** 记执行记录 \(e=(\tau,y)\)（轨迹与交付物），一步改进写成

$$
(H',\ e',\ \xi) = \Phi(q_t,\ H,\ \mathcal{E};\ \mathcal{R}_t)
$$

其中 \(\mathcal{R}_t\) 是改进 harness，在整个任务内固定。三段：

- **Propose**：先采样参考执行 \(e_0\)。论文强调参考执行揭示的是「harness 怎么表现」，不是「交付物对不对」。按 invariant / domain 两个 scope 各提一份可执行候选，可复用库里的组件，但任务事实必须对照当前证据核实。
- **Probe**：候选在同模型同环境下跑同一任务，与参考对比，判断改动是缓解了目标缺陷、没影响、还是引入回归。作者明确说这种对比**用来指导合成，不是验证正确性**。
- **Compose**：读参考、候选、diff 与全部任务内证据，选择性地合并、调和冲突、只采一份或保持原样，然后执行合成结果，把决定和证据记进 \(\xi\)。

**并行 / 串行。** 并行借 RSA 的聚合思想，但操作对象是可执行 harness 及其行为后果：\(k\) 份参考执行、\(k\) 份 invariant + \(k\) 份 domain 候选组成池，\(k\) 个独立 Compose 会话各出一个后继；串行则把上一步 harness 与累积证据带进下一步。\(k=1\) 两者都退化为单个对比步。

**改进器级递归。** 任务结束后，Reflector 审完整改进记录 \(D_t\)，只保留被执行对比支撑的教训：

$$
\mathcal{R}_{t+1} = \mathrm{Update}(\mathcal{R}_t,\ H_t^\star,\ D_t)
$$

库按 benchmark 领域分目录，每条存**完整可执行的组件树**而不是散文摘要，外加 `EXPERIENCE.md` 记录适用情境、教训与证据，并有索引供按需翻阅。关键设计：下一个任务**从公共初始 harness \(H_0\) 出发**，旧组件只能经 Propose 被选择性复用，不自动继承。

**防作弊细节。** 改进会话拿到的是文件形式的证据目录，有一个 guard 拒绝交出任何含评分结果、rubric 或分数的目录；prompt 里也明确不许揣测「评分者想要什么」。无效树（skill 没有触发句、脚本不能编译、引用了没打包的 helper）重试一次，再失败就回退到起始树并记录。

## 🧪 关键证据

**WorkBuddy-Bench（Table 1，三次运行均值）。**

| 执行模型 + 初始 harness | Base 平均 | Meta-Harness† | Harness² \(k=1\) | \(k=5\) |
| --- | --- | --- | --- | --- |
| Gemini 3.5 Flash + OpenCode | 72.4 | 76.4 | **77.5** | 80.8 |
| Gemini 3.5 Flash + Codex | 74.5 | 73.3 | **77.5** | 80.4 |
| GLM-5 + OpenCode | 64.2 | 69.7 | **75.7** | 79.6 |
| GLM-5 + Codex | 64.4 | 74.2 | **75.3** | 78.3 |

†Meta-Harness 是在单独训练任务上离线搜出来的。分领域看，Gemini + OpenCode 在 \(k=5\) 时 Code 73.4 → 80.8、Web 69.9 → 78.3、Office 74.0 → 83.4，三个领域都超过最强基线。平均执行步数同时下降（如 Gemini + OpenCode 25.4 → 21.9）。

**JobBench / LAB（Table 2）。** Gemini + OpenCode：JobBench 31.5 → 36.0，LAB Partial 63.6 → 69.3；GLM-5 + OpenCode：LAB 59.6 → 71.4。唯一被反超的格子是 Gemini + Codex 的 LAB，Meta-Harness 领先。对照组也有意思：ReasoningBank 在 coding 上最多比 base 低 6.6；Harness Scaling 12 个基准与配置组合里有 7 个低于 base。

**弱模型吃得更多。** WorkBuddy 与 LAB 上 GLM-5 的绝对增益都大于 Gemini；GLM-5 改完 harness 后超过 Gemini 的原始 harness。JobBench 反过来，Gemini 涨得更多。

**预算与算力（Fig. 5/6）。** 并行与串行都随 \(k\) 单调上涨；两种递归在 \(k=2\) 就超过所有基线在 \(k=5\) 的结果。把执行与改进的 token 全算上，Harness² 两个配置都在经验 Pareto 前沿；Meta-Harness 花得比 \(k=5\) 还多，分数更低。

**消融（Table 3，Gemini + OpenCode，\(k=1\)）。** 去掉库：WB −3.1 / JobBench −1.8；去掉 scope 分工（换成两个泛化编辑器）：−2.9 / −3.7；去掉合成（只挑证据更好的那一份）：−1.6 / −1.9。

**改进库本身有没有用（Fig. 7）。** 不跑参考、不探针、不带库，直接让编辑器改 base harness：Code 73.4 → **63.2**、Web 69.9 → **65.0**，是掉分的。带 \(k=1\) 积累的库直接改，恢复到 base；带 \(k=5\) 积累的库，不再额外探针也能在 Code / Web / Office 上涨 0.9 / 4.4 / 5.1。JobBench 积累的库迁到 WorkBuddy 单步改，涨 0.6 / 0.5 / 2.9。

**不需要更强编辑器（Fig. 8）。** 执行者与编辑器用同一模型（OpenCode，\(k=2\)），从 GLM-5 到 Claude Opus 5 五个模型在所有基准上都涨；Opus 5 在 WB / JobBench / LAB 分别 +3.3 / +5.5 / +3.0，GLM-5 在 LAB +13.7。

**泼冷水。** 每个任务至少要跑参考 + 两份候选 + 合成结果四次执行，现实里有副作用的任务（发邮件、改线上系统）不能随便重跑，作者的设定默认「可以在有限预算内重跑当前任务」；三个基准的分数都依赖 LLM 裁判按 rubric 打分，增益里有多少是「更会写出裁判喜欢的交付物」没有单独拆；默认编辑器是 Opus 4.8，同模型实验缓解了这个顾虑但只跑了 \(k=2\)；库是简单索引，随规模增长后的合并、淘汰、过期经验修订都留给未来工作；作者也承认行为对比受执行随机性和共享模型偏差影响，不保证正确性。

## 🔬 最有意思的部分

1. **「没有标准答案」被换成「有对照组」。** 参考执行不是用来判对错，而是当对照；同一任务同一环境下的候选执行就是处理组。这是在没有 verifier 时最接近受控实验的东西，值得直接搬进任何在线 harness 改动流程。
2. **invariant 与 domain 分开提。** 消融里去掉 scope 分工比去掉合成伤得还重。把「agent 通用毛病」和「这个领域缺的知识」拆给两个编辑器，本质是在提案阶段就做了归因。
3. **不继承执行 harness，只继承改进经验。** 很多自进化系统直接把上次最好的 harness 带到下一题；Harness² 每题从 \(H_0\) 重新开始，把复用权交给 Propose。这正好回应了 [EvoHarnessBench](../../202609/week3/20260921_EvoHarnessBench_论文解读_脚手架越加越忘_非平稳性放进harness本身.md) 里「脚手架越加越忘」的问题。
4. **盲改比不改还差。** 无证据直接改 harness 在 Code 上掉 10 分，这是对「让模型自己反思一下改改 prompt」最直接的反证。
5. **案例很工程。** JobBench 一个制片任务 43.1 → 77.8：基线轨迹暴露的是流程失败（跨文件数字从不核对、写完不回读），invariant 改动加了一条 guardrail 和 `verify_outputs.py` 回读脚本（会检查公式单元格读出来是不是空），domain 改动加了一份排期、场地、人力、预算对账 skill 和数字格式的 tool guidance，Composer 四处改动全部保留。

## 🤔 我的判断

定位：**开放世界在线 harness 进化的协议 + 实证**，不是新模型也不是新基准，最大贡献是把「无监督时的证据来源」和「跨任务该存什么」讲清楚了。

亮点三条：

1. 对比探针把无标签任务上的改动决策落到同条件行为差异上，且每个合成决定都要绑定观察；
2. 两层递归里改进器在长、执行 harness 每次重置，避开了定制 harness 的跨任务污染；
3. 证据覆盖三个专业基准、两种执行模型、两种初始 harness，还做了同模型编辑、跨基准迁移和算力 Pareto。

问题与局限：重跑成本与有副作用任务的适用性；LLM 裁判打分下的增益归因；库管理尚未处理；selector 在 \(k>1\) 时本身也是一个无监督判断点。

对工程的直接启发：**(1)** 改 harness 前先固定一份参考执行当对照，候选必须在同条件下跑一次再决定合不合；**(2)** 提案按「通用 agent 缺陷」和「领域知识」两个 scope 分开写，合成时再调和；**(3)** 经验库存可执行的组件树加证据说明，不要只存散文教训；**(4)** 新任务从干净基线出发，让复用经过显式选择；**(5)** 给改进会话一个硬隔离：任何含评分、rubric 或分数的文件都不进它的工作目录。对 MMP 这类显式 Manifest 的 harness 来说，8 组件的文件级分解和 `EXPERIENCE.md` 几乎可以直接对齐到 Rules / Skills / Hooks 的版本化。

一句话收束：**没有裁判时别假装有裁判；把同任务的对照实验当证据，把改进过程本身当学习对象，harness 才能在开放世界里越改越会改。**
