# 深研别把协调和研究搅在一条链里：共享工作区加验证闸，让难题答对近翻倍

你有没有过这种体验：让 deep research agent 回答一道多跳题，它搜了几十轮、读了一堆网页，交互历史越拉越长；中途某一步把「卡特」认成「里根」，后面每一步都查得很认真、算得也对，最后答案却稳稳地错了。你翻日志才发现：**研究状态全埋在对话历史里，错误一旦进来，就被当成事实一路复用。**

UCLA 这篇 **PANINI-DR**（arXiv:2610.15208）把问题拆成两件事：一是把「整体调查的协调」和「单个子问题的研究与验证」分给不同 agent；二是用一块基于 Generative Semantic Workspace（GSW）的共享工作区，显式记录子问题、依赖、发现与证据，每条发现在被后续复用前先过一道 Verifier。看完我的感受：这是把「显式研究状态 + 发现入库前验证」这条思路做成了可执行协议，而且在同 backbone、同语料、同检索服务下，硬生生把 BrowseComp-Plus 拉开了 16 个点。

## 核心摘要

PANINI-DR 是一个多 agent 深研 harness：Orchestrator 统筹，Planner 先把问题写成 GSW 结构化计划（子问题是 blank，依赖构成 DAG，每个 blank 带期望答案类型和一条「验证声明」），harness 先做结构检查和有界修复；Researcher 领一个子问题，先做一次带已知发现代入的快速检索，失败再转 ReAct（20 轮上限），阅读工具用单独 Reader 抽取引文；Verifier 结合确定性检查（类型、证据附件）与 LLM 判断，要求「证据支持该答案」且「能把它和其他候选区分开」两条都成立才放行，失败就带反馈让 Researcher 重查（默认最多 5 次）；被接纳的发现填回工作区，驱动下游子问题与代码计算。所有系统统一用 gpt-oss-120b、同一冻结语料和检索服务对比七个 SOTA harness，PANINI-DR 在 BrowseComp-Plus（CF-150）拿到 **73.3%**，比次优的 SLEUTH 高 **16.0** 点；hard 组 **52% vs 28%**，接近翻倍；三基准均值 **69.1** 最高。反直觉的一点是：它在 MoNaCo 官方 F1 只排第五，但作者提出的 **observed support**（只有答案能从保存证据里还原才给分）在三个基准上全部领先，均值 **60.9 vs 49.6**，「靠记忆蒙对」被剔掉后优势反而更大。真正价值在于把深研的状态与验证做成了可审计的数据结构，而不是一份越写越长的研究报告。

## 🎯 为什么这件事值得写

ReAct 式单 agent 把「决定查什么、调工具、推理」全塞进一条增长的交互历史，研究状态是隐式的。历史一长，lost in the middle、context rot 就来了；更要命的是子问题之间有依赖，**一个中间错误会被下游老老实实地放大**。

| 路线 | 状态放在哪 | 验证 | 痛点 |
| --- | --- | --- | --- |
| ReAct / CodeAct | 交互历史 | 无或末端 | 状态隐式，错误传播 |
| IterResearch / Re-TRAC | 演化报告 / 压缩轨迹 | 弱 | 散文笔记难对齐子问题 |
| SLEUTH / Omni-Decision | 事实、假设、证据需求 | 有检查的更新 | 没把审查绑到子问题声明 |
| **PANINI-DR** | GSW 计划 + 节点级研究记录 | 子问题级 Verifier + 确定性检查 | 计算成本高 |

这和 [ReHarness](./20261012_ReHarness_论文解读_反思写进记忆就不再改_反向修订让harness状态也能吃到下游反馈.md) 关心「harness 状态能不能被下游反馈修订」、[DerivAudit](../week1/20261001_DerivAudit_论文解读_记忆不是摘抄是推导_分布式证据悖论卡死写入闸.md) 关心「记忆写入闸」是同一条主线：**状态要显式，写进去之前要过闸。** PANINI-DR 的切口是深研场景里的子问题粒度。

## 🏗️ 机制：计划 DAG + 节点记录 + 子问题级验证

工作区写成：

$$
W_t = (P_t, S_t)
$$

$P_t$ 是 GSW 计划（实体、角色、关系、计算），$S_t$ 是挂在每个节点上的研究记录（发现、证据、审查状态）。初始 $W_0$ 里所有 blank 都是 unresolved。

**Planner（一次）。** 把问题写成 DAG：节点是子问题与最终目标 $v^\star$，边 $u\to v$ 表示 $u$ 的发现是解 $v$ 的输入。每个 blank 带三样东西：自然语言检索提示（如「When was [wife] born?」，占位符在上游确定后替换）、期望答案类型（如 date）、验证声明（如「该日期是 [wife] 的出生日期」）。启动前检查无效引用、目标缺失或多个、环依赖、提示与依赖不一致，有界修复。

**Researcher。** 先做一次快速检索 + 候选提议；不过关再进 ReAct，保留已有候选、来源与反馈。没解完的子问题会保存候选、来源、历史搜索和验证反馈，下次分配时接着做。发现计划缺一步时，可以把「建议新增子问题 + 理由」交回 Orchestrator，由 Planner 修订计划并重开受影响的发现。

**Verifier。** 先确定性检查类型与证据附件，再由 LLM 判断两件事：引证是否支持该答案、是否能区分它和合理替代项。两者都通过才 endorse；否则返回「缺什么支持、哪里有歧义」。不同 Researcher 的提议可并行审。

**计算与收尾。** 计划里的计算节点在输入齐备后用代码执行（Camp David 例子里 1927-08-18 与 1978-09-17 算出 51 岁）；预算耗尽仍无答案时，可用一次不再搜索的 Finalizer 从已收集证据合成。

## 🧪 关键证据

**主结果（Table 1，gpt-oss-120b 统一 backbone）。**

| 方法 | BCP Hard | BCP Overall | FRAMES | MoNaCo F1 | Avg. |
| --- | --- | --- | --- | --- | --- |
| Open Deep Search | 28 | 53.3 | 76.0 | 0.571 | 62.1 |
| IterResearch | 20 | 54.7 | 70.5 | 0.564 | 60.5 |
| SLEUTH | 28 | 57.3 | 77.2 | 0.556 | 63.4 |
| HyMem | 12 | 48.7 | 70.8 | **0.612** | 60.2 |
| **PANINI-DR** | **52** | **73.3** | **79.1** | 0.549 | **69.1** |

三次重复下 PANINI-DR BCP 平均 72.7%，SLEUTH 与 Open Deep Search 都是 58.0%，领先 14.7 点。

**Observed support（Table 2）。** 只保留能从保存证据中还原的答案分：PANINI-DR BCP **70.7** / FRAMES **66.1** / MoNaCo **0.458**，均值 60.9；SLEUTH 为 54.0 / 55.2 / 0.396，均值 49.6。官方分到 Obs. 的落差，PANINI-DR 在 FRAMES 是 79.1→66.1，HyMem 是 70.8→36.7。

**消融。**

| 对照 | 设置 | BCP |
| --- | --- | --- |
| 规划/状态（Table 11） | OFF 散文笔记 → ON 计划+节点发现+修订 | 41.3 → 58.0；同样加恢复后 56.7 → 73.3 |
| 验证（Table 12） | 去掉 LLM 审查与证据附件检查 → 完整验证 | 57.3 → 73.3（Obs. 54.7 → 70.7） |
| 重试上限（Table 13） | cap 1 / 2 / 5 / 10 | 67.3 / 72.0 / 73.3 / 66.0 |

ON 臂 hard 题答对数从 10 翻到 20；新发现实体被后续搜索复用的比例 77.4% vs 32.1%。验证在 FRAMES 200 题子集上 69.5→79.5、MoNaCo 0.517→0.583。

**泼冷水。** prompt token 是 SLEUTH 的 19.2 倍，算上 vLLM 前缀缓存（66.5% 输入命中）估算计算量仍是 7.3 倍；只测了一个 backbone、冻结语料，开放 web 未验证；Verifier 与 claim-support 审计都依赖模型判断。

## 🔬 最有意思的部分

1. **等算力堆票不顶用。** 让 SLEUTH 每题跑 8 次取多数，用掉 1.12 倍 PANINI-DR 的计算，BCP 也只到 64.7%，仍低 8.6 点。**结构化状态不是「多跑几遍」能替代的。**
2. **验证次数不是越多越好。** cap 10 把 warned finding 降到 0，准确率却掉到 66.0%；cap 5 才是甜点。验证要有界，不然 Researcher 会被反复拒绝拖进死胡同。
3. **被拒后再通过的提议，大多真改了东西。** 101 条「先被拒、后被 endorse」的提议里 77 条换了答案或引证集合（40 条换值、37 条换证据），说明反馈是在驱动补证据，而不是换个说法蒙混过关。
4. **找到来源只是第一步。** 直接把标注文档喂给同一 backbone，BCP 到 93.3%、hard 45/50，而 PANINI-DR 是 26/50；还有 17 道题 PANINI-DR 其实找齐了所有标注文档却答错。瓶颈在「把事实一直绑在正确子问题上直到提交」。
5. **MoNaCo 的取舍很诚实。** 集合题上精度 0.690 最高，但召回 0.462 低于 HyMem 的 0.566，F1 因此排第五；换成 observed support 后又回到第一。

## 🤔 我的判断

定位：**深研 harness 的工程方法突破 + 评测口径补丁**。核心不是 GSW 这个表示本身，而是「typed 子问题分配 → 子问题级审查 → 准入后的值驱动下游」这套执行协议。

亮点三条：

1. 同 backbone、同语料、同检索下 BCP +16 点、hard 近翻倍，并经三次重复与去除 SLEUTH 超长拒答题后仍成立；
2. 规划/状态、验证、重试上限三组消融干净，且都同时报官方分与 observed support；
3. observed support 把「答对」和「有证据地答对」分开，给深研 eval 加了一条该有的 gate。

问题与局限：计算成本高（7.3 倍估算计算）；单 backbone、冻结语料；计划没覆盖的步骤，子问题级验证无从兜底；observed support 依赖各系统证据格式，claim-support 审计仍是 LLM 判断。

对工程的直接启发：**(1)** 深研状态写成「子问题 + 依赖 + 节点记录」的结构，别只留散文笔记；**(2)** 每个子问题在计划阶段就写好期望类型和验证声明，让 Verifier 有可检查的靶子；**(3)** 验证放在「发现被复用之前」，重试设上限；**(4)** 评测时加一列「答案能否从保存证据还原」，和 [GraphForge](../week1/20261002_GraphForge_论文解读_真文件证据图才同时钉死任务和Rubric.md) 的证据图思路一样，把蒙对的分剔掉；**(5)** 和 [LLM-as-Judge](../../202609/week3/20260917_LLM-as-Judge_论文解读_裁判只是评测栈的一层如何搭闭环.md) 的分层栈对齐：确定性检查在前，LLM Verifier 在后。

一句话收束：**PANINI-DR 证明，深研要赢在难题上，靠的不是更长的历史或更多的独立重跑，而是把研究状态写成可验证的结构，让每条发现过闸之后才去指挥下一步。**
