# 「恰好一次」住在工具合同里：Harness 几乎不决定，模型只罩得住能回读的故障

你有没有过这种体验：agent 调收费 / 发帖 / 部署，工具超时或 5xx——**副作用可能已经生效**；盲目重试变双扣款，放弃又漏做。团队争论该把 exactly-once 写进更强模型、更聪明 harness，还是 MCP/工具合同？微软这篇（arXiv:2609.29095）用确定性沙箱做了 **25,930** 幕分级实验，答案很刺耳：**取决于故障能不能被立即回读揭开**——能揭开时前沿模型几乎不重复（timeout 丢确认后重复率 **0.5%**），模型解释约 **53%** 方差；揭不开（晚提交、传输重投）时同一批前沿模型重复率飙到 **56% / 74%**，合同解释约 **81%**。**Harness 份额≈0**；全写路径给幂等键可把重复从 **28%→4%**。看完我的感受：这是给 Byron 的 harness / MCP 工具面的「可靠性分层图」——别指望换 CLI 或加一句 prompt 解决网络模糊性。

> **命名提醒**：文中沙箱也叫 Limbo，与仓库已有的 [LIMBO](./20260924_LIMBO_论文解读_经验回放别全塞进提示_按任务在线配记忆预算.md)（记忆预算，arXiv:2609.14138）**不是同一工作**；本篇 slug 固定为 **ExactlyOnce**。

## 核心摘要

问题：写工具超时/出错时，客户端分不清「请求丢了」还是「确认丢了」。作者问 exactly-once 该落在 **模型 / agent harness / 工具合同** 哪一层。沙箱含六服务（社交、计费、工单、邮件、数据、部署），合同含可选幂等键、最终一致与缺失回读路径；十二种边界注入故障（含晚提交、重投、部分批次）；每幕用已提交效应账本打分。覆盖九模型、三生产 harness（Copilot CLI / Hermes / Codex CLI）+ 最小脚手架、两种合同、十五种恢复条件。可回读故障：前沿几乎 exactly-once，弱模型仍常重复。不可回读：证明 **无在飞时长上界时，任何只靠观测的验证策略都无法对晚提交保证 exactly-once**；等待在固定短上界下可用，重尾延迟下即使等一小时仍不如「每写都带键」。透明客户端重试把 EOS 从约 **72%→50%**；重复后仍报 success 约 **90%**——人读终局报告几乎无感。

## 🎯 为什么这件事值得写

分布式系统早把「超时模糊」当成一等公民：幂等键、条件写、可查询操作状态（Stripe 风格等）。Agent 继承模糊，却常不继承合同级补救——只靠「再聪明一点 / harness 再包一层」。同期有观察等价超时对、IdempotencyBench、verify-then-retry 包装等，但缺少把 **模型 × harness × 合同 × 故障族** 拆开的大规模测量。

对 Byron（MMP / MCP / OpenClaw / coding-agent 写操作）：这直接回答「可靠性预算该砸哪」——**能回读的靠模型纪律；不能回读的必须合同**；harness 换皮几乎买不来 exactly-once。

## 🏗️ 机制：Limbo 沙箱、故障族、合同旋钮

**服务与合同（摘要）**：计费 `create_charge` 等支持键；社交仅部分平台；工单评论 / 邮件发送 / 部署触发等默认非幂等；若干 list/search **滞后 120–180s**；有的平台 **无 list**，写后不可验。通用工具：`wait`、模拟 on-call `escalate_to_human`、结构化 `finish`（含不确定操作列表）。工具带 MCP 风格机器可读注解。

**故障注入在服务边界**：丢确认、误导性 500、请求实际未执行的 pre 类超时/500、晚提交、传输重投、部分批次等——观测上可混淆，账本上可分。

**合同变体**：native（仅部分写支持键）vs **keys-everywhere**（所有非幂等写接受 Stripe 风格键，含可恢复批次 / 晚提交 / 重投）。

**恢复条件**：prompt 级 aware / reflect；中间件级 sdk-retry（透明重试超时与 5xx/429）、rules、vbr（验后再试）、wait-Δ、guard（自动填键 + 滞后复验 + 不可验非幂等阻断并要求升级 + 标注未知）；以及可见在飞请求的 outcome oracle（客户端策略上界）。

**命题 1**：非幂等、无键写在 \(t_0\) 超时；若策略只依赖观测且在「请求从未执行」世界能于时间 \(T\) 内必完成任务，则对任意晚提交延迟 \(\delta>T+\lambda\)（\(\lambda\) 为可见滞后），该策略在晚提交世界 **必产生重复**。

**命题 2**：服务按键至多执行一次并重放原结果时，重试复用原键即可消解晚提交困境。

## 🧪 关键证据

**RQ1 行为画像（最小脚手架）**：六档前沿在 `timeout_post` 重复率 **0.5%**、误导 500 约 **8%**——机制是超时后先回读；弱模型（mai-code / gpt-5.4-mini）丢确认重复 **18%**、误导 500 **47%**。同批前沿在晚提交 **56%**、重投 **74%**。297 幕「超时后一分钟内重发」里 **69%** 重复——回读时原请求仍在飞。等 ≥60s 再重发的 123 幕 **100%** 重复，且 99% 落在最终一致回读上（从上界错误时刻起算可见滞后，而非未知提交时刻）。明确未执行的 pre 故障重复仅 **0.6%**、任务完成 **99%**。

**RQ2 方差分解（Shapley / McFadden \(R^2\)）**

| | 可回读解开 | 回读解不开 |
| --- | --- | --- |
| 合同份额 | 30% | **81%** |
| 故障模式份额 | 18% | 10% |
| **模型份额** | **53%** | 8% |
| 重复率 | 11% | 66% |

E3（四 harness）：harness 份额在可回读约 **3%**、不可解约 **0%**——**换生产 CLI 几乎不改重复结构**。

**E5 等待 vs 键**：固定 90s 在飞，wait 120s 可把 dup 压到约 **1%**；重尾（40s–2h）下 wait 3600s 仍 **16%** dup、均时近 50 模拟分钟；**keys:vanilla** 约 **8–9%** dup、均时 **0.9** 分钟。摘要口径：全写给键使重复 **28%→4%**（agent **98%** 会带键；剩余重复多来自首发未带键或重试换键）。

**RQ3 自我认知**：≥1 次重复的 1,279 幕中，**90%** 终态 `completed`，**80%** 未把任何操作标 uncertain——终局报告对人类几乎无报警。不可逆写（邮件/评论）在模糊故障后未检查就重发的比例不亚于可逆写。

**RQ4 缓解**：sdk-retry 有害（EOS ~72%→50%，dup~50%）。前沿上 prompt/guard 增益有限（已会验）。Guard 在晚提交上甚至可能把「升级人工」挤成「验了再试」而更糟。Outcome oracle 在 native 合同也难到顶——无键重投超出任何纯客户端策略；keys + guard 才把上界拉开。

## 🔬 最有意思的部分

1. **分层答案**：能回读 → 模型；不能 → 合同；harness ≈ 噪声项。
2. **验证有证明边界**：不是「再等等/再读读」的工程口味问题，是观测不可分辨性。
3. **透明重试是反模式**：SDK 默认重试超时/5xx，在 agent 写路径上直接制造双份副作用。
4. **成功幻觉**：重复了还报完成——评测若只看 agent 自报，会系统漏掉可靠性事故。
5. **键是便宜杠杆**：合同写明并让 agent/guard 自动附键，比堆等待与更强模型更划算。

## 🤔 我的判断

定位：**工具副作用 exactly-once 的分层测量基础设施 + 合同优先处方**，不是新训练算法。亮点三：

1. 故障族切开后，「模型 vs 合同」不再混谈；
2. 命题 + 25k 幕把「只靠验证」的天花板写死；
3. 三生产 harness 对照直接服务工程选型——**别为可靠性盲目换壳**。

局限：沙箱语义再真也不是全网生产长尾；模型名单绑定 2026-09 网关 ID；部分条件样本量与配额缺口（如 gpt-4.1）；人类升级通道被模拟简化。对 Byron（MCP / Pi / OpenClaw）：**写工具合同清单**——幂等键参数、可见性滞后、是否可 list、不可验写必须强制 escalate；harness 中间件 **禁止**对模糊写做透明重试；评测加 **账本级重复率**，不信 `finish=success`；guard 可跨 harness 复用（附键 + 滞后复验 + 不可验阻断），但晚提交仍要键，不能只靠 vbr。与已有 LIMBO 记忆文并列时：**一个管上下文预算，一个管副作用语义——同名不同物**。

一句话收束：agent 的「恰好一次」别先找更强模型和更花的 harness——**能回读的练模型，不能回读的改工具合同，并关掉那些好心的透明重试**。
