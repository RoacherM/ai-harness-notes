# 预算够了仍忘：写时后悔才是常驻记忆的瓶颈，不是窗口太小

你有没有过这种体验：agent 跑长任务时每步把历史压成固定长度 summary（MemGPT / 递归摘要 / 信念槽），上下文永远便宜，但刀在抽屉里——四步之后要切片胡萝卜时，状态里早就丢了；你加大预算到 128/256 token，oracle 装得下事实几乎通关，LM writer 却最多赢约 17%。ICLR 2027 投稿 DSSR（arXiv:2609.32805）把损失拆成 **budget loss**（任何同尺寸状态都得付）与 **write-time regret**（writer 在不知道未来时选错了放什么），并证明在可控 relevance lag 下，瓶颈几乎全是后者。看完我的感受：这和 Byron 盯的 **long-horizon memory / JITMem / MutableTranscripts** 正对——[JITMem](../week4/20260925_JITMem_论文解读_记忆别在写入时裁剪_读时按任务现场策展同一条轨迹能榨出不同课.md) 主张读时策展，DSSR 量化 **写时承诺** 有多痛，以及训练 writer 能救多远。

## 核心摘要

常驻上下文 agent：writer \(U\) 每步把状态重写为 \(\le B\) token 的 \(z_t\)，丢弃原始历史；冻结 reader \(\pi\) 只看 \((g,z_t,o_t)\) 决策。作者用 TextWorld 烹饪游戏控制「事实出现 → 需要它」的 lag \(\ell\)，并验证 filler 步只有在**不再重现该事实**时才算真延迟。分解显示：128-token 真值状态几乎全胜，五种仿照现有记忆系统的 prompt writer 成功率 ≤17%，且 write-time regret 随 lag 增长。DSSR 用 **前向滚动充分性分数** 给候选状态打分——让冻结 reader 在 writer 真会如何续写的轨迹上看几步决策，再 DPO 偏好训练 writer；该分数与结局相关 \(\rho=0.48\)，而「候选 + 原始后续当固定上下文」的 hindsight 打分 \(\rho\le 0.07\)。预注册测试集：短 lag 上训练带来 **+7.0 [+1.9, +12.2]** 成功率，逼近 belief/slot 提示；长 lag 增益消失，预注册检验失败——根因是逐步分数看不见「现在留下的事实必须在后续每次 rewrite 都保住」。匿名代码：https://anonymous.4open.science/r/AgentDSSR。

## 🎯 为什么这件事值得写

长程 agent 的记忆方案分成两派（文中 Figure 1）：

- **读时压缩**：保留全文，query 已知后再压（retrieval / prompt compression）——信息不先死。
- **写时压缩**：每步承诺一个固定状态，历史丢弃——便宜、可部署，但不可逆。

业界大量「运行摘要 / mental model / slot memory」落在写时一侧，却常用任务成功率一个数评价，分不清是预算不够还是 writer 选错。DSSR 的贡献首先是 **测量协议**：用 hindsight 同预算 oracle 分离 \(\beta\)（budget loss）与 \(\kappa\)（write-time regret），再用可控 lag 证明痛点在 \(\kappa\)。这对 harness 设计是冷水：别先加窗口或加 embedding 库，先问你的 writer 是不是在用未来才知道的需求做选择。

## 🏗️ 机制：损失分解 × 真延迟协议 × 前向滚动打分 × DSSR 训练

**损失分解。** 决策点 \(t\) 上，用 reader 对最优动作 \(a_t^*\) 的 NLL 定义 sufficiency gap；read-time oracle \(z_t^{\mathrm{rt}}\) = 同预算下对全文一次压缩并按 NLL 选优的样本。则  
\(\delta = \beta + \kappa\)：\(\beta\) 是相对全文的预算代价，\(\kappa\) 是实际 writer 状态相对 oracle 的额外损失。

**真延迟协议。** 在事实与使用之间插入 walk 时，若中间 observation 再次暴露该事实，lag 被「刷新」——作者专门用 pilot 验证协议，避免假延迟。这是测量可信的关键细节。

**DSSR 打分。** 写步骤上采样多个候选 \(z\)；对每个候选，**让当前 writer 继续向前滚** \(K\) 步，用冻结 reader 的决策损失聚合为分数；再 DPO（+ 选中样本似然项）更新 writer。关键对比：把候选当固定上下文、后接真实 raw steps 的 hindsight 打分几乎不预测结局——因为状态价值取决于 writer **以后还会从中扔掉什么**。

**训练与评测纪律。** Reader 行为克隆 + DAgger 后冻结；测试集预注册、只开一次；多级 gate（G1/G2…）在数据产生前写好——对 memory 论文少见的诚实实验文化。

## 🧪 关键证据

**预算不是瓶颈。** 验证网格：真值 128-token 状态近乎全胜；LM writers（自由摘要 / belief+置信 / 固定槽 / 手写保留指南等）成功率上限约 17%；\(\kappa\) 随 measured lag 从约 0.61（短）爬到 1.87–2.30（\(\ell\ge10\)），全文损失保持低位。

**打分形式决定能否学。** 前向滚动充分性 \(\rho=0.48\)（延迟协议下 0.26）；固定上下文 hindsight \(\rho\le0.07\)。训练信号必须模拟「状态还要被同一 writer 继续糟蹋」。

**预注册测试。** \(B=128\)、90 局测试：零 lag 上训练 writer 10.4% vs 提示 SUMMARY 3.3%，**+7.0 [+1.9, +12.2]**，达到 belief/slot 提示水平；随 lag 增大增益收缩，长延迟预注册门全灭。手写「该留什么」规则在各 lag 都更好——但用了 writer 训练时没有的任务知识。

**极限诊断。** 逐步分数无法给「跨多次 rewrite 的保留」正确信用；best−worst 候选差距随延迟变薄。作者建议课程（短→长 lag）或允许 reader 回要事实等出路。

## 🔬 最有意思的部分

1. **Write-time vs read-time 是架构分岔，不是程度差。** 和 [JITMem](../week4/20260925_JITMem_论文解读_记忆别在写入时裁剪_读时按任务现场策展同一条轨迹能榨出不同课.md) 对读：JITMem 站读时策展；DSSR 量写时承诺的税。生产上两者可并存——热路径常驻短状态，冷路径保留可回放轨迹。
2. **「假延迟」陷阱。** 插入无关步却在 observation 里重晒事实 = 没测到记忆。搭 memory bench 的人应抄这个协议卫生检查。
3. **Hindsight 打分失效。** 很多「用未来损失训压缩器」的直觉默认固定后续；在递归 writer 下，必须把未来压缩行为滚进去——否则 \(\rho\) 塌掉。
4. **预注册与诚实失败。** 长 lag 训不动被写进结论，而不是藏起来——对 harness 评测文化是正面样本。
5. **手写规则仍赢** 说明：任务知识（留刀位置、留食材状态）在结构上强于盲训 writer；工程上「schema 化必留槽」可能比端到端 DPO 更稳——对齐 slot/belief 提示的胜利。

## 🤔 我的判断

定位：**常驻上下文 agent 的测量基础设施 + 有限的 writer 训练修复**（分解 write-time regret、验证 lag 协议、前向滚动打分）。亮点三：

1. 把「忘了」从笼统失败拆成预算 vs 写时选择，并证明后者主导；
2. 打分形式的消融（滚动 vs hindsight）直接可迁移到记忆训练管线；
3. 预注册纪律与长 lag 失败诊断，避免过度宣称。

局限：环境是 TextWorld 烹饪、模型约 4B 级；在线成功率绝对值仍低；长延迟信用分配未解；匿名仓待转正。对 Byron：  
- 若 harness 用运行摘要当唯一记忆——**默认有 write-time regret 税**，长依赖事实应进可检索/可回放存储（读时路径），或强制 schema 槽（刀/文件路径/API 句柄）。  
- 训 memory writer 时，用「writer 自滚后续」打分，别用「候选+真实未来」偷懒。  
- 和 [MutableTranscripts](../week4/20260928_MutableTranscripts_论文解读_对话别只追加纠错_把历史改成可编辑状态剪掉上下文污染.md) 合读：可编辑历史是另一条减污路径；DSSR 提醒「编辑/重写」每一步都在交不可逆税。  
- 与 vectorize-io/hindsight 一类 retain/recall/reflect 对照：reflect 若仍是写时压缩，就要量 \(\kappa\)，不能只报 LongMemEval 总分。

一句话收束：**窗口够大也救不了选错要留的事实**——先量 write-time regret，再决定是训 writer、加槽位，还是干脆别在写时把历史扔掉。
