# 还没跑轨迹也能攒技能库：Code2Skill 从两万仓库榨出百万条可验证技能

你有没有过这种体验：agent 技能库要么等自己跑轨迹再蒸馏（冷启动慢、绑死当时的模型/工具/harness），要么从文档/wiki 抽（难验证、易空话）。GitHub 上已经躺着被调试过无数次的过程知识——能不能**不跑 agent 轨迹**，直接从源码长出可检索、可验证的 skill？Ant International 这篇 Code2Skill（arXiv:2609.05571；亦见 2026-09-21 HF Daily Papers）给的答案是一整条自动管线 + **CodeSkillBank**：**19,769** 活跃高星仓 → **1,006,822** 条接受记录。看完我的感受是：它把「技能合成」从经验回放扩成**代码资产复用**，和轨迹银行、文档技能形成第三极——对 Byron 这种 skills/harness 取向，冷启动与规模化价值都很实。

## 核心摘要

Code2Skill 将选中的代码单元提升为锚定实现的三类技能记录：**atomic-operation / composite-workflow / recurring-pattern**，字段覆盖适用条件、步骤、不变量、失败路径、反目标与源证据。验证两段式：**source-body-blind reconstruction**（只看技能、不见源码体，重建实现）→ **source-aware comparison**（对照原码过滤未支撑/不完整记录）。规模：对 **19,769** 仓跑通后得到 CodeSkillBank **1,006,822** 条带 workflow / boundary / provenance / evidence 元数据的接受记录。下游：**72** 组协议匹配评测（九模型设定 × 八基准），相对无技能基线宏均 **42.90→47.90**（相对 **+11.7%**），**57/72** 组提升；统一接口下对七个共享基准平均 **49.5**，轨迹侧 Trace2Skill / ExpeL / SkillRL-Bank 为 **31.0 / 27.9 / 32.8**，即便「每基准取三者最优」的 oracle 也只到 **40.1**（低 **9.5** 分）。插入点：planning-time **8/8** 评测全涨；post-generation review 覆盖最广（Table 1 主表）；summary 渲染在 \(k=3\) 把技能上下文从 **6,352→707** 字符（**−88.9%**）且不伤甚至抬分。另：测过的 AI 生成代码抽出的技能通过率 **93.50%** vs 人类代码 **93.00%**——管线可随 AI 写码继续扩库。

## 🎯 轨迹银行与文档技能各缺一角

论文把既有技能合成钉在两类局限：

1. **Trajectory-based**：从成功/失败轨迹蒸馏——与产生它们的环境、模型、工具、harness 强耦合；组件一换，旧技能易失效；质量受生成 agent 能力上限约束。
2. **Document-based**：从人类可读文本抽——不依赖交互，但缺少可执行证据，难做 grounding / verification。

源码被选为第三基底：天生可执行、可测、可版本化；GitHub 已积累大量「实现过、修过、复用过」的过程。挑战是真实代码交织框架胶水、项目私有标识、隐式依赖与未决边界——金牌技能必须回答：**何时适用、哪些步骤必要、哪些不变量、哪些失败改路径、哪些泛化越界**，并在抽象后仍留足够证据可验。

## 🏗️ 管线：排序 → 分型抽取 → 盲重建 → 留证入库

Figure 1 四段：

1. **AST/解析 + 全局排序**：\(R(u)=W\cdot\Phi(u)-P(u)\) 对函数/方法/类等源单元打分，Top-K 选出可复用过程密度高的单元。
2. **分型写卡**：atomic（单函数级操作）、composite（跨操作工作流）、recurring-pattern（更高层重复结构）；产出含适用性、步骤、约束、失败、证据的 operational card。
3. **验证**：LLM **不见源码体**仅凭技能重建实现；source-aware judge 对比重建与原文，拒绝或送审未支撑记录。
4. **组织**：接受记录进 provenance-rich archive，并做 feature / purpose 索引供检索。

银行侧：purpose-level 卡片里 atomic-only 约 **65.35%**（490,457）、composite-only **31.12%**（233,549）；多步过程约占 **57.3%**；agent 相关性标注里 code generation **69.1%**、SWE-agent **58.3%**、tool use **41.8%**。人工抽检摘要：接受库技能描述准确率约 **92%**，直接接受记录中约 **84%** 亦支持等价重建叙事——强调「不是表面 API 查找表」。

默认下游 harness：draft → review → revise 式 agentic loop；技能在预定阶段检索注入；协议匹配对照只改「有无技能」，其余（模型、推理模式、题集、评测器、loop）固定。主实验检索为效率起见随机采样银行约 **10%** 记录。

## 🧪 主证据：宏均 +11.7%，且打赢轨迹 oracle

### RQ1：固定 loop 上普遍涨

八基准：SWE-bench Verified、BigCodeBench、AIME 2026、HMMT 2025、GPQA、TerminalBench、LongCLI-Bench、AgentBench-OS；模型含 DS4-Flash、Qwen3.5/3.6 27B、Gemini 2.5 Pro、GPT 5.2 等。Table 1：**57/72** 组提升；每模型×推理模式的八基准均分涨 **2.26–7.39** 点（相对 **6.0%–20.7%**）；SWE-bench Verified **九组全涨**。宏均叙事 **42.90→47.90（+11.7%）**。短题 BigCodeBench 在部分 reasoning 设定下收益更混——能力够强、步骤短时，技能边际小。

### RQ2：同一接口下碾压轨迹银行

用 DS4-Flash reasoning、同一 loop，对七共享基准（Table 2，五 run 均值）：

| Method | SWE | BigCode | AIME | HMMT | Terminal | LongCLI | AgentBench | 均分（文中） |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Trace2Skill | 6.0 | 31.9 | 63.3 | 46.7 | 6.9 | 18.8 | 43.1 | 31.0 |
| ExpeL | 7.5 | 29.4 | 50.0 | 20.0 | 22.2 | 18.8 | 47.4 | 27.9 |
| SkillRL-Bank | 36.8 | 29.4 | 43.3 | 26.7 | 31.9 | 10.4 | 51.2 | 32.8 |
| **Code2Skill** | **44.7** | **42.3** | **70.0** | **53.3** | **45.2** | **30.0** | **61.3** | **49.5** |

逐基准取轨迹三者最优再平均仅 **40.1**，仍低 Code2Skill **9.5** 分；单基准领先幅度约 **6.6–13.3** 分。洞察：增益不只来自「有个 review loop」，而是**代码挖出的银行本身更有用**——且在 agent 自己攒够交互经验之前就能供油。

### RQ3：插在哪——规划与复盘最香

- **Planning-time**：Figure 5，DS4-Flash / Qwen3.5 × 四基准，**8/8 全涨**（分解任务前就能约束计划）。
- **Generation-time**：Figure 4，DS4 四基准都涨（AIME/Terminal 很大），Qwen 更不稳定——要在形成计划前直接吞指导，更难点菜。
- **Post-generation critique**：对应 Table 1 主设定，覆盖最广，**57/72** 改善。

技能的计算角色随插入点变：规划时约束分解、复盘时给候选打检查单；首遍生成则要求模型把同一指导直接译成完整答案。

### RQ4：少露字比多捞条更划算

BigCodeBench Instruct-Hard 上 \(k\in\{1,3,10\}\)：\(k:1\to10\) 平均渲染从约 **2.1K→17.8K** 字符，效用增加有限。**Summary @ \(k=3\)**：技能上下文 **6,352→707** 字符（**−88.9%**）；Qwen 持平满分记录，DS4-Flash **28.40→31.80**。Purpose indexing 略减满记录上下文（约 **6.4K→5.0K**），pass 效应混杂。工程启示：**先压渲染，再堆 retrieval depth。**

### AI 源码几乎同样可挖

同源匹配评测：人类实现技能 pass **93.00%**，AI 生成且测过的实现 **93.50%**（Figure 7）——管线不排斥 AI 写码扩库，和「仓库供给持续增长」叙事一致。

## 🔬 最有意思的部分：验证当过滤器，不是测试替代

作者强调 reconstruction consistency **不是**单元测试替代，而是仓库级可扩展过滤器：问的是「技能是否被源实现支撑」，不是「行为在所有输入上正确」。这和 [LLM-as-Judge](./20260917_LLM-as-Judge_论文解读_裁判只是评测栈的一层如何搭闭环.md) 栈分层一致——盲重建 + 源感知比较 ≈ 可自动化的 grounding 门禁；真要行为正确性，仍需测试/属性基方法（相关工作已点出）。

与 [Subagents-vs-Skills](./20260921_Subagents-vs-Skills_论文解读_技能该塞进主上下文还是开子代理.md) 对照：Code2Skill 解决**内容从哪来、如何验**；微软剑桥文解决**验过的包用 agent-skill 还是 subagent 执行**。与 [EvoHarnessBench](./20260921_EvoHarnessBench_论文解读_脚手架越加越忘_非平稳性放进harness本身.md) 连读：银行膨胀会带来 engagement / forgetting 压力——Code2Skill 的 purpose 索引与 summary 渲染，正是「库越大越要检索与呈现策略」的工程答案。

## 🤔 我的判断

定位：**技能合成的新基底（代码）+ 可验证规模化管线 + 百万级银行**，方法论文与资源论文各半。亮点三：

1. 冷启动：不依赖本 agent 轨迹，却在七基准上系统性打赢轨迹银行乃至其 oracle；
2. 验证闭环：盲重建 + 源感知比较，把「文档幻觉技能」挡在门外；
3. 插入点与渲染消融可直接搬进产品——planning/review 优先，summary @ \(k=3\) 先砍九成上下文。

局限与代价：主表检索只用约 **10%** 银行，全量效果未完全展开；重建等价≠测试完备；仓库选择（>500 stars 等）有偏；跨语言/私有仓/非代码过程知识外推未知；与特定 agent harness 的工具schema对齐仍要工程层适配。对 Byron：若 Wayne-Skills / harness-dojo 要「先有库再谈进化」，Code2Skill 是离线灌库候选；灌完务必接 EvoHarnessBench 式 engagement/BWT 监测，并按 Subagents 文给契约化包选执行模态——**挖得到、验得过、调得动、测得住**，才是完整技能供应链。

一句话收束：轨迹蒸馏回答「我做过什么」，Code2Skill 回答「人类与 AI 已经写进仓库、可被重建验证的过程是什么」——agent 智能的下一档扩展，不必只等自己再跑一轮 episode。
