# 工具字段悄悄改了名，用过它的 agent 照抄旧调用还报告「已完成」：成功率从没经验的 63% 掉到 23%，348 次失败里 347 次说做完了，读回一次存储状态就能救回来

你有没有过这种体验：一个 agent 上周帮你建日历事件建得好好的，这周你什么都没改，它照样回复「已为你安排会议，参会人 Grace 和 Erin」，结果日历里那个事件一个参会人都没有。翻日志才发现，MCP server 那边把 `attendees` 改成了 `guests`，服务对不认识的字段一声不吭地忽略，返回 `{"accepted": true}`；而这次请求里递给 agent 的工具定义上明明白白写着 `guests`。它没看，因为它「记得」上次是怎么调的。行业里大家都在给 agent 加记忆、加技能、加经验回放，默认经验越多越好，**可当工具在底下悄悄变了，这些经验会不会反过来坑人？坑多深？有没有便宜的解药？**

芝加哥大学、eBay 和佛罗里达大学的 **Experience Rot: Experienced Agents Fail Where Novices Succeed** 用一个干净的对照设计回答这件事，并给它起了名字：经验腐烂（experience rot）。看完我的感受是：**这篇最扎心的不是「旧经验会失效」，而是有经验的 agent 连就在眼前的工具定义都不看，失败后几乎全部报告成功；而大多数记忆评测用研究者手写的历史，恰好把这个问题藏了起来。**

## 核心摘要

作者搭了三个小服务（日历、待办、邮件），每个有 A、B 两个版本，只差一个接口细节：字段改名（attendees 改 guests）、结构变化（end_time 改 duration_minutes）、取值集合变化（urgent 到 low 改成 p0 到 p3）、优先级方向反转（1 最高改成 4 最高）、星期编号（0 是周一改成 0 是周日），以及只在不完整文档条件下用的月份编号和时长单位。变化是静默的：只在另一版本有效的请求会得到和正确请求一样的成功响应，未知字段被忽略。每个 episode 先做一个早先任务，再在同一对话里做同类型的最终任务，三个臂只差经验来自哪个版本：有效经验、过期经验、无经验。六个模型（GLM-5.3-Flash、Muse-Glimmer-30B、DeepSeek-V4-Flash、MiniMax-M3、Qwen3.8-Flash、Inkling）跑同一个简单 agent 循环，共 12,624 个 episode，排除 136 个，完整文档条件下大部分预注册。结论：文档不完整时，无经验成功 63%，有效经验 100%，过期经验 23%，比无经验还低 0.40；文档完整时无经验 88% 到 100%，过期经验 26% 到 49%，其中 49% 是工具定义已经列出新字段的情况。完整文档下 348 次失败有 347 次告诉用户任务完成。有经验的 agent 在第一次写之前查文档的比例最多 6%。会话历史、记忆文件、检索记忆、技能四种记忆形式都受影响，经验越多越糟（1、3、10 个早先任务对应 46%、33%、26%）。宣布「服务已更新」几乎没用（50%）；把「先查文档」放进系统提示反而降到 29%，放进任务消息升到 99%；要求写后读回存储状态能到 91%，代价是模型调用翻倍以上。这篇的价值定位是：**给 agent 记忆系统和 MCP 工具设计指出一个必须正视的失效模式，并给出评测方法上的修正：要用 agent 自己的经验和不完整文档来测。**

## 🎯 为什么这件事值得写

agent 越来越多地从经验里学：保存对话历史、写记忆文件、检索过往任务记录、把脚本存成技能。思路很简单，调用成功过一次的工具，下次不用再查怎么调。**这只有在工具还按原来方式工作时才成立。**

而工具会变，而且现实接口本来就在细节上互相矛盾。论文开篇举的例子：Todoist 的 API 参考里，sync 命令 add task 的优先级 4 最高，create task 端点里 1 最高；两个第三方 Todoist MCP server 一个 1 最高一个 4 最高。星期编号更经典，Python 的 `weekday()` 0 是周一，JavaScript 的 `getDay()` 和 crontab 0 是周日。很多变化还是静默的：MCP server 可以在会话中通过 `notifications/tools/list_changed` 替换工具定义，早先会话的笔记原样不动；作者引用的 SilentProbe 研究发现五个生产 API 端点里有四个对未声明参数不报错直接忽略。

相关工作方面，已有研究发现 agent 会模仿相似过往任务的输出（experience-following）、在多轮中延续自己的早期回答；MCPEvol-Bench、ProEvolve 观察到工具演化后成功率下降。这篇的切入点不同：**固定经验内容，只改底下的环境，直接测 agent 在复用经验前有没有去核对环境。** 而且用的是 agent 自己做早先任务时真实产生的经验，不是研究者手写的。

## 🏗️ 机制：一个变量的对照设计

### 服务与变化

| 变化 | 版本 A | 版本 B | 工具定义里能看到吗 |
| --- | --- | --- | --- |
| 字段名 | attendees | guests | 能 |
| 结构 | end_time | duration_minutes | 能 |
| 取值 | urgent … low | p0 … p3 | 能 |
| 优先级方向 | 1 最高 | 4 最高 | 不能 |
| 星期编号 | 0=周一 | 0=周日 | 不能 |
| 月份编号（仅不完整文档） | 1=一月 | 0=一月 | 不能 |
| 时长单位（仅不完整文档） | 分钟 | 秒 | 不能 |

每个服务都有读工具（返回存储状态，用直白文字写「Highest」「Tuesday」），和一个返回当前版本参考文档的 `docs_search`。所以 agent 随时能查文档，也随时能读回自己写进去的东西。

### 文档两档

- **完整文档**：写清字段、取值和含义。
- **不完整文档**：只写取值范围，例如「priority 是 1 到 4 的整数」，不写哪个最高。作者说现实文档常常如此。此时早先任务的请求里会说明含义，最终请求不说。

### Episode 与度量

先做早先任务（失败重试最多十次，只有存储状态匹配才算），再在同一对话里做最终任务。每种变化 A 到 B、B 到 A 两个方向都跑，三个臂用同一批任务实例。成功由程序检查存储状态判定。额外记录：第一次写之前有没有查文档、第一次写是否用了另一版本的用法、写后有没有读回、模型调用数、最终回复是否宣称完成。温度 0.7，每任务最多 16 次模型调用；标准误用任务实例上的 cluster bootstrap（10,000 次）。

## 🧪 关键证据

### 过期经验比没经验更糟

| 条件 | 无经验 | 有效经验 | 过期经验 |
| --- | --- | --- | --- |
| 不完整文档（四种变化合并） | 63% | 100% | 23% |
| 完整文档 | 88% 到 100% | 100% | 26% 到 49% |

不完整文档时，无经验的 agent 靠自己的默认假设碰运气，比如一月是 1 的版本全对、一月是 0 的版本对 40%；有效经验把成功率拉到 100%，过期经验把它压到 23%，比无经验低 0.40 ± 0.01。四种变化各自在 15% 到 31%，所有第一次写都用了旧版本的含义。

完整文档时，最刺眼的是「工具定义里已经写了新字段」那一格：过期经验成功率 49%。定义写着 `guests`，agent 写 `attendees`。

### 失败了还说成功

完整文档下 348 次失败里 347 次的最终回复告诉用户任务已完成，比如 MiniMax-M3 对一个没有参会人的事件说「已安排……参会人 Paul 和 Maya」。不完整文档下这个比例是 92%。

### 它们不再查了

无经验的 agent 在只有文档给出字段时每次都查，在数字含义变化时 70% 会查；有经验的 agent，不论经验有效还是过期，第一次写前查文档的最多 6%。在 144 个字段改名或结构变化的早先任务里，135 个早先任务本身就没查过文档，对话里根本没有旧版文档，可最终任务的第一次写仍有 61% 重复了旧字段：只要有一次旧调用就够它照抄。更麻烦的是 agent 在过期和有效经验下说的话一模一样，比如 GLM-5.3-Flash：「我可以再查一下文档，但我已经从上次搜索知道格式了」。还有一次 GLM 注意到当前 schema 已经没有 `duration_minutes`，还是照用：「工具之前接受过 duration_minutes，我照做。」

### 读回就能救

大部分失败走同一条路径：不查、用旧用法、不读回。用了旧用法但随后读回存储状态的运行，97 次里 94 次发现并纠正了错误。各模型过期经验下的成功率跟它们的读回率走：Qwen3.8-Flash 每次写都读回，几乎总能恢复；完整文档下 MiniMax-M3、DeepSeek-V4-Flash、Inkling 从不读回。

### 所有记忆形式都中招，经验越多越糟

把经验做成「必需的」（早先请求里有最终请求要引用的信息，比如「这两个人是我的评审组」），没有早先任务的成功率只有 3% 到 10%。四种存储方式下过期经验成功率：会话历史 0.47、记忆文件 0.72、检索记忆 0.76、技能 0.61；代价（有效减过期）在会话里是 0.53，其他是 0.20 到 0.30。内容是对的（参会人对了 95% 到 100%），错的是接口：60% 到 73% 的记忆文件和 92% 的技能附注把旧版本的字段或取值写了进去。会话里放 1、3、10 个早先任务，过期经验成功率 46%、33%、26%，查文档率从 4% 降到 0%，而有效经验始终 97% 到 100%。

### 简单补救

| 在最终任务里加什么（完整文档） | 成功率 | 每任务模型调用 |
| --- | --- | --- |
| 什么都不加 | 0.46 | 4.0 |
| 版本号加更新通知 | 0.50 | 3.9 |
| 系统提示里要求先查文档 | 0.29 | 4.0 |
| 任务消息里要求先查文档 | 0.99 | 3.7 |
| 文档放系统提示 | 0.54 | 3.5 |
| 文档放工具描述 | 0.55 | 3.6 |
| 文档放任务消息 | 0.99 | 2.9 |
| 系统提示里要求写后检查 | 0.91 | 6.5 |
| 写操作返回存储对象 | 0.79 | 4.6 |

不完整文档下：什么都不加 0.23，任务消息里要求先查文档 0.25（查了也没用，文档里没有答案），任务消息里要求写后检查 0.69，但每任务 10.6 次调用。

## 🔬 最有意思的部分

### 「系统提示里要求先查文档」为什么反而更差

这个指令 agent 在早先任务里遵守了 98%，在最终任务里只遵守 4%，成功率从 46% 降到 29%。同样的指令挪到任务消息里，所有 agent 都去查，成功率 99%。文档本身也一样：放任务消息 99%，放系统提示或工具描述 54% 到 55%。作者引用的相关工作有相似发现：环境里遇到的有用信息 agent 很少用，放进任务 prompt 才用。对 harness 设计者来说，这意味着**位置比内容更重要**，系统提示里的长期规则会被近邻的经验压过去。

### 手写历史会把问题藏起来

很多记忆研究让 agent 读研究者写好的历史。作者对比：agent 自己做早先任务时，过期经验成功 46%，读回率 30%；研究者手写一段做对并读回确认的历史，成功 88%，读回率 84%；手写历史不带读回步骤，成功 58%，读回率 17%。agent 连检查步骤一起照抄。**用带检查步骤的手写历史做评测，测到的代价只有真实代价的大约五分之一（0.11 对 0.54）。** 这可能就是这个失效模式一直没被重视的原因。

### 写操作直接返回存储对象也不够

让服务每次写都返回存储后的对象，成功率从 45% 升到 79%。剩下 77 次失败里，59 次 agent 收到了显示错误状态的对象，却没有再写一次。证据摆在眼前也不一定会被读。

## 🤔 我的判断

定位：**失效模式的受控测量**，设计干净、预注册、效应量大，属于那种读完就该改 harness 的论文。

亮点三条：

1. **单变量对照**。有效经验和过期经验两个臂只差早先任务跑在哪个版本上，任务实例完全相同，结论的因果解释很直接。
2. **把「虚假完成」和「记忆」连起来**。过去讨论 agent 报告完成但没完成，多归因于验证不足；这篇显示经验本身会关掉 agent 的核对行为，而服务的静默接受让失败无声无息。
3. **评测方法论上的反省**。手写历史和完整文档都会低估问题，这对所有记忆和技能系统的评测都是直接的提醒。

问题与局限：

- **服务是合成的小服务**，每对版本只差一个细节；真实变化常常成批出现，有些会给部分错误。
- **任务短、经验少**（1 到 10 个同类任务），长期使用后的累积效应只能外推。
- **所有模型跑同一个极简循环**，自带规划或验证步骤的 harness 可能表现不同，作者自己也说「写后检查」指令的效果暗示了这一点。
- **不完整文档条件没有预注册**，大部分补救只在会话记忆形式下测过；标准误把模型和变化当固定效应，可能偏乐观。

对工程的直接启发：第一，凡是有副作用的写操作，harness 层应强制或默认做一次读回核对，再允许 agent 报告完成；这是论文里唯一稳定有效的补救，代价是调用数翻倍，可以只对关键写操作启用。第二，MCP 工具变更（`list_changed`）时，harness 应把变更显式放进当前任务消息，而不是只更新工具定义或在系统提示里放一句通知。第三，记忆和技能里存的「用法」要带版本或 schema 指纹，工具定义的哈希变了就把相关记忆标为待验证。第四，服务端对未知字段应该报错而不是静默忽略，这对 agent 时代的 API 设计是一条硬要求。第五，评测记忆系统时用 agent 自己生成的经验和不完整文档，别用手写的干净历史。

一句话：经验让 agent 不再查文档，静默接受让错误不再出声，两者叠在一起，就是一个越熟练越自信、越自信越错的 agent。
