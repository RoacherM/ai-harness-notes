# 同一个 GPT-5.6 配三个 harness，17 道昇腾算子题全都交出了正确实现，几何平均加速却从 1.05 倍到 1.69 倍；七成「模型加 harness」组合不到 1.2 倍，而晚到的提速要按 token 扣分

做过算子优化的人都知道，这活儿的起点通常不是空白文件，而是一份已经能跑、已经正确、只是不够快的实现。你要拿着生产里真实的张量形状去看瓶颈，改代码、编译、对精度、测延迟，一轮一轮地磨。现在大家开始让 coding agent 干这件事，问题随之而来：**拿什么判断一个 agent 优化得好？最终加速比高就算赢吗？如果一个组合用 1000 万 token 拿到 1.5 倍，另一个用 1.4 亿 token 拿到 1.6 倍，谁更值得用？如果两个组合最后都停在 1 倍，一个是改了 80 版全没过精度，一个是全过了但没提速，它们算一样吗？**

SLAI AI 训练平台团队的 **AscendGYM: A Cost-Aware Kernel Optimization Benchmark for Real-World Workloads on Ascend NPUs** 给出的回答是一个昇腾 NPU 上的算子优化基准，外加一个把「提速」和「花掉的 token」放进同一个分数的指标 STS。看完我的感受是：**这篇的榜单本身信息量有限（只测了第一批 17 题，多数具体数字只在图里），但它把 harness 对比里最容易被忽略的三件事都拆成了独立指标：成本、到达时间、以及「1 倍」背后到底是没做对还是没做快。** 对一直关心 harness 和模型怎么配、配了以后成本怎么算的人，这套指标设计比排名更值得看。

## 核心摘要

AscendGYM 的任务是「在保持正确的前提下，把一份已有的、正确的 Ascend C 算子实现进一步提速」。48 个算子分三批：第一批 17 个是以访存优化为主的基础算子，第二批 17 个是归一化、量化等多步计算，第三批 14 个是稀疏注意力等复杂注意力和融合计算。题目来自对 MindSpeed-LLM、vLLM-Ascend 真实训练推理负载的 profiling，挑 top-k 瓶颈算子，每题保留目标模型、执行阶段、并行配置和由此得到的张量形状与数据类型。执行沙箱 AscendForge 基于 SandboxFusion，把编译、精度检查、性能测量分开回报。评测分两种模式：模型加 harness 模式把 Claude Code、Codex CLI、OpenCode 这类现成 agent 当成完整系统测；模型模式固定用内置 harness（基于 AuraKernel，简称 Default）比较模型。指标分四类：联合指标 STS 和 CTG，性能指标几何平均加速和 fast_p，预算指标 token、交互轮数、墙钟时间，可靠性指标候选通过率和任务通过率。论文只报告了第一批 17 题。几个关键结果：约 70% 的组合几何平均加速低于 1.2 倍；GPT-5.6 用三个 harness 都能在全部任务上交出正确候选，但几何平均加速在 Codex 上约 1.69 倍、在 Claude Code 上约 1.05 倍；Codex/GPT-5.6 每题约 1.404 亿 token，Claude Code/Opus 5 约 8175 万 token，但后者几何平均加速更高；Qwen3.6-35B-A3B 在 OpenCode 和 Codex 上加速相近（约 1.06 倍和 1.05 倍）、token 相近，每题耗时却是 11.1 小时对 2.2 小时。这篇的价值定位是：harness 对比必须同时报「拿到多少、花了多少、什么时候拿到、是没对还是没快」，单一的最终加速比会把这些差别全部抹平。

## 🎯 为什么这件事值得写

已有的算子基准大多测「生成」：KernelBench 给 PyTorch 程序让模型写等价的 GPU kernel，NPUKernelBench 和 CANN Bench 把这件事搬到昇腾上，看能不能编译、对不对、多快。AscendGYM 关心的是另一件更贴近日常工程的事：**给你一份正确的实现和一组来自真实负载的输入配置，在可接受的预算内，你能不能让它更快且不出错。**

作者在引言里提了三个设计问题，基本就是这篇的骨架：

- **任务怎么设计**：同一个算子在不同输入下优化重点不同，比如注意力在 prefill 和 decode 阶段处理的数据规模不同。所以题目要带上真实的形状和参数，性能提升才能映射回具体负载。
- **评估怎么可靠**：改过的代码能不能编译、对不对、快不快，必须分开靠真实执行来确认；在昇腾上还涉及 host 和 device 代码的协同构建。
- **效果怎么衡量**：两个系统最终加速相同，一个几次就找到了，一个搜了很久，单看最终加速分不出来。

第三点是我最想写这篇的原因。harness 对比里「花了多少钱」往往被放在附录，或者干脆不报。AscendGYM 把它做进了主指标。

## 🏗️ 机制：真实负载出题、沙箱分层回报、按 token 计分

### 题目从哪来

作者从昇腾框架上的真实训练和推理负载采集 profiling 数据，识别 top-k 瓶颈算子。每道题包含基线源码、描述输入输出形状的模板元数据、测试输入，以及由对应 CPU 实现生成的参考输出。题目来源是 CANN ops-nn、ops-transformer 和 vLLM Ascend，任务包里写明源码版本、测试输入和数值比较规则。

论文给了一个具体例子：AddRMSNorm 题来自 Qwen3-0.6B 推理的一次前向，prefill 阶段、不量化、eager 执行、单卡、TP 1、BF16、batch 1、输入长度 32。分支输出和残差张量形状都是 [32, 1024]，归一化权重是 [1024]。profiling 显示这个算子每次前向调用 56 次，占总计算时间 8.77%，按累计执行时间排进前五。**保留这层上下文的意义在于，某题快了多少，可以直接换算成对应负载快了多少。**

### AscendForge 沙箱

AscendForge 建在 SandboxFusion 之上，增加了管理 host 端注册、device 端 kernel、目标 SoC 和自定义算子包之间依赖的适配器。四层结构：

| 层 | 作用 |
| --- | --- |
| 执行与构建层 | 支持 Ascend C 和 Python NPU 后端，适配 CANN 算子仓、Ascend C 自定义算子模板和 vLLM Ascend，自动完成提交、编译安装、Python 接口绑定和测试执行 |
| 资源编排层 | 调度代理、任务队列、多执行节点，按 NPU 数量、设备型号、节点偏好分配资源，支持并发评测 |
| 开发反馈层 | 静态分析和性能剖析，返回构建日志、精度结果、性能测量和测试产物 |
| 部署运维层 | 硬件健康监控、配置热加载、进程自动恢复、离线依赖准备和版本校验 |

关键设计是**编译结果和执行结果分开回报**，让模型能区分构建失败、数值精度失败和性能回退三种情况。测试驱动先验精度再收集性能。每次构建有独立工作区。搜索结束后 AscendGYM 会对候选重新评估。

### STS：晚到的提速要扣分

STS（Speedup–Token Score）的定义是：

$$\mathrm{STS}=100\log_{2}S_{n}-50\sum_{k=1}^{n}\frac{B_{k}}{B_{\max}}\Delta g_{k},\qquad \Delta g_{k}=\log_{2}S_{k}-\log_{2}S_{k-1}$$

$B_{\max}$ 是 token 预算，$n$ 是预算内完成的候选评估次数，$B_k$ 是第 $k$ 次评估完成时累计消耗的 token（失败和没提速的尝试也算），$S_k$ 是第 $k$ 次评估后可用的最好的、通过精度验证的加速比。没找到提升时保留参考实现，所以 $S_0=1$、$S_k\ge 1$。

读法很直观：第一项奖励最终提速（以 2 为底的对数，翻一倍记 100 分）；第二项对每一段提速按「它是在预算用掉多少比例时拿到的」加权扣分。**同样的最终加速，越早拿到分越高。**没有任何提升时 STS 为 0。

### CTG：再提 1%、5%、10% 要多花多少

CTG（Cost-to-Gain）衡量从某个参考检查点 $r$ 起，加速比再提高 $\delta$（1%、5%、10%）需要额外消耗的最少 token；预算内达不到就记为无穷大。越低越省。

### 其余指标

| 类别 | 指标 | 含义 |
| --- | --- | --- |
| 性能 | fast_p | 正确实现加速严格大于 $p$ 的任务比例（沿用 KernelBench） |
| 性能 | GM Speedup | 各任务最好加速比的几何平均 |
| 预算 | token、交互轮数、墙钟时间 | 分开报，不合成 |
| 可靠性 | 候选通过率 | 被评估候选中编译、执行、精度全通过的比例 |
| 可靠性 | 任务通过率 | 至少有一个候选通过精度检查的任务比例，没提交或没通过的任务留在分母里 |

### 评测协议

- **模型加 harness 模式**：Claude Code、Codex CLI、OpenCode 三个 harness，搭配 Claude Opus 5、GPT-5.6 Terra、GLM-5.3、Qwen3.5-122B-A10B、Qwen3.6-35B-A3B、DeepSeek-V4-Flash 中的部分组合。所有 harness 收到同一份任务提示，保留各自的系统提示和工具。
- **预算**：每次优化最多 80 次候选评估，提示里给一个「探索 50 个实质不同方案」的软目标；失败提交消耗预算，基线测量不算；**不限制总 token 和墙钟时间**。搜索结束后最终实现额外测 5 次性能，不消耗预算也不提供反馈。
- **测量**：每次评估跑 8 轮，前 3 轮预热，其余取 device 侧 kernel 时间的算术平均，用 msprof 采集；硬件是 Ascend 910C，CANN 9.0.1。
- **模型模式**：固定 GPT-5.6 Luna、推理强度 xhigh，比较 Default 的四种配置：cold、warm、no lessons、code only。

任务提示（附录 C 给了节选英译）有几条值得注意的约束：只有列出的 kernel 源文件可以修改，manifest、测试、规格、golden 参考和评测程序必须保持不变；评测时冻结提交快照，评测期间不得改源文件；**不得修改容差、golden 参考、测试覆盖、算子接口、形状或数据类型**；不得把未验证的代码说成最好的已验证实现；预算为零或收到 `stop_required = true` 时必须停止编辑和评测，由控制器交付最好的已验证快照；HTTP 中断不代表评测没跑，要保留 request_id 用原 ID 查询或重试。

## 🧪 关键证据

需要先说明：论文的主要结果大量以图呈现，正文只给出了部分具体数值。下面只列论文文字里明确写出的数字。

### 整体难度

- 约 **70%** 的模型加 harness 组合几何平均加速低于 1.2 倍。
- 单题最好的观测加速是 fused_gdn_gating 上约 **3.29 倍**；moe_gating_top_k 上最好只有约 1.17 倍。
- 在 17 题中的 **13 题**上，所有受支持组合的加速中位数低于 1.1 倍。

### 同样「全部做对」，提速差很多

| 观察 | 数值 |
| --- | --- |
| GPT-5.6 的任务通过率 | 三个 harness 下都通过全部任务 |
| GPT-5.6 + Codex 几何平均加速 | 约 1.69 倍 |
| GPT-5.6 + Claude Code 几何平均加速 | 约 1.05 倍 |
| Claude Code/Opus 5 与 Codex/GPT-5.6 | 都让全部任务提速，但超过 2 倍的任务分别是 7 个和 3 个 |

**同一个模型换 harness，正确率一样，提速可以差出 0.6 倍以上。**这和最近几篇 harness 排行榜审计看到的现象一致：模型和 harness 的配对本身就是一个变量，不能只报底座模型。

### 成本不跟着效果走

| 组合 | 观察 |
| --- | --- |
| Codex/GPT-5.6 | 每题约 1.404 亿 token |
| Claude Code/Opus 5 | 每题约 8175 万 token，几何平均加速更高，交互轮数更多 |
| 两者每轮 token | 按总 token 除以总轮数，Codex/GPT-5.6 每轮约为 Claude Code/Opus 5 的三倍 |
| OpenCode/Qwen3.6-35B-A3B | 几何平均约 1.06 倍，每题 11.1 小时 |
| Codex/Qwen3.6-35B-A3B | 几何平均约 1.05 倍，每题 2.2 小时 |

最后两行最有意思：加速相近，token 相近，墙钟时间差约五倍。作者的结论是 token、轮数、时间描述的是不同维度的开销，单一成本指标不够。

### 预算不同，排名的含义不同

作者设了三档每题预算：10M（紧）、20M（中）、50M（宽）token。在 10M 时，Opus 5 配 Claude Code 和配 OpenCode 的 STS 相近；预算加大后，Claude Code 的性能项继续增长，OpenCode 增长有限。到 50M 时，Claude Code/Opus 5 性能项更大、扣分也更大，扣分缩小了差距但没有反转。

CTG 揭示了另一层：50M 预算、10% 提升目标下，Opus 5 配 OpenCode 在达标任务上的中位成本是 380 万 token，配 Claude Code 是 660 万 token；**但 OpenCode 只在一部分任务上达标，Claude Code 在全部任务上都达标。**达标集合不同，条件中位数低不代表在同样任务上更省。所以作者坚持 CTG 要和达标数一起报。

### 「1 倍」背后的两种失败

附录 E.3 做了任务通过率核算。在所有选中的记录里，有 31 条最终停在 1 倍：其中 17 条交出了正确但没提速的候选，14 条一个通过精度验证的候选都没有。只看加速比，这两类完全一样。

以 Codex/GLM-5.3 为例：17 题里通过 10 题；没通过的 7 题中，5 题根本没有候选提交，moe_token_unpermute 和 recurrent_gated_delta_rule 两题有提交但没有一个通过精度验证。全部任务都留在分母里。

### 模型模式：harness 配置本身就会改变结论

固定 GPT-5.6 Luna 比较 Default 的四种配置：

| 配置 | 初始经验 | 在线积累 | 搜索策略 |
| --- | --- | --- | --- |
| Cold | 无 | 策略加代码 | 完整 Default |
| Warm | 5 条策略经验 | 策略加代码 | 完整 Default |
| No lessons | 无 | 无 | Agent-search |
| Code only | 无 | 仅代码 | Agent-search |

结果：warm 在三档预算下 STS 都最高，10M 时性能项已超过 cold 且扣分更小；预算加大后 cold 追回一部分但仍落后。code only 三档都高于 no lessons，但两者都低于完整的 cold。作者据此提醒：用 Default 比较模型时必须固定配置和先验经验，否则会把配置差异误读成模型能力差异。

## 🔬 最有意思的部分

### STS 把「什么时候拿到」写进了分数

大部分 harness 对比只看终点。STS 的扣分项是每一段对数提速乘以它到达时的预算占比。举个按公式推的直观例子（论文没有给这个算例）：同样最终 2 倍，如果在预算用掉 10% 时拿到，扣 5 分，得 95 分；如果在预算用掉 90% 时拿到，扣 45 分，得 55 分。这对实际选型很有用：线上只给 1000 万 token 的预算时，你关心的是谁在前 1000 万里能拿到东西，而不是谁搜到 1 亿 token 时最好。

把同一条轨迹在 10M、20M、50M 三处截断，看排名怎么变，这种报告方式本身就值得借鉴：Opus 5 配 Claude Code 和配 OpenCode 在 10M 时打平，到 50M 才拉开。只报 50M，你会以为 Claude Code 全面占优；只报 10M，你会以为两者没区别。

### 「先过精度再谈速度」的提示词护栏

附录 C 的任务提示把一长串「不准做的事」写得非常具体：不准动测试、容差、golden、接口、形状、数据类型，不准把没验证过的代码说成最好的已验证版本，收到停止信号就停下由控制器交付。评测端也配合：冻结提交快照，只编译 manifest 里的文件，搜索结束后统一重测。

这是一套典型的防奖励投机设计，思路和最近几篇讲「验证器被钻空子」的工作一致：可写范围收窄到被测的那几个文件，最终结果由控制器从已验证快照里取，而不是信 agent 自己的报告。不过论文没有报告有没有 agent 尝试越界、被拦了多少次，这是我觉得可惜的地方。

### 墙钟时间差五倍，说明 harness 的执行方式也是成本

Qwen3.6-35B-A3B 在 OpenCode 和 Codex 上 token 和效果都差不多，时间却是 11.1 小时对 2.2 小时。论文没有进一步拆解原因，但这至少说明 harness 的调度、工具调用和等待方式会在 token 之外制造显著开销。如果你的优化必须在一个运维窗口内完成，这比 token 更关键。

## 🤔 我的判断

定位：**基准加指标设计的技术报告**。任务和沙箱是工程贡献，STS、CTG 和「任务通过率留分母」是方法贡献，实验部分更多是演示这些指标能分出什么。

亮点三条：

1. **成本是一等指标**。STS 把 token 消耗和到达时间写进主分数，CTG 把「再提一点要多少钱」和达标覆盖率配对报告，token、轮数、墙钟时间分开列。这正是 harness 和模型配对评估最缺的部分。
2. **把「1 倍」拆开**。17 条正确但没提速、14 条一个正确候选都没有，这种核算让「看起来没退步」的结果暴露出真实的失败分布。
3. **题目绑定真实负载**。每题记录调用次数、时间占比、形状和阶段，提速可以回溯到具体负载，避免在没人用的形状上刷分。

问题与局限：

- **只评测了 48 题里的第一批 17 题**，第二、三批留待后续；第一批以访存优化为主，结论能否推广到融合和注意力类算子未知。
- **大量结果只在图里**，正文只零散给出了几个数值，三档预算下各组合的 STS 具体值、fast_p 曲线都无法从文字核对。
- **每个组合每题只保留最新一条记录**，没有独立重复运行，作者也只说「有重复时可以额外评估稳定性」。在单次运行下，1.05 倍和 1.06 倍这种差别不具备区分意义。
- **只评测了部分组合**，不是完整的模型乘 harness 网格，模型和 harness 的主效应无法干净分离。
- **模型模式的四种配置协议不一致**：warm 在 CANN 题上每次测量跑 11 次，其他配置跑 8 次；在三道 vLLM Ascend 题上，warm 导入的 5 条经验来自**同一算子**的 cold 运行中验证过的正收益经验。作者说明了经验准备成本单独记录、warm 不继承 cold 的代码，但这仍然意味着 warm 在这三题上用了同题的先验，「warm 最好」需要打折理解。作者自己也写了比较结果反映的是各自协议下的表现。
- **STS 的常数 100 和 50 没有敏感性分析**，扣分权重的选择会直接影响紧预算下的排名。
- **没有报告越界或投机行为的统计**，提示词里的护栏到底拦住了什么，看不出来。

对工程的直接启发：第一，做 harness 或模型选型时，把同一条优化轨迹在几个预算点截断分别打分，而不是只看最终结果；你的生产预算在哪一档，就看哪一档的排名。第二，「达标成本」必须和「达标覆盖率」一起报，只在成功任务上算中位成本会偏向挑软柿子的组合。第三，性能类任务的验收要把「没交出正确候选」和「交出了但没提速」分开计数，前者是可靠性问题，后者才是优化能力问题。第四，给 agent 做性能优化时，可写文件列表、冻结快照、控制器交付最好已验证版本这三件事应该由 harness 强制，而不只写在提示词里。

一句话：同样停在 1 倍的两个 agent，一个是没做对，一个是没做快；同样拿到 2 倍的两个 agent，一个在预算开头拿到，一个在预算末尾拿到。AscendGYM 的价值就是让这些差别在分数里看得见。
