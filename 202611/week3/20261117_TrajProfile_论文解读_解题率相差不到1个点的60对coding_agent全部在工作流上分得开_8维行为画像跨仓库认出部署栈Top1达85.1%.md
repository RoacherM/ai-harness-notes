# 解题率相差不到 1 个点的 60 对 coding agent，每一对都在工作流上分得开；不看结果、不看 token、不看工具名，8 维行为画像跨仓库认出部署栈 Top-1 达 85.1%

你有没有过这种体验：排行榜上两个 agent 配置解题率几乎一样，你挑了一个上线，结果它在你的仓库里一个任务要跑六七十步，另一个十几步就交了；或者某个提交声称用的是 A 模型加 B 脚手架，你心里犯嘀咕，却只能看一个 pass 率。行业里早就知道 scaffold 会显著改变成功率，但评测还是把多步交互压成一个二值结果。**问题是：解题率之外，执行轨迹本身能告诉我们多少？能不能稳定到足以认出「你到底是谁」？**

Nebius 的 **Interpreting Coding Agents Through Their Behavioral Trajectories** 拿 SWE-rebench 排行榜上 143,209 条执行轨迹（125 个 agent 配置、117 个基座模型）做了一次大规模行为分析：用确定性规则解析器把异构的工具调用映射到同一套动作分类，再做解题率匹配的配对比较、同栈 A/A 零假设对照、跨仓库和跨语言的部署栈检索。看完我的感受是：**这是一份把「轨迹指纹」变成可复现测量工具的工作，对 harness 排行榜审计尤其有用，但作者也很克制地说了它测的是低层操作签名，不是推理策略。**

## 核心摘要

解析器以单次工具调用为单位，把每个事件分成十类主操作（探索、搜索、读文件、改文件、正式测试、git diff/status/show 这类工作区检查、构建、其他、非仓库操作、未知），并独立标注目标文件角色、修改类型、读取方式。在此之上定义六个工作流指标：操作动作数、探索占比、非测试仓库写入、正式测试调用、连续重复失败、最后一个有效动作之后的「无效尾巴」。解析器用六个前沿模型的共识（6 个里至少 5 个一致才算参考标签）在 500 个分层抽样动作上审计，主操作一致率 82.4%，读取方式 96.6%，目标文件角色 77.0%，修改类型 68.8%。核心结果三条：60 对同脚手架、解题率差不超过 1 个百分点（中位数 0.40）的配置，在任务配对 bootstrap 95% 区间下全部至少在两个指标上分开，58 对在至少三个指标上分开，而同一配置拆两半的 A/A 对照里只有 0.781% 能在三个指标上分开；脚手架和推理强度系统性地改变行为，比如 Claude Opus 4.8 在 Claude Code 里从 Low 到 xHigh，动作数从 31.3 升到 54.4，增加的部分主要是探索，不是无效重复；不用结果、token、动作总数和原生工具名，8 维画像在两半互不相交的仓库之间检索 111 个部署栈，Top-1 85.1%、Top-3 96.8%，跨五种语言 16 个栈 Top-1 90.3%。

## 🎯 为什么这件事值得写

SWE-bench 一类基准把 agent 的多步交互压成「补丁过没过测试」，聚合成解题率，适合排名，不适合理解。已有工作也意识到这一点：同一个 issue 上重复 rollout 行为差异很大；有人做阶段标注、过程流图、失败点定位（TrajAudit 等）；Raj 等人强调 agent 能力和交互 harness、工具定义、运行时环境紧紧绑在一起，而不只是模型权重。

难点在于轨迹是异构的：不同 harness 暴露不同工具、用不同命令格式、按不同 schema 记录。直接比工具名或原始命令，会把「语义上在做什么」和「这个 harness 怎么记录」混在一起。这篇的切入点是先做一个跨系统的共享表示，再用三种对照把行为差异从「成功率差异」和「随机波动」里剥出来：解题率匹配、同栈 A/A、跨仓库和跨语言检索。

这里的「部署栈」指完整系统：基座模型、脚手架（SWE-agent 式通用 bash、Claude Code、Codex 等）、推理强度、API 解码参数。同一模型换脚手架就算不同的栈。作者不看推理文本，只看可观察的执行工作流。

## 🏗️ 机制：规则解析器、六个指标、三种对照

### 数据

| 集合 | 内容 | 用途 |
| --- | --- | --- |
| Python 全集 | 860 个任务、413 个仓库（2025 年 1 月到 2026 年 5 月），111 个配置，134,329 条轨迹 | 跨仓库检索 |
| 多语言集 | 111 个任务，Go/Java/Python/Rust/TypeScript，16 个前沿配置，8,880 条轨迹 | 跨语言检索 |
| 2026 春季面板 | 110 个 Python 任务（2026 年 3 月到 5 月），每任务多次 rollout | 匹配配对、A/A、代际和脚手架比较 |

两个集合共享两个配置，并集是 125 个。

### 动作分类与指标

| 指标 | 定义 |
| --- | --- |
| 操作动作数 | 每次 rollout 尝试过的非终止工具调用，包括格式错误和被拒的 |
| 探索占比 | 探索、搜索、读文件占已执行语义动作的比例 |
| 非测试仓库写入 | 对非测试路径的修改，且没有观察到失败 |
| 正式测试调用 | 识别出的测试框架调用次数，复合命令里可以超过一次 |
| 连续重复失败 | 规范化签名相同的相邻失败次数 |
| 无效尾巴 | 最后一次有效动作（计数的写入或通过的测试）之后的非终止动作数 |

### 解析器审计

不做人工标注，而是让六个前沿模型（claude-opus-5、gpt-5.6-sol、gemini-3.7-flash、Kimi-K3、DeepSeek-V4-Flash-0731、MiniMax-M3）盲评 500 个分层抽样动作，隐藏解析器预测、元数据和任务结果；至少 5 个一致才形成参考标签，抽样严格排除了调试解析器用过的 1,475 条开发轨迹。

| 字段 | 共识率 | 与共识一致 | Macro-F1 |
| --- | --- | --- | --- |
| 主操作 | 94.0% | 82.4% | 88.8% |
| 目标文件角色 | 96.6% | 77.0% | 57.8% |
| 修改类型 | 98.2% | 68.8% | 73.7% |
| 读取方式 | 99.0% | 96.6% | 98.4% |
| 四字段完全一致 | 91.4% | 77.5% | 无 |

因此依赖路径解析和修改分类的指标（比如非测试写入数）作者只当诊断代理用。

### 三种对照

1. **解题率匹配**：同脚手架、不同基座，至少 50 个共享任务上解题率差不超过 1 个百分点。
2. **同栈 A/A**：把同一配置每个任务五次 rollout 中的四次随机分成两半，100 个随机种子，共 12,000 次拆分，衡量同栈自身的运行间差异。
3. **跨环境检索**：在一半仓库（或三种语言）上算画像，在另一半上用余弦最近邻找回同一个栈。

## 🧪 关键证据

### 解题率一样，工作流不一样

| 至少分开的指标数 | 同栈 A/A 拆分 | 解题率匹配的 60 对 |
| --- | --- | --- |
| ≥1 | 30.53% | 100.0% |
| ≥2 | 6.40% | 100.0% |
| ≥3 | 0.781% | 96.7% |

单个指标在 A/A 里的假阳性率接近名义水平：动作数 6.30%，探索占比 5.97%，测试调用 6.58%。只看三个主指标（动作数、探索占比、测试调用），60 对里每一对都至少在一个上分开。附录还举了两边五次都解出的任务：pypsa-1653 上 Claude Opus 5 平均 62.4 个动作、48.4% 的编辑走 heredoc 重定向、12.4 次测试调用，GPT-5.6 Sol 15.0 个动作、100% 编辑走内联 Python、3.4 次测试。

### 脚手架、推理强度、模型代际

- **脚手架决定怎么改、怎么读**：同样是 Opus 4.7，在 SWE-agent 式通用 harness 里 37.0% 编辑用原生编辑、24.4% 用 shell 重定向，原生读只占 5.5%；在 Claude Code 里 92.4% 编辑和 90.5% 读走原生 API。GPT-5.5 在通用 harness 里 69.0% 编辑走内联 Python，在 Codex 里 30.9% 走原生编辑、54.6% 走 Python。
- **推理强度加的是探索，不是瞎转**：GPT-5.5 从 Medium 到 xHigh，动作数 24.2 到 43.4；Opus 4.8 在 Claude Code 里从 Low 到 xHigh，31.3 到 54.4（差 +23.0，95% 区间 [16.5, 27.8]），其中探索和读 +12.7，无效尾巴反而 −0.50，最后一次写入后做过工作区检查的 rollout 比例从 12.7% 升到 66.8%，读的占比基本稳定在 23% 到 25%。
- **代际变化**：通用 harness 下，Opus 从 4.6 到 5，用 `sed -n` 按行切片读的比例从 6.9% 升到 57.7%，`pytest -q` 从 22.7% 升到 99.8%；GPT 从 5.4 到 5.6 Sol，工具操作数从 24.4 降到 12.8，72.1% 的编辑走内联 Python。

### 画像能认出部署栈

| 表示 | 跨仓库（111 栈，随机 0.9%）Top-1 / Top-3 | 跨语言（16 栈，随机 6.25%）Top-1 / Top-3 |
| --- | --- | --- |
| 完整画像 | 85.1% / 96.8% | 90.3% / 98.8% |
| 只用动作坐标 | 62.6% / 86.5% | 87.5% / 98.4% |

跨仓库的 8 维画像是四个归一化动作坐标（探索、读文件、非测试写入、正式测试）加四个序列与验证特征（归一化熵、工具切换率、写后工作区检查、未验证即终止），严格不含解题结果、动作总数、token 量和原生工具名。只用序列与验证特征是 56.8%；只在 107 个通用 SWE-agent 栈里检索仍有 85.5%，说明不靠脚手架特有的工具语法。跨语言里只用熵和切换率是 36.3%，信号主要来自动作构成；13 个同脚手架栈里 88.5%。

## 🔬 最有意思的部分

**「停止策略」是最直观的差别。** lsdb-1349 这个任务上，Opus 5 最后一次写代码后还跑了目标测试、全量回归、`git status`，平均写后 8.8 个动作；GPT-5.6 Sol 目标测试一过就提交，写后 4.4 个动作。两边都五次全对。对关心 stop hook 和过早完成的人来说，这说明「什么时候停」是一个独立于成功率、可以被量化的栈属性，而且附录里已经有现成的定义：未验证即终止（改了仓库文件，之后没有通过的正式测试）和写后工作区检查。

**行为画像可以当排行榜的「栈声明核验」。** 作者自己的表述是：画像可以揭示不同模型和脚手架之间共享的或变化的操作模式，轨迹审计可以暴露 reward hacking 或表面硬编码。把这个和最近 harness 排行榜审计里出现的问题放在一起看（声明用 A 模型、实际走代理模型；声明的能力和实际配置不符），一个不依赖工具名的行为指纹就是很便宜的第一道检查：提交的轨迹画像和同一声明栈的历史画像差得很远，就值得人工去看。当然作者也提醒了，这类画像可能被用于非预期的系统归因，要谨慎。

**推理强度的钱花在哪了。** 很多人默认「高推理档多出来的步数是在原地打转」。这里的数据是相反的：无效尾巴略降，多出来的是探索、读和写后检查。

## 🤔 我的判断

定位：**测量基础设施 + 大规模经验观察**。贡献是一个确定性、可复现、跨 harness 的轨迹归一化工具和一套带零假设对照的比较方法，而不是新的 agent 方法。

亮点三条：

1. **A/A 对照做得扎实**：12,000 次同栈拆分给出了「多指标同时分开」的经验假阳性率，让「解题率一样、行为不同」这个结论不只是看图说话。
2. **刻意排除捷径特征**：检索画像不含结果、token、动作总数、工具名，并做了只限同一脚手架的检查，避免「靠工具名认出 Claude Code」这种平凡结论。
3. **工具开源、数据可得**：解析器、流水线、标注子集都发布了，别人可以直接拿来跑自己的轨迹。

问题与局限：

- **审计参考是 LLM 共识而不是人工**，目标文件角色只有 77.0%、修改类型 68.8%，共享的系统性偏差无法排除；也只审了单个动作标签，没验证重复失败、无效尾巴这类序列指标。
- **跨仓库检索没有控制任务构成**，作者明确说这可能贡献了检索效果，不能据此说存在与任务无关的行为签名；他们把画像解读为低层操作签名，不是问题求解策略。
- **单一基准体系**：全部来自 SWE-rebench，模型可能认出评测环境，画像未必原样迁移到真实部署。
- **匹配的是聚合解题率**，不控制各自解出哪些任务；按每任务结果匹配会更严格。
- **分类法是为软件工程定的**，换到科研、交互设计等领域要扩展解析器。

对工程的直接启发：做 harness 对比或内部选型时，除了解题率，至少再报三项：每任务动作数、写后是否跑过测试或做过工作区检查、未验证即终止的比例；比较两个配置前先做一次同栈 A/A，知道自己的噪声底在哪。做排行榜或第三方提交审核时，可以把这套不依赖工具名的画像当成栈声明的一致性检查，异常再人工看轨迹。

一句话：解题率告诉你它做没做成，轨迹告诉你它是谁、怎么做成的、什么时候觉得自己做完了；后两者对上线和审计同样重要。
