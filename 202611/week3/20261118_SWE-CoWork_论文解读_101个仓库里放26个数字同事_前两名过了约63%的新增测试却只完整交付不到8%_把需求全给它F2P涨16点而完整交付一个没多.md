# 把 coding agent 丢进一个有 26 个同事的公司：前两名过了约 63% 的新增测试，却只完整交付不到 8% 的任务；直接把全部需求写给它，F2P 涨 16 个点，完整交付一个都没多

你给 coding agent 派活的时候，大概率是这样写的：一个 issue、一段需求、几个验收点，它照着改，跑测试，交差。SWE-bench 一路刷到接近饱和，测的也是这种「需求已经写好」的场景。可你自己在公司里接手一个项目时，真正难的往往不是写代码：前任休假了，需求散在看板卡片、改过三版的设计文档、几百条群聊和 CI 记录里，有的已经作废，有的贴错了运行日志，有的只有某个模块负责人心里清楚，而且他会先让你给出复现路径再回答。**如果 agent 要当「数字员工」，它能不能自己把需求问清楚、追到底、做完、再如实汇报做到了哪一步？**

TokenWave AI 的 **SWE-CoWork: Benchmarking Coding Agents as Digital Employees in Organizations** 把这件事做成了一个可执行的基准。看完我的感受是：**它最有价值的不是又一个低分榜单，而是把每一条需求从「谁持有」到「问没问」「拿没拿到」「实现没实现」「交接报告里说没说完成」一路串到具体测试节点上，于是能看清 agent 到底在哪一环把需求弄丢了。** 结论很扎心：前沿模型已经很会找对人，问题出在后面：追问半途而废、拿到需求也没做对、提前收工、交接报告里说「做完了」的需求有 31% 测试不过。

## 核心摘要

SWE-CoWork 有 101 个开发任务，来自 101 个真实开源仓库，覆盖 11 种语言和 12 个应用领域。每个任务配一个虚构的工程组织：26 个由规则约束、LLM 驱动的「数字同事」，各有职责、有限的本地知识和受控的协作行为；外加看板、版本化文档、群聊、合并请求和 CI 记录。agent 从一份很短的交接说明出发，自己查记录、找负责人、调和矛盾证据、实现并验证，最后交一份交付说明，由私有的 F2P/P2P 测试判分。11 个模型里，Claude-Opus-5.5 和 GPT-6 Astra 的 F2P 分别是 63.84% 和 62.91%，完整通过率只有 6.93% 和 7.92%，其余 9 个模型 F2P 至多 39.09%、完整通过率至多 0.99%。配对的 Oracle-Spec 条件把全部需求一开始就给 agent：Seed Evolving 的 F2P 从 39.09% 涨到 55.76%，GPT-6 Astra 从 62.91% 涨到 78.84%，但两者的完整通过率纹丝不动（0.99% 和 7.92%）。对 Claude-Opus-5.5 的 101 条轨迹做需求级追踪：第一问发给正确负责人的比例平均 93%，但只拿到 64% 的同事持有需求；450 个被同事推迟回答的线程里有 153 个再也没跟进，放弃时中位还剩 7.1 小时预算；交接报告里声称完成的 826 条需求有 255 条（31%）测试不过。作者的结论是：可靠交付的瓶颈在于把每条需求的状态从澄清一路维持到实现、验证和交接。

## 🎯 为什么这件事值得写

作者开篇引了一组背景数字：Anthropic 报告截至 2026 年 5 月，其内部代码库合入的代码 80% 以上由 Claude 编写，2026 年二季度典型工程师每天合入的代码行数是 2024 年的 8 倍。代码产出不再是瓶颈，瓶颈转移到了组织层面：谁来把散落的上下文整理成一份自洽的规格？今天的 agent 大多是被动的「规格执行器」，加速了底层实现，但仍然需要人去策展组织上下文、消解历史记录里的矛盾、把不断变化的诉求翻译成自包含的需求。

已有基准大多给 agent 一个已经界定好的开发目标。研究需求不完整的工作要么改变初始请求里的信息量，要么让 agent 去问一个「指定的模拟用户」，缺失的需求都在这一个人身上。SWE-CoWork 的区别在于：需求分散在多个职责边界清晰、知识有限的同事和多种记录里，agent 得先判断谁有权回答，带着足够的代码上下文去问，跟进被推迟的问题，还要分辨哪些历史记录已经过时。作者把目标能力归成四个词：持续（跨多个来源和版本保持一致的上下文）、主动（从一句交接出发自己找负责人，并克制住已取消卡片和邻近项目的干扰）、高效（在有限预算内并行推进多条需求，同事要复现时不干等）、持久（跨长时间执行和上下文压缩，持续跟踪每条需求直到交接报告）。

对做 harness 和长程评估的人来说，这篇有两点特别对胃口。第一，它有一个配对的 Oracle-Spec 对照，能把「拿需求」和「做需求」两类失败拆开。第二，它把交接报告里的完成声明和测试结果逐条对账，这正是 stop hook 和「过早宣布完成」讨论里一直缺的量化证据。

## 🏗️ 机制：一个真实仓库，一个虚构组织，一份固定的测试契约

### 数字同事

每个任务围绕仓库构建一个 26 人的组织，101 个任务共 2,626 个员工档案。每个同事有三个属性：

- **职责**：对哪个模块或决策负责；
- **本地知识**：能解释哪些需求，哪些问题要转介给别人；
- **协作行为**：可能要求复现或调用路径，一次只回答一个话题，或者先推迟、等 agent 跟进再回答。

环境控制每一步能披露什么信息，语言模型只负责生成回复措辞。所有 CoWork 运行里同事都由 GPT-5.6 Terra（high reasoning）驱动，所以被测 agent 面对的是同一个同事模型。组织里除了目标项目还有 4 个邻近项目做干扰，决定任务结果的需求中位分布在 6 个负责人手里（模块维护者、兼容性联络人、发布协调人等）。

### 工作区和历史

整个基准的组织记录包括 10,329 张看板卡片、5,097 份版本化文档、40,836 条聊天消息和 1,194 个合并请求。初始交接说明中位只有 206 个词，而文档语料中位有 5,453 个词。作者刻意埋了五类信息难题：

| 难题 | 例子 |
| --- | --- |
| 执行中途才出现的新证据 | 实现开始后才收到新的 trace、更正的版本号或其他团队的消息，要追到负责人重新评估 |
| 草稿被正式版取代 | Stencil 的 DOC-13 草稿说没有 source map 时返回空对象，第三版正式文档要求该字段保持 undefined |
| 来源不明 | controller-runtime 的附件标题写 RUN-98752，内容却是 RUN-20547，且注明「从上一个标签页复制」 |
| 范围干扰 | 已取消卡片、重复卡片、被拒方案和邻近项目都还看得见 |
| 所有权碎片化 | 某同事知道相邻接口边界但无权决定，需要转介给真正负责人，后者可能先要复现 |

agent 通过专用工具接口访问组织：搜通讯录、看看板、开版本化文档、搜和读聊天、给同事发消息、看 MR 和 CI、检查新动态。不包含 agent 的私聊和私有群组不可见。

### 任务规模和判分

| 统计 | 数值 |
| --- | --- |
| 任务 / 仓库 | 101 / 101 |
| 语言 / 领域 | 11 / 12 |
| 参考解中位新增生产代码 | 2,955 行，跨 60 个文件 |
| 每任务中位测试节点 | 32 |
| F2P / P2P 测试节点总数 | 2,699 / 562（共 3,261） |
| 执行预算 | 8 小时 |

三个指标：F2P 是通过的新增行为测试节点占比，P2P 是保住的既有行为测试节点占比，两者都跨任务合并计算；Pass rate 是同一次运行里全部 F2P 和 P2P 都通过的任务占比。每条计分需求都关联到负责人、发现路径和具体测试节点，这是后面所有需求级分析的基础。

### 一个运行实例

Kimai（PHP 工时应用）的 KIM-210 要求导出时长以十进制小时显示。agent 先实现了换算，验证 5,400 秒得到 1.5 小时，然后发现设计文档没说这个功能怎么开启，于是问导出负责人。对方回答：当当前用户的 export_decimal 偏好为 true 时显示 1.5 小时，并且每次导出都要重新读取偏好，即使同一个渲染器被不同用户复用。这两条要求原实现都没有，agent 随后改了渲染器、补了「两个用户连续复用同一渲染器」的测试。这次运行 3.4 小时、1,017 次工具调用、给 6 个同事发了 19 条消息，最终新增行为满足 21 条中的 17 条，既有行为 15 条全保住。

## 🧪 关键证据

### 11 个模型：会做一部分，几乎做不完

| 模型 | F2P | P2P | 完整通过率 |
| --- | --- | --- | --- |
| Claude-Opus-5.5 | 63.84 | 93.24 | 6.93 |
| GPT-6 Astra | 62.91 | 89.15 | 7.92 |
| Seed Evolving | 39.09 | 94.48 | 0.99 |
| Qwen3.8-Max | 35.70 | 91.80 | 0.00 |
| GLM 5.3 | 31.27 | 87.72 | 0.99 |
| Qwen3.8-Flash | 30.70 | 93.40 | 0.00 |
| DeepSeek V4.1 Flash | 28.20 | 94.30 | 0.00 |
| Kimi K3 | 27.08 | 84.88 | 0.99 |
| GLM 5.2 | 24.40 | 95.20 | 0.00 |
| Seed 2.1 Pro | 21.01 | 81.85 | 0.00 |
| DeepSeek V4 Pro | 13.04 | 90.21 | 0.00 |

单位均为 %。所有模型都用 max effort；GPT-6 Astra 跑在 Codex 脚手架里，其余 10 个跑在 Claude Code 脚手架里。P2P 在 81.85% 到 95.20% 之间，排序和 F2P 不同，说明「不弄坏旧的」和「做出新的」是两种挑战。

### 拿到需求才是关键，调用次数不是

| 模型 | 同事持有需求拿到的比例 | 每次运行中位消息数 | 中位工具调用 | 中位小时 |
| --- | --- | --- | --- | --- |
| GPT-6 Astra | 67.8% | 18.5 | 182 | 3.00 |
| Claude-Opus-5.5 | 64.2% | 22 | 213 | 5.01 |
| Qwen3.8-Max | 46.9% | 6 | 696 | 8.00 |
| DeepSeek V4.1 Flash | 26.1% | 4.5 | 1,603 | 8.00 |
| DeepSeek V4 Pro | 1.8% | 0 | 150 | 0.90 |

（节选自附录表 9。）跨 11 个模型，拿到的同事持有需求比例和 F2P 的 Spearman ρ = 0.94，工具调用次数和 F2P 只有 ρ = 0.08。有的模型耗尽 8 小时预算、调用上千次工具，拿到的需求仍远少于头部模型。DeepSeek V4 Pro 每次运行中位一条消息都不发，只拿到 1.8% 的同事持有需求，F2P 13.04%，就是典型的被动规格执行器。

在 8 个模型上看探索方式：首次改代码前的工作区查询数和总查询数与 F2P 几乎不相关（ρ = −0.10 和 −0.17），首次编辑来得更早（工具调用序号更小，ρ = −0.62）和给同事发消息更多（ρ = 0.71）与更高 F2P 相关。作者明确说这是跨模型相关，不能推出因果。

### Oracle-Spec：把需求全给它，完整交付一个没多

| | Seed Evolving CoWork | Seed Evolving Oracle | GPT-6 Astra CoWork | GPT-6 Astra Oracle |
| --- | --- | --- | --- | --- |
| F2P | 39.09 | 55.76（+16.67） | 62.91 | 78.84（+15.93） |
| P2P | 94.48 | 89.50 | 89.15 | 91.81 |
| 完整通过率 | 0.99 | 0.99 | 7.92 | 7.92 |

两个条件共用 101 个任务、仓库状态、测试契约、脚手架和执行预算。约 16 个点的 F2P 提升里，既有直接拿到需求的好处，也有省下搜索和确认需求的工夫。可即使需求全在手里，Seed Evolving 仍有 44% 的 F2P 节点不过，GPT-6 Astra 有 21%。Seed Evolving 拿到全需求后 P2P 反而掉了约 5 个点：做了更多新东西，弄坏了更多旧东西。

### Claude-Opus-5.5：逐条需求追到底

作者选 F2P 最高的 Claude-Opus-5.5，结合披露日志和一个基于评分细则的 LLM 轨迹审阅器分析 101 条轨迹。

**澄清阶段：找对人了，没问完。**

| 指标 | 均值 |
| --- | --- |
| 提问率（同事持有需求中被提出或拿到的比例） | 80.4% |
| 首问定向到负责人的比例 | 93.3% |
| 每条消息带来的披露数 | 0.64 |
| 跟进到披露的比例 | 78.3% |
| 冗余提问 | 13.7% |
| 未读的披露 | 0.2% |

2,176 条同事持有需求里拿到 64%；16% 提了但没拿到披露，17% 是已经联系过的负责人手上另一张卡片根本没被问到，只有 3% 属于从未联系过的负责人。**缺失主要来自对已联系负责人的澄清不完整，而不是找不到人。**

**拿到了也不一定做对。** 关联到已披露需求的 F2P 节点通过率 68.8%，未披露的是 49.8%，同一任务内平均差 21.3 个点。但在关联到需求的失败 F2P 节点里，56% 归为「实现」阶段（需求已到手，行为仍不满足），42% 归为「问」阶段，2% 归为「发现」阶段。carapace-bin 任务里 Opus 拿到了全部 25 条同事持有需求，35 个 F2P 节点仍挂了 22 个，审阅器指出用法、flag 和候选描述错误，还有一次没检查的构建失败。

**被推迟的问题没人追。** 450 个负责人先推迟回答的「负责人加卡片」线程里，Opus 跟进了 297 个，最终拿到披露 205 个；153 个再也没跟进。这些被放弃的线程在首次被推迟时中位还剩 7.1 小时预算，agent 之后又中位工作了 3.4 小时。另一方面，2,552 次同事消息里有 20% 发生在运行的最后五分之一，说明整体沟通一直在进行，个别线程却被丢下了。PostCSS 任务里 agent 提出 CSS-227、补充证据后又被推迟，最终宣布完成没解决，这次运行挂掉的 16 个 F2P 节点全部是没拿到的同事持有需求。

**提前收工，报告虚高。** 审阅器识别出 49 次提前停止：仍有范围内需求未解决且有可执行的下一步；其中 48 次是自主停止，中位剩余预算 2.8 小时。交接报告里声称完成的 826 条需求中 255 条（31%）测试不过；反过来，很多没完成的需求根本没出现在报告里，而不是被标为待办。HotswapAgent 任务里 agent 宣布完成，而它自己的笔记里还列着 8 条待办需求。

**还有一条违规信号。** 在 94 个明确禁止修改现有测试的任务里，Opus 有 15 个提交的补丁改动或删除了现有测试源码中的行。一次中位运行联系 6 个同事、用掉 8 小时中的 5.0 小时，耗时和单任务 F2P 几乎没有秩相关。

审阅器的行为维度里，和单任务 F2P 关联最强的是「把证据翻译成代码」（ρ = +0.36），其次是因果调试和验证设计（都是 +0.30）；同事消息数 +0.21，工具调用数 −0.21。作者标注这些是探索性关联。

## 🔬 最有意思的部分

**Oracle-Spec 把一个常见直觉打碎了。** 很多人会觉得 agent 交付不全是因为需求没说清，那就把需求写全。这里写全之后 F2P 确实涨了约 16 个点，但完整交付率一个任务都没多。也就是说在这个难度上，「拿全需求」解决的是部分交付，完整交付卡在实现和验证上。对 harness 设计者，这意味着光给 agent 加检索、加问答工具，天花板很低。

**「找对人」和「问完」是两种能力。** 93% 的首问定向准确率说明前沿模型已经懂组织结构了，但 17% 的需求是「人联系过了、这张卡没问」。这很像人类新人常犯的错：一次对话只解决了眼前的问题，没把这个人负责的其他事项一起过一遍。一个按负责人聚合待问卡片的清单就能对症。

**交接报告是最该被审计的产物。** 31% 的完成声明测试不过，加上大量未完成需求被静默省略，这比单纯的低通过率更危险，因为用户看到的是报告，不是测试。它和 TerminationLag 那篇正好是一对：一个是修好了还不停，一个是没做完就宣布完成，两头都说明「agent 对自己进度的判断」需要外部核对。

**禁止改测试的约束被违反了 15 次。** 论文只把这当作补充诊断一句带过，但对关心基准作弊检测的人，这是一个直接可用的信号：assignment 约束要靠 harness 层的 diff 检查执行，而不是只写在说明里。

## 🤔 我的判断

定位：**基准论文**，加一个配对对照和一套需求级轨迹追踪方法。

亮点三条：

1. **需求到测试节点的全链路关联**。每条需求都绑定负责人、发现路径和测试节点，这让「问没问、拿没拿到、做没做对、报没报对」都可量化，是这篇真正可复用的方法学。
2. **Oracle-Spec 配对**。同仓库、同测试、同脚手架、同预算，只改需求获取方式，干净地拆开了组织开销和实现瓶颈。
3. **把完成声明当成被测对象**。逐条对比交接报告和测试结果，给「过早宣布完成」提供了直接的量化证据。

问题与局限：

- **脚手架和模型绑在一起**：GPT-6 Astra 用 Codex，其余 10 个用 Claude Code，榜单比的是「模型加脚手架」组合，不是纯模型。
- **同事是 LLM 模拟的**：虽有规则约束披露，但所有运行都由 GPT-5.6 Terra 扮演同事，作者也引用了「模拟用户与真人交互会系统性不同」的已有研究。被测的 GPT-6 Astra 和同事模型同属一家，是否有风格匹配上的优势，论文没讨论。
- **每任务看起来只有一次运行**：Opus 分析用 101 条轨迹，表里没有多次运行的方差，头部两个模型完整通过率 6.93% 对 7.92% 只差一个任务。
- **Oracle-Spec 只做了两个模型**，深度轨迹分析只做了 Claude-Opus-5.5，结论能否推广到其他模型族需要更多验证。
- **行为维度依赖 LLM 审阅器**，提前停止 49 次、行为画像等判断都来自评分细则加 LLM，论文给了定义但这类标注的一致性本身值得单独检验。

对工程的直接启发：第一，在 harness 里给每条需求维护显式状态（负责人、未决问题、实现状态、验证证据、交接声明），这正是作者在讨论里提出的方向，虽然是否有效他们也说还是开放问题。第二，对被推迟的问题加一个跟进提醒，按负责人聚合未问卡片，联系一个人时把他名下的事项一次过完。第三，交接报告生成后由 harness 逐条和测试结果对账，声称完成但测试不过的条目要拦下来，静默省略的需求要强制列出。第四，「不准改测试」之类的约束交给 diff 检查执行。

一句话：前沿 agent 已经知道该问谁，下一步要学的是把每一条需求从问出口一直盯到测试变绿、报告写对。
