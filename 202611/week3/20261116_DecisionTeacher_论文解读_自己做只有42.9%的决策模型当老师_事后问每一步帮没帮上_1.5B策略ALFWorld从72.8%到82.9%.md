# 自己上手只做成 42.9% 的决策模型，凭什么当老师？ZJU 把 JEV 拆成 Actor、Judge、Teacher 三个角色：事后看完整条轨迹、只问「这一步帮没帮上」，1.5B 策略在 ALFWorld 从 72.8% 涨到 82.9%

你有没有过这种体验：给 agent 挂了一个便宜的决策模型做 gate，先拿它直接当 policy 试了一下，发现它连「先加热杯子再放桌上」都做不对，于是顺手判了它死刑，觉得这种模型拿来打分也靠不住。决策模型这条线（JEV、GPT Decisions、Decider v1.2）过去几个月的评测几乎都是这么做的：**看它当 actor 能做成多少**。但 judge 和 actor 其实是两种问题，**一个不会做题的模型，能不能看完别人的答卷之后判得准？**

浙江大学和百度的 **Actor, Judge, or Teacher? Understanding Decision Models in Long-Horizon Agents** 就专门拆这件事：同一批决策模型、同一批 ALFWorld 任务，分别当 Actor（选下一步）、Judge（给记录好的轨迹逐步打分）、Teacher（训练时给 policy 的每一步打分，加进 GRPO 的优势里）。看完我的感受是：**这篇真正的产出不是「JEV 能当老师」，而是给 judge 设计了两个旋钮（看到多少、问什么），而且证明了这两个旋钮可以在训练前用录好的轨迹便宜地筛出来。**

## 核心摘要

作者比较三个专用决策模型（JEV、Decider v1.2、GPT Decisions）和三个通用 LLM 的决策化用法（Qwen3.8-27B 提示词输出 JSON、Qwen3.8-27B 首 token 概率约束读出、GPT-6 Luna 提示词），全部关推理。当 Actor 时六个模型都栽在「有顺序依赖的子目标」上：JEV 在两个独立子目标的 Pick2 上做成 70.8%，在必须先清洗、加热或冷却的任务上单项最高 18.8%；在 116 个「一步就能完成简单子目标」的诊断状态里，JEV 把 63.8% 的概率给了「直接放下」，只给前置子目标 14.6%，把简单子目标从目标里删掉后变成 2.5% 和 77.6%，说明它知道该做什么，只是被简单的那个吸走。加一句「考虑任务要求之间的依赖」只改变成功率 -2.8% 到 +5.2%。当 Judge 时，作者改两个变量：上下文是到当前动作为止（Prefix）还是整条轨迹（Hindsight），问题是「做完这步任务会成功吗」（Value）还是「这步帮助达成目标了吗」（Progress）。Hindsight 加 Progress 下，JEV 给里程碑动作的分比同轨迹空操作高 0.36，Value 只高 0.05，因为整条轨迹可见时每一步对「会不会成功」的答案都一样。当 Teacher 时，JEV 的分数在组内中心化后乘 λ=0.5 加到 GRPO 结果优势上：Qwen2.5-1.5B 在 ALFWorld 从 72.8% 到 82.9%、WebShop 从 56.8% 到 71.4%，7B 从 77.6% 到 83.8%、66.1% 到 73.6%，1.5B 加老师在两个环境都超过只用结果奖励的 7B；每次训练的 JEV API 费用 22.21 到 30.07 美元。代码在 https://github.com/ZJU-REAL/decision-agents 。

## 🎯 为什么这件事值得写

决策模型的卖点是「问一个问题，返回带概率的类型化答案，又快又便宜」。在 harness 里它天然有两种用法：选动作，或者评估已经发生的动作。可现有工作（作者引用的 JevAgentHarness、Yang 等对 JEV 选动作的研究）基本只在前一种上做文章，而且结论偏负面：被提到任务物体的命令吸引、跳过前置子目标、顺序做反。

问题在于，步级监督本来就贵。结果奖励给一条轨迹里每一步一样的信用；PRM 需要每个领域的步级标注；LLM judge 每一步问一次又慢又贵。如果一个冻结的决策模型在 episode 结束后能给每一步打出有区分度的分，那就是一条几乎零工程成本的过程奖励来源。这篇的问题就是：**actor 表现差，能不能推出 judge 和 teacher 也差？** 答案是不能，而且差在哪里、怎么问才对，作者给了相当干净的拆解。

对我们关心的「决策模型当 judge/gate」这条线，它补上了一个此前没人系统做过的问题：**gate 的问题措辞和可见上下文，本身就是要调的超参。**

## 🏗️ 机制：三个角色、两个旋钮

| 角色 | 问题形式 | 看到什么 | 输出怎么用 |
| --- | --- | --- | --- |
| Actor | 多选：下一步做哪个动作 | 目标、历史、当前观测、候选动作 | 选中的动作被执行 |
| Judge | 是否题：对录好轨迹里的某个动作打分 | Prefix 或 Hindsight，结果标签被遮住 | 分数在 [0,1] |
| Teacher | 同 Judge，但对象是正在训练的 policy 的 rollout | 默认 Hindsight + Progress | 加进 GRPO 优势，测试时不调用 |

Judge 的两个旋钮：

- **看到多少**：Prefix 只到目标动作，连执行后的观测都不含；Hindsight 是整条轨迹。中间还有加上即时反馈、再揭示后续 25%、50%、75% 的梯度。
- **问什么**：Value 问「这一步之后任务会成功吗」，Progress 问「这一步帮助达成目标了吗」。

Teacher 的融合方式很朴素：对任务 u 的一组轨迹，Teacher 给每个已执行动作打分 $s_{i,t}=D(g,\tau_i,t)\in[0,1]$，输入只有目标和轨迹中的观测与动作，没有环境奖励、成功标签或隐藏状态。然后

$$A_{i,t}=A^{\mathrm{out}}_{i,t}+\lambda\,(s_{i,t}-\bar{s}_u),\quad \lambda=0.5$$

其中 $\bar{s}_u$ 是组内所有被打分动作的均值。作者刻意不除以标准差，理由是如果 Teacher 对一组动作打的分都差不多，就只该给很小的修正，不应该被放大。每个动作的优势分给它生成的所有 token。训练用 veRL 的 PPO 式更新，150 步，每批 16 个任务、每个任务 8 条 rollout，ALFWorld 每条最多 30 个动作，WebShop 最多 15 个。

通用 LLM 怎么「装」成决策模型也写得很清楚：提示词版让模型输出 JSON 再解析；约束读出版取合法答案标签的首 token 概率，再在合法标签上归一化，是否题就在 Yes 和 No 上归一化。

## 🧪 关键证据

### Actor：知道该做什么，但被简单子目标吸走

| Actor | Pick2（无依赖） | Clean / Heat / Cool | 全部 |
| --- | --- | --- | --- |
| JEV | 70.8 | 11.1 / 18.8 / 16.0 | 42.9 |
| Decider v1.2 | 83.3 | 55.6 / 18.8 / 40.0 | 63.6 |
| GPT Decisions | 62.5 | 29.6 / 25.0 / 24.0 | 52.9 |
| GPT Luna | 37.5 | 18.5 / 0.0 / 4.0 | 34.3 |

在提示里加一个「加热杯子再放上桌」的顺序示例，Qwen 约束读出从 41.7% 到 58.3%，GPT Decisions 从 20.8% 到 32.1%，JEV 只从 19.0% 到 24.1%，Decider v1.2 反而从 89.7% 降到 85.3%。作者的结论是：真要让决策模型去行动，把目标改写成有序子目标比往提示里塞提醒更靠谱。

### Judge：Progress 问题才有区分度

在 462 条至少含一个里程碑和一个空操作的 ALFWorld 轨迹上（Hindsight 上下文）：

| 问题 | 里程碑 / 其他 / 空操作 平均分 |
| --- | --- |
| Value | 0.632 / 0.604 / 0.577 |
| Progress | 0.659 / 0.440 / 0.298 |

Recall@R（一条有 R 个里程碑的轨迹里，分数最高的 R 步有多少是里程碑）上，Progress 在每个 R 都比 Value 高 8.0% 到 16.0%。六个 judge 都是同一方向。

成本上，Decider v1.2 比它的底座 Qwen3.8-27B 提示词版漏掉更少里程碑（36.5% 对 49.6%）、更少空操作（57.1% 对 80.8%），每次打分便宜约 43%；GPT Decisions 对 GPT Luna 是 50.2% 对 54.1%、61.1% 对 78.4%，便宜约 28%。

### Teacher：四种组合里只有一种明显赢

| 1.5B 策略 | ALFWorld 全部 | WebShop 成功率 |
| --- | --- | --- |
| GRPO（只用结果奖励） | 72.8±3.6 | 56.8±3.8 |
| Prefix + Value | 79.0±3.6 | 67.7±0.5 |
| Prefix + Progress | 78.3±0.4 | 66.6±0.2 |
| Hindsight + Value | 69.3±0.7 | 68.3±1.5 |
| Hindsight + Progress | 82.9±2.9 | 71.4±0.7 |

在有依赖的任务上 Hindsight + Progress 达到 86.8%，比其他三种高 6.9% 到 16.2%。按动作数截断看，20 步内完成 74.5% 的 ALFWorld 任务，其他设置是 63.6% 到 69.5%；WebShop 10 步内完成 71.1%，其他是 60.9% 到 62.2%，也就是说它不光做得成，而且做得更快。

泼冷水的地方要先说清楚：**GRPO 基线数字直接引自 GiGPO 论文，不是作者在同一套设置下重跑的**；表里也没有放 GiGPO 这类已经做步级信用的基线，所以「比 GRPO 好」不等于「比现有最好的步级信用方法好」。Teacher 实验只用了 JEV 一个模型。

## 🔬 最有意思的部分

**Hindsight + Value 比纯 GRPO 还差（69.3% 对 72.8%）。** 这是整篇最有教育意义的一格。看完整条轨迹再问「会不会成功」，judge 实际上只是把结果奖励又复述了一遍，所有步拿到近似的分，组内中心化后几乎是噪声。同样的模型、同样的上下文，换成 Progress 就是最强的一格。**看得多不等于判得好，问题必须落在单个动作上。**

**一个具体轨迹把三个角色串起来。** 任务是把加热过的杯子放进柜子。轨迹里先把没加热的杯子放进柜子（第 6 步），再拿出来、去微波炉、加热、放回。Prefix 下 JEV 给「过早放入」0.79，给「走到微波炉」0.23、「打开微波炉」0.20，跟它当 Actor 时偏爱简单子目标是同一个毛病；加上即时反馈后放入升到 0.90，微波炉两步反而降到 0.22 和 0.18。直到可见的后续包含「加热杯子」，打开微波炉才升到 0.66，看完整条轨迹是 0.76。作者测了平均排名漂移：加即时反馈相对 Prefix 移动 1.95 个位置，看完整条轨迹是 3.30。**这说明 hindsight 的价值恰恰集中在 actor 最容易做错的那类动作上。**

**judge 可以在训练前筛。** 作者在录好的轨迹上用 Judge 指标比较四种问法和上下文，选出的正是后来训练效果最好的那一格，花的钱只是一次 RL 训练的零头。这对任何想把 LLM 或决策模型当 reward 的人都是一个可以照搬的流程：**先离线评 judge，再上线训 policy，按 judge 质量选，不按 actor 能力选。**

## 🤔 我的判断

定位：**一份把「决策模型当 judge 和 teacher」拆干净的测量研究**，方法本身很朴素（组内中心化加到优势上），价值在于控制变量做得细。

亮点三条：

1. 三角色在同一批任务和模型上对照，直接回答了「actor 差能不能推出 judge 差」，答案是不能。
2. 两个旋钮（Prefix/Hindsight、Value/Progress）各自的作用都有单独证据，并且 Hindsight + Value 这个反例把「问题措辞」的权重钉死了。
3. 成本透明：每次训练 22 到 30 美元的 JEV 调用，测试时不需要 Teacher，决策模型比同底座提示词版更准更便宜。

问题与局限：

- **任务短**：两个文本环境，每条最多 30 个动作。作者自己也承认软件工程、工具调用这种更长更乱的依赖关系里是否成立是开放问题。
- **只适用于离线**：Hindsight 需要 episode 结束。论文明说决策模型「不太适合在线过滤动作」，这恰好是很多人想拿它做的事（运行时 gate、stop-hook 判断）。在线场景只有前缀，而前缀判断正好继承了 actor 的偏差。
- **基线偏弱且非同条件**：GRPO 数字引自 GiGPO，没有和步级信用方法对比；Teacher 只试了 JEV。
- **黑盒**：JEV 和 GPT Decisions 的适配方式都未公开，没法知道是哪种训练让它成为好 judge。

对工程的直接启发：如果你在 harness 里用决策模型做验收门或 stop 判断，**把问题从「任务会成功吗」改成「这一步对目标有贡献吗」，并且尽量在拿到后续证据之后再判**；更实际的一条是，换 judge 模型或改 judge 提示词之前，先在一批录好的轨迹上测里程碑和空操作的区分度，这个离线测试比上线看效果便宜得多。对「运行时 gate 只能看前缀」的场景，这篇其实是一个警告：前缀判断会犯和 actor 一样的错。

一句话：会不会做和会不会判是两种能力，决策模型的价值取决于你问它什么、什么时候问。
