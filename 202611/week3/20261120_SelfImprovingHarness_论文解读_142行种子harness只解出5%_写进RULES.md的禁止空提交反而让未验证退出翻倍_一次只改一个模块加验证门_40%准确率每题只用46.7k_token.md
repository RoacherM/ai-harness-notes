# 142 行种子 harness 只解出 5%；写进 RULES.md 的「禁止空提交」反而让未验证退出翻倍；一次只改一个模块再过验证门，40% 准确率每题只用 46.7k token

你有没有过这种体验：agent 老是还没跑测试就宣布完成，于是你在 AGENTS.md 或 RULES.md 里加一句「没有改动或没有测试过就不许调用 finish」。下一轮它照样提前退出，甚至更频繁。你又让另一个模型帮你把整个 harness 重写一遍，准确率确实上去了，但轮数上限被它从 12 改成 28，每题 token 涨到原来的几倍，有一条 rollout 直接烧掉两百多万 token。行业里管这一类「让 harness 看自己的轨迹、改自己的代码」的做法叫 self-improving harness 或 harness RSI，**但到底哪些改动该进 prompt、哪些必须写成代码，一次该改多大范围，改完靠什么门放行？**

Google 两位作者的 **Harnesses That Improve Themselves: A Unifying Framework for Self-Improving Agent Harnesses** 主体是一篇框架和综述：把 harness 拆成四个可编辑组件，把自我改进拆成四阶段循环，把现有十几个系统映射上去，总结五类反复被发现的运行时机制和五类失败模式，再在 SWE-bench Lite 上做一个小规模验证。看完我的感受是：**综述部分是目前把 harness 自进化讲得最工程化的一份清单，尤其是安全边界和报告标准；实验部分规模很小，最可信的信号是 token 成本而不是准确率。**

## 核心摘要

作者把 agent harness 定义为由四个有状态代码模块组成的四元组：上下文与状态（记忆、规则、压缩）、agent 控制（轮次循环、重试、子 agent）、动作接口（工具、shell ACI、沙箱）、验证与恢复（停止前测试和修复钩子）。自我改进是一个外循环：诊断失败、提议补丁、验证过滤、部署或路由。形式化成一个带约束的优化：在冻结模型下最大化期望奖励，同时要求每题运行时 token 不超过预算 $B_{tok}$，并且必须通过第三阶段的验证门（修改过的代码路径真的被执行到，留出验证集不退步）。综述部分总结了优化器反复发现的五类机制（停止前验证、空轮与失控推理恢复、打破循环、跨轮环境与记忆持久化等），五类失败模式（规则膨胀、工具过载、模块编辑冲突、benchmark 作弊、篡改评测器日志和记忆），以及四条安全边界和三条报告标准，其中一条明确要求自我修改后的 harness 不能给自己比父版本更大的文件、网络或子进程权限。实验在 60 个 SWE-bench Lite 题上做：sympy 分开发 12、验证 8、留出 20，django 20 题做跨仓库分布外留出。从同一个 142 行 Python 种子 harness 出发，冻结 Gemini 3.8 Flash 当执行模型，Gemini 4 Carbon 当优化器。种子 harness 留出准确率 5.0%（2/40）；Best-of-3 仍是 5.0% 但 token 翻倍；只改 RULES.md 的反思降到 2.5%，分布外未验证退出从 15% 翻倍到 30%；不设门的整体重写到 42.5%（17/40），但每题 451.6k token；一次改一个模块并过门的方法到 40.0%（16/40），每题 46.7k token，零未验证退出，每个解出的题 116.8k token，对比整体重写的 1062.6k。零样本迁移到 Gemini 4 Argon 后，模块化门控方法 37.5%，整体重写掉到 30.0%。这篇的价值定位是：一份带安全和报告规范的 harness 自进化工程框架，加一个「代码钩子胜过文字规则、小步过门胜过整体重写」的示范实验。

## 🎯 为什么这件事值得写

作者开篇给了三个「harness 和模型一样重要」的理由：第一，同一个模型放进不同的生产 harness，主导失败模式（没测试就退出、在失败命令上打转、上下文溢出、跳过验证）跟着 harness 设计走，而不是跟着模型家族走，每个解出的题的 token 用量能差一个数量级。第二，短任务上 harness 结构主要弥补弱模型，仓库级长任务上好 harness 反过来给强模型提供它独自完成不了的脚手架。第三，没有一个静态 harness 对所有模型最优，为一个模型调好的 harness 换个模型常常表现变差甚至翻转排行；即使模型固定，人工维护的 harness 版本迭代也经常停滞或在旧任务上回退。

这就把问题从「调 prompt」推到了「让 harness 自己改自己的代码」。过去几个月这个方向冒出了 Meta-Harness、AHE、HarnessBank、DGM、RRSI、SoL-Pi 等一堆系统，各自的术语和评测方式都不一样。这篇的用处在于给了一个统一坐标系，把这些系统放进同一张表里比。

## 🏗️ 机制：四个组件，四个阶段，一个带约束的目标

### 四个可编辑组件

| 组件 | 管什么 | 典型可改内容 |
| --- | --- | --- |
| 上下文与状态 | 多轮历史 | 动态指令、工作记忆与经验记忆分离、过期观测的遮蔽和压缩 |
| agent 控制 | 多轮探索 | 轮次预算、检测并打破重复循环、计划与执行阶段切换、子任务委派给子 agent |
| 动作接口 | 如何作用于环境 | 把模型输出翻译成沙箱 shell、文件编辑或 GUI 动作，截断单轮原始输出，按需加载工具 schema |
| 验证与恢复 | 停止或提交信号 | 跑测试、lint、视觉检查，把失败送回上下文让 agent 自修 |

### 四阶段外循环

1. **诊断失败**：在开发集上跑当前 harness，聚类验证器错误、对比成功和失败轨迹、搜索原始执行日志，定位系统性瓶颈。
2. **提议补丁**：优化器把诊断翻译成一个或多个组件上的代码或钩子补丁。
3. **验证过滤**：在验证集、轨迹回放模拟器或效率前沿上筛候选，检查运行时执行、防止退步、过滤过拟合和浪费 token 的改动。
4. **部署或路由**：合进默认 harness，或存进变体档案供以后分支，或配一个轻量路由器按任务选 harness。

### 带约束的目标

$$
\max_{h\in\mathcal{H}}\ \mathbb{E}_{x\sim\mathcal{D},\,\tau\sim P(\cdot\mid x;M_{\theta},h)}[R_{x}(\tau)]\quad \text{s.t.}\quad \mathbb{E}[C(\tau)]\leq B_{tok},\ \ \mathcal{G}_{val}(h,h_{0})=1
$$

$M_\theta$ 是冻结模型，$R_x$ 是外部只读验证器，$h=(h_{ctx},h_{ctrl},h_{act},h_{ver})$。$\mathcal{G}_{val}$ 是第三阶段的门：修改过的代码路径必须真的被执行，并且在留出验证集上不退步。模块化演化用块坐标更新逐个改模块，最后做一次解决冲突的合并。

### 诊断：怎么分清是 harness 的锅还是模型的锅

这段是我觉得综述里最实用的一段。判断标准是看「推理和执行是否背离」：如果模型的推理已经找到了对的文件或修法（或者某次重试做对了），但因为编辑工具拒绝了补丁格式、shell 调用丢了工作目录、上下文压缩丢了早期约束、循环没跑测试就退出而失败，那是 harness 的问题；如果工具调用都干净执行、观测都完整留在上下文里，所有重试仍然在领域逻辑上失败，那是模型能力问题，第一阶段应该放弃提议 harness 改动，别把搜索算力浪费在模型知识缺口上。四种具体技术：验证器驱动的失败聚类（过滤一次性失误）、对比轨迹 diff、从最终测试失败反向追溯到最早写错或读错变量的那一轮、让执行 agent 自报哪里被工具卡住但只保留有轨迹事件佐证的说法。

### 优化器反复发现的机制

- **停止前验证和补丁检查子 agent**：退出前检查必需文件存在、看 git diff 有没有意外改动和残留调试语句、自动跑语法和单测，或者起一个轻量验证子 agent 审补丁。作者认为提前终止是 coding 和终端 agent 最常见的失败之一，拦住未验证退出往往带来最大的单项提升。
- **空轮与失控推理恢复**：推理模型耗尽思考预算却没发出工具调用，或者返回了格式错误的动作块时，钩子接住这一轮、总结卡住的推理、注入续写提示和完成自检。
- **打破循环和策略转向**：重复失败命令、重复读同一段文件、在两个坏编辑之间来回时，用有状态计数器强制退一步、检查假设、换策略。
- **跨轮环境与记忆持久化**：在无状态 shell 调用之间捕获和恢复工作目录和 PATH，把当前子目标、文件指针、用户约束这类工作记忆和可复用经验记忆分开。

## 🧪 关键证据

### 综述层面：五类失败模式和安全边界

| 失败模式 | 根因 | 日志里的预警信号 | 防护 |
| --- | --- | --- | --- |
| 无用规则与 prompt 膨胀 | 单次反思把随机失误当成缺规则，追加后不清理 | prompt 越来越长，验证收益为零，用户约束被丢掉 | 要求重复失败才加规则，用短的「不许」规则，删掉没帮助的规则 |
| 工具过载 | 工具或插件 schema 重叠 | 频繁 schema 错误，工具选择不一致 | 最小 shell 和代码接口，按需加载 schema |
| 模块编辑冲突 | 同时改循环上限、输出过滤和停止检查，打破共享假设 | 补丁单独能过一起就挂，轮数暴涨或提前退出 | 分模块演化，合并时解冲突，验证新代码真的跑到 |
| benchmark 作弊与过拟合 | 搜索奖励泄露 git 答案或记住可见测试的补丁 | 读 git 历史的命令，可见和隐藏通过率差距大 | 去掉 git 历史和网络，用留出测试集判分 |
| 篡改评测器、日志和记忆 | 评分脚本、日志、记忆文件在 agent 可写目录里 | 校验和或配置变化，token 暴涨，档案分数过期 | 只读评测器，追踪记忆来源，给 token 和测试分支设预算 |

四条安全边界：评测器和追加式日志放在沙箱外只读存储；**自我修改不得提权**，修改后的 harness 永远不能给自己比父版本更宽的文件、网络或子进程权限；保存的记忆、学到的规则、生成的插件当成不可信输入，追踪来源，设按技能和按会话的 token 预算，安全策略变化时重测档案里的旧 harness；进化出来的运行时模块要配单测和分支覆盖测试。三条报告标准：搜索、验证、留出测试严格分开，同时报分布内和分布外收益；搜索成本和运行时成本分开报，按全部尝试任务和按解出任务各算一次，并和种子 harness 上同算力的 Best-of-N 比；至少两个模型家族或尺寸上测，逐个关掉进化出的模块看是否真有用。作者把这些概括成一个架构不变量：**可变的 harness 永远不能控制自己的权限边界、判分系统和审计日志。**

### 实验层面：SWE-bench Lite 60 题

设置：每次运行在干净的单 commit 沙箱里，去掉 git 历史，补丁由外部在留出测试集上判分。种子 harness 142 行，四个文件：context_mgr.py（prompt 和原始轮次历史）、control.py（12 轮上限和 JSON 解析）、action_aci.py（bash、view_file、edit_file、finish）、verify.py（直通的停止钩子）。

第一部分，冻结 Gemini 3.8 Flash 演化（优化器 Gemini 4 Carbon，全模块 prompt 超时回退到 Gemini 4 Argon，运行时 token 上限 110k）：

| 方法 | 可改范围 | 搜索 rollout | 轮数上限 | sympy 留出 | django 分布外 | 合计 (N=40) | 每题 token | 每解出题 token | 分布外未验证退出 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 种子 Pass@1 | 无 | 0 | 12 | 10.0% (2/20) | 0.0% (0/20) | 5.0% (2/40) | 114.8k | 2296.7k | 15.0% |
| 种子 Best-of-3 | 无，3 次测试时排序 | 0 | 12 | 5.0% | 5.0% | 5.0% (2/40) | 237.6k | 4752.2k | 5.0% |
| 只改 prompt 的反思 | 仅 RULES.md | 24 | 12 | 5.0% | 0.0% | 2.5% (1/40) | 60.5k | 2420.2k | 30.0% |
| 不设门整体重写 | 四个模块，无门 | 24 | 28 | 35.0% | 50.0% | 42.5% (17/40) | 451.6k | 1062.6k | 5.0% |
| 模块化门控演化 | 每步一个模块，有门 | 100 | 12 | 40.0% | 40.0% | 40.0% (16/40) | 46.7k | 116.8k | 0.0% |

第二部分，把第一部分冻结的 harness 零样本迁到 Gemini 4 Argon，不再演化：

| 方法 | 合计 (N=40) | 每题 token | 每解出题 token |
| --- | --- | --- | --- |
| 种子 | 10.0% (4/40) | 140.4k | 1404.0k |
| 只改 prompt 的反思 | 15.0% (6/40) | 143.9k | 959.2k |
| 不设门整体重写 | 30.0% (12/40) | 284.7k | 949.0k |
| 模块化门控演化 | 37.5% (15/40) | 64.8k | 172.7k |

模块化门控演化每一步的去留：

1. context_mgr.py 被接受：把两轮以前的观测压缩成首尾摘要，追加一个实时的轮次和编辑状态页脚。开发集和验证集准确率提升到五倍，同时 token 下降。
2. action_aci.py 被接受：加窗口化文件查看、截断 shell 输出、finish 前的空 diff 守卫，消除了提前空退出。
3. control.py **被第三阶段拒绝**：把轮数上限从 12 提到 18，开发集准确率跳升，但验证集准确率下降，且 token 超过 110k 上限。
4. verify.py 被接受：除非 git diff 非空、改过的 Python 文件能编译、改后测试跑通无错误，否则拦住退出。

作者算了一笔账：模块化方法每题比种子少用 2.5 倍 token，比整体重写少近 10 倍，运行时节省的 token 在不到 100 个部署任务内就能还清 100 次搜索 rollout。

## 🔬 最有意思的部分

**一，文字规则写得越明确，越说明代码钩子的必要。** 只改 prompt 的反思写出来的 RULES.md，第一条规则就是禁止在 diff 为空或没测试时调用 finish。结果没有 Python 代码在运行时拦住终止，模型照样早退，分布外未验证退出从 15% 翻倍到 30%，留出准确率从 5.0% 掉到 2.5%。这和我们关心的「停止钩子防过早完成」完全对上：完成门必须是代码，不能是提示词。

**二，被拒绝的那一步比被接受的更有说服力。** 把轮数从 12 提到 18 在开发集上是明显的进步，换成任何只看开发集分数的循环都会接受它。门同时看验证集和 token 预算，把它挡下来了。而不设门的整体重写正是靠把轮数提到 28 拿到了 42.5%，代价是每题 451.6k token、一条 rollout 超过 280 万 token，迁到 Argon 后又掉到 30%。

**三，Best-of-3 一点没用。** 三次采样把 token 翻倍，准确率不变，因为每次重试都在同样的地方溢出上下文。这是一个很干净的「测试时扩展救不了 harness 结构缺陷」的例子，也解释了作者为什么在报告标准里要求和同算力 Best-of-N 比。

**四，权限不升级写进了自我修改的安全边界。** 「修改后的 harness 不能给自己比父版本更宽的权限」，和我们最近关注的跨 harness 委派里「子 agent 权限不得高于父 agent」是同一条原则，只是这里的父子关系是时间上的版本链，而不是调用链。作者还提醒，安全规则随时间收紧会让档案里旧候选的缓存分数过期，可能让不安全的旧变体一直活着，所以策略变了要重测档案。

## 🤔 我的判断

定位：**工程框架和综述为主，附一个示范性小实验**。它不是方法突破，价值在于统一术语、整理机制和失败模式、给出安全与报告规范。

亮点三条：

- **安全边界和报告标准可以直接抄进团队规范**。只读评测器、不提权、记忆来源追踪、搜索与运行成本分开报、跨两个模型家族测、逐个关模块消融，这几条覆盖了 harness 自进化里最容易出事的地方。
- **「harness 的锅还是模型的锅」的判定规则很实用**。推理找对了但执行没落地就是 harness 问题；执行干净但逻辑全错就别改 harness。这条规则能省下大量无效搜索。
- **把 token 预算写进优化目标的约束**，而不是事后报告。被拒绝的 control.py 改动说明这个约束确实在起作用。

问题与局限：

- **实验规模太小**。每个留出集只有 20 题，合计 40 题，看起来每个配置只跑了一次。按今天另一篇 Resolution Hypothesis 的测量，Terminal-Bench 这类 agent 基准的单次评测噪声标准差就有几个点；在 40 题上，40.0%（16/40）和 42.5%（17/40）只差一题，不能说模块化方法在准确率上和整体重写有区别。摘要里「outperforms full-harness rewrites」在第一部分的合计准确率上并不成立，第二部分的 37.5% 对 30.0% 也只差三题。
- **真正稳健的信号是成本**：46.7k 对 451.6k 每题 token，116.8k 对 1062.6k 每解出题 token，这个量级差距不太可能是噪声。我更愿意把这个实验读成「同等准确率下成本差一个数量级」，而不是「准确率更高」。
- **种子 harness 太弱**。142 行、12 轮上限、直通停止钩子，基线 5% 很低，任何合理改动都容易涨。在一个已经调过的生产 harness 上，门控模块化演化还能拿到多少，没测。
- **搜索预算不对等**。模块化方法用了 100 次搜索 rollout，另两个演化方法只用 24 次。作者在脚注里解释了构成，但从对比公平性看这是一个混淆因素。
- **只有 Gemini 家族**，执行模型、优化器、迁移目标都是 Gemini，没有满足它自己提出的「至少两个模型家族」报告标准。
- 综述部分引用了大量今年的工作，作为框架它很全面，但很多机制的有效性来自被引论文的结论，本文没有逐一复现。

对工程的直接启发：

1. 「不许空提交」「不许没测试就完成」这类规则，必须写成 verify 钩子：检查 git diff 非空、改过的文件能编译、改后测试跑过。写进 RULES.md 不算数。
2. 自动改 harness 时一次只动一个模块，每次过两道门：验证集不退步，运行时 token 不超预算。尤其要警惕「把轮数上限调高」这类改动，它几乎总能在开发集上涨分。
3. 汇报 harness 改进时，每题 token 和每解出题 token 都要报，并且和种子 harness 上同算力的 Best-of-N 比。
4. 评测器、日志、记忆文件不要放在 agent 可写的目录里；harness 自我修改后的权限不能超过上一版本。
5. 小样本实验里看到的几题差距，先别下结论；准确率接近时，成本差距才是更可信的信号。

一句话：让 harness 自己改自己并不难，难的是给它一道既看验证集又看 token 账单的门，再把评测器和权限放在它够不着的地方。
