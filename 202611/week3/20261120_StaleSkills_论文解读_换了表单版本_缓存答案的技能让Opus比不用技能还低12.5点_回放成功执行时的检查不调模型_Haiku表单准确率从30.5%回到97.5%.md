# 换了表单版本，缓存答案的技能让 Opus 比不用技能还低 12.5 点；回放成功执行时记下的检查，不调模型就能发现过期，Haiku 的表单准确率从 30.5% 回到 97.5%

你有没有过这种体验：上个月让 agent 把一套部署流程沉淀成 skill，里面写死了 Nginx 配置路径、API 端点名、表单字段编号，之后每次复用都又快又准。某天运维改了配置结构，或者上游 API 改了名，agent 还是按 skill 里的旧路径写文件，文件写进了 Nginx 根本不加载的位置，任务照样报完成。更隐蔽的情况是 agent 发现了不对，自己多查了几轮把活干完，成功率看起来没掉，但 skill 原本帮你省下的那些轮次全没了，而 skill 本身一个字都没改，下次还得再绕一遍。行业里管这种沉淀下来的可复用经验叫 agent skills，**但当环境在变，过期的 skill 到底是帮忙还是添乱？该什么时候修、修哪里？**

AWS Agentic AI 和南加州大学的 **When Agent Skills Go Stale: Runtime Behavior and Selective Maintenance in Evolving Environments** 在 TerminalBench-2、历年 IRS 税表、AppWorld、ScienceWorld 四个场景、Opus 4.7 和 Haiku 4.5 两个模型上测了这件事，并提出一种不需要变更说明的选择性维护方法。看完我的感受是：**这篇把「skill 过期」拆成了性能和成本两个维度，而且证明了只看成功率会漏掉一半问题；它和昨天的 ExperienceRot 是一对，那篇讲经验记忆随工具改名腐烂，这篇讲怎么在复用前把它查出来修掉。**

## 核心摘要

作者把 skill 跨执行携带经验的那部分（指令、代码、附带资源）叫 skill 状态 $\sigma_0$，在原环境 $W_0$ 里创建或验证，环境变成 $W_1$ 后原样复用。skill 价值定义为相对同一 agent 不带 skill 的基线的两个量：任务性能增益 $\Delta U$ 和执行成本相对减少 $S$（成本是 agent 轮数，ScienceWorld 用环境步数）。环境变化包括软件和配置更新、表单字段改号改名、API 端点改名、目标物体换房间，任务目标和评分标准不变。主要发现：在缓存型 skill 的八组比较里，环境变化后执行节省全部下降，性能增益七组下降；Opus 在 TB-2 上从 +4.7 点变成 -11.4 点，在 IRS 上从 +18.8 点变成 -12.5 点，在 ScienceWorld 上性能 -13.0 点且步数比不用 skill 多 38.9%。同一份过期 skill 对 Haiku 却仍然有正增益。作者对比了两种写法：过程型（写怎么在当前环境里查找和推导）和缓存型（把当时解析出的值和命令直接写死）。在 TB-2 和 IRS 上，缓存型在原环境省得更多，但环境变化后掉得更狠，四组比较全部如此。方法叫选择性维护：从 skill 内容和成功执行中自动构造可执行检查，记下原环境的观测；复用前不调模型地回放这些检查，有差异再由验证步骤判断是否真的和 skill 冲突并定位到具体内容；LLM 只修受影响的部分，修不好或定位不了就在新环境里按原流程重建；候选更新要在验证任务上同时过性能和成本标准才替换。全程不提供任何变更说明。相对复用过期 skill，Haiku 的缓存型 IRS 表单字段准确率从 30.5% 回到 97.5%（最高提升 67 点），ScienceWorld 步数最多减少 37%；IRS 上维护的一次性 token 成本在 21.2 到 41.9 次后续使用内回本。这篇的价值定位是：把 skill 生命周期管理从「失败了再说」推进到「复用前做便宜的执行回放检查」。

## 🎯 为什么这件事值得写

skill 的价值本质上是「摊销推理时计算」：今天留下的经验，减少以后同类任务需要的推理和环境交互。但 skill 里不可避免地会固化环境相关的细节：一个文件路径、一个字段编号、一个关于 API 行为的假设。环境一变，这部分就过期了，而其他部分可能仍然有用。

现有工作要么评测 skill 写得好不好、检索得准不准，要么研究 agent 怎么应对工具和接口变化，要么研究 skill 库怎么增删演化。这篇关注的是一个更具体的问题：**同一份 skill 状态，环境变化前后，它的价值怎么变？什么时候还有用，什么时候增加成本或降低性能，选择性更新能不能把价值拿回来？**

作者给出两个判断 skill 该不该维护的理由。检查「环境有没有变」太宽，很多变化根本不影响 skill 内容；等「任务失败」再修又太晚，会漏掉额外执行成本，而且部署时往往拿不到任务结果。所以需要一个只针对 skill 依赖的东西、不依赖任务结果的检查机制。

## 🏗️ 机制：两个价值维度，两种写法，一套维护流程

### skill 价值的两个分量

$$
\Delta U_t=U_t(\sigma_0)-U_t(\varnothing),\qquad S_t=\frac{C_t(\varnothing)-C_t(\sigma_0)}{C_t(\varnothing)}
$$

$\Delta U_t$ 是相对无 skill 基线的性能增益，$S_t$ 是相对执行成本减少。跨环境的损失 $L_U=\Delta U_0-\Delta U_1$，$L_S=S_0-S_1$。$\Delta U_1<0$ 叫负迁移：带着旧 skill 比不带还差。

### 四个场景和环境变化

| 场景 | 任务 | 指标 | 成本 | 环境变化 |
| --- | --- | --- | --- | --- |
| TB-2 | 30 个任务上的 38 个任务与变化对 | 通过率 | 轮数 | 审计过的软件包、配置、schema、文件变化 |
| IRS | 5 个表单族各 10 个申请人 | 字段准确率 | 轮数 | 历年表单修订，字段改号、改名、删除、新增 |
| AppWorld | test_normal 中 51 个任务 | 任务成功 | 轮数 | API 端点改名并更新文档 |
| ScienceWorld | 41 个导电性测试变体 | 归一化得分 | 环境步数 | 目标物体挪到 agent 起始房间，题面位置描述不变 |

TB-2 上两个模型都以 Claude Code agent 形式通过 Harbor 运行；IRS 每次最多 15 轮，AppWorld 50 轮，ScienceWorld 90 步。skill 由 Opus 4.7 按 Anthropic skill-creator 指南撰写，每个 skill 只创建一次，两个模型在变化前后原样使用。

### 两种写法

两种变体来自同一份 $W_0$ 素材、同一个作者模型，只改写作风格指令：

- **过程型**：写成可复用流程，描述如何在运行时检查环境、推导任务相关的值，不写死，用占位符。
- **缓存型**：尽可能直接缓存解析出的方案，环境相关的决定写成字面值，命令原样写进去，不留发现、检查、推导步骤，不留占位符和兜底，但永远不写任务答案。

作者把 skill 预先固化了多少环境相关选择叫「操作特异性」。

### 选择性维护流程

1. **构造执行接地的检查**：规则抽取 skill 指令和代码里的路径、命令、标识符；对字段写入、API 调用、环境动作这类操作，执行 skill 例程或回放成功运行中的代码。对支持的操作，构造过程不调模型，也不需要为每个 skill 手写测试。每条检查记录三样：对应的 skill 内容或已验证执行 $p_j$，可执行检查 $q_j$，原环境输出 $e_j^{(0)}$。检查在原环境重复跑，输出不稳定的丢掉。表单检查用带占位值的合成输入记录每次写入落在哪，不用申请人数据。
2. **复用前检查**：在当前环境不调模型地跑一遍，得到差异集 $D_t=\{j:q_j(W_t)\neq e_j^{(0)}\}$。为空就原样复用。
3. **验证差异**：观测变了不等于 skill 过期。简单冲突直接用执行档案判定，需要解释的由 LLM 验证器对比 skill 内容和新旧观测。不需要外部变更日志，没有支撑的差异不改 skill。
4. **修复或重建**：能定位的冲突由 LLM 只改受影响部分；定位不了或修复反复过不了验证，就在新环境里按原撰写流程重建，且不看旧 skill。先修后建，以保住仍然有效的内容。
5. **验证更新**：候选在当前环境的验证任务上跑，同时看性能阈值和成本目标，过了才替换，否则保留原 skill。验证任务与报告评测不相交。

执行任务的 agent 本身不变，维护只改 skill 状态。

### 写法的取舍（Table 2）

TB-2 和 IRS 上，缓存型在原环境的成本减少更多（四组里三组），变化后的性能损失也更大（四组全部）。例如 TB-2 上 Opus 的原环境成本减少，过程型 34.9%、缓存型 66.5%；性能损失过程型 -6.8 点（即变化后反而更好）、缓存型 16.1 点。IRS 上 Opus 两种写法起初的准确率增益相近，变化后过程型还保留 6.2 点增益，缓存型比无 skill 低 12.5 点；但过程型几乎丢光了原来的成本节省，缓存型仍然省轮数。AppWorld 和 ScienceWorld 上两种写法表现相近，因为变化击中的是两者都会存下的信息（端点名、题面给的位置）。

| 模型 | 写法 | 先检查当前表单 | 检查后仍写旧字段 | 准确率差（检查减不检查） | 轮数差 |
| --- | --- | --- | --- | --- | --- |
| Opus | 过程型 | 43/50 | 5/43 | +24 | +6.2 |
| Opus | 缓存型 | 30/50 | 2/30 | +68 | +10.4 |

两个模型都经常去看当前表单，但看了之后的行为不同：Opus 在 73 条检查过的轨迹里只有 7 条仍写旧字段，Haiku 在 80 条里有 36 条。作者也提醒这些是完整轨迹的相关性比较，不能单独归因到「检查」这一动作。

### 检测准确吗（TB-2，Table 12）

| 情况 | 总数 | 回放标出 | 验证确认 |
| --- | --- | --- | --- |
| 过程型冲突 | 22 | 15 | 9 |
| 缓存型冲突 | 29 | 19 | 19 |

两种写法合计，回放标出 51 个已标注冲突中的 34 个，验证确认 28 个；17 个漏掉的都是检查记录属性之外的字节级文件内容变化。62 个等价变化对照里，回放标出 7 个，验证否掉 5 个，剩下 2 个导致了不必要的过程型 skill 修复。IRS 上验证接受全部 10 个冲突变化，否掉 4 个字段名没变的表单修订；回放未变化的 AppWorld 环境，51 个任务一个都没标。

回放不调模型，IRS、AppWorld、ScienceWorld 上中位运行时间 0.2 到 4.3 秒（TB-2 没计时）。IRS 上重建消耗的模型 token 是修复的 1.24 到 2.28 倍。

## 🔬 最有意思的部分

**一，更强的模型更容易被过期 skill 伤到。** 同一份缓存型 IRS skill，Opus 的绝对准确率高于 Haiku（73.1% 对 30.5%），但相对各自的无 skill 基线，复用让 Opus 变差、让 Haiku 变好。四个场景里 Haiku 在两种写法下都保持正增益，Opus 有时不用 skill 更好。原因是强模型自己本来就能做得不错，旧 skill 带来的误导抵消了它的优势；弱模型没有 skill 几乎做不了（IRS 上无 skill 只有 .007 和 .046），哪怕是过期 skill 也比没有强。这对「skill 库在不同模型间共享」是一个重要提醒：skill 的实际价值取决于读它的 agent，而不只是 skill 本身。

**二，轮数少了可能是坏消息。** 缓存型 Opus 在 IRS 上的轮数减少，全部来自那些没去看当前表单的轨迹，而这些轨迹的准确率低于无 skill 基线；去看了的轨迹准确率更高但轮数更多。所以「skill 让 agent 更快了」不一定是好事，可能只是它在更自信地照抄旧答案。这跟我们关注的「自信完成」失败是同一类现象。

**三，看了不等于用了。** Haiku 在检查过当前表单的轨迹里仍然有 45%（36/80）往已经不存在的旧字段里写。读到新信息和据此修正行为是两件事，这也解释了为什么不能把希望全寄托在 agent 的运行时补救上，而要把修正落到 skill 状态里。

**四，检查是从「成功过的执行」里长出来的。** 和 SkillGuard 从 skill 文档里提合同去对照环境不同，这里的检查来自 skill 实际被验证成功的那次使用：路径存在与否、写入落在哪个字段、API 调用返回什么。好处是检查只覆盖 skill 真正依赖的东西，不会因为无关变化误报；代价是检查记录之外的变化（比如文件内容的字节级变化）会漏掉，TB-2 上 17 个漏报都属于这一类。

## 🤔 我的判断

定位：**测量加工程方法**。前半部分是对 skill 过期现象的受控测量，后半部分是一个实用的维护流程。

亮点三条：

- **性能和成本两个维度分开测**。「成功率没掉但节省没了」「轮数少了但准确率低于不用 skill」这两种情况，只看成功率都会漏掉。
- **过程型和缓存型的对照很有工程指导意义**。写死值的 skill 在稳定环境里省得多，环境一变掉得狠；写查找流程的 skill 更抗变化，但节省少。这是一个可以在写 skill 时就主动做的取舍。
- **回放检查不调模型、不要变更说明**。复用前花 0.2 到 4.3 秒跑一遍检查，代价很低，可以作为每次 skill 加载前的默认步骤。

问题与局限：

- **两个模型都来自 Claude 家族**，作者在局限里写了。强弱模型对过期 skill 的反应差异，在别的模型家族上是否成立未知。
- **受控变化每次只改一件事**，好让每个损失都能追溯到具体的过期内容。真实部署里多处同时变、长时间累积变化的情况没测。
- **只评估了一次维护事件**，接受更新后自动刷新执行档案留给了未来工作，连续多次维护的表现未知。
- **样本量小、单次运行居多**。IRS 每个申请人、AppWorld 每个任务、ScienceWorld 每个变体在每个条件下只跑一次，TB-2 大多数任务每个条件一次。Table 4 作者自己注明「着色不代表统计显著」，配对估计放在附录。像 AppWorld 缓存型 .627 到 .667 这样的小差距不宜过度解读，IRS 缓存型 30.5% 到 97.5% 这样的大差距才可靠。
- **维护模型用的是 Opus 4.7**，同时也是 skill 作者，修复质量受它能力影响；换成更小的维护模型效果如何没测。
- 回放检查对「文件内容变化」这类记录属性之外的变化是盲的，62 个等价对照里还有 2 个导致不必要的修复。

对工程的直接启发：

1. 写 skill 时区分哪些值该写死、哪些该写查找方法。对频繁变化的环境细节（配置路径、字段名、端点），优先写「怎么查」，必要时缓存值但附上查找流程作为兜底。
2. skill 首次成功执行时顺手记录依赖的环境观测（路径存在、写入位置、API 返回结构），复用前不调模型地回放比对。这是一个便宜的过期检测器。
3. 观测变了先验证再修：62 个等价变化里大部分被验证步骤否掉了，直接触发修复会造成不必要的改写。
4. 修复优先，重建兜底；修复的 token 成本低于重建。更新要在留出任务上同时过性能和成本两道门才替换。
5. 评估 skill 价值时一定要和同一个 agent 的无 skill 基线比，而且要分模型看。对强模型可能有害的 skill，对弱模型可能仍然有益。
6. 监控里别只看成功率和轮数，「轮数下降但准确率也下降」是 skill 过期的典型信号。

一句话：skill 省下的是以后的推理和交互，但它只在环境还认它的时候才省；复用前花几秒钟回放一遍当初成功时的检查，比事后靠成功率发现问题便宜得多。
