# API 返回 200，却悄悄忽略了一个过滤条件：judge 看出问题，agent 照样把错数字报出来。把决定权交给 harness、扣下数值后，七个开源模型的错答从 74.0% 降到 1.7%

你有没有过这种体验：agent 去查一个公开数据库「人类样本里满足条件 X 的有多少」，文档里那个过滤参数名写得有点不对，API 不报错，返回 HTTP 200 和一个看起来很合理的数字，其实是把那个过滤条件直接忽略了，数的是全量。agent 拿着这个数字写进报告，语气笃定。你加了 LLM judge，judge 说「这个数字可疑」，agent 回头看了一眼，把置信度从 1.0 降到 0.4，然后**还是报了那个数字**。行业里管这叫 silent failure、implicit tool error，现在的主流修法是 checklist、reviewer 模型、LLM judge、outcome monitor，**它们的共同点是：最后信不信这个结果，还是模型说了算。**

Virginia Tech 与 Genentech 的 **Invariant-Aware Harness Enforcement to Protect LLM Agents from Silent API Failures** 正面回答一个问题：如果模型能看见问题却还是答，那这个决定还应该交给模型吗？它的答案是 SilentGuard：在执行工具调用的 harness 里，对每个结果检验「任何正确 API 都必须满足的不变量」，过不了精确检验的值直接扣下，不给模型。看完我的感受是：**这篇把「证据、许可、强制」三件事在受控实验里拆开了，拆完以后结论非常干脆：只有强制在每个模型上都可靠；而且它是靠「说不知道」而不是靠「找回正确答案」做到的，作者自己把这一点写在了摘要最后一句。**

## 核心摘要

作者先在 15 个公开科研 API 上做探测：给每个 API 发无过滤查询、文档规定的过滤查询，以及两三个看似合理的错误过滤名。10 个 API 对至少一个错名返回 HTTP 200、恰好等于无过滤的计数、不带任何警告，最多虚高 691 倍；算上分页被悄悄截断、带错别字的过滤值被丢弃，11 个 API 至少有一种静默故障。然后在自建的 AgentOrchBench（8 个本地 REST 服务、400 条目录记录、答案是单个精确计数、服务端注入故障）上，用 7 个开源模型做受控对照：无防护时 74.0% 的故障运行报错数，checklist、reviewer、Outcome Monitors 都在 72% 到 74% 附近；judge 看到一致性检验结果时能把 82.4% 的故障运行标为可疑，但作为建议时仍有 71.2% 错答，被标记的运行里 77.4% 照报不误。给出「可以回答无法确定」的许可，警告后的错答从 70.1% 降到 18.2%，但各模型 0% 到 59% 不等。SilentGuard 用计数恒等式、列表成员检验、参数规格检验等精确不变量加从干净数据学来的契约，失败先重查一次，再失败时精确检验就扣下数值只接受经过检验的计数，学来的检验只警告。结果是错答 1.7%（单模型最多 4%），干净任务正确率 84.9% 不变；三个前沿模型从平均 70.2% 降到 0.5%。代价是覆盖率：故障下它大多回答「无法确定」，正确答案从 16.4% 降到 2.4%；对冻结后新写的六类故障，错答只从 61.1% 降到 24.5%。这篇的价值是把「harness 该有最终否决权」从口号变成了一组拆得很干净的对照实验。

## 🎯 为什么这件事值得写

大多数工具调用失败很好发现：报错、超时、格式坏了。静默失败不一样：状态码 200，响应格式良好、自洽，只是没有回答你发出的那个请求。作者特别强调，**在他们的故障里，光看响应本身无论如何看不出问题，必须向同一个 API 发额外查询才能发现。** 这就是为什么让模型「仔细看看结果」没用：结果里根本没有可看的东西。

现有修法都把模型放在决策位置：checklist 提示词让模型逐个检查结果，reviewer 模型在调用前审查，Outcome Monitors 从干净轨迹学契约并给可疑结果附一条不具约束力的警告，LLM judge 打分。论文的反直觉发现是：问题不在于看不见，而在于**看见了也照答**。模型默认要给一个数字，因为训练和打分都奖励猜测。

这和我们一直关注的方向一脉相承：检查放在模型外面、由 harness 执行、证据来自可复算的不变量而不是另一个模型的意见。相关工作里 ToolGate 用手写后置条件决定是否提交工具结果，确定性门拦截违规写操作，最终验证器可以扣下整个 episode；这篇的区别是对**每个读结果**用精确恒等式检验，由 harness 自己向同一 API 发额外查询，并且用对照实验说明为什么决定必须离开模型。

## 🏗️ 机制：先找证据，再决定怎么处置

### 精确检验

对过滤计数，每次查询后检验计数恒等式：

$$N(F)+N(F_{<k}\wedge\neg C_k)=N(F_{<k})$$

$N(F)$ 是 API 对过滤 $F$ 返回的计数，$F_{<k}$ 去掉第 $k$ 个条件 $C_k$。即带某个条件的计数加上带其否定的计数，必须等于去掉该条件的计数。两次额外查询由 harness 自己发，并且对条件列表的每个位置都做一遍，所以任何位置被忽略的过滤都能抓到。这是一个蜕变关系，是数据库引擎查询分区测试的双向形式。

其他精确检验：列表结果的每条记录都必须满足过滤条件、无重复、条数等于报告的总数；API 公布了参数列表时，带列表外参数的请求在运行前就被拒（spec check）；单一过滤时做值替换检验（换一个值结果应该变）。

| 操作 | 静默失败 | 必须成立的检验 | 是否测过 |
| --- | --- | --- | --- |
| 过滤计数 | 过滤被忽略、被当成 OR、被截顶 | 每个位置的计数恒等式 | 是 |
| 过滤列表 | 混入不满足条件的记录、重复 | 每条满足、无重复、条数等于总数 | 是 |
| 有文档的 API | 接受未知参数 | 参数在公布的规格里 | 是 |
| 单一过滤 | 过滤被忽略 | 换值后结果改变 | 是 |
| 分页、范围、排序、写 | 跳记录、忽略边界顺序或更新 | 页不重叠、结果在范围内且有序、读得到刚写的 | 否 |
| 任意工具（学来的） | 类型、回显、范围、关系异常 | 从干净响应挖出的契约 | 是 |

在 13 个公开 API 的 84 个有文档操作里，61 个允许精确检验，全部允许 spec check。

### 处置规则

每个检验 $j$ 有一个估计误报率 $\hat\alpha_j=1/(n_j+2)$（$n_j$ 为它在干净样本上成立的次数，继承律），精确检验 $n_j=\infty$，所以 $\hat\alpha_j=0$。失败检验满足 $\hat\alpha_j\le\tau$ 时扣下，否则警告。流程：

1. 通过的结果原样放行。
2. 失败的结果重查一次：harness 把同一调用再发一次，新结果通过才放行。
3. 仍失败：若失败的是精确检验，**扣下失败的值**，告诉 agent 哪些值无法验证、可以用哪个工具重做；在计数答案上变成一条答案规则，只接受通过检验的计数，其他计数拒绝两次后回答「无法确定」。若失败的是学来的检验，数据保留、附警告。
4. 本身带错误的结果原样通过。

阈值 $\tau=1\%$。作者补充：在他们的运行里没有任何学来的检验达到这个阈值，所以实际规则就是「精确检验扣、学来的检验警告」，并且任何低于 1.85% 的阈值给出同样决定。**SilentGuard 从不自己修值**，恢复永远是 agent 用列出的工具自己调用。

### 实验协议

每个计划内的实验都在运行前写下预测；代码按哈希冻结，代码一变运行就拒绝启动。方法在 ToolMaze 上迭代了三个版本，每版只在没见过的工作流上测，最终版本在所有计划内运行之前冻结。评分分三类：正确、未知（不给计数）、错误（任何其他计数）。

## 🧪 关键证据

### 拆开三个成分（AgentOrchBench，7 个开源模型，故障运行错答率）

| 设置 | 错答 | 干净任务正确 |
| --- | --- | --- |
| 无防护 | 74.0（单模型 32–87） | 84.9 |
| 警告 | 70.1（19–87） | 86.3 |
| 警告 + 允许弃答 | 18.2（0–59） | 83.5 |
| SilentGuard（扣下） | 1.7（0.0–3.7） | 84.9 |

同一个 judge（gpt-oss-120b）的四种设置：

| | 作为建议 | 由 harness 强制拦截 |
| --- | --- | --- |
| 看不到检验结果 | 71.7 | 70.8 |
| 看得到检验结果 | 71.2 | 6.1 |

读法：没有证据，拦不拦都没用；有证据但只是建议，也没用；有证据且强制，才有效。

完整对照里，自验证 56.2、重查 74.9、盲重试 74.4、LLM judge 71.2、checklist 72.3、reviewer 73.8、Outcome Monitors 72.2、OM 加拦截 70.9（它的契约在故障运行里只触发 3.5%，干净运行 6.2%）。SilentGuard 在 7/7 个模型上错答都少于无防护、每个已发表方法和盲重试。

一个对照很值得注意：Enforce（只接受检验过的计数，但失败的计数仍然可见）按模型错答 0.5% 到 24.8%，因为 agent 会反复换着查，直到某个查询碰巧通过检验。**扣下数值和只是拒绝接受，差别很大。**

### 前沿模型

| 模型 | 无防护 | 自验证 | 警告 | 警告+弃答 | Enforce | SilentGuard |
| --- | --- | --- | --- | --- | --- | --- |
| GPT-5.6 Sol 错答 | 89.4 | 2.5 | 11.3 | 2.3 | 31.5 | 0.0 |
| GPT-5.6 Terra 错答 | 62.3 | 3.9 | 53.9 | 35.9 | 34.0 | 0.2 |
| GPT-5.6 Luna 错答 | 59.0 | 6.9 | 63.2 | 45.1 | 36.1 | 1.4 |
| GPT-5.6 Sol 干净正确 | 98.6 | 29.2 | 77.8 | 86.1 | 100.0 | 100.0 |
| GPT-5.6 Terra 干净正确 | 93.1 | 15.3 | 68.1 | 76.4 | 90.3 | 98.6 |
| GPT-5.6 Luna 干净正确 | 84.7 | 16.7 | 69.4 | 73.6 | 87.5 | 95.8 |

无防护下最强的 Sol 反而错得最多。让它们自己跑检验，错答几乎归零，但干净任务正确率从平均 92.1% 掉到 20.4%，作者认为它们主要是在拒答。SilentGuard 错答 0.0% 到 1.4%，干净正确平均 98.1%。在真实 API 上，前沿模型错答从 57.8% 降到 8.9%。

### 其他基准

- **零售域（第二套 schema）**：无防护 78.6% 错答，SilentGuard 11.0%。
- **9 个真实 API、文档里一个过滤名被改错**：无防护 89.8% 错、3.5% 对；SilentGuard 21.3% 错、69.5% 对；文档正确时无防护是 92.1% 对。这里的收益**来自 spec check 而不是计数检验**，spec check 单独就是 21.0%。严格 schema 的 typed tool call 反而更差（28.6%）。剩下的错误主要在过滤写在查询字符串里的 API（NCBI、UniProt、Europe PMC、arXiv），schema 和值替换检验都看不到。冻结前选的 4 个 API 上错 38.6%，之后加的 5 个上错 7.4%。
- **ToolMaze（别人的基准，自带 judge）**：这里只有学来的检验，SilentGuard 只警告不扣，所以测的是重查而不是强制。静默故障下任务成功 36.0% 对 checklist 加 OM 的 32.7%，5/7 模型领先，95% 区间 [1.8, 4.9] 点，领先来自一次性故障；干净成功比 OM 低 4.6 点。
- **列表答案**：在未见过的故障上错误列表从 37.8% 降到 11.5%，正确列表也从 56.7% 掉到 7.1%。

## 🔬 最有意思的部分

**弃答，而不是恢复。** 这是全文最诚实的地方。故障下 SilentGuard 的正确率从 16.4% 掉到 2.4%，大部分答案是「无法确定」。所以作者用选择性预测的方式报告风险与覆盖：在 25% 故障率下，SilentGuard 回答 67% 的任务、答案里 3.3% 是错的；LLM judge 回答 91%、风险 24.0%；无防护回答 90%、风险 24.6%。

**自动修复会把错答盖上「已验证」的章。** 作者在冻结后写了六种新故障，只跑 harness 不跑模型，每种 36 题。SilentGuard 合计 53 错 41 对 122 未知，而且**只要它的检验触发了，就从没放出过错答**，53 个错答全部来自检验看不到的故障。Auto-repair（harness 换条路重算）对得更多（79 对 41），但错了 102 个，其中 49 个错的修复被标成了已验证，用户根本分不出来。这条直接支撑了「只修检验能确认的故障类型」这条建议。

**盲重试的代价不只是没用。** 每个调用发两次，在 AgentOrchBench 上错答 74.4%、真实 API 上 89.5%，并且每次运行平均重复执行预订、付款或发消息 2.36 次（SilentGuard 是 0.24 次）。不过在 ToolMaze 的一次性故障上盲重试确实更好（60.4% 对 47.6%），作者承认这与他们的预测相反。

**计数恒等式的盲区写得很清楚。** 自洽的故障（前缀匹配）、「知道检验存在的 API」（consistent lie）都能通过；agent 根本没发的过滤条件无从检验；恒等式假设过滤是二值的，有缺失值的字段需要三分区；估计值或查询之间会变的总数会破坏恒等式，值格式实验里就有 4 个错答因为总数在请求和检验之间略有变化而漏过。

## 🤔 我的判断

定位：**工程方法 + 很干净的消融**。方法本身不复杂，蜕变测试、规格检验、契约挖掘都是现成的；贡献在于把「证据、许可、强制」三个成分在同一批模型上拆开，证明决定权放在哪里比检验本身更重要。

亮点三条：

1. **证据与强制的 2×2 拆分**：同一个 judge，看不看得到检验结果、建议还是强制，四格里只有一格有效。这张小表应该贴在每个想用 LLM judge 兜底工具结果的团队墙上。
2. **扣下数值而不是只拒绝**：Enforce 和 SilentGuard 的差别说明，只要失败的值还留在上下文里，agent 就会想办法绕回去。
3. **预注册、哈希冻结、冻结后新故障**：协议上比同类工作严格，作者也把不利结果（盲重试赢 ToolMaze、新故障上只降到 24.5%、frontier 运行没有日志和哈希）都摆了出来。

问题与局限：

- **覆盖率代价很大**，故障下主要是在说不知道，对需要数字的用户帮助有限。
- **前沿模型和 Nemotron-3-Ultra 部分运行在 Genentech 内部平台**，只报答案计数，日志不能公开，没有哈希记录，而且是计划外追加、没有预先写预测。前沿模型都来自同一家厂商。
- **故障注入器跑在作者自己的 API 上**，真实 API 只测量了忽略过滤、静默截断分页、忽略过滤值这几类，其他故障类型没在真实服务上验证。
- **适用面以计数和列表为主**，分页、排序、写操作的精确检验列在表里但没测。
- 7 个开源模型限制了模型层面检验的功效。

对工程的直接启发：第一，对能写出精确不变量的工具（计数、过滤列表、有公开参数规格的 API），把检验放进 harness 的工具结果通道，失败的值不要回到模型上下文，只告诉它哪些值无法验证、可以用哪个工具重做。第二，先上 spec check：拒绝文档外参数几乎零成本，在真实 API 实验里单独就把错答从 89.8% 降到 21.0%。第三，学来的契约只警告不拦截，自动修复只用于检验能确认的故障类型。第四，系统提示里明确允许「无法确定」，但别指望它单独起作用。对 MCP 服务端作者，论文的建议也很直接：拒绝未知参数，分页被截断时明说。

一句话：模型看得见问题却还是会答，所以对那些能证明错了的结果，最后一票应该在 harness 手里，而代价是你得接受更多的「不知道」。
