# 16 个「模型加 harness」组合给 32 个科学程序提速：几乎都能算对，差距全在快多少；同一份源码只改构建和运行设置，就能从 0.29 倍跑到 2.12 倍，一个改动值 1.01 倍还是 6.4 倍取决于另一个改动

让 coding agent 做性能优化，现有基准大多是这样出题的：从某个人类的优化 commit 倒推出一道题，告诉 agent 要优化哪个函数，再拿专家补丁当参照。可真实的性能工程不是这样。你接手一个跑了十年的科学计算程序，没人告诉你瓶颈在哪，可以改算法、改数据结构、改编译选项、改线程数，而且改动之间会互相影响：某个改动单独看毫无用处，配上另一个改动突然快了好几倍；某个 kernel 快了十倍，整个流程只快了 5%，因为它只占总时间的一小块。**agent 能不能在一个完整应用上找到该改的地方、把局部提速兑现成端到端的加速，同时不偷工减料？**

腾讯 Hy 团队和港科大等的 **Accelerate Bench: Evaluating Agents for Application-Level Program Optimization** 用 32 个改编自超算竞赛的 CPU 优化任务来测这件事。看完我的感受是：**这篇作为基准做得非常克制，最值得看的反而不是榜单，而是它对「怎样的分差才算分差」的审计：重新判分会抖多少、独立重跑会抖多少、厂商安全分类器拦截怎么计分、只调配置不改代码能拿多少分，都做了单独测量。** 在大家越来越关心 harness 对比是否公平的当下，这些附录比主表更有参考价值。

## 核心摘要

Accelerate Bench 有 32 个任务，来自 ASC、PAC、IPCC、SC 和 ISC 的 SCC、IndySCC 六个超算竞赛的应用，覆盖八个应用领域。每个任务给出一个能跑的程序、要保留的计算、正确性要求、计时边界和允许修改的范围，不提供任何参考优化补丁。agent 在 8 小时内反复调用公开测试迭代，最终提交由一个独立的私有验证器在更大或新随机化的输入上重新构建、校验和计时。奖励是节省的基线运行时间比例（正确的 2 倍加速得 0.5），Score@1 是 32 个任务的平均奖励。在 v1.1 上评测 16 个「模型加 harness」组合，Score@1 从 25.5% 到 67.4%。512 个结果里 472 个通过正确性检查，每个 agent 正确的任务数在 26 到 32 之间，正确性本身拉不开差距，提速幅度才拉得开：两个 Claude agent 在 22 个以上任务上至少快 2 倍，其余 14 个只在 8 到 17 个任务上做到，并且它们 412 个正确结果里有 125 个提速不到 1.25 倍。作者用 v1.0 上五个 agent 的 480 次运行做过程分析：agent 主要改计算本身，很少动构建；可受控重放显示同一份 GROMACS 源码只改构建和运行设置就能从 0.29 倍到 2.12 倍，一个 QiboTN 改动单独值 1.01 倍、配合另一个改动值 6.4 倍。

## 🎯 为什么这件事值得写

应用级优化和局部改代码不是一回事。一个有效的补丁可能完全不改变端到端运行时间，而有效的加速又常常依赖于跨层改动的相互作用。SWE-Perf、GSO、SWE-fficiency 等基准把评估锚定在已知的人类优化实例上，提供了真实仓库和专家参照，但也等于告诉了 agent 往哪里使劲。作者想测一个互补的问题：**当只规定要保留的行为和要变快的工作负载，没有任何已知补丁指引时，agent 能不能自己优化一个应用？**

这篇还特别值得 harness 研究者读，因为作者在正文和附录里反复强调一件事：每个分数都是一个模型在它的 harness 里跑出来的，分差同时混合了模型能力、harness 行为、推理算力和执行条件。他们没有回避这件事，而是把能测的噪声来源一个个测了出来，并明确写出「单次运行排不出相差几个点的 agent」。这和最近大家关心的 harness 对比审计、能力声明是否准确是同一类问题。

## 🏗️ 机制：用工作负载定义题目，公开测试迭代，私有验证器判分

### 任务定义

每个任务由一个完整应用的工作负载和必需输出定义，而不是一个历史补丁。给 agent 的是一个能跑的基线实现、构建和执行脚本、任务说明和公开测试接口，运行在固定 CPU 核数和内存上限的容器里。允许在指定目录内修改源码、编译选项和依赖，但必须保留规定的计算和输出。以 SU2 为例：必须在给定的 10,216 单元网格上跑完全部 250 次迭代并产出 5 个完整流场快照。

计时覆盖整个工作流，排除一次性的构建和准备。GROMACS 只计 mdrun 模拟；HPCG 派生任务计稀疏矩阵组装、初始化、多重网格求解和输出；分页生成任务计模型加载、自回归解码、检查点保存以及在新进程里恢复。**因为这些阶段一起计时、一起检查，一个更快的 kernel 只按它在工作流里的占比得分，而跳过必需输出或恢复步骤的捷径会直接判错，拿不到加速分。**

### 规模化处理

竞赛工作负载原本要在多节点集群上跑几个小时。为了让 agent 能在实际预算内反复编辑、构建、测试，作者把输入规模和迭代次数缩小到单节点 4 到 8 核、最多 32 GiB 内存。32 个任务里 29 个直接基于竞赛的应用（从完整源码树到选定的求解器子树），3 个（分页 LM 生成、Tucker 重建、图稀疏化）是作者围绕竞赛的优化主题自己写的工作流。另有 3 个候选任务因为无法计分对所有 agent 一并剔除。

### 公开测试与私有验证

agent 可以反复调用公开测试：重新构建当前程序，在几个公开输入（通常两个）上运行，报告正确性、运行时间，多数任务还报告基线时间或加速比、或失败在哪一步。agent 看不到检查代码。运行结束后，隐藏的验证器在同类但通常更大或每次新随机化的私有输入（通常四个）上重新构建并计时，只有它的重复计时和检查决定奖励。比如 SU2 的私有输入换了别的马赫数和攻角。

验证器强制执行任务相关的数值容差、完整输出文件和有状态要求（例如在新进程里从检查点正确恢复）。作者做了 14 个计划内的对照：4 个源码不变的运行、2 个合法变换、8 个非法变体，全部合法的通过，8 个非法的都在它违反的那项检查上失败，比如省略第二个解会挂在输出大小检查上，四个能过组件测试的 attention 变体挂在应用级检查上。作者特别注明：这些对照只验证了被点名的检查，不估计整个基准的误接受率。

### 评分

$$r_t(a)=C_t(a)\cdot\max\left(0,\ 1-\frac{T_t(a)}{B_t}\right),\qquad \text{Score@1}=\frac{1}{32}\sum_t r_t(a^*_{m,t})$$

$B_t$ 是基线运行时间，$T_t(a)$ 是提交程序的运行时间，$C_t(a)$ 是是否通过全部正确性检查。正确的 2 倍加速得 0.5，10 倍得 0.9，100 倍得 0.99，所以大加速在 Score@1 里被压缩，作者另报 $A_\tau$（正确且至少 τ 倍加速的任务占比）和几何平均加速 GM。

### 怎样的分差才算分差

这是我认为全文最有价值的部分，分散在正文和附录 A：

| 噪声来源 | 测量结果 |
| --- | --- |
| 源码不变的程序被私有验证器判一次 | 0.923× 到 1.017×（中位 0.999×），对应 Score@1 0.40% |
| 冻结提交、重新判分 | 单次运行 Score@1 约有 1.5 个点的测量不确定性 |
| 独立重跑（GPT-6 Astra、Hy4-Preview 各三次） | Score@1 标准差 2.5 和 4.4 个点 |
| 任务自助法配对区间 | Sonnet 5.5 领先所有非 Claude agent 至少 13.4 个点；Opus 5.5 领先 GPT-6.1 Sol 10.2 个点（区间 0.1 到 18.2）；Claude 之下相邻两名之间没有一对区间排除零，120 对里 64 对排除零 |
| 去掉 3 个自写任务或 HPCG 派生任务 | 排序几乎不变（Kendall τb ≥ 0.95） |

重新判分时有 10 个提交的正确性发生了变化：7 个数值输出一次在容差内、一次在容差外，3 个有一次没跑起来。原因是很多任务每次判分都会新抽私有输入，误差贴着容差的程序可能这次过、下次不过。对 GPT-6 Astra，按点估计，重新判分的方差约占独立运行间方差的三分之一，其余来自 agent 的搜索本身，不过三次运行下这个拆分很不精确（比值 95% 区间 0.07 到 3.30）。

### 只调配置能拿多少分

作者事先固定了一个只改构建和运行设置、不改源码的配方：R1 用 -O3 -march=native（不加改变浮点语义的选项），R2 加上应用自带的最高级 SIMD 选项，R3 把线程或进程数设为分配的核数并绑核，由公开测试选出最快的通过者。结果 32 个配置全部正确，但只有 GROMACS 超过 1.25 倍：把 SIMD 选项从默认 None 改为 AVX2_256 并加 -march=native，得到 2.23 倍。次高是 ThunderSVM 1.249 倍和 Palabos 1.16 倍。有 8 个任务 R1 改变了数值输出、没过完整输出比对。以这个配置基线作参照，各 agent 的 Score@1 下降 0.5 到 2.4 个点。GPT-6 Astra 三次运行在 HPCG 派生、QiboTN、分页 LM 生成上分别达到 28.9 到 36.7 倍、7.9 到 11.5 倍、11.1 到 11.9 倍，而配置基线在这三个任务上是 0.995 倍、1.009 倍、0.990 倍：**最大的加速不来自调参。**

### 安全分类器拦截怎么算

Claude Opus 5.5 在图稀疏化、PRESTO、VPIC 三个任务上被厂商的安全分类器以网络安全或生物内容为由拦截。Claude Code 原本会把被标记的请求转给 Claude Opus 4.8（网络安全）或 Claude Opus 5（生物）继续会话，但作者的网关把每个请求都送到被测模型，这个回退没生效，三次运行直接终止。表里按零分计，所以 Opus 5.5 是 59.4%，在其余 29 个任务上是 65.6%。作者还列出了别家的不同做法：Vals AI 两种口径都报，Artificial Analysis 把回退模型完成的尝试照常计分，另有研究保留厂商回退因为那是组织实际部署的路径。如果拿 Sonnet 5.5 在这三个任务上的结果当回退，Opus 5.5 会是 65.2%。

### agent 是怎么优化的（v1.0，五个 agent，480 次运行）

分析样本是 DeepSeek-V4.1-Flash、Grok 4.6、DeepSeek-V4-Pro、DeepSeek-V4-Flash 和 Hy3 各在每个任务上跑三次。GPT-5.6 Luna 给 476 次运行的最终提交标注优化技术，DeepSeek-V4.1-Flash 给每次工具调用标注动作和理由。作者强调这部分刻画的是这些任务上的优化方式，不解释 v1.1 的排名。

- **主要改计算，很少动构建**：计算或复用类改动出现在 476 次运行中的 225 次（29 个任务），并行或向量化 132 次（22 个任务），编译和构建调优只有 40 次。
- **并行和向量化最常达标**：用了它们的运行里 62.9% 正确且至少 1.25 倍，计算或复用类是 48.0%，两者正确率都在 88% 左右。和同模型同任务不用这些技术的运行比，计算或复用类平均奖励高 8.0 个点（95% 区间 1.4 到 15.9），并行或向量化高 8.9 个点（1.9 到 17.0）。
- **测得多不等于成功**：所有 agent 越到后期测试调用占比越高。Hy3 后三分之一的测试占比最高（21.7%），却只在 96 次运行里的 16 次达到 1.25 倍，是五个里最少的。
- **测量有用但没想象中大**：480 次里 61 次没有任何计时或剖析命令（P0），251 次只有计时（P1），168 次有剖析（P2），正确且至少 1.25 倍的比例分别是 11.5%、37.1%、44.6%；但控制任务和模型之后，P1 相对 P0 的奖励差只有 +4.4 个点，区间 −4.0 到 12.8，跨过零。
- **迭代有回报但不单调**：31 段版本历史里 19 段最后一个正确候选比第一个快 1.05 倍以上；70 对源码不同的相邻正确候选里，36 对比前一个快，只有 26 对刷新了最好成绩。480 条轨迹里 206 条出现了回退或挑选候选的操作。

### 改动之间的相互作用

| 现象 | 证据 |
| --- | --- |
| 同一份源码，只改构建和运行设置 | 一次 GROMACS 提交只改了构建和运行配置；在四种设置下重放，全部正确，加速从 0.289 倍到 2.123 倍；AVX2 向量化在 4 线程下 2.123 倍，单线程下 0.709 倍 |
| 一个改动的价值取决于另一个 | DeepSeek-V4-Flash 的 QiboTN 程序，对三个改动做全因子实验：延迟加载张量库单独只值 1.01 倍，打开「更广的快速精确模拟器分派」之后值 6.3 到 6.4 倍；两者合起来比全关快 9.6 到 9.7 倍；状态复用在这个负载上没有可测收益 |
| 优化只有被执行到才算数 | 一次 HPL 运行里 agent 优化了 HPL_dgemm.c，比对二进制后发现可执行文件没变，因为应用实际调用的是 cblas_dgemm，于是把优化挪到这个入口 |
| 跨层依赖很常见 | 抽样复核估计 480 次运行中约 72%（95% 区间 63% 到 80%）的工具输出显示改动的效果或正确性依赖构建设置、运行设置或实际执行的代码路径；其中涉及优化速度或正确性的约 52%（41% 到 63%） |

两个具体例子很有画面感：一个 Palabos 运行的 OpenMP 程序用默认线程数（看到主机全部 192 个 CPU）跑了 11 分钟，设成 4 线程只要 1.5 秒；SIESTA 用 -march=native 构建后 868 个值里有 662 个和参考不一致，关掉融合乘加收缩之后才对上。

## 🔬 最有意思的部分

**几乎都能算对，分数全靠提速。** 472/512 的正确率意味着「别把程序改坏」在这个设置下已经不是主要难点。难点在于把局部改进兑现成端到端加速。这和很多 SWE 类基准的情况正好相反，也提醒我们：一个只看正确性的验收门在性能任务上几乎没有区分度。

**agent 系统性地低估构建和运行层。** 只有 40 次运行动了编译和构建，可同一份 GROMACS 源码光靠构建和线程设置就能差 7 倍多。agent 的优化直觉明显偏向「改代码」，而性能工程师的第一反应往往是先看编译选项和线程绑定。这是一个很具体的 skill 缺口，写成一条优化前检查清单就能补。

**单次运行排不出相差几个点的 agent。** 2.5 到 4.4 个点的运行间标准差，加上约 1.5 个点的重判不确定性，意味着榜单中段那一串 34 到 45 分的组合在统计上基本分不开。作者把这句话直接写进了表注。现在很多 harness 榜单只跑一次就排名，这篇给出了一个应该怎么报告的范例。

**安全分类器拦截是一个新的 harness 对比混杂因素。** 同一个模型，走不走厂商回退，分数差 6 个点左右（59.4% 对把 Sonnet 当回退时的 65.2%）。各家评测机构口径不一，而这在 harness 对比里通常不会被披露。这正是 harness 能力声明审计该覆盖的一项。

## 🤔 我的判断

定位：**基准论文**，附带一套扎实的计分审计和过程分析。

亮点三条：

1. **任务按工作负载定义，不给参考补丁**，计时覆盖完整工作流并检查有状态要求，捷径直接判错，这比函数级的速度基准更接近真实性能工程。
2. **噪声审计做得完整**：源码不变控制、重新判分、独立重跑、任务自助法区间、配置基线、剔除自写任务的稳健性，全部单独量化，并明确写出单次运行的分辨率上限。
3. **受控重放把「为什么要整体协调」讲清楚了**：0.29 倍到 2.12 倍、1.01 倍和 6.4 倍这样的因子实验，比任何轨迹统计都更有说服力。

问题与局限：

- **模型和 harness 绑在一起**：三个 GPT 模型用 Codex，其他用 Claude Code，作者自己也说分数比较的是组合而非底座模型；v1.0 里 Grok 4.6 和 Gemini-3.8-Flash 还用过 Grok Build 和 Gemini CLI，v1.1 改成了 Claude Code。分离模型和 harness 被列为后续工作。
- **主表每个 agent 只跑一次**，只有两个 agent 做了三次重跑，中段排名不可靠。
- **过程分析用的是 v1.0 的五个 agent**，不包括榜单前列的模型，作者也说明它不解释 v1.1 排名；标注依赖 LLM，流行度估计靠抽样复核。
- **作者团队来自腾讯 Hy 团队**，自家的 Hy4、Hy4-Preview、Hy3 都在评测之列（Hy4 系列排第五、六名，Hy3 垫底），论文没有对此做利益冲突说明。
- **只覆盖缩小规模的单节点 CPU 工作流**，基线的调优程度不一，作者说明其他规模、硬件和生产环境需要另行评估；验证器对照只验证了被点名的检查，不代表整体误接受率。

对工程的直接启发：第一，给做性能任务的 agent 加一条优化前检查清单：编译优化级别、SIMD 选项、线程数和绑核、实际执行的代码路径（比对二进制或剖析确认），这几项成本很低但收益可能很大。第二，性能任务的验收门要像这里一样分开公开反馈和私有验证，私有输入要更大或随机化，并检查完整输出和有状态步骤，防止只在小输入上有效的改动和跳过步骤的捷径。第三，做 harness 对比时至少报告重判方差和多次运行方差，并披露安全拦截和模型回退的处理口径。

一句话：在完整应用上，agent 已经很少把程序改坏，真正的分水岭是能不能看到构建、运行和代码之间的耦合，把局部提速变成端到端的加速；而判断谁更强之前，先得知道分数自己会抖多少。
