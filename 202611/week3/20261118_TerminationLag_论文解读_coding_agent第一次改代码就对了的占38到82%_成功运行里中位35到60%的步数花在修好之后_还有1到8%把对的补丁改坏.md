# coding agent 早就修好了，为什么还不停？第一次改代码就对了的占 38% 到 82%，成功运行里中位 35% 到 60% 的步数花在修好之后，还有 1% 到 8% 把对的补丁改坏

你有没有过这种体验：看 coding agent 的 trace，第 10 步它就改对了那一行，后面又跑了 40 步：重跑测试、写临时脚本、grep 调用方、git diff 看一遍、再删掉临时文件，最后才 submit。SWE-bench 的分数对这两种 agent 一视同仁，账单却差了几倍。更糟的是偶尔它在第 35 步「顺手优化」一下，把对的改坏了，最终提交的是错的补丁，你在排行榜上看到的只是一个「未解决」。行业里把这叫 overthinking、过度验证、premature completion 的反面，大家讨论 stop hook 多半是在防「还没做完就宣布完成」，**很少有人量化另一头：已经做完了，agent 还要多干多久，多干的这些到底在干什么，会不会把事情搞砸？**

宾夕法尼亚州立大学的 **Termination Lag: Coding Agents Solve Early but Stop Late** 只做这一件事。它在每一步之后快照仓库补丁，离线用官方测试评估每一个不同的补丁，agent 自己看不到这些结果，从而定位「第一个正确补丁」出现的那一步。看完我的感受是：**这是一篇很朴素的测量论文，但它给 stop-hook 和长程评估提供了一个以前缺的参照系：停在正确时刻最多能省多少，继续干最多会赔多少。**

## 核心摘要

作者定义两个指标：首个正确补丁时间 TTFCP（第一个能通过官方基准测试的补丁出现在第几步）和终止滞后 TL（之后 agent 又走了多少步），再除以总步数得到归一化终止滞后 NTL。核心评估是 OpenHands 上的 Qwen3-Coder-30B-A3B 和 Laguna-XS.2，跑完整的 SWE-bench Verified（500 题）和 Multilingual（300 题）；泛化部分加了 Claude Haiku 5.5 和 GPT-6 Luna（Verified）、Seed-OSS-36B（SWE-bench Pro），以及 mini-SWE-agent 框架。结论有四条。第一，正确补丁出现得早：在最终达到正确补丁的运行里，第一次改源码就已经正确的比例在 38% 到 82% 之间，平均只需要 1.3 到 3.6 个不同补丁。第二，停得晚：成功运行里，Qwen3-Coder 的中位 NTL 是 35% 到 37%，Laguna-XS.2 是 54% 到 60%，Haiku 54%，GPT-6 Luna 36%。第三，多出来的步数主要是验证（48% 到 63%）和探索（15% 到 29%），再改源码的很少（2% 到 6%，Seed-OSS 在 Pro 上是 19%）。第四，61% 到 96% 的运行把正确补丁保持到最后，但有 1% 到 8% 后来改坏且没救回来，停在首个正确补丁就能保住这些题。一个停在首个正确补丁的 oracle 在不丢任何已解决题的前提下，能砍掉成功运行中位 35% 到 60% 的步数。这篇的价值不在方法，在于把「解出来」和「知道自己解出来了」拆成了两种可测能力。

## 🎯 为什么这件事值得写

最终补丁正确率是 coding agent 的主指标，但它把两种能力混在一起：**产生正确修复**，和**认识到修复已经完成**。作者举的例子很直接：两个 agent 都在第 10 步做出同样的正确修改，一个立刻提交，另一个再跑 40 步重跑测试、看调用方、审 diff。两者拿同样的分，但每多一步都是一次在更长上下文上的模型调用，加 token、加延迟、加算力，还加了把能用的代码弄坏的风险。

但验证又不能不做：agent 看不到基准的隐藏测试，只能靠自己的证据判断补丁对不对。所以要刻画停止行为，需要三样东西：正确补丁第一次出现在什么时候、之后还跟了多少步、这些步对补丁做了什么。

相关工作里，推理模型 overthinking 和代码生成的早停都是在单次回复内部；agent 成本研究发现失败运行更长、有些成功运行在验证过的修复之后还在探索、agent 自己写的测试经常放过错误补丁；早停方向多是从轨迹预测成功或失败，或者直接限制轮数和成本。作者的定位是：**别人预测成败，这篇测的是补丁什么时候已经对了，从而给出「在成功时停下」最多能省多少的上界。** 同期也有工作（Kim 等人）指出中途写对的修复会被后续编辑丢掉，这篇把这件事系统量化了。

## 🏗️ 机制：每步快照，离线判分，agent 不知情

### 记录补丁

在 agent 和模型端点之间放一个日志代理。每一步（模型推理、选择的动作、工具执行结果）结束后，在 agent 等待下一次模型响应时，代理记录当前仓库相对基准 commit 的 diff。补丁用临时 Git index 构造，不动 agent 的工作仓库。运行结束后，在隔离容器里按基准官方流程评估每个记录的补丁，相同补丁只评一次。**agent 收不到任何反馈，所以测量不改变它的行为。**

### 指标

令 $F$ 为最早一个补丁通过官方评估的步，$S$ 为 agent 自己停下的那一步：

$$\text{TTFCP}=F,\qquad \text{TL}=S-F,\qquad \text{NTL}=\frac{S-F}{S}$$

上下文增长定义为 $(\text{ctx}_S-\text{ctx}_F)/\text{ctx}_F$。另外定义「第一个补丁」为第一次改源码之后记录的补丁，统计到首个正确补丁为止出现了几个不同补丁。

### 设置

| 模型 | 基准 | 框架 | 步数预算 | 上下文 |
| --- | --- | --- | --- | --- |
| Qwen3-Coder-30B-A3B | Verified、Multilingual | OpenHands（另在 Verified 上跑 mini-SWE-agent） | 100 | 131K |
| Laguna-XS.2 | Verified、Multilingual | OpenHands | 250 | 256K |
| Seed-OSS-36B | SWE-bench Pro | OpenHands | 150 | 131K |
| Claude Haiku 5.5、GPT-6 Luna | Verified | OpenHands | 100 | 未单列 |

开源模型在 Argonne 的 Aurora 上用 vLLM 服务。每题只跑一次。

### 步骤分类

成功轨迹里首个正确补丁之后的每一步，按记录的工具和参数用规则归类：验证（跑已有测试、写并执行额外测试脚本、构建项目）、探索（看文件、搜仓库、用 git 查看改动）、再改源码、收尾（删临时文件、提交最终回复）、思考与其他。

上半部分是成功轨迹中首个正确补丁之后的步骤构成；下半部分是所有达到过正确补丁的轨迹（包括最终失败的）里补丁的命运。

Oracle 上界：在首个正确补丁处停下、从未正确的运行不变，成功运行的步数中位可省 Qwen3-Coder 35%（Verified）和 37%（Multilingual），Laguna-XS.2 60% 和 54%，Haiku 54%，且保留每一道原本解决的题。

## 🔬 最有意思的部分

**滞后主要是验证，不是瞎折腾。** 修好之后近一半到三分之二的步数在跑测试、写检查、构建。这不是 bug：agent 确实看不到隐藏测试，验证是它唯一能做的事。问题在于验证的量和它带来的信息不成比例。作者的 RQ4 结论说得很冷静：**补丁一旦通过基准测试，后续工作无法提升它的基准正确性，只可能引入回退。**

**「坏了又修回来」比「坏了没救回来」多得多。** Laguna-XS.2 在 Multilingual 上 31% 的轨迹都经历过把正确补丁改坏再修好；最终没救回来的是 8%。这意味着很多「修好之后的步数」其实是在给自己挖坑再填坑。对长程评估来说，这类来回会被最终分数完全掩盖。

**上下文膨胀是隐形成本。** Laguna-XS.2 在 Verified 上修好之后上下文还涨了 78%，每一步都在更长的上下文上付费。mini-SWE-agent 的最后一步上下文只有 OpenHands 的一半左右，非缓存 token 也少了不少，但滞后比例差不多，说明「停得晚」更像模型行为，而不是哪个框架特别啰嗦。

**最终分数会把「已经解出来」藏起来。** 1% 到 8% 的运行在中途就有了正确补丁，最后却交了错的。在排行榜上，它们和从来没找到方向的运行是同一个「未解决」。

## 🤔 我的判断

定位：**测量论文**，给 stop-hook 和停止策略研究提供了一个上界参照，不提出停止方法本身。

亮点三条：

1. **测量干净**：每步快照、临时 Git index、离线隔离评估、agent 完全不知情。这套代理加快照的做法本身就值得在自家 harness 里复用，因为它能把「什么时候已经对了」变成可回放的数据。
2. **把两种能力拆开**：产生正确修复和识别修复已完成是两件事，后者以前只在「过早宣布完成」那一侧被讨论，这篇补上了「过晚停止」一侧。
3. **跨模型、跨基准、跨框架一致**：五个模型、三个基准、两个框架都看到同样的分离，滞后比例在 35% 到 60% 一带。

问题与局限：

- **每题只跑一次**，没有方差估计；Seed-OSS 在 Pro 上解得很少，统计样本小，作者自己也说了。
- **以步数代替成本**，步数只是计算成本的近似。
- **步骤分类靠规则**，按工具和参数归类，没有人工校验比例。
- **只给上界，不给可部署的停止规则**。oracle 用的是 agent 看不到的隐藏测试，真实停止规则只能用运行中可得的证据。作者明确把这留给后续工作。
- **「正确」的定义是基准官方测试**，通过隐藏测试不等于补丁在工程上就完美，有些修好之后的验证和清理可能对真实合入有价值，论文没有区分这部分。

对工程的直接启发：第一，在 harness 里加每步补丁快照，评测时离线算 TTFCP 和 TL，把「停止效率」和「补丁保持率」作为和解决率并列的指标报告。第二，stop hook 不只防早停，也可以防晚停：比如补丁在连续 N 步验证都通过且没有新的源码编辑时触发提交提示，或者限制修好之后的验证轮次。第三，任何「修好之后再改源码」的动作都值得单独提醒或要求理由，因为这正是 1% 到 8% 把对的改坏的来源；有快照的话，提交前可以对比当前补丁和历史上通过本地验证的补丁，择优提交。

一句话：会解题和会收手是两种能力，排行榜只奖励前一种，而账单和回退都来自后一种。
