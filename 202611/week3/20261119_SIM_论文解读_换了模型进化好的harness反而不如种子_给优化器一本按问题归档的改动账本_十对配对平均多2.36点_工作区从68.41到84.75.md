# 换了模型，进化好的 harness 反而比种子还差？给优化器一本按问题归档的改动账本，十对配对实验平均多 2.36 点，工作区任务从 68.41 拉到 84.75

你有没有过这种体验：花了一周让 Opus 帮你把 agent harness 迭代到很顺手，加了完成门、修了解析器、补了一堆中间件。然后公司说要换成更便宜的 Flash 模型，或者新版本发布了，你把同一套 harness 原样接上去，分数不升反降。更麻烦的是你已经不记得哪段代码当初是为了修什么问题加的，于是新一轮自动优化又从头摸索：把门收得更紧，结果死锁，再修死锁，再误以为这个门是自己第一轮刚加的。行业里管这套自动改 harness 的流程叫 harness RSI（递归自我改进），Meta-Harness、AHE 这一类工作都在做，**但几乎都假设模型和基准是固定的。真实世界里两者都会变，那上一轮优化留下来的经验，到底应该以什么形式传给下一轮？**

Google Cloud AI 和宾夕法尼亚州立大学的 **Self-Improvement Memory Enables Continual Recursive Self-Improvement** 给出的答案是：别只传 harness 代码，还要传一本「为什么这么改、预计修好哪些题、实际修好了哪些」的账本，而且这本账本是写给 harness 优化器看的，不是写给干活的 policy 模型看的。看完我的感受是：**这篇把「harness 进化的可迁移性」从代码层面挪到了决策记录层面，并且用了配对统计检验来证明它，不是一张漂亮曲线了事。**

## 核心摘要

作者定义了一个新设定叫持续递归自我改进（CRSI）：一轮 harness 优化在源设置上结束后，换基准（跨数据集，policy 不变）或换 policy 模型（跨模型，基准和划分不变），从源设置进化好的 harness 继续优化，前提是 harness 的可执行接口兼容。方法叫自我改进记忆（SIM）：把每一次被选中的 harness 改动按它要解决的「反复出现的 harness 问题」（根因假设，比如「没有执行证据就宣布完成」）归组，每次尝试记录改动内容、理由、预测会修好哪些任务、实际修好哪些、以及来源（领域、基准、policy、轮次）。预测在评估前写下，评估后核对，回退了也照记。proposer 和 selector 每轮都在系统提示里看到完整 SIM，不检索不截断。实验覆盖四个领域：coding（Terminal-Bench 2.1 到 Terminal-Bench 4）、文本分类（Meta-Harness 的 3 数据集到 8 数据集）、agentic 工作区（Harvey LAB 到 JobBench、GDPval、APEX-Agents 的等权平均）、工程设计（EngDesign 到 Frontier-Eng），每轮 10 轮、每轮 5 个候选。四个条件共用同一起点和预算：冷启动、只传 harness、只传根因、完整 SIM。结果是完整 SIM 在六个跨数据集设置和四个 Opus 5.5 到 Gemini 3.8 Flash 的跨模型设置里都是最终最高；跨数据集比只传 harness 多 2.43 到 4.35 点，跨模型多 3.60 到 11.33 点。最硬的证据是 coding 的十对配对：从 Terminus-2 独立跑十次源优化，每次分出带 SIM 和不带 SIM 两条 TB4 续跑，SIM 赢 9 对，平均多 2.36 点（95% CI [1.05, 3.68]，配对 t 检验 p=0.003，符号秩检验 p=0.006）。反直觉的地方是：源设置上进化得越好，不代表到目标设置时起点越高，Opus 进化出的 harness 拿到 Gemini 上四个领域全部低于 Gemini 自己的种子 harness。这篇的价值定位是：harness 进化的迁移单位不该只是代码 diff，而是「问题、改动、预测、观测」这四元组。

## 🎯 为什么这件事值得写

harness 自动优化这一年的进展很快：Meta-Harness 和 AHE 用执行轨迹和分数搜 harness 代码，RRSI 用正则化搜索提升可迁移性，HarnessBank 按问题归组候选 harness。大家已经证明进化出来的 harness 能迁移到别的任务、别的模型上，但优化本身通常在一个固定设置里做完就结束。

作者指出两个现实场景让「做完就结束」站不住：

- **换模型**。一种是多模型服务，一套 harness 同时服务几个 policy；一种是模型代际更替，新版本替换旧版本。适合一个 policy 的改动换到另一个 policy 上可能起反作用。论文的工作区实验里，Opus 进化的 harness 在 Gemini 上起点 68.41，低于 Gemini 种子 harness 的 73.89。
- **换数据**。policy 不变，任务分布变了，会暴露源优化没处理过的失败。比如完成门在源基准上只需检查命令跑没跑成功，到目标基准上还要检查可行解是不是最优解。文本分类实验里，源进化的 FewShotAll harness 在目标套件起点 72.92，低于种子的 75.72。

问题在于 harness 代码本身不解释自己：某段中间件为什么存在、当初修好了哪几题、有没有回退过，代码里看不出来。没有这段历史，目标优化可能重复以前的尝试，或者在不知道用途的情况下改掉继承来的组件。

## 🏗️ 机制：给优化器而不是给 policy 的记忆

### Harness RSI 基本循环

沿用 Meta-Harness 的设定：policy 模型权重冻结，优化可执行的 harness（上下文、工具、执行流程）。每个设置有互不相交的 evolve 集和 held-out 集，**只有 evolve 集的反馈能用于提议、选择、更新 SIM 和决定停止**。每轮：评估器在 evolve 集上跑当前 harness，返回分数、轨迹和错误；proposer 生成 $k$ 个候选；selector 在执行前先筛一遍，再在执行过的候选里综合性能、复杂度、领域特异性和回退风险选一个，或者都不要。proposer 和 selector 都是 LLM harness 工程师。

### SIM 条目长什么样

对一个根因假设 $p$（例如「过早完成」），条目是按时间排列的一串尝试，每次尝试存四样：

| 字段 | 内容 |
| --- | --- |
| 改动 | 代码 diff 及涉及文件 |
| 理由 | 为什么这么改 |
| 预测与观测 | 评估前预测会修好哪些任务，评估后实际修好、漏掉哪些，通过数 |
| 来源 | 领域、基准、policy、轮次 |

几条规则值得注意：每个提议必须引用已有根因或命名新根因；只记录被选中的候选，但即使它回退或没修好预测的题也照记；根因文本完全相同的条目合并且不丢历史；proposer 和 selector 读的是完整记录，没有检索也没有截断。

### 四个对照条件

| 条件 | 起点 harness | 带入目标优化的记忆 |
| --- | --- | --- |
| Cold Start | 种子 | 无 |
| Harness Transfer | 源进化结果 | 无 |
| Problem-Only Memory | 源进化结果 | 只有根因列表 |
| Full SIM | 源进化结果 | 完整记录 |

三个迁移条件起点完全相同，目标任务、policy、轮数和候选数都匹配，记忆条件在整个目标优化期间保持。所有 run 都是 $N=10$ 轮、每轮 $k=5$ 个候选，每个任务 5 次 rollout 全部计分。主实验里 proposer 和 selector 都是 Gemini 3.8 Flash，即使干活的是 Opus 也一样。成本方面作者给了一个数：一轮 coding 大约 4 小时，其中评估 1.7 小时、候选采样 34 分钟；轮数和候选数对齐，但 token 和运行时间各方法可能不同。

## 🧪 关键证据

### 跨数据集（policy 固定为 Gemini 3.8 Flash，held-out 目标分）

| 领域 / 种子 | Cold Start 前→后 | Harness Transfer 前→后 | Problem-Only 前→后 | Full SIM 前→后 |
| --- | --- | --- | --- | --- |
| Coding / AHE | 16.36→19.39 | 18.18→20.61 | 18.18→18.79 | 18.18→**24.85** |
| Coding / Terminus-2 | 18.18→19.39 | 19.39→19.39 | 19.39→20.61 | 19.39→**21.82** |
| 文本分类 / NoMemory | 68.60→72.00 | 71.40→71.00 | 71.40→73.40 | 71.40→**73.60** |
| 文本分类 / FewShotAll | 75.72→75.92 | 72.92→74.12 | 72.92→75.52 | 72.92→**77.92** |
| 工作区 / ReAct | 73.89→82.98 | 74.93→85.07 | 74.93→85.54 | 74.93→**87.89** |
| 工程 / ReAct | 39.13→40.87 | 39.13→42.61 | 39.13→42.61 | 39.13→**46.96** |

完整 SIM 六个设置都最高，比只传 harness 多 2.43 到 4.35 点，比只传根因多 0.20 到 6.06 点。只传根因的效果是混合的，从比只传 harness 低 1.82 点到高 2.40 点都有。作者的结论是：光保留诊断不够，改动历史和评估证据才是增量来源。

### 跨模型（Opus 5.5 源，Gemini 3.8 Flash 目标）

| 领域 / 种子 | Cold Start 前→后 | Harness Transfer 前→后 | Problem-Only 前→后 | Full SIM 前→后 |
| --- | --- | --- | --- | --- |
| Coding / AHE | 16.36→19.39 | 13.94→18.18 | 13.94→20.61 | 13.94→**21.82** |
| 文本分类 / FewShotAll | 78.32→82.72 | 77.72→80.20 | 77.72→81.32 | 77.72→**83.80** |
| 工作区 / ReAct | 73.89→82.98 | 68.41→73.42 | 68.41→79.22 | 68.41→**84.75** |
| 工程 / ReAct | 39.13→40.87 | 34.78→42.61 | 34.78→46.96 | 34.78→**50.43** |

Opus 进化的 harness 拿到 Gemini 上，四个领域起点全部低于 Gemini 种子，差距 0.60 到 5.48 点。只传 harness 的续跑有三个领域最后还是输给冷启动。完整 SIM 四个领域都最高，比只传 harness 多 3.60 到 11.33 点；工作区最夸张，同从 68.41 起步，SIM 到 84.75，只传 harness 到 73.42。

### 十对配对（最该看的一张表）

上面每个条件都只跑了一次完整 RSI，5 次 rollout 估计的是执行波动，不是优化波动。作者自己也承认这些是描述性结果，所以专门做了 coding 的配对研究：从 Terminus-2 在 TB2.1 上独立跑 10 次源优化，每个产物分出两条 10 轮 TB4 续跑，一条带 SIM 一条不带，独立源 run 是分析单位。

| 指标 | 数值 |
| --- | --- |
| 平均起点 | 18.36 |
| 不带 SIM 平均终点 | 19.33 |
| 带 SIM 平均终点 | 21.70 |
| SIM 胜出对数 | 9/10（唯一输的一对差 0.61） |
| 平均配对优势 | 2.36，95% CI [1.05, 3.68] |
| 配对 t 检验 | t(9)=4.06，p=0.003 |
| 符号秩检验 | p=0.006 |
| 效应量 | d_z=1.28 |

### 跨代际与共享 harness

在 TB2.1 上沿 Gemini 代际链传递 harness 和 SIM：2.5 Flash 上 CRSI 22.4 对 fresh RSI 21.4，3.5 Flash 上 76.8 对 73.3，3.8 Flash 上 90.5 对 88.9，但到 4 Argon 上是 94.8 对 95.6，**反而低 0.8 点**。三个后续代里赢两个，不是全胜。

一套 harness 同时服务 Grok 4.20 Reasoning、Opus 5.5、Gemini 3.8 Flash 的文本分类实验里，用三个模型反馈统一合成的 harness held-out 75.24，和每个模型单独进化的 75.20 基本持平，高于共享种子的 73.28；顺序 CRSI 是 74.20。作者明确说这只是描述性比较。

## 🔬 最有意思的部分

### 一个完成门的前世今生

附录 F.2 的案例几乎就是长程 agent 评估里「过早完成」问题的教科书。源任务是配置一个 git 服务器：建裸仓库、写 post-receive 钩子、建 SSH 用户 user、起 8080 端口 HTTP 服务。失败的 rollout 里，agent 把「我会自己设置登录」理解成账户会由外部提供，从没创建 user，拿已有的 ubuntu 账户本地测了一遍，所有命令都成功，就宣布 `task_complete: true`。验证器从容器外以 user 身份克隆，SSH 拒绝，推送失败，页面 404。

种子 Terminus-2 的完成检查只是让模型再说一遍「确定完成吗」，问的是意图不是证据。SIM 里记的根因 P5 是「没有执行验证就过早完成」，源 RSI 用三轮被接受的改动建了一个跨轮状态机 `execution_gating_interlock.py`：上一轮有解析错误或根本没执行命令时拒绝完成，最多拒绝三次（防止把真做完的任务锁死）；第 8 轮加上拦截模型模拟多轮文本、输出截断丢弃命令块、总共只执行了不超过一条命令就想完成的情况；第 10 轮在请求完成时检测终端崩溃、断言失败、HTTP 404 和测试错误。文件从 137 行长到 275 行。configure-git-webserver 和 circuit-fibsqrt 都从 5 次成功 1 次变成 5 次全成功。第 10 轮那次预测修好三题，实际只修好一题，账本照实记下了漏掉的两题。

到了 TB4，带 SIM 的续跑读到这个门的理由和源结果，保留完成验证，同时加入目标基准需要的检查，比如可行解和最优解的区别。不带 SIM 的续跑则把门收得更紧，两次修复完成死锁，还把继承来的门误认为是自己第一轮加的。作者的总结一句话很准：**需求可以继承，实现需要改写。**

### 「源上进化得好」不等于「目标上起点高」

源 RSI 在六个设置的 held-out 源分上都涨了 2.75 到 6.41 点，但 FewShotAll 的进化 harness 到目标套件起点低于种子。只传 harness 的续跑最后 74.12，还不如冷启动的 75.92；带 SIM 到 77.92。NoMemory 上冷启动涨得比 SIM 多（3.40 对 2.20），但终点更低（72.00 对 73.60）。这提醒所有比较 harness 进化方法的人：只报涨幅会误导，必须同时报起点和终点。

### 源性能保留

在 AHE 的保留实验里，三个迁移条件都从 held-out TB2.1 的 90.22 出发，完整 SIM 在 225 次 rollout 里丢了 3 次成功，只传根因丢 4 次，只传 harness 丢 6 次，而 SIM 在 TB4 上的涨幅明显大于只传根因（6.67 对 0.61 点）。

## 🤔 我的判断

定位：**方法加实验设计的组合贡献**。方法本身不复杂，就是一个结构化的变更日志；真正有分量的是 CRSI 这个设定和十对配对检验。

亮点三条：

1. **把记忆给了优化器而不是 policy**。大部分 agent 记忆工作是让干活的模型记住经验，这篇让改 harness 的那个 agent 记住自己为什么改、改了有没有用。这和人类工程团队的 ADR（架构决策记录）、changelog 是同一个思路。
2. **预测先写后核对**。每次改动在评估前写下「我预计修好哪些题」，评估后核对。这天然就是一个对优化器自身判断力的校准记录，也是防止优化器自欺的一道门。
3. **有配对统计**。十个独立源 run、配对 t 检验、符号秩检验、效应量都报了，比单次 run 画曲线可信得多，和用配对统计做接受门的 harness 进化思路一致。

问题与局限：

- **除 coding 外每个条件只跑一次**，跨数据集和跨模型的大部分表格都是描述性的，作者自己在局限里写了。工作区 11.33 点的大差距只有一次 run 支撑。
- **工作区分数用 Gemini 3.8 Flash 当 judge**，而 proposer、selector、policy 在主实验里也是 Gemini 3.8 Flash，存在同源偏差的可能，作者在伦理声明里提到 judge 偏差但没有做换 judge 的检验。
- **成本只对齐了轮数和候选数**，token 和运行时间可能不同。完整 SIM 不截断地塞进系统提示，长期续跑后上下文会持续增长，论文没有报 SIM 本身的 token 开销，也没有测更长的迁移链。
- **代际链第四代输了 0.8 点**，说明随着模型变强，旧记忆可能开始拖后腿；论文没有给出何时该清理或降权旧条目的机制。
- **前提是接口兼容**。harness 换框架、换工具协议时 SIM 还有没有用，没测。

对工程的直接启发：第一，任何自动或半自动的 harness 迭代，都应该同时维护一份按问题归档的改动账本，至少包含根因、改动、预测修好的任务、实际结果、来源模型和基准。第二，换模型或换基准时，不要只拷贝 harness 代码，把账本一起交给下一轮优化器。第三，完成门这类机制在跨基准迁移时最容易「需求还在但实现过时」，迁移后应优先复核。第四，报告 harness 进化结果时同时给起点、终点和对照组的起点，单报涨幅会误导。

一句话：harness 会变，模型会换，能跨越这些变化保留下来的不是代码，而是每次改动背后那句「为什么」和那张「预测对了几题」的成绩单。
