# 拿决策模型当验收门之前，先问它两件事：选项换个顺序还选不选同一个？正确答案被拿掉了它看不看得出？SO-Arena：能力榜和可靠性榜是两张榜

你有没有过这种体验：在 harness 里接了一个 System One 决策模型做路由、做「这一步完成了没有」的判定，延迟从几秒降到一百多毫秒，离线准确率看着也不错，上线后却发现它偶尔会在选项顺序变了之后改口，或者在根本没有正确选项的时候照样给某个选项打很高的概率。准确率榜单从来不告诉你这两件事。

这类模型现在被统称为 **System One 模型**：给定状态、决策目标和一组可选结果，一次前向就输出这组结果上的概率分布，不生成推理文本。Jev 把这个接口做成了通用服务，开源侧有 Kev、JevAny 等一批实现。它们天生适合当 agent 里的门：路由、工具动作选择、完成度验收。**问题是：一个决策模型分数高，是否意味着它的决策可靠？** NUS 的 SO-Arena 把这个问题拆成两个维度分别测。看完我的感受是：这篇最值钱的结论不是谁排第一，而是「准确率几乎能预测顺序稳定性，却几乎预测不了模型能否察觉正确答案缺席」，后者必须单独测。

## 核心摘要

SO-Arena 是一个面向 System One 决策模型的基准，共 2,919 题，覆盖 11 个领域、五个能力族：语义理解、知识与推理、安全与策略合规、证据评估、agent 任务完成。题目来自 40 个公开数据集、基准和环境，参考标签经过人工加 LLM 复核，去掉了标签可疑的题，并核对参考答案能被模型可见的输入支撑。11 个领域里有 9 个按领域内标准分了难度档，能力分只取每个领域最难的一档、各领域等权平均。环境类任务包括 337 道网页任务和 282 个交互式工具使用回合（BFCL 和 ToolSandbox 模拟器真实执行每一步），模型既当执行者选动作，也当验收者判断已记录的执行是否满足要求，其中最难一档专门构造了「最终状态一样、过程中是否合规不一样」的轨迹。可靠性另算：同一题打乱 12 次选项顺序看答案是否保持（顺序稳定性 S），把正确选项删掉后看模型给「没有正确答案」的概率能否把两种副本分开（空缺识别 N），两者取几何平均得到可靠性分 R。21 个模型的结果：GPT-6 Sol 和 Luna 两个 System Two 参照领先能力榜，最强的 System One 模型 GLiDE 和 KnowLine-31B 比 Luna 低约十分，但所有开源 System One 模型在单张 H100 上每题都在 0.3 秒内答完；顺序稳定性大体随能力上升，18 个 System One 模型里 14 个 S 超过 0.8，空缺识别却从接近随机到约 0.8 分布很散；可靠性最高的两个模型 JevAny-27B 和 Jev API 1.14，能力只排在 18 个里的第八和第六，而能力最强的 System One 模型在可靠性上只排第七。这篇的价值是：**给「决策模型当门」这件事补上了能力之外的第二把尺子，并且证明这把尺子不能用准确率代替。**

## 🎯 为什么这件事值得写

决策模型这条线最近很热。我们这个仓库已经记过不少：MMDM 发现挑全一组选项比挑对一个难得多，DecisionConflict 用决策模型替代 LLM 判断来源冲突，Drex 和 DecisionRank 在比谁更快更准，今天另一篇 DecisionTeacher 讨论决策模型当老师。评测侧也不缺：JevBench 测能力、校准、延迟和成本，JEVal 覆盖十个应用领域，OpenDecisions 加了难度档和受控扰动。

SO-Arena 的切入点有三处不同。

第一，**标签可追溯**。每道题记录来源、版本和原始编号，模型推导出来的参考答案在元数据里单独标记，参考答案和模型输入严格分开。这对决策模型尤其重要，因为它们输出的是分布，标签错一点，校准和排名都会跟着偏。

第二，**领域内分难度档**。能力分只看每个领域最难的一档（数学取 hard 加 very hard），目的是让榜单对高难度题上的差异更敏感。作者特别说明，难度档只在领域内定义，跨领域不可比。

第三，也是我最关心的：**把可靠性和能力拆开**。如果你要拿一个决策模型做 stop hook 或者完成度验收门，你真正怕的不是它平均准确率低两个点，而是它在关键时刻因为选项排列不同而翻转判决，或者在「其实一个都不对」的时候自信地选一个。

## 🏗️ 机制 / 任务定义

**统一接口**。每道题表示为 $(x, q, \mathcal{Y})$：$x$ 是提供给模型的状态（文本、结构化记录、检索段落或交互历史），$q$ 是决策目标，$\mathcal{Y}$ 是允许的结果及其描述。模型返回一个分布。沿用 Jev 风格接口的三种输出格式：`choice`（无序多选）、`noul`（是或否）、`score`（有序等级，相邻等级给部分分）。

**五个能力族、11 个领域**：

| 能力族 | 领域（题数） |
|---|---|
| 语义理解 | 情感与情绪（200）、意图与路由（300） |
| 知识与推理 | 数学（200）、代码理解（200）、科学推理（200）、知识与常识（200） |
| 安全与策略合规 | 安全（500） |
| 证据评估 | 检索与重排（300）、任务完成验收（200） |
| agent 任务完成 | 工具与 API 使用（282）、文本网页交互（337） |

总计 2,300 道静态题和 619 道环境题。

**环境题的两种角色**。当执行者时，单步网页题给一个记录下来的页面状态，问某个动作是否推进目标或者选最好的动作；多步网页题沿着一条经回放验证可完成的参考路线逐步决策，经回放确认仍可完成的替代顺序和无害绕路也算对；工具题在 BFCL 或 ToolSandbox 模拟器里真实执行每一步，按原基准的检查器打分。BFCL 困难题每个回合限 96 次决策、12 次工具调用，超预算按同样规则计分。

**任务完成验收的最难一档**是这篇最有设计感的部分。作者从 VirtualHome 的五个基础任务出发，先跑出一次成功执行，再追加一段可执行的「审计后缀」：改变电器状态，挪走两个目标物体，再放回零个、一个或两个。这样一条轨迹可能**最后物体都在正确位置，但在操作电器的那一刻物体并不在位**。模型要判断三个条件：C1 要求后缀里至少有一次开电器动作，并检查每次开之前所有放置要求都成立；C2 要求后缀里至少有一次关闭动作，检查第一次关闭前放置要求成立；C3 检查最后一个动作之后原任务目标是否全部成立。模型在四个三位真值组合里选一个，每个干扰项恰好翻转正确组合的一位。对每条被评估的轨迹，都有一条已验证的反事实轨迹到达**相同最终状态**但 C1 或 C2 的取值不同。这 20 道题里每个条件各有 10 道为真。

**能力分**：

$$C(m)=\frac{100}{D}\sum_{d=1}^{D}\frac{1}{|\mathcal{T}_{d}|}\sum_{i\in\mathcal{T}_{d}}c_{i}(m)$$

$\mathcal{T}_d$ 取领域 $d$ 的最难一档（无分档领域取全部），$D$ 为领域数。

**顺序稳定性**：每题原序加 12 种重排，按选项内容而非位置识别答案：

$$S(m)=\frac{A(m)-p_{e}}{1-p_{e}},\quad A(m)=\frac{1}{12M}\sum_{i=1}^{M}\sum_{r=1}^{12}\mathbf{1}\{a_{i}^{(r)}=a_{i}^{(0)}\}$$

$p_e$ 是随机选择下的一致率，随机为 0、完全一致为 1。注意 $S$ 只衡量一致性，不衡量对错。

**空缺识别**：每题出两份，一份原样，一份删掉正确选项。$p_{\mathrm{null}}=1-p(\mathrm{inc})$，$p(\mathrm{inc})$ 是模型估计「至少有一个正确选项在列」的概率。用 $p_{\mathrm{null}}$ 去区分两种副本，$N(m)=2\,\mathrm{AUC}(m)-1$，随机为 0，完美为 1。

**可靠性分**：$R(m)=\sqrt{S(m)N(m)}$，只有两者都高于随机时才为正，否则为 0。

## 🧪 关键证据或主结果

**被测模型**：16 个开源 System One 模型（0.4B 到 31B）、一个自动切换快慢模式的 StartLux Auto、两个闭源决策 API（Jev API 1.14、OpenAI Decisions）、两个闭源 System Two 参照（GPT-6 Luna、Sol，均为 medium effort）。

**能力榜部分结果**（能力分 $C$，表 2）：

| 模型 | 类型 | 能力分 |
|---|---|---|
| GPT-6 Sol | System Two 参照 | 82.3 |
| GPT-6 Luna | System Two 参照 | 79.7 |
| KnowLine-31B | 开源 31B | 70.2 |
| GLiDE | 开源 27B | 70.2 |
| Sieve-31B-v3 | 开源 31B | 67.7 |
| Decider-27B | 开源 27B | 66.7 |
| Kev-27B | 开源 27B | 61.4 |
| Jev API 1.14 | 闭源决策 API | 60.4 |
| StartLux Instant | 开源 4B | 59.0 |
| JevAny-27B | 开源 27B | 58.4 |
| OpenAI Decisions | 闭源决策 API | 53.6 |
| Laya | 开源 0.4B | 30.9 |

**延迟**：所有开源 System One 模型在单张 H100 上每题 0.3 秒内答完，比 GPT-6 Sol 和 Luna 快几十倍。附录的计时表里，GLiDE 均值 113 毫秒（P90 214、P99 774），KnowLine-31B 均值 177 毫秒，4B 档的 Kev-4B 和 JevAny-4B 均值 25.2 毫秒，而会自己决定要不要思考的 StartLux Auto 均值 3,084 毫秒。计时口径是从请求交给模型官方入口到概率回到主机，含分词和本地 HTTP 往返。闭源 API 无法在同一硬件上计时，按端到端时间画在图上。

**可靠性**：

- 顺序稳定性：18 个 System One 模型里 14 个 $S>0.8$。除 Jeva-4B 因为逐个编码选项、$S=1$ 是构造使然之外，这 14 个落在 0.83 到 0.94；另外四个对顺序敏感：Laya 0.35，SII-4B、Kev-4B 和 OpenAI Decisions 在 0.68 到 0.72。
- 空缺识别：从接近随机到约 0.8，分布很散。同一家族的大号模型确实比小号高，但有的 4B 模型高过一些 9B 和 27B 模型。
- 排名错位：可靠性最高的两个模型 JevAny-27B 和 Jev API 1.14，在 18 个 System One 模型里能力只排第八和第六；能力最强的 System One 模型在可靠性上只排第七。

**泼点冷水**。第一，最难一档的任务完成验收只有 20 题，作者在附录里自己承认，换成「中档加难档」和「只看难档」两种口径时，这个领域的骨干增益从 17.4 分掉到 3.8 分，结论在小样本上会晃。第二，排名靠的是模型各自官方文档里的设置，个别例外（比如 Laya 取消了选项 48 token 截断，SII-4B 的计时版本加了 flash-linear-attention）作者都列了出来，但这意味着排名是「各家推荐配置下」的排名。第三，可靠性测的是选项集合的受控变化，不是输入扰动或对抗样本，作者也没有声称覆盖后者。第四，OpenAI Decisions 在安全类和含敏感信息的网页步骤上有拒答，拒答一律按零分处理，它的分数里混了策略因素。

## 🔬 最有意思的部分

**1. 准确率能预测顺序稳定性，预测不了空缺识别。** 作者对 16 个 System One 模型（去掉 Laya 和 Jeva-4B）做了能力分对 $S$、对 $N$ 的二次拟合，覆盖 90% 模型的残差带半宽，$S$ 是 0.07，$N$ 是 0.18。更具体的是：模型在自己答错的题上换序后改口的比例，远高于答对的题，**不稳定主要出在它本来就不会的地方**。而 $N$ 上，Kev-27B、Jev API 1.14 和 JevAny-27B 每一个都高过能力前四（GLiDE、KnowLine-31B、Sieve-31B-v3、Decider-27B）中的每一个，12 组配对差值的 95% 区间都在零以上（对 597 道题自助重采样 2,000 次）。所以如果你的门需要「什么都不选」这个出口，**榜单分数基本帮不了你，得自己测。**

**2. 最终状态相同、过程合规性不同的验收题，把决策 API 拉开了。** 任务完成验收的难档（就是上面那 20 道审计后缀题）上，GPT-6 Sol、GLiDE 都是 100，KnowLine-31B 90，JevAny-27B 35，Jev API 1.14 是 20，Clef-27B 和 Decider Flash 是 15。四选一题目，随机水平是 25%。同一个 Jev API 在这个领域的简单档和中档都是 88。换句话说，**只看最终状态的验收它没问题，一旦要回看历史判断过程是否合规，就跌到随机附近。** 这正是 stop hook 和完成度门最常见的失败方式：结果看起来对了，过程里有一步违规。

**3. 差距在哪、什么能补，按领域分成三类。** 作者拿 GPT-6 Luna 对比 StartLux Instant（4B）和 GLiDE（27B），在中档加难档上算差值：

| 类别 | 领域 | 现象 |
|---|---|---|
| 直接语义判断 | 知识常识、情感情绪、检索重排 | System One 与 Luna 相当，GLiDE 在知识常识和情感上反超约 5 分；换大骨干或开思考都帮助不大 |
| 细粒度有据决策 | 意图路由、安全、完成验收、工具使用、网页交互 | GLiDE 与 Luna 差距在 4 分以内，StartLux Instant 最多落后 29 分；换更大更新的骨干涨得远比开思考多 |
| 多步推导 | 数学、科学推理、代码理解 | 两个 System One 都显著落后；思考在数学和科学上帮助最大，数学上 StartLux Auto 从不思考的 50.8 到总是思考的 92.5 |

对 harness 设计者来说，这张表很实用：**路由、安全分类、完成验收这类门，值得换更大的 System One 骨干，而不是让它思考；需要算的题，交给会推理的模型。**

**4. 自动思考在完成验收上反而比总是思考好。** StartLux Auto 在任务完成验收（中档加难档）上，从不思考 58.7，总是思考 66.1，自动模式 73.4。作者没有专门解释这个现象，我只记下数字，不做推断。

## 🤔 我的判断

**定位**：测量基础设施。它不是方法突破，但把「决策模型当门」这件事需要测的维度补齐了一块。

**亮点三条**：

1. 可靠性独立成分，并用两个互补指标定义：顺序稳定性管「会不会因为排列改口」，空缺识别管「会不会在没有正确答案时硬选」。两者取几何平均，任一不过随机就记零，口径清楚。
2. 历史相关验收题的构造方式很干净：每条被评估轨迹都配一条最终状态相同、过程条件不同的已验证反事实轨迹，堵死了「只看终态就能答对」的捷径。
3. 标签可追溯、模型推导标签单独标记、各家按官方设置运行并列出例外，整体是一份诚实的评测报告。

**问题与局限**：最能说明问题的难档验收只有 20 题，作者自己给了口径敏感性；可靠性只覆盖选项集合扰动；闭源 API 的延迟含网络和排队，和本地 H100 计时不可直接比；模型推导的参考标签（如 BrowseComp-Plus 部分）仍有引入偏差的可能，作者只做了标记。

**对工程的直接启发**：如果你在 harness 里用决策模型做路由或者完成度验收，上线前至少补两项自测。一是把你自己的选项打乱十几次，看判决翻转率，翻得多的地方基本就是它不会的地方，可以直接当作需要升级到慢模型的信号。二是对每个门都加一个「以上都不对」的出口，再构造删掉正确选项的副本，看它能不能把两种情况分开；分不开的门，不要让它独自放行。至于需要回看历史判断过程合规性的验收，这篇的难档数字说明，**不要默认一个在终态验收上表现很好的决策模型也能胜任。**

一句话收束：**SO-Arena 的提醒很朴素：决策模型快是真的，准也越来越接近了，但「准」和「可靠」是两张榜，拿它当门的时候，要按第二张榜挑。**
