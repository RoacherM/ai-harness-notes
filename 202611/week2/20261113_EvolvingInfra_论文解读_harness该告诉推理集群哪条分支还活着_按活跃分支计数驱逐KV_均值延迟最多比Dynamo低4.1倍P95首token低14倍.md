# 子 agent 跑了六分钟回来，主线程的 KV 缓存已经被 LRU 扔了：Evolving Infra 让 harness 把分支信息交给推理集群，P95 首 token 最多快 14 倍

你有没有过这种体验：Claude Code 一类的 agent 派出一个子 agent 去跑测试，几分钟后回来，主线程的下一步请求明明和之前的上下文几乎一模一样，首 token 却慢得出奇。原因很可能不在模型，而在服务端：主线程等待的那几分钟里，它的 KV 缓存因为「最近没被访问」被 LRU 驱逐了，反倒是刚被压缩（compaction）替换掉、以后再也用不上的旧历史还留在缓存里。

这篇来自 Georgia Tech、UIUC、UC Berkeley、NVIDIA、OpenAI 和 MIT 的论文，把问题放在 PD 分离（prefill–decode disaggregation）推理集群上讨论。**核心问题是：agent 的上下文管理（fork、子 agent、压缩）决定了哪些前缀以后会被复用，但推理服务只看访问时间和队列深度，怎么才能让服务端知道这些？** 看完我的感受是：这是一篇系统论文，但它对 harness 设计者的意义比对 infra 团队还大。它要求 harness 做的事情很少，只是给每个请求打上分支 ID、在分支结束时报一声，换来的收益却是数量级的。这其实是在给「harness 和推理服务之间该有什么协议」提一个具体答案。

## 核心摘要

Evolving Infra 做了三件事。第一，把计算分配和 KV 管理解耦：每个节点跑一个能同时服务 prefill 和 decode 的对称引擎（在 SGLang 上扩展出单一调度循环和双向 KV 传输协议，复用 Mooncake 的 RDMA 传输），所有节点的主机内存组成共享 KV 池，节点切换角色时不用重启，KV 也不会被困在原节点上。第二，按 agent 负载自适应分配算力：在线拟合 prefill 和 decode 的迭代时间模型，prefill 模型把已缓存和未缓存 token 分开算，规划器按 600 秒窗口里请求的平均工作量决定 PD 配比，只有预测收益在整个窗口持续时才切换，避免子 agent 齐发造成的短时突发引起无谓切换。第三，按 agent 上下文管理来路由和驱逐 KV：harness 给每个请求打分支 ID、报告分支结束，路由器维护一棵集群级前缀树，记录每个块在每个节点上被多少条活跃分支引用，压缩时给分支升版本并释放旧块的计数，驱逐时先扔计数为零的块，也就是被替换的历史、已结束子 agent 的上下文和传输留下的重复副本。在 36 张 GB300 上用 GLM-5.2 和 Kimi K2.6 服务 PutnamBench 数学 agent、Claude Code 真实轨迹和 OSWorld 2.0 电脑操作 agent，相比 NVIDIA 的 Dynamo，吞吐最多 2.73 倍，丢失的 KV 复用少 81% 到 95%，均值端到端延迟最多低 4.12 倍，P95 首 token 时间最多低 13.92 倍；一次角色切换平均 6.2 秒，Dynamo 重启平均 754 秒。这篇真正的价值定位是：**agent 上下文管理信号应该成为推理服务的一等输入，而 LRU 在 agent 负载下是系统性错误的**。

## 🎯 为什么这件事值得写

agent 请求的结构和聊天请求很不一样。一个 agent 分步执行，每一步是一次模型请求加它触发的工具调用，harness 在两步之间更新上下文。所以相邻请求通常共享很长的前缀，KV 复用的空间很大。但论文的图 2 指出了三层变化：

1. **不同 agent 差异大**：OSWorld 每步追加一张截图，是 prefill 重负载；Putnam 每次生成很长的推理，是 decode 重负载。它们各自最优的静态配比从 2P7D 到 6P3D（x 个 prefill 节点、y 个 decode 节点）不等。
2. **负载组成随时间变**：从 Putnam 过渡到 OSWorld 时，每 10 分钟窗口的最优配比从 3P6D 移到 7P2D，全程最好的静态配比 5P4D 在两头时段最多损失 24% 吞吐。论文还引了生产数据：用户触发的任务跟着工作日节奏走，自动触发的任务全天更均匀。
3. **同一个 agent 内部，最近访问不代表还会复用**：Claude Code 轨迹里，一次 359 秒的子 agent 调用之后，98% 的 prompt 能和之前的 KV 匹配；一次仅 12 秒的压缩之后，只有 14% 能匹配。

现有系统在这里有三个具体问题。角色切换太贵：Dynamo 每次切换平均要 681 秒（论文第 3 节的测量），另一种原地切换的系统 Arrow 在 34 次切换里丢掉了 55.5% 的可用 KV 复用。算力需求估错：在线规划器看队列深度或预测的首 token 时间，子 agent 齐发的短时突发就会误导它；有的规划器按完整输入长度估 prefill 工作量，忽略了 KV 复用，于是高估了需要的 prefill 节点。KV 复用判断错：缓存感知路由把同一分支的请求集中到少数持有前缀的节点上，把它们压垮；LRU 驱逐又扔掉了等工具、等子 agent、等用户的分支的 KV。

## 🏗️ 机制拆解

**数据面**：对称引擎让每个节点都能跑两种阶段；每个节点在 GPU 内存（L1）缓存 KV，并写穿到本机主机内存（L2），所有节点的 L2 组成共享池。prefill 节点通过目录找到可复用的 KV，从对端 L2 经 RDMA 拉取，而且是在请求排队期间就完整拉到本机 L2、载入 GPU、广播给本节点所有 GPU，prefill 开始时已经就位。decode 节点只往池里写，不从主机内存读，因为那会拖慢 decode。

**分支计数目录**：这是和 harness 关系最紧的部分。

| 事件 | harness 做什么 | 路由器怎么改计数 |
|---|---|---|
| fork 或派生子 agent | 把新分支 ID 发给路由器 | 新分支复用的每个块在服务它的节点上加一 |
| 同一分支的连续请求，只追加 | 请求带分支 ID | 只给新追加的块加一，复用块保持不变 |
| 压缩改写了上下文 | 请求带分支 ID | 分支版本号加一，释放新上下文丢掉的块，给新包含的块加一 |
| 分支结束 | 报告结束 | 释放该分支全部计数 |
| 同阶段节点间传输 | 无 | 计数迁到目标节点，源节点在目标拿到当前版本后释放 |
| 跨阶段传输 | 无 | 两边都保留计数，因为下一步两个阶段都要用 |

结果是每条活跃分支在每个阶段至多在一份副本上持有计数。驱逐顺序是先扔零计数块，只有零计数块全扔完了，才轮到活跃分支仍在引用的块。

**迭代时间模型**：prefill 主要受算力限制，一个请求在因果注意力下要算的 query–key 对数是

$$
A = t_{uc} t_c + \frac{t_{uc}(t_{uc}+1)}{2}
$$

其中 $t_{uc}$ 是未缓存 token，$t_c$ 是已缓存前缀。节点 $n$ 上一次 prefill 迭代的时间是

$$
T^{iter}_{P,n} = c^P_{n,0} + c^P_{n,1}\sum t_{uc} + c^P_{n,2}\sum A + c^P_{n,3}\sum t_{rst}
$$

四个系数分别是固定开销、每个未缓存 token、每个 query–key 对、每个从主机内存恢复的 token 的成本，全部在线拟合。论文报告在拟合点之外，单请求平均误差 4.2%，2 到 8 个请求的批次 6.3%，模型在一分钟内收敛。decode 侧按访存受限建模，主要是权重读取的固定成本加随运行请求数增长的部分。

**路由**：对请求工作量 $w$ 和 prefill 节点 $n$，预测首 token 时间为当前批次剩余时间、队列里各请求服务时间之和、加上本请求服务时间，路由到预测值最小的节点。这样就不再是「哪个节点有前缀就发给谁」，而是在队列长度和需要拉取的 KV 之间权衡。

## 🧪 关键证据

实验设置：mini-SWE-agent 跑 PutnamBench，Anthropic 的电脑操作 agent 跑 OSWorld 2.0，Claude Code 真实用户轨迹用 Trie 回放器重放（保留请求间停顿和前缀共享，固定每次输出长度和工具时长）。GLM-5.2 服务 Putnam 和 CC，Kimi K2.6 服务 OSWorld，NVFP4 量化、FP8 KV、MTP 投机解码，九台 4×GB300 节点，每节点 TP4。每次运行先热身 30 分钟不计，再以固定并发跑一小时。基线是 Dynamo v1.5.1，起始配比都是 6P3D。

**稳态负载**（九个设置）：

| 指标 | 相对 Dynamo |
|---|---|
| 吞吐 | 1.10 到 2.73 倍 |
| 丢失的 KV 复用 | 少 81% 到 95% |
| 均值端到端延迟 | CC 低 3.80 到 4.12 倍，OSWorld 低 2.34 到 2.69 倍，Putnam 低 1.15 到 1.23 倍 |
| P95 首 token | CC 和 OSWorld 上低 3.25 到 13.92 倍 |
| 每次角色切换 | 6.2 秒，对比 Dynamo 重启 754 秒 |
| 每次运行切换次数 | 平均 2.0 次，Dynamo 3.6 次 |

CC 上 Dynamo 丢失的 KV 复用里，34% 到 46% 来自 LRU 扔掉了正在等工具、子 agent 或用户的分支的 KV。Dynamo 不带缓存 prefill 的 prompt token 比例最高是 Evolving Infra 的 2.99 倍。

**负载漂移**：三小时里依次跑 288 个 Putnam agent、144 个 Putnam 加 72 个 OSWorld、144 个 OSWorld。规划器的配比跟住了每 10 分钟窗口的最优配比，OSWorld 时段稳定在 8P1D。均值端到端延迟比 Dynamo 低 2.15 倍、比最佳静态配比低 1.33 倍；吞吐是 Dynamo 的 2.14 倍、最佳静态配比的 1.28 倍。

**诚实泼冷水**：在 decode 重负载的 Putnam 上，规划器只留一到两个 prefill 节点来最大化吞吐，于是在 224 和 288 并发时 P95 首 token 反而比 Dynamo 高，换来的是均值延迟更低。这是一个明确的取舍，不是全面碾压。和最佳静态配比相比，在每个负载最低并发下吞吐只有 0.98 到 1.38 倍，也就是说有一个设置略输。CC 是用回放器重放的，固定了输出长度和工具时长，真实 agent 在服务变快之后行为可能会变。

## 🔬 最有意思的部分

第一，消融显示**大头收益不来自规划器**。在 CC 126 并发、固定 4P5D 不开在线配比调整时，仅靠第 4 节的基础设施和第 5.3 节的按复用路由加驱逐，吞吐就是最佳静态配比的 1.37 倍。其中异步 KV 拉取单独贡献 1.12 倍（prefill 节点空闲时间从 23.6% 降到 14.4%），剩下的来自按复用的路由和驱逐：同配比下丢失的 KV 复用从缓存感知路由的 2.4% 降到 0.7%，每个请求少 prefill 31% 的未缓存 token。在最佳静态配比上打开在线调整只损失 0.3% 吞吐，而离线搜出这个配比要 10,752 GPU 小时。

第二，**暂停 agent 没用**。论文对比了 ThunderAgent 那种暂停 agent 的做法，结果是 0.95 倍。原因是在 GB300 上 KV 容量本身不是瓶颈，瓶颈在于扔错了 KV 和路由不均。这对「容量不够就排队」的直觉是个纠正。

第三，图 2c 那组数字值得单独记住：**359 秒后回来的子 agent 调用复用 98%，12 秒前的压缩只剩 14%**。任何以最近访问为依据的缓存策略，在 agent 负载下都会恰好反着来。

## 🤔 我的判断

**定位**：系统方法论文，同时是一个「harness 到推理服务」信号协议的工程样本。

**亮点三条**：

1. 只要求 harness 提供两个信号（请求所属分支 ID、分支结束），服务端就能把 fork、子 agent、压缩这些上下文管理语义完整还原成 KV 引用计数。
2. 迭代时间模型把已缓存和未缓存 token 分开，按窗口平均工作量而不是瞬时负载规划，切换次数少一半，还不需要离线剖析。
3. 消融把收益拆得很清楚：异步拉取、按复用路由驱逐、在线配比调整各自贡献多少，Putnam 上的 P95 首 token 取舍也写明了。

**问题与局限**：版本号只在压缩时加一，依赖路由器自己比较前后请求判断是不是纯追加，harness 如果做了不规则的上下文编辑（比如中间插入记忆片段），计数是否仍然准确没有单独评估。分支 ID 和结束信号需要 harness 配合，论文没讨论 harness 忘记报告结束时的泄漏回收。实验全在 GB300 上，KV 容量充裕，换到显存紧张的硬件上结论可能不同。

**对工程的直接启发**：如果你在做 harness，现在就可以开始在请求元数据里带上分支 ID，并在子 agent 或 fork 结束时显式发一个结束事件，哪怕你用的推理服务暂时不读它。如果你在做自托管推理，至少把 LRU 换成「被活跃分支引用」优先保留，并把压缩后的旧历史标成可优先驱逐。跨 harness 比较成本和延迟时，也要记录压缩阈值和子 agent 并发策略，因为它们直接决定了服务端能复用多少 KV。

一句话收束：**Evolving Infra 说明 agent 的上下文管理不该只是 harness 内部的事，把分支生命周期告诉推理集群，是目前性价比最高的一次跨层协作。**
