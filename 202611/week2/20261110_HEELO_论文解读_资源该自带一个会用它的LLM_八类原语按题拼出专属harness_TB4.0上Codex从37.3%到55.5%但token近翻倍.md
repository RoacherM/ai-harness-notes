# 工具摆到手边还不够，得有人会用：给每个资源配一个常驻 LLM，按题拼出专属 harness，Terminal-Bench 4.0 上 Codex 从 37.3% 拉到 55.5%

你有没有过这种体验：MCP 工具挂了几十个，模型也确实调到了对的那个，结果参数填错了一半；或者检索回来的代码片段明明是对的，塞进目标仓库却跟周围三个模块对不上。资源已经「够得着」了，任务还是失败。UIUC 这篇论文给这一步起了个名字，叫**最后一公里**：从「拿到资源」到「把资源用在当前任务的对象上」。

作者的回答是把「会用这个资源的能力」跟资源绑在一起：每个工具、代码组件、证明方法、文档源都配一个常驻 LLM，由它负责在上下文里落地，调用方只用自然语言提需求。在此之上，HEELO 这个框架按题挑出需要的几个原语，拼成一张任务专属的图，跑完用环境证据验收，失败了只改被牵连的那几个原语，验证过的新原语再入库。看完我的感受是：**这是一篇把八篇伴生论文装进同一个框架的总纲**，思路对我们做 harness 很有参考价值，但数字要分开看，尤其要看成本那一列。

## 核心摘要

作者定义了 **agent-native primitive（agent 原生原语）**：一个可复用资源 \(a_i\)，配一个常驻 LLM，对外暴露一个接口描述 \(d_i\)。调用时给它自然语言请求和上下文，它返回结果，外加发给其他原语的消息（比如「我的返回值要求你那边的字段是 UTC 时间」）。能用确定程序完成的地方（比如 harness 的控制操作）就用程序代替 LLM。HEELO 用三个机制把原语组织成每题的 harness：**库选择与组合**（按接口检索或让原语自评相关度，拼成依赖图）、**基于证据的执行与改进**（分轮执行，用任务自己的测试、编译器、答案验收，失败追溯到被牵连的原语，只重做那部分，默认 3 轮预算）、**验证与发布**（新原语或改进版只有通过测试等验证才入库，走独立于任务执行的路径）。作者实例化了八类原语：工具、代码、数学、知识、多 agent、开发、导航、harness，分别对应八篇伴生研究，共建了 25,519 个工具原语（其中 16,464 个包装真实 API）、1,424 个带测试的代码原语、82 个 Lean 可编译的数学原语。主要数字：开发原语（HERMES）在 Terminal-Bench 4.0 上把 GPT-5.6 Sol 最大推理档从 Codex 的 37.3% 拉到 55.5%；harness 原语按题组合（STITCH）在 100 道 SWE-bench Verified 上 Pass@1 从种子 harness 的 73.0% 到 80.5%，45 道 Terminal-Bench 2.0 上从 60.0% 到 72.2%；在作者自建的 heelo.dev 46 个真实任务上，Claude Code 和 Codex 单干各完成 9 个，接上 HEELO 的 MCP 服务器后分别完成 39 和 35 个。真正的价值定位是：**harness 不该每次都从零重建「怎么用这个资源」，这份能力应该随资源一起被复用、被验证、被版本化。**

## 🎯 为什么这件事值得写

过去一年 harness 圈的主流做法是「把资源送到模型手边」：工具学习、RAG、技能库、代码库、多 agent 框架、自动生成 harness。这篇的批评很直接：**这些方法都把资源放近了，却把「用」的能力留给了调用方**。调用方必须在自己的上下文里读懂每个资源的细节，库越大要读的越多；它在这道题学到的经验，题一结束就没了；结果还很难检查。

作者给出的诊断有三层：

1. **在上下文里应用**：工具调用的每个参数都要落地，经常依赖上一步的输出；检索回来的代码要改到目标仓库能用；证明方法只在条件成立时才适用；文档里来的答案要忠实于来源。
2. **组合**：一步的产出和要求必须以下一步能用的形式送到。
3. **基于证据的修订**：环境报告失败时并不告诉你是哪一环错了，得追溯回去只重做那部分。

这三层正好对应我们在 MMP 里关心的几件事：工具结果的类型化传递、子 agent 之间的契约、失败后的局部重试。所以即使它的大数字需要打折，**问题定义本身就值得收**。

## 🏗️ 机制

**原语的定义**：

$$
(r_i, m_i) = P_i(x_i; c_i) = \mathcal{M}[a_i; c_i; x_i]
$$

一个基座模型可以给整个库当常驻 LLM，每次只是条件化在不同资源上，所以「原语由它拥有的资源定义」。原语还有两个可选能力：**相关度自评**（在被选中之前判断「这个请求我能不能管」并给出用法建议，解决相似度检索会漏召回的问题）和**自带验证**（资源自带测试或 schema，返回前先跑一遍，失败就报结构化错误）。注意作者说得很清楚：自带验证只证明「这一步对了」，任务有没有被满足由 harness 决定。

**三个机制**：

| 机制 | 做什么 | 关键约束 |
|---|---|---|
| 库选择与组合 | 按接口检索或一次读全部接口，读原语自评，产出激活集和依赖边组成的计划图 | 只有被激活的原语运行，成本跟激活数走，而不是库大小 |
| 基于证据的执行与改进 | 分轮执行计划，用任务自己的验收程序（测试、证明检查器、答案）验收，失败追溯到被牵连原语只重做它们 | 有轮数预算 \(B\)，开发原语默认 3 轮 |
| 验证与发布 | 新的或改进的原语在任务之外的路径上验证（测试、编译器、开发轮），通过后才入库 | 任务运行期间预建库不变 |

**两个伴生论文里证明的性质**：一是激活集大小受任务需求上界约束，库再大也不会逼着激活部分变大；二是在一个简化的加法模型下，按题组合打过最佳固定 harness，**当且仅当**选择损失（该开没开、不该开开了，按收益加权）小于固定 harness 与 oracle 之间的差距 \(\Gamma_{\text{fixed}} = \sum_i \min(\mu_i \bar g_i, (1-\mu_i)\bar\kappa_i)\)。这个式子的直觉很实用：**某个原语如果只对一部分任务有益、对另一部分有害，那它就是按题选择的收益来源；对所有任务都有益的原语，固定开着就行。**

**八类原语**：工具（HEART）、代码（LEGO）、数学（Method Contract）、知识（SourceLearn）、多 agent（Agent Primitives，甚至通过 KV cache 通信）、开发（HERMES）、导航（ANTMAN）、harness（STITCH）。每一类都是先有一篇解决某类任务的论文，再被收编进统一定义。

## 🧪 关键证据

**开发原语 HERMES，Terminal-Bench 4.0（66 题跑 5 次，节选）**：

| 模型 / 推理档 | 基线 harness | 基线 | HERMES | 变化 | 基线成本 | HERMES 成本 |
|---|---|---|---|---|---|---|
| GPT-5.6 Sol max | Codex | 37.3 | 55.5 | +18.2 | $2.5k | $4.7k |
| GPT-5.6 Terra max | Codex | 21.5 | 48.2 | +26.7 | $1.7k | $2.9k |
| Claude Opus 5 max | Claude Code | 51.8 | 53.0 | +1.2 | $6.0k | $8.6k |
| Claude Sonnet 5 max | Claude Code | 12.4 | 40.0 | +27.6 | $9.6k | $7.4k |
| DeepSeek-V4 max | mini-SWE-agent | 28.8 | 39.4 | +10.6 | $0.7k | $1.1k |
| Grok 4.6 high | Grok Build | 20.3 | 31.5 | +11.2 | $3.6k | $5.2k |
| Qwen3-8B | 无 | 无 | 27.6 | 无 | 无 | $0.7k |

SWE-bench Verified 上，GPT-5.6 Sol 中档 HERMES 97.00% 对 mini-SWE-agent 96.20%，每题 $1.80 对 $1.15；Claude Opus 5 两边都是 97.00%。整体规律是**基线越弱收益越大**，GPT-5-mini 从 60.80% 到 80.20%。

**harness 原语 STITCH，按题组合对固定 harness（GPT-5.6 Luna 做执行者，各两次尝试）**：

| 方法 | SWE-bench Verified 100 题 Pass@1 | Terminal-Bench 2.0 45 题 Pass@1 | TB2.0 困难题 Pass@1 |
|---|---|---|---|
| mini-SWE-agent（种子） | 73.0 | 60.0 | 38.5 |
| Codex | 79.0 | 56.7 | 30.8 |
| MetaHarness | 73.5 | 55.6 | 38.5 |
| 最好的单个固定原语 | 76.0 | 66.7 | 46.2 |
| 随机组合 | 73.3 | 63.5 | 39.1 |
| STITCH | **80.5** | **72.2** | 46.2 |

组合本身的成本是一次执行者尝试的 2.7% 到 4.3%。

**heelo.dev 46 个真实任务**（发页面、发外联邮件序列、读邮箱里的发票、抓取等，四个闭环 26 种能力）：

| 组合 | 总分 | 完成数 | 每个完成任务耗时 | 每个完成任务成本 |
|---|---|---|---|---|
| Claude Opus 5.5 + Claude Code | 28% | 9 | 6.3 分钟 | $1.24 |
| 同上 + HEELO（MCP） | 90% | 39 | 3.4 分钟 | $0.80 |
| GPT-6.1 Sol + Codex | 25% | 9 | 8.0 分钟 | $0.65 |
| 同上 + HEELO（MCP） | 83% | 35 | 3.5 分钟 | $0.42 |

泼冷水，而且要泼好几盆。

第一，**这是一篇总纲，附录里明说所有数值都抄自八篇伴生研究**。不同家族用不同的底座、不同的基准、不同的对照，「HEELO 在 26 个对比里全部领先」这句话的含义是「八个子系统各自打过了各自选的基线」，不是一个统一系统的一次评测。

第二，**Terminal-Bench 4.0 的 +18.2 点是用接近翻倍的 token 买来的**：GPT-5.6 Sol 最大档从 44 亿 token 涨到 89 亿，总成本从 $2.5k 涨到 $4.7k。在 Claude Code 这个已经很强的 harness 上，Opus 5 只涨了 1.2 点，成本却多了 43%。HERMES 的收益主要体现在「基线 harness 和模型不匹配」或「基线很弱」的格子里。

第三，**heelo.dev 是作者自己的平台、自己的 46 个任务**。单干组几乎都在「需要操作账号或服务」的能力上得零分（发布页面、发邮件序列、读邮箱），这本质上是「有没有凭据和对应工具」的差距，不完全是 harness 设计的差距。论文自己也承认中位数上接 HEELO 的一次 Claude Code 助理任务要读 160,701 个 token，单干只读 19,456 个；「每个完成任务更便宜」是因为分母变大了。

第四，STITCH 的实验只有 100 道和 45 道采样题、各两次尝试，困难题只有 13 道左右，Pass@1 的差距在这个样本量下置信区间不会窄。

## 🔬 最有意思的部分

**「收益来自原语内部」这个对照最有说服力。** 工具原语在同样调用预算下，对比「在原始 schema 上自我修正」的做法，ToolBench 通过率翻了一倍多。代码原语的消融显示，原语携带的字段（自带测试、接口契约、来源出处）解释了它对通用编辑的大部分优势。这说明价值不在「多一个 LLM 调用」，而在**资源旁边固化下来的那份上下文**。

**激活集不随库膨胀。** 导航原语实验里，干扰项让信息空间扩大 16 倍，被激活的原语只增长 1.23 倍。这正是 \(|\mathcal{A}_q| \le \rho D(q)\) 那条命题想说明的东西，对我们这种技能和 MCP 越挂越多的 harness 很重要：**选择器要按需求激活，而不是按库大小线性付费。**

**随机组合和单个固定原语都打不过按题组合，但单个原语也能打过 Codex。** Terminal-Bench 2.0 上一个「State Guard」固定开着就有 66.7%，比 Codex 的 56.7% 高 10 点。这对工程的启示比 STITCH 本身还直接：先找出那一两个对大多数任务都有益的原语固定开启，再考虑按题选择。

**KV cache 通信需要位置重编码。** 多 agent 原语之间交换 KV cache 时，不做 RoPE 重索引准确率会掉。作者在结论里把它和「需求必须送达它关心的组件」并列为一条原则：**跨边界传过去的东西必须保持含义**。这句话放在工具结果、子 agent 交接、记忆读写上都成立。

## 🤔 我的判断

**定位**：一篇有野心的总纲论文，问题定义清晰，单个子系统的结果有一定扎实度，但「统一框架」的说法更多是组织方式，而不是一个经过统一评测的系统。

**亮点三条**：

1. 把「最后一公里」拆成应用、组合、修订三层，给 harness 设计提供了一个可以逐层对照的清单。
2. 「按题组合何时优于固定 harness」的条件式很实用，给出了判断一个原语该常开还是按需开的标准。
3. 验证与发布走独立路径，任务运行期间库不变。这和我们一直强调的「写入与读取分离、执行期不改自身」是同一个原则。

**问题与局限**：数字来自八篇伴生论文拼接；成本经常翻倍；自建平台评测有凭据差异；小样本实验；常驻 LLM 本身的可靠性（会不会在落地参数时出错、出错怎么归因）讨论不够；原语之间的消息是自然语言，契约的强度取决于常驻 LLM 的服从程度。

**对工程的直接启发**：

- 在 MMP 的 Manifest 里，可以把高频工具或技能升级成「带用法上下文的原语」：资源加接口描述加一份落地说明加自带验证，调用方只发需求。
- 原语返回值除了结果，额外带一个「对下游的要求」字段，用结构化格式而不是自由文本，相当于把 HEELO 的消息通道契约化。
- 失败归因做成显式步骤：验收失败后先定位被牵连的原语，只重跑它们，保留其余结果，并设轮数预算。
- 新技能或新原语入库前过一道离线验证（测试、编译、回放），跟任务执行分开。
- 评估这类方案时一定同时报 token 和成本，像 Terminal-Bench 4.0 那张表那样，把「涨了多少分」和「多花了多少钱」放在同一行。

一句话收束：**资源旁边那份「怎么用」的能力才是真正该复用的东西，但把它做成原语之后，账单和契约强度要一起算清楚。**
