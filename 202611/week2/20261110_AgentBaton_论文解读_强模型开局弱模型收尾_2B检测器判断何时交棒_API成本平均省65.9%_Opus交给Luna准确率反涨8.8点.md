# 贵模型只该干前半程？让 Opus 开局、便宜模型收尾，一个 2B 小检测器决定何时交棒，API 成本平均省 65.9%

你有没有过这种体验：一个长程编码任务，旗舰模型跑了四十轮，账单十美元；回头看轨迹，前十几轮在读代码、定位问题、写出主体实现，后面二十多轮其实是在反复跑测试、改一两行、补个边界条件。那后半段真的需要最贵的模型吗？行业里常见的省钱办法叫 **模型路由**：按问题难度在请求开始时决定交给哪个模型。可长程 agent 任务的难度不是一开始就定好的，**它随着工作区被改动、反馈被拿到而一直变化。**

NVIDIA 这篇 AgentBaton 研究的是同一个任务内部的模型协作：先系统地比了「谁先谁后」和「历史怎么交接」，然后训练了一个 2B 的小检测器，在每轮之后判断「现在可以交棒了吗」。看完我的感受是：结论出奇地简单，**一次交棒、强先弱后、时机对了就够**，按轮切换的精细路由反而又贵又不准。

## 核心摘要

作者在 Terminal-Bench 2.1 和 DeepSWE v1.1 上，用 mini-SWE-agent v2.4.0 做统一脚手架，比较两种交棒方向（高效到强、强到高效）和两种上下文传递方式（把历史直接放进接手模型的上下文，或者写成 .jsonl 日志让接手模型自己用 cat、grep 去翻）。接手模型继承完整工作区。发现是**不对称的**：先让便宜模型开局再交给强模型，通常比强模型单干差，而且常常省不了多少钱；反过来，强模型先做、在合适的进度交给便宜模型，能基本保住准确率并大幅省钱。比如在 DeepSWE 上 GLM-5.3 在 30% 进度交给 Qwen3.8-27B，准确率和 GLM 单干持平（61.1%），成本降 82.4%。案例分析发现好的交棒点有共同特征：已经有实质性的实现或产物，拿到了任务相关的执行反馈，剩下的主要是局部的诊断、修补或验证。据此作者从 SWE-rebench V2 抽 2000 道题、跑出 4000 条强模型轨迹，用 Codex 回顾式标注「最早合适的交棒点」，训练 Qwen3.5 2B 做逐轮二分类。在 11 个模型对、两个基准上，API 成本平均降 65.9%，最多比强模型单干还高 8.8 个点（Claude Opus 5 交给 GPT-5.6 Luna，DeepSWE 上 67.3% 到 76.1%，成本降 70.5%）；检测器在单张 H100 上中位延迟 338 毫秒。和按轮路由的 MTRouter 比，成本再低 46.7% 到 86.6%，准确率持平或更高。真正的价值定位是：**把「哪段工作值得用贵模型」从请求级的猜测，变成任务进度上的一次学得会的判断。**

## 🎯 为什么这件事值得写

之前收的 RouteAnything 用一个路由器在 452 种候选里调度，oracle 比固定最优多 5.4 点，可学到的路由平均只多 0.3 点。这说明请求级路由的天花板和实际收益之间隔着很大一道沟。原因之一正是这篇点出来的：**长程 agent 任务里，所需能力随轮次变化**，开始时你根本不知道这道题后面会难在哪。

另一个现实背景是本地模型变强了。Qwen3.8-27B 这种能在工作站上跑的模型，编码和推理已经够用，只是单独做长任务成功率明显低。作者的记账约定把本地可部署模型的成本记为零。如果强模型能把「最难的那部分」先做完，剩下的交给本地模型，云端账单就只剩前半程。

还有一个和我们关心的 harness 设计直接相关的问题：**交接时到底该给多少历史？** 全量塞进上下文成本高，还可能把前任的错误假设带过去；写成日志让接手者按需翻，省钱但可能漏信息。这篇给了有对照的答案。

## 🏗️ 机制 / 任务定义

一次性交棒：源模型做若干轮，接手模型继承工作区继续直到结束，不再切回。总成本是两段之和。

两种历史传递方式：

| 方式 | 做法 | 适合 |
|---|---|---|
| 上下文传递 | 把交棒前的对话（角色、回复、工具调用和输出）转成接手模型的聊天格式；源模型不公开思维链时省略推理字段 | 强到弱，源模型是 GLM-5.3、Kimi K3 这类公开推理的 |
| 日志传递 | 写一个 .jsonl，每轮一条记录（轮号、原始回复、动作列表含命令、返回码、stdout、stderr），接手模型新开会话，只拿到任务、日志路径和字段说明，并被要求先看最后几条 | 弱到强；强到弱时源模型是 GPT-5.6 Sol、Luna 这类不公开思维链的 |

AgentBaton 检测器：

- 底座 Qwen3.5 2B（9B 版本没有明显更好）。
- 输入是检测说明、原始任务、源模型每轮的动作和工具返回，以及之前每轮的判断。
- 输出 JSON：交棒点之前每轮是 HANDOFF_NOT_READY，交棒点那一轮是 HANDOFF_READY。
- 一个小技巧：交棒点之后的每一轮也各生成一个正样本，之前的判断都设为未就绪且不计损失，用来平衡标签并模拟「错过了也要在稍后补上」。
- 推理时上下文超长就丢掉最旧一半的轮次，保留系统说明和任务。第一次判为就绪就交棒。

标注规则沿用案例分析得到的三条：已有实质性实现或任务要求的产物；有任务相关的执行或检查反馈；剩余工作主要是局部诊断、修补或验证。没有清晰转折的轨迹单独标为「无明显交棒点」。

## 🧪 关键证据或主结果

方向和传递方式的对照（DeepSWE v1.1，准确率 / 单题成本，节选）：

| 交棒 | 30% 上下文 | 30% 日志 | 75% 上下文 | 75% 日志 |
|---|---|---|---|---|
| Qwen 到 GLM | 51.3 / 4.04 | 62.8 / 2.93 | 38.9 / 2.61 | 53.1 / 1.87 |
| Qwen 到 Kimi | 47.8 / 7.77 | 62.0 / 4.45 | 37.2 / 5.76 | 50.4 / 2.52 |
| GLM 到 Qwen | 61.1 / 0.56 | 54.9 / 0.56 | 62.8 / 2.07 | 59.3 / 2.07 |
| Kimi 到 Qwen | 69.9 / 1.11 | 56.6 / 1.11 | 76.1 / 3.34 | 76.1 / 3.34 |

便宜模型开局时，日志传递一致更好也更省；强模型开局时，公开推理的 GLM 和 Kimi 用上下文传递更好。作者推测 GPT-5.6 Sol 偏好日志传递，是因为它不公开完整思维链，上下文传递时接手者拿到的推理信息本来就不全。

AgentBaton 主结果（节选，括号内是相对强模型单干的变化）：

| 强模型 | 接手 | DeepSWE 准确率 | DeepSWE 成本 | TB2.1 准确率 | TB2.1 成本 |
|---|---|---|---|---|---|
| GPT-5.6 Sol 单干 | 无 | 68.1 | $5.32 | 87.6 | $0.97 |
| GPT-5.6 Sol | Luna | 67.3 | $1.39（−73.9%） | 82.0 | $0.47（−51.5%） |
| Claude Opus 5 单干 | 无 | 67.3 | $9.91 | 84.3 | $2.83 |
| Claude Opus 5 | Luna | **76.1** | $2.92（−70.5%） | 86.5 | $1.17（−58.7%） |
| Claude Opus 5 | Qwen3.8-27B | 61.9 | $2.61（−73.7%） | 87.6 | $1.13（−60.1%） |
| Kimi K3 单干 | 无 | 73.5 | $4.73 | 86.5 | $1.50 |
| Kimi K3 | Qwen3.8-27B | 72.6 | $1.28（−72.9%） | 86.5 | $0.57（−62.0%） |

其他关键点：

- 22 个（模型对，基准）设置里有 12 个准确率提升或相对损失小于 5%。
- 检测到的交棒点在 DeepSWE 上平均位于源模型轨迹的 26.6% 到 41.1%，在 Terminal-Bench 上是 55.6% 到 68.9%，两个基准差别很大，固定阈值显然不行。
- 请求级路由基线：用同样 2B 底座、2000 条 SWE-rebench 结果训练「Qwen 能不能独立解这题」，训练集准确率 99.55%，上线后只把一道题交给了 Qwen，等于没路由。
- 和固定进度交棒比（这个基线偷看了源模型最终轨迹长度这一未来信息），准确率接近、成本持平或更低；和固定轮数交棒比，准确率稳定更高。

泼冷水。第一，「平均省 65.9%」建立在本地模型成本记为零的约定上，你自己的硬件、电费和吞吐都不在账里；换成 Luna 这种云上便宜模型时，节省幅度仍在 66% 到 74%，这个数更可信。第二，不是所有组合都好：Opus 交给 Qwen 在 DeepSWE 上掉了 8%，Sol 交给 Qwen 掉了 11.6%，GLM 交给 Luna 在 Terminal-Bench 上掉了 7.7%。第三，「准确率反涨」主要出现在交给 Luna 时，作者没有充分解释为什么接手者能比强模型单干做得更好，我猜和强模型后半程的过度探索或卡死有关，但这需要验证。第四，标注依赖 Codex 回顾式判断，训练只用了 SWE-rebench 一类数据，换到非编码的长程任务能不能迁移没有测。

## 🔬 最有意思的部分

**弱先强后为什么不行。** 直觉上让便宜模型先去读代码、收集信息再交给强模型很合理。但数据说，DeepSWE 上 Qwen 在 30% 交给 GPT-5.6 Sol，准确率 70.8%（比 Sol 单干 68.1% 还高），成本却只降 6.1%；交给 GLM 和 Kimi 则省钱但掉点。原因是强模型接手后要花大量力气去理解和纠正前任留下的工作区。作者由此推论**按轮来回切换的路由会累积轨迹错误，强模型反复付出纠错成本**，后面 MTRouter 的对照正好印证了这一点。

**交棒点的三个特征**几乎可以直接写成规则：有东西了、有反馈了、剩下的是局部问题。案例里的转折包括修好一个带引号路径的处理问题、验证了坐标变换、定位到一个编码错误。这些都不是「写完了」，而是「问题被缩小了」。这和我们之前收的 ShortContext（每步只带任务和语义状态）是一个思路：**任务状态被压缩成局部问题时，就不再需要大模型的全局推理。**

**为什么不用规则而要训练一个 2B 模型？** 固定轮数交棒的准确率明显更低（Kimi 交 Qwen 在 DeepSWE 上 69.9 对 72.6），固定进度需要未来信息。学到的检测器其实就是把这三条特征在线识别出来，338 毫秒的中位延迟相比强模型每轮几十秒的推理几乎可以忽略。

**交接格式要看源模型。** 不公开思维链的源模型，上下文传递时接手者只看到动作没看到理由，反而不如让它自己翻日志。这对任何做多模型 harness 的人都是一条很具体的经验：**交接格式不是一个全局开关，而是按源模型配置的。**

## 🤔 我的判断

**定位**：工程样本，配一份扎实的对照实验。方法本身很轻，但对照实验把「方向、格式、时机」三个变量分开测清楚了，这部分比检测器本身更有长期价值。

**亮点三条**：

1. 方向不对称的发现很干净：强先弱后能省、弱先强后不划算，直接否定了很多人直觉上的「便宜模型做侦察」设计。
2. 一次交棒加一个小检测器，就打过了按轮路由和请求级路由，说明在长程任务里「少切换」本身就是一种能力。
3. 交棒点特征可解释，可以先用规则近似，再用检测器精修，落地门槛低。

**问题与局限**：本地模型零成本的记账约定美化了数字；只测了编码和终端任务；标注由 Codex 完成，没有人工校验比例；只研究一次交棒，没有探索「交出去后发现不行再收回」的机制；接手后准确率反超的原因没讲透。

**对工程的直接启发**：

- 在我们的多模型 harness 里，可以先做一个规则版交棒：当已有测试被运行过、失败集中在少量文件、最近几轮的改动都是小 diff 时，把后续轮次交给便宜模型。
- 交接默认写结构化日志（每轮动作、返回码、stdout、stderr），接手者从最后几条看起；源模型公开推理时再考虑全量上下文。
- 子 agent 路由别做成按轮的细粒度切换。这篇和 Hermes 那种按 profile 路由的思路可以结合：路由粒度放在阶段上，而不是轮上。
- 评估省钱方案时，把本地模型的成本按真实硬件折算，再看帕累托前沿是否还在。

一句话收束：**贵模型的价值在于把问题缩小，缩小之后就该把接力棒交出去；难的不是交，而是知道什么时候问题已经够小了。**
