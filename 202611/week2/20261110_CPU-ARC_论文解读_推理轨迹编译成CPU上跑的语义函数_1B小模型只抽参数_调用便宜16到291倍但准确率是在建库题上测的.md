# 同一类题别让大模型每次重想一遍：把推理轨迹编译成 CPU 上跑的语义函数，1B 小模型只管抽参数，调用便宜 16 到 291 倍

你有没有过这种体验：agent 的某个端点每天收几千个请求，提示词一样、计划一样，只是负载不同，可每个请求都要让云端大模型从头读一遍指令、从头推理一遍。你看着账单想：**它昨天已经把这道题的解法想明白了，今天换个数字，为什么还要再想一遍？**

NVIDIA 这篇 CPU-ARC（和 AgentBaton 同一个组，Peter Belcak、Pavlo Molchanov 都在作者里）给的答案是：**把「找解法」和「执行解法」拆开**。大模型推理过一次之后，让一个构建模型把它的推理轨迹改写成一组参数化的「语义函数」，以后同类题只需要一个 1B 小模型从输入里把参数抽出来，剩下的交给 CPU 执行代码。看完我的感受是：这个想法对做重复型 agent 端点的人非常实在，它其实是**把技能沉淀做到了代码级**；但论文里「缓存比源模型还准」那组数字，要先弄明白是在哪些题上测的。

## 核心摘要

作者提出 **agentic reasoning caching（智能体推理缓存）**，产物叫 ARC。两个观察：一是一旦问题被推理通了，执行解法（计算或数据操作）几乎不需要语言模型参与；二是一次推理往往适用于一整类「同理」的问题，换措辞、换参数，推理步骤一个字都不用改。构建分五步：输入输出分离、把轨迹拆成函数大小的逻辑操作、识别可变参数并生成通用输入模板、规划函数依赖和粒度、在一个智能体循环里逐个实现并测试语义函数，每个函数都要过语法检查、叙述质量静态检查和 judge 比对，最后根函数端到端测正确性和参数抽取的稳健性。调用时四步：入口语义检索（没命中就回退到大模型）、小模型抽参数、执行根函数、返回结果和完整叙述轨迹。成熟后的缓存还可以静态编译成一个不依赖向量库的独立 Python 模块。实验用 Claude Opus 4.5 做源模型和构建模型，微调后的 Llama 3.2 1B 做目标模型，在 MATH-500、AIME 2024 到 2026、GPQA Diamond、GSM8K、MMLU-Pro、SciBench 八个设置上，缓存准确率在七个上持平或超过源模型，对改措辞、改参数、两者都改的扰动通过率都在 90% 以上，调用成本是源模型的 1/16 到 1/291，构建成本是源模型单次推理的 12 到 84 倍。真正的价值定位是：**对「同指令、不同负载」的重复工作，推理可以被缓存成可审查、可增量扩充的代码，而不只是缓存 KV 或答案。**

## 🎯 为什么这件事值得写

现在的系统级缓存大致两类：

| 类型 | 代表 | 优点 | 问题 |
|---|---|---|---|
| 整体缓存 | 前缀 KV 缓存、按会话 ID 缓存、语义相似度匹配 | 计算便宜，命中时可保证完全正确 | 对一点点扰动都不稳；用语义匹配变稳了，又可能答错 |
| 模块化缓存 | 把上下文拆成关键逻辑步骤，再喂回给模型加速 | 对参数扰动更稳 | 命中了也要重新生成一遍，无法在审查后保证正确 |

ARC 想同时拿到两边的好处：像模块化缓存一样拆开、能换参数复用，又像整体缓存一样命中后直接出结果、可以事先审查。对我们关心的方向来说，它和之前收的 Work2Skill（录一次人类操作写成 SKILL.md）、技能库、harness 持续学习是同一条线，只是把沉淀物从自然语言说明推进到了**可执行、可编译、可版本化的代码**。作者自己也说，缓存可以持续往里加新条目而不用重建旧条目，这一点比微调模型要友好得多。

## 🏗️ 机制

**语义函数**是核心抽象。它不靠固定的变量名和函数名，而是靠自然语言描述来绑定：

- `load(ctx, "the blue vertex set B", d_type=list)`：按描述从上下文里语义检索取值。
- `do(ctx, "Compute the difference set D(B) for ...", {...})`：按意图而不是按名字调用子函数。
- `lm(...)`：只在需要时调小模型做值抽取、格式转换、分类、摘要这类基础语言处理。
- `narrate(ctx, "...")`：记录推理过程，最后拼成人能读的解释。

上下文是一个分层的记忆栈，每层背后是一个用小嵌入模型的 CPU 向量库，`load()` 从最内层往外找，`do()` 进入时压栈、返回时出栈，天然隔离作用域。

**构建五步**：

1. **输入输出分离**：从查询里抽出用户输入，从轨迹里抽出最终答案作为参照。
2. **分解**：把推理拆成层级化的逻辑操作，每个操作只说它消费哪些基本输入，同时标出可能在其他题里复用的子计算。
3. **参数识别**：判断这道题属于哪一类，哪些输入是这一类题里会变的参数，生成通用模板 \(q(\bullet_1, \ldots, \bullet_n)\)，并分析每个参数的合法取值范围。
4. **规划**：决定建哪些函数、依赖关系、自底向上的实现顺序和根函数；粒度可选细、中、粗。
5. **实现**：先在注册表里找语义等价的已有函数，能复用就复用；写好的候选要过语法检查、叙述数量和控制流复杂度是否相称的静态检查、用原参数执行并由 judge 和轨迹对应片段比对。全部函数注册后，根函数先用原参数测正确性（对照轨迹和标准答案），再模拟真实调用，让小模型从原始输入抽参数，重复 \(N\) 次测抽取稳健性。

**编译**：注册表稳定之后，把每个 `do()` 替换成直接函数调用，每个 `load()` 替换成字典查找，得到一个不需要嵌入模型和向量库的独立 Python 文件。代价是冻结了函数网络，加新条目要重新编译。

**目标模型能多小**：Claude Haiku 4.5、Gemini 3.0 Flash Lite、GPT 5.4 Nano 都够用；作者又用 20% 的真实调用样例加十倍合成数据微调 Llama 3.2 1B，也够用。构建循环能观察调用输出并调整函数里的 LM 调用，所以能容忍一个不完美的小模型。

## 🧪 关键证据

主结果（源模型和构建模型都是 Claude Opus 4.5，扩展思考预算 4096 token；缓存端是微调的 Llama 3.2 1B）：

| 基准 | 源模型准确率 | 缓存准确率 | 缓存与源一致率 | 改措辞 | 改参数 | 两者都改 | 构建倍数 | 节省倍数 |
|---|---|---|---|---|---|---|---|---|
| MATH-500 | 98.6 | 98.8 | 99.6 | 96.7 | 94.5 | 91.6 | 30.5 | 88.7 |
| AIME '24 | 100.0 | 100.0 | 100.0 | 96.0 | 99.3 | 95.1 | 12.9 | 262.4 |
| AIME '25 | 83.3 | 93.3 | 90.0 | 98.4 | 91.2 | 93.4 | 12.1 | 291.1 |
| AIME '26 | 90.0 | 96.7 | 90.0 | 97.9 | 90.9 | 90.8 | 12.9 | 281.4 |
| GPQA Diamond | 83.8 | 83.8 | 98.5 | 93.8 | 93.9 | 94.0 | 25.1 | 38.1 |
| GSM8K | 98.5 | 98.0 | 99.5 | 96.2 | 94.2 | 92.5 | 83.7 | 16.3 |
| MMLU-Pro | 88.0 | 89.0 | 100.0 | 95.7 | 96.7 | 91.9 | 40.8 | 22.9 |
| SciBench | 85.2 | 88.2 | 99.4 | 97.5 | 98.8 | 96.4 | 29.0 | 83.0 |

缓存每次调用的绝对成本在 $0.0004 到 $0.0019 之间。回本点约为构建成本除以每次节省：AIME 大约 13 次同类调用就回本，GSM8K 大约要 90 次。

泼冷水，这篇需要的冷水比较多。

第一，**「缓存准确率」是在建缓存用的那批题上测的**。每道题单独建一个缓存再合并，构建第五步的根函数正确性测试明确用了标准答案作对照。所以 AIME '25 从 83.3% 到 93.3% 并不说明缓存「比源模型更聪明」，更接近于「源模型推理基本对了，构建者在知道正确答案的情况下把最后一步的算错修掉了」。作者给的解释是确定性代码避免了源模型最后几步的计算失误，这个解释成立，但前提是构建时看过答案。

第二，**泛化证据只来自扰动测试**，而扰动只对已经答对的条目做，扰动题由 Opus 4.5 生成、两个 Opus 4.5 组成的委员会验证、另两个 Opus 4.5 组成的委员会判分。整个链条都是同一个模型家族，扰动的难度和多样性有天然上限。没有「用 A 题建的缓存去解从未见过的 B 题」这种跨题测试。

第三，**源模型的思考预算只有 4096 token**，这让源模型的准确率偏低，也让节省倍数偏高。

第四，作者自己说用数学和科学题评测「不是因为打算用在这类题上」，而是把它们当作智能的代理指标，推论「能缓存这些就能缓存相应领域的所有智能」。这个推论跳跃很大，真实 agent 端点的输入远比数学题杂乱，入口检索的阈值和误命中率才是落地时最要命的指标，论文里几乎没讨论。

## 🔬 最有意思的部分

**「同理」这个概念很好用。** 作者把能用同一套推理解的题叫 equirational，再把扰动分成同参数改措辞、同措辞改参数、两者都改。表 1 那个例子很直观：196 和 144 的约数个数，推理步骤一个字不变，只是数字不同。**大量 agent 工作其实就是这种「同理」的重复**：同一个发票字段校验、同一个日志分类、同一个报表口径计算。

**函数靠描述而不是名字绑定。** 这让缓存里的逻辑可以被不同措辞、不同结构的问题复用，也让构建者在写新函数前先去注册表里按语义找已有实现。随着缓存变大，复用率会上升，作者推测缓存的增长会是相对输入量的亚线性。这和我们在 HEELO 里看到的「激活集不随库膨胀」是同一类期望，都需要实测。

**编译这一步对工程最友好。** 一个成熟的缓存最后变成一个可读、可 diff、可代码审查、可独立部署的 Python 文件。对受监管的场景，这比「模型这次大概会这么答」有本质区别：**你可以在上线前审代码，而不是事后审输出。**

**回退路径是设计的一部分。** 入口检索没命中就把请求交回大模型。这让 ARC 天然适合放在大模型调用前面做一层「先试缓存」，不会因为缓存覆盖不全而降低服务能力。作者设想的部署方式是：在一个重复型端点上先积累几小时到几周的使用，然后按这套方法产出一个更高效的版本，保留大模型兜底。

## 🤔 我的判断

**定位**：工程方法论文，想法有长期价值，评测设计偏乐观，离生产还缺误命中和跨题泛化的数据。

**亮点三条**：

1. 把「找解法」和「执行解法」明确拆开，给技能沉淀提供了一个比自然语言说明更硬的落点。
2. 语义函数加分层上下文加编译，从可增量扩充到可冻结审查，生命周期设计完整。
3. 成本账算得清楚，给出构建倍数和回本点，而不是只报节省倍数。

**问题与局限**：同题构建同题测试，且构建时用了标准答案；扰动生成和判分全靠同一模型家族；没有误命中率和阈值敏感性分析；源模型思考预算偏低；只测了数学和科学题，离 agent 端点的真实输入差很远；多个相似函数合并成更通用函数的问题作者明确说没解决。

**对工程的直接启发**：

- 在我们的 harness 里，对高频、同指令的子任务（固定口径的数据转换、格式校验、分类路由）可以试一层「推理缓存」：首次由大模型解，随后让构建模型把轨迹改写成参数化函数，配测试入库，下次先查缓存，没命中再回退。
- 这条路和技能库是互补的：SKILL.md 记录「怎么做」，ARC 式的函数记录「已经做对过的那一类计算」。前者给模型读，后者直接执行。
- 入库门槛要用**未见过的同类样例**测，而不是用构建样例测；构建时如果用了标准答案，就必须另留一份从未参与构建的验证集。
- 给入口检索设阈值时，把误命中当成头号风险监控：一次误命中是用错误的解法稳定地输出错误答案，比大模型偶尔出错更隐蔽。
- 叙述轨迹（narrate）可以直接当审计日志用，和我们在记忆系统里要求的写入凭据是同一个思路。

一句话收束：**大模型想明白一次，就不该再为同一类题反复付费；但「想明白」的证据，得在它没见过的题上拿。**
