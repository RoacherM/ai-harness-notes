# 给 agent 的经验记忆，为什么反而让它做砸了本来会做的题？WikiTrace：每条教训都要能追回当初那次运行

你大概见过这种场景：给 agent 挂上一套「经验记忆」，平均分确实涨了，可翻开逐题结果会发现，有些它原本稳稳能做对的题，挂上记忆后反而错了。原因往往很朴素：记忆里有一条教训说「台灯类任务，只要物体放在亮着的台灯旁边就算完成」，agent 照着做，结果失败。而这条教训的来源轨迹里，当时 agent 其实是**先把物体拿起来再开灯**才成功的。教训是错的，证据就在原始轨迹里，可 agent 只拿到了教训，看不到轨迹。

这类问题有个名字，叫**记忆诱发退化**（memory-induced degradation）。KAIST 和 DeepAuto.ai 的这篇论文把它当成一等公民来测，并给出一个很工程化的回答：**教训别单独存，每条都要带着一条能追回原始运行的链接，agent 觉得不对劲时自己顺着链接下去查。** 看完我的感受是：这不是一个更聪明的记忆抽取方法，而是一个关于记忆来源（provenance）的数据结构选择，而且它的收益主要来自「出了问题之后去查证据」。

## 核心摘要

WikiTrace 把记忆组织成三层并保持上下链接：最上层是简短的 insight（做什么、何时适用、来自哪次运行、那次运行成功还是失败），中间层是 compilation（对那次运行为什么成功或失败的诊断，成功和失败用不同模板），最下层是原样保留的原始轨迹。每次运行最多抽 3 条 insight，各自独立生成、写入后不再修改或删除，冲突留给 agent 在用的时候判断。测试时 agent 一开始拿到全部 insight，并被提示在三种情况下顺着链接往下查：insight 缺少可执行的细节、和另一条冲突、来自失败运行；动作失败时也要再查。记忆以只读文件挂载，agent 用 read 和 bash 去翻。实验在 5 个基准、8 个套件上进行（ALFWorld 两套、ScienceWorld、PlanCraft 两套、AppWorld 两套、τ³-bench Retail），统一用 Pi 终端 agent 加 deepseek-v4-flash，每个方法 3 次试验。WikiTrace 在全部 8 个套件上第一，平均 90.2，对比无记忆 79.5、只给同样 insight 不给来源的 Insights Only 87.0；Regression（无记忆能做对、加记忆后做错的比例）从 Insights Only 的 6.5% 降到 4.5%，而无记忆重跑一遍的自然波动是 9.7%。它是唯一一个在每个套件上都不低于无记忆的方法。测试时单题成本是 Insights Only 的 1.17 倍。真正的价值在于：**把「记忆该不该信」从写入时的一次性决定，变成使用时可以回溯证据的判断。**

## 🎯 为什么这件事值得写

经验记忆这条线已经很热闹：Reflexion 式的语言反思、ExpeL 的规则列表、AWM 的工作流、ReasoningBank 的推理策略，还有各种技能库和手册。它们的共同点是**把一条只带成功或失败标签的轨迹，蒸馏成几句话的教训**。问题在于，一条轨迹有几十步，单一的成败标签并不告诉你是哪一步导致了结果。任何从中抽教训的方法都得猜：哪些动作重要、在什么条件下重要。猜错一次，就多一条会误导后续任务的错误教训。

更麻烦的是，现有方法交给 agent 的只有教训本身，来源被丢掉了。agent 没有任何办法核对。

作者先做了一个诊断：取那些无记忆时三次都能做对、加记忆后却做错的任务，让 gpt-5.6-sol（中等推理强度）对比两条轨迹，找到第一次分叉的回合并归因。所有方法合计 355 个这样的失败里：

| 类别 | 含义 | 数量 |
|---|---|---|
| A | 记忆条目本身是错的 | 70 |
| B | 有效条目用在了适用范围外 | 41 |
| C | 有效条目被 agent 用错 | 45 |
| D | 记忆里有更好的条目却没用 | 28 |
| E | 和任何记忆条目都没有可见关联 | 171 |

A 到 D 合计占 52%，其中最多的是条目本身就错（20%）。按方法看，ExpeL 贡献了 101 个，ReasoningBank 78 个，AWM 68 个，Insights Only 62 个，WikiTrace 46 个。

这对我们做多 agent 共享记忆的人很直接：**一条记忆如果失去了来源，它就从「可以核对的证据」变成了「只能相信的断言」。**

## 🏗️ 机制 / 任务定义

**问题设定**。给定一批无记忆时收集的历史运行 $D_{train}=\{(x_i, r_i, s_i)\}$，其中 $s_i\in\{0,1\}$ 是成败。没有标准答案也没有专家解释。记忆在任何测试任务开始前一次构建完成，之后只读，不允许额外跑运行来验证某条记忆。

**构建**。记忆 $M=(R, C, I, E)$：原始轨迹、compilation、insight、来源链接。

$$(c_i, I_i) = \text{Compiler}(x_i, r_i, s_i)$$

- compilation 对成功运行记录「关键决策和支撑观察」，对失败运行记录「可能的失败原因」。作者特别强调这些只是**解释**，不是经过验证的因果。
- insight 每次运行最多 3 条，每条是独立文档，固定模板：Insight、Applicability、Source episode（指向 compilation 和原始轨迹路径）。
- 原始轨迹原样保存：任务元数据、每回合的推理、动作、观察、成败。
- 每层都有索引，方便 agent 导航。
- insight 一旦写入不再更新或删除，所以池子里可能有冗余和互相矛盾的条目，**判断哪条适用交给使用时的 agent**。

**使用**。初始消息里放全部 insight，再列出与当前任务最相似的 3 次历史运行及其 insight 标题，作为搜索起点。提示要求 agent 在以下情况「下潜」（descend）：

| 触发条件 | 说明 |
|---|---|
| 缺细节 | insight 没给出当前能执行的具体信息（比如命令格式） |
| 冲突 | 和另一条 insight 说法不一致 |
| 来自失败运行 | 来源运行本身是失败的 |
| 动作失败 | 任何动作失败后再查一次 |

**对照设计**。最关键的基线是 Insights Only：给完全相同的 insight，但不挂 compilation 和原始轨迹，也不给下潜提示。两者唯一差别就是能不能回到来源，所以差值可以干净地归因到「来源可达」。

## 🧪 关键证据或主结果

**主结果**（3 次试验均值）：

| 方法 | ALF 见过 | ALF 未见 | ScienceWorld | PlanCraft 见过 | PlanCraft 未见 | τ³ Retail | AppWorld 常规 | AppWorld 挑战 | 平均 |
|---|---|---|---|---|---|---|---|---|---|
| 无记忆 | 94.4 | 94.3 | 83.7 | 72.3 | 56.3 | 86.8 | 75.4 | 72.7 | 79.5 |
| AWM | 94.7 | 97.3 | 88.9 | 76.3 | 57.3 | 85.5 | 79.3 | 73.4 | 81.6 |
| ReasoningBank | 92.1 | 92.8 | 85.0 | 84.7 | 61.3 | 86.4 | 80.8 | 70.7 | 81.7 |
| ExpeL | 94.4 | 98.0 | 91.9 | 74.0 | 51.0 | 82.5 | 80.5 | 70.0 | 80.3 |
| Insights Only | 96.7 | 97.3 | 94.9 | 88.7 | 73.0 | 85.1 | 86.8 | 73.7 | 87.0 |
| WikiTrace | 98.7 | 98.8 | 96.1 | 93.3 | 81.3 | 88.2 | 89.5 | 75.8 | 90.2 |

几个读法：

- 现有方法都有低于无记忆的格子：ReasoningBank 在 ALFWorld 和 AppWorld 挑战集，ExpeL 在 PlanCraft 未见集（51.0 对 56.3）和 τ³ Retail，连 Insights Only 在 τ³ Retail 也低于无记忆（85.1 对 86.8）。**WikiTrace 是唯一一个每格都不低于无记忆的方法。**
- 最大的提升在 PlanCraft：未见集从无记忆 56.3 到 81.3。但 PlanCraft 未见集上 WikiTrace 的标准差是 8.5，Insights Only 是 10.7，波动不小。

**Gain 和 Regression**。作者把「把失败变成功」和「把成功变失败」分开算：以无记忆三次的多数结果为参考，Gain 是参考失败的题上加记忆后成功的比例，Regression 是参考成功的题上加记忆后失败的比例。为了扣掉随机波动，又额外跑了三次无记忆作为「重跑基线」。

| 指标 | WikiTrace | Insights Only | 重跑基线 | 现有记忆方法 |
|---|---|---|---|---|
| Regression | 4.5% | 6.5% | 9.7% | 与重跑相当或更高 |
| Gain 超过重跑基线 | 35 个百分点 | 27 个百分点 | — | 7 到 14 个百分点 |

WikiTrace 在 8 个套件中的 7 个上 Regression 低于 Insights Only，且是唯一一个 Regression 置信区间完全落在重跑波动带之下的方法。

**什么时候下潜有用**。在三个文本世界基准上，WikiTrace 在简单题上 22% 的运行会下潜，难题上是 44%。下潜运行相对 Insights Only 的领先比不下潜的运行多 1.6 到 4.7 个点，差距随难度从 1.8（简单）到 3.7（中等）到 4.1（难）递增。不过作者也提醒：下潜是 agent 自己选的，下潜和不下潜的运行不只差在下潜这一件事上。

**成本**。为排除「只是构建预算更多」，作者把 AWM 的构建跑 9 遍，ExpeL 和 ReasoningBank 各跑 3 遍，平均分分别到 83.8、83.3、82.8，仍低于 WikiTrace 的 90.2。测试时单题成本是 Insights Only 的 1.17 倍。

**换骨干**。用 GLM-5.3-flash 在 PlanCraft 和 ScienceWorld 三个套件上重做：WikiTrace 平均 92.7，Insights Only 90.9，无记忆 71.2；每个现有记忆方法都至少在一个套件上低于无记忆。

泼几盆冷水：

- **训练集很小**：每个基准只有 38 到 54 次训练运行，记忆总量不大，所以作者可以把**全部 insight 都塞进第一条消息**。记忆一旦大到放不下，就得先检索，这个问题论文明确留给了后续。实际系统里这是最大的工程差距。
- **归因靠 LLM judge**：失败类别和下潜的动机、效果都由 LLM 读 agent 推理文本来标，作者自己也说这些标签描述的是「推理里怎么说」，而不是「是什么导致了结果」。触发和目标的 judge 间一致性 κ 分别是 0.77 和 0.63，效果标签更难，用了三个 judge 投票。
- **来源链接不等于验证**：compilation 对失败原因的诊断本身可能是错的，链接只是让 agent 有机会核对，并不保证核对正确。
- **单 agent、离线、只读**：记忆在测试前固定，没有测在线写入、多个 agent 并发读写的情况。

## 🔬 最有意思的部分

**第一，收益集中在「出事之后」的下潜。** 作者把下潜按触发原因分类：遇到动作受阻、观察和计划不符、怀疑某条 insight 之后的下潜只占 36%，但相对 Insights Only 领先 10.4 个点；一切正常时的下潜领先只有 3.7 个点。最大的一格是 17.3 个点：**动作受阻后去历史运行里找一个具体事实**，这恰恰是只有 insight 的方法完全做不到的。最常见的下潜是例行检查（38%），其中 90% 是去读一个相似运行的流程，领先只有 3.4 个点。这对 harness 控制器设计很有参考价值：**证据回溯最值钱的触发器不是「每次都查」，而是「失败或冲突时查」。**

**第二，打开来源后有 43% 的情况改变了计划。** 改计划的方式包括修正一条 insight（24%）、补上 insight 漏掉的细节（14%）、找到 insight 根本没覆盖的事实（4%）。改了计划的运行领先 8.3 个点，只确认原计划或打开后没用上的运行领先 4.4 个点。

**第三，失败运行是一把双刃剑。** 在 PlanCraft 和 ScienceWorld 上分别只用成功运行、只用失败运行、两者都用来建记忆，两种方法都是「只用失败」好于「只用成功」，两者都用最好。但 Insights Only 只用失败运行时 Regression 最高，PlanCraft 9.3%、ScienceWorld 9.4%；同样的 insight 换成 WikiTrace，降到 7.1% 和 8.9%。也就是说，**从失败里学到的教训最有用也最危险，危险的部分可以靠保留来源部分化解。**

**第四，一个具体的冲突消解案例。** PlanCraft 里有一条来自失败运行的 insight 说「如果放一个材料就已经合成出东西，需要多个该材料的配方可能不可行，考虑放弃」。实际上输出槽里那个东西只是预览，拿走它才会消耗材料。Insights Only 照着这条错误教训宣告不可能；WikiTrace 在推理里写了一句「等等，也看看那次成功的运行」，读到成功轨迹的观察，修正了教训，然后完成任务。

**第五，WikiTrace 报告「用到的 insight」更少。** 不下潜的运行里报告使用的 insight 比 Insights Only 少 19% 到 28%，下潜运行里少 38% 到 57%。更少地用记忆，反而做得更好，说明**挑剔地用记忆本身就是一种能力**。

## 🤔 我的判断

**定位**：一个记忆来源（provenance）设计的工程样本，加上一套把「记忆帮了多少」和「记忆害了多少」分开测的评测方法。方法本身不复杂，核心就是「别丢掉来源，并给 agent 一个什么时候回去查的规则」。

**亮点三条**：

1. Gain 和 Regression 分开报告，并用无记忆重跑作为噪声基线，直接暴露出现有记忆方法的退化率并不比随机重跑好。
2. Insights Only 这个对照把变量控制得很干净，差值可以归到「来源可达」这一件事上。
3. 下潜动机和效果的细分数据给出了可操作的结论：失败或冲突触发的回溯最值钱，例行回溯收益有限。

**问题与局限**：记忆规模小到可以全量放进上下文，检索问题没解决；归因依赖 LLM judge 读推理文本；只测了离线、只读、单 agent；compilation 的诊断本身可能错。

**对工程的直接启发**：

- 任何共享记忆或技能库，每条条目都应带一个指回原始运行（轨迹、日志、提交）的不可变链接，并标明来源运行的成败。这比在写入时做更聪明的筛选成本低得多。
- 记忆条目写入后不改不删，冲突留在库里，由使用方在有证据的情况下裁决。这和多 agent 共享记忆里「追加写、读时裁决」的并发策略天然兼容。
- 在 harness 的提示或控制器里写明回溯触发器：条目缺细节、条目冲突、条目来自失败运行、动作失败。不必每步都查。
- 评测记忆或技能系统时，除了平均分，一定要单独报 Regression，并跑一次无记忆重跑作为噪声带。
- 来自失败运行的教训单独打标签，使用前优先核对来源。

一句话收束：**记忆的问题不是记得不够多，而是记住的结论失去了出处；WikiTrace 用一条链接把「可以信」变回了「可以查」。**
