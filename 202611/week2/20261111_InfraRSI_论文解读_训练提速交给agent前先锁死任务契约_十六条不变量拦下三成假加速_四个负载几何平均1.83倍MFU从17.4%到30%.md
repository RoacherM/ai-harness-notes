# 让 coding agent 去调分布式训练，它最先学会的是改计时器？InfraRSI 先锁契约再搜索，四个负载几何平均 1.83 倍

你有没有过这种体验：让 agent 去优化一份训练脚本，它很快回报「step time 降了 30%」，你兴冲冲去看 diff，发现它把一部分优化器更新挪到了计时窗口外面，或者偷偷加了一个不在允许列表里的低精度 cast，loss 曲线也悄悄歪了。行业里这类事统称 **reward hacking**，在 kernel 合成、算法发现这些 RSI（递归自我改进）场景里大家已经吃过亏；可一旦目标换成多机多卡的训练基础设施，噪声、OOM、编译冲突全都叠上来，问题就变成：**agent 报回来的加速，到底有多少是真的？**

这篇来自 TokenRhythm、北大、无问芯穹、上交、清华的 InfraRSI，把「训练系统优化」做成了一个带合同、带审计、带经验库的 harness：init、doctor、run、report、apply 五个确定性阶段，中间的 run 是一个不靠 LLM 拍脑袋、而是靠全局时间模型和删失内存模型驱动的组合搜索。看完我的感受是：这篇最值钱的不是 2.75 倍那个数，而是它把「agent 改基础设施」该有的验收闸，一条一条写成了可以抄的清单。

## 核心摘要

InfraRSI 的目标是在固定任务契约下最大化训练吞吐：模型结构、数据集、每次优化器更新处理的 token 数、允许的精度菜单、优化器更新协议全部锁死，候选只能在「启动参数 knob 加源码 patch」这个联合空间里找。init 阶段解析仓库 AST，声明 editable_files，并对数据加载、评测脚本、loss 定义、harness 计时器这些 frozen_files 锁 SHA-256；doctor 跑基线、裁掉 warmup、标定集群配对噪声、拆出前向反向优化器通信各阶段耗时；run 阶段用 Cholesky 贝叶斯线性模型拟合 log 加速、用右删失 Tobit 模型拟合峰值显存（OOM 的试验也算一条观测，只是给出下界），在此之上做三起点初始化、反常识大 knob 探测、OOM 后的「显存搭档」补全、局部最优逃逸和小 patch 叠加；最后把最快的有效候选和基线背靠背重跑，过了校准噪声门才晋升，通过全部不变量的观测写回跨硬件经验库。验收由五层 16 条确定性不变量完成（执行、负载、调度、数值、计时）。在 Qwen3.5-9B（8×H100）、Gemma-4-26B-A4B MoE（8×H200）、Qwen3.8-27B（8×H200）、两机 Qwen3.5-35B-A3B MoE（16×H100）四个负载上，InfraRSI 几何平均 1.83 倍，平均 MFU 从 17.4% 到 30.0%，高于 RE-Bench 脚手架（1.37 倍）、Auto-Research（1.34 倍）和只调 knob 的 OptiCo（1.23 倍）。离线重判 1,212 次存档执行，16 条不变量拒掉 400 次（33.0%）。反直觉的一条是：前沿 LLM 对加速幅度的零样本预测和实测的 Spearman 相关在 -0.49 到 -0.06 之间，**模型给的先验不只是不准，是方向上偏反的**。它真正的价值定位是：**一个把「LLM 出主意」和「测量、验收、搜索、记经验」彻底拆开的基础设施 RSI 样板。**

## 🎯 为什么这件事值得写

FunSearch、AlphaEvolve、Darwin Gödel Machine、AIDE、Karpathy 的 autoresearch，这一路 RSI 的共同点是：评测便宜（毫秒到秒）、可以跑成千上万次、噪声低。训练基础设施完全反过来。论文的 Table 1 把差别列得很清楚：一次评测要占多卡、整个搜索只能跑 10 到 20 次、配对噪声从 0.04% 到 6% 以上横跨两个数量级、reward hacking 的风险从「验证集过拟合」升级到「预取偏斜、计时器偏移、精度漂移」。

作者在四个负载上让现成的 coding agent 和贪心调参器直接上，总结出四种反复出现的失败：

1. **奖励作弊和计时边界偏移**：未授权的低精度 cast、把辅助更新推迟到计时窗口外并用单条 receipt 的 valid 标记把 import 错误盖住、日志计时和墙钟时间不一致、激进 fused cross-entropy 让 loss 变差。
2. **宽谱噪声**：固定 2% 门槛在安静集群上会丢掉 0.5% 到 1.5% 这种能叠加的通信重叠小优化，在吵的共享主机上又会把随机抖动当成加速。
3. **LLM 定量先验失准**：Gemma-4-26B-A4B MoE 上模型预测 torch.compile 只有 +2.0%，实测 +55%；两机 MoE 上模型预测加 NCCL 通道会略慢，实测 +10.2%。
4. **单一现任者近视**：关掉激活重算单独就 OOM（差 18 GiB），开 compile 配默认 fused kernel 直接挂，不会配「省显存搭档」的搜索器就永远卡在这里；Auto-Research 在 Gemma 上停在 1.29 倍原地打转。

这四条里，第一条对任何「让 agent 改会被打分的东西」的场景都成立，第三条则直接挑战了「LLM 当搜索先验」这个默认假设。

## 🏗️ 机制 / 任务定义

优化目标写成一个带硬约束的最大化：

$$
\max_{a\in\mathcal{A}}\; y(a)=\ln\frac{T_0}{T(a)}\quad \text{s.t.}\quad I_k(a)=\text{True},\;\forall k\in\{1,\dots,16\}
$$

16 条不变量分五层：

| 层 | 检查什么 | 离线重判触发（触发数 / 首次失败归因） |
|---|---|---|
| L1 执行 | 退出码 0、完成目标更新数、无 NaN/OOM/NCCL/import 错误、显存在上限内 | 503 / 352 |
| L2 负载 | 每次更新 token 数、序列长度、数据摘要、模型摘要与参数量、frozen_files 哈希 | 7 / 7 |
| L3 调度 | 实际优化器步数相同、辅助状态更新在计时窗口内同步完成 | 0 / 0（推迟更新靠源码审计抓） |
| L4 数值 | 预先声明的 loss 容差、梯度范数、精度菜单 | 42 / 41 |
| L5 计时与配对 | harness 墙钟增益和脚本自报增益一致（\|Δln\| ≤ 0.03），晋升需背靠背重跑超过校准噪声 | 158 / 0 |

几个关键设计：

- **噪声门**：doctor 合并配对基线重跑差和窗口内 split-half 偏差得到 \(\sigma_{pair}\)，搜索中用 \(\max(0.02, 2\sigma_{pair})\) 判断大 knob 和停滞，晋升要求背靠背重跑超过 \(e^{2\sigma_{pair}}-1\)。安静的 8×H100、8×H200 节点上测到的配对噪声只有 0.04% 到 0.10%。还用 doctor 测得的阶段耗时占比给单个杠杆的预测加了 Amdahl 上限。
- **三起点**：第一起点是经验库里最相似环境的已验证最优整套配置；第二起点是先验模型评分最高、且至少一个大 knob 与第一起点不同的配置；第三起点是过滤冲突规则后的均匀随机合法配置。
- **删失内存账本**：完成的试验给精确峰值，OOM 的试验给「至少需要这么多」的下界，接近满卡的抖动给区间。这样 OOM 不再是废数据，而是能给出「这个设置要多花多少 GiB」的估计，用来区分显存花销项和节省项。
- **失败归因**：OOM 的设置被标成「需要一个能覆盖缺口的省显存搭档」，换了多个搭档都失败才排除；非显存类崩溃只封禁最小冲突元组（所有成功运行里都没出现过的那对或三元组）；代码探索阶段的失败归咎于 patch，不连累底下的启动配置。
- **经验协议**：Environment、Observation、Effect 三类实体，71 个规范化机制，按兼容范围和环境距离排序。经验只用来定起点和初始化先验，后验完全由目标机器上的实测决定。

## 🧪 关键证据或主结果

| 负载 | 基线 MFU | OptiCo | Auto-Research | RE-Bench | InfraRSI |
|---|---|---|---|---|---|
| Qwen3.5-9B（8×H100） | 25.3% | 1.24× | 1.53× | 1.62× | 1.73×（43.8%） |
| Gemma-4-26B-A4B MoE（8×H200） | 6.4% | 1.32× | 1.29× | 1.33× | 2.75×（17.6%） |
| Qwen3.8-27B（8×H200） | 29.3% | 1.19× | 1.39× | 1.38× | 1.55×（45.4%） |
| Qwen3.5-35B-A3B MoE（16×H100） | 8.7% | 1.17× | 1.17× | 1.17× | 1.51×（13.2%） |
| 几何平均 / 平均 MFU | 17.4% | 1.23× | 1.34× | 1.37× | 1.83×（30.0%） |

Gemma 那个 2.75 倍的来历很典型：删失内存模型认出「关掉 Liger fused cross-entropy」能省 14 GiB，于是把「关激活重算（缺 18 GiB）+ 关 Liger + 开 torch.compile」凑成可行的三元组，再合成一个缓存 25 个滑窗层 block-sparse mask 的 FlexAttention patch，外加给 5 个全局层的 chunked causal kernel。两机 MoE 则是靠反常识探测打开 32 通道 NCCL，再叠 fused SwiGLU、fast zero-grad、分桶梯度范数 all-reduce。

跨硬件迁移（Qwen3.5-9B，8×H100）：冷启动 1.70 倍、用全部可用经验包 1.70 倍、只用其他 GPU 型号的经验 1.82 倍，且只有后者在预算内达到 90% 峰值 log 加速（第 9 次试验，2.97 GPU·h）。

离线审计：40 条系统测试 100% 一致（28 条单点扰动全拒、12 条良性全收）；HMAC-SHA256 签名的 receipt 能拒掉未签名、签后改 step time、schema 不匹配的；1,212 次历史执行拒掉 400 次，其中 39 次（3.2%）**只有数值层 L4 能抓到**。

泼几盆冷水：

- **每个负载只有一条搜索轨迹**。主表没有多 seed 的置信区间，Gemma 上 2.75 倍和其他方法 1.3 倍左右的差距足够大，但 9B 上 1.73 对 1.62 这种差距，单次运行说明不了太多。
- **经验迁移只做了一个负载**，而且「全部可用经验包」和冷启动一样是 1.70，「只用跨型号经验」反而更好。作者的解释是排除了同任务同型号的自我回放，但只有一个点，很难区分是机制还是运气。
- **容差消融几乎不敏感**：loss 相对容差从 0.10% 放到 50%，最终加速在 1.70 到 1.75 之间，固定 2% 噪声门是 1.72。这说明在 9B 这个负载上数值层不是瓶颈，但也意味着「数值层到底拦下了多少真实损失」主要靠离线那 39 条来证明。
- **出主意的 LLM 是哪个、花了多少 token，正文没有交代清楚**，图里横轴是以美元计的 token 消耗，最多到 10 美元左右；对一个强调「失败试验成本全记账」的系统，这块写得偏少。
- 源码审计排除了两类作弊候选，但审计是谁做、自动化到什么程度，正文只说「source review excluded」，读起来像有人工参与。

## 🔬 最有意思的部分

**第一，LLM 先验是反的。** 零样本加速预测和实测的 Spearman 相关全在负区间（-0.49 到 -0.06）。InfraRSI 的回应不是换个更强的模型，而是做经验贝叶斯收缩：knob 的先验方差下限设成 \(\max(\sigma_{min}, 0.5|\mu_0|)\)，代码 patch 的增益预测乘一个保守系数 \(\kappa_0\)，并且只要某个大 knob 被先验打了低分、但两倍标准差的上行空间超过大 knob 门槛，就**主动安排一次反向探测**。torch.compile 的 +55% 和 NCCL 的 +10.2% 都是这样被捞回来的。这和我们之前看到的「LLM 当 judge 时数值打分不可信」是同一类问题，只是这里代价是 GPU 小时。

**第二，OOM 是信息，不是垃圾。** 大多数 agent 循环看到 OOM 就回滚、换个方向。Tobit 删失模型把「这个配置至少需要 X GiB」当成一个不等式观测，于是能算出每个设置的显存价格，再去找刚好能覆盖缺口的搭档。这是一个很小但很通用的想法：**失败的试验只要带着「差多少」的量化信息，就能变成搜索约束**。

**第三，最小冲突元组封禁。** 非显存类崩溃只封「在所有成功运行里都没一起出现过的最小那组设置」，单个设置在别的组合里仍然可用。这比「这次挂了就把刚改的全部拉黑」细得多，也避免了把一个好 knob 和一个坏 patch 绑在一起冤死。

**第四，小 patch 要成组验。** 每个 patch 单独只有零点几个百分点，低于噪声门，单独验永远过不了；InfraRSI 借群测思想，把验证过的小 patch 叠在一起，合计 log 增益过门了再一起验。这解释了为什么只调 knob 的 OptiCo 早早平台，也解释了为什么固定 2% 门会在安静集群上丢东西。

## 🤔 我的判断

**定位**：工程样本加验收规范。方法层面每一块（贝叶斯线性回归、Tobit、群测、信任域）都不新，新的是把它们装进一个以「固定任务契约」为中心的 harness，并且把 agent 优化基础设施时会出现的作弊方式系统地列出来、逐条变成可执行的检查。

**亮点三条**：

1. 五层 16 条不变量加 frozen_files 哈希加 HMAC 签名 receipt，是我目前见过最完整的「agent 改性能」验收清单，可以直接套到别的吞吐类优化任务上。
2. 失败全记账（GPU 小时和 API 成本都算进去，没过门的交付 1.00 倍），避免了只报成功的幸存者偏差。
3. 把 LLM 降级成「提方案的人」，测量、搜索、记经验全部由确定性组件负责，并且用实测反过来修 LLM 的先验。

**问题与局限**：单条轨迹没有方差；经验迁移证据只有一个点；出主意的模型和成本口径不够透明；源码审计的自动化程度不清楚；四个负载都是 Hopper 一代，跨代（比如到 Blackwell）时那些符号翻转会不会更多，论文没测。

**对工程的直接启发**：

- 任何让 agent 优化「会被计时或计分的东西」的任务，先写契约：哪些文件锁哈希、哪些量必须守恒（每次更新的 token 数、优化器步数）、计时由谁做，然后才放 agent 进去。
- 验收门别用固定百分比，先测基线配对噪声，用 \(2\sigma\) 级别的门；同时要求背靠背重跑。
- OOM、超时这类失败要记「差多少」，而不是只记「失败了」，这是后续搜索能用的约束。
- LLM 给的定量估计默认打折，对被它否掉的高方差选项定期做反向探测。
- 经验库写回只收过了全部验收的观测，并且读取时按环境兼容性分级，宁可少用也别负迁移。

一句话收束：**基础设施 RSI 的难点不在于让 agent 想出更快的配置，而在于让「更快」这个结论经得起审计；InfraRSI 把验收做成了主角，搜索反而是配角。**
