# 工具结果不必用文字喂给 agent：Coca-Cola 把每次观测压成 128 个潜在 token，只对齐「下一步动作分布」，总 token 省 70.01% 到 89.24%，EM/F1 还全面高过不压缩

你有没有过这种体验：搜索 agent 跑到第四步，上下文里九成以上是网页片段，真正决定下一步搜什么的可能只有一个人名。剪 token 怕剪掉关键证据，让另一个 LLM 写摘要又慢又贵，而且摘要本身还得是「通顺的文字」，压缩比天花板就在那里。问题变成：**工具结果非得用文本 token 喂给 agent 吗？如果压缩器只需要保住「agent 下一步会做什么」，能压到多狠？**

清华 AI Agent 组的 **Tools Need Not Speak in Text: Latent Context Compression for Agents** 给出的答案是 Coca-Cola（Context Compression via Continuous Latent tokens）：一个小模型把「任务指令 + 当前推理轨迹 + 工具观测」编码成固定数量的连续潜在 token，经适配器直接塞进冻结 agent 的输入嵌入空间；训练目标不是重建原文，而是让 agent 在「看全文」和「看潜在 token」两种条件下的下一步动作分布尽量一致。看完我的感受是：**这是把上下文压缩的验收标准从「信息有没有丢」改成「决策有没有变」，而这个改动本身比潜在 token 更值得抄。**

## 核心摘要

ReAct 式 agent 每调一次工具就把原始观测追加进上下文，论文统计的搜索轨迹里第 4 步时工具返回已占上下文 96.7%。Coca-Cola 的做法分三块：**上下文感知编码器**（小 LM，加 LoRA）同时读任务、当前推理前缀和观测；**潜在适配器**把隐状态变成 k 个落在目标 agent 输入嵌入空间的向量，用特殊边界标记包起来；**Action-Preserving Training** 把同一个冻结 agent 分别喂全量观测和潜在 token，最小化两者下一步动作分布的 KL，再加一项对轨迹里记录动作的交叉熵。梯度穿过冻结 agent 回到压缩器，agent 本身一个参数不动。在四个搜索 QA（NQ、TriviaQA、2Wiki、HotpotQA）和两组模型对上，总 token 消耗降 70.01% 到 89.24%，端到端时延降 24.45% 到 55.97%，EM 和 F1 在所有设置都高于不压缩的 Vanilla，16 个数据集与指标组合里 13 个第一。同架构但用重建目标训练的 ICAE 在 8 个设置里压缩率全部输给它。代码在 https://github.com/THU-Agent/Coca-cola 。

## 🎯 为什么这件事值得写

工具观测压缩这条线过去两年基本在两个方向打转：

1. **token 剪枝**（LLMLingua、LongLLMLingua）：按信息量删词，保留下来的还是离散 token。
2. **文本摘要**（RECOMP、Search-o1 的 Reason-in-Documents、ACON）：用辅助 LLM 写摘要，结果仍然要是一段通顺的自然语言。

两条路共享一个隐含前提：压缩结果必须能被人读懂。论文的论点很直接，工具结果的唯一消费者是 agent 的下一步决策，那它就没必要说人话。作者还给了一个容量层面的论证：长度为 m 的文本 token 序列，码本容量上限是 m·log|V|；同样 m 个位置的连续向量，每个向量有多个有效坐标、每个坐标在有限精度下有多个可区分取值，容量可以更大。论文自己也承认这只是动机，实际能用多少取决于编码器和 agent 会不会用。

对做 harness 的人来说，这篇真正有用的是第二个前提的替换：**压缩器的好坏不看重建，看它让 agent 的下一步变了多少**。这和我们最近反复看到的「验收看行为不看文本」是一个思路。

## 🏗️ 机制：编码器 + 适配器 + 动作保持训练

### 上下文感知编码器

作者分析工具轨迹时发现，一段观测里哪些信息重要，取决于任务目标和 agent 此刻推理到哪。所以编码器输入是三件套：任务指令 I、当前步推理轨迹前缀、工具观测 o_t，输出带上下文条件的隐状态。

### 潜在适配器

编码器和目标 agent 不在同一个表示空间。适配器把隐状态变成固定 k 个、维度等于 agent 输入嵌入维度的向量，前后插入特殊边界标记，直接拼进 agent 的输入嵌入序列。默认 k=128。

### Action-Preserving Training

同一个冻结 agent 跑两遍：一遍看全量观测，一遍看潜在 token，得到两个下一步动作分布。损失 = λ1·KL(全量 ∥ 压缩) + λ2·CE(压缩条件下预测轨迹中记录的动作)。附录给的权重是 0.3 和 1.0，KL 权重在前 20% 训练步 warmup。只更新编码器的 LoRA（rank 16、α 32、dropout 0.05）和适配器参数。

训练数据：4,188 个任务里抽出 4,363 个「工具观测与动作」对，3,927 条训练、436 条验证。训练时冻结 agent 分布在 3 张 A100 上，压缩器单独一张；推理时 agent 只占一张卡，压缩器另占一张。

### 推理

每次工具调用后，原始观测被替换为 k 个潜在 token，agent 在更短的上下文上继续推理。搜索设置是每次最多返回 5 条结果、每题最多 5 次工具调用。作者强调压缩器没有任何搜索专用设计，理论上可以换到别的工具。

## 🧪 关键证据

### 效率（RQ1）

| 设置 | Vanilla 输入 token | Coca-Cola 输入 token | 总 token 压缩率 | 时延 |
| --- | --- | --- | --- | --- |
| Qwen 对，NQ | 14,362.12 | 1,766.53 | 85.78% | 96.19 s → 64.64 s |
| Qwen 对，2Wiki | 37,427.21 | 10,744.51 | 70.01% | 164.99 s → 119.91 s |
| GLM 对，2Wiki | 31,693.47 | 3,003.38 | 89.24% | 106.37 s → 46.83 s |
| GLM 对，HotpotQA | 28,781.88 | 4,041.03 | 84.30% | 84.55 s → 49.37 s |

Qwen 对时延降 24.45% 到 32.80%，GLM 对降 41.61% 到 55.97%，所有设置都是最低时延。压缩率在 8 个设置里 5 个第一，剩下 3 个输给 LLMSummary，但这 3 个里 LLMSummary 的 EM/F1 都更低，比如 GLM 对 NQ 上 LLMSummary 的 EM 只有 16.00，Coca-Cola 是 23.50。

### 效果（RQ2）

| 设置 | Vanilla EM / F1 | Coca-Cola EM / F1 |
| --- | --- | --- |
| Qwen 对，TriviaQA | 56.10 / 62.87 | 59.20 / 67.07 |
| Qwen 对，HotpotQA | 11.00 / 16.41 | 25.70 / 33.75 |
| GLM 对，TriviaQA | 41.50 / 44.57 | 51.50 / 59.41 |
| GLM 对，2Wiki | 26.50 / 31.29 | 28.00 / 36.20 |

16 个数据集与指标组合里 13 个第一，8 个模型与数据集组合里 6 个 EM 和 F1 同时第一（GLM 对四个全中）。例外都在 Qwen 对：TriviaQA 上 ICAE 更高（61.80 / 69.27），2Wiki 上 LongLLMLingua 的 F1 更高（34.25），但它们的压缩率分别只有 66.92% 和 41.96%，对应 Coca-Cola 的 83.68% 和 70.01%。

### 消融（RQ3，GLM 对，NQ）

| 变体 | EM | 压缩率 |
| --- | --- | --- |
| Full | 23.50 | 73.73% |
| 去掉推理状态 | 21.45 | 80.43% |
| 去掉任务目标 | 20.02 | 78.38% |
| 只看观测 | 18.34 | 79.94% |

潜在 token 数从小到大，F1 从 26.34 稳步升到 31.45；压缩率在较小 k 下维持在 78.83% 到 82.56%，到 k=128 时降到 73.73%。

## 🔬 最有意思的部分

**ICAE 对照是这篇最干净的证据。** 作者把 ICAE 改造成同一套编码器与适配器架构，只把训练目标换成「从潜在 token 重建原始观测」。结果 8 个设置里 Coca-Cola 压缩率全赢，GLM 对 2Wiki 上是 89.24% 对 74.12%；效果上 GLM 对四个数据集 ICAE 甚至全部低于不压缩的 Vanilla。换句话说，**同样的容量，拿去记原文和拿去记「下一步该干什么」，结果天差地别**。

第二个有意思的点：「只看观测」的变体不给任务也不给推理状态，EM 18.34、压缩率 79.94%，仍然在 GLM 对 NQ 上压过所有压缩基线（EM 最多 17.00，压缩率最多 74.62%）。说明收益主要来自训练目标，而不是条件输入。

第三，压缩之后反而更准。作者给的解释是冗余观测会稀释注意力，HotpotQA 案例里 Vanilla 被「Jens Risom 与 Mid-Century Modern」的信息带偏，多搜一次还答错；Coca-Cola 抓住了「把斯堪的纳维亚设计带到美国」那条证据，搜得更少还答对了。

## 🤔 我的判断

定位：**一份把上下文压缩的训练目标从「重建」换成「动作保持」的白盒方案**，用在搜索 QA 上效果和效率都站得住。

亮点三条：

1. 动作分布 KL 作为压缩验收，概念上和「验收看行为」一脉相承，ICAE 对照把这个选择的价值单独剥出来了。
2. agent 全程冻结，只训 LoRA 和适配器，4 千来条数据、4 张 A100 就能复现。
3. token 和时延的收益同时成立，不只是纸面上的 token 数。

问题与局限：

- **只在短程搜索 QA 上验证**：每题最多 5 次调用、每次最多 5 条结果，离长程编码 agent 或多工具工作流差得远；「对其他工具无需改架构」目前只是声明。
- **必须是白盒 agent**：潜在 token 要注入输入嵌入层，梯度要穿过 agent，闭源 API 模型用不了；换一个 agent 就得重训一个压缩器。
- **Vanilla 基线偏弱**：Qwen 对 HotpotQA 上 Vanilla EM 只有 11.00，相对提升 133.64% 的数字看着吓人，绝对值是 25.70；论文没有报告多次运行方差或显著性检验。
- **不可审计**：观测变成向量之后，人看不到 agent 依据什么做了决定，注入攻击能不能藏进潜在 token 里、压缩器会不会被恶意网页诱导，论文完全没碰。对关心护栏和审计的 harness 来说这是最大的缺口。

对工程的直接启发：即便不上潜在 token，**「全量观测与压缩观测下 agent 下一步动作是否一致」本身就是一个可以挂在任何文本压缩器（包括 protocol 化的状态块压缩）后面的验收门**。先用它来评估现有摘要器，再决定要不要换成向量。

一句话：Coca-Cola 证明了工具结果不必说人话，只要压缩器对 agent 的下一步负责，压掉八成多的 token 还能更准；代价是白盒、短程、不可读。
