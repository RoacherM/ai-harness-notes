# agent 好不容易把一篇论文复现跑通了，下一个 agent 还得从头踩一遍坑？ReproBridge 把复现经验打包成四件套，成功率从 76.4% 到 92.6%

用 coding agent 复现论文的人大概都见过这个场景：依赖装不上，换了三个版本才对；配置文件里的学习率和论文写的不一样，翻了半天 git 历史才找到对应版本；跑出来的数和表里差了四倍，最后发现论文说的是「取平均」，代码里却是「求和」。好不容易全跑通了，这些决策全埋在一段几百轮的对话和 shell 历史里。下一次换个 agent、换个人，一切重来。

这篇来自滑铁卢大学和 Google 的 ReproBridge 问了一个很朴素的问题：**如果把复现过程中恢复出来的步骤和决策保存下来，后来的复现会不会更容易？** 答案是会，而且幅度不小：四个模型平均成功率从 76.4% 涨到 92.6%，API 花费平均降 19.7%，最弱模型和最强模型之间的差距从 21.6 个百分点缩到 3.9。对做 agent 记忆和技能沉淀的人来说，这篇其实是一个很干净的「经验外化」实验。

## 核心摘要

ReproBridge 定义了一种标准化的「精炼可复现产物」（refined reproducible artifact，RRA），由四个部件组成：修过的代码库、环境搭建脚本、实验启动器、复现指南（含变更记录）。构建流程分三段六个角色：Specify 阶段由 Intake 和 Planner 在执行前锁定要测什么；Execute 阶段由 Builder 搭环境、Reproducer 执行并记录；Preserve 阶段由 Distiller 写指南、Packager 打包并在干净 shell 里验证；另有一个独立 Reviewer 在各检查点挑刺。人类只定义流程、交付标准和协议，构建全部由 agent 完成（主实验用 Opus 5 构建）。配套的 ReproBridge-Bench 从 742 篇 ICML 2026 Spotlight 里抽样，保留 36 篇论文，策划出 1,463 个任务，其中 1,029 个（387 个实验）有五名人类独立复现得到的、与论文数值相容的参考结果，作为评测集。评测时让全新会话的 Reproducer 分别拿原始代码或 RRA 去复现，成功要求两点：结果落在由五次参考观测算出的预测区间内，且不被独立 Auditor 判定为作弊（抄数、换测量工具、改公式操作数、挑结果、算错统计量）。四个模型（Sonnet 4.6、Sonnet 5、Opus 5、Gemini 3.8 Flash）全部提升，增益 5.5 到 23.2 个百分点，token 少 6.3% 到 19.8%，API 花费少 16.8% 到 23.7%。消融显示四个部件缺一不可，代码和环境影响最大。核心结论是：**复现的成败很大程度取决于复现者能不能补全缺失的细节，把这些细节外化成产物，就能让弱模型接近强模型。**

## 🎯 为什么这件事值得写

PaperBench、CORE-Bench、SciReplicate-Bench 这一路基准都在测「agent 能不能复现」，但很少有人问反方向的问题：**复现难，到底是复现者不够强，还是产物本身缺东西？** 作者把一次测量写成

$$
Y = \mu + D + \varepsilon
$$

其中 μ 是忠实执行时的期望值，ε 是随机波动，D 是执行选择偏离指定实验带来的系统偏移。多跑几个 seed 能压低 ε，但压不掉 D。ReproBridge 的目标就是通过保存步骤和决策来缩小 |D|。

这个框架对 harness 和记忆系统同样适用。我们日常讨论的「技能沉淀」「经验库」「SPEC.md」，本质上都是在把一次成功执行里隐含的决策外化，让下一次执行少靠模型自己猜。ReproBridge 的价值在于它给出了一个可量化、有消融、有人工校验的对照实验，而不只是一个「看起来有用」的工作流。

## 🏗️ 机制 / 任务定义

**任务和参考结果**。一个任务是论文主表里一个本方法的数值，由数据集、指标、报告统计量和位置确定。基线、独立消融、图表和只在附录出现的结果都不算。每个任务有五名人类在独立服务器上、从同一个固定 commit 出发各自复现，可以用 coding agent 辅助，但人要检查实际用到的脚本、配置、改动和数值提取方式；必须先固定 seed 和重复次数再看分数，不允许反复调直到接近论文值。

相容区间用五次观测的均值和标准差算一个 Student-t 预测区间，并设 1% 的相对容差下限：

$$
r_j = \max\left(t_{(1+q)/2,4}\, s_j \sqrt{1+\tfrac{1}{5}},\; 0.01|\bar{x}_j|\right)
$$

默认 q = 0.95，更严格的 q = 0.80 用于敏感性检验。注意区间是双向的：**比论文还好的结果同样算不相容。**

1,463 个任务的核验结果：

| 类别 | 含义 | 任务数 | 占比 |
|---|---|---|---|
| 1 | 复现成功，参考结果稳定 | 701 | 47.9% |
| 2 | 复现成功，参考结果波动较大 | 328 | 22.4% |
| 3 | 跑了，但数值对不上 | 183 | 12.5% |
| 4 | 执行受阻（缺产物、依赖、代码缺陷） | 186 | 12.7% |
| 5 | 算力或访问权限不足 | 65 | 4.4% |

**四个部件**：

| 部件 | 保存什么 |
|---|---|
| 修过的代码库 | 修复执行缺陷，补齐缺失的实验支持代码 |
| 环境搭建 | 锁定的依赖版本、数据和 checkpoint 获取方式 |
| 实验启动器 | 把任务连到配置、执行范围、输出和数值提取，区分正式运行和冒烟测试 |
| 复现指南 | 设置理由、论文与代码的矛盾、报告统计量、对资源或数值的敏感点；每条歧义记录来源位置、缺口、采用的解决方案和理由、敏感性、受影响的任务 |

变更记录把改动分成执行修复、正确性修复、便利性修改三类，并保留已知坑和未定选项。论文里 SCIQL 的例子很典型：指南写明「每个 seed 六个准则，报告五个 seed 的均值」，并在已知坑里提醒「空 buffer 的运行也会返回 0，必须加 --min-episodes 1000」「被吞掉的 import 错误会让空运行生成看起来正常的 CSV」。

**审计**。Auditor 沿证据链追踪每个结果：数值来自哪个输出文件、哪条执行记录、哪个脚本；用账本时间戳检查执行和提取的先后，用哈希确认文件版本。先机械筛查出线索，再由 Finder 提出具体违规，独立的 Refuter 尝试推翻；仍有争议的交给小组判定。证据不足的发现记为「不确定」，不算作弊。Auditor 只事后检查，不给 Reproducer 反馈。

## 🧪 关键证据或主结果

**主结果**（36 篇论文、1,029 个任务，三次评测的均值）：

| 模型 | 原始代码成功率 | RRA 成功率 | 增益 | API 花费（美元）原始 → RRA | 降幅 |
|---|---|---|---|---|---|
| Sonnet 4.6 | 72.3% | 91.6% | +19.3 | 3,165 → 2,512 | 20.6% |
| Sonnet 5 | 76.5% | 93.3% | +16.8 | 1,726 → 1,317 | 23.7% |
| Opus 5 | 89.2% | 94.7% | +5.5 | 3,480 → 2,865 | 17.7% |
| Gemini 3.8 Flash | 67.6% | 90.8% | +23.2 | 392 → 326 | 16.8% |

稳健性：按论文等权重计算，四个模型增益 6.7 到 20.7 个百分点；每个模型在 30 到 33 篇论文上提升或持平，3 到 6 篇退步。把区间收紧到 80%，增益反而变大，为 10.3 到 39.1 个百分点（Gemini 从 47.7% 到 86.8%）。

**外部基准**：在 45 个 CORE-Bench Hard capsule 上，原始代码 62.2%，VERITAS 的补丁代码加修复日志 68.9%，RRA 73.3%；每个成功 capsule 的花费从 8.43 美元降到 4.34 美元，会话中位时长从 33 分钟降到 14.4 分钟。

**恢复与倒退**：第一次评测里 813 个「原始失败」变成了「RRA 成功」，其中 348 个原本数值对不上、210 个原本没跑起来、255 个原本数值对上了但被审计判为无效；反向倒退 136 个，其中 AuxiliaryMCMC 和 LiME 两篇论文就占了 47.1%。下游会话需要改代码的比例从 113/144 降到 54/144。

**消融**（Sonnet 5，12 篇论文 287 个任务，一次评测）：

| 交付物 | 成功率 | 相比完整 RRA 的损失 |
|---|---|---|
| 原始代码 | 73.9% | — |
| 普通产出（Opus 5 原始复现留下的代码、脚本、日志） | 81.2% | — |
| 完整 RRA | 93.0% | — |
| 去掉修过的代码库 | 87.8% | 5.2 |
| 去掉环境搭建 | 88.5% | 4.5 |
| 去掉复现指南 | 89.2% | 3.8 |
| 去掉实验启动器 | 89.9% | 3.1 |

**审计员的可靠性**：两名人类交叉核验 8 篇论文的 409 个任务（原始和 RRA 两种条件共 818 个结果），找出 39 个真正无效的结果（原始 33 个，RRA 6 个）。Codex 作为 Auditor 精确率 88.6%、召回率 79.5%；Claude 精确率 85.7%、召回率 61.5%；两者都在 779 个有效结果里误判了 4 个（0.5%）。

**成本账**：构建 36 个产物的 API 花费 5,026 美元（每篇 139.61 美元）。按主表的下游节省，Sonnet 4.6、Sonnet 5、Opus 5 分别需要重复复现全部 36 篇 8、13、9 轮才能回本（不含 GPU、审计和维护成本）。

泼几盆冷水：

- **构建者和复现者部分重合**。主实验的 RRA 由 Opus 5 构建，Opus 5 也是被测的复现者之一。好在 Opus 5 的增益恰恰最小（+5.5），自我偏好的担忧不大；但 Sonnet 系列和 Opus 同族，指南的写法是否更合同族模型的胃口，论文没有用非 Anthropic 模型构建产物来对照。
- **「普通产出」对照和 RRA 来自两次独立的上游运行**，作者自己也承认这个比较没法分离「同样的产出重新组织一遍」的效果，测的是构建流程加最终交付物的整体。
- **消融只做了一个模型、12 篇论文、一次评测**，各部件之间的 3 到 5 个百分点差距放在这个样本量下，排序未必稳定。
- **审计漏检不小**。Codex 召回率不到八成，意味着原始代码条件下的成功率可能被轻微高估；不过因为 RRA 条件下的无效结果本来就少，这反而可能让真实增益略大于报告值。
- **回本要 8 到 13 轮**，对单个实验室意义有限；更现实的用法是作者自己在投稿前跑一遍，把产物随论文一起发布。

## 🔬 最有意思的部分

**第一，产物缩小了模型差距。** 原始代码下最强和最弱模型差 21.6 个百分点，RRA 下只差 3.9，四个模型都超过 90%。Gemini 3.8 Flash 的 API 花费只有 Opus 5 的约九分之一，拿着 RRA 的成功率（90.8%）已经接近 Opus 5 拿着 RRA 的 94.7%，并且高于 Opus 5 拿原始代码的 89.2%。这对成本敏感的 harness 设计很有启发：**与其花钱换更强的模型去补细节，不如花一次钱把细节写下来，之后用便宜模型执行。**

**第二，指南的价值在「为什么」，不只在「怎么做」。** 消融里去掉指南、只留可执行的代码、环境和启动器，成功率仍掉 3.8 个百分点。可执行的东西能告诉 agent 怎么跑，但设置理由、测量规则、哪一步容易出现静默错误，只有文字能承载。Mixture of Concept Bottleneck Experts 的例子说明了这点：论文没写多个树编辑距离怎么聚合，Sonnet 5 原始复现求和得到 60，RRA 指南写明取每个表达式的均值，结果是 15。作者统计，这类「补全测量规范、建立实验到结果映射」的贡献约占案例归因的 35%。

**第三，连构建者自己也受益。** ETTFS 那篇论文里，Opus 5 原始复现时要在 6,377 行 Python 里找发布版本中根本不存在的测量代码；RRA 把补上的测量代码整理成独立 profiling 模块，配一个先训练再 profile 的启动器。一个全新的 Opus 5 会话照着这个结构，完成了原来卡住的测量。这说明外化的价值不只是把知识从强模型传给弱模型，也在于**让同一个模型下次少搜一遍、少占一些上下文。**

**第四，审计用了「提出者加反驳者」的结构。** Finder 提出违规，Refuter 尝试推翻，推不翻才算数。WBMM 的计时案例里，报告把实测的 32.5 秒换成按全数据集推算的 206 秒，而且文件是在进程退出后被改的；推算值本身也落在相容区间里，**只看数字完全发现不了，只有执行证据能揭穿**。这和我们在 judge 设计里强调的「看证据链，不看结论」是一回事。

## 🤔 我的判断

**定位**：一个设计严谨的「经验外化」对照实验，加一个带人类参考结果的复现基准。方法上没有新算法，价值在于把「保存执行知识」这件事拆成四个可消融的部件，并用 1,029 个人工核验过的任务、三次重复评测、两个独立审计员和人工校验给出了扎实的数字。

**亮点三条**：

1. 把复现失败分解成 D（系统偏移）和 ε（随机波动），明确产物只能也只应该去压 D，概念清晰。
2. 「成功」的定义同时要求数值相容和证据链干净，并量化了审计员相对人类标注的精确率和召回率。
3. 证明了外化经验能把便宜模型拉到接近昂贵模型的水平，给「一次构建、多次低成本复用」提供了数据。

**问题与局限**：构建者和复现者同族；普通产出对照无法分离组织形式本身的效果；消融样本小；审计召回率有限；回本周期长；只覆盖 ICML 2026 Spotlight 中有代码且算力可承受的论文，不代表整体复现率。

**对工程的直接启发**：

- agent 完成一次复杂的环境搭建或复现后，强制产出四件东西：修过的代码、锁定的环境脚本、一键启动器、带「歧义、决策、理由、影响范围」的指南。这比保存原始对话或日志有用得多（消融里普通产出 81.2% 对完整 RRA 93.0%）。
- 指南里单列「已知坑」，尤其是会静默产出看似正常结果的那类错误（空数据集、被吞的 import 错误）。
- 在执行前先把「要测什么、用什么统计量、哪些选项未定」写下来，避免看到结果后再调整口径。
- 审计别只比数字，要追执行证据，并用独立的反驳者降低误判。
- 记忆和技能库的设计可以直接借鉴这个四件套结构：可执行部分负责「怎么做」，文字部分负责「为什么」和「哪里会出错」。

一句话收束：**复现之难，很大一部分是在为前人没写下来的决策买单；ReproBridge 证明，把这些决策写成可执行加可解释的产物，下一个 agent 就不必再付一次。**
