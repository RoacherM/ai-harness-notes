# agent 读一份 300 页的 PDF，真正用上的可能只有 3%，剩下 97% 却要在后面每一轮里被重新喂一遍？SparseRead：先说清要什么证据，再按预算给片段

你一定见过这种 agent 轨迹：它要回答一个关于某份报告的小问题，于是调用 `read_file`，整份文件进了上下文；接着又去翻另一个仓库文件，又是整份；最后答案只引用了其中两段话。更糟的是，这些整页整文件的内容并不会读完就走，它们会留在历史里，在之后每一次模型调用里被重新带上。上下文越来越长，token 越来越贵，模型还时不时被无关内容带偏，调错工具、混淆来源、该停的时候不停。

作者把这件事叫**过度阅读**（over-reading）：外部资源是按「对象」粒度交给 agent 的，可每个决策往往只需要一小片证据。这篇论文的问题很朴素：**在 agent 做下一步决策之前，它应该从一个外部资源里读到什么？** 看完我的感受是：SparseRead 不是又一个检索或压缩算法，而是一层夹在 agent 和文件之间的「阅读控制层」，它最有价值的部分是那份契约和那个带上限的回退规则，而不是哪个检索后端更强。

## 核心摘要

SparseRead 在不改模型参数、不引入额外生成式压缩模型的前提下，接管 agent 对外部资源的读取。它由三部分组成：**Read Intent Protocol** 让 agent 每次读取时说明自己这一步要什么证据，协议记录哪些证据槽已经有支撑、哪些还没覆盖，但从不替 agent 判断「够不够」；**Adaptive Reader Backends** 按资源类型选定位方法和暴露形式，文本和 PDF 用词法、BM25 或混合检索找段落，表格可以扫全表算出结果只返回数字和出处，JSON 和日志走键路径；**Budgeted Read Gate** 给每个阅读回合设一个原文暴露预算，下一批证据如果塞不进剩余预算就整批扣下，改给一份忠实的全文视图，从而保证一个回合的总暴露不超过全文的两倍。在 NanoBot 上跨 6 个模型（含 Claude Opus 5）和 5 类场景的 30 个设置里，token 降低 15.7% 到 92.9%（中位 61.4%），耗时降低 23.0% 到 89.0%（中位 53.7%），29 个设置分数持平或提升；Web 深度搜索上 6 个模型都涨了 5 到 14 个百分点，同时省 31.0% 到 43.0% 的 token。接入 OpenCode 和 OpenClaw 后 18 个设置全部更省，15 个分数不降。这篇真正的价值在于：**把「读多少」从模型的自觉，变成一份由运行时强制执行的契约。**

## 🎯 为什么这件事值得写

先看作者给的几组诊断数字。长文档问答里，人工标注的支撑证据中位数只占原文 token 的 3.17%；Qasper 中可回答且有证据标注的问题，比例大约 5.8%。已有工作报告外部观察占了 agent 轨迹里 60% 到 80% 的 token。配对运行中，不加控制的 agent 最多会多花 17.3 倍 token，任务分数却没有更高。

现有手段各管一段。长上下文架构和 KV 压缩降低的是上下文的计算和显存开销，并不决定模型该看哪些内容。ACON、观察遮蔽这类方法在观察进入轨迹之后再压缩或丢弃。检索，包括迭代式和 agentic 检索，可以按需取段落，但没有一份跨资源类型的统一契约来记录「当前在找什么、已经看过哪里、还缺什么、什么时候该放弃精读直接看全文」。

作者还指出了一个容易忽视的边界：**稀疏阅读并不总是划算**。在高稀疏度的问答和审计任务上它能省 80% 到 88% 的 token，可如果强行用在全局统计和一个规则编码任务上，token 反而分别增加了 309% 和 210%，因为反复的局部访问比一次读全还贵。而这个边界在读之前往往无法判断，对象大小和类型都不够用。

这对写 harness 的人很直接：**「读文件」这个工具本身就是上下文成本最大的单一来源之一，它值得一份比 `cat` 更讲究的接口。**

## 🏗️ 机制 / 任务定义

SparseRead 把系统分成两层：控制层负责理解意图、选配置、维护证据记录、决定什么进上下文；证据层是一组可替换的 Reader，只负责取证据，不决定自己何时被调用。两层之间只有一份契约：

| 输入 | 输出 |
|---|---|
| Read Intent（这一步要什么证据） | EvidencePack（带出处锚点的证据、处理过的范围、暴露了多少、每个证据槽的覆盖状态和未解决项） |

**三个量要分开看**。作者特别区分了处理范围（Reader 实际扫了多少原文）、暴露量（进入模型上下文的内容）和覆盖度（当前意图里哪些槽有证据）。三者不必同步：表格 Reader 可以扫完每一行算出总和，却只暴露结果、行数和出处。

**Read Intent Protocol**。每次访问的意图优先于从用户首条请求推出的会话意图，会话意图只用来填补未说明的细节。意图太模糊时先返回一个有界的对象预览（`scout`）。证据记录用 SHA-256 指纹绑定资源版本，文件一改，之前的证据和覆盖全部作废。agent 只有五个固定动作，新增 Reader 不会扩大动作集。

**Budgeted Read Gate**。设 $L$ 为当前请求可用的最便宜的忠实全文视图长度（可以是原生读取，也可以是无损紧凑视图），$B$ 为本回合的稀疏暴露预算。Gate 的规则是：必须看全文或没有合适 Reader 时直接给全文；小对象直接跳过稀疏路径；否则先给稀疏证据，并在交付每批之前检查剩余预算，塞不下就扣下这批，改给全文。由此得到命题 4.1：

$$\text{单回合原文暴露} \le B + L \le 2L$$

作者很克制地说明了这个界的范围：它只限制下行风险，不是对重放加权上下文、计费 token、延迟的界，也只对单个阅读回合成立，不覆盖整个会话。回退时会把之前的稀疏观察从后续提示里撤掉，避免继续被重放，但已经花掉的成本收不回来，而且编辑点之后的前缀缓存可能失效。

**接入方式**。NanoBot 直接注册 SparseRead 工具；OpenCode 和 OpenClaw 用很薄的插件或桥接适配器暴露 `sro_preview` 和 `sro_read`，把本地的读和打开事件转成同一套核心调用。模型侧有一份 SKILL.md 告诉 agent 何时先预览、何时定向读、何时回到原生访问，但这份指引只是建议，意图校验和暴露预算是在核心里强制执行的，**任何一个 harness 的保证都不依赖模型是否听话**。

## 🧪 关键证据或主结果

**跨模型跨场景**。六个模型分三档：Qwen3.6-Plus、DeepSeek-V4-Flash 为中等模型，DeepSeek-V4-Pro、GLM-5.1、Kimi-K2.5 为大型开源模型，Claude Opus 5 为闭源旗舰。五类场景是长上下文阅读、多文件审计与诊断、结构化分析、Web 深度搜索、AI for Science（LAMMPS 脚本生成）。

| 场景 | token 降幅 | 耗时降幅 | 分数 |
|---|---|---|---|
| 长上下文阅读 | 76.5% 到 92.9% | 67.1% 到 89.0% | 持平或提升 |
| 多文件诊断 | 26.8% 到 74.5% | 原文未单列 | 每个模型都持平或提升 |
| 结构化分析 | 15.7% 到 64.1% | 原文未单列 | 每个模型都持平或提升 |
| Web 深度搜索 | 31.0% 到 43.0% | 23.0% 到 37.0% | 六个模型都涨 5 到 14 个百分点 |
| AI for Science | 82.7% 到 89.1% | 28.3% 到 63.0% | 五个模型持平或提升，GLM-5.1 下降 |

Opus 5 在五类场景里省 41.0% 到 89.0% 的 token，作者的结论是**强模型也照样受益于少读**。

**对比检索和上下文压缩**。在 3 个场景、5 个模型共 15 个设置里，SparseRead 每个设置分数都不降，省 27.0% 到 92.9% 的 token。RAG Static 在 Web 设置里更快，但 15 个里有 9 个分数低于原生；同样迭代和超时限制下的 RAG Agent 有 8 个掉分、8 个比原生还慢；ACON 有 5 个掉分、6 个两项成本都上升；观察遮蔽有 5 个掉分。多文件诊断上，SparseRead 在全部 5 个模型上同时拿到最少 token 和最短耗时，分数还涨了 17.8 到 34.5 个百分点。

**跨框架**。NanoBot、OpenCode、OpenClaw 的 token 中位降幅分别为 65.0%、65.2%、30.6%。OpenClaw 上的收益明显小一截，原文没有展开原因，我猜和它原生工具本身已经有部分读取，或者桥接方式只覆盖了一部分访问路径有关，这只是推测。

**泼点冷水**。第一，原始的六场景矩阵里其实还包括一组「原生更合适」的对照任务（找目录里最大的文件、写折扣计算器、写 SPARQL 查询），作者把它们移到了附录 C，主文的 30 格是去掉这组之后的结果；附录里纳入它们时，分数持平或提升的是 30 格中的 26 格。第二，Reader 的可靠性是在带标注的开发请求上校准的，换到没有标注的新资源类型，这个阈值怎么来没有说清。第三，消融里 Reader 定位方法那组只比较了四种文本定位方法的命中率（混合检索 65.3%，BM25 60.1%，词法 39.5%），作者自己也承认它**没有单独测出配置选择器相对固定配置的增益**。

## 🔬 最有意思的部分

**覆盖度不等于充分性**。协议只告诉 agent「这些槽有证据、那些槽还空着」，从来不说「可以停了」。完成与否由 agent 决定，协议和 Reader 都不宣布完成。这个设计和我们在 harness 里做 stop-hook 守卫的思路正好互补：一个外部记录告诉你还缺什么，但判断权留在 agent 手里，避免控制层越权。

**意图消融的诊断指标很实用**。同时用会话意图和访问意图时，每个任务的重复读取从 4.8 次降到 1.5 次，无法追溯来源的证据从 28% 降到 8%，能解决证据缺口的验证检查从 37% 升到 89%，因缺证据而答错的比例从 25% 降到 5%。这四个指标本身就可以拿来当 harness 的阅读健康度监控。

**检查要放在交付之前**。Gate 的消融对比了交付后检查和交付前检查：交付后检查会越界，三次升级达到全文的 2.10 到 2.33 倍；交付前检查把六个暴露比都压在 1.62 到 1.93 之间。这是一个很小但很硬的工程细节：**预算检查放在副作用之后，就不是预算，只是记账。**

**加宽窗口反而更差**。把 BM25 的窗口放宽，暴露从 1,497 字符涨到 2,106，命中率却从 60.1% 降到 56.7%。多给不一定多中。

## 🤔 我的判断

**定位**：工程框架加一个可证明的下行界，属于 harness 基础设施，而不是检索方法突破。

**亮点三条**：

1. 一份跨资源类型的统一读取契约（Read Intent 进，EvidencePack 出），新 Reader 注册即对所有 harness 可用，不改适配器。
2. 预算由核心强制执行，SKILL.md 只是建议，保证不依赖模型合规。这是我最认同的一点。
3. 明确承认稀疏阅读有失效区间，并用「最多两倍全文」把最坏情况兜住，而不是假装它永远划算。

**问题与局限**：没有看到代码仓库；主表剔除了原生更优的对照任务；可靠性校准依赖标注数据；两倍界只管单个回合，不管整段会话里重放带来的累计成本；回退时撤掉旧观察会破坏编辑点之后的前缀缓存，在按缓存计费的场景里实际省多少还要自己测。

**对工程的直接启发**：如果你在维护一个 Pi 或 OpenCode 之类的 harness，最便宜的第一步不是换检索后端，而是给 `read` 工具加两样东西：一个「这次要找什么」的必填意图字段，和一个交付前检查的单回合暴露预算，超了就直接给全文并把之前的片段从上下文里撤掉。再把重复读取次数和无出处证据比例做成指标。

一句话收束：**SparseRead 的野心是让 agent 像人一样先想清楚要什么再翻书，它的取舍是承认有些书就该整本读，并且提前算好最多会多读多少。**
