# 世界不等模型想完：一次调用写出控制器接着打，实时成功率 68.6% 对上 VISTA 的 38.3%，同样分数只需五分之一费用

你有没有过这种体验：同一个视觉模型，游戏暂停时打得还行，时间一开始跑就立刻崩。子弹还在屏幕左边，模型想了几秒，动作落地时船已经没了。团队的第一反应往往是换更快的模型、缩短思维链，或者给它加更好的视觉记忆，让它把上一帧看得更清楚。

这篇把问题从「模型够不够快」挪到了 harness 上：**模型的输出，在时间里是怎么变成动作的？** 现有视觉 harness 多半每调用只出一步，所以 agent 的出手频率被模型思考速度卡住。AutoPILOT 让一次调用可以出一步、发一段开环宏，或者写一个闭环控制器，在不再调用模型的情况下对着画面继续打，直到它把控制权交回来。看完我的感受是：这是少数把「时间」当成一等设计变量的 harness 论文，而且对照组和预算账都算得很清楚。

## 核心摘要

AutoPILOT 是一个面向实时游戏的视觉 agent harness，在 VISTA / Codex harness 上加了宏、控制器和唤醒事件。模型看到的仍是渲染画面、游戏时钟和剩余预算，看不到游戏状态或 DOM。每次模型调用可以选择三种执行方式：发一个原始动作；启动一段不看屏幕的开环宏；或者写一个短 Python 函数 `run(api)`，在沙箱里大约每 0.4 秒读一帧并行动，最长 120 秒，直到自己交接或被 harness 唤醒。为了量「实时到底让 agent 付出多少代价」，作者做了 AFK-Bench：120 个浏览器游戏，按「什么都不做会发生什么」分成敌对实时、良性实时和回合制各 40 个，并且同一批游戏都能在实时和暂停时钟下玩。相同预算下，GPT-6.1 Sol 的实时成功率是 68.6%，VISTA 是 38.3%；在敌对实时子集上是 62.5% 对 16.7%。在 GameWorld 的 170 个任务上，VISTA 从暂停时的 84.1% 掉到实时 42.9%，AutoPILOT 仍有 80.0%。优势在多个模型上成立，并且它用大约五分之一的 API 费用就能达到 VISTA 的最终成功率。暂停时钟时 AutoPILOT 仍领先 17.0 个点，说明差距不只是延迟：一次调用能执行整段计划，100 次调用的预算被用得完全不一样。

## 🎯 为什么这件事值得写

视觉和游戏 agent 的 harness 讨论，最近多半集中在「模型看见什么、记住什么」。VISTA 靠视觉记忆和回看旧帧，在 ARC-AGI-3 上把同一批模型抬到满分解；OpenVLHarness 也是在工具和多模态记忆上做功。这些都很重要，但默认了一个前提：世界会等模型想完。很多游戏基准，包括 VideoGameBench 的 Lite，评测时本来就会把时钟停掉。

真实界面不是这样的。The World Won't Wait 已经比较过暂停和实时，但那边的 agent 读的是结构化文本，方法也还是每一步都要调用模型。AutoPILOT 走的是另一条路：不训练、不换模型，只改一次调用能覆盖多少步。这和我们在 coding agent 里看过的问题是亲缘关系：TerminationLag 说成功运行里很大一部分步数花在已经修好之后；CompoundingKernel 说卡住规模的不是 agent 数量，是可靠测量的速度。这里卡住实时表现的，是「一步一调用」这个接口假设。

如果你在做会操作活页面、终端或机器人的 agent，这篇值得当成一张设计清单：harness 除了上下文和记忆，还要决定模型不在线的那些几百毫秒里，谁在动手。

## 🏗️ 机制：三种执行方式，外加六种唤醒

AutoPILOT 明确建在 VISTA 上，而 VISTA 又建在 Codex harness 上。两边暴露的只读工具（检查、读像素、历史）、笔记文件和 `act` 是对齐的，差别几乎只在委派。所有游戏共用同一套 harness 指令，只有游戏说明、任务和按键不同。模型永远看不到内部状态，重启和决策画面事件是从画面里派生出来的。

时间 t 时，agent 可以读一帧并发送一个键盘或鼠标事件，或者显式等待，这算一步。模型调用是离散的：第 k 次调用读的是 t_k 时刻的画面，GPT-6.1 Sol 在低推理力度下中位耗时 6.1 秒。传统视觉 harness 把这次调用变成一个动作，却在 t_k + 6.1 秒才落地。实时里这会造成两件事：动作是过时的，而且出手频率被思考速度封顶。暂停时钟能同时消掉这两个问题，但任务已经变了。

AutoPILOT 的三种工具是：

1. **原始动作 `act`**：只发一步，同时停掉正在跑的宏或控制器。
2. **开环宏 `run_macro`**：模型写出一串动作，例如从前面交互里学会的菜单路线，工作进程按序列发送，中途不看屏幕。
3. **闭环控制器 `python`**：模型写一个短函数 `run(api)`，在沙箱里运行，单 CPU、1 GB 内存、无网络，最多 120 秒。它用 `api.observe()` 读帧，用普通代码决策，用 `api.act()` 行动，大约每 0.4 秒一轮，也可以请求交接把控制权还给模型。

论文里有一个几乎原样保留的例子：在 Praxis Fighter X 里，控制器用颜色定位船身和附近的洋红/红色弹体，边射击边躲避，循环结束后再交还控制权。在 Figure 1 的那局里，模型先自己死了三次，然后控制器接手，到 1:26 获胜。

委派要安全，控制权就得能回来。宏或控制器在跑的时候，模型的工具调用是堵住的，它在等，游戏由工作进程在打。调用会在六种唤醒事件上返回，并带上一帧新画面：

- 来自程序：控制器请求交接（可以附理由，并可在模型阅读时继续打）；函数写好的停止条件或出错；宏发完。
- 来自 harness：决策画面（商店之类）；场景突变后稳住（旧计划可能已经失效）；超时 120 秒。

失败重启对两种模式不一样：它会停掉宏并唤醒模型，但不会打断控制器，因为控制器能看到重置计数并继续下一局。实践里，交接造成的「边想边打」只占推理时间的 2.3% 到 3.5%。

### AFK-Bench 怎么测实时代价

120 个浏览器游戏，每个一题、带官方成功判定，在真实浏览器里玩。游戏来自公开站点，并用 13 项脚本检查做过校验。成功和进度由评测器从游戏状态计算，但状态不对 agent 开放。

环境类型用一条 60 秒停手探针划分：

- **敌对实时**（40）：不动就可能直接失败，比如几秒内会被打掉的射击游戏。
- **良性实时**（40）：世界继续动，但不动手不会立刻结束这一局，比如赛车。
- **回合制**（40）：只有 agent 行动世界才往前走，没有倒计时。

两种时钟协议覆盖同一批游戏。实时模式下，模型思考时游戏也不停，相当于人把视线从键盘上挪开。暂停模式下，每次模型调用期间（包括正在跑的宏和控制器）游戏被冻住，对 agent 来说每一步都变成了回合制。游戏自带的暂停和重启被挡住，agent 不能自己把钟停掉。从暂停到实时的掉分，就是它为自己的延迟付的学费。

预算是：100 次模型调用、2000 秒游戏时间或 2000 个环境步，先到先停。一次模型调用最多发一个工具调用。对「一步一调用」的 harness，100 次调用也就最多 100 步；对 AutoPILOT，一步宏或控制器可以一次走很远。

## 🧪 关键证据

### 一、实时主结果：68.6% 对 38.3%，敌对场景差距更大

在 AFK-Bench、相同预算、GPT-6.1 Sol 下：

- 全部 120 个游戏，实时成功率 68.6% 对 VISTA 的 38.3%。
- 敌对实时子集 62.5% 对 16.7%。
- 360 局成对 episode 里，111 局只有 AutoPILOT 赢，只有 2 局是 VISTA 独赢。
- 空操作和随机智能体最多赢 5.8%。
- 另外四个模型上也全部领先，实时领先幅度从 Qwen4-Max 的 13.3 个点到 Hy4-flash 的 29.2 个点；这些模型的绝对水平仍低于 GPT-6.1 Sol 和 Claude Opus 5.5。

GameWorld（170 个任务、34 个浏览器游戏，和 AFK-Bench 无重叠）把「世界不等你」说得更清楚：

| 模型 | Harness | 暂停时钟 | 实时时钟 |
| --- | --- | --- | --- |
| GPT-6.1 Sol | VISTA | 84.1 | 42.9 |
| GPT-6.1 Sol | AutoPILOT | 82.9 | 80.0 |
| Claude Opus 5.5 | VISTA | 67.1 | 41.2 |
| Claude Opus 5.5 | AutoPILOT | 72.4 | 67.6 |

暂停时两边接近，VISTA 甚至在 Sol 上略高；一改实时，VISTA 掉 41.2 和 25.9 个点，AutoPILOT 只掉 2.9 和 4.7 个点。

### 二、暂停时也领先，所以不只是更快出手

AFK-Bench 上，把时钟暂停之后，AutoPILOT 仍比 VISTA 高 17.0 个点（Sol）和 21.7 个点（Opus）。从暂停到实时，VISTA 和 Codex 在 Sol 上分别掉 17.8 和 12.8 个点，AutoPILOT 只掉 4.5 个点（73.1% 到 68.6%）。延迟解释了一部分，但不是全部。

其余来自「一次调用执行整段计划」。VISTA 的 222 次实时失败里，有 208 次是把 100 次调用用光，而且每局平均只走出 78 步。AutoPILOT 平均用 43 次调用走出 681 步，大约每次调用 16 步。模型也会按环境选模式：敌对实时里 98% 的步数、良性实时里 89% 的步数来自控制器；回合制里宏占 36% 的调用和 26% 的步数，因为可以提前排好动作。

把控制器拿掉、只保留宏，敌对实时成功率从 62.5% 掉到 50.8%。控制器是敌对环境里真正的承重墙；宏更像是在回合制里把计划一次发完。

另一个有点扫兴、但很重要的对照：实时条件下，VISTA 并不比普通的 Codex / Claude Code harness 更好（Sol 上 38.3% 对 38.9%，Opus 上 30.0% 对 32.5%）。它的无损视觉记忆和检查工具，看的是大约一次调用之前的那一帧，帧已经过时了，看得再清也帮不上忙。即使把时钟暂停，这些工具相对 Codex 只加 4.4 个点（56.1% 对 51.7%），相对 Claude Code 没有增益。

### 三、预算、推理力度和费用

把调用预算放到 3 倍，VISTA 从 37.5% 升到 55.0%，但和 AutoPILOT 的差距还在：标准预算下 AutoPILOT 是 69.2%，放宽全部预算后是 78.3%；在敌对实时环境里，VISTA 在各种预算下都不超过 37.5%。VISTA 的提升很贵，每局 5.28 美元，大约是 AutoPILOT 的 6 倍。按每局花费封顶来看，AutoPILOT 用 0.2 倍的总费用就达到了 VISTA 的最终成功率：Sol 上是 37 美元对 180 美元，Opus 上是 75 美元对 369 美元。

提高推理力度不会伤害任一 harness，但只有 AutoPILOT 能把它变成大涨幅。Opus 从 53.3% 到 69.2%，VISTA 只从 30.0% 到 36.7%；Sol 两边都只高几个点（68.6% 到 71.7%，38.3% 到 42.5%）。无论哪一档，VISTA 即使用高力度，也明显低于 AutoPILOT 的低力度，差距分别是 26.1 和 16.7 个点。对 AutoPILOT 来说，一次更长的调用换来的是一段能跑很多步的程序。

生成速度也是如此。在 80 个实时任务上，Sol 低力度从 10 token/s 的 55.0% 升到 200 token/s 的 63.8%，已经接近暂停时钟；VISTA 即使 200 token/s 也只有 38.8%，暂停时则是 57.5%。AutoPILOT 在慢速下仍能撑住，是因为速度只延迟控制器开工的时刻，一旦写好，它就会按满速打，不管模型想得有多慢。

## 🔬 最有意思的部分

最有意思的是那句看起来很克制的话：VISTA 改进了模型看见什么、记住什么，却把每次调用变成至多一个动作，于是 agent 只能以模型思考的频率行动。这把 harness 里常被忽略的第三轴单独拉了出来。

结合「暂停也领先 17 个点」和「208/222 的失败是调用耗尽」，实时崩溃有很大一块其实是预算会计问题。一步一调用的 harness 在长动作序列上会先把自己的调用预算花光，看起来像是「模型不够快」，账面上却是接口把 100 次思考换成了 100 个微操作。AutoPILOT 把一次思考变成一条可运行的计划，同一笔预算能覆盖一个数量级以上的环境步。

控制器的形态也很值得 coding-agent 借鉴。它不是预先训好的技能库，而是模型在这一局里现写的短程序，用颜色阈值这类非常具体的感知去扛 0.4 秒一级的循环，再在目标达成或情况变化时把控制权交还。这更接近「运行时合成一个短技能」，而不是「仓库里常驻一套技能」。当然，这也把新的风险带到了台上：程序写错、颜色启发式在换皮后失效、控制器在失败重启后继续用旧逻辑。论文用场景变化、决策画面和交接来回收控制权，但这些守卫本身也是 harness 的一部分，值得单独拿来审。

## 🤔 我的判断

这是一篇**harness 设计论文**，附带一个专门为「实时代价」服务的基准。亮点有三条。第一，它把「输出如何在时间中变成动作」定义成和感知、记忆并列的设计轴，并且用暂停 / 实时同题对照把账算清。第二，主结果跨模型、跨两个基准成立，费用和预算消融写得很完整，没有只报一个好看的总成功率。第三，AFK-Bench 按「不动会怎样」分类，比笼统说「我们测了实时」有用得多。

局限也很明确。游戏是浏览器里的 2D / 类 2D 环境，控制器大量依赖颜色和像素启发式，迁到复杂 3D 或视觉变化更大的界面时，现写程序还能不能扛住，文中没有同等强度的证据。沙箱里的 Python 是一种很强的动作接口，换到不允许任意代码执行的产品环境，宏可能还在，控制器这一档就得另找载体。基准和 VISTA 的对比绑定了「100 次调用」这类预算形状，如果改成按环境步或按墙钟计费，数字会变，不过按费用封顶的那张图已经部分回答了这个问题。另外，论文没有训练，也就没有回答控制器能不能沉淀成可复用技能，以及过期之后会不会出现我们在 StaleSkills 里看到的那种负贡献。

对工程的直接启发是：做实时或准实时 agent 时，先检查 harness 是不是把每次推理都锁成一步。如果是，加记忆、加高力度推理，可能只会让动作更晚落地。更值得试的是让模型输出一段能在本地循环的策略，并明确规定它何时必须把控制权还回来。编码代理里的「一次调用改完一个文件再跑测试」，其实已经是这个想法的慢速版；把同样的结构用到 GUI 和机器人上，这篇提供了一份可对照的实现和评测。

一句话收束：世界不排队，harness 就不该让模型每想一次只走一步。
