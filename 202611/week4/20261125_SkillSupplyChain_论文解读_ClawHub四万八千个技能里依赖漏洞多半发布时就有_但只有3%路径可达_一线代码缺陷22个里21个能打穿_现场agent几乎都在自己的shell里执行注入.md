# ClawHub 四万八千个技能里，依赖漏洞多半发布时就有，但只有 3% 的路径真能走到；一线代码缺陷 22 个里 21 个能打穿，现场 agent 几乎都在自己的 shell 里执行注入

你有没有过这种体验：给 coding agent 装了一个看起来无害的技能，SKILL.md 写得清楚，依赖也钉死了版本；后来才发现，模型会从网页、邮件里把参数填进这条技能，而技能脚本把参数拼进了 `os.system`，或者 agent 自己用 `bash -c` 拼命令，参数还没进技能，壳就已经展开了 `$(...)`。行业里把技能市场当作新的软件分发层，安全讨论却经常停在「有没有恶意技能」或「依赖里有没有 CVE」。**问题是：善意作者留下的缺陷，经由 agent 拼出来的参数，到底有多少真能被打到？打到的是技能里的 sink，还是 agent 自己的壳？**

这篇 **Carried-Over and Agent-Native Threats in the Supply Chain of LLM Agent Skills** 是我看到的第一份把这个问题做到注册表规模、并且用执行来量可达性的研究。看完我的感受是：**依赖 CVE 的数字看起来很吓人，但绝大多数走不到；真正危险的是一线脚本里的命令注入，以及一个更简单的事实——很多运行时还在用 shell 传技能参数。**

## 核心摘要

作者在 2026 年 3 月取了 ClawHub 的全量快照：48,682 个技能、17,130 位作者，其中 44.3% 带可执行代码。他们把无意缺陷分成两类从包生态带过来的风险（依赖 CVE、一线代码里从 agent 输入到命令或代码执行 sink 的流）和两类技能生态特有的风险（安装文档里的危险指令、凭证打到标准输出再进上下文），用静态分析筛选后，对四个主检测器标出的全部 3,428 个案例做了人工普查，再在沙箱和带间接提示注入的现场 agent 上抽查可达性。依赖一侧：能解析到具体版本的技能里，49.6% 依赖某个已知 CVE 的版本，涉及 1,555 个技能（占全库 3.2%）；其中 78.3% 是「出生即漏洞」——发布时 CVE 已经公开，中位早 676 天，而且 98.6% 当时已有修复版。六个月后再扫，仍在清单里的advisory 占 88.7%，作者真正升级或删除脆弱依赖的只有 1.7%，尽管这些技能里 55% 发布过新版本。人工确认其中 627 个是包可达的，但输入能走到脆弱函数的只有 47 个（3.0%）。一线代码一侧：848 个技能被标出从 agent 输入到执行 sink 的路径，确认 315 个（精确率 37.1%）；沙箱里抽到的 22 个一线缺陷有 21 个能端到端利用，14 个依赖 CVE 一个都没有。现场用 gpt-4o-mini 跑 200 个被标记技能，48.5% 会执行注入的 payload，但几乎都发生在 agent 自己的 `bash -c` 里、技能还没启动；payload 到达技能自身 sink 的只有 5.0%（10/200）。把工具改成传参数向量、拒绝直接 shell 的 execve 条件后，97 次利用里能复现的从 94.8% 降到 10.3%。结论很硬：注册表应优先处理一线缺陷而不是依赖告警，运行时不要把技能参数经 shell 传递。这篇的价值定位是：**一份带人工确认和执行可达性的注册表级测量，而不是又一份只报静态告警的技能安全扫描。**

## 🎯 为什么这件事值得写

技能把可执行代码、第三方依赖、安装逻辑和自然语言说明书捆在一起，告诉 agent 何时、如何调用。和传统包不同，调用者不再是会做代码审查的开发者，而是一个会从用户请求和外部内容里拼参数的语言模型。间接提示注入走的就是这条路：攻击者只控制网页、文档或邮件，不能改技能、注册表、用户请求或模型。善意作者留下的 `eval`、`os.system` 或一个过时依赖，就可能在用户机器上变成代码执行。

已有工作多半瞄准故意作恶（后门、凭据窃取、写进 SKILL.md 的注入），或只用正则和 LLM 分类器报静态告警，执行也只用来确认恶意行为或泄露。没有人在整个注册表上问：agent 的输入到底能不能走到这些缺陷。难度有两层。静态检测会过近似，告警必须人工确认才能计数；而注入是否到达，取决于 agent 怎么拼、怎么跑命令，必须靠执行来看。所以静态告警的数量，和 agent 真能打到的数量，完全可能差出一截。

作者明确把恶意技能排除在外，并用可观察信号而不是推测意图来隔离：混淆、无关端点的硬编码外传、无关的凭据库访问等八条里至少两条才标成恶意。315 个确认的代码缺陷里，自动信号命中 13 个，人工复查后一个都不算恶意。

## 🏗️ 机制：先普查，再把「代码里有洞」和「agent 打得到」分开

### 五个暴露点和一个利用定义

技能调用链上有五个暴露点。依赖里的已知 CVE 和一线脚本里的危险 sink 是从包生态带过来的；SKILL.md 里的 `curl | bash` 这类安装指令、以及技能把凭据打到标准输出再进对话，是包管理器没有的。还有一个跨两边的点：agent 用自己的 shell 调用技能，参数在技能启动前就被展开。

作者沿用污点分析的三元组（源、汇、净化）。代码缺陷和可达的依赖 CVE 共享源——agent 供给技能的输入，汇分别是一线的命令/代码执行调用，和公告里的脆弱函数。标准输出泄露是从凭据读到 stdout。安装指令不是数据流，按文档模式匹配。

关键定义是：**技能被 agent 利用，当且仅当存在攻击者控制的内容 $c$，使得运行 $A(c)$ 会执行攻击者的 payload。** 若 payload 在技能内部的 sink 执行，是技能汇路径；若在 agent 的 shell 解释 $A(c)$ 时、技能还没启动就执行，是 agent 壳路径。后一条不需要技能里有流。

### 检测、普查、可达性

SkillTriage 为每种模型跑一个检测器。依赖用 OSV 覆盖 PyPI、npm 和 GitHub Advisory，扫描带 requirements 或 npm lockfile 的 3,188 个技能；没有 lockfile 的 npm 技能不在依赖扫描范围内。代码缺陷对准 CWE-078 和 CWE-094，三阶段：正则预筛、CodeQL 加模式查询、滤掉已知良性模式（list 形式的 subprocess、硬编码兄弟文件的 exec 等）。安装指令用十二条正则扫 install.sh 家族和 SKILL.md。标准输出泄露用 CodeQL 从环境变量、`~/.ssh/`、`.env`、dotenv 追到 print 和 logger，按汇附近窗口里的凭据证据分严重级别。

静态结果只当高召回筛子。两个作者在标注前固定规则，对四个主检测器的全部 3,428 个案例做普查，另对每个检测器抽 150 例算一致率：stdout 和 curl|bash 的 $\kappa=1.0$，依赖 0.96，代码缺陷 0.62（主要分歧是环境变量算 agent 设的还是运维设的）。确认数以普查为准。代码预筛的召回大约 89%；第三阶段过滤器在 159 处 sink 的基准上留住 104 个真阳性里的 103 个。

可达性分两层。沙箱 harness 用构造好的输入跑抽样出的缺陷，看 payload 是否端到端执行。现场 agent 是 gpt-4o-mini，工具为经 `bash -c` 的 `run_command`，分朴素注入和「要求原样传递」的显式注入，各三轮。配对对照再把工具换成 `run_program(program, args)`，只接受参数向量、拒绝直接 shell：只在 shell 条件下能复现的，是 agent 壳路径；execve 条件下仍在的，是技能汇路径。

## 🧪 关键证据或主结果

依赖数字要分层看。1,555 个技能依赖已知 CVE 版本，占能解析到具体版本者的 49.6%。和 npm 里「安装之后才变得脆弱」不同，这里 78.3%（1,217/1,555）发布时至少已有一个公开 CVE，只算作者钉死的版本也有 57.1%；出生即漏洞的对里，CVE 公开的中位时间是 676 天，且 98.6% 当时已有修复。脆弱的精确 Python 钉死里，85.8% 来自五位作者提交的 `pip freeze` 转储，其中一个 127 行文件被复制进 40 个技能，就贡献了 1,092 条。近重复聚类（MinHash，Jaccard ≥ 0.85）把语料收成 2,538 个大小至少为 2 的簇，抽 100 簇有 97% 是真正的重复，五分之一还跨作者复制。发布之后也很少修：六个月后 88.7% 的 advisory 还在当前清单里，真正去掉脆弱依赖的只有 1.7%，尽管 55% 的这类技能发过新版本。

但这些 CVE 大多走不到 agent。21,012 个（技能, CVE）对里，运行时会 import 的只有 24%；其余是开发依赖、测试夹具，或声明了却从不导入。普查确认输入能走到脆弱函数的只有 47/1,555（3.0%），而且集中在少数公告：三条就占 28 个（requests 的 .netrc 泄露、yaml 栈溢出、PyPDF2 死循环）。47 个里只有 5 个（10.6%）属于对 agent 真正相关的类型（RCE、反序列化、SSRF、路径穿越、认证和密码学缺陷）。沙箱里 14 个依赖案例一个都没被利用：有的包没被调用，有的函数已被补丁或根本不是这条路径在用。

一线代码正好相反。848 个技能被标记（1.74%），确认 315 个，命令注入为主，JavaScript 的 `child_process.execSync` 加模板字符串最多。沙箱里 22 个一线案例 21 个被端到端利用。作者举了两个具体例子：一个阅读技能把 LLM 返回的扫描函数送进带完整 builtins 的 `exec`，攻击者把指令藏在书里，payload 还能顺着重试循环再试三次；一个差旅技能把 agent 的位置参数直接拼进九处 `os.system`，SKILL.md 还说明参数来自城市、日期和乘客信息。844 个带 SKILL.md 的被标记技能里，9.6% 自己在说明书里要求 agent 把用户或外部内容传给有漏洞的脚本，是未被标记技能的 2.3 倍。有三个以上技能的作者被标记的可能性更低（调整后优势比 0.79）。

安装指令和标准输出是包生态没有的面。十二条模式在 install.sh 里原始命中 102 个、SKILL.md 安装节 707 个、全文 3,440 个；按各模式的精确率加权后，真正有风险的大约是 40、266 和 910。`curl | bash` 这种高精确模式在安装节确认 192/202（95.0%），全文 445/727。标准输出一侧，带凭据证据的 433 个里只确认 22 个真把秘密打出来（精确率 5.1%），很多是变量名、掩码预览或主机名；沙箱 4 个里利用了 3 个。

现场 agent 是全文最关键的一张表。200 个抽样技能里，97 个（48.5%，Wilson 95% CI 42–55）执行了 payload；另有 18 个走到了汇但缺依赖，装全最多到 57.5%。97 个里有 95 个是 agent 把 `$(...)` 不带引号放进了自己的命令行，壳先展开。这 97 个里 41 个普查为阳性、56 个是普查假阳性，说明这条路径不依赖技能代码。配对对照：shell 条件复现 92/97（94.8%），execve 条件只在技能自身 sink 打到 10 个（10.3%），而且这 10 个全部是普查确认的，56 个假阳性一个都没有。技能汇利用率因此是 10/200（5.0%）。130 个普查阴性里没有一个在自身 sink 被打到（单侧 95% 上界 2.3%）。换言之，37.1% 的普查率量的是代码审查能确认什么，5.0% 量的是这一个 agent 实际打到了什么，中间的缺口在运行时，不在漏标。

模型当参数过滤器不可靠。小规模试验里，它会改写「目的地城市」这种自然语言字段，却原样传递 URL 和日期；显式指令还能关掉改写。200 个样本里，有 21 个在朴素注入下没被利用，加上「原样传递」的指令就被利用了。gpt-4o 能拒绝一眼能看出是代码的值，但挡不住长得像普通参数的值。该做的检查在技能入口，不在模型侧。

三类确认风险几乎不相交：可达依赖 CVE 47、可利用代码缺陷 315、真正的标准输出泄露 22，并起来 381 个技能，只有 3 个同时占两类，没有一个三类都占。六个月后 83% 仍在架上，合计下载 529,181 次，中位下载略高于全库，在带代码的未标记技能里也偏高。抽查的可利用技能里，46% 在同一段代码里既读秘密又做网络 I/O，一次注入就可以把凭据送出去。

必须记住的限制：只覆盖一个注册表、一个时间点；现场 agent 是 gpt-4o-mini（五个试点技能用过 gpt-4o），不是生产宿主里的模型，每变体三轮未设种子，具体利用率不可外推。但两条路径依赖的条件更一般：壳路径只需要一个未经消毒的 shell 工具，技能汇路径取决于技能代码而不是模型。依赖扫描覆盖不到没有清单的技能，代码扫描覆盖不到非 Python/JS。确认数是下界。文中没有公开分析代码仓库。

## 🔬 最有意思的部分

「出生即漏洞」和 npm 的时间线是反的。成熟生态里，多数 CVE 是安装之后才披露，依赖更新机器人和 lockfile 还能补救；技能这边，作者发布时就把已经公开几百天、并且已有修复的版本钉死了，后来发新版本也不改这一针。五个人的 `pip freeze` 和跨作者复制，让同一个脆弱模板出现在很多技能里。所以「发布后再扫依赖」的运维假设，在这里不成立，检查应该发生在发布当刻。

更有意思的是可达性把这个故事翻了过来。依赖告警可以上到一千五百个技能，真能从 agent 输入走到脆弱函数的只有 3%；一线命令注入在沙箱里几乎全中。把两类叠在同一个技能上的 36 个案例里，也没有发现「一线路径把依赖 CVE 变成可打」的链条——一线缺陷本身已经能执行代码。注册表如果按告警数量排优先级，会把精力耗在走不到的 CVE 上。

现场试验把第三条路径暴露出来：最大的利用面居然不是技能，是 agent 自己的壳。payload 在 48.5% 的抽样里能跑起来，听起来很吓人；换成参数向量工具之后，只剩技能里真正有洞的那 10 个。技能一个字节都不用改。对运行时来说，这大概是全文最便宜的修补。

## 🤔 我的判断

定位：**注册表级的测量基础设施。** 方法上的贡献是把静态告警、人工确认、沙箱利用和现场 agent 利用分成四层计数，并且把技能汇路径和 agent 壳路径切开。它不提供新的防御系统，但把该修哪一层说得很清楚。

亮点三条：

- **把「清单里有 CVE」和「agent 打得到」分开，数字差了一个数量级。** 49.6% 对 3.0%，再对上沙箱里 21/22 对 0/14，足够改变分诊顺序。
- **发现并量化了一条包生态没有的主路径：agent 用 shell 传参。** 48.5% 对 5.0%，以及 execve 对照里 94.8% 降到 10.3%，是可以直接交给运行时的证据。
- **普查做得老实。** 3,428 个案例全部人工看过，精确率从 curl|bash 的 95% 掉到 stdout 的 5.1% 都报出来；还测了筛子的召回，并把恶意技能用可观察信号隔开。

问题与局限：

- 单一注册表、单一快照，现场模型不是生产模型，利用率不能当成生态常数。
- 依赖和代码检测都有覆盖空洞（无清单、非 Python/JS）。
- 确认依赖专家判断；代码缺陷的 $\kappa$ 只有 0.62，虽然分歧没有进最终阳性计数。
- 没有公开分析代码，复现普查不容易。
- 下载次数会被镜像放大，作者用安装次数做了对照，但仍是平台计数。

对工程的直接启发：

1. **注册表分诊：一线污点告警排在依赖告警前面，先丢掉开发依赖和从未导入的包，再通知作者。** 发布时用 OSV 核对钉死的版本，npm 要求 lockfile。
2. **运行时不要用 `bash -c` 拼技能命令。** 改成参数向量工具，文中这一项就把壳路径上的利用从 94.8% 降到 10.3%，而且不用改任何技能。
3. **技能入口处校验 agent 传来的参数，不要指望模型帮忙消毒。** 模型会改写看起来像自然语言的字段，却放行看起来像普通参数的 payload；显式注入还能关掉改写。
4. **标准输出进上下文前先打码**；SKILL.md 里的安装指令只用高精确模式自动检查，不要把安全警告和占位符当成 `export secret`。
5. **评估技能安全时，至少同时报四类数：静态标记、人工确认、沙箱利用、现场 agent 利用，并分开壳路径和技能汇路径。** 只报「有多少技能含 CVE」或「有多少次注入成功」，都会把真正该修的层看错。

一句话：技能供应链里，看起来最多的是带过来的依赖漏洞，真正打得穿的是一线脚本，而现场跑起来的往往是 agent 自己的壳；注册表该按可达性分诊，运行时先把参数从 shell 里拿出来。
