# 静态 CUA 考场一过就分不出高下：任务和检查点判分器跟着 rollout 一起进化，宏平均分从 60.6 降到 47.5，特征覆盖扩了 3.65 倍，人和判分一致 84%

你有没有过这种体验：刚给 CUA 搭好一套桌面考场，模型过了两代，分数就挤在天花板上，分不出谁真的更强，也看不出它到底卡在哪类操作上。现有基准多半是人写死任务、再配一条任务专用的判分脚本，行业里把它叫做静态评测。**问题是：agent 在持续变强，考场却不跟着动，难度天花板、功能覆盖和测量精度会一起失效，而且这三件事常常被搅在同一次「把题改难」里。**

这篇 **Self-Evolving Evaluation Environments for Computer-Use Agents** 提出 CUA-SEE，把评测做成闭环：每一轮用有效 rollout 更新测量状态，再分别进化共享基准任务、针对单个 agent 的边界探针，以及可执行的状态检查点。看完我的感受是：**它真正有用的不是再堆一批更难的题，而是把「考什么、怎么分得更细、怎么量得更准」拆开，并且让判分器和任务一起长；四轮之后分数下来了、覆盖上去了，持出的模型和一起进化的模型掉分幅度还对得上。**

## 核心摘要

作者把 CUA 评测的静态困境写成三件事：固定题集一旦被掌握就分不出继续进步；人工出题对软件功能的覆盖很窄，他们对核心 OSWorld 应用的审计显示，已有任务用到的软件特征分类还不到 20%；静态基准既不跟踪移动的能力边界，也不会主动去找新出现的弱点、捷径和泛化缺口。CUA-SEE 用三套算子分别对付这三件事。基准任务进化由异质 agent 队列的对齐轨迹出发，用队列的一致和分歧把源任务标成已掌握、仍能分辨、不稳定或被混淆，再在轮次层面同时推进可测量的难度前沿和特征覆盖，候选必须保住语义谱系锚点，也不能把某一种模型的偶发失败写成基准目标。诊断任务进化则是条件于单个 agent 的：在七个校准过的能力维上做自适应探针，干净的成功向上探、失败向下探，含混结果先去混淆，目标是缩小过关边界，而不是把题尽量出难。两边共用一套判分器进化：任务无关的软件适配器把原生状态导出规范成 CanonicalState，再把演进后的任务合同编译成原子检查点；一个信息隔离的 verifier agent 和独立的 pass agent 做对抗交叉审查，用来卡检查点是否完整、以及 PRE/PASS 能否分开。实验在 20 个应用的底板上，对八个核心 OSWorld 应用、50 步预算做严格的 R0 对齐。基准进化用 100 个谱系对齐的任务组，从 R0 演到 R4，五个模型共 2,500 次配对观察：Kimi-K2.6、Seed-2.1-Pro、Gemini-3.5-Flash 负责驱动进化，Qwen-3.7-Plus 和 GPT-5.5 严格持出。R0 仍用原生 OSWorld 任务和判分器，进化轮改用 CanonicalState 判分器。五个模型的宏平均分从 R1 的 60.6 降到 R4 的 47.5，平均轨迹从 27.4 步加长到 39.3 步；精确特征操作从 R0 的 127 个扩到 R4 当时的 464 个，正好是 3.65 倍，累计前沿登记为 487。对 400 条跨四轮的 Kimi 轨迹做人工对照，检查点判分器与人的判断一致率为 84.0%（Cohen's κ 为 0.640），并从 81% 升到 89%。这篇的价值定位是：**给持续变强的 CUA 配一套也能一起进化的评测基础设施，而且把范围、分辨率和测量精度分开管理，而不是再发一份一次性的难题集。**

## 🎯 为什么这件事值得写

CUA 的对错不能只看一段文本，也不能只看代码测例绿没绿，而要核对软件内部状态和多条款任务合同。OSWorld 这类人工基准把这件事做起来了，但出题和写判分脚本都贵，agent 一进步，考场就冻在原地。作者用一张对照表把已有可进化方向摊开：OSWorld 五项都不动，TRACE、CUA-Gym、OpenComputer 各自只覆盖其中几项，CUA-SEE 把任务难度、特征覆盖、边界分辨率、判分器质量和过程信号都标成可进化。

更关键的是方法上的拆分。很多「让评测跟着模型长」的管道，其实是把题改难、把覆盖拉宽、把判分改严搅在一次硬化里。这里三件事分属三个算子：队列校准的共享基准不该被某个模型的癖好带跑；针对单个 agent 的诊断探针不必也不能写成公共考场；而无论题怎么变，测量工具都得把新义务落到可观察状态上。对做 harness 和评测的人来说，这几乎是在问：你的考场有没有和被测系统一起版本化。

## 🏗️ 机制：范围、分辨率和精度分成三条进化环

闭环很清楚。每一轮，agent 先在当前的任务-判分器对上交互；通过有效性过滤的轨迹和检查点结果更新测量状态；这些证据再决定下一轮该测什么、对应的判分器该怎么实现。

基准进化强调模型中性。它保留全部重复实验，把执行是否有效和任务是否成功分开，再用队列的一致与分歧给源任务定级，从而约束这一轮允许加强到什么程度。轮次规划同时优化难度前沿和特征覆盖：难度要在校准过的能力需求上可测量地增加、且不能把任务整体改退；覆盖则必须在精确的「软件-分类-操作」单元或「能力-强度」单元上真正新增。纯平移不算进化，转移过来的题必须带上可独立测量的新需求。候选还要过一组门：保住谱系锚点、不出现实质性难度回退、预算内可完成、最终状态可唯一观察、并且有模型中性的证据；步数需求超过可用预算 0.85 的直接拒掉。

诊断进化则把预算集中到不确定的能力边界附近。批次规划器先把通过、部分通过、混淆和无效结果分开，只用设置和判分器都有效的观察当干净边界证据，再按软件、特征、主能力、强度派出探针。七个能力维是尺度一致性、精度控制、目标锚定、依赖状态的推理、流程遵循、特征整合，以及验证与控制，强度从 0 到 5。搜索不是单调加难：干净的成功或失败会向上或向下调强度，含混结果则先去混淆、简化或复现。作者特意写了，他们更愿意要一道稍弱但能干净归因的探针，而不是一道更难却分不清边界的题。

判分器进化是两者共用的测量脊梁。演进后的任务合同被拆成可独立测试的结果条款，再映射到可观察字段；只靠文件是否存在、文件名、或不可用的动作前取值当代理检查，是被禁止的。原有检查点会标成保留、修改或删除，新义务则新增。构造时，每个软件的适配器探测原生状态导出接口，把快照规范进共享的 CanonicalState，每个检查点只核对一项任务效应，并返回期望与实际的理由。验证分成句法与导入、结构合同、静态模式三项静态门，以及 PRE/PASS 判别和检查点负向夹具两项行为门。pass agent 独立做出可执行的通过态，verifier agent 在看不到实现的前提下审查这个态是否真的满足任务，交叉审查用来抓住敷衍检查点、漏掉的义务和错误期望值。

## 🧪 关键证据或主结果

表 2 是最硬的那张难度账。五个模型在 R4 的总分分别是 Kimi 53.6、Seed 44.6、Gemini 49.3、Qwen 46.1、GPT-5.5 44.0，通过率掉到 13% 到 19%。作者强调，宏平均分从 R1 的 60.6 降到 R4 的 47.5，平均步数从 27.4 加到 39.3。有的模型在 R2 会比 R1 略高，但轨迹更长，说明后面的题往往需要更长的交互链，新引入的功能也可能更对上某个模型的能力。难度也不均匀：Chrome 在后面几轮仍相对容易，GIMP、Calc 和 Writer 掉分更明显。

覆盖方面，表 3 给出层级扩张：R0 到 R4，当时的特征操作从 127 个到 464 个，正好 3.65 倍；能力-强度 35 格的累计覆盖在 R2 就到了 100%。八个应用都在涨，不是只深挖一两个软件。诊断一侧，每轮还会稳定引入 57 到 73 个新的特征叶节点。画像也很具体：Gemini 在精度控制和目标锚定上更强，高尺度一致性仍难；Kimi 在点击、打字和导航上更稳，Seed 对拖拽、滚动和依赖状态的控件更敏感；三个被诊断的模型在 Chrome 和 VS Code 上更稳，GIMP 和 Thunderbird 则暴露得更清楚。

判分器没有在变难的同时塌成「只看最后一项」。962 个任务平均 4.82 个检查点，原子需求覆盖率 overall 为 92.5%，几乎所有应用都超过 85%，覆盖偏低主要出在原生适配器受限的软件，例如 Thunderbird。400 条 Kimi 轨迹上，与人工判断一致 84.0%，κ 为 0.640，一致率从 81% 升到 89%；对不上的地方，作者归因于适配器状态不完整、判分器覆盖不全，以及状态字段错位。

可靠性上，持出的 Qwen 和 GPT 分别掉 26.9 和 24.0 个点，和驱动进化的队列掉分节奏相符，却没有参与出题。R4 的通过率已经窄到 13% 到 19%，连续分数仍把边界信息量抬高 20.8 个百分点，到 69.7，并且暴露出被标量总分掩盖的、每个应用 20 到 37 个百分点的名次对调。效率上，作者按 GPT-5.5 的 API 单价估了成功进化一次的代价，指出主要瓶颈是基准任务进化里的共享上下文构造，而不是生成判分器本身。

## 🔬 最有意思的部分

最有意思的不是「分数变低了所以题变更难了」，而是他们把降分解释成评测信息量被重新打开。R0 上 Kimi、Gemini 已经有 89.0 和 80.0 的总分，接近饱和；进化之后，考场才重新具备分辨力。同时他们没有把 R0 和 R4 直接拿来当同一把尺：R0 用的是原生 OSWorld 判分器，后面才换 CanonicalState，正文比较宏平均时用的是 R1 到 R4。

另一处是诊断和基准的分工。共享基准刻意不盯着某一个模型的失败，诊断探针才去贴着某个 agent 的边界挖。如果把这两件事合成一条「对着最强模型出难题」的流水线，公共榜很容易变成该模型的个性化错题本。CUA-SEE 把这层风险写进了候选门和模型中性约束里。

还有一个工程上很诚实的选择：观察不到的条款必须显式标成覆盖缺口，而不是用歪代理检查硬判，更不会为了图省事把难检查的应用从套房里拿掉。部分可观察的任务只要至少有一项目标效应被可靠验证、且所有省略都声明了，就仍可以进入 rollout。这让 Thunderbird 这类适配器更弱的软件还能留在表里，而不是被悄悄删掉。

## 🤔 我的判断

定位：**测量基础设施。** 贡献是把 CUA 评测从一次性人工命题，改成任务、判分器和有效轨迹共同版本化的闭环，并且把范围、分辨率和精度分开进化。

亮点三条：

- **把「改难、加覆盖、改判分」拆成三个可分开验收的算子。** 共享基准走队列校准和谱系门，诊断探针走自适应夹逼，判分器走状态锚定和对抗审查，不容易在一次硬化里把三件事搅乱。
- **难度和覆盖的账是对得上的。** 宏平均从 R1 的 60.6 到 R4 的 47.5，特征操作 3.65 倍，持出模型掉分幅度与队列相符，说明这不全是出题模型在拟合自己。
- **判分器进化有人工对账，而且没有把检查点收成一句总分。** 84.0% 的轨迹级一致、92.5% 的原子覆盖，以及 Partial 任务仍保留 3 到 7 个检查点，让过程信号还在。

问题与局限：

- 文中没有单独的局限节，也没有公开代码或数据；复现这条包含适配器、对抗审查和多轮编排的管道，成本不低。
- 人工一致性只在 400 条 Kimi 轨迹上评估，κ 为 0.640，属于中等吻合；作者自己把对不上的地方归因于观察性限制。
- R0 与后续轮的判分器不同，跨轮绝对分数不能直接当同一把尺；正文已经用 R1 到 R4 来报宏平均，读的时候不要把它误写成从 R0 的高分直接掉下来。
- 进化由三个模型驱动，虽然两个持出模型跟上了掉分节奏，但诊断画像只覆盖了 Gemini、Kimi 和 Seed。
- 成本按 GPT-5.5 单价估算，且只统计成功的进化 run，完整的经济账还不透明。

对工程的直接启发：

1. **静态 CUA 榜一旦接近饱和，先不要急着换更大的模型再刷同一套题。** 更值得问的是题目覆盖了多少功能单元，以及判分器还能否跟上新的任务合同。
2. **给单模型找弱点的探针，不要直接写进公共基准。** 公共题要模型中性，个性化诊断单独记账。
3. **判分器要和任务一起改，而且每个新义务都得落到可观察状态。** 用文件名或「看起来做完了」当代理检查，会在进化之后把测量偷偷弄松或弄歪。
4. **通过率掉到十几二十以后，还要看连续分数和分应用的名次。** 不然会误以为所有模型都一样不会做，其实边界和软件短板还在换位。
5. **进化评测的主要花费可能在共享上下文，而不在生成检查点。** 若要自己做类似闭环，先压缩任务谱系和覆盖登记表的上下文，再考虑换更强的出题模型。

一句话：CUA 还在长，考场如果还停在人写死的那一轮，分数就会先失去分辨力；CUA-SEE 给出的办法不是把题一次性出得更狠，而是让任务、探针和可执行判分器跟着有效轨迹一起升级，并且把这三件事分开验收。
