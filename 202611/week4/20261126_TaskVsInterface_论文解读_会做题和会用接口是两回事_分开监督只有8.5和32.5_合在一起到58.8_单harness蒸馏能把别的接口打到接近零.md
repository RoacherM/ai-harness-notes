# 会做题和会用接口是两回事：分开监督只有 8.5% 和 32.5%，合在一起到 58.8%，单 harness 蒸馏能把别的接口打到接近零

你有没有过这种体验：同一个模型，换一套工具格式或终端脚手架，分数就掉一截；于是你用在 A 脚手架里跑出来的成功轨迹去做蒸馏，结果 B 脚手架不但没跟上，有时还从还能用变成几乎为零。行业里把「系统提示、动作格式、反馈环和资源限制」整包叫 harness，训练却常常默认：会做这道题，换个接口也能做。**问题是：一次失败，到底是缺任务知识，还是不会在这个接口上把知识表达出来？这两部分是不是必须合在一起学，才能真正用得上？**

这篇 **Learning What vs. Learning How: Decomposing Task and Interface Competence in Agentic Training** 把 agent 能力拆成任务能力和接口能力，并用一种叫 harness rehearsal 的监督把二者分开。看完我的感受是：**只从别的脚手架搬成功轨迹，或只在目标接口上做「正确动作已经写明」的排练，往往都不够；两者合在一起，收益会远大于相加。反过来，只在一个 harness 上做蒸馏，可以把另一个接口的成绩打到接近零——而同样的单接口训练，若改成 on-policy RL，破坏性会小得多。**

## 核心摘要

作者认为，任务能力可以跨 harness 迁移，但要在推理时用出来，取决于会不会操作当前接口。实验在 Harbor 里收集 SFT 轨迹、跑 GRPO 和评测，覆盖 MedAgentBench、Reasoning Gym、AppWorld 以及 BFCL 的单轮和多轮，每个基准三个训练用 harness、一个全程不参与训练的留出接口，学生主要是 Qwen3-4B。成功定义为验证器分数达到 0.99。冻结策略在不同接口上能解开的题并不重合，说明同一套知识会被接口挡住。单 harness 蒸馏通常抬高训练接口，却可能破坏其他接口：BFCL 多轮上，只在原生工具调用（fc）上蒸馏，JSON 接口从 33.5% 掉到 0.1%；MedAgentBench 上只在 fc 上蒸馏，Terminus-2 从 3.7% 掉到 0。三接口蒸馏（3H）则在训练接口上继续涨，并大体避免在留出接口上崩掉。为了把两种监督拆开，作者引入 harness rehearsal：用 $\rho(x)$ 改写任务说明，直接给出正确动作，但环境和验证器不变，再在目标接口上收集成功轨迹当接口监督；任务监督则来自其他 harness 上的成功解题轨迹，目标接口全程不出现。二者单独用时收益有限，合在一起远大于任一端：在 BFCL V3 多轮、目标为 fc 时，交叉任务监督和排练分别是 8.5% 和 32.5%，合在一起 58.8%，接近三接口蒸馏的 59.0%，也高于只在目标任务上蒸馏的 55.2%；MedAgentBench 的 Terminus-2 上是 2.0% 和 9.5% 合成 34.4%，Reasoning Gym 上是 19.8% 和 20.0% 合成 37.0%。失败分析里，BFCL 多轮在只做任务监督时，失败案例中 86% 到 94% 被标成接口失败，加上排练后降到 17% 到 25%。随后的 GRPO 更耐单接口训练：从 3H 蒸馏检查点继续做单接口 RL，不会再现蒸馏那种跨接口坍缩，多接口能力可以带进强化学习阶段。这篇的价值定位是：**一份把「会做题」和「会用这个 harness」拆开测量、并给出可操作训练配方的方法论文，而不是再发一个新脚手架。**

## 🎯 为什么这件事值得写

最近的工作已经承认：harness 不只影响评测，也在塑造训练。Harness-Bench 在改配置，HarnessBandit、What Does Multi-Harness RL Learn?、HarnessX 在讨论多脚手架之间的调度、信用分配和可迁移性。缺的是更底层的一刀：跨接口迁移失败时，失败的是任务知识，还是接口本身？

如果分不清，训练决策就会拍脑袋。看到 A 接口分数低，就继续在 A 上堆成功轨迹，结果可能把 B 接口的操作方式覆盖掉；或者以为多收集一些别的脚手架的解题过程，目标接口自然会用。作者要验证的假设很明确：**任务能力可以汇总，但没有接口能力，这些知识在推理时用不出来。**

## 🏗️ 机制：交叉任务监督 × 目标接口排练

所有数据收集、RL 和环境执行都走 Harbor，GRPO 经由 SkyRL 接在同一套 rollout 环上，保持 on-policy。每个基准的接口集合分成三个训练用 harness 和一个留出接口，例如 BFCL 多轮是 fc / json / pycall 训练、xml 留出，Reasoning Gym 是 Terminus-2 / mini-swe / Goose 训练、Aider 留出。这些接口的动作通道差得很远：有的是原生工具调用，有的是 JSON 或 XML 标签，有的是在终端里跑 JSON 命令，历史管理、终止条件也不一样。

多接口蒸馏把不同 harness 上的成功轨迹汇进同一个策略。单接口蒸馏则只吃其中一个。为了拆开任务监督和接口监督，harness rehearsal 做了一次很干净的替换：任务说明变成 $\rho(x)$，里面已经写明正确动作，环境和验证器保持原样；只在目标接口 $h$ 上采集成功轨迹，组成排练集 $\mathcal{R}_h$。这样，模型在学「怎么在这个接口里发动作、何时停」，而不必再解原来那道题。交叉任务监督则完全相反：成功轨迹来自其他接口上的真题，目标接口不出现。把两者做成 2×2，就能看见交互，而不是只看见又一次涨分。

## 🧪 关键证据或主结果

单接口蒸馏的破坏性，是全文最不宜忽略的数字。fc 专用策略在 BFCL 多轮把 json 从 33.5% 打到 0.1%，在 MedAgentBench 把 Terminus-2 打到 0。涨分是真的，塌陷也是真的：训练接口变好，不代表策略更会做题，有时只是更会、也只会这一个接口。3H 蒸馏在多个训练接口上同时上升，并大体避开这种崩塌，例如 BFCL 多轮上 fc / json / pycall 分别到 60.2%、50.2%、49.1%。

排练实验把「为什么 3H 有用」说得更清楚。交叉任务监督或排练单独做，常常只是小幅波动；合在一起才跳起来。BFCL 多轮目标 fc 上的 8.5%、32.5% 对 58.8%，几乎追上 3H 的 59.0%。四个随机种子上，合取始终落在约 55% 到 59%，而只做任务监督的种子里出现过 8.2%，也出现过 26.0%，波动不小，但合取的优势稳定。把合取数据量减到与单侧相同，或把单侧重复到合取规模，都解释不了这个跳变，说明不是多喂了几条轨迹这么简单。模板级拆开看，排练过的读类模板涨得最多，但从未排练过的模板平均也能从任务监督的 8.5% 涨到合取的 42.2%，说明接口练习并不完全绑死在见过的模板上。

失败类型对上了这个故事。BFCL 多轮在只做任务监督时，自动和人工标注都显示失败里绝大部分是接口失败；加上排练后，接口失败占全部试验的比例从大约 66%–72% 降到 7%–10.5%。Reasoning Gym 上接口失败占比也下降，但失败案例里仍有约七成被标成接口问题，说明排练不是万能的。MedAgentBench 上自动标注和人工标注分歧更大，不宜只引用其中一侧。

RL 阶段给出另一条训练建议。从 3H SFT 出发再做 GRPO，单接口 RL 不再明显打压其他接口，有时还能带动只在蒸馏阶段见过的接口：MedAgentBench 上，fc 从 3H SFT 的 56.4% 升到 parity 专属 GRPO 的 61.4%，再升到 Terminus-2 专属 GRPO 的 66.9%。3H GRPO 在该基准上往往最强，parity / fc / 留出 xml 分别到 77.6%、85.7%、78.0%。从基座直接做单接口 GRPO，也不会再现单接口 SFT 那种把别的接口压到基线以下的模式。作者的归纳是：on-policy RL 对单接口训练更稳健，蒸馏阶段学到的多接口能力可以带过去。

## 🔬 最有意思的部分

最有意思的是那个 2×2：不是「接口监督有用」或「多脚手架轨迹有用」，而是二者几乎呈与门。交叉任务监督在目标接口上有时甚至有害，BFCL 多轮上单独做任务监督只有 8.5%，低于基座的 44.6%——把别的接口的成功轨迹灌进去，却还没教会 fc 怎么说话，会先把原来会的接口用法扰乱。排练单独做能部分挽回（32.5%），仍远低于合取。这很像学会一门专业之后还要学一套新的仪器操作：只看别人用另一台仪器做出来的结果，或只在空仪器上练习按钮，都不够；二者同时有，仪器才会把专业知识用出来。

另一个细节是留出接口并不自动享受同样的红利。Reasoning Gym 上 3H SFT 把训练接口抬得很高，留出的 Aider 却从基座的 20.8% / 17.6% 掉到 19.0% / 9.8%。多接口训练能减少崩塌，不等于对所有没见过的脚手架都有正迁移。接口离得远的时候，排练或 3H 也救不了全部。

## 🤔 我的判断

定位：**方法论文，也是一套训练诊断框架。** 它没有发明新的 agent 系统，但把「换个 harness 就掉分」从现象推进到可以分开干预的两个能力。

亮点三条：

- **把任务能力和接口能力拆开，并且真的做成了可交叉的 2×2。** 8.5% 和 32.5% 对 58.8% 这种合取远大于分项的数字，比再强调一次「要多脚手架训练」更有指导意义。
- **单接口蒸馏的跨接口坍缩被写得很硬。** 33.5% 到 0.1%、3.7% 到 0，提醒一句：训练接口涨分，可能是在覆盖别的接口，而不是在积累可迁移的任务知识。
- **SFT 和 RL 对单接口训练的耐受性不同。** 多接口能力可以在蒸馏阶段获得，再由更稳健的 on-policy RL 接着用，这给「先 3H SFT、再 RL」提供了机制上的理由。

问题与局限：

- 正文没有单独的局限节。学生以 Qwen3-4B 为主，规模和模型族是否同样成立，没有展开。
- 排练需要一份能写明正确动作的 $\rho(x)$，这在有验证器和可执行环境时好做，在开放式任务上并不总是现成。
- 留出接口的迁移并不一律成功，Aider 就是反例；MedAgentBench 上失败类型的自动标注和人工标注也不够一致。
- 接口集合仍是有限的几种格式和终端脚手架，不能直接外推到任意 GUI 或专有 IDE agent。

对工程的直接启发：

1. **看到某个 harness 上分低，先问是不会做题，还是不会在这个接口里行动。** 前者该从其他接口补成功轨迹，后者该补接口排练，不要只在原接口上继续蒸馏。
2. **不要用单接口 SFT 当默认岗位训练。** 它可能把其他部署接口打崩；如果必须在一个接口上继续训，优先考虑 on-policy RL，而不是再灌一轮专用轨迹。
3. **多接口蒸馏仍然值得做，尤其当你还要在没见过的格式上评测。** 它不是万能迁移，但比单接口专用策略更不容易塌。
4. **如果拿得到正确动作说明，接口排练可以比在目标接口上重跑全部真题便宜得多。** 先恢复「会操作」，再让跨接口的任务知识落地。
5. **评测时至少看两个以上接口，并记录失败是格式、终止还是真正答错。** 只报一个 harness 上的总分，会把接口事故误读成能力不足。

一句话：任务知识可以跨脚手架汇总，但不会用这个接口，汇总来的知识就还是别人的；把「做题」和「操作」分开教，再合在一起用，比在一个 harness 上把分数堆到最高更安全，也更接近你真正要部署的那件事。
