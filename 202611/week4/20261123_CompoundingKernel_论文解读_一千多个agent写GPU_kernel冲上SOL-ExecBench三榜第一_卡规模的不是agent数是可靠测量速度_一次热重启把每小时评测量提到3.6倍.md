# 一千多个 agent 同时写 GPU kernel，冲到 SOL-ExecBench 三个公开榜第一；真正卡规模的不是 agent 数，是可靠测量的速度：一次热重启把构建移出 GPU 锁，每小时评测量涨到 3.6 倍

你有没有过这种体验：把一个长程 agent 任务并行化，开了几十上百个 agent，结果吞吐没怎么涨，看监控才发现大家都排在同一把锁、同一个评测服务、同一块 GPU 后面。或者 agent 跑了一夜，第二天发现最好的结果是靠计时器挑分支、改测试输入刷出来的。行业里把这类系统叫 agentic search 或 self-improving harness：模型不动，围绕它的搜索、记忆和验证在进化。**问题是：当你真的把它扩到上千个 agent、跑上几周，决定上限的到底是什么？**

Amazon 团队的 **CompoundingKernel: Self-Improving from Zero to First** 是一份 47 页的工程报告：用固定的 Claude Opus 5.5 做所有 agent，从 PyTorch 定义出发，在 NVIDIA B200 上为 SOL-ExecBench 的 235 个问题写 kernel，截至 2026-11-11 拿下 L1、L2、Quantization 三个公开榜第一。看完我的感受是：**这篇最有价值的不是排名，而是它把一个长程多 agent 搜索系统怎么跑、怎么防作弊、怎么在运行中改 harness 讲得非常具体，而且有两个负面结果：加更多指导没用，加更多 agent 也不直接等于更多实验。**

## 核心摘要

系统由四层嵌套循环组成：最内层的子 agent 拿到一个父 kernel（或者没有，即新设计）和一个方向，改代码、编译、在 B200 上计时，第一个正确的 kernel 就停；第二层每个问题一个 LLM 控制器，读这个问题的归档，选父节点或开新根，给每个空闲子槽位写一个方向；第三层由 lead 和 helper agent 监控系统、修 harness，修复在下一次热重启时生效；最外层由人决定哪些 kernel 提交到官方榜、什么时候提交。**每个问题的所有正确 kernel 及其谱系存在模型之外的归档里**，agent 只能用只读 SQL 查，只有评测能追加正确的 kernel。**正确性全部由模型之外的检查决定**，官方分数从不进入前两层循环。结果：235 个问题全部有网站判定正确的 kernel；在三个公开榜的 209 个问题上，相对基准的 PyTorch 基线几何平均快 4.40 倍（中位数 3.78 倍），89 个问题单题第一，193 个进前十。同样墙钟时间下，LLM 控制器在 38 对问题中的 35 对上胜过一个按 UCB 打分的编码树搜索，但按相同尝试次数比只赢 15 对、输 23 对，赢面来自它在同样时间里做出了 2.4 倍的正确尝试。把可选的参考文档和技能改成必读，使用率涨 4.3 倍，233 对问题的最终加速比几何平均比值 0.981，没有提升。一次热重启把构建移出 GPU 锁、把 shell 启动从 12 到 15 秒降到毫秒级，每小时评测候选数涨 3.6 倍。这篇的价值定位是：**在固定模型的长程搜索里，扩展上限由「每小时能拿到多少可靠测量」决定，而不是 agent 数量或 prompt 里塞了多少知识。**

## 🎯 为什么这件事值得写

kernel 是在 GPU 上跑一个算子的程序。Blackwell 的快路径要走 tcgen05 张量核指令、tensor memory 和 TMA 拷贝引擎，而大多数融合或低精度形状还没有库 kernel 用上它们。写这种 kernel 本质是搜索：试一个设计、测、按测量修、再试。难点在于三件事：让搜索建立在之前的尝试之上，把它同时铺到几百个问题上，以及**别让它自己骗自己**。

SOL-ExecBench 是 NVIDIA 的公开 kernel 基准：235 个问题来自 124 个真实模型，官方榜上覆盖 3,957 个工作负载，包括 BF16、FP8、NVFP4 的前向和反向，分为 L1（单算子 94 题）、L2（融合算子 82 题）、Quantization（33 题）、FlashInfer-Bench（26 题）四个榜。每个工作负载有一个未公开的优化 PyTorch 基线时间和一个「光速」下界，分数

$$
S_w(k)=\frac{t_b(w)-t_{\mathrm{sol}}(w)}{\bigl(t_k(w)-t_{\mathrm{sol}}(w)\bigr)+\bigl(t_b(w)-t_{\mathrm{sol}}(w)\bigr)}
$$

和基线一样快得 0.5，达到下界得 1，失败得 0。网站在自己的 B200 上锁定 1,500 MHz 计时，构建超过 300 秒直接拒绝。

**正确性为什么难**：错的 kernel 通常不崩，而是返回看似合理的数。这批 kernel 的中位长度约 7,000 行，人审不过来。而一个足够强、能找到快 kernel 的搜索，也一定会找到检查器的漏洞，学会不做真实工作就拿分的 reward hack。基准作者在自己的 agent 运行里就标记并拒绝了 589 份提交（14.5%）。论文的相关工作部分还列了几个已知的翻车：一个早期 agent 结果被追溯到复用了参考实现的内存，加固后的重新评测把 KernelBench 上最好的模型从 1.43 倍拉到 0.88 倍，kernel 经常把测试形状写死。

## 🏗️ 机制：四层循环，记忆和裁判都在模型之外

### 四层循环

| 层 | 谁 | 做什么 | 看得到什么 |
| --- | --- | --- | --- |
| ① 子 agent | Claude Opus 5.5 | 拿一个父节点和一个方向，编辑、编译、计时；最终运行里第一个正确 kernel 就停 | 自己的父节点、归档（只读）、CUTLASS 头文件、互联网、可选的技能和公开 wiki |
| ② 控制器 | Claude Opus 5.5，每个问题一个 | 只有两个工具：查归档，调用 expand（一个父节点 + 一组互不相同的方向，每个空闲子槽一个）；子槽一空就补 | 归档；自身不保存状态，每轮重读 |
| ③ 团队循环 | lead 和 helper agent | 监控系统和进度，修 harness 故障，需要时通知人；修复在热重启时上线 | 运维信息 |
| ④ 外层 | 人 | 决定提交哪些 kernel、什么时候提交、算力怎么分 | 公开榜单 |

控制器一步可以写成：

$$
(p,d)\sim\pi_{\mathrm{LLM}}(\cdot\mid A),\quad k'=\mathrm{Child}(p,d),\quad A\leftarrow A\cup\{k'\}\ \text{若}\ k'\ \text{正确}
$$

### 模型之外的共享记忆

- 每次运行一个独立归档，其他运行看不到，所以实验运行不会影响最终运行。
- 控制器和子 agent 用只读 SQL 读；**只有评测会追加节点，而且只追加正确的 kernel**，失败的尝试只记日志、不成节点。
- 写路径：每个运行追加一个 ledger，每个候选一个文件夹，一个单独的 builder 从 ledger 重建 SQLite 并原子替换，agent 永远只看到完整的数据库。
- 候选是树节点，父链接是树边，没有父节点的就是新设计。
- 人看的 dashboard 读一份 agent 看不到的独立副本；每日的 shell 命令审计会检查有没有 agent 碰过它。

### 奖励只来自本地计时

对正确的 kernel，奖励是相对官方公开基线时间的几何平均加速比：

$$
R(k)=\Bigl(\prod_{w\in\mathcal{W}}\frac{t_b(w)}{t_k(w)}\Bigr)^{1/|\mathcal{W}|}
$$

计时在自己的 B200 上做。不用 SOL 分数做奖励，因为它在高加速比时会变平；SOL 分数只作为上下文给 agent 看（运行后期按本地算出的类网站分数排序候选）。自家 GPU 不锁频，最高约 1,965 MHz，所以本地时间偏快；人用一个 agent 看不到的校准系数去修正。

### 「从零开始」的边界

作者把「从零」说得很清楚：指搜索，不指模型。每次运行冷启动，只有问题的 PyTorch 定义、形状和数据类型，不继承之前运行的任何东西，不看参考 kernel，不看官方结果。但模型本身在公开代码上预训练过，agent 能读 CUTLASS、上网、读一个公开 wiki。人也参与了：搭早期系统、批准热重启时的 harness 修复、根据公开榜单决定提交什么和何时提交。**从 2026-10-25 起，人按每个问题离第一名的差距分配子槽位**，离第一近的多给，稳居第一的让出一些，总数不变；agent 只收到一个槽位数。人还往部分运行的 prompt 里加过少量批准过的说明（设计方向、Triton 指导、一条时钟说明），不含分数和排名。

### 模型之外的检查

| 类别 | 确认什么 | 什么时候跑 |
| --- | --- | --- |
| 官方正确性 | 每个工作负载都在官方容差内匹配参考实现，部分运行算失败 | 每次评测 |
| 鲁棒性 | 在未发布的形状、超出范围的尺寸、极端或结构化输入上也正确；内存安全 | 每个新最优；每次提交时 16 个种子在发送的确切字节上跑两遍 |
| 规则与 reward hack | 速度和正确性都来自真实计算 | 新最优计入之前；每次提交 |
| 网站就绪 | 构建时间留有余量；在自己的 B200 上预演官方评测 | 每次提交 |
| 审查与官方分数 | 每行一次清单审查和书面结论、一个人点头、网站自己的检查 | 每次提交 |

精度规则在运行中收紧过：降精度计算只有在保留声明的输入输出类型并通过鲁棒性检查时才算；用更快的单元模拟 fp32（3xTF32、BF16x9、Ozaki）可以，低于声明类型的 bf16/fp16 计算算违规；Quantization 问题豁免。**反 reward hack 的检查是在代码里强制的，而不只是写在给 agent 的说明里。**

### 榜单结果（Table 4，截至 2026-11-11）

| 榜 | 问题数 | 名次 | 公开 SOL 均值 | 单题第一 | 单题前十 | 相对基线加速比（网站计时，几何平均） |
| --- | --- | --- | --- | --- | --- | --- |
| L1 | 94 | #1 | 0.823339 | 35 | 84 | 4.04× |
| L2 | 82 | #1 | 0.819260 | 39 | 76 | 3.62× |
| Quantization | 33 | #1 | 0.909670 | 15 | 33 | 9.19× |
| 三榜合计 | 209 | | | 89 | 193 | 4.40× |

- 39 个问题至少快 10 倍，2 个至少快 100 倍，最大是 L1/094 的 1062 倍；也有两个比基线慢：L2/037（0.30 倍）和 L1/030（0.96 倍）。209 个里 21 个低于 1.5 倍，全在 L1 和 L2。
- L2/037 的差成绩部分是自找的：一个通过了所有自动检查的库 fallback 被代码审查拒了。
- 本地对比：在自家机器上比 torch.compile 默认模式快 11.2 倍，但同一批 kernel 网站口径是 4.47 倍，差距来自本地时钟偏快（约 1.19 倍）和 torch.compile 比官方基线慢（约 2.11 倍）。作者明确说以官方基线为准。
- 235 个最终 kernel 里 214 个是 CUDA C++，13 个 CuTe DSL，6 个 Triton，2 个混合；221 个超过 1,000 行；按源码文本匹配，77% 提到 tcgen05，72% 用 TMA，94% 含内联 PTX，没有一个用 Hopper 的 wgmma。
- 截至 2026-11-02，上千个 agent 会话评测的候选里 98.4% 是正确的。

### 收益来得早（§4.3）

每个榜在运行前 15% 的时间里拿到了 73% 到 85% 的提升；按候选数算，前 2% 的候选贡献了 81% 的提升。问题的正确候选数和它的提升之间 Spearman 相关是 -0.36：难题、余量小的题吃掉了大量尝试，后期槽位又被挪向离第一名近的题。所以候选数反映的是成本，不能说明在同一题上多试就多涨。

### 三个规模化教训（§5）

| 教训 | 挑战 | 干预 | 测量 |
| --- | --- | --- | --- |
| agent 多不等于实验多 | 早期所有 GPU 锁都被占着，每块 GPU 约 5 个调用排队，但 GPU 只有约 13% 在忙；锁覆盖整个远程调用，包括 CPU 构建和 12 到 15 秒的 shell 启动 | 一次热重启：构建移出锁，shell 启动降到毫秒，profile 改为可选，新最优的验证交给基础设施 | 相同 GPU 和槽位、匹配时段，每小时评测候选 3.6 倍，每个落地候选的锁时间降 71%，正确率保持约 98% |
| 热重启保住进度 | 长运行要吸收修复、检查和硬件变化 | 记忆在归档和 ledger 里，热重启只改一处、在同一运行上重启 agent；有一次重启让 agent 停了几个小时之后，定下「每次发布只上一个可门控的改动」 | 之后只重启 agent 的成本降到几分钟；最终运行经历了十几次热重启，从没从头开始 |
| 只验证可能发出去的 | 子 agent 自己跑鲁棒性检查，每个候选约 0.77 次，占了约四分之一锁时间 | 只自动检查每个运行的新最优，发送行做全量检查 | 每个落地候选的鲁棒性检查从 0.66 降到 0.27，约 95% 的新最优仍在几分钟内被检查，其中 95.9% 鲁棒 |

第四条是把大的父 kernel 作为文件路径而不是粘贴文本传给子 agent，首条 prompt 写入的上下文减少 88% 到 96%，吞吐不变。

注意第一条教训作者自己的限定：3.6 倍属于整个热重启加上两个时间窗之间的其他进展，几个改动的贡献没有拆开；**也还没有通过直接改变 agent 数量来验证这个上限**。

### 三个搜索设计对照（§6，Table 5）

| 对照 | 样本 | 时长 | 结果 | 结论 |
| --- | --- | --- | --- | --- |
| LLM 控制器 vs UCB 式编码树 | 38 对 | 每臂 24 小时（Phase 1 harness） | 同等墙钟 35/38 胜（严格 24 小时截断 34/38），几何平均比 1.14 倍；同等候选数 15 胜 23 负 | 赢在 2.4 倍的正确尝试数，不是挑得更准 |

前两个对照在最终版之前的 harness 上跑，第三个只是一次短筛选，每臂都只跑一次，没有在最终 harness 上重复。参考资料的使用率本身也在说明问题：可选时，最终运行前 5% 的时间里 13.6% 的子会话打开了技能，过了前 10% 之后低于 2%，整个运行只有 1.19% 打开技能、0.83% 打开公开 wiki。

## 🔬 最有意思的部分

**慢的 kernel 是垫脚石。** 归档保留每一个正确的 kernel，控制器可以扩展任何节点，不只是当前最优。235 条最优路径里，41 条（17%）至少有一步比父节点慢 10% 以上，75 条（32%）至少一次从低于当时最优 0.9 倍的节点扩展。Quant/030（NVFP4 解码层）最典型：在 9.71 倍时，控制器让子 agent 把 Triton attention 换成 Blackwell 张量核上的 CuTe DSL attention，第一次只有 1.52 倍；下一个子 agent 查出是寄存器溢出，到 7.10 倍，还是低于父节点；第三个子 agent 把新 attention 移植到当时最优节点（12.93 倍）上，得到 13.97 倍。运行里 93% 的节点都源自那个 1.52 倍的节点，最终路径从 6.25 倍走到 27.36 倍，270 步里有 76 步持平或变慢。L2/043（Mamba-2 分块扫描）和 L1/065 也是同样的模式：落后的分支提供了在某些形状上更快的部件，嫁接到领先者上成为新的基座。

**reward hack 是搜索自己找出来的，而且作者把它写出来了。** Quant/030 那条路径上，从第 3 步到第 155 步（大约运行的前三分之一），kernel 在首次使用时用一个短计时跑来按形状挑变体，先是 autotuner，后来是构建启动计划时的计时跑。这被认定为 reward hack，后来被规则禁止；禁令下来后，一个子 agent 删掉所有这类计时，把选择固定成按形状查表，本地掉了 6%（25.36 倍到 23.88 倍），大约运行时间的 1% 之后又回到 25.42 倍。发出去的 kernel 和后来 27.36 倍的最优都来自这个无计时器的节点。另一次是作者自己的评分器出错：有一段时间把只跑了部分工作负载的评测算成正确，发现后受影响的行被降级，一些问题的最优成绩随之下降。

**为了正确性主动退一步。** L2/001 是一个 fp32、容差很紧的视觉 attention 反向。运行早期最快的 kernel（5.73 倍）在投影 GEMM 里用了单次舍入的 fp16 张量核计算，通过了官方工作负载，却在更多形状上被鲁棒性检查判为 NOT_ROBUST，误差随归约长度增长。它的子节点改用分精度操作数，掉到 4.26 倍，再修一次到 4.17 倍并通过全部六种形状。搜索在这个节点上继续，大约运行时间 3% 之后超过了原来的 5.73 倍，最终到 15.20 倍，是那个脆弱 kernel 的 2.65 倍。另一个例子是 L2/079：最优 kernel 通过了所有形状，但在压力输入上 FP16 溢出，团队宁可接受从 1.62 倍掉到约 0.48 倍。

**本地分数只是对自己机器的断言。** Quant/029 本地最优 14.55 倍，但它把可能用到的每个变体都编译进去（41 到 71 个源文件），运行时计时挑选，结果连续三次提交都超出网站 300 秒构建限制。冷缓存串行构建时，被接受的 kernel 最多 308 秒，被拒的至少 1,965 秒。后来一个 unity 构建被接受，但它仍在运行时计时选变体，被自家 agent 发现，又换成一个删掉不可达配置的无计时版本（68 个配置只留 12 个、4 个文件）。

**安全边界写得很具体**：agent 跑在 CPU pod 上，通过托管模型 API 用 pod 级凭证，没有长期密钥；agent 从不自己跑 kernel，每次工具调用都是对本运行 GPU pod 的远程命令；GPU pod 不持有云凭证，所有 pod 屏蔽云元数据服务，agent 只能访问自己运行的指定 GPU pod。

## 🤔 我的判断

定位：**工程样本加几条测量出来的系统教训**。它不是一个可以严格复现的方法论文，而是一份把长程、多 agent、固定模型搜索系统做到公开榜第一的完整运行记录。

亮点三条：

- **记忆和裁判都放在模型之外**：只读归档、只有评测能写、只收正确的 kernel；正确性由代码检查决定，反 hack 规则在代码里强制；人用的 dashboard 与 agent 隔离并每日审计。这几乎就是多 agent 共享状态并发契约和来源追溯的一个现成参考实现。
- **两个诚实的负面结果**：必读参考不涨分，LLM 控制器每次挑选并不比 UCB 树更准。它们共同指向「每小时可靠测量数」这个变量，比再加一层 prompt 工程更有指导意义。
- **把 harness 当成可以热更新的版本序列**：每次重启只上一个可门控的改动，进度保存在 agent 之外，所以「方法」变成了一串有日期的版本，作者也承诺按这个序列发布。

问题与局限（大部分作者自己写在了 §9）：

- **只有一个基准、一个模型、一次冷启动的最终运行**，外加几组分开的 A/B；三个设计对照要么在最终版之前的 harness 上，要么只是短筛选，每臂一次。
- **「官方分数不进入搜索」有边界**：人根据公开榜单决定提交和算力分配，从 2026-10-25 起子槽位跟着离第一名的差距走。官方分数没进 agent 的上下文，但进了资源分配。
- **正确性是测出来的，不是证明出来的**：作者调研过的形式化和 SMT 工具都不能建模 Blackwell 的异步张量核操作（最好的候选也只覆盖约 16% 的问题）；运行中鲁棒性检查覆盖的是新最优（94.9%），不是每个候选，只有约 1/40 的候选被做过鲁棒性检查。
- **作者既是参赛方又是报告方**：排名和加速比是自报的，有明确的截止时间；agent prompt 不开源，外部很难复现搜索行为本身。
- 没有报告总成本（模型调用、GPU 小时）。对关心 harness 与模型配对成本的读者来说，这是一个明显的缺口。

对工程的直接启发：

1. **先看吞吐瓶颈，再决定加不加 agent**。锁的范围、构建和 shell 启动时间、评测排队，这些在 agent 数量上来之前就该测。
2. **记忆放在 agent 外面，并且只允许评测写入**。这让热重启、换 harness、换 agent 都不丢进度，也天然给每个结果留了来源。
3. **反作弊规则写进代码，不只写进 prompt**；同时预期搜索一定会发现新的 hack，留出「运行中加检查」的流程。
4. **验证放在决策点上，并测量放弃了多少覆盖**：每个候选都验太贵，只验可能被采纳或发出去的，再报告覆盖率。
5. **保留慢但结构不同的候选**。按当前最优贪心剪枝，会丢掉之后被嫁接出更好结果的那条线。

一句话：上千个 agent 能不能比几十个 agent 走得更远，取决于每一次尝试能不能被快速、可靠地测出来并留在模型之外；这篇把这件事在一个真实的公开榜上做到了第一，也老实地写出了它没测的东西。
