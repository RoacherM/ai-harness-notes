# 把压缩上下文的决定交给模型，GPT 6.1 在 32K 预算上 OfficeQA 从 21% 到 56%：Kimi 少用 41% 输入 token，会不会用、何时压，模型差得很远

你有没有过这种体验：长任务跑着跑着窗口满了，脚手架到了阈值就把前面的历史摘要掉，摘要里偏偏丢了后头还要用的那条证据，模型再怎么认真也找不回来。行业里把这种「窗口到线、由脚手架决定何时压、压哪一段」叫 harness-driven context management，今天大多数 agent 脚手架都这么做。**问题是：如果改成让模型自己决定何时压、压什么，现有模型能不能用好？这对分数和 token 有没有用？推理引擎能不能让这种中途改写变得更便宜？**

这篇 NVIDIA 技术报告 **Letting Models Manage Their Own Context: Where We Stand** 把模型驱动的上下文管理接进自家开源脚手架 NOOA，在文档研究和机器学习工程上，把 8K 到 512K 的上下文预算扫了一遍。看完我的感受是：**会用上下文 API 的模型，在同样预算下可以明显更高分，常常还更省输入 token，紧预算上最明显：GPT 6.1 Sol 在 OfficeQA Pro v2、32K 预算上从 21% 到 56%，几乎翻了三倍；Kimi K3 在同样 32K 上限下累计输入 token 少 41%（36M 对 62M），分数还略高（43% 对 41%）。可差异非常大：GPT、Kimi、DeepSeek 在 42% 到 53% 的任务里至少调用一次，Opus 5.5 只有 4%；拿掉「用到 85% 再考虑压」这句提示，Kimi 和 DeepSeek 会提前很多开始压，大预算上大约比脚手架基线低 8 个点。推理侧把编辑后没改动的后缀 KV 缓存留下来，相对标准前缀缓存能少做 4% 到 15% 的 prefill，准确率没有可测变化。**

## 核心摘要

对照很干净。脚手架驱动：上下文用到预算的 80%，就由脚手架把更早的历史摘要掉，保留最初指令和最近 10 个事件。模型驱动：模型拿到 NOOA 的上下文 API、实时用量指示，以及「用量到 85% 再考虑压缩」的说明，窗口接近上限时请求里还会加一条压力警告；模型可以用 `collapse` 把一段事件收成摘要，被收掉的事件会归档，之后再按原来的标签取回。两个基准分别是 OfficeQA Pro v2 的 90 道美国联邦收支问题（要在预解析的大文档库里检索和阅读，上下文涨得很快），以及 MLE-bench Lite 的 22 场 Kaggle 比赛（要看数据、写代码、看反馈、提交预测）。预算从 8K 扫到 512K，每档都是请求大小的硬上限，超了就丢掉最旧事件重试，三次失败记为答错。四个模型是 GPT-6.1 Sol、Kimi K3、DeepSeek V4 Pro 和 Claude Opus 5.5。收益集中在紧预算，文档研究上比机器学习工程上更明显；GPT 单次压缩后请求中位缩小 3.7 倍，Kimi 2.1 倍，DeepSeek 1.8 倍，Opus 1.5 倍，GPT 在 19% 的压缩之后还会再把归档内容取回来。64K 预算下第一次收到压力警告时，Opus 多半直接交卷，GPT 有 69% 的回合会先读 API 文档再压，DeepSeek 有 46% 先检查事件历史，Kimi 有 49% 直接压。把「85% 再压」的提示拿掉，Kimi 在 128K 上第一次压缩的中位用量从约 84% 掉到 29%，DeepSeek 在 256K 上从 83% 掉到 40%，Opus 则从几乎不压变成经常很早压，128K 上中位只有 16%。64K 预算上，Kimi 比脚手架基线少用约 11% 的累计输入 token，分数 57% 对 52%。作者又把 NOOA 的上下文 API 接到 SGLang 里一套后缀 KV 复用原型上，用 Qwen3.6-27B 在 MLE-bench Lite、OfficeQA Pro 和 DeepSWE、32K 上下文下测，prefill 计算少 4% 到 15%，任务指标没有可测变化，节省最大的是 OfficeQA，因为编辑后留下来的后缀平均大约 10K token，约占提示的 60%。这篇的价值定位是：**一份把「模型自己管上下文」从口号落到共享 API、多模型和紧预算上的实测，并把它和推理引擎的 KV 编辑连在一起。**

## 🎯 为什么这件事值得写

Agent 一工作，工具调用、输出和模型回合就会把历史堆起来，既会加重 context rot，也会把窗口撑满。现在的默认办法是脚手架到线就摘要，启发式决定何时压、覆盖哪一段，模型只负责写出那份摘要。实现简单，但关键任务信息可能在这一下里丢掉。

另一条路是把决定权交还给模型。NOOA 发布时就把「通过 API 直接控制脚手架，包括上下文压缩」写成核心想法之一；后来 SideQuest、Context Language Models 也在直接讨论这件事，Codex 还出了实验性的上下文管理模式，把历史、笔记和 `new_context` 工具放在一起。缺的是一次把现有模型放到同一套 API 下、再看紧预算和推理成本的对照。作者问的正好是这三句：现在的模型管得好自己的上下文吗，分数会不会更好，推理引擎能不能把模型改写过的上下文变得更便宜。

## 🏗️ 机制：collapse 负责收，归档标签负责取回来

NOOA 的上下文 API 需要的操作其实只有两个。`collapse` 把一段事件收成一份摘要，被收掉的事件不是扔掉，而是归档；模型之后可以用原来的标签把原文取回。和脚手架到 80% 再统一摘要相比，模型可以在中途更早或更晚出手，也可以选择只收某一段，而不是按固定窗口切。

实验把上下文压力定义成「任务需要的东西相对于窗口能装下的东西」。缩小预算是在模拟更长的任务：同样要读很多文档或迭代很多轮，窗口却更紧，管理历史的次数会变多。模型驱动这一侧除了 API 本身，还带了用量指示、85% 的时机说明，以及接近上限时的压力警告，这样作者才能同时观察「会不会用」和「何时开始用」。如果请求仍然超限，回退是丢掉最旧事件再试，三次失败记错，这一点在读小预算分数时必须记住，因为它本身也会影响得分。

## 🧪 关键证据或主结果

OfficeQA Pro v2 上的曲线是主结果。会用 API 的模型在同样预算下可以明显高于脚手架压缩，不必为此再训练；最清楚的是 GPT-6.1 Sol 在 32K 上从 21% 到 56%。增益在紧预算最大，预算变宽之后差距缩小。GPT 和 Kimi 在小预算上就走在脚手架基线前面，Opus 则一直落后，直到预算大到两种策略收敛。MLE-bench Lite 上的效应小得多，而且主要出现在最紧的几档，作者认为这些比赛需要的上下文本来就少得多，这和近期「上下文管理在窗口相对任务长度偏紧时最有用」的观察一致。

使用行为把分数差解释清楚了。GPT、Kimi、DeepSeek 会在大约一半任务里至少压一次，Opus 几乎不用。GPT 不仅更常调用，单次压得也最狠，而且还最常把归档再取回来，看起来最把这套 API 当成可逆的工作区，而不是一次性删历史。64K 上第一次接到压力警告时，四个模型的反应几乎像四种性格：交卷、先读文档、先看历史、直接压。

提示对时机的影响同样大。有「85% 再考虑」时，多数模型会等到接近这条线；拿掉之后，Kimi 和 DeepSeek 会提前很多开始压，在 128K 及以上预算上，这两种无时机提示的变体大约比脚手架基线低 8 个点，GPT 和 Opus 没有类似的准确率变化。作者把这种「窗口明明还有空，却过早把上下文压得很小」叫做 context anxiety，沿用已有文献里模型误判剩余预算的说法，并猜想 Kimi K3 在训练里对过长 rollout 的 RL 惩罚，可能教会了它即便还有空也要省 token。

## 🔬 最有意思的部分

最有意思的不是「少用 token 就一定更便宜」。标准前缀缓存只复用「还没改过的前缀」，在历史中间插入一份摘要之后，摘要后面哪怕原文没变，也要重新 prefill。所以模型把上下文改短了，并不自动等于推理更省，还要看引擎在每次编辑之后必须重算多少。作者把后缀 KV 复用做成 SGLang 里的原型，让编辑点之后没改动的那段缓存留下来，这是对完整重算的近似，目的是在保留有用模型状态的同时减少服务端计算。OfficeQA 上节省最大，正是因为工具取回的长文档常常还留在上下文里，编辑后能活下来的后缀又长又稳定。这项测量用的是一个开源模型、一个引擎，比的是每请求的 prefill，不是端到端延迟或美元成本，作者自己把范围写进了局限。

另一处值得停一下的，是他们对 GPT 为什么更强的解释。文中提到 Mainplane 这类脚手架已经提供和 NOOA 类似的上下文管理，Codex 的实验模式也让人觉得相关能力在 GPT 的开发里可能被注意过。他们猜想，针对模型驱动上下文管理的训练，可能是 GPT 在这套 API 上更自如的原因之一；同时又写明：功能存在并不能说明被测模型是怎么训练的，更不能说明这种训练会迁移到 NOOA 的接口上。这是猜想，不是被检验过的因果。

## 🤔 我的判断

定位：**在共享上下文 API 上的实测，外加一次把模型决策和推理引擎 KV 编辑连起来的共设计样本。** 它没有训练新的上下文管理模型，也没有宣称所有模型拿了 API 都会变强。

亮点三条：

- **在紧预算的文档任务上，模型自己管上下文可以同时加分和省输入。** 32K 上 GPT 几乎翻三倍，Kimi 少用 41% 累计输入 token，这不是微调换来的。
- **把「会不会用、压得多狠、何时开始」写成可以对照的行为差异。** 四个模型面对同一套 API 和同一句提示，用法几乎完全不同，提示还能大幅度改时机。
- **指出更短的提示不等于更便宜的推理，并给出后缀 KV 复用的初步数字。** 4% 到 15% 的 prefill 下降、准确率没有可测变化，方向和 Byron 关心的缓存级上下文工程是对齐的。

问题与局限：

- 两个基准都不大，OfficeQA 90 题、MLE-bench Lite 22 场，策略或模型之间的小差异未必显著；图里的误差是重复的最小到最大，不是完整的统计检验。
- 缩小预算只是长程任务的代理，不一定覆盖真长任务的全部性质，触顶后丢掉最旧事件的回退自己也会影响分数。
- 只评了四个模型，训练史未知，关于 GPT 更强的解释仍是猜想。
- 后缀 KV 复用只在一个开源模型和一个引擎上测了 prefill，不是端到端成本。
- MLE-bench 和编码任务上的增益明显更小，不能把 OfficeQA 上的倍数直接搬到所有 agent 工作负载。

对工程的直接启发：

1. **如果任务会反复把窗口塞满，值得给模型一个能收、能取回的上下文 API，而不只在 80% 处统一摘要。** 先在紧预算上对照分数和累计输入 token。
2. **不要假定所有模型都会用这套接口。** 上线前先看调用率、单次压缩倍数、以及压力警告之后是交卷还是真的在管上下文。
3. **时机提示不是小事。** 有的模型没有「用到接近上限再压」的说明，就会过早把有用上下文丢掉；需要的话把这条写成明确合同，而不是指望模型自己会估对剩余预算。
4. **省输入 token 之后，还要看推理引擎在编辑点之后重算了多少。** 若要让模型驱动的压缩变成更便宜的服务，引擎需要能复用未改动后缀的 KV，并释放不再需要的缓存项。
5. **若要把这件事做稳，最终还是得在训练里教模型何时压、压什么。** 只靠提示，四个模型的行为已经分叉得太开。

一句话：把压缩上下文的决定交给模型，在紧预算上可以又准又省，但这件事今天还很看模型会不会用、提示怎么写，以及推理引擎能不能把中途改写变得真正更便宜。
