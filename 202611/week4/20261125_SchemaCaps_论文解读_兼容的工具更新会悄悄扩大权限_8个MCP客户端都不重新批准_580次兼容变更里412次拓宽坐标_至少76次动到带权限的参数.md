# 兼容的工具更新会悄悄扩大权限：8 个 MCP 客户端都不重新批准，580 次兼容变更里 412 次拓宽了某个坐标，至少 76 次动到带权限的参数

你有没有过这种体验：给 agent 批过一个工具，过几天服务器发了新版本，调用还是那个名字，旧参数也都能用，客户端一声不响地换上了新 schema；事后才发现多出来一个 shell、一个 webhookUrl，或者本来封闭的对象被打开了，模型可以往里面塞你从没批过的字段。行业里把「旧调用仍然合法」叫做向后兼容。**问题是：兼容保证的是接口还能用，不保证你当初批出去的那份权限没有变大。**

这篇 **SchemaCaps: When a Compatible Tool Update Silently Widens an AI Agent's Authority** 把这个问题说死了，并且给了一条不靠字段名默认标签的再绑定规则。看完我的感受是：**最有信息量的不是又一个「检查 schema 有没有改」的开关，而是它把「接口兼容」和「授权有没有被放大」拆成两件事情，然后用真实 MCP 服务器的版本对和现成客户端，量出了这件事已经在发生、而客户端几乎都没问。**

## 核心摘要

作者把一次授权写成能力 $c$，绑在服务器身份、输入 schema 的摘要、以及一份由客户端维护的角色清单上。schema 变迁 $S\to S'$ 向后兼容，当且仅当旧调用的合法集合仍被新 schema 包含；但它是否放大授权，要看权威坐标上的有效值投影：非放大要求 $\pi_K[\![S']\!]\subseteq\pi_K[\![S]\!]$。坐标包括已声明路径，以及每个对象上「未声明字段」这个额外坐标；清单里没标成 inert 的路径，一律按带权限处理，没有清单时整份 schema 都按带权限处理，所以默认规则不信任任何字段名。再绑定只在每一步检查都通过时静默换绑，否则挂起工具，请授权人批准这个版本、收紧策略，或拒绝。证据分四层：117 行无公理的 Coq 证明组合性；48 个回归测试和一个可精确枚举的对照基准（审稿版本曾把 27 次放大变更静默换绑，现已修好）；一个插在 stdio 客户端和服务器之间的代理原型；以及对 39 个公开 MCP 服务器、604 个发行版的试点。试点里 1,197 次 schema 变更中有 580 次兼容，其中 412 次拓宽了某个坐标，词法标注器标出 84 次动到带权限参数，作者双人标注裁定至少 76 次（84 里确认 66，另补 10 个漏掉的）。在已有工具上，这条规则会触发 645 次重新批准，钉死输入 schema 是 1,197 次（连描述一起钉是 2,004），只问兼容性是 617 次。作者调查了 8 个 MCP 客户端和扫描器，能判定的都不会在 schema 拓宽时重新批准（两个产品只看了文档，无法确定）。schema 完全不变、只改背后行为，任何规则都挡不住。这篇的价值定位是：**一条针对「工具定义更新时授权有没有变大」的客户端再绑定规则，加上对现成 MCP 生态的测量；它不试图证明服务器行为没有偷偷改变。**

## 🎯 为什么这件事值得写

MCP 服务器是普通软件包，隔几天就发版，会话中途也可以宣布工具列表变了。用户按工具名批过一次，之后的 schema 往往被 SDK 静默交给模型。作者举了一个真实例子：Desktop Commander 0.1.34 的 `execute_command` 只收 `command` 和 `timeout_ms`，对象拒收其它字段；0.1.35 多了一个任意字符串的 `shell`。旧调用全部仍然合法，兼容性上看什么都没变。可是你当初针对某一种解释器写的 `command` 策略，在模型自己能挑解释器之后，已经不再描述「可以跑什么」。

有些参数带着权限：shell、webhookUrl、目标项目，因为它们的值决定了动谁、数据去哪、以什么方式执行；limit、分页游标通常不是。现成客户端问的几乎都是「定义改没改」或「旧调用还能不能过」，不是「授权有没有变大」。Vercel AI SDK 的漂移检查是可选的，且任何改动都报警；mcp-scan 一度只钉描述的 MD5，纯 schema 拓宽不会响。

作者的命题很明确：**一次授权要在 schema 变更后继续有效，只有当变更在所有可见的、带权限的坐标上不引入新的有效值；这件事可以保守地用 schema 包含来判定，并且只要把未标注坐标都当作带权限，就可以不信任任何字段名标签。** 更简单的规则也有：一切都钉死，每次改都再问；或者只问不兼容。论文要量的是这几条规则各要问多少次、各会漏掉什么。

## 🏗️ 机制：兼容不是授权，再绑定只在不放大时静默通过

### 能力和有效值

授权人把调用工具 $t$ 的权利交给 agent，客户端拦下每一次调用。能力记为 $c=(\mathrm{id}_{srv},t,h_S,h_A,U,P)$：服务器身份（启动命令摘要和报告名）、绑定 schema 的 SHA-256、角色清单条目的摘要、已经见过的坐标及其角色、以及对有效权限值的策略 $P$。调用 $x$ 只有落在 $S$ 接受的值里、并且 $P$ 在有效值上成立时才放行。

参数可以省略。路径 $a$ 的有效值 $\mathrm{eff}_S(x)_a$ 是实参，否则是声明的默认值，再否则是 $\bot$（「由服务器决定」）。$\bot$、`null` 和空字符串是三件不同的事。服务器上配置出来、计算出来的默认值在 schema 里看不见，一律算 $\bot$。

坐标是已声明路径，再加上每个对象一个「未声明字段」坐标 $\star_o$。带不带权限是工具语义上的事，记在客户端的版本化清单里，不由字段名决定。清单没列的路径视为未知，按带权限处理；没有清单时整份都未知，规则就变成不看标签。论文另外做了一个只按字段名模式判断的词法标注器，用来和人工判断对比，它不是默认规则。

对手模型覆盖诚实但粗心的功能拓宽、一步 rug-pull、以及把字段洗进被打开的对象。它不覆盖客户端被攻破，也不覆盖跨客户端的说法不一致（那需要透明度日志）。

### 两轴交叉

$S\to S'$ 兼容当且仅当 $[\![S]\!]\subseteq[\![S']\!]$。给封闭对象加字段是兼容的，却把该路径的有效值从 $\{\bot\}$ 扩到一个值域，也就是 Desktop Commander 那种情况；打开一个对象会把 $\star_o$ 扩到策略根本叫不出名的字段；新增必填字段会打破旧调用，同时也可能放大。兼容问的是接口，放大问的是授权。

非放大的定义是权威坐标集合 $K$ 上的联合投影包含。当旧 schema 里没有关联兄弟字段的关键字（anyOf、oneOf、dependent* 等）时，它可以落到逐坐标检查；否则回答「未知」，规则选择提问，因为只看边际会不健全。JSON Schema 的包含一般不可判定，作者用 jsonsubschema，失败当作未知；它本身也不是处处健全（例如无约束 boolean 对 enum/const 收窄会错说「是」）。检查器会改写这类 boolean，并用有界、固定种子的反例搜索（60 次抽样、2 秒）把「是」守住，这是纵深防御，不是证明。

再绑定算法的要点是：服务器身份变了就整份挂起；清单把某个已见坐标改成 inert 就挂起；工具提示从只读放宽、或标成破坏性/开放世界，也挂起；只改描述或标题则直接通过。新坐标出现在封闭对象上、对象被打开、字段变为可选、新接受 null、默认值改了、必填或带默认的字段被删、声明超出了原来 typed additionalProperties 的范围，都要提问。不兼容但只收窄的变更可以静默换绑：旧调用可能会失败，但授权没有变大。命题是：角色固定、每一步都静默换绑时，最终授权的有效值不会超出最初那一步。

Coq 开发 117 行，没有公理也没有 admit，机械化了定义、引理、链条命题，以及在「服务器效果不超过授权元组所允许范围」这一保真下的推论；隐藏的行为变化会打破这个保真假设。逐步包含来自检查器，检查器是测过的，不是验证过的。

## 🧪 关键证据或主结果

精确对照基准在一个有限论域的 JSON Schema 片段里枚举。926 次合法变更里，论域大于 15 万的 326 次被丢掉。剩下用于检查器的 600 对里，330 次是放大的。审稿时的规则曾把其中 27 次静默换绑（删掉必填或带默认的字段 24 次，在 typed additionalProperties 之外新声明 3 次），作者后来补进了算法第 7 步。修好后，无标签模式在该基准和事先记录的第二组种子上，都不再把任何放大变更静默换绑。旧 schema 关联兄弟字段的 135 次变更被标成未知并提问，而不是硬判。

代理原型加在客户端和 stdio 服务器之间：`tools/list` 时按选定规则处理变更，被挂起的工具对模型不可见，调用会被拒绝并带上原因；`tools/call` 时按绑定 schema 校验参数、在有效值上执行 $P$。每次决定追加一条签名、哈希链接的回执。带校验和策略时，每次调用大约多 0.47 ms，每次 list 多 1.1 ms；对变更做一次决定，无标签模式中位 22 ms，但 p99 到 2.6 秒、最坏 10.5 秒，主要花在检查器的 2 秒守护上，结果按 schema 摘要缓存。

演示用的是脚本化规划器，没有跑活模型，因为客户端的决定只依赖 list 和 call。兼容性放行所有拓宽；钉死能挡住，但良性改动也要问。无标签 SchemaCaps 挡住全部可见于 schema 的攻击，良性改动也要问；把 priority 标成 inert 后，良性改动可以静默通过；词法标注器会漏掉 `env` 这种枚举拓宽，因为名字不像权限字段。schema 不变、只改行为，所有规则都失败。六条手工核对过的真实拓宽（Desktop Commander 的 shell 和 isUrl、Firecrawl 的 webhookUrl、GitLab 的 target_project_id、Sentry 的 regionUrl、Notion 被打开的 parent）上，兼容性全部静默换绑，钉死和 SchemaCaps 全部挂起。

试点协议在 2026-09-29 15:25 UTC 抽取语料前做了哈希，但没有第三方托管，顺序是作者自证。语料覆盖官方参考服务器和下载量最高的 15 个第三方 npm stdio 服务器，窗口是 2025 年 1 月到 2026 年 9 月，每包最多 20 个稳定版；657 个抽样发行版里 604 个（91.9%、39 个包）响应了 `tools/list`，得到 565 对相邻版本。1,197 次变更里 580 次兼容；412 次在无标签意义下拓宽了坐标，词法「核心」84 次全部落在第三方层。双人标注原始一致率 84%，Cohen's $\kappa=0.67$，第三人裁定分歧；词法规则相对裁定标签的精确率 0.75、召回 0.60，漏掉了 saveScript、webhook.headers 和一种执行模式，所以「至少 76 次」是 66 加 10，不是上限。

代价对比很清楚。钉死整个定义要在已有工具上问 2,004 次，其中 807 次只是描述或标题改了；只钉输入 schema 问 1,197 次，收窄也要再问。兼容性问 617 次，但把 412 次兼容拓宽全放了。无标签 SchemaCaps 问 645 次，只比兼容性多 28 次（+4.5%），大约是只钉输入 schema 的一半，比全钉少 68%，并且按构造挡住那 412 次拓宽。加上 907 个新增工具（任何规则都当作新权限），总数分别是 2,911、1,524、1,552。检查有 20 次给出未知。作者写得很老实：这 645 次提问里有多少会被授权人觉得没必要，这里没有测，需要真实用户，否则 21 个月问 645 次仍然可能被习惯性点过。

2026-09-30 的客户端调查更扎眼。MCP TypeScript SDK、Python SDK 会把拓宽后的调用送出去；VS Code 按工具名派生标识，批准能活过变更；Vercel AI SDK 默认静默，可选漂移检测只报告「改了」；Claude Code 的文档是按名字匹配规则、列表变化就刷新；mcp-scan 0.4.2 只钉描述。Claude Desktop 和 Cursor 只看到文档，无法确定。能判定的产品里，没有一个会在 schema 拓宽时重新批准。

对有效性的威胁也写得直白：语料不是随机样本，拓宽集中在少数服务器，推不到 HTTP 服务器和其它生态；规划器是脚本，真实案例只在抽取的 schema 上重放，没有真正打到服务器；8 个产品里 4 个实际跑过，源码阅读和文档分类可能和真实行为有出入。标注者和裁定者都是作者。正文和代码在作者指导下由 Claude 起草，标注和核对由作者完成。

## 🔬 最有意思的部分

「加一个可选字段」为什么算放大，值得单独说清楚。封闭对象上原来没有这条路径，有效值只有 $\bot$；一旦出现，模型就可以填一个你从未授权过的值，即使所有旧调用仍然合法。打开对象更麻烦：未声明字段这个坐标会扩到策略叫不出名字的键，两步清洗可以把权限字段塞进一个看起来无害的开放对象里。规则把这些和「字段新接受 null」「必填或带默认的字段被删（有效值变成 $\bot$）」放在同一张要提问的清单里，是因为它看的是有效值，不是表面兼容。

反过来说，钉死也不是没有代价。服务器可以把行为变化和一次收窄、或一次只改描述配在一起：SchemaCaps 会静默放行，钉死会再问。这就是它比钉死便宜的价钱。一条更简单的「只要新调用集合是旧的子集就换绑」会问 693 次，却会静默放行 22 次 SchemaCaps 会提问的变更（其中 7 次它判为放大，15 次它判不了），因为它看不见有效值。

词法标注器看起来能少问（413 对 645），但精确率 0.75、召回 0.60，会把 `env` 这种执行模式漏掉。所以默认必须是无标签的：宁可把未知坐标都当作带权限，也不要把安全建立在字段名叫什么上。

## 🤔 我的判断

定位：**授权接口上的一条可执行再绑定规则，加上对 MCP 生态的测量。** 形式部分证明的是组合性，不是检查器本身；经验部分证明拓宽已经存在、现成客户端基本不问，并不估计全生态发生率。

亮点三条：

- **把「旧调用还能不能过」和「授权有没有变大」分开。** 这是这篇真正的问题贡献。兼容性工具、钉死描述、按名字的批准列表，答的都不是这个问题。
- **默认不信任字段名，用包含关系做保守判定，并把自己检查器的盲点写出来。** 审稿版本静默换绑过 27 次放大变更，作者修了，还用差分预言机在试点的静默换绑上跑了五万多次生成调用、零个反例。这种写法比「我们有一条形式化规则」可信得多。
- **代价数字很可用。** 645 对 617 对 1,197 对 2,004，让「是不是该上这条规则」变成可以讨论的工程取舍，而不是原则之争；客户端调查则说明这不是假想题。

问题与局限：

- **挡不住 schema 不变的行为变化**，作者反复强调，这是构造上的边界。
- 语料偏官方和头部 npm stdio 服务器，拓宽还集中在少数包；HTTP、要登录才能 list 的服务器不在范围内。
- 演示没有活模型，真实案例没有真正执行服务器。
- 检查器是测过、守过的，不是验证过的；最坏决策可能到 10 秒，调用在此期间仍绑在旧 schema 上。
- 645 次提问会不会被习惯性点过，没有用户研究。

对工程的直接启发：

1. **MCP 客户端不要只在工具名或「旧调用是否仍合法」上做批准缓存。** 输入 schema 相对上次批准发生拓宽，就应该重新问，至少对带权限的坐标问。
2. **不要用字段名当权限标签。** 词法规则会漏执行模式和 webhook 头；没有清单时，把未声明字段和未知路径都当作带权限，是更安全的默认。
3. **钉死一切能换绝对安全，但 21 个月对已有工具问两千次，其中八百次只是改了描述。** 如果要降低提问疲劳，优先忽略纯描述变化，对有效值拓宽提问，而不是反过来。
4. **代理可以做在客户端和服务器之间，不必改模型。** 挂起的工具对模型不可见、调用拒绝带原因、决定写成哈希链接回执，这三项可以直接抄。
5. **评估「工具定义完整性」时，要把窄化、拓宽、只改描述、以及同 schema 换行为分开报。** 只报「有没有检测到变更」，会把该问的和不该问的混在一起。

一句话：旧调用还能用，并不表示你批出去的权限还是原来那么大；在 MCP 这种工具定义会自己演进的协议里，客户端该问的是授权有没有被放大，而不是接口还兼不兼容。
