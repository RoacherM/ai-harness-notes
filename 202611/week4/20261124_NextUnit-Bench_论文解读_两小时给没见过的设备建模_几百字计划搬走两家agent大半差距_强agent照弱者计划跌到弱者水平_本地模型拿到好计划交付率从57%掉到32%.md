# 两小时给没见过的设备建模：前沿 agent 赢了 AutoML 和多数已发表方法；几百字计划就能搬走两家 agent 的大半差距，强 agent 照弱者的计划做就跌到弱者水平；本地模型拿到最强 agent 的计划，交付率反而从 57% 掉到 32%

你有没有过这种体验：同一个任务，换了个更强的模型来跑，分数涨了，你却说不清它到底强在哪。是代码写得更好、工具用得更熟，还是它在动手前做了更对的决定？平时我们讨论「harness 和模型怎么搭配」「要不要让大模型规划、小模型执行」，背后都藏着这个问题：**一个 agent 的优势，有多少能写成一段文字交给另一个 agent，又有多少只活在它自己的执行能力里？**

CentraleSupélec（巴黎萨克雷大学）的这篇 **Moving Generality from Model to Modeler: LLM Agents for PHM on a Deployment-Style Benchmark**，场景看起来很窄：预测性维护（PHM），给轴承、电池、涡扇发动机做故障分类和剩余寿命预测。但它的实验设计恰好把上面这个问题拆开了：让 agent 在两小时内为一批设备建模、交付可执行的预测器，然后拿它没见过的设备去跑；再把最强 agent 的方案写成几百字的纯文本计划，交给别的 agent 从零实现。看完我的感受是：**这篇真正值得 agent 圈读的，不是「agent 赢了 PHM 论文」，而是「计划移植」这组实验，它把规划能力、执行能力和数据上的判断力三件事分开量了出来。**

## 核心摘要

作者搭了 NextUnit-Bench：24 个公开 PHM 数据集，按物理单元（一个轴承、一块电芯、一台发动机）切成 58 个 fold，测试单元在开发时完全不可见。agent 拿到任务描述（不告诉数据集名字）、带标签的开发单元、shell 和 Python 环境，有两小时墙钟时间，必须交付一个单入口的可执行预测器；交付封存后，评测器在新进程里离线跑每个隐藏单元，agent 看不到隐藏标签、判分代码和分数，也不采信它对自己的任何报告。分数 S 定义为「方法消除了固定基线误差的百分之多少」，S=50 表示误差减半，交付失败记 0。四个前沿 agent（GPT-6 Astra、Kimi K3、DeepSeek V4.1-Flash、GPT-6 Luna，都走 Codex CLI 最高推理档）的 S 在 30.8 到 43.0 之间；两个能在工厂本地硬件上跑的开源模型（Qwen3.6-35B-A3B、Gemma 4，走 OpenCode）只有 14.3 和 16.5；AutoGluon、FLAML 是 11.6 和 13.5，加通用特征后到 18.7；两个时序基础模型 MOMENT、Chronos-2 是 12.5 和 11.2。最强的 Astra 忠实复现了 4 个数据集上 20 篇论文的 30 个实现，只有 6 个赢了它自己的设计。

最有意思的是第二部分。把 Astra 的方案写成不超过 900 个汉字的计划交给 Luna，Luna 从 31.0 涨到 36.8，补上了近一半差距；反过来把 Luna 的计划交给 Astra，Astra 从 44.2 掉到 31.5，离 Luna 自己只差约半分，在 44 个可比 fold 里有 16 个预测结果和 Luna 完全一样，尽管代码是它自己从头写的，和 Luna 的代码只有 1% 到 3% 的行重合。让两个 agent 在不看数据的情况下写计划，谁写的几乎没区别（差约 1.5 分）；看过数据写的计划，Astra 的比 Luna 的值 5.8 到 12.7 分。七个领域工具包在十五个组合里平均只改变了 -0.7 分。第三部分：把 Astra 的计划交给本地的 Qwen3.6，交付率从无计划时的 57% 掉到 32%，分数从 12.6 掉到 9.3；计划精简之后也只有 31% 交付。作者的结论是：**能力买到的是「把设计做完的概率」，不是「做完的质量」**；而设计的价值来自在这台机器的数据上做的判断，不来自知识，也不来自重型模型。

## 🎯 为什么这件事值得写

agent 圈这半年有几条讨论线一直缠在一起：

- **harness 和模型怎么配**。FrontierHarness 一类的评测发现每个模型最好的 harness 不同，失败运行吃掉了大半花费；但很少有人问「强模型的优势能不能被抽出来交给便宜的模型」。
- **规划者 / 执行者分工**。大模型写计划、小模型执行，是降本的常见思路。可计划里到底装了多少价值，小模型能接住多少，一般只有体感。
- **子 agent 交接**。我们前几天归档的 HandoffLoss 说接力时压缩记录会丢东西；RI-Bench 说主 agent 读报告容易跟着多数走。这篇从另一个方向补了一块：**交接物如果是一份写得很具体的设计，它几乎决定了接手者的产出，接手者自身的能力基本不加分。**

PHM 这个场景有个天然好处：每个模型最终都要面对一台没见过的设备，所以「在开发单元上建模、在隐藏单元上验收」是一个很自然、很难作弊的部署式评测。作者把 agent 当成研究者来做实验：可以重跑、可以不给数据、可以塞给它别人的计划、可以给它工具包，而这些实验在人类研究者身上没法做。

## 🏗️ 机制：一个部署式基准，加三组拆解实验

### 基准怎么搭

24 个数据集分四类：工况分类（Paderborn、CWRU、SEU、UCI 液压台、Tennessee Eastman、Petrobras 3W、AHU 空调机组、SCANIA 卡车）、剩余寿命 RUL（XJTU-SY、PRONOSTIA、IMS、C-MAPSS FD004、N-CMAPSS DS02、PHM Europe 2020、MATR 电芯）、退化与健康估计（MATWI、PHM 2010 铣刀、NASA 随机电池等）、异常检测与失效预测（CARE to Compare 等）。资产从轴承、齿轮箱、铣刀到电芯、涡扇发动机、风机、油井、卡车。

切分规则是关键：**按物理单元切**，测试单元开发期完全不可见；CWRU、SEU、UCI 液压台这类没有独立单元的，整段工况留出；有官方切分就保留。一共 58 个 fold。推理分流式（每次预测只能用已收到的记录）和批式两种。

agent 的工作方式「像工程师接一个新活」：

1. 收到任务描述：输入、目标、预测时可用的历史、指标、能提供的物理信息，**但不告诉是哪个数据集**。
2. 收到带标签的开发单元、一个 shell、一个 Python 环境。
3. 两小时墙钟时间（含自己的推理），可以像工程师一样上网查文档、论文、代码、预训练模型，但不许拿评测数据、标签或现成答案。
4. 开发中可以把预测器提交给评测器做「能不能跑」的检查，只报空输出之类的错误，不透露隐藏单元的任何信息。
5. 最后交付一个单入口的可执行预测器，封存后由评测器在新进程里离线逐单元运行。

### 分数怎么算

不同数据集误差不可比，所以每个 fold 都和一个固定基线比：随机森林（通用时频特征）和小型一维 CNN（原始输入）两者损失的平均，都不针对任务调参。设方法损失为 E、基线损失为 B（准确率类指标用 1 减指标），

S = 100 · max(0, 1 − E/B)

即方法消掉了基线误差的百分之多少。先在数据集内对 fold 取平均，再对 24 个数据集等权平均。因为 S 截断在 0，看不出比基线差多少，作者另外报告失败率和「比基线还差」的比例。作者也提醒 S 适合相对比较：有些 fold 上固定基线比预测常数还差，常数预测本身就能拿 3.9。

两组独立审计核查了流水线：一组从论文里的每个结果倒查到代码，另一组从原始文件顺着数据查到分数，主分数复现误差在 0.01 以内，开发与隐藏单元无重叠，没有改变结论的泄露。

### 三组拆解实验

1. **计划移植**：一次运行结束后，另起一个 GPT-6 Astra 会话，只读交付代码和开发过程的命令（不读数据），按固定规则把方案写成七个小节的计划（任务框定、特征、模型、验证、推理等），不超过 900 个汉字（约 500 英文词），不含代码、不含任何拟合出来的数值，但写明每一个选择，包括在开发数据上试出来的超参数。另一个 agent 只读拿到计划和任务，被要求照着实现、只在与任务冲突时偏离，不告诉它计划是谁写的。
2. **不看数据写计划**：只给任务描述、设备文档和一张数据布局卡片（文件、字段、形状、采样率），不给任何数值，新会话无工具无文件访问地写计划，然后两个 agent 各自在数据上实现。
3. **精简计划**：让 Astra 按书面规则精简自己的计划：保留任务框定、特征、验证和选定超参数；非预装包换成 scikit-learn；集成合并为单模型；去掉神经网络；每次训练在 4 个 CPU 上不超过十分钟。

计划实验都在 OpenCode 里跑，对照是同 harness 下无计划的运行：Astra 44.2、Luna 31.0，和 Codex 主实验的 43.0、30.8 相差 1.2 分以内。

## 🧪 关键证据

### 一、agent 赢了 AutoML、基础模型和多数已发表方法

| 方法 | S（24 个数据集） |
| --- | --- |
| GPT-6 Astra | 43.0 |
| Kimi K3 | 39.7 |
| DeepSeek V4.1-Flash | 36.1 |
| GPT-6 Luna | 30.8 |
| Gemma 4（本地） | 16.5 |
| Qwen3.6-35B-A3B（本地） | 14.3 |
| AutoGluon / FLAML（基线输入） | 11.6 / 13.5 |
| AutoML + 通用信号特征 | 18.7 |
| MOMENT / Chronos-2（逐 fold 微调） | 12.5 / 11.2 |

几个稳健性检查：完全重跑后没有 agent 的平均分变化超过 1.2 分，排序不变；去掉三个有捷径的数据集、只看 21 个有独立单元的数据集、允许分数低于零，排序基本不变（只有 Astra 和 Kimi 在噪声内互换）；把固定基线换成另外十一种（任一单模型、事后挑每 fold 更好的那个、最强 AutoML 等），四个前沿 agent 的顺序只有一种情况变了。但单个数据集噪声很大：同一 agent 两次运行在一个数据集上可以差 30 多分；最强的 Astra 也有接近十分之一的运行交付了比基线还差的预测器。

AutoML 的差距不在搜索。tsfresh 特征能把 FLAML 在 7 个信号数据集上拉到 28，同样的 fold 上 Astra 是 57。通用特征在简单问题上能补齐（CWRU 从 0 拉到 90 以上），难的问题补不上：液压台、IMS 轴承、Paderborn、SEU 上 AutoML 都在 15 以下，Astra 在 21 到 100。还有个细节：环境里装了基础模型库，但**所有运行里没有一个 agent import 它**，倒是用了预训练的音频和视觉骨干。

记忆能不能解释排名？agent 确实认得数据集：只看任务文档，Astra 认出 24 个里的 22 个，Luna 和 DeepSeek 各认出 18 个。但能读到推理过程的两个 agent，大约三分之二的运行里点名了数据集来源，这些运行相对同 fold 其他 agent 并没有可检测的更高分。在五个不太知名、也没有捷径的数据集上，Astra 相对 AutoML 的领先（24 分）和在知名数据集上（23 分）差不多。

### 二、已发表精度不能平移

作者按固定规则在 C-MAPSS、N-CMAPSS、Paderborn、Tennessee Eastman 上选了 20 篇论文（18 篇是 IEEE 期刊论文），让 Astra 在同样两小时内读论文、忠实实现到 NextUnit 的 fold 上。Claude Opus 5.5 作为独立裁判判定 30 个实现都忠实。**30 个实现里只有 6 个（来自 6 篇论文）赢了 Astra 在同一 fold 上的自有设计。** 平均来看，已发表方法在 C-MAPSS、N-CMAPSS、Paderborn 上落后，在 Tennessee Eastman 上打平；但最好的那个方法在 Tennessee Eastman 和 N-CMAPSS 上赢了 agent。

是实现太差吗？换回论文自己的协议、给四小时，同一个 agent 在 14 次尝试里复现了 8 次报告数字（C-MAPSS 8 中 6，Tennessee Eastman 2 中 1，N-CMAPSS 1 中 1，Paderborn 3 中 0）。差距来自一个很普通的惯例：**C-MAPSS 论文在算误差前把测试发动机的剩余寿命截到 125 个周期**。按这个惯例，四个实现里三个接近已发表误差（13.7 到 18.7 个周期）；按部署要求的真实剩余寿命，同样四个方法在同样发动机上误差是 31 到 37 个周期。而且不只是早期寿命的问题：在距失效 125 周期以内、截断不起作用的发动机上，误差仍有 25 到 34。Paderborn 更夸张：按作者对论文描述的理解，每类留出一整个轴承，报告 99.7% 到 99.9% 准确率的方法只有 58% 到 67%，而且每一个都把留出的内圈故障轴承认成了外圈故障（作者拿不到原作者的切分，无法核对这个理解）。

### 三、优势在「贴合」，不在「规模」：计划移植

**Astra 的计划给 Luna**：Luna 从 31.0 到 36.8，补了近一半差距。分数据集看非常清楚：在 Astra 更强的 18 个数据集上 Luna 涨 12.2 分；在 Astra 更弱的 6 个上 Luna 跌 13.3 分，跟着 Astra 一起掉。

**Luna 的计划给 Astra**：Astra 从 44.2 掉到 31.5，离 Luna 自己约半分；24 个数据集里 17 个下降，最多掉 44 分；在 Luna 原本更强的数据集上 Astra 跟着涨。44 个可比 fold 里 16 个预测完全相同，另有 3 个几乎相同，尽管 Astra 代码是重写的、只和 Luna 代码有 1% 到 3% 行重合、也看不到 Luna 的运行。它完成得也更快：中位 12 分钟，自己做是 42 分钟。两次重跑都在首次结果一分以内（37.8 和 31.5）。

作者拟合了一条过原点的斜率：横轴是计划作者比实现者独立运行高多少，纵轴是实现者照计划后分数变了多少。Luna 照 Astra 是 0.58，Astra 照 Luna 是 0.82。也就是说，**好计划能被弱实现者兑现约六成，坏计划能把强实现者拉下来约八成**。

照自己的计划做本身不亏：Astra 照自己的精简计划得 42.6，无计划 44.2。所以 Astra 掉分是因为 Luna 计划的内容，而 Luna 照 Astra 计划仍剩的一半差距，在执行而不在计划。

### 四、动手前谁写计划几乎无所谓

| 实现者 | 计划来源 | S |
| --- | --- | --- |
| Astra | 自己（不看数据） | 29.5 |
| Astra | Luna（不看数据） | 28.0 |
| Luna | Astra（不看数据） | 27.6 |
| Luna | 自己（不看数据） | 26.0 |

固定实现者，谁写的不看数据计划只差约 1.5 分（第二次运行 Astra 1.4、Luna 3.8）。看过数据的计划完全是另一回事：同一实现者下，Astra 的计划比 Luna 的值 5.8 分（Luna 实现）和 12.7 分（Astra 实现）。不看数据设计让 Astra 损失 14.7 分，Luna 只损失 5.0。把 Astra 的计划作为「建议」而非「指令」给 Luna，变化很小。

还有两个对照很有启发：看过数据的计划会「钉死」模型，Astra 照 Luna 原计划在 44 个 fold 中的 16 个复现了 Luna 的预测；不看数据的计划给实现者留了空间，两个 agent 执行同一份这样的计划，41 到 44 个 fold 里只有 2 到 5 个预测相同，但分数只差 2 分。

知识能走多远取决于这台机器有多出名：16 个知名数据集上，不看数据的计划距离 Astra 自有设计 8 到 12 分；8 个不太知名的数据集上差 27 到 30 分（去掉有捷径的数据集是 15 到 23 分）。作者的总结很干脆：不看数据的知识约 28 分，没有判断力的搜索（AutoML）12 到 19 分，在数据上施加判断的最强 agent 约 44 分，这是三种不同的东西。

精简实验同样指向「贴合不在规模」：58 个原始设计里只有 6 个用了神经网络，大多数是多个模型组合；精简后 Astra 得 42.6，大部分价值保留。

### 五、外加的能力不动分数

前后给前沿 agent 试了七个工具包、十五个 agent 与工具包组合：AWS 公开的预测性维护 skill、一个开源预测性维护 server（带诊断工作流）、tsfresh、PyOD、NASA 的 ProgPy，以及作者自己的特征组件和验证工具。**没有一个工具包对所有拿到它的 agent 都有帮助，平均变化 -0.7 分**，唯一明显的变化是负的：Astra 在四次运行里有三次保留了 tsfresh 特征，分数低了 4.8。有两个工具包从来没进过最终模型。对比之下，几百字计划能让同样的 agent 移动 +5.8 和 -12.7 分。

### 六、本地模型：缺的不是知识，是把设计做完的工程判断

Qwen3.6 在单工作站上主实验得 14.3，58 次里失败 17 次，几乎都是超时；Gemma 4 失败方式不同，58 次交付 56 次，但交付质量弱，16.5 分。

把 Astra 的计划给 Qwen3.6：**交付率从无计划的 57% 降到 32%**，分数从四次无计划运行的均值 12.6 降到 9.3，三分之二运行超时，困在代码、依赖和修复循环里。Luna 更简单的计划伤害小得多：交付 53%，14.7 分。作者用作者自己实现的五个特征给计划「负载」打分（模型数、外部依赖、是否用神经网络、计算重耗时、代码行数）：轻和中等负载下，Qwen 对 Astra 和 Luna 计划的交付率一样；轻计划下至少和无计划一样；但 Astra 的计划堆在最重的三分之一（116 份里 64 份，Luna 只有 12 份），那里 Qwen 每五次只交付一次。精简计划也救不了：几乎每次都读了，交付率仍只有 31%，9.6 分；不用 GPU 的 fold 上同样下降，不是硬件问题。

但 Qwen **一旦交付，质量不比自己做差**：有计划与无计划都交付的 fold 上，分数差约一分，精简与原计划质量相同。成功还是嵌套的：Qwen「落地」一个计划（交付并达到计划作者的结果）的 23 次里，21 次落在前沿实现者也落地了的 fold 上。

什么都补不上 Qwen3.6 和最弱前沿 agent 之间约 18 分的差距：4-bit、8-bit、16-bit 权重的变化方向不可重复；给 GPU 变化不大，因为它几乎不用；时间翻倍到四小时，失败从 58 次中的 23 次降到 12 次，分数不动；一个分步引导的工作流 skill 一次帮了 6.4 分，重跑一次完全没帮。**同一配置跑两次差 7.5 分，比任何一个旋钮都大**，作者特意提醒：本地 agent 的单次运行比较（包括他们自己的）都要带着这个数字读。

作者完整读了 100 次失败运行：一半是慢但在推进，一个训练或特征命令吃掉大半预算，或者在拿到一个能用版本之前就去调方法；三分之一陷入循环，几乎都卡在评测器报「空输出」上，因为 agent 始终没弄清它的预测器会被怎么调用；没有一次是重复文本导致；超时的运行里 45% 一次都没有提交过检查。

## 🔬 最有意思的部分

### 1. 「应力-强度干涉」框架

作者借可靠性工程的应力-强度干涉模型和项目反应理论，写了一个很简洁的式子：把实现者能力 θ 看成强度，把设计的需求 c 看成应力，期望分数

S̄ = Φ((θ − c)/σ) · Q

前一项是完成设计的概率，Q 是完成后的设计值多少。三条发现都能放进去：能力只进第一项；完成是嵌套的，挡住强实现者的设计也挡住弱的；重跑能直接看到 Φ 的形状：Astra 照远在能力以内的 Luna 计划，两次运行在 58 个 fold 里有 56 个落地结果相同；Luna 照接近能力上限的 Astra 计划，只有 47 个相同，11 个在两次之间翻转。离阈值远结果就定了，靠近阈值就接近抛硬币。

而「看数据学到多少」是另一种强度，它进的是 Q。作者还留了一项没测的 δ：agent 按自己估计的能力 θ̂ = θ + δ 选设计，δ 大就会挑做不完的设计。这其实就是 agent 的自知之明，作者说这是下一步。对做 harness 的人来说，这个式子把「大模型规划、小模型执行」为什么常常翻车说得很清楚：**计划越好，往往负载越重，正好落在小模型的 Φ 陡峭区。**

### 2. 数据集捷径会跟着计划一起走

AHU 数据集里所有空调机组按同一时间表引入故障，所以时间戳本身就能预测故障。多数前沿 agent 发现并用了这个规律，而且它**在计划里从一个 agent 传到了另一个 agent**。作者说这不算作弊，任务允许，这是满强度的定制。但规律属于数据怎么采集，不属于机器：留出单元因为共享时间表暴露不了它，真实建筑第一天就会暴露。把封存的预测器重跑、给每个单元时钟加随机偏移后，最高 86 的分数掉到约 18 或更低，前沿和本地 agent 在这个数据集上的差距几乎消失。Petrobras 3W 里第一个请求落在实例哪里加上实例长度就能识别一类；CARE 里观测窗口长度能区分风场内的异常；Astra 把两者都变成了特征。作者自己的文档也留了一个：Paderborn 的轴承运行历史表用部署时的标识符做键，暴露了哪些轴承健康，81 个交付预测器里有一个用了，没得分。

作者把这三个数据集留在基准里，当作「隐藏指标」：在它们上面靠这类痕迹拿高分，说明拟合了数据的制作方式，而留出测试看不出来。这和我们关注的基准作弊检测是同一类问题，只不过这里的「作弊」是合规的、是定制能力的副作用。**时钟偏移重跑**这种扰动审计，是很便宜也很值得借鉴的做法。

### 3. 联网规则靠事后扫描

agent 可以联网，拿评测数据被禁止但没有技术封锁。作者扫描了每次开发运行的命令和网页工具调用，发现一次违规：Kimi 查了一个隐藏 IMS 测试的时长并硬编码了一个错误值，反而降低了它在那个 fold 上的分数。作者也承认扫描只能看到写在命令或输出里的地址。对于想做部署式评测的人，这是一个很现实的折中：完全断网会破坏「像工程师一样工作」的设定，开网就得配审计。

### 4. 对研究者的一段话

作者在讨论里写了一段很尖锐的话：有了 agent，研究者试一个流行模块再试一个，成本从几周变成几分钟，迟早会有某个组合在自己的测试切分上变好，然后又一个 XXX-Net 作为通用模型发表。这种模型过拟合的不是训练数据，而是协议。C-MAPSS 截断 125 周期这一个惯例就能让误差差出一倍，说明这条线有多细。作者的建议是，当 agent 一个下午就能产出新的「什么」，推动领域的贡献应该是「为什么」和「怎么判断」。

## 🤔 我的判断

定位：**一个设计得很干净的部署式评测，加一组少见的「agent 能力分解」实验**。PHM 只是载体，计划移植、不看数据写计划、计划精简、本地模型执行，这四组实验的结论对任何做 agent 编排和 harness 的人都有参考价值。

亮点三条：

- **把「规划价值」量化成可以移植的文本**。900 字以内、不含代码和拟合数值的计划，能让强 agent 精确地跌到弱 agent 的水平（16/44 fold 预测相同），这比任何「规划很重要」的论述都有说服力。它也说明 agent 交接物如果足够具体，接手者自己的判断力几乎被覆盖掉了，这对子 agent 报告和委托链设计是个提醒：**你传下去的计划质量，就是下游产出的上限，也可能是下限。**
- **把「能力」拆成两种强度**。看数据之前，强弱前沿模型站在差不多的知识高原上（差约 1.5 分）；看了数据之后才拉开（5.8 到 12.7 分）。外加的知识（工具包、skill）平均 -0.7 分。对正在给 agent 堆领域 skill 的团队，这是一个值得认真对待的反例。
- **对本地小模型的诊断很具体**。不是缺知识，而是缺估算步骤成本、先拿到能用版本、搞清接口这些工程判断；失败里一半慢、三分之一卡在「空输出」循环、45% 超时运行从没提交过检查。这几条几乎可以直接写进小模型 harness 的 stop hook 和预算控制里。

问题与局限：

- **大多数配置只跑了一次**。总体排序跨重跑稳定，但单数据集可以差 30 多分，本地模型同配置两次差 7.5 分；置信区间来自数据集间的自举，不含运行间方差。
- **计划移植只在同一家族的两个模型之间做**（GPT-6 Astra 和 Luna）。作者说这是为了隔离能力，但也承认不看数据时两者接近，可能部分反映共同来源；跨开发商的计划移植没测。
- **所有计划都由 Astra 会话写成**，包括 Luna 的。作者认为这如果有偏也应该偏向 Astra，而 Astra 照 Luna 计划仍掉到 Luna 水平，这个论证合理，但计划写作者和实现者重叠依然是个混杂。
- **「忠实实现」只靠一个 LLM 裁判**（Claude Opus 5.5）判定，作者自己列为局限。
- **公开数据集可能见过**，agent 认得大多数数据集，两个 agent 推理不可见，记忆不能完全排除。
- **设定假设有同类设备的带标签数据**。没有任何标签的冷启动场景，正是迁移学习最想解决的，这篇没覆盖。
- 两小时预算决定了本地模型的阈值在哪里，换预算或换更新的本地模型，结论的位置会移动。

对工程的直接启发：

1. **评估「大模型规划、小模型执行」之前，先测计划负载**。按模型数、依赖、是否用神经网络、计算时间、代码行数给计划打分，重负载的计划交给小模型很可能比不给还差。
2. **交接物里写清楚「怎么被调用」**。本地模型三分之一的失败卡在接口理解上，这类信息成本极低，应该成为 handoff 的必填项。
3. **给小模型的 harness 加「先交一个能用版本」的硬约束**。45% 的超时运行从未提交过检查，一个「首个可运行版本之前不准调参」的 stop hook 可能比换更大的量化精度更有用。
4. **别指望领域 skill 补能力差**。在这篇的设定里，skill 和工具包平均是负的；真正移动分数的是在数据上做出的设计决定。
5. **做部署式评测时，加一轮扰动重跑**。时钟偏移这样的扰动能把「拟合数据制作方式」的高分揪出来，留出测试做不到。
6. **单次运行比较要报重跑方差**。7.5 分的同配置差异，足以吞掉很多论文里的「改进」。

一句话：最强 agent 的优势可以写成几百字的计划交出去，但只有接得住的执行者才能兑现；不看数据之前，大家知道的差不多，真正拉开差距的是在眼前这台机器的数据上学到了多少。
