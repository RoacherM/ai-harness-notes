# MCP agent 的训练环境该先造数据库还是先看真实调用？ToolSpace 用确定性规则从相邻调用里挖工具依赖，35B-A3B 七项均值从 23.0 涨到 41.0，744B 追平 Claude Opus 5

你有没有过这种体验：为了训练一个会用 MCP 工具的 agent，先让 LLM 编一个「电商客服」场景，再编数据库，再从数据库反推出一组工具和任务。结果工具名字很像回事，参数语义却和真实的 Gmail、Google Drive、Slack 对不上；任务也基本困在一个环境里，十来步就做完，和真实工作里「查邮件、找附件、改表格、发 Slack」的跨服务长链差得很远。

这就是 **MCP 环境扩展** 的主流做法，作者称之为 data-centric：**先造数据和场景，再派生工具和任务。** 问题是工具成了数据的附属品，工具之间的连接也常常靠 LLM 判断「这两个看起来能接上」。

人大、复旦、上交团队的 **ToolSpace** 把方向倒了过来：先从真实 MCP 服务和公开 agent 语料的执行轨迹里收集工具调用，用 **不调用 LLM 的确定性规则** 在相邻调用之间挖出数据、状态、重试三类依赖，建成一张带权工具图；只给需要持久状态的环境按需造数据库；再在图上做状态感知随机游走、失败就回滚，每条走通的链反向写成不含工具名的任务，配上一套从初始状态重放必须全过的断言。看完我的感受是：**这篇最该抄的是那行消融：同一套流水线，把规则挖边换成 LLM 判边，AutomationBench 从 45.8 掉到 37.8，τ3-Bench Banking 从 34.0 掉到 26.7。**

## 核心摘要

ToolSpace 是一个 tool-centric 的跨环境 agent 数据合成框架，分三层。第一层是 **工具图**：节点是真实工具调用（工具名、参数 schema、返回 schema、可选的环境状态快照），边只来自相邻调用，类型分三种：数据依赖（后一次调用的参数可追溯到前一次的输出）、状态依赖（前一次修改了某个环境对象，后一次读取或继续修改同一对象）、重试依赖（前一次报错、换工具后成功）；边权取转移频率 $w=N_{ij}/N_i$，删去低频边，数据边额外要求参数溯源，防止 `limit=10` 这类常量造成假连接。最终 77,760 个节点，来自 2,042 个工具，平均出度 2.3、最大 56，边类型中数据 69%、状态 25%、重试 6%。第二层是 **按需环境**：按连接密度把图聚成 804 个环境，只有 181 个（22.5%）含增删改工具的操作型环境才合成数据库；状态查询型环境用真实工具返回的部分快照初始化 $s_0$；无状态环境（如网页搜索）直接重放缓存的工具返回。第三层是 **可验证任务合成**：在图上做状态感知随机游走，只在「输入能从历史返回或当前快照填上」的邻居里按边权采样，失败或状态不一致就恢复到 $s_{t-1}$ 重采；走通的链由 LLM 写成不含工具名和调用顺序的任务 $q$，并生成三类断言（终态、关键中间快照、返回字段），只有从 $s_0$ 重放全部通过才保留。用 Kimi K3 做老师，得到 34,376 条 SFT 轨迹和 653 条 RL 样本。Qwen3.6-35B-A3B 在七个长程工具基准上的均值从 23.0 到 41.0（SFT），加 RL 到 43.2；GLM 5.2 744B 从 44.6 到 56.6，和 Claude Opus 5 的 56.6 持平，高于老师 K3 的 49.7。作者还用同一套图把 AutomationBench 和 τ3-Bench Banking 升级成 Pro 版，前沿模型在 Pro 上普遍大幅掉分。它的价值是把「工具之间怎么连」从 LLM 的判断换成了执行证据，并把每个合成样本都绑上可重放的断言门。

## 🎯 为什么这件事值得写

MCP 工具使用训练数据这条线，过去半年大致是「EnvScaler、AWM、Agent-World 一类先造环境再派生工具」的天下。ToolSpace 指出了这一类方法的三个结构性问题：

1. **反向合成的工具和真实工具语义不匹配。** 工具是从合成数据库派生出来的，名字和参数看起来合理，但和真实服务的语义有偏差。
2. **工具图缺少执行证据。** 已有的图方法大多靠 schema 或 LLM 判断两个工具「能不能接」，而不是看真实执行中它们是否真的前后衔接。
3. **任务被困在单环境复杂度里。** 7 到 8B 的环境扩展基线在 AutomationBench、τ3-Bench Banking、JobBench、Harvey LAB 这类跨环境长程基准上都不到 10 分，作者的说法是：单环境数据只纠正了调用的格式，没有教会跨环境组合。

对做 harness 的人，这篇有两处直接对口：一是 **确定性规则代替 LLM 做结构判断**，和我们一直关注的「LLM 审完之后加一道代码门」是同一种直觉；二是 **每个样本都要过可执行断言**，验证不靠参考答案，而靠从初始状态重放之后检查终态、中间快照和返回字段。

## 🏗️ 机制：挖边、按需造环境、游走加回放

### 三类边，全靠规则

| 边类型 | 规则 | 占比 |
| --- | --- | --- |
| 数据依赖 | 后一次调用的参数可追溯到前一次调用的输出（参数溯源，排除 `limit=10` 一类公共常量） | 69% |
| 状态依赖 | 前一次修改了某个环境对象，后一次读取或继续修改同一对象，而不是碰巧取值相等 | 25% |
| 重试依赖 | 前一次返回错误，轨迹换了工具，下一次成功；错误被当成可恢复的观测保留 | 6% |

边权就是转移频率：

$$
w(v_i,v_j)=\frac{N_{ij}}{N_i}
$$

其中 $N_i$ 是节点 $v_i$ 在执行记录中出现的次数，$N_{ij}$ 是 $v_j$ 紧跟 $v_i$ 出现的次数。低频边删除。作者强调：这样得到的图记录的是「执行时工具怎么转移」，而不是「有哪些工具可用」。原始材料是超过 20 万条 agent 与工具的交互轨迹，在任务级和轨迹级都做了去污染：任务、调用序列或初始状态与任一评测集重叠的轨迹一律排除。

### 只在需要的地方造数据库

| 环境类型 | 数量 | 处理方式 |
| --- | --- | --- |
| 操作型（含增删改工具） | 181（22.5%） | 按 Agent-World 的做法由研究 agent 收集并对齐网页数据，迭代扩充，过单元测试和状态转移检查才保留 |
| 状态查询型 | 包含在 623 个非操作型中 | 用 `google_drive.files.list`、`gmail.users.messages.get` 这类工具的真实返回作锚点初始化 $s_0$ |
| 无状态型 | 包含在 623 个非操作型中 | 网页搜索、固定索引查询等，重放时直接用缓存的工具返回，不打线上 API |

操作型工具一共 453 个，占 2,042 个工具的 22.2%。作者用合成文件数做成本代理：在抽样的 500 个环境上和 data-centric 方式比，需要合成的文件从 2,724 个降到 1,218 个，少 55.3%。

### 状态感知随机游走 + 回滚

```text
输入：环境数 K、链长 L
从绑定了数据库 D_k 和 s0 的工具节点出发
循环：
  候选邻居 = 当前节点的出边邻居中，满足
     依赖可达（输入能从历史返回或 s_t 填上）
     状态前置条件成立
     参数可溯源
  按边权 P(v'|v) ∝ w(v,v') 在候选里采样，执行，更新 s_t
  若执行失败，或执行后状态与所走边的数据/状态关系不一致：
     丢弃这一步，恢复 s_{t-1}，在 v_{t-1} 的邻居里重采（rollback）
直到长度达到 L 且覆盖 K 个环境
反向合成：LLM 把链写成任务 q（不含工具名和调用顺序）
         生成断言 V = V_state ∪ V_trace ∪ V_out
保留条件：从 s0 重放，全部断言通过
```

论文的交互演示里，一条游走跨 6 个环境、28 次调用，经过 2 次回滚，最后通过重放验证被保留。RL 用的奖励也是执行验证：完整轨迹通过断言脚本得 1，否则 0。

### 训练配置

| 项 | 设置 |
| --- | --- |
| 老师 | Kimi K3（同时负责轨迹生成和反向任务合成） |
| SFT 数据 | 34,376 条；其中 21,385 条至少 5 次调用，平均 18.86 次（最多 209），平均跨 2.29 个环境（最多 22），多环境占比不低于 66.2% |
| 轨迹长度 | 平均 30,466 token，最长 855,386 |
| RL 数据 | 653 条，用 35B 模型做 Pass@16 筛选，只留 16 次里对 1 到 2 次的 |
| RL | GRPO，clip 0.8 / 1.28，48 步，lr 2e-6，batch 256，group 16，staleness 4 |
| 基座 | Qwen3-8B、Qwen3.6-35B-A3B、GLM-5.2-744B-A40B |

## 🧪 关键证据

### 主结果：七个长程工具基准

基准为 AutomationBench、SkillsBench、JobBench、τ3-Bench Banking、BFCL V4、Harvey LAB、OfficeQA Pro。论文的结果来源规则是：优先官方榜单，其次是官方协议下的厂商自报，开源模型都没有时才用官方 harness 本地复现，三次平均。

| 模型 | 七项均值 |
| --- | --- |
| Claude Opus 5 | 56.6 |
| GPT 5.6 Sol | 48.9 |
| GLM 5.3 | 53.8 |
| Kimi K3（老师） | 49.7 |
| GLM 5.2（744B 基座） | 44.6 |
| **ToolSpace-744B-A40B** | **56.6** |
| Qwen3.6-35B-A3B（基座） | 23.0 |
| ToolSpace-35B-A3B（SFT） | 41.0 |
| ToolSpace-35B-A3B（SFT + RL） | 43.2 |

35B 上 AutomationBench 从 8.2 涨到 45.8，七项全部超过基座；RL 再加 2.2 点均值，最大增益在 τ3-Bench Banking（34.0 到 42.3）。8B 档 ToolSpace-8B 均值 19.6，加 RL 后 20.7，同档最好的环境扩展基线 Agent-Reflex-8B 为 9.2。作者用「744B 超过老师 K3」来论证这不是简单的能力蒸馏，而是学到了可迁移的工具组合结构。

### 组件消融（35B，SFT）

| 设置 | AutomationBench | SkillsBench | BFCL V4 | τ3-Bench Banking | OfficeQA Pro |
| --- | --- | --- | --- | --- | --- |
| 完整 ToolSpace | 45.8 | 42.4 | 74.3 | 34.0 | 48.9 |
| LLM 判边代替规则挖边 | 37.8 | 36.4 | 66.9 | 26.7 | 43.5 |
| 去掉状态边 | 36.5 | 38.0 | 70.1 | 21.5 | 44.0 |
| 去掉数据边 | 38.2 | 37.5 | 62.4 | 29.8 | 40.6 |
| 均匀游走代替按边权游走 | 39.6 | 38.9 | 69.8 | 28.4 | 45.1 |
| 去掉回滚 | 41.0 | 39.8 | 71.5 | 30.1 | 46.3 |
| 去掉重试边 | 43.9 | 41.2 | 72.8 | 32.6 | 47.9 |

几个读法：状态边对 τ3-Bench Banking 最关键（34.0 到 21.5），数据边对 BFCL V4 最关键（74.3 到 62.4）；只占 6% 的重试边去掉后各项只掉 1 到 2 点左右；LLM 判边在五项上都掉 5 到 8 点。

### 规模与相关性

- **环境规模**：环境比例从 1/16 到 1/8，AutomationBench 从 9.2 跳到 33.8；τ3-Bench Banking 的最大一跳直到用上全部环境才出现（19.6 到 34.0），作者解释为它依赖较窄的一组有状态银行工具。
- **数据规模**：数据比例从 1/16 到全量，AutomationBench 从 25.2 涨到 45.8，τ3-Bench Banking 从 20.6 涨到 34.0，从 1/2 到全量仍在涨，没有平台。
- **相关性排查**：用 BGE 向量按与基准的相关度给环境簇排序，Top-50% 与 Random-50% 的差距不超过 1.7 点，作者据此认为增益不是来自对基准式环境的过拟合。
- **多样性**：ToolSpace 覆盖 42 个簇，对比基线为 25、31、34。

## 🔬 最有意思的部分

1. **同一张图也能把基准变难。** 作者用相同规则从 AutomationBench 和 τ3-Bench Banking 的真实调用建图，链入原基准之外但与基准工具有数据或状态关系的工具，生成 AutomationBench Pro（300 题）和 τ3-Bench Banking Pro（98 题），由 3 位博士专家审核，Fleiss κ 为 0.82，一致率 93.1%。AutomationBench 上平均调用次数从标准版的 26.8 到 43.6 涨到 Pro 的 56.3 到 60.6。七个前沿模型全部明显掉分：Claude Opus 5.5 分别掉 32.9 和 15.8 点，GPT 6.1 Sol 掉 26.1 和 16.8 点，DeepSeek-V4.1-Flash-1017 在 AutomationBench 上从 60.5 掉到 22.3，GLM 5.2 掉 11.3 和 24.9 点。

2. **「LLM 判边」那一行，是这篇论文对整个 harness 社区最有用的一个数。** 很多工具图、技能图、workflow 图的构建都默认让 LLM 判断两个节点能否衔接。这里给出了受控对照：同样的游走、同样的回放验证，只把边的来源换成 LLM 判断，五个基准全部掉 5 到 8 点。执行证据比语义直觉更可靠，至少在工具组合这件事上是这样。

3. **重试边是把「失败」当成数据。** 前一次报错、换工具后成功的模式被显式保留在图和轨迹里，错误被当作可恢复的观测。它在消融里贡献不大，但思路和「让 agent 学会从工具错误里恢复」直接相关。

4. **验证不靠参考答案。** 断言分终态、中间快照、返回字段三层，任务描述里不出现工具名和调用顺序，agent 可以走别的路径，只要状态对了就算过。这比「和参考轨迹逐步比对」宽松，也比「LLM 看最终回答打分」可靠。

## 🤔 我的判断

**定位：MCP 工具使用训练数据合成的一次方向性纠偏，从「先造世界再派生工具」改为「先看工具真实怎么被串起来」；对 harness 工程最有价值的是「确定性挖边」和「重放断言门」这两个可单独复用的部件。**

亮点：

1. **规则挖边有受控对照。** LLM 判边全线掉分，这是少见的、能直接拿来说服团队「别让 LLM 做结构判断」的实证。
2. **按需造环境。** 只有 22.5% 的环境需要合成数据库，其余用快照锚点或缓存返回，合成文件数少 55.3%，把成本花在真正有状态的地方。
3. **每个样本都过可执行门。** 从 $s_0$ 重放、三层断言全过才入库，RL 奖励也用同一套执行验证，数据侧和训练侧共享一个判据。

问题与局限：

- **成本只给了代理指标。** 合成文件数少 55.3% 是唯一的成本数据，token 消耗和计算开销没有测量，作者也承认这只是代理。
- **Pro 基准只测了前沿模型。** Pro 版是用同一套工具图规则构建的，论文报告了前沿模型的掉分，但没有给出 ToolSpace 自己训练的模型在 Pro 上的成绩；而训练图和 Pro 图出自同一方法，存在分布接近的可能，论文未单独讨论。
- **结果来源混合。** 主表混用了官方榜单、厂商自报和本地三次复现，不同来源的协议细节不完全可比。
- **超过老师的论证有限。** 744B 均值高于 K3，但 GLM 5.2 基座本身就是 744B 级模型，「超过老师」更多说明数据有效，未必能排除基座能力的作用。
- **RL 规模很小。** 653 条 RL 样本、48 步，RL 的 +2.2 点能否随规模继续增长，论文没有展示。

对工程的直接启发：

- **工具图和技能图的边，优先用执行日志挖。** 参数溯源加转移频率，就能得到比 LLM 判断更可靠的依赖关系；记得过滤公共常量造成的假连接。
- **合成任务时把工具名藏起来。** 任务里只描述目标，验证只看状态，agent 才会真正学会选工具而不是背调用顺序。
- **状态断言分三层。** 终态、关键中间快照、返回字段，比单一的最终答案比对更难被糊弄。
- **把错误恢复显式写进数据。** 报错后换工具成功的片段值得保留，而不是当噪声过滤掉。
- **用同一套图去升级你自己的评测集。** 链入相邻工具就能把十几步的任务拉长到几十步，用来压测 harness 的长程能力。

一句话收束：**ToolSpace 的核心主张很朴素：工具之间怎么连，问执行日志比问 LLM 靠谱；而它用一行消融把这句话变成了可以量化的工程结论。**
