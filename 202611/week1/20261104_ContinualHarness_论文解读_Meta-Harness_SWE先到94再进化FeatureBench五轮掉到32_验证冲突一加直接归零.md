# Meta-Harness 在 SWE 上先冲到 94%，再进化 FeatureBench 五轮掉到 32%；验证冲突一加，最好的 harness 直接归零

你有没有过这种体验：给 coding agent 换了一套「针对当前任务进化出来的」脚手架，单任务榜刷得漂漂亮亮，换一类题就塌？SWE 上修 bug 很强，一转去写测试或加新功能，之前攒下的规则、工作流和验证器突然互相打架。行业里把「让 harness 自己改自己」叫自进化，但多数工作只在**同一类任务**上进化；真正要长期部署的人，迟早会问：**跨任务类型连续进化，还能不能保住旧能力？**

清华大学 / Tsinghua AI Agent Group 的 Jia Li 这篇 **Can Coding Agents Sustain Continual Evolution without Forgetting?**（arXiv:2611.03219，HF Daily Papers）把问题钉死了：单任务上 AHE 能把 SWE 从 82% 拉到 96%，Meta-Harness 到 94%；可一旦进入持续进化，Meta-Harness 在 SWE 上先到 94%，再为 FeatureBench 进化五轮，SWE 掉到 32%，相对跌幅约 66%。把最好的 96% SWE harness 单独塞进「验证产物冲突」，分数直接变成 0%。

## 核心摘要

ContinualHarness 研究的不是「再给一个任务涨几分」，而是 coding agent 的 harness 在**多种任务类型之间连续自进化**时，会不会灾难性遗忘。作者以 Mini-SWE-Agent 为种子，固定模型 DeepSeek-V4-Flash-0731，在 E2B 沙箱里跑两套进化方法：AHE 与 Meta-Harness。评测覆盖三类：SWE-Bench Verified 子集 50 题、改写过提示的 SWT-Bench 50 题、FeatureBench 30 题。单任务设定下两边都很强：AHE 的 SWE 82%→96%，Meta-Harness→94%；SWT 两边都到 100%；FeatureBench 提升超过 10 个百分点。持续设定下故事反过来：SWE→FeatureBench 时 Meta-Harness 从 94% 五轮后跌到 32%；SWE→SWT 时 AHE / Meta-Harness 五轮后对旧 SWE 的遗忘分别达到 100% / 98%。对「原来过、现在挂」的冲突归因里，验证相关占 87.1%，工作流 8.2%，预算 0.6%。消融最刺眼：在 96% 的最优 SWE harness 上，只加验证产物冲突就归零；加工作流冲突剩 66%（耗时 +235%）；加预算冲突仍 96%（耗时 +79%）。作者还特意改写了 SWT 提示，避免交付物类型的模板捷径。

## 🎯 为什么这件事值得写

Harness 自进化已经不是新鲜词。过去一年里，从单脚手架搜索到 RSI 闭环，大家习惯用「这一轮涨了多少分」讲故事。ContinualHarness 把评价尺子换成了另一把：

1. **单任务进化成功，不代表可持续。** 你在 SWE 上进化出一套很猛的验证器和工作流，下一轮要去写测试或加 feature，旧规则可能变成新任务的毒药。
2. **遗忘可以被定位到冲突类型。** 不是笼统地说「忘了」，而是把 pass→fail 拆成验证、工作流、预算三类，看谁在拆台。
3. **任务相关性决定遗忘烈度。** SWT 与 SWE 更不相关，遗忘更狠；SWE 与 FeatureBench 关系近一点，掉得相对温和。这对「先进化哪一类」的产品决策很直接。

如果你在做可版本化的 coding harness、或者想把「进化日志」当长期资产，这篇几乎是必读的反面教材：**涨分轨迹不等于可迁移能力。**

## 🏗️ 机制：跨任务类型的持续 harness 进化

### 设定

- **种子**：Mini-SWE-Agent
- **模型**：DeepSeek-V4-Flash-0731（固定，不训权重）
- **沙箱**：E2B
- **进化方法**：AHE、Meta-Harness
- **任务族**：
  - SWE-Bench Verified（50）
  - SWT-Bench（50，提示改写过，降低「看交付物类型猜模板」的捷径）
  - FeatureBench（30）

核心操作不是改模型，而是让 harness（提示、工作流、验证步骤、预算策略等）在一类任务上进化，再切到另一类继续进化，同时回测旧任务。

### 两种视角

| 设定 | 问什么 |
| --- | --- |
| 单任务进化 | 只在一类题上进化，能不能显著涨分 |
| 持续（continual）进化 | 先在 A 上进化，再在 B 上进化多轮，A 还剩多少 |

后者才是部署视角：真实产品不会永远只修 bug，也不会为每类任务永久分叉一套互不通信的 harness。

## 🧪 关键证据

### 单任务：两边都能把分数拉上去

| 任务 | 基线/起点相关 | AHE | Meta-Harness |
| --- | --- | --- | --- |
| SWE | 82% 起 | →96% | →94% |
| SWT | — | →100% | →100% |
| FeatureBench | — | 提升 >10pp | 提升 >10pp |

单看这一表，结论会是「自进化很香」。ContinualHarness 的价值恰恰在于不让你停在这里。

### 持续进化：旧能力断崖

| 序列 | 现象 |
| --- | --- |
| SWE → FeatureBench（Meta-Harness） | SWE 先到 94%，FeatureBench 进化到第 5 轮后 SWE 掉到 32%（相对约 −66%） |
| SWE → SWT（AHE） | 5 轮后对旧 SWE 遗忘 100% |
| SWE → SWT（Meta-Harness） | 5 轮后对旧 SWE 遗忘 98% |

SWT 路径的遗忘几乎是抹平：新任务学满了，旧任务归零级。FeatureBench 路径没那么绝，但 94→32 也足够毁掉「这套 harness 可以一直叠」的幻想。

### 冲突从哪来

对 pass→fail 案例做冲突归因：

| 冲突类型 | 占比 |
| --- | --- |
| 验证（verification） | 87.1% |
| 工作流（workflow） | 8.2% |
| 预算（budget） | 0.6% |

验证类占绝对多数：新任务进化出来的检查步骤、产物约定、通过条件，和旧任务的成功路径正面冲突。

### 消融：把冲突单独塞回最优 harness

以最好的 SWE harness（96%）为载体，分别注入三类冲突：

| 注入 | SWE 结果 | 时间开销 |
| --- | --- | --- |
| +验证产物冲突 | **0%** | — |
| +工作流冲突 | 66% | +235% |
| +预算冲突 | 96% | +79% |

**验证冲突一加直接归零**，工作流冲突主要是拖慢并伤一部分分，预算冲突几乎不伤准确率只伤时间。这和占比表互相印证：真正致命的是验证层语义冲突，不是「步数不够」或「流程略丑」。

### 任务相关性与提示改写

作者观察到：SWT 与 SWE 关系更远 → 遗忘更重；SWE↔FeatureBench 关系近一点 → 遗忘相对温和。同时对 SWT 做了 paraphrased prompts，避免 agent 靠「交付物类型」走模板捷径，否则持续学习评测会被捷径污染。

## 🔬 最有意思的部分

1. **单任务表和持续表讲的是两个世界。** 同一套 AHE / Meta-Harness，在单任务上看是成功方法，在持续设定下可以把旧 SWE 忘光。评 harness 进化如果只报「本轮最优」，等于鼓励过拟合当前任务族。
2. **遗忘可以被工程化定位。** 87.1% 落在验证冲突，消融里验证产物冲突能把 96% 打成 0%。这意味着「持续进化」的护栏不该先盯预算，而该先做**验证契约的兼容性检查**：新验证器是否否定了旧任务曾经合法的产物形态。
3. **预算冲突几乎是无辜的。** 加预算冲突准确率仍 96%，只是时间 +79%。很多团队一听遗忘就想加更多 step / 更大 context；这篇数据说，至少在这个设定里，预算不是主犯。
4. **改写 SWT 提示是小事，却堵住了假阴性遗忘。** 如果模型靠交付物类型猜流程，持续评测会低估冲突；paraphrase 逼 harness 学的是任务语义，不是模板开关。

## 🤔 我的判断

**定位：给 harness 自进化泼冷水的测量文，也是一份「验证层才是遗忘主战场」的工程诊断书。**

亮点：

1. **问题切换干净。** 从「能不能进化」切到「连续进化会不会忘」，正好打在部署痛点上。
2. **数字够狠且前后一致。** 94→32、100%/98% 遗忘、验证冲突归零，和 87.1% 归因同一指向。
3. **消融可操作。** 不是只说「有冲突」，而是把冲突类型单独注入最优 harness，给出准确率与时间的对照。
4. **SWT 提示 paraphrase** 显示作者意识到评测捷径，这在自进化论文里并不总有。

问题与局限：

- **公开事实里模型固定为 DeepSeek-V4-Flash-0731，种子固定 Mini-SWE-Agent。** 换旗舰模型或另一套种子 harness，遗忘曲线是否同构，还需要外推谨慎。
- **子集规模有限**（50/50/30）。方向信号强，区间估计与方差交代在摘要级事实里不多。
- **预算类冲突占比极低（0.6%）**，可能和具体预算编码方式有关；换一种预算语义，结论或许会动。
- **「任务相关性」偏观察性表述**，若能量化任务族距离并预测遗忘幅度，会更可迁移。
- **代码已公开**，但持续进化的回归套件是否标准化成可复用的 CI gate，从论文叙事上看还有工程化空间。

对工程的直接启发：

- **Harness 进化流水线必须带旧任务回归。** 只看新任务涨分，等于批准遗忘。
- **把验证器当兼容性表面。** 新验证规则上线前，用旧任务的成功轨迹做 pass→fail 扫描；验证冲突优先于工作流美化和预算扩容。
- **按任务相关性排进化日程。** 远任务（如 SWE→SWT）连续硬切，遗忘风险极高；近任务切换可以缓一些，但仍要回归。
- **别用「再加点 step」治疗遗忘。** 这篇消融里预算冲突几乎不掉分，验证冲突直接归零。
- **评测提示去捷径。** 尤其是交付物类型、文件后缀、固定目录结构这类模板开关，改写后再比进化收益。

一句话收束：**Harness 会进化，也会忘；ContinualHarness 说明单任务上的 96% 救不了跨任务后的 32%，而把你从高处拽下来的，多半是那条新加的验证规则。**
