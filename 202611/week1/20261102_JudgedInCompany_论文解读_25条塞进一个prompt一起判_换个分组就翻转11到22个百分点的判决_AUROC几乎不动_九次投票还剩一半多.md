# 25 条塞进一个 prompt 一起判：换个分组就翻转 11% 到 22% 的判决，AUROC 几乎不动，九次投票还剩一半多

你有没有过这种体验：为了省 token，把 25 条评论塞进一个 prompt 让模型一次性打标，返回一个 JSON。上线前拿标注集验了一遍，准确率和逐条打标差不到两个点，于是放心批量跑。某天有人申诉说自己的评论被误判为骚扰，你单独把那条拿出来重判，模型说不是；再塞回原来那批，又说是。

**同一条内容，判决取决于它和谁排在一起。**

LLM-as-judge 这条线我们写过位置偏差、改写敏感、参考答案泄露、决策模型级联，但都是在「一次判一条」的前提下讨论。工程上真正大量使用的，其实是**上下文内批处理**（in-context batching）：一个 prompt 里放很多独立条目，模型逐条给判决。厂商推荐在非实时审核里这么用，有研究还认为 25 到 100 条一批对大多数现有模型是安全的，能省 80% 以上 token、准确率损失不到 2 个点。慕尼黑工业大学的 Peng Xie 和 Amr Alanwar 的 **Judged in Company: In-Context Batching Makes LLM Verdicts Depend on Other Items**（arXiv:2610.40241）专门检验这件事背后很少被说出口的假设：判决是**可分离**的，某一条的判决不依赖同批的其他条目，也不依赖它排在第几位。

看完我的感受：这篇数学和实验设计都非常讲究，最有价值的结论却很朴素：**准确率是检验批处理的错误工具。** 分数上很小的扰动，在决策上会被放大；投票能削掉一部分，但削不掉「和谁同批」那部分，更回不到单条判决。

## 核心摘要

作者把可分离性形式化，证明两个随机分组之间的判决翻转率可以精确分解为三部分：邻居的**顺序**、条目所在的**槽位**、以及**成员**（哪些条目同批），并且在一个阈值模型下，翻转率随上下文贡献的方差的**平方根**增长，所以对分数很小的效应对决策很大。实验用三个判断任务（社交媒体评论的伤害等级、简答题评分、Yelp 星级）和五个 4B 到 9B 的开源模型（Qwen3-4B、Qwen3-8B、Gemma-4-E4B、Granite-3.3-8B、GLM-4-9B），每个任务 2,000 条，单条判一次，再分别在三个独立随机分组（每批 25 条）里判。在伤害和评分任务上，换一个随机分组会改变 11% 到 22% 的判决，比改名条目键或改写指令这类基线多 6.5 到 13.3 个百分点，而相对人工标签的 AUROC 和单条判决相比只差 −0.033 到 +0.010。四个 14B 到 32B 的模型上翻转 6% 到 15%，比基线多 4.2 到 9.1 个点。分组之间的潜在差异大部分来自顺序和槽位；成员的主效应占 0.11 到 0.22，这一部分对同一批做排列投票也去不掉，九次排列的多数票仍保留 52% 到 60% 的翻转。批处理判决还会系统性地偏离单条判决：15 个独立随机分组的多数票仍有 8.4% 到 17.8% 和单条判决不同。逐 token 编辑生成过程表明，模型自己之前写下的判决和邻居的文本**两个通道都在起作用**。简单任务（星级）只有 2.9% 到 3.9% 的判决改变。作者的建议是：模糊的条目一条一个 prompt，用缓存前缀把大部分成本省回来；凡是批处理，都要报告它与单条判决的一致率。

## 🎯 为什么这件事值得写

论文图 1 就是一个足够让人不安的例子。SciEntsBank 里一道题，学生答案人工评为 CORRECT，Qwen3-4B 的判决如下：

| 条件 | 判决（概率） |
| --- | --- |
| 单独判 | CORRECT（0.97） |
| 单独判，改条目键名 | CORRECT（1.00） |
| 随机批 A，第 14/25 位 | PARTIAL（1.00） |
| 批 A，改条目键名 | PARTIAL（1.00） |
| 批 A，改写指令 | PARTIAL（1.00） |
| 随机批 B，第 15/25 位 | PARTIAL（0.85） |
| 随机批 C，第 8/25 位 | CORRECT（1.00） |

**每一次都很自信，对 prompt 的琐碎改动都很稳，但换一批就变。** 解码器模型在写第 12 条的判决时，已经读过另外 24 条和自己写下的前 11 个判决，没有任何机制保证它不受影响。

已有工作要么报告批大小增长时的总体准确率，要么发现准确率依赖位置，BatchPrompt 用排列投票来缓解。最接近的一项发现筛选决策在单条和 20 条一批之间变化 1% 到 27%，而且总体指标不一定反映这些变化。这篇新增的是：把成员效应和顺序、槽位分开的分解；在一次生成内部分离两个通道的干预；测量排列投票和独立批投票分别能留下多少；以及跨任务统一的决策级比较。

为什么 Byron 会在意：我们做的 harness 里，裁判、gate、决策模型往往就是批量调用的。不管是批量给轨迹打 rubric 分、批量审 PR 评论、批量判 skill 有没有被正确触发，只要是一个 prompt 多个条目，这篇的结论都直接适用。它属于「裁判鲁棒性」，只不过干扰源不是攻击者注入的文本，而是**同批的其他合法条目**。

## 🏗️ 机制：可分离性、三分解和平方根定律

**1. 分解。** 记一个条目在某个上下文里的判决函数为 f，上下文由三个因素决定：槽位 s、成员 N（同批是哪些条目）、以及其余排列 ω（邻居顺序）。重抽其中一个子集 R，定义

$$G(R) = \tfrac12\,\mathbb{E}\big(f(C) - f(C^{(R)})\big)^2$$

对决策来说，G(R) 就是翻转概率的一半。按 Hoeffding 和 Sobol 的方差分解，令 V_s、V_N 为槽位和成员的主效应方差，V_sN 为交互，T_ω 为给定槽位和成员后剩下的方差，就有

$$G(\{s, N, \omega\}) = T_\omega + V_s + V_N + V_{sN}$$

四个实验条件恰好对应重抽这四组因素：保持一切只重排其他（keep）、保持成员和槽位重排邻居、保持槽位换成员、整体换一个新分组（new）。

**2. 平方根定律。** 在阈值模型下（决策是潜在分数过阈值，两个上下文的分数服从标准二元正态，相关系数 ρ，潜在差异 D = 1 − ρ），两次决策不同的概率在 D 很小时近似为

$$\Psi(h, \rho) \approx \frac{\sqrt{2D}}{\pi}\, e^{-h^2/2}$$

**翻转随上下文贡献方差的平方根增长。** 在中位数阈值附近，占潜在方差 1% 的上下文效应就会翻转 4.5% 的决策，占 10% 会翻转 14.4%。反过来，把分数在 M 个独立上下文上取平均，方差降为 1/M，翻转只降约 1/√M；做多数票，降得还更少。

**3. 投票能去掉什么。** 对同一批做 m 次排列，平均值的方差是 V_N + G({s, ω})/m，m 趋于无穷时收敛到只剩 V_N。所以**排列投票去掉了槽位、顺序以及槽位和成员的交互，去不掉成员主效应**，任何奇数 m 都达不到那个下限。对独立批做投票，会把成员也平均掉，但收敛到的是「批处理下的主判决」，不是单条判决：投票去掉方差，去不掉偏差。

**4. 实验设置。**

| 项 | 设置 |
| --- | --- |
| 任务 | 伤害：Measuring Hate Speech 语料，五级伤害量表，判决为二级及以上；评分：SciEntsBank 简答，INCORRECT、PARTIAL、CORRECT，判决为 CORRECT；星级：Yelp Review Full，判决为四星及以上 |
| 规模 | 每任务 2,000 条 |
| 主模型 | Qwen3-4B-Instruct-2507、Qwen3-8B（关思考）、Gemma-4-E4B-it、Granite-3.3-8B-Instruct、GLM-4-9B-0414，bf16 贪心解码，每模型一张 RTX 5090 |
| 追加模型 | Qwen3-14B、Qwen3-32B（关思考）、Gemma-4-31B-it、GLM-4-32B-0414，每模型一张 H200 NVL |
| 条件 | 单条判；三个独立随机分组，k = 25；每个分组派生三个条件；分组 0 另切成 5、10、50 条一批 |
| 基线 | 改条目键名、改写指令、同样的 prompt 逐个生成（量批推理的数值噪声） |
| 干预 | 每任务 200 个目标，分别放在第 12 位和第 24 位（最后一位），另一组独立邻居提供替换用的判决和文本 |

作者在实验前固定了三个通过标准：G1 普适性（星级和评分任务上，至少五个模型中的三个，新分组翻转率超过最大批处理基线，超出部分下界至少 2 个点）；G2 成员（固定槽位时成员份额的下界大于 0，至少两个任务、至少三个模型）；G3 机制（不编辑的干预能复现生成的判决，近似平局除外，并且至少一个通道改变 3% 以上的判决）。

## 🧪 关键证据

**判决依赖分组。** 主结果（分组 0 对分组 1，单位为百分比，括号内为超出基线的点数及 95% 区间）：

| 模型 | 伤害：新分组 | 伤害：最大基线 | 评分：新分组 | 评分：最大基线 | 星级：新分组 | 星级：最大基线 |
| --- | --- | --- | --- | --- | --- | --- |
| Qwen3-4B | 13.3 | 4.6 | 12.9 | 4.7 | 3.9 | 2.2 |
| Qwen3-8B | 15.5 | 6.2 | 11.7 | 4.6 | 3.6 | 1.7 |
| Gemma-4 | 13.0 | 4.4 | 10.7 | 4.2 | 2.9 | 1.4 |
| Granite | 15.7 | 5.9 | 21.7 | 8.4 | 3.5 | 2.1 |
| GLM-4 | 16.2 | 6.5 | 15.6 | 8.0 | 2.9 | 1.3 |

伤害和评分任务上超出基线的下界在 5.3 到 11.1 个点；只是逐个生成同样 prompt 带来的数值噪声只有 0.5% 到 2.1%。G1 在评分上五个模型全部满足，在星级上一个都没满足，作者因此**只对真正有模糊性的判断任务声称普适**。看写下的等级而不是二值决策，新分组会改变 16% 到 39% 条目的等级，是改写指令的 1.6 到 2.9 倍。

**准确率看不出来。** AUROC 变化只有 −0.033 到 +0.010，但操作点会移动得更多：伤害任务上，Gemma-4 被判为有害的比例从单条的 49% 降到批处理的 31%，Granite 从 59% 降到 43%；评分任务上 Qwen3-4B 判为 CORRECT 的比例从 43% 降到 34%。更反直觉的是较大模型：伤害任务上批处理反而让 AUROC 升了 0.011 到 0.057，因为它们单条判时把大量评论放在同一个等级上，平局压低了 AUROC。**一个在标注数据上的验证会批准批处理，尽管 8.4% 到 14.6% 的伤害判决在分组之间不一样。** 作者给出了两个解释：两个条件的翻转率等于它们各自不共享的错误，所以在 20% 到 38% 的错误率下，准确率相同和 0 到 41% 至 74% 之间的任何翻转率都兼容；以及上下文效应对 AUROC 的影响与方差份额成正比，对翻转的影响与它的平方根成正比。

**不同模型朝不同方向偏。** 一个更早的、样本部分重叠的研究里，Gemma-4 单条判时把 58% 针对种族的评论标为有害，批处理时降到 35%，GLM-4 却在批处理时标得更多。

**来源分解。** 伤害和评分上两个随机分组之间的潜在差异 D_new 为 0.06 到 0.24。其中邻居顺序占 0.42 到 0.69，槽位占 0.09 到 0.32，成员主效应占 0.01 到 0.25（均值 0.15），槽位和成员交互占 −0.07 到 0.18（均值 0.07）。

**投票留下什么。** 主模型在 H200 NVL 上把分组 0 和 1 的每批按九种顺序重判：三、五、九次排列的多数票分别保留 71% 到 76%、60% 到 69%、52% 到 60% 的分组间翻转，代价是三倍、五倍、九倍。拟合到这些数据上的阈值模型在每一对上的预测误差都在一个点之内；用主实验事先做的预测，偏差在 −2.0 到 +2.2 个点。换成在独立批上投票：单个随机批让 10.9% 到 19.8% 的条目与单条判决不同，15 个独立批的多数票仍有 8.4% 到 17.8%（合并 12.6%），**15 个批只去掉了大约五分之一的不一致**。把每个分组的阈值重新校准到和单条判决给出一样多的正例之后，多数票仍有 7.9% 到 13.5% 不同。

**两个通道。** 不编辑的干预在伤害和评分上复现了 97.8% 到 99.5% 的生成判决。只替换之前的判决（保留文本）改变 7% 到 23% 的目标决策，只替换邻居文本（保留判决）改变 9% 到 26%，两者都替换改变 9% 到 22%，在每一对里都少于两者之和，十对里有七对还少于任一单项。判决通道对内容敏感：把之前的判决都降一级会改变 8% 到 54%，把模型自己的判决打乱改变 5% 到 19%，替换成模型单独判这些邻居时给的判决只改变 2% 到 12%。把每个邻居的文本都换成一个短横、保留键和判决，改变 12% 到 41%。

**什么时候要紧。** 伤害和评分上，单条判时不确定的条目在分组间翻转 14% 到 38%，确定的条目仍翻转 6% 到 21%；各模型里不确定条目的比例从 2.4% 到 47.8% 不等。星级对五个模型都很简单（相对真实星级 AUROC 0.96，其他任务是 0.72 到 0.83），不确定的评论只有 1.4% 到 4.7%，确定的只翻转 2.2% 到 3.5%。**缩小批次帮助有限**：5 条一批时已有 9% 到 16% 的判决不同于单条，50 条一批是 12% 到 23%。

## 🔬 最有意思的部分

**第一，单条判决也不是「真值」。** 校准阈值之后，单条判决与 15 批中 13 批的多数票不同的频率（合并 10.4%），和一个批与其他 14 批中 13 批多数票不同的频率（11.0%）差不多。在多数票和单条判决不一致的条目上，有四对模型任务里多数票有超过一半和人工标签一致（最高 83%）。换一个改写过的单条 prompt 当参照，不一致率每对会变化 −4.5 到 +1.7 个点。作者没有说批处理更差，而是说**批处理让判决变得武断**：你得到的是哪一个判决，取决于一个跟内容无关的随机分组。对用来决定删不删评论、给不给分的系统，这本身就是问题。

**第二，模型变大治得了琐碎扰动，治不了批处理。** Qwen3 家族里，改键名在 1.7B、4B、8B 上分别改变 24.2%、3.2%、1.1% 的判决，批处理却分别改变 24.0%、12.9%、12.8%。到 1.7B 为止两者差不多，从 4B 到 8B 改键名的影响降到三分之一，批处理几乎没变。14B 和 32B 也没有延续这个趋势：改键名改变 2.1% 的单条判决，不比 8B 少，而一个批和单条判决的不一致分别是 12.0% 和 17.0%。

**第三，成本账算得很具体。** 设共享前缀 S 个 token、每条 L 个 token、缓存读取按输入价的 c_cache 计费。单条 prompt 加缓存前缀每条成本 c_cache·S + L；批处理不走缓存是 S/k + L，走缓存是 c_cache·S/k + L。所以隔离只要 c_cache < 1/k 就比不走缓存的批处理便宜。Anthropic 的模型和 OpenAI 从 GPT-5.6 起缓存读取计费 c_cache ≤ 0.1，但只缓存至少 512 到 4,096 token 的前缀；自托管服务对任意长度前缀都能复用，c_cache 几乎为零，隔离的成本和走缓存的批处理差不多。前提是所有共享文本，包括请求本身，都要放在条目之前，作者自己的 prompt 把请求放在条目之后，需要重排。**可靠的修法是构造上的可分离**：一条一个 prompt，或者用块注意力掩码让每个条目和它的判决只看见共享指令和自己，键和位置 id 也不依赖槽位。

**第四，预注册也老实交账。** G1 在星级上没通过，作者就收窄了主张；G3 原先要求 99.5% 的复现率，冒烟测试发现 bf16 下带 KV cache 的填充批生成和单次前向在近似平局时概率能差 0.10，于是在正式运行前加了近似平局例外，并且每个编辑都和不编辑的前向比较。最后实际复现率 97.8% 到 99.5%，作者承认 G3 第一个条件只是近似成立。

## 🤔 我的判断

**定位：测量基础设施，外加一个有理论支撑的工程警告。** 它没有提出新的裁判模型，而是告诉你一个几乎人人都在用的省钱技巧，会让裁判的单条判决失去可分离性，并且你常用的验证方法看不出来。

亮点：

1. **把「准确率没掉」和「判决没变」彻底分开。** 平方根定律给了一个很好记的直觉：分数上 1% 的方差，决策上 4.5% 的翻转。
2. **分解把可修和不可修的部分分开。** 顺序和槽位能用排列投票平均掉，成员主效应不能，单条和批处理之间的系统偏差连跨批投票都不能。
3. **建议可直接执行。** 一条一个 prompt 加缓存前缀；批处理时报告与单条判决的一致率和两个随机分组之间的翻转率，并配上改键名这类不需要标签的基线。

问题与局限：

- 主模型都是 4B 到 9B 的开源模型，14B 到 32B 只复现了核心设计，没跑星级、其他批大小、干预和投票；闭源模型可能更敏感也可能更不敏感，附录里的闭源模型是按条目对共享上下文作答，不测判决通道。
- 只有三个英文任务、一个 prompt 模板加一个改写版本、JSON 输出、贪心解码；在一个对话里一条一条问，可能表现不同。
- 阈值模型假设上下文对所有条目贡献相同方差，而实测它低估了 15 批里判决不全一致的条目比例，说明有些条目对上下文更敏感。
- 极端的干预（所有之前判决都设为最低级）产生的是模型自己不会写的上下文，作者的结论主要建立在自然生成之间的互换上。

对工程的直接启发：

- **harness 里的裁判和 gate 默认一条一个 prompt。** 尤其是会触发不可逆动作或者影响人的判决：拦不拦 PR、算不算违规、合不合并 skill。用缓存前缀把共享指令放前面，成本基本回得来。
- **如果一定要批处理，加两个监控指标。** 与单条判决的一致率，以及同一批数据换一个随机分组后的翻转率，配上改键名基线。只看标注集准确率不够。
- **别指望排列投票兜底。** 九次排列仍留一半以上翻转，成本却是九倍，不如直接隔离。
- **批量打 rubric 分的 RL 奖励要警惕。** 如果奖励是一批轨迹一起打分，同批其他轨迹会变成奖励噪声的来源，而且不是均值为零的噪声。
- **把「判决可分离」当成裁判服务的一条接口契约。** 和「裁判不能读执行者的推理」一样，写进 harness 的规范里。

一句话收束：**裁判省下的每一个 token，都可能是从下一个被误判的人身上省出来的；想省钱就用缓存前缀，别用邻居。**
