# 造训练任务先倒推信息链：前提给全、结果留给 agent 算，探针先跑一遍再修，35B-A3B 在 GDPval 上从 879 涨到 1565

你有没有过这种体验：给 agent 布置一个「比较四家供应商三年总成本并推荐一家」的任务，资料给了需求预测，给了报价单，它算得头头是道，最后你发现有一家报价到底含不含运费根本没写，它自己默认了一个。结论看着专业，其实建立在一个没人给过的前提上。

如果这只是一次使用，顶多是个错答案。可如果这条轨迹被拿去当 SFT 的示范数据，学生模型学到的就是「信息不够时自己编一个」。行业里给办公类 agent 造训练数据，大多是检索、复用、改写或合成一批材料，再让老师模型去做。**材料单看都合理，合在一起信息链是不是完整、有没有自相矛盾、有没有把该让 agent 算的结果提前写进了题面？**

IQuest Research、人大高瓴、浙大、北大等的 **WorkFactory: Turning Professional Intents into Executable Work for Scalable Agent Training**（arXiv:2610.37161）把这个问题当成造题的核心约束。看完我的感受是：这是一篇数据工程论文，但它把「造题」做成了一个带验收的流水线，前面倒推规划，后面用探针跑一遍找毛病再修，思路和我们之前读的 GraphForge、WorkForge 一脉相承，又往「可执行性」上多走了一步。

## 核心摘要

WorkFactory 从三个来源合成职业意图：职业分类体系（角色和场景）、技能文档（可组合的操作）、真实职业交付物（反推目标和受众）。对每个意图，规划器从「要交付什么」往回倒推，建一张信息支撑图：每个结论依赖哪些计算和判断，这些计算又依赖哪些信息，每条信息放在用户请求、参考文件、外部资源还是未来的交付物里。图明确区分「给定的前提」和「要 agent 自己推出来的结果」，前者必须在 agent 能看到的输入里找得到，后者绝不能提前写出来。材料生成后，一个只看得到请求和文件、看不到图和计划的探针先把任务做一遍，报告阻断性的环境问题；修复器只改请求和已有文件的内容，修完要通过构建检查和一次「工作内容没变」的审查，再换新探针重跑，最多三轮，修不好就丢。通过的任务交给独立的老师模型 GLM-5.3 收集轨迹。最终 112,686 道任务、612 个职业，训练出 WorkPilot 4B、27B、35B-A3B 三个模型，四个职业工作基准全部涨分：WorkPilot-35B-A3B 的 GDPval-AA Elo 从 879 到 1565，JobBench 从 28.91 到 62.35；WorkPilot-27B 本地估计 1612 Elo，和前沿模型在同一区间。消融显示信息级规划把「推导链断裂」从 24.86% 降到 6.86%，再加执行式修复把「跨文件不一致」从 25.74% 降到 4.84%，下游 Elo 从 1245 到 1293 再到 1326。

## 🎯 为什么这件事值得写

软件工程方向造训练环境有天然优势：仓库就是真实上下文，测试就是验收（SWE-Gym、SWE-smith、R2E-Gym）。职业工作没有这种现成的结构，一份采购分析的「正确性」取决于一串分散在多份文件里的前提。

作者把难点说得很准：**环境要划一条边界，所有必要前提都得给到，中间结果和最终结论又必须留给 agent 自己算。** 漏了前提，老师就会自己补假设；给多了，老师抄个结论就交差。两种情况下收集到的轨迹都不是好示范。

和相关工作的区别：GraphForge 从一个真实文件工作区的证据图里同时编译出任务和评分标准；WorkGenesis 围绕检索到的文件合成配套材料，用评分标准做失败归因来修。WorkFactory 则从交付物往回倒推信息依赖，修复时直接在 agent 能看到的环境里跑探针，并且约束修复不能改变原本要做的工作。

## 🏗️ 机制：倒推规划，探针验收，独立老师

### 1. 多来源意图合成

三条路线：把职业扩展成具体场景下的角色；当一个技能的输出能喂给另一个技能时把它们组合成工作流；从真实交付物用指令反译推出合理的目标。所有候选意图过一遍 LLM 审查（内部是否自洽可行、是否符合职业规范、像不像真实工作），进入共享意图库。

### 2. 信息支撑图

图里有四样东西：信息单元、承载位置、信息之间的支撑关系（关联、变换、证据、约束）、信息到位置的绑定。每个节点标记它是「提供的」「外部获取的」「agent 推导的」还是「构造内部的」。

以论文的纸箱采购为例：

- 请求里写明目标、规则和输出要求：8% 折现率（第 1 到 3 年）、一次性开办费计入第 0 年、运费按箱计、美元不变价。
- 参考 PDF 里给出三年需求 48K、60K、78K 箱，标准箱与保温箱 60:40，以及各家报价（单价、开办费、运费）。
- 各家的现金流、NPV、成本服务权衡和最终推荐，绑定到「未来的成本对比表格」，也就是留给 agent 算。

图对 agent 隐藏，规划器把它翻译成具体的请求、文件规格和构造依赖，再由环境构建 agent 去复用、改写或合成文件。

### 3. 执行式修复

| 步骤 | 做什么 | 约束 |
| --- | --- | --- |
| 探针诊断 | 只用 agent 可见的请求和资源做一遍任务 | 看不到图、计划和之前的诊断；要区分环境问题、自己犯错和合理的开放选择；只有阻断性问题触发修复 |
| 修复 | 改请求和已有参考文件的内容 | 文件数量、类型、依赖结构不变 |
| 复检 | 构建检查加「工作内容保持」审查 | 核心目标、关键操作、交付要求不能变；不过就丢 |
| 重跑 | 新探针在干净环境里再做一遍 | 最多三轮，还有阻断就丢 |

纸箱例子里，探针发现 C 供应商的运费没写清楚是含在单价里还是另计；修复器加了一条「每箱另收 0.15 美元运费」，补全了 NPV 比较需要的前提，但没有替 agent 做比较。

在 5K 题的分析集上，约 20.24% 的题修了一轮，7.70% 修了两轮，2.48% 修到三轮上限，最后 24 道（0.48%）仍被阻断而丢弃。

### 4. 独立老师收集轨迹

意图合成、规划、构建和修复都用 DeepSeek-V4-Flash-0731；老师是 GLM-5.3，在干净沙箱里做题，信息边界和探针一样。轨迹过一遍轻量过滤（重复推理、重复工具调用、交付物缺失或太单薄），最长的 5% 额外做基于交付物两两比较的拒绝采样。轨迹分别用 Stirrup 和 Claude Code 两种 harness 收集。

语料规模：112,686 道任务，23 个大类、612 个职业，平均每题 4.15 个参考文件，交付物里 xlsx 占 30.7%、pdf 28.0%、docx 22.9%；老师轨迹平均 57.36 轮、62.95 次工具调用、136.18K token。构造成本平均每道尝试的任务 11.656M token，其中信息级规划 4.737M 最大。

## 🧪 关键证据

### 主结果

| 模型 | GDPval-AA Elo | JobBench | Workspace-Bench | OmegaUse-OfficeVal |
| --- | --- | --- | --- | --- |
| GLM-5.3（老师） | 1646 | 66.35 | 61.80 | 31.09 |
| DeepSeek-V4.1-Flash | 1600 | 67.69 | 63.06 | 31.43 |
| GPT-5.6 Sol | 1588 | 50.91 | 53.77 | 19.25 |
| Qwen3.8-27B | 1409 | 62.12 | 59.26 | 23.47 |
| Qwen3.5-4B → WorkPilot-4B | 661 → 1375 | 4.67 → 39.87 | 26.92 → 51.30 | 1.71 → 11.77 |
| Qwen3.6-35B-A3B → WorkPilot-35B-A3B | 879 → 1565 | 28.91 → 62.35 | 47.12 → 56.53 | 7.14 → 21.18 |
| Qwen3.6-27B → WorkPilot-27B | 975 → 1612 | 37.81 → 63.05 | 49.41 → 59.18 | 10.18 → 26.61 |

三个尺度、四个基准全部涨分。WorkPilot-27B 的 1612 是本地估计（Gemini 3.1 Pro Preview 当裁判、对齐到 v2.1 量表），比 DeepSeek-V4.1-Flash 高 12，比老师 GLM-5.3 低 34。其他基准用 Claude Code harness，需要裁判时用 Claude Sonnet 4.6。

### 规模化：收益递减，执行长度先涨后落

- 35B-A3B 从 879 到 1565，前 5K 道任务贡献了 447 分，从 75K 到 110K 只多了 13 分。到 30K 时，35B-A3B 和 27B 分别拿到了全部增益的 88% 和 94%。
- 平均执行轮数先从 24.87 涨到 2K 时的 162.88，再降到 110K 时的 85.90，而 Elo 一直在涨；撞到 250 轮上限的比例从 21.9% 降到 2.7%。作者的解读是：少量数据先教会模型「多干」，更多数据才教会它「干得省」。
- 代码执行失败率从 16.0% 降到 6.3%；网页搜索失败率在 2K 时先升到 22.4%，110K 时回到 10.4%；网页抓取失败率一直在 40% 到 48% 之间，没怎么变。

### 消融：规划和修复各管一段

| 缺陷类型（探针诊断的硬缺陷发生率） | 直接按文件规划 | 加信息支撑图 | 再加执行式修复 |
| --- | --- | --- | --- |
| 证据缺失 | 9.62% | 3.64% | 2.02% |
| 跨文件不一致 | 32.82% | 25.74% | 4.84% |
| 推导链断裂 | 24.86% | 6.86% | 3.26% |
| 请求不明确 | 7.22% | 0.62% | 0.28% |
| 泄露或捷径 | 1.92% | 3.36% | 0.84% |
| 执行可行性 | 10.80% | 6.64% | 0.48% |
| 自相矛盾 | 3.28% | 4.46% | 1.74% |
| 事实错误 | 4.52% | 2.56% | 1.30% |
| 下游 GDPval-AA Elo | 1245 | 1293 | 1326 |

最诚实的一点是：加了信息支撑图之后，「泄露或捷径」和「自相矛盾」反而升了 1.44 和 1.18 个点。作者的猜测是，依赖关系写得太明确，构建器容易把该让 agent 推导的东西直接写进请求；约束更密，跨文件保持一致也更难。也就是说，**把信息需求写清楚，不等于生成出来的材料就守住了它**，这正是需要后面那道执行式修复的原因。

### 老师选择影响很大

在同样的 30K 任务上，用 GLM-5.3 的轨迹训练出的学生 1483 Elo（95% 区间 1455 到 1510），用 DeepSeek-V4-Flash-0731 重新生成轨迹训练的学生 1248（1220 到 1274），都高于底座的 879。同一批题，换老师差了 235 分。

## 🔬 需要打折看的地方

1. **消融里的缺陷率由同一类探针打分。** 修复环节本身就是按探针报告来修的，再用探针报告去衡量修复效果，下降是部分「按构造」成立的。比较有说服力的是下游 Elo 那一行，但修复那一步只多了 33 分，正文表格也没给这一行的置信区间。
2. **构建和探针用同一个模型。** 意图、规划、材料和修复都是 DeepSeek-V4-Flash-0731，它眼里的「阻断性问题」不一定和老师 GLM-5.3、学生 Qwen 眼里的一致。
3. **GDPval 的大部分分数是本地估计。** 底座和 WorkPilot 的 Elo 多数不是官方评分，而是用 Gemini 3.1 Pro Preview 做两两比较、按两个锚点对齐量表得到的。附录给了任务级 bootstrap 区间，但裁判本身的偏好没有讨论。
4. **只做了纯文本。** 老师 GLM-5.3 只接受文本，所以学生的视觉能力完全没用上。办公任务里大量信息在图表和版式里，这一块是空白。
5. **只有 SFT。** 学生上限被老师压住，WorkPilot-27B 已经逼近 GLM-5.3，再往上需要 RL 或别的信号，论文把它留给了后续工作。
6. **污染检查是基于请求重合和文件哈希的。** 作者做了请求重叠检查、人工复核可疑对和文件哈希比对，没发现评测任务复用。对于这种按职业大规模合成的数据，语义层面的接近（同一类分析换个数字）这种检查是查不出来的。

## 🤔 我的判断

**定位：一份扎实的数据工程方案，加一组诚实的规模化观察。对造 agent 训练环境的人，最可借鉴的是那条「前提给全、结果留空」的边界和执行式修复。**

亮点：

1. **把造题的验收对象从「材料」换成「可执行性」。** 材料单看都合理不够，要让一个和老师同信息边界的探针实际做一遍，看会不会卡住。这和 coding 方向「先跑一遍参考解、确认空提交过不了」是同一个思路，搬到了没有测试的职业任务上。
2. **修复受约束。** 只能改内容、不能改结构，还要过一次「工作内容没变」的审查。很多自动修题流程最大的问题是越修越简单，这里专门防了这一手。
3. **消融里敢报负数。** 信息支撑图让泄露和自相矛盾变多，作者没有藏，还解释了为什么需要修复补位。
4. **执行长度先涨后落是个有用的诊断信号。** 小数据训练让模型变得「啰嗦」，撞轮数上限的比例很高；数据够了才收回来。看训练进度时，除了看分数，也该看轮数分布。

问题与局限：

- 消融的评价有循环，下游收益的统计强度不够。
- 老师差异的影响（235 分）比规划加修复（81 分）大得多，说明在这套流水线里，选对老师可能比把题造得更干净更值钱。
- 网页抓取失败率从头到尾都在四成以上，说明有一类工具能力不是靠更多 SFT 数据能解决的，可能需要 harness 层的改进。

对工程的直接启发：

- **造训练任务时，显式标出哪些是给定前提、哪些是要推导的结果。** 哪怕不建完整的图，在任务规格里列一份「必须能在输入里找到的信息」清单，再让一个看不到清单的 agent 做一遍，就能抓到大部分漏前提的问题。
- **自动修题要锁住任务结构，并单独审查「工作量有没有被修没」。**
- **看 SFT 进度时盯住执行长度和工具失败率。** 轮数暴涨可能是学会了多干，也可能是学会了绕圈，要和分数一起看。
- **别低估老师。** 同一批题换老师的差距远大于造题工艺的改进，先在小样本上比较几个老师，再决定大规模收集。

一句话收束：**好的训练任务不是材料堆得多，而是信息刚好够用、结论刚好留空，并且有人真的跑过一遍证明它做得完。**
