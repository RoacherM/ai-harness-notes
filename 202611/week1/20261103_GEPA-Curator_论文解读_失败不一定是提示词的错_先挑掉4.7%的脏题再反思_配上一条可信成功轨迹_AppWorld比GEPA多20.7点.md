# 失败不一定是提示词的错：先挑掉 4.7% 的脏题再反思，配上一条可信的成功轨迹，AppWorld 上比 GEPA 多 20.7 点

反思式提示优化这一年很火。GEPA、ACE、SkillOpt 这类方法的逻辑都差不多：让 agent 跑一批任务，把失败的轨迹交给一个 Reflector，让它说出「这次为什么错」，再据此改提示词或者 playbook。这是目前最便宜的一种自我改进，不碰权重，只改文字。

但这套逻辑有个默认前提：**失败里有可以学的东西，而且这个东西是提示词的问题。** 真实的 agent 任务里，失败可能来自网页按钮临时坏了、harness 根本没提供需要的工具、任务描述本身有歧义，或者 LLM 评判今天心情不好。Reflector 看不出这些区别，照样会给提示词加一条规则，比如「如果购买按钮没反应，就去找别的购买方式」，而按钮下一次又好了。

伯克利、ICSI、LBNL、Furiosa AI 和 KAIST 合作的 **GEPA-Curator: Curated Learning for Self Improving Agents**（arXiv:2610.37651）要解决的就是这个问题：在优化器前面加一个 Curator，决定哪些经验有资格塑造提示词。看完我的感受是：**自我改进的瓶颈不在反思能力，而在喂给反思的数据干不干净。** 这和预训练时代 LIMA 那句「少量高质量数据胜过大量脏数据」是同一个道理，只是搬到了 agent 的经验回放里。

## 核心摘要

GEPA-Curator 是一层跑在现有提示优化器外面的 harness，给每个训练任务维护一份历史（每次执行的轨迹和评测结果），用这份历史做两件事。第一是**任务筛选**：不再随机抽 minibatch，而是先跑没探索过的任务积累历史，然后跳过那些「再跑一次也学不到东西」的任务，包括已经稳定成功的、反复因为 harness 或环境原因失败的、以及评判结果前后矛盾的。跳过是暂时的，每个 epoch 都会重新考虑。第二是**成功轨迹检索**：当前任务失败时，从历史里挑一条最可信的成功轨迹，作为对照材料一起交给 Reflector；找不到可信的就放弃，不硬塞。两件事在同一次 Curator 调用里完成。

在 WebArena 的四个站点（GoBrowse 任务集）上，用 Gemini 3.1 Pro 做优化器时，GEPA 比种子提示词提高 6.3 点，GEPA-Curator 提高 9.7 点；换成 Claude Opus 5，两者分别是 6.4 点和 11.4 点，四个站点全部胜出。在 ALFWorld、AppWorld 和 τ-bench 上，相对 GEPA 最多高 20.7 点（AppWorld Test-N），相对 ACE 最多高 21.2 点（τ-bench）。优化成本方面，精简版 Curator 的总花费只是 GEPA 的 1.31 倍，在非 WebArena 基准上比 ACE 便宜 4.42 倍。

## 🎯 为什么这件事值得写

现有的反思式优化器对噪声的防御基本只有一招：**验证集门控**。改完的提示词在验证集上跑一遍，变差了就拒绝；GEPA 还会在同一个 minibatch 上再跑一次，确认没退步。作者认为这不够，理由有两条：

1. **门控本身也有噪声。** 门控依赖聚合分数，而 agent 执行和 LLM 评判都有随机性，坏的修改可能碰巧通过，好的修改可能碰巧被拒。
2. **门控只能事后把关。** 它在修改生成之后才起作用，没法提高反思和修改本身的质量。如果 Reflector 拿到的就是一条「按钮坏了」的失败轨迹，它产出的修改再怎么过滤也只是在烂选项里挑。

所以作者把干预点往前移：**在反思之前就决定看什么、对照什么。**

## 🏗️ 机制：一份任务历史，两个决定

### 优化器被看成一个黑盒接口

论文把提示优化器抽象成一个输入输出接口：每一步收到一个提示词、一个任务 minibatch、可选的附加元数据，跑完以后返回新提示词、每个任务的轨迹和评测结果。普通优化器每一步就是随机打乱训练集再顺序取。GEPA-Curator 不改优化器内部，只控制两样东西：**minibatch 里放哪些任务**，以及**附加元数据里放哪些成功轨迹**。这让它可以套在 GEPA 上，也可以套在 Meta-Harness 上（后面会讲）。

### 任务筛选：什么时候该跳过一道题

Curator 读每个任务的历史，判断这次值不值得跑。论文示意图里的三个典型判断很直观：

| 历史情况 | Curator 的判断 |
| --- | --- |
| 只跑过一次 | 证据不够，再跑一次积累历史 |
| 有成功也有失败 | 能做但不稳定，再跑一次拿更多信号 |
| 多次失败都卡在同一个网页 | 暂时跳过，再跑也不会有新信息 |

需要跳过的情况包括：反复稳定成功（没什么可学）、反复因为提示词之外的原因失败（harness 或环境限制）、相似结果却得到不一致的评判（评判有噪声）。

关键设计是**跳过只是暂时的**。每个 epoch 都会重新考虑被跳过的任务，原因是双向的：已经学会的任务可能因为提示词为了别的任务做了压缩或加了冲突规则而退步；一开始太难被跳过的任务，也可能随着提示词变好而变得能做。附录统计显示，被判为不可能的任务平均跳过的连续 epoch 数从训练前期的 5.50 涨到后期的 8.75，已掌握的任务也越跳越久但会周期性回查，评判不稳的任务则被更频繁地重新检查。

### 成功轨迹检索：给 Reflector 一个可信的参照

普通 Reflector 只看当前的失败轨迹，只能靠猜。GEPA-Curator 的做法是：如果同一个任务以前成功过，就挑一条成功轨迹一起交过去，让 Reflector 做对比，看清「这次哪里走岔了」。

挑选的标准是**可信**：优先选有一致评判证据支撑的成功，避开那些成功本身就可疑、或者和其他观察矛盾的。如果没有合适的成功，Curator 就放弃，不提供参照。这和剔除脏失败是对称的：脏的成功同样会误导 Reflector。

由于任务筛选和成功检索在同一次 Curator 调用里完成，检索不额外花一次 LLM 调用。

## 🧪 关键证据

### 先看动机实验：几道坏题就能拖住整个优化

作者把 GoBrowse 的 GitLab 任务分成四类：一开始就稳定成功的 Easy、能通过优化变好的 Optimizable、怎么都失败的 Impossible、以及因为意图歧义或评判不稳而时好时坏的 Flaky。然后让 GEPA 在三种混合数据上学 Optimizable 任务：

- 和 Easy 混在一起时，GEPA 能把 16 道 Optimizable 题做到接近全对。
- 和 Impossible 或 Flaky 混在一起时，峰值只有 12/16。

这说明**坏题的信号会污染提示词，拖累对正常题的学习**，而不只是「浪费一些 rollout」。

作者还算了一笔账：Curator 最终只把 1,581 道训练题里的 75 道（4.7%）判为不可能或不稳。看起来不多，但在 16 道题的 minibatch 里随机抽，至少抽到一道这种题的概率约是 54%；而反思又是由失败驱动的，这些题失败得远比别的题多。附录的例子显示，一两次这样的失败就足以让 Reflector 写出一条过度泛化的规则，这条规则还能通过 minibatch 门控，同时让一道本来能做的题退步。

### 只看成败统计不够，得看轨迹

一个自然的问题是：要筛题，用成功率统计（类似课程学习）不就行了？作者在一个混合了 48 道 Easy、54 道 Optimizable、45 道 Impossible、21 道 Flaky 的数据集上对比：

| 方法 | 成功率 |
| --- | --- |
| GEPA | 66.2% |
| 只看成败历史的数值课程学习 | 62.5% |
| 只做任务筛选 | 67.4% |
| GEPA-Curator（筛选加成功检索） | 70.2% |

数值课程学习反而比 GEPA 还差。原因是 Flaky 题和正常的「能做但不稳」题在成败统计上长得一样，都是有成有败，只有读轨迹才能分清是评判或环境在捣乱，还是提示词真的有问题。

### WebArena 主结果

held-out 测试集成功率（五次运行均值）：

| 优化器模型 | 方法 | GitLab | Shopping | Shopping Admin | Reddit | 总体 |
| --- | --- | --- | --- | --- | --- | --- |
| Gemini 3.1 Pro | 种子提示词 | 78.2 | 73.5 | 65.2 | 72.6 | 72.4 |
| | GEPA | 82.1 | 83.8 | 71.5 | 77.6 | 78.7 |
| | GEPA-Curator | 84.6 | 85.8 | 73.1 | 85.0 | 82.1 |
| Claude Opus 5 | 种子提示词 | 79.6 | 73.9 | 67.7 | 71.3 | 73.1 |
| | GEPA | 82.5 | 80.5 | 72.9 | 81.9 | 79.5 |
| | GEPA-Curator | 83.1 | 86.5 | 80.3 | 88.2 | 84.5 |

按论文的说法，Curator 拿到的优化增益是 GEPA 的 1.54 倍（Gemini）和 1.78 倍（Opus）。Actor 是 gpt-oss-120b，minibatch 16，每个站点 5,000 次 rollout。

### 其他 agent 基准

| 优化器模型 | 方法 | ALFWorld | AppWorld Test-N | AppWorld Test-C | τ-bench |
| --- | --- | --- | --- | --- | --- |
| 无 | 种子提示词 | 66.9 | 8.9 | 5.6 | 52.0 |
| Gemini 3.1 Pro | GEPA | 82.4 | 38.0 | 27.8 | 75.4 |
| | ACE | 90.1 | 55.7 | 34.5 | 80.6 |
| | GEPA-Curator | 91.8 | 58.7 | 46.2 | 84.0 |
| Claude Opus 5 | GEPA | 95.8 | 52.9 | 32.5 | 82.9 |
| | ACE | 89.7 | 61.2 | 33.4 | 61.7 |
| | GEPA-Curator | 98.4 | 68.8 | 46.4 | 82.9 |

AppWorld 上的提升最明显，Test-C（挑战集）上两种优化器都把 GEPA 的分数提高了十几个点。τ-bench 在 Opus 下和 GEPA 打平。作者把这几个基准称为「更干净的环境」，说明筛选和成功检索的作用不只是去噪，也在提高反思本身的质量。

### 消融：两个部件互补

GitLab 子集上（200 道验证题）：GEPA 82.8%，只做任务筛选 84.2%，只做成功检索 84.7%，两者都开 88.6%。两样单开都只涨一两点，合起来涨将近 6 点。作者的解释是：筛选决定拿哪些失败去反思，检索决定反思时有什么参照，两者解决的是不同的问题。

### Curator 都把题判成了什么

在 1,581 道 GoBrowse 训练题上，Curator 的诊断分布是这样的：

- 95.3% 是正常题，1.1% 被判为不可能，3.6% 被判为评判不稳。
- 不可能题里，三分之二（66.7%）归因于 harness 或环境限制，比如需要的工具根本没提供；22.2% 是任务本身有问题。
- 评判不稳的题里，最大的原因是任务描述歧义或错误（46.2%），其次是 harness 或环境限制（29.2%）。后者的一个典型机制是：actor 声称「这个任务做不到」，宽松的评判就接受了。

成功检索方面，随着训练推进，失败案例能配上成功参照的比例从前期的 6.9% 涨到中后期的约 50%。在 554 道有历史成功可选的题里，Curator 在 17 道（3.1%）题上避开了可疑的成功而选了可信的那条，在 50 道（9.0%）题上明确判断现有成功都不可信而放弃。

### 套到 Meta-Harness 上

作者还把 Curator 套到 Meta-Harness 上（优化对象从提示词变成 harness 代码）：Curator 负责挑选父 harness 和一部分训练任务，并附上理由。结果提升比较温和：Math-RAG 总体准确率从 45.33% 到 46.33%，文本分类从 48.06% 到 51.04%，其中 USPTO 还略有下降。每种设置只跑了一次优化。

### 成本

精简版 Curator 做了三处改动：一次决定跳过几个 epoch 而不是每个 epoch 都问；只保留最近几次执行的完整轨迹，更早的压成摘要；单独保留一条完整成功轨迹，失败时总是附上。精简版在各基准上和完整版持平，AppWorld 上甚至更高（Test-N 67.1 对 58.7）。总成本上，WebArena 四站 GEPA 约 594 美元，精简版 Curator 约 777 美元；非 WebArena 基准上 GEPA 约 133 美元，ACE 约 769 美元，Curator 约 174 美元。

## 🔬 最有意思的部分

1. **「数据清洗」被重新发明了一遍，而且必须由 agent 来做。** 预训练和 SFT 时代我们早就知道数据质量比数量重要，但在经验驱动的自我改进里，脏数据的形态变了：不是乱码或重复，而是「这次失败是因为按钮坏了」。这种噪声只能读轨迹才看得出来，数值统计分不清，这正是数值课程学习输给 GEPA 的原因。
2. **成功轨迹的价值被低估了。** 大家做反思时习惯只看失败，因为失败才有「信息」。但这篇说明，一条可信的成功轨迹是最好的对照组：它把 Reflector 的任务从「猜错在哪」变成「对比哪里不一样」。我们日常 debug 也是这样，能复现一个好的版本，问题就解决了一半。
3. **评判噪声和 harness 缺陷会伪装成提示词问题。** 不可能题里三分之二是 harness 或环境的问题。换句话说，如果你用反思式优化调提示词，却发现提示词越改越长、规则越加越奇怪，很可能是 harness 少了个工具，而优化器在用提示词补这个窟窿。

## 🤔 我的判断

**定位：一个工程上非常对路的数据层补丁。它不改优化算法，只管喂给优化器的经验，收益稳定、成本可控，适合直接借鉴到任何反思式自我改进流程里。**

亮点：

1. **问题定义准。** 把「反思的输入质量」从「门控的输出质量」里拆出来，指出门控是事后的、本身也有噪声，这个论证很清楚。
2. **动机实验有说服力。** Easy、Optimizable、Impossible、Flaky 四类混合的实验，直接展示了坏题如何拖住好题的学习，还给出了 54% 的抽中概率估算。
3. **跳过是暂时的。** 这一点很容易被忽略但很重要：一道题今天学不到东西，不等于永远学不到，提示词变了以后要回头检查，也要监测已掌握的题会不会退步。
4. **成本分析做得实在。** 给出了具体美元数和精简版，说明这不是一个只在论文里成立的昂贵方案。

问题与局限：

- **Curator 自己也是 LLM 判断。** 「这道题是 harness 问题还是提示词问题」本身就可能判错，论文没有给出人工核对 Curator 诊断准确率的数据。
- **GEPA 被简化了。** 实验用的是去掉 Pareto 选择的贪心版 GEPA。作者说消融里差别不大，但这还是让「比 GEPA 高多少」的对比打了个折扣。
- **Meta-Harness 部分很初步。** 每种设置只跑了一次优化，提升一到三个点，还有一个数据集下降，证据比较薄。
- **Actor 只有 gpt-oss-120b。** 一个较便宜的开放模型。作者自己也说换更大的 actor 时成本比会变，至于收益会不会变，没有数据。
- **精简版在 AppWorld 上比完整版还高不少，论文没解释。** 这可能说明完整历史在某些环境里反而是干扰，值得进一步研究。

对工程的直接启发：

- **给自我改进流程加一个「这次失败值不值得学」的判断。** 哪怕只是一个简单的规则：同一个任务连续几次因为同一个外部错误失败，就先别拿它去改提示词。
- **保存可信的成功轨迹，反思时一起给。** 失败案例配一条同任务的成功轨迹，比单独看失败有效得多。注意要挑评判一致的成功，不要拿一次侥幸过关的当参照。
- **提示词越改越长时，先查 harness。** 如果优化器反复加「遇到 X 时尝试 Y」这类绕路规则，多半是工具或环境缺了什么。
- **被跳过的题要定期回查。** 包括已掌握的题，用来发现提示词改动带来的退步。

一句话收束：**反思式自我改进不缺反思能力，缺的是一个先判断「这次失败该不该算提示词的错」的环节，再加上一条值得对照的成功轨迹。**
