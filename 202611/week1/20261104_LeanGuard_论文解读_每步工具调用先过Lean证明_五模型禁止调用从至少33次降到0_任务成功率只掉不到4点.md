# 每步工具调用先过 Lean 证明：五模型禁止调用从至少 33 次降到 0，任务成功率只从 72.7% 掉到 68.9%

你有没有过这种体验：agent 的系统提示写满「禁止退款超过限额」「不能在未验证前改支付方式」，一到工具调用还是打穿了？提示词护栏是软的，模型一被间接注入或一着急完成任务，禁令就变成建议。真正要上工具的生产系统，迟早会问：**能不能在调用进环境之前，用可执行的形式化策略卡死，而且卡住之后还能修，而不是只会裸拒绝？**

Case Western Reserve / UT Austin 的 Sreehari Sankar、Debargha Ganguly、Vikash Singh 等人这篇 **LeanGuard: Lean-Verified Guardrails for Tool-Using Agents**（arXiv:2611.02332，HF Daily Papers）给出的答案是：用 Lean 4 在运行时检查每一次工具调用，fail-closed，并证明判定过程与 LeanLTL 语义等价。τ²-bench 上五个 Qwen 模型，无护栏时禁止类调用至少执行 33 次；LeanGuard 下禁止调用执行数为 0。任务成功率从 72.7% 到 LeanGuard 68.9%，加反馈到 70.9%。

## 核心摘要

LeanGuard（亦写作 LEANGUARD）把工具调用护栏做成 **Lean 4 运行时策略**：每次调用在进入环境前对照 Lean 策略检查，失败则关闭（fail-closed）；作者证明该判定与 LeanLTL 语义等价。策略语言覆盖 permits / requirements / forbids，并支持过去时算子 previous / once / since 与作用域。拦截后有两条恢复路径：一是把失败规则与自然语言提示反馈给模型；二是用 `guard_repair?` 元编程做证明引导的参数修复，无需再问模型。τ²-bench 五模型：无护栏禁止调用 ≥33 次，LeanGuard 为 0；任务成功 72.7%→68.9%（仅护栏）→70.9%（护栏+反馈，反馈相对无反馈 p=0.21）。DTap 上直接注入攻击成功率 57.9%→5.9%，间接 22.3%→3.8%；电信良性约 75% 不变，但只读部署下整体良性从 53.1% 掉到 12.5%。反馈让被拦调用 983→719、恢复动作 34→48，五模型中四模型任务成功高于裸拒绝。离线修复：252 次参数值拒绝里修成 88 次，中位耗时 2ms，多为退款与支付方式类。作者明确：响应文本伤害不在覆盖范围，部分纯文本攻击仍有约 30% 成功率。

## 🎯 为什么这件事值得写

工具调用安全长期卡在三层半吊子方案之间：

1. **提示词禁令**：便宜，但不是强制。
2. **外部正则 / JSON schema**：能卡格式，卡不住带历史依赖的业务策略（「自从上次验证以来不得改支付方式」）。
3. **事后审计**：能追责，拦不住当次危害。

LeanGuard 把护栏前置到**每一次工具调用之前**，用 Lean 给出可执行策略，并把「判定 ≡ LeanLTL 语义」写成证明义务。对做支付、退款、电信工单这类有状态工具的人，这比再写三段「你必须遵守」有用得多。

## 🏗️ 机制：Lean 策略挡在环境之前

### 运行时位置

```text
模型提议 tool call
    → LeanGuard 对照策略检查（Lean 4）
        → 通过：进入环境执行
        → 失败：fail-closed，走反馈或证明引导修复
```

关键性质：**fail-closed**。检查不过就不执行，不存在「先跑了再告警」。

### 策略语言

| 构件 | 作用 |
| --- | --- |
| permits | 允许什么 |
| requirements | 必须满足什么 |
| forbids | 禁止什么 |
| previous / once / since | 过去时时间算子 |
| scopes | 作用域，限制规则生效范围 |

过去时算子让策略能表达「曾经 / 自从…以来」这类依赖历史轨迹的约束，这正是纯 schema 验证最弱的地方。

### 语义承诺

判定过程被证明与 **LeanLTL** 语义等价：不是「我们觉得这个解释器大概对」，而是把决策对齐到线性时序逻辑的一条可陈述语义。这对审计与合规叙事很重要：护栏行为有形式化说明书。

### 两条恢复路径

| 路径 | 谁来修 | 输入 |
| --- | --- | --- |
| (a) 反馈 | 原模型 | 失败规则 + 自然语言 hint |
| (b) 证明引导修复 | `guard_repair?` 元编程 | 无需再问模型 |

(a) 适合策略违反可以靠改意图解决的情况；(b) 适合参数值明显可修正（退款金额、支付方式字段）且希望低延迟、不消耗模型上下文的情况。离线数据显示 (b) 中位 2ms。

## 🧪 关键证据

### τ²-bench：禁止调用清零，任务成功微降

五个 Qwen 模型：

| 条件 | 禁止类调用执行数 | 任务成功率 |
| --- | --- | --- |
| 无护栏 | ≥33 | 72.7% |
| LeanGuard | **0** | 68.9% |
| LeanGuard + 反馈 | **0**（护栏仍在） | 70.9% |

相对无护栏，仅护栏掉 3.8pp；加反馈回到 70.9%，反馈 vs 无反馈 p=0.21（差异未达常规显著，但点估计向好）。安全侧硬约束（禁止调用 = 0）与效用侧小幅代价同时出现，这是可部署护栏该有的形状。

### DTap：注入显著下降，只读部署有良性代价

| 设定 | 变化 |
| --- | --- |
| 直接注入 | 57.9% → 5.9% |
| 间接注入 | 22.3% → 3.8% |
| 电信良性 | ~75%，基本不变 |
| 整体良性（只读部署） | 53.1% → 12.5% |

前两行说明对工具调用通道上的注入，Lean 策略非常有效。最后一行是冷水：若以只读方式部署护栏，良性任务可能被大量误伤。电信场景良性大致持平，说明代价与策略/领域绑定，不能一概而论「加上就无损」。

### 反馈比裸拒绝更有用

| 指标 | 变化 |
| --- | --- |
| 被拦调用 | 983 → 719 |
| 恢复动作 | 34 → 48 |
| 任务成功 | 4/5 模型高于裸拒绝 |

把「你犯规了」写成失败规则 + NL hint，模型少撞墙、多改参数再试。这对产品体验几乎是必需：fail-closed 若只回一句 denied，成功率会无辜再掉一截。

### 离线证明引导修复

- 252 次参数值拒绝中修复 88 次
- 中位耗时 **2ms**
- 多数落在退款、支付方式类修正

88/252 说明修复不是万能，但在对的错误类型上又快又稳，适合做「模型改意图 + 元编程改参数」的分工。

### 明确不覆盖的攻击面

响应文本伤害仍不在范围内；部分纯文本攻击成功率仍约 30%。LeanGuard 卡的是**工具边界**，不是生成文本的全部安全问题。

## 🔬 最有意思的部分

1. **安全指标与效用指标拆开报。** 禁止调用归零是硬指标；任务成功 72.7→68.9→70.9 是软代价。很多护栏论文只报攻击成功率，不报良性掉多少；这篇两边都写了，包括只读部署良性 53.1→12.5 这种难看数字。
2. **恢复被当成一等公民。** 反馈路径与 `guard_repair?` 并列，避免「形式化护栏 = 只会拒绝」。中位 2ms 的参数修复，对支付类工具几乎是免费的。
3. **过去时算子对准真实业务。** forbids 加上 since/once，才能写「验证之前不许改支付方式」这种有状态政策；这比「工具名黑名单」更接近合规条文。
4. **语义等价证明抬高了讨论层级。** 护栏从「我们写了个拦截器」变成「判定对齐 LeanLTL」。即便工业团队不读证明细节，审计对话会轻松很多。

## 🤔 我的判断

**定位：工具调用路径上的形式化 fail-closed 护栏，带反馈与证明引导修复；是「提示词禁令」的硬替代，不是端到端安全银弹。**

亮点：

1. **禁止调用清零**，五个模型一致，安全结论硬。
2. **效用代价可控**（约 3.8pp），反馈还能补回一截。
3. **两条恢复路径**设计完整，离线修复毫秒级。
4. **诚实写清文本攻击仍剩约 30%**，以及只读部署良性大跌，避免过度承诺。

问题与局限：

- **不覆盖响应文本。** 社交工程、有害建议、泄露类文本攻击仍要靠其他层。
- **只读部署良性 53.1→12.5** 说明策略过严或部署模式选错时，可用性可以崩；策略工程本身仍是成本中心。
- **反馈相对无反馈 p=0.21**，点估计有益但统计上不硬，复制时别把 70.9% 当成稳赢。
- **修复覆盖 88/252**，多数在退款/支付方式；换到代码执行、邮件发送等动作空间，元编程修复率可能低得多。
- **策略仍要人写对。** Lean 保证的是「按策略执行且语义对齐」，不保证策略本身符合业务真实意图。
- **评测以 τ²-bench 与 DTap 为主**，更广工具生态与多 agent 编排下的组合策略仍待观察。

对工程的直接启发：

- **工具边界用强制策略，提示词只作补充。** 禁令写进 Lean（或同等可执行策略），不要只写进 system prompt。
- **Fail-closed 必须配恢复。** 至少给失败规则 + hint；对高频参数错误考虑无模型修复。
- **分开度量「攻击成功率」和「良性成功率」。** 尤其要测只读 / 强制执行等不同部署模式。
- **有状态政策用过去时算子建模**，不要指望单次 JSON schema。
- **文本出口另布防。** LeanGuard 之后仍需要响应侧过滤或人类复核，别以为工具拦完就结束。

一句话收束：**LeanGuard 不让模型「答应不调用」，而是让每一次调用在进环境前先过 Lean；禁止调用可以归零，但文本伤害和过严策略下的良性塌方，仍然要你自己接住。**
