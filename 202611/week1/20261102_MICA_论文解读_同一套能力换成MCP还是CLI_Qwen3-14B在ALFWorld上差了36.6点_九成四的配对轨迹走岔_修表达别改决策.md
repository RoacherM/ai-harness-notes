# 同一套能力换成 MCP 还是 CLI：Qwen3-14B 在 ALFWorld 上差了 36.6 点，九成四的配对轨迹走岔，修表达别改决策

你有没有过这种体验：给 agent 接同一批能力，一次包成 MCP 工具，一次包成命令行，跑出来的效果完全不像同一个东西。社区里「MCP 还是 CLI」的争论已经吵了大半年，一派说结构化 schema 更稳，一派说 shell 才是模型最熟的语言，各自都能拿出跑分。

问题是，这些对比几乎都不干净。换成 CLI 的时候，工具粒度变了，提示词变了，校验和执行脚手架也跟着变了，最后差出来的分数到底算谁的？**如果能力完全一样、执行路径完全一样，只换模型看到的那层表示，agent 的行为还会不会变？**

香港理工和中科院计算所的 **Matched Capabilities, Different Behaviors: A Controlled Study of MCP and CLI Interfaces for Language Agents**（arXiv:2610.34298）做的就是这个对照。看完我的感受是：接口不是一层透明的管道，它本身就是决策环境的一部分，而且大部分可修的毛病出在「把决定写出来」这一步，而不是「做什么决定」。

## 核心摘要

作者提出 MICA（Matched Interface Comparison and Analysis）：先给每个基准定义一份共享的语义动作契约（操作名加带类型的参数），再分别渲染成 MCP 工具和 CLI 命令，两边解码回同一个规范化语义动作后，走同一套校验、编译和执行。接口被拆成三块：能力怎么呈现（presentation）、模型怎么写出动作（realization，含响应协议和解码器）、执行反馈怎么回给模型（feedback）。在 ALFWorld、WebShop、ScienceWorld 三个环境、六个模型（Qwen3 4B/8B/14B/32B、DeepSeek-v4-Flash、Gemini-2.5-Flash）上，能力完全对齐的两种接口仍然在分数和 token 上拉开很大差距，方向还会随模型和环境翻转：Qwen3-14B 在 ALFWorld 上 MCP 比 CLI 低 36.6 分（20.1 对 56.7），在 WebShop 上反而高 4.9 分。2,004 对配对轨迹里有 1,889 对（94.3%）出现结构性分叉，而且多半在交互一开头就分了。三因子析因探针显示，「写出动作」这一块的局部影响最大，单项能让表达失败率差出 84.4 个百分点。据此作者提出 DART：先让模型选定并校验语义动作，把它锁成承诺，表达失败时只修写法、不重选动作。DART 在 Gemini-2.5-Flash 的六个基准乘接口设置里全部涨分，最多涨 9.0 分，MCP 下每题最多省 27.1k token。

## 🎯 为什么这件事值得写

已有的 MCP 与 CLI 对比大多是系统级的：同一个任务，一边是一堆 MCP 工具，一边是终端加脚本。作者指出这里有两个归因难题。

1. **系统级对比改的不止接口。** 工具粒度、提示词、公开信息、校验和执行脚手架经常一起变，分差没法算到「表示」头上。之前企业自动化方向的工作已经发现，能力怎么打包本身就能解释相当一部分差距。
2. **只看终点分数会把不同的路径压成一个数。** 同样的分数可能来自不同的语义选择、不同的表达失败和不同的成本；更麻烦的是，早期一个小差异会改写后面所有步骤的上下文。

所以要回答「表示本身有没有影响」，既要做语义对齐，又要做轨迹级归因。

## 🏗️ 机制：一份契约，两种渲染，三块可拆的接口

### 共享语义契约

每一步，基准定义一份契约：有哪些操作、每个操作的参数类型、当前状态下参数能取哪些值、以及它绑定到哪个原生动作。模型的动作被规范化成（操作，参数）对。两个提议只要操作相同、规范化后的参数等价，就算同一个语义动作。

MCP 把它渲染成带 schema 的具名工具（比如 `webshop__search`，参数 `query`）；CLI 渲染成注册过的命令（比如 `bench webshop search --query '...'`）。两边解码后进同一条「校验、编译、执行」路径。

### 三块接口

| 组件 | 含义 | MCP 侧 | CLI 侧 |
| --- | --- | --- | --- |
| 呈现 Φ | 能力怎么展示给模型 | 工具列表加 JSON schema | 命令和 flag 的说明 |
| 表达 R | 响应协议和解码器 | `<tool_call>` 里的 JSON | `<command>` 里的 argv，要求 POSIX 单引号 |
| 反馈 Ψ | 执行结果怎么回给模型 | 结构化结果 | 文本结果和错误提示 |

把这三块各取 MCP 或 CLI，就有 2×2×2 = 8 种组合。两种纯组合就是正常的 MCP 和 CLI，另外六种是「混搭」，用来在固定的决策点上测每块各自的主效应和交互效应。

### 第一个有后果的分叉点

每一步记一个交互签名：语义提议、失败在哪一层、执行结果、恢复状态。MCP 和 CLI 轨迹从同一起点出发，签名第一次不一致的那一步叫 t★。之前的公共前缀可以做严格的局部对比，之后两条轨迹各走各的历史和状态，用来观察差异怎么传下去。

### DART：先承诺，再表达，坏了只修表达

DART 用同一个模型分两步：

1. **选择阶段**只输出规范化的语义动作，并绑定当前契约版本；通过语义校验才成为承诺。
2. **表达阶段**把承诺写成 MCP 或 CLI 形式。只有解码结果和承诺的操作、每个参数都一致，且承诺在当前状态下仍然有效，才放行。
3. 如果表达失败但承诺仍有效，就发一次「保持承诺的修正」：带上失败的写法和公开报错，只许改引号、序列化、嵌套结构这类表达细节，不许改操作和参数。
4. 契约变了、承诺失效、或者调用预算不够，就交回普通重试策略。

触发范围也收得很窄：只在可重试、由策略造成、且确认环境状态没变的失败上启动。

## 🧪 关键证据

### 能力对齐，分数照样拉开，而且方向会翻

| 模型 / 环境 | 原生接口 | CLI | MCP | token（k/题，CLI / MCP） |
| --- | --- | --- | --- | --- |
| Qwen3-14B / ALFWorld | 62.7 | 56.7 | 20.1 | 241.9 / 296.8 |
| Qwen3-14B / WebShop | 54.9 | 59.5 | 64.4 | 83.1 / 48.1 |
| Qwen3-8B / ALFWorld | 31.3 | 44.8 | 35.1 | 292.4 / 356.5 |
| Gemini-2.5-Flash / ALFWorld | 67.2 | 56.7 | 67.2 | 120.0 / 113.8 |
| DeepSeek-v4-Flash / ALFWorld | 97.0 | 99.3 | 95.5 | 58.0 / 56.7 |
| DeepSeek-v4-Flash / ScienceWorld | 81.3 | 77.5 | 75.3 | 97.4 / 93.1 |

几点观察：

- **没有哪一种接口通吃。** Qwen3-14B 在 ALFWorld 上 CLI 大胜，在 WebShop 上 MCP 更好，而且 token 成本也同步翻转：ALFWorld 上 MCP 每题多花 54.9k，WebShop 上少花 35.0k。
- **越强的模型越不敏感。** DeepSeek-v4-Flash 在三个环境里两种接口差距都在几分之内；接口敏感主要出现在中小模型上。
- **原生接口经常不输。** 表里很多格子里，两种对齐接口都低于基准自带的文本接口，说明「对齐后的 MCP 和 CLI 谁更好」并不等于「换成任一种比原来好」。

### 接口改的不只是写法，还有选什么动作

即使成功解码，语义动作的分布也变了。WebShop 上 Qwen3-14B 用 MCP 时，`click` 的占比高了 6 个百分点，`search` 少了 6 个点。失败落在哪一层也不一样：WebShop 上 MCP 让六个模型的尝试级失败率都降了 1.1 到 8.9 个点，剩下的失败从 CLI 常见的表层解码错误，转移到后面的可用性和执行层。

恢复路径同样带着接口的烙印：WebShop 上 Qwen3-4B 失败后重试被接受的比例，CLI 是 50%，MCP 是 77%；之后完成任务的比例分别是 18% 和 34%。

附录里的例子很具体：同一个找衬衫的任务，CLI 版本模型写了 `--query 'men's dress shirts ...'`，`men's` 里的撇号把单引号提前闭合，解码报错；模型改成 `mens` 重试成功，但这次失败已经进了历史，后面走了不同的路，最后撞到步数上限。MCP 版本 JSON 里撇号没问题，一路做到成功。

### 局部效应很大，而且互相纠缠

在固定决策点上做 2×2×2 析因（温度 0.6 重复采样估分布）：

- **表达（R）的主效应最大。** 把表达从 MCP 换成 CLI，对表达失败率的影响在 ALFWorld/Qwen3-32B 上达到 84.4 个百分点，ScienceWorld/Qwen3-4B 上 72.9 个点。
- **交互项也不小。** WebShop/Qwen3-14B 的三阶交互项让「解码后被接受」的比例变化 37.8 个点。也就是说，某一块单独换成 CLI 是好是坏，要看另外两块是什么。

### 分叉很普遍，而且来得早

2,004 对配对轨迹里，1,889 对（94.3%）出现结构性分叉，首次分叉的平均步数集中在前几步。分叉原因里语义动作不同占大头，表达差异是第二来源。分叉后两条轨迹的 token、尝试次数和结局都各自分开。也有被后续交互「吸收」的情况：ScienceWorld 的种橘子任务，两边一开始对目标物的描述不同，环境弹出歧义选择，最后都选了 `choose-0`，都成功了。

### DART 的效果

只在 Gemini-2.5-Flash 上做，六个设置和协议对齐的 Base 一一配对：

| 环境 | CLI 分数变化 | MCP 分数变化 | CLI token 变化（k/题） | MCP token 变化（k/题） |
| --- | --- | --- | --- | --- |
| ALFWorld | +1.5 | +9.0 | −0.8 | −27.1 |
| WebShop | +0.8 | +4.4 | +4.8 | −11.2 |
| ScienceWorld | +6.7 | +5.3 | +1.6 | −4.3 |

触发后 71% 到 100% 在第一次表达时就被放行；进入「保持承诺的修正」的只有 4 次，其中 3 次一次修好。附录的 WebShop/CLI 例子里，第一次表达把 `18"x18"` 里的字面引号弄丢了，修正只改命令写法，保留了 `click` 和完整的目标值，然后顺利下单。

## 🔬 最有意思的部分

1. **「决策」和「表达」可以分开计费。** 这篇最有用的概念不是 MCP 好还是 CLI 好，而是把一个动作拆成「选什么」和「怎么写」。前者错了要重新想，后者错了只该改写法。普通重试把两者混在一起：一次引号错误之后，模型常常连动作都换了，于是轨迹被一个和决策无关的错误带偏。
2. **报错本身也是接口。** CLI 那条报错信息写得很详细（当前允许的操作、要求单引号、一行一个命令），但它进了历史以后，后续决策的上下文就和 MCP 那条不同了。反馈层不只决定能不能修好，还决定修好以后模型「记得」什么。
3. **强模型把接口差异吃掉了。** DeepSeek-v4-Flash 两种接口差距很小。这和我们日常的直觉吻合：对旗舰模型争 MCP 还是 CLI 意义有限，对中小模型或本地模型，接口设计可能比换模型更值钱。

## 🤔 我的判断

**定位：一份测量基础设施加一个很小但对路的控制器补丁。价值在于把「接口影响」从系统级口水战拉回到可归因的对照实验。**

亮点：

1. **对照做得干净。** 共享契约加共享运行时，把「能力不同」这个最大的混杂因素拿掉了，剩下的差异才能算到表示上。
2. **三块拆分有工程含义。** 呈现、表达、反馈分别对应工具描述、输出格式和错误回显，正好是 harness 里三个可以独立改的地方。
3. **DART 改动小、收益稳。** 不改模型、不加新能力，只在失败时把「重选动作」和「重写动作」分开，六个设置全涨，MCP 下还省 token。

问题与局限：

- **模型偏旧偏小。** 主实验是 Qwen3 系列加 DeepSeek-v4-Flash 和 Gemini-2.5-Flash，没有当前旗舰。结论里「接口敏感」的强度很可能主要来自中小模型。
- **环境偏玩具。** ALFWorld、WebShop、ScienceWorld 的动作空间小、参数简单，离真实的 MCP 生态（几十个工具、嵌套参数、长返回）和真实终端（管道、组合命令）都有距离。这里的 CLI 也是注册命令加 flag 的「结构化 CLI」，不是自由 shell。
- **DART 只测了一个模型，触发次数很少。** 只有 Gemini-2.5-Flash，进入修正分支的只有 4 次。分数提升很可能主要来自「先选后写」的两阶段本身，而不是修正分支；正文也没给 DART 结果的置信区间。
- **自然轨迹是温度 0 单次运行。** 配对轨迹的分叉统计很有说服力，但分数差里有多少是单次运行的偶然，没有多种子的估计。
- **历史截断不一样长。** ScienceWorld 只保留 8 个事件，这会放大早期失败对后续的影响方式，结论能不能迁移到长上下文 harness 不好说。

对工程的直接启发：

- **工具调用失败时，先判断是写法错还是决策错。** 解码失败、引号、schema 不符这类，应该把原动作和报错一起交回去只修写法，不要让模型从头再想下一步。
- **评测 harness 改动时固定能力、只换表示。** 想知道换 MCP 还是 CLI 值不值，至少做一组语义对齐的对照，否则分差里混着工具粒度和提示词的变化。
- **对中小模型，表达层的容错比工具数量更重要。** 比如 CLI 参数里允许 JSON 字符串、对引号做宽松解析，或者给 MCP 工具更扁平的参数结构，都可能比加工具更有用。
- **错误回显要克制。** 报错信息会长期留在历史里影响后续决策，写清楚怎么修就够了，不要把整份规则再贴一遍。

一句话收束：**MCP 和 CLI 之争的答案是「看模型、看环境」，但更有价值的发现是，agent 很多失败不是想错了，而是写错了，修写法的时候别顺手把决定也改了。**
