# 真实用户的改页面需求：最强模型平均过七成验收项，整题全过只有 26.4%，换个 harness 同一模型能差 19 点

你有没有过这种体验：让 coding agent 改一个页面，它回来说「已完成」，你一点开，按钮在，样式也对，可一点就不动；或者十条要求做了八条，剩下两条恰好是你最在意的。单看「做了多少」，它表现不错；看「能不能直接用」，它还差一截。

现在很多 Web 编码基准已经被 agent 跑满了。这篇论文开头就做了一个对照：在 WebCompass-edit 的 150 道题上，同一个 qwen3.7-plus，单次生成平均完成度 73.6%，换成 agentic 执行（能跑、能看、能改）就到了 95.1%，opus-4-8 更是 99.4%。**当 agent 能自己运行和检查时，旧考卷还剩多少区分度？真实用户的复合修改需求，agent 到底能交付几成？**

复旦、阿里巴巴 Token Hub、浙大、港中文等的 **Co-Design Bench: Multimodal Collaborative Coding Evaluation for Agentic Models**（arXiv:2610.35138）给出的回答是：平均验收项过了七成，整题全过只有四分之一。看完我的感受是：这份基准最值得借鉴的不是排行榜，而是它的验收流程，先判、再反驳、证据不够就作废。

## 核心摘要

Co-Design Bench 从 26,314 个真实用户编码会话的 39,325 条请求里去重得到 37,463 个候选，最后整理成 273 道题、2,331 条专家写的隐藏验收标准。两条赛道：多模态编辑（ME，100 题）做局部的视觉、结构和内容修改，可附带图片、音频、视频或文档；仓库编辑（RE，173 题）在多文件前端仓库里做跨组件、路由、状态和数据流的协同修改。每道题都有能跑起来的改前应用，所以不需要标准答案代码或目标截图。评测用「先判后驳」：固定的 agentic 裁判结合源码 diff、渲染页面和 Playwright 操作记录给每条标准判 PASS、PARTIAL 或 FAIL；另一个 LLM 校验员专门挑战 PASS 和 PARTIAL，查桩代码、硬编码、入口不可达和需求不符；视觉结论必须有截图，交互结论必须有浏览器操作日志，证据缺失直接中止评测。在统一的 Claude Code harness 下测了十个模型，最强的 gpt-6-astra 平均严格完成度 0.699，但只有 26.4% 的题全部通过；ME 上 41.0%，RE 上只有 17.9%。所有十个模型在涉及三四种修改类型的仓库题上都比一两种的题低。附录里换 harness 的实验显示，同一个 Qwen3.8-27B 在 RE 上用 opencode 拿 0.749，用 qwen-code 只有 0.560。

## 🎯 为什么这件事值得写

已有的 Web 编码基准大致三类：照着截图或视频重建页面（Design2Code、IWR-Bench 等），在页面上做预定义的编辑（WebCompass、MT-Web2Code、DesignBench），以及仓库级软件工程（SWE-bench M、SWE-Lancer）。作者对比下来，缺的是三样东西同时具备：

1. **任务来自真实用户会话。** 预定义编辑是从操作池里抽的，真实请求往往是几件事缠在一起。论文的例子是一个体育剪辑编辑器：限制片段数量和时长、缩放时保持时间轴锚点对齐、删除或拆分片段后要重新启用「添加」按钮。这三条互相依赖，不是三道独立的题。
2. **不依赖标准答案的验收。** 同一个需求有很多种合法实现，拿参考代码或目标截图比对会误杀。
3. **agent 能执行时的对抗式验证。** agent 会跑、会看，也就会「做出看起来完成了」的东西，裁判必须能识破。

## 🏗️ 机制：怎么造题，怎么验收

### 造题

- **恢复能跑的起点。** 从会话日志、仓库存档或 HTML 包里重建应用，必须通过依赖安装、构建、容器启动和 Playwright 渲染检查；依赖无法恢复的外部服务的题直接剔除。
- **挑请求、写标准。** 先做规范化（打包附件、澄清措辞），过滤掉环境受阻、不可执行和不是编辑的请求；剩下的按结构难度、可验证性，以及用户在会话里反复改口或回滚这类「历史失败信号」排序，再合并成有边界的会话片段。专家细化请求，写隐藏的逐条验收标准。
- **注意一点**：题目保留了会话里的修改目标，但评测的是一个固定请求，执行过程中不再模拟用户追加反馈。

### 两条赛道的构成

| 赛道 | 题数 | 验收标准 | 特点 |
| --- | --- | --- | --- |
| ME 多模态编辑 | 100 | 553 条，平均 5.5，最多 11 | 无附件 20、图片 4、视频 27、音频 32、文档 17 |
| RE 仓库编辑 | 173 | 1,778 条，平均 10.3，最多 46 | 173 题里 166 题需要多种修改类型 |

### 先判后驳

1. **取证与初判。** 在隔离环境里构建、渲染候选应用。固定的 agentic 裁判用源码 diff、渲染页面和 Playwright 轨迹逐条判分。证据要和结论匹配：源码只能证明静态属性，截图才能证明视觉要求，录下来的操作才能证明交互和它导致的状态。构建失败或 DOM 节点缺失，依赖渲染的标准一律作废；源码里有个事件处理函数，不能说明用户真能在界面上点到它。
2. **反驳。** 另一个 LLM 校验员拿到初判和证据，专门挑战 PASS 和 PARTIAL：有没有桩代码、硬编码输出、不可达入口、换个输入就坏、或者和请求对不上。
3. **证据审计。** 视觉结论没有成功渲染和截图、交互结论没有浏览器操作日志，评测直接中止，不进入汇总。
4. **失败归因（补充分析）。** 得分低于 0.8 且改前应用能正常启动时，另起一个「可解性探针」在隔离沙箱里尝试最小补丁（对拿不到的网络接口打桩，保留核心业务逻辑），把未满足的标准归为模型能力、环境受阻、混合原因或起点缺陷。原始分数和分母不改，只另外报告一份环境调整后的分数。

### 三个指标

- 严格完成度：每题里 PASS 的比例，再对题取平均。
- 分级完成度：PARTIAL 算半分。
- 全过率：所有标准都 PASS 的题占比。

三者满足 全过率 ≤ 严格完成度 ≤ 分级完成度。严格完成度和全过率之间的差，就是「做了一部分但没交付完」的那块。

## 🧪 关键证据

### 主结果（统一 Claude Code harness，3 小时、120 轮上限）

| 模型 | ME 严格 / 全过率 | RE 严格 / 全过率 | 合计严格 / 全过率 |
| --- | --- | --- | --- |
| gpt-6-astra | 0.754 / 41.0% | 0.667 / 17.9% | 0.699 / 26.4% |
| opus-5 | 0.695 / 30.0% | 0.642 / 11.6% | 0.661 / 18.3% |
| qwen3.8-max-0902 | 0.667 / 31.0% | 0.644 / 8.1% | 0.653 / 16.5% |
| qwen3.8-27b | 0.642 / 23.0% | 0.645 / 10.4% | 0.644 / 15.0% |
| kimi-k3 | 0.662 / 26.0% | 0.610 / 9.8% | 0.629 / 15.8% |
| gpt-5.6-sol | 0.583 / 20.0% | 0.627 / 11.0% | 0.611 / 14.3% |
| opus-4-8 | 0.593 / 16.0% | 0.575 / 6.9% | 0.581 / 10.3% |
| glm-5.3-flash | 0.538 / 18.0% | 0.594 / 6.4% | 0.573 / 10.6% |
| glm-5.2 | 0.572 / 16.0% | 0.564 / 5.8% | 0.567 / 9.5% |
| grok-4.6 | 0.467 / 6.0% | 0.536 / 6.9% | 0.511 / 6.6% |

- **覆盖率和交付是两回事。** 最强模型 73.6% 的题至少有一条没完全满足。RE 上全过率普遍只有个位数到十几。
- **两条赛道排名大体一致但有换位。** Spearman 相关 0.818；kimi-k3 从 ME 第四掉到 RE 第六，Qwen3.8-27B 从第五升到第二，在 RE 上 0.645 略高于 opus-5 的 0.642。作者也提醒这么小的差距不能说明一般意义上的模型优势。
- **花得多不等于做得好。** ME 上 gpt-6-astra 中位 32 轮、每题 1.24M token 拿 0.754；GLM-5.2 用 69 轮、7.29M token 只有 0.572。grok-4.6 最「省」，ME 上中位 14 轮，但分数也最低。

### 分组看难点

- **修改类型越多越难。** RE 里涉及一两种修改类型的题严格完成度 0.654，三四种的 0.591，差 6.3 个点，十个模型无一例外。有意思的是两组全过率差不多（9.1% 对 9.7%），但零分率从 0.9% 升到 5.8%。
- **文档题覆盖高、全过低。** ME 里文档附件题合并严格完成度最高（0.652），全过率却只有 18.2%，而无附件题是 37.0%。论文的收据例子要求一个数值在源文档、可编辑行和下游汇总之间保持一致，改对一处不难，处处一致才难。
- **功能实现最难交付。** 按主要能力分，功能实现类 126 题严格完成度最高（0.619），全过率最低（10.3%）。
- **agent 会自己找工具处理媒体。** 68.5% 的视频轨迹用了 OpenCV，ffmpeg 出现在 31.5% 的视频和 25.0% 的音频轨迹里，还有模型自己跑 Whisper、CLIP、OWLv2 这类预训练模型拿转写、分类分数或检测框。

### 裁判换了，排序不变

附录用 GLM-5.2、kimi-k3、Qwen3.8-27B 三个替代裁判重评 kimi-k3 和 Qwen3.8-27B 的输出，分级完成度最多变动 0.053，kimi-k3 在 ME 领先、在 RE 落后的格局在四种裁判下都成立。作者自己也说这是描述性的敏感度检查，不能证明裁判不变性。

### harness 换了，排序会变

附录 H 固定模型，换三个 harness（codex 0.142.0、opencode 1.18.13、qwen-code 0.21.11）：

| harness | ME kimi-k3 | ME Qwen3.8-27B | RE kimi-k3 | RE Qwen3.8-27B |
| --- | --- | --- | --- | --- |
| codex | 0.842 | 0.773 | 0.649 | 0.638 |
| opencode | 0.828 | 0.801 | 0.709 | 0.749 |
| qwen-code | 0.849 | 0.722 | 0.682 | 0.560 |

ME 上两个模型对 harness 的排序完全相反（Spearman −1.00）；RE 上 Qwen3.8-27B 最好和最差的 harness 差了 18.9 个点，两个模型谁领先也随 harness 翻转。作者的结论是：比较模型时要把模型和 harness 一起报，直接比模型就得固定 harness。

## 🔬 需要打折看的地方

1. **人工复核没给一致率。** 两位前端专家复核了 200 个任务与模型组合的逐条判分，但正文和附录里我没找到复核结果的具体数字（一致率、被推翻的比例）。对一份完全依赖 LLM 裁判的基准，这是最该给的数。
2. **反驳环节的效果没有量化。** 校验员推翻了多少 PASS、推翻得对不对，论文没有单独报告。
3. **生产裁判的型号没写清。** 敏感度实验把替代裁判和「production」配置对比，但生产配置具体用的是哪个模型，我在正文和附录里没找到。
4. **附录 H 的口径和主表对不上。** 同一个 kimi-k3 在 ME 上，主表严格 0.662、分级 0.718，附录 H 里是 0.842 左右，表头只写「平均完成率」，没说明是哪种口径，也可能是 prompt 或评测设置不同。读的时候只看相对变化比较稳妥。
5. **数据来源和参评方有关联。** 会话来自生产环境的编码产品，作者团队含阿里巴巴，参评模型和替代裁判里都有 Qwen 系列。作者在相关工作里也提到了裁判的自我偏好问题，但没有针对这一点做专门检查。
6. **固定请求不是真协作。** 名字叫 co-design，实际评测的是一次性给出的规范化请求，执行中没有用户反馈。和我们上周读的 RealCLI 比，它测的是「一次交付有多完整」，不是「边改边沟通」。

## 🤔 我的判断

**定位：一份面向前端修改的真实任务基准，最值钱的是验收协议，其次才是排行榜。**

亮点：

1. **证据必须和结论同类型。** 源码证明不了能点，截图证明不了能交互，没有证据就中止。这条规则直接针对 agent 最常见的「声称完成」问题，任何自建的验收 harness 都可以照搬。
2. **先判后驳。** 让另一个模型专门挑 PASS 的毛病，比让同一个裁判再看一遍更接近代码审查的做法。这和我们之前读的 HarnessVerification（独立的便宜 critic 比让 agent 自己再查一遍强）思路一致：通过要有人反对过才算数。
3. **把全过率和覆盖率并列报。** 七成和四分之一同时摆出来，比任何单一分数都更接近「能不能直接上线」。
4. **harness 敏感度实验很有说服力。** 同一个模型换 harness 差 19 个点、排序翻转，再次说明脱离 harness 谈模型能力意义有限。

问题与局限：

- 人工复核和反驳环节都缺定量结果，裁判可信度主要靠流程设计而不是数据。
- 273 道题、十个模型、单次运行，分组分析里不少格子只有几道题（图片附件题只有 4 道），细分结论要谨慎。
- 前端修改是很好的试验场，但验收标准依赖专家手写，扩展成本不低。

对工程的直接启发：

- **自家 agent 交付前加一道「证据审计」。** 每条完成声明都要附对应类型的证据：视觉改动附截图，交互改动附操作记录，没有就不算完成。
- **验收裁判至少分两步。** 一个判，一个专门找反例（桩代码、硬编码、入口不可达、换输入就坏）。
- **把复合需求拆成逐条可验的标准再交给 agent。** 修改类型一多分数就掉，说明 agent 在多处联动上容易漏，拆开写、逐条核对比一句话描述可靠。
- **评估模型时固定 harness，选 harness 时固定模型。** 两者混着比，结论可能是反的。

一句话收束：**agent 已经能把大部分要求做个七七八八，真正的门槛是把每一条都做完并且拿得出证据；考卷要难，验收更要严。**
